# Гонки, дедлоки, утечки и модель памяти

Конкурентный код ломается не так, как обычный. Обычный баг воспроизводится: подал тот же ввод, получил ту же ошибку. Конкурентный баг проявляется раз в тысячу запусков, только под нагрузкой, только на 16-ядерном сервере и никогда на твоём ноутбуке. Сервис неделю работает, а потом счётчик заказов «теряет» пару штук, или под пиковой нагрузкой все запросы встают, или память медленно растёт, пока под не убьют по OOM.

За этим стоят четыре класса проблем: **гонка данных** (data race), **состояние гонки** (race condition, логическая ошибка), **взаимоблокировка** (deadlock и её родственники livelock и starvation) и **утечка горутин**. Под всеми лежит **модель памяти Go**: формальные правила, когда запись одной горутины гарантированно видна другой.

На собесе этот урок даёт сразу несколько обязательных вопросов: «чем data race отличается от race condition», «что такое happens-before», «как найти утечку горутин», «как Go обнаруживает дедлок и почему не всегда». Хорошая новость: для каждой проблемы есть инструмент, и ты научишься ими пользоваться.

## Data race

**Гонка данных**: две горутины одновременно обращаются к одной ячейке памяти, хотя бы одна пишет, и между обращениями нет синхронизации. Формально из модели памяти Go: запись в ячейку конкурентна с другим чтением или записью той же ячейки, если только все обращения не атомарные (`sync/atomic`).

Самый частый пример:

```go
var n int
var wg sync.WaitGroup
for range 1000 {
	wg.Go(func() { n++ })
}
wg.Wait()
fmt.Println(n)
```

`n++` это три операции: прочитать `n`, прибавить 1, записать. Две горутины могут прочитать одно и то же значение, обе прибавят единицу и обе запишут, одно приращение потеряется. На маке с 10 ядрами пять запусков подряд дали 955, 939, 954, 950, 947. Иногда может выйти и 1000, поэтому «у меня работает» ничего не доказывает. А строго по модели памяти программа с гонкой вообще не обязана вести себя разумно.

Почему «теряются приращения» это ещё мягкий исход. Гонка в Go это не «неточный счётчик», а неопределённое поведение в сильном смысле:

- **компилятор** вправе считать, что без синхронизации переменную никто другой не меняет: держать её в регистре, переставлять записи, выносить чтение из цикла;
- **процессор** переупорядочивает операции с памятью, а записи сначала попадают в буфер ядра и видны другим ядрам позже;
- **составные значения** (строки, слайсы, интерфейсы, мапы) состоят из нескольких машинных слов. Гонка может дать «разорванное» значение: указатель от одной записи, длину от другой. Модель памяти Go прямо говорит, что это может привести к произвольной порче памяти. Здесь Go опаснее Java: там гонка не ломает безопасность памяти, а в Go может.

Для мап рантайм ловит часть гонок сам: конкурентная запись в обычную `map` из нескольких горутин даёт `fatal error: concurrent map writes`. Это не паника, `recover` её не перехватит, процесс просто умирает.

### Race detector

Главный инструмент: флаг `-race`.

```bash
go test -race ./...
go run -race .
go build -race -o app-race .
```

Компилятор вставляет проверку перед каждым обращением к памяти, а рантайм отслеживает, какие обращения упорядочены синхронизацией. Если находит два неупорядоченных обращения, печатает отчёт:

```text
==================
WARNING: DATA RACE
Read at 0x00c00019e038 by goroutine 8:
  main.main.func1()
      /tmp/r/main.go:12 +0x2c

Previous write at 0x00c00019e038 by goroutine 7:
  main.main.func1()
      /tmp/r/main.go:12 +0x3c

Goroutine 8 (running) created at:
  sync.(*WaitGroup).Go()
      .../src/sync/waitgroup.go:238 +0x6c
...
==================
Found 1 data race(s)
exit status 66
```

Читается снизу вверх по смыслу: два доступа (чтение и предыдущая запись) к одному адресу, в каких строках, и где были созданы обе горутины.

Что важно знать о детекторе:

- он находит только гонки, которые **реально произошли** в этом запуске. Код, который тесты не выполняют, он не проверит. Поэтому `-race` гоняют в CI на всех тестах, а иногда собирают с ним тестовый стенд под реалистичной нагрузкой;
- **ложных срабатываний не бывает**: если детектор сказал «гонка», она есть;
- цена: по документации память растёт в 5-10 раз, время в 2-20 раз. В продакшн такую сборку не катят.

### Как убрать гонку

1. **Мьютекс**: все обращения к общему состоянию под одним `sync.Mutex`.
2. **Атомики** для простых счётчиков и флагов: `atomic.Int64`, `atomic.Bool`, `atomic.Pointer[T]`.
3. **Не делить память вообще**: данными владеет одна горутина, остальные общаются с ней через каналы. Отсюда девиз Go: «не общайся через общую память, а делись памятью через общение».
4. **Неизменяемость**: значение, которое после публикации никто не меняет, можно читать из скольких угодно горутин. Публиковать его нужно через синхронизацию (канал, мьютекс, `atomic.Pointer`).

## Race condition

**Состояние гонки** это логическая ошибка: результат зависит от того, в каком порядке выполнились операции разных горутин. Гонки данных при этом может не быть совсем: каждая отдельная операция защищена.

```go
type Inventory struct {
	mu    sync.Mutex
	stock map[string]int
}

func (inv *Inventory) Left(item string) int {
	inv.mu.Lock()
	defer inv.mu.Unlock()
	return inv.stock[item]
}

// Плохо: проверка и списание в разных критических секциях
func (inv *Inventory) Reserve(item string, n int) bool {
	if inv.Left(item) < n { // 1. проверили: осталось 1, хватает
		return false
	}
	// <-- здесь другая горутина тоже проверила и тоже увидела 1
	inv.mu.Lock()
	inv.stock[item] -= n // 2. обе списали: остаток -1
	inv.mu.Unlock()
	return true
}
```

Race detector тут молчит: все обращения к мапе под мьютексом. Но 200 покупателей на 50 билетов дают 54 успешных покупки. Это паттерн **check-then-act** (он же TOCTOU, time of check to time of use): решение принимается по данным, которые к моменту действия устарели. Лечение: проверка и действие в **одной** критической секции.

Та же ошибка встречается в базах данных: `SELECT stock` и затем `UPDATE stock = stock - 1` в разных запросах. Там её решают условием в самом `UPDATE ... WHERE stock >= 1` или блокировкой строки, это будет в уроке про транзакции.

| | Data race | Race condition |
|---|---|---|
| Что это | неупорядоченный доступ к памяти, хотя бы одна запись | логическая ошибка из-за порядка операций |
| Уровень | память, модель памяти | бизнес-логика, инварианты |
| Ловит `-race` | да, если случилась в запуске | нет |
| Пример | `n++` из двух горутин | проверить остаток, потом списать |
| Лечение | мьютекс, атомики, каналы | укрупнить критическую секцию, атомарная операция «проверь и сделай» |

Одно может быть без другого. `n++` без мьютекса это и data race, и race condition. Check-then-act с мьютексами это race condition без data race. А гонка данных на флаге «показать отладочный баннер», где любой исход допустим, это data race без race condition (и всё равно баг по модели памяти).

## Deadlock

**Взаимоблокировка**: группа горутин ждёт друг друга, и никто не может продолжить. Для дедлока нужны четыре условия Коффмана одновременно: ресурс эксклюзивен, его держат и ждут другой, его нельзя отобрать, и есть цикл ожидания. Ломаешь любое, дедлока нет. На практике ломают цикл.

### Как Go обнаруживает дедлок

Если **все** горутины программы заблокированы, рантайм это видит: функция `checkdead` в планировщике проверяет, что не осталось ни одного потока, исполняющего Go-код, и программа падает:

```text
fatal error: all goroutines are asleep - deadlock!
```

Но это только **глобальный** дедлок. Если заблокированы 10 горутин, а одна (например, HTTP-сервер, ждущий соединений в сетевом поллере, или тикер) жива, рантайм молчит. В реальном сервисе так почти всегда: зависшие обработчики копятся, а процесс «работает». Это **частичный дедлок**, и ловят его по метрикам числа горутин, дампу стеков и профилю утечек (о нём ниже).

### Типичные дедлоки

**Отправка без получателя** в небуферизованный канал, когда читатель стоит дальше в той же горутине или ждёт чего-то ещё. Пример с `wg.Wait()` перед чтением из канала ты видел в прошлом уроке.

**Повторный захват мьютекса**. `sync.Mutex` не реентерабельный: горутина, которая уже держит его, на втором `Lock` заблокируется навсегда. Типичный случай: публичный метод под мьютексом вызывает другой публичный метод, который тоже берёт мьютекс. Решение: внутренние методы без блокировки (`fooLocked`), которые вызываются из публичных.

**Разный порядок захвата.** Классика с переводом денег:

```go
func Transfer(from, to *Account, amount int) {
	from.mu.Lock()
	defer from.mu.Unlock()
	to.mu.Lock() // горутина 1: держит A, ждёт B
	defer to.mu.Unlock()
	// ...
}
// горутина 1: Transfer(A, B, 10)
// горутина 2: Transfer(B, A, 20)  держит B, ждёт A  →  цикл
```

Лечение: **глобальный порядок захвата**. Всегда сначала берём счёт с меньшим ID, независимо от направления перевода. Цикл ожидания становится невозможен. Отдельный случай: перевод самому себе, `from == to`, тут даже упорядоченный захват возьмёт один мьютекс дважды. Это задача 2 домашки.

**Рекурсивный RLock.** `sync.RWMutex` запрещает повторный захват на чтение в одной горутине, и это ловушка с подвохом: в простом тесте всё работает (см. «Что выведет программа?»), а под нагрузкой зависает. Причина: если между двумя `RLock` пришёл писатель и встал в `Lock`, новые читатели ждут его, чтобы писатель не голодал. Писатель ждёт первого читателя, первый читатель ждёт сам себя на втором `RLock`.

Общие правила профилактики:

- не держи мьютекс, пока делаешь что-то долгое или внешнее: сетевой вызов, отправку в канал, вызов чужого колбэка;
- захватывай несколько мьютексов в одном фиксированном порядке;
- блокирующие ожидания делай с `ctx` или таймаутом, чтобы зависание превращалось в ошибку, а не в вечность.

## Livelock и starvation

**Livelock**: горутины не заблокированы, они активно работают, но прогресса нет. Аналогия: двое в коридоре одновременно шагают влево, потом одновременно вправо, и так бесконечно. В коде это бывает с повторными попытками без случайности:

```go
// Обе горутины крутятся вечно, если их тайминги совпадают
for {
	a.Lock()
	if b.TryLock() { // не вышло взять второй, отпускаем первый и пробуем снова
		break
	}
	a.Unlock()
	time.Sleep(time.Millisecond) // одинаковая пауза у обеих: снова столкнутся
}
```

Лечат случайной задержкой (jitter) и экспоненциальным откатом, а лучше вообще фиксированным порядком захвата, как с дедлоком. Тот же jitter применяют в ретраях HTTP-клиентов, чтобы тысяча клиентов после сбоя не ударила по серверу синхронно.

**Starvation (голодание)**: прогресс есть, но какая-то горутина годами не получает ресурс, потому что другие всё время успевают раньше. `sync.Mutex` в Go защищается от этого сам: если ожидающая горутина не может получить мьютекс дольше 1 мс, мьютекс переходит в **режим голодания** и передаётся строго по очереди ожидания (константа `starvationThresholdNs = 1e6` в `internal/sync/mutex.go`). Планировщик тоже борется с голоданием, это в следующем уроке.

## Утечки горутин

**Утечка горутины**: горутина, которая никогда не завершится, хотя работы у неё больше нет. Чаще всего она навсегда заблокирована: ждёт канал, который никто не прочитает или не закроет. Каждая такая горутина держит свой стек (от 2 КБ и больше) и всё, на что ссылается: буферы, ответы, соединения. Сборщик мусора её не соберёт: заблокированная горутина для него живая.

Утечки коварны тем, что программа от них не падает:

```go
func main() {
	ch := make(chan int)
	go func() {
		ch <- 1 // никто не прочитает
	}()
	time.Sleep(100 * time.Millisecond)
	fmt.Println("конец main")
}
```

Выведет `конец main` и спокойно завершится: когда `main` возвращается, программа заканчивается, не дожидаясь других горутин. Никаких ошибок. В сервисе, который живёт неделями, такая горутина на каждый запрос это рост памяти до OOM.

Классические источники утечек:

1. **Ранний выход при чтении результатов из небуферизованного канала.** Запустили N горутин, прочитали первую ошибку и вернулись. Оставшиеся N-1 горутин навсегда висят на отправке. Лечение: буфер на N, отмена через контекст или errgroup.
2. **Ожидание канала, который никто не закроет.** `for v := range ch` в воркере, а производитель забыл `close(ch)`.
3. **Нет отмены.** Горутина-генератор или стадия конвейера без `ctx.Done()` в `select`.
4. **Забытый `cancel`** не утечка горутины напрямую, но держит в памяти контекст и таймер.

### Как искать утечки

**Метрика числа горутин.** `runtime.NumGoroutine()` в метриках сервиса. Пила, которая со временем растёт и не возвращается, почти всегда утечка.

**Дамп стеков.** `net/http/pprof` даёт `/debug/pprof/goroutine?debug=2`: стеки всех горутин. Если 50 000 горутин стоят на одной и той же строке в `chan send`, ты нашёл место.

**Профиль утечек (Go 1.27).** В Go 1.26 появился экспериментальный, а в 1.27 стал штатным профиль `goroutineleak`. Рантайм использует сборщик мусора: если горутина заблокирована на примитиве (канал, мьютекс, `sync.Cond`), до которого не может дотянуться ни одна живая горутина, разблокировать её некому, значит, это утечка.

```go
func leak() {
	ch := make(chan int)
	go func() {
		ch <- 1 // никто никогда не прочитает
	}()
}

func main() {
	for range 3 {
		leak()
	}
	time.Sleep(50 * time.Millisecond)
	pprof.Lookup("goroutineleak").WriteTo(os.Stdout, 1)
}
// goroutineleak profile: total 3
// 3 @ 0x1020abf28 0x102046224 ...
// #	0x1020ff517	main.leak.func1+0x27	main.go:12
```

В сервисе тот же профиль доступен как `/debug/pprof/goroutineleak`. Детектор консервативный: если канал достижим через глобальную переменную или локальные переменные живой горутины, утечку он не увидит. Ложной тревоги нет, но и найти он может не всё.

**В тестах: goleak.** Библиотека `go.uber.org/goleak` сравнивает горутины до и после теста:

```go
func TestStart(t *testing.T) {
	defer goleak.VerifyNone(t)
	Start() // внутри запускает горутину, которая виснет на отправке
}
// --- FAIL: TestStart (0.44s)
//     leak_test.go:12: found unexpected goroutines:
//         [Goroutine 36 in state chan send, with x.Start.func1 on top of the stack:
//         ...
```

Для целого пакета пишут `func TestMain(m *testing.M) { goleak.VerifyTestMain(m) }`. Как она устроена внутри, ты повторишь в задаче 5 домашки: запомнить горутины, выполнить код, подождать, сравнить, напечатать стеки.

**В тестах: testing/synctest (Go 1.25).** `synctest.Test(t, f)` запускает `f` в «пузыре»: время внутри фейковое и прыгает вперёд, когда все горутины пузыря заблокированы, а в конце `Test` ждёт завершения **всех** горутин пузыря. Если какая-то заблокирована навсегда, тест падает с `deadlock: ... blocked goroutines remain`. Так тесты этого модуля и проверяют твои решения на утечки.

```go
func TestWaitReadyTimeout(t *testing.T) {
	synctest.Test(t, func(t *testing.T) {
		ctx, cancel := context.WithTimeout(t.Context(), 30*time.Second)
		defer cancel()
		start := time.Now()
		err := WaitReady(ctx, func() bool { return false })
		if !errors.Is(err, context.DeadlineExceeded) {
			t.Fatalf("err = %v", err)
		}
		t.Log(time.Since(start)) // 30s фейкового времени, тест идёт миллисекунды
	})
}
```

## Модель памяти и happens-before

Вернёмся к вопросу, который стоит под всем уроком: когда запись одной горутины **гарантированно** видна другой? Интуитивный ответ «когда запись уже случилась» неверен. Процессор держит записи в буфере ядра, кеши разных ядер синхронизируются не мгновенно, компилятор переставляет независимые операции. Без явной синхронизации у разных горутин может быть разная картина памяти.

Модель памяти Go отвечает через отношение **happens-before** (в документе «synchronized before», «происходит раньше»): если событие A происходит раньше B, то B гарантированно видит все эффекты A. Внутри одной горутины порядок совпадает с порядком в коде. Между горутинами порядок создают только синхронизирующие операции:

| Операция | Что гарантирует |
|---|---|
| `go f()` | всё до оператора `go` видно в начале `f` |
| выход из горутины | **ничего**: завершение горутины ни с чем не синхронизировано, нужен канал, `WaitGroup` или мьютекс |
| отправка в канал | происходит раньше, чем завершится соответствующее получение |
| `close(ch)` | происходит раньше получения нулевого значения из-за закрытия |
| получение из небуферизованного канала | происходит раньше, чем завершится соответствующая отправка |
| k-е получение из канала ёмкостью C | происходит раньше, чем завершится (k+C)-я отправка (поэтому канал работает как семафор) |
| `mu.Unlock()` (n-й) | происходит раньше, чем вернётся следующий `mu.Lock()` |
| `once.Do(f)` | завершение `f` происходит раньше возврата любого `once.Do(f)` |
| атомарные операции | если атомарная операция B увидела эффект A, то A произошла раньше B; все атомики выглядят как выполненные в одном последовательном порядке |

Отношение транзитивно: если A раньше B (в одной горутине), B раньше C (через канал), а C раньше D (в другой горутине), то D видит A. Именно поэтому работает обычный приём «заполнил структуру, отправил указатель в канал, получатель читает поля»: все записи в поля в коде стоят до отправки, а отправка раньше получения.

Главная гарантия называется **DRF-SC**: если в программе нет гонок данных, она ведёт себя так, будто все горутины по очереди выполняются на одном процессоре. Поэтому на практике модель памяти сводится к одному правилу: **убери гонки данных, и можешь рассуждать о программе как о последовательной**. Модель памяти Go формально переписали в версии 1.19, тогда же атомики получили явную последовательно согласованную семантику.

Пример из официального документа:

```go
var a string
var done bool

func setup() {
	a = "hello, world"
	done = true
}

func main() {
	go setup()
	for !done { // гонка данных на done
	}
	print(a)
}
```

Здесь две проблемы. Даже если `main` увидит `done == true`, ничто не гарантирует, что он увидит и запись в `a`: может напечатать пустую строку. И хуже: ничто не гарантирует, что `main` вообще когда-нибудь увидит изменение `done`, компилятор вправе прочитать его один раз до цикла. На моём маке эта программа печатает `hello, world`, но это везение, а не гарантия. Правильно: `done` сделать `atomic.Bool` (тогда запись `a` раньше `done.Store(true)`, а `done.Load()` в `main` её увидит) или вообще ждать канал.

::: hood Как работает race detector
Детектор построен на ThreadSanitizer, той же библиотеке, что используется для C/C++ в Clang. С `-race` компилятор вставляет перед каждым чтением и записью памяти вызов в рантайм детектора, а синхронизирующие операции (каналы, мьютексы, `WaitGroup`, атомики, `go`) сообщают детектору о новых рёбрах happens-before.

```text
для каждой горутины:  векторные часы  [g1: 15, g2: 7, g3: 40 ...]
для каждых 8 байт памяти: теневые ячейки (shadow memory)
    последние обращения: кто (горутина), когда (её часы), чтение или запись
```

При обращении к памяти детектор сравнивает его с запомненными обращениями к тем же байтам. Если одно из них запись и по векторным часам нельзя сказать, что одно произошло раньше другого, это гонка. Отсюда оба главных свойства: детектор не даёт ложных срабатываний (он проверяет именно happens-before) и видит только реально выполненные обращения. Теневая память и проверки и есть те самые «память ×5-10, время ×2-20».
:::

::: trap Копирование структуры с мьютексом
```go
type Stats struct {
	mu   sync.Mutex
	hits int
}

// Плохо: value receiver копирует Stats вместе с мьютексом.
// Каждый вызов блокирует свою копию, защиты нет, и инкремент теряется.
func (s Stats) Inc() {
	s.mu.Lock()
	s.hits++
	s.mu.Unlock()
}
```

```go
// Хорошо: pointer receiver, мьютекс один на всех
func (s *Stats) Inc() {
	s.mu.Lock()
	defer s.mu.Unlock()
	s.hits++
}
```
`go vet` ловит копирование мьютексов проверкой `copylocks`. Структуру с `sync.Mutex`, `sync.WaitGroup` и атомиками после первого использования не копируют.
:::

::: trap Рекурсивный RLock
```go
// Плохо: Total держит RLock и зовёт Get, который снова берёт RLock.
// Работает, пока не придёт писатель между двумя RLock: тогда дедлок.
func (c *Cache) Get(k string) int {
	c.mu.RLock()
	defer c.mu.RUnlock()
	return c.m[k]
}

func (c *Cache) Total(keys []string) (sum int) {
	c.mu.RLock()
	defer c.mu.RUnlock()
	for _, k := range keys {
		sum += c.Get(k) // второй RLock в той же горутине
	}
	return sum
}
```

```go
// Хорошо: внутренний метод без блокировки, блокирует только публичный
func (c *Cache) getLocked(k string) int { return c.m[k] }

func (c *Cache) Total(keys []string) (sum int) {
	c.mu.RLock()
	defer c.mu.RUnlock()
	for _, k := range keys {
		sum += c.getLocked(k)
	}
	return sum
}
```
:::

```go
// Плохо: data race, цикл может никогда не закончиться
var stop bool

		work()
	}

```

```go

```

## Что выведет программа?

```go
var mu sync.Mutex
mu.Lock()
fmt.Println("захватили")
mu.Lock()
fmt.Println("захватили снова")
```

<Predict :options="['захватили, затем захватили снова', 'захватили, затем fatal error: all goroutines are asleep - deadlock!', 'паника: мьютекс уже захвачен', 'программа зависнет без сообщений']" :correct="1">

`sync.Mutex` не реентерабельный: второй `Lock` в той же горутине ждёт сам себя. Других горутин нет, поэтому рантайм видит глобальный дедлок и падает с `fatal error: all goroutines are asleep - deadlock!`. Если бы где-то жила ещё одна горутина (например, HTTP-сервер), программа просто зависла бы без сообщений.

</Predict>

```go
var mu sync.RWMutex
mu.RLock()
mu.RLock()
fmt.Println("ok")
```

<Predict :options="['ok', 'fatal error: all goroutines are asleep - deadlock!', 'паника: recursive read lock']" :correct="0">

Выведет `ok`: читателей может быть сколько угодно, и пока писатель не ждёт, второй `RLock` проходит. Поэтому рекурсивный `RLock` и опасен: в тестах всё зелёное, а под нагрузкой появляется писатель между двумя `RLock`, и всё встаёт (смотри «граблю» выше). Документация `sync.RWMutex` прямо запрещает рекурсивный захват на чтение.

</Predict>

```go
func main() {
	m := map[int]int{}
	var wg sync.WaitGroup
	for i := range 100 {
		wg.Go(func() { m[i] = i })
	}
	wg.Wait()
	fmt.Println(len(m))
}
```

<Predict :options="['100', 'меньше 100', 'fatal error: concurrent map writes (скорее всего)', 'паника, которую можно перехватить recover']" :correct="2">

Рантайм мап проверяет флаг «идёт запись» и, заметив конкурентную запись, валит процесс с `fatal error: concurrent map writes`. Это именно fatal error, `recover` не поможет. Проверка не гарантирована (если записи случайно не пересеклись, может и напечатать 100), но в трёх запусках из трёх у меня было падение. Правильно: мьютекс вокруг мапы или `sync.Map` для специфических сценариев.

</Predict>

::: interview
<details><summary>Чем data race отличается от race condition?</summary>

Data race: два конкурентных доступа к одной ячейке памяти, хотя бы один на запись, без happens-before между ними. Это проблема уровня памяти, её ловит `-race`, по модели памяти поведение программы непредсказуемо. Race condition: логическая ошибка, когда результат зависит от порядка операций разных горутин (check-then-act). Может быть без data race, если каждая операция защищена, но проверка и действие в разных критических секциях. `-race` её не ловит. Лечится укрупнением критической секции или атомарной операцией «проверь и сделай».

</details>
<details><summary>Как работает race detector и какие у него ограничения?</summary>

Основан на ThreadSanitizer: компилятор инструментирует обращения к памяти, рантайм ведёт векторные часы горутин и теневую память с последними доступами, синхронизация добавляет рёбра happens-before. Гонка: два доступа без порядка, хотя бы один запись. Ложных срабатываний нет, но находит только гонки, случившиеся в этом запуске, поэтому важно покрытие тестами. Дорогой: память ×5-10, время ×2-20, в продакшн не используют.

</details>
<details><summary>Что такое happens-before? Приведи синхронизирующие операции.</summary>

Отношение частичного порядка: если A happens-before B, B видит все эффекты A. Внутри горутины это порядок в коде. Между горутинами: `go` раньше старта горутины; отправка в канал раньше завершения получения; закрытие раньше получения нуля из-за закрытия; получение из небуферизованного раньше завершения отправки; k-е получение из канала ёмкости C раньше (k+C)-й отправки; `Unlock` раньше следующего `Lock`; `once.Do(f)`: завершение `f` раньше любого возврата `Do`; атомики последовательно согласованы. Выход горутины ни с чем не синхронизирован. Без гонок данных программа ведёт себя последовательно согласованно (DRF-SC).

</details>
<details><summary>Как Go обнаруживает дедлок? Всегда ли?</summary>

Только глобальный: если не осталось ни одного потока, выполняющего Go-код, и все горутины заблокированы, рантайм падает с `fatal error: all goroutines are asleep - deadlock!`. Частичный дедлок (часть горутин ждёт друг друга, а сервер или тикер живы) не обнаруживается. Его ищут по метрике числа горутин, дампу `/debug/pprof/goroutine?debug=2`, а с Go 1.27 профилем `goroutineleak`.

</details>
<details><summary>Как избежать дедлока при захвате нескольких мьютексов?</summary>

Захватывать их всегда в одном глобальном порядке (например, по ID объекта), тогда цикл ожидания невозможен. Не держать мьютекс во время внешних вызовов и отправки в каналы. Использовать `TryLock` с откатом и случайной задержкой только как крайний вариант: легко получить livelock. Для ожиданий использовать контекст с таймаутом.

</details>
<details><summary>Что такое утечка горутин? Как её найти и предотвратить?</summary>

Горутина, которая никогда не завершится, обычно навсегда заблокированная на канале. Держит стек и всё, на что ссылается, GC её не соберёт. Причины: отправка в канал, который никто не читает (ранний выход из цикла чтения результатов), `range` по каналу, который никто не закроет, отсутствие отмены. Поиск: рост `runtime.NumGoroutine()`, pprof-профиль `goroutine`, профиль `goroutineleak` (Go 1.27), в тестах `goleak` и `testing/synctest`. Профилактика: у каждой горутины понятное условие завершения, `ctx` в каждом блокирующем `select`, буфер на всех писателей там, где читатель может уйти раньше.

</details>
<details><summary>Чем livelock отличается от deadlock и starvation?</summary>

Deadlock: все участники заблокированы и ждут друг друга, CPU не тратится. Livelock: участники активны, постоянно меняют состояние в ответ друг на друга, но прогресса нет (одинаковые повторные попытки); лечится случайной задержкой. Starvation: система в целом прогрессирует, но конкретная горутина долго не получает ресурс. `sync.Mutex` после 1 мс ожидания переходит в режим голодания и отдаёт мьютекс строго по очереди.

</details>
<details><summary>Безопасна ли map для конкурентного использования?</summary>

Нет. Конкурентные чтения безопасны, но любая запись одновременно с другим доступом это гонка. Рантайм часто ловит конкурентную запись и аварийно завершает процесс `fatal error: concurrent map writes`, которую нельзя перехватить `recover`. Защищают мьютексом (`sync.RWMutex` при преобладании чтений) или используют `sync.Map` для специфических случаев: ключи пишутся один раз и много читаются, или разные горутины работают с непересекающимися ключами.

</details>
<details><summary>Почему цикл `for !done {}` с обычной bool-переменной некорректен?</summary>

Это гонка данных: нет happens-before между записью и чтением. Компилятор вправе прочитать `done` один раз и крутить бесконечный цикл, а даже увидев `true`, горутина не обязана видеть другие записи, сделанные до него. Правильно: `atomic.Bool` или ожидание закрытия канала. Плюс активное ожидание жжёт CPU, канал лучше и по этой причине.

</details>
:::
