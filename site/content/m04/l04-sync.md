# Пакет sync и atomic

Каналы хороши, когда данные **переходят** из рук в руки. Но часто данные просто **лежат**, и их читают и меняют многие горутины: кеш, счётчик запросов, мапа сессий, конфиг. Для такого общего состояния есть пакет `sync` (мьютексы, однократная инициализация, пулы) и `sync/atomic` (атомарные операции над числами и указателями).

Правило из вики Go: канал, когда передаёшь владение данными или координируешь горутины; мьютекс, когда охраняешь состояние. На собесе спрашивают устройство `Mutex` и режим голодания, разницу с `RWMutex`, двойной `Lock`, `Once` при панике, когда нужна `sync.Map` и почему `atomic` быстрее мьютекса.

## Гонка данных: от чего защищаемся

**Гонка данных (data race)**: две горутины обращаются к одной переменной одновременно, хотя бы одна пишет, и между обращениями нет синхронизации. Результат такой программы в Go не определён: потерянные обновления, разорванные значения, повреждённая мапа.

```go
count := 0
var wg sync.WaitGroup
for range 1000 {
	wg.Go(func() { count++ })
}
wg.Wait()
fmt.Println(count) // меньше 1000, каждый раз по-разному
```

`count++` это три шага: прочитать, прибавить, записать. Две горутины читают 41, обе пишут 42, одно увеличение потеряно. Детектор `-race` ловит такие места во время выполнения. Подробно гонки и модель памяти разберём в отдельном уроке модуля.

## Mutex

`sync.Mutex` это взаимное исключение: внутри `Lock()`...`Unlock()` в каждый момент находится не больше одной горутины.

```go
type Counter struct {
	mu sync.Mutex
	n  map[string]int
}

func (c *Counter) Inc(key string) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.n[key]++
}
```

Правила, которые стоит сделать рефлексом:

- **Нулевое значение готово к работе.** `var mu sync.Mutex` уже незахваченный мьютекс, конструктор не нужен.
- **`defer mu.Unlock()` сразу после `Lock()`.** Тогда ранний `return` или паника не оставят мьютекс захваченным навсегда.
- **Мьютекс рядом с данными.** Поле `mu` кладут прямо над полями, которые оно защищает, это соглашение читается сразу.
- **Методы с указателем-получателем.** Структура с мьютексом не должна копироваться (ниже ловушка).
- **Критическая секция минимальна.** Внутри только работа с общими данными. Сетевые запросы, запись в базу и вообще всё медленное держи снаружи.

Мьютекс в Go **не реентерабельный**: если горутина уже держит его, повторный `Lock` в той же горутине заблокирует её навсегда. В Java `synchronized` реентерабелен, поэтому вопрос любят на собесах тех, кто пришёл из Java. Чем именно это кончится, разберём в задаче в конце урока. В реальном коде это выглядит как метод `A`, который берёт мьютекс и вызывает метод `B`, который тоже берёт тот же мьютекс. Лечат разделением: публичные методы берут лок, приватные `bLocked()` предполагают, что лок уже взят.

Ещё два факта из документации. Захваченный мьютекс **не привязан к горутине**: разрешено захватить в одной и освободить в другой (так, например, передают «право на секцию»). А `Unlock` незахваченного мьютекса это ошибка времени выполнения. Какая именно и можно ли её перехватить через `recover`, проверь в задаче в конце урока.

Есть и `TryLock() bool` (с Go 1.18), но документация предупреждает: правильные применения редки, чаще это признак проблемы в дизайне.

::: hood Как устроен sync.Mutex
Вся структура это два поля: `state int32` и `sema uint32`. В `state` упакованы биты «захвачен», «есть разбуженный ожидающий», «режим голодания» и счётчик ожидающих. Реализация лежит в `internal/sync/mutex.go`.

**Быстрый путь.** `Lock` пытается одной атомарной операцией CompareAndSwap поменять `state` с 0 на «захвачен». Получилось, и всё, никаких системных вызовов. Поэтому незанятый мьютекс очень дешёвый.

**Медленный путь.** Если занят, горутина сначала немного **крутится** (spinning): несколько активных проверок, вдруг владелец сейчас отпустит (только на многоядерной машине и при строгих условиях). Не повезло, засыпает на семафоре рантайма `sema`.

**Нормальный режим и режим голодания.** В нормальном режиме разбуженная горутина не получает мьютекс автоматически, она **соревнуется** с только что пришедшими горутинами, которые уже работают на процессоре и чаще выигрывают. Это даёт высокую пропускную способность, но старый ожидающий может проигрывать снова и снова. Если горутина ждёт дольше **1 мс** (`starvationThresholdNs = 1e6`), мьютекс переходит в **режим голодания**: владение передаётся напрямую первому в очереди, новые горутины не пытаются захватить и встают в хвост. Как только очередь рассосалась (или последний ждал меньше 1 мс), мьютекс возвращается в нормальный режим. Компромисс: пропускная способность в обычной жизни и гарантия отсутствия вечного голодания под нагрузкой.

С точки зрения модели памяти n-й `Unlock` «синхронизируется до» m-го `Lock` для любых n меньше m. Поэтому всё, что записано под мьютексом, видно следующему владельцу.
:::

## RWMutex: много читателей, один писатель

`sync.RWMutex` разделяет доступ на чтение и запись:

- `RLock`/`RUnlock`: сколько угодно читателей одновременно;
- `Lock`/`Unlock`: писатель один, и в это время нет ни читателей, ни других писателей.

```go
type Config struct {
	mu   sync.RWMutex
	data map[string]string
}

func (c *Config) Get(k string) string {
	c.mu.RLock()
	defer c.mu.RUnlock()
	return c.data[k]
}

func (c *Config) Set(k, v string) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.data[k] = v
}
```

Помогает, когда чтений намного больше, чем записей, **и** секция чтения не микроскопическая. На коротких секциях обычный `Mutex` бывает не медленнее. Выбирай по бенчмарку.

Важная деталь из документации: если писатель вызвал `Lock` и ждёт, **новые** `RLock` блокируются, пока писатель не получит и не отпустит замок. Это защита писателя от голодания. Следствие: рекурсивный `RLock` запрещён, и повысить `RLock` до `Lock` нельзя.

::: trap Рекурсивный RLock
Плохо: публичный метод под `RLock` вызывает другой публичный метод, который тоже берёт `RLock`.

```go
func (c *Cache) Get(k string) Item {
	c.mu.RLock()
	defer c.mu.RUnlock()
	return c.items[k]
}

func (c *Cache) GetMany(keys []string) []Item {
	c.mu.RLock()
	defer c.mu.RUnlock()
	var out []Item
	for _, k := range keys {
		out = append(out, c.Get(k)) // второй RLock в той же горутине
	}
	return out
}
```

В тестах работает годами. А в продакшне однажды писатель вызывает `Lock` ровно между внешним и внутренним `RLock`: внутренний `RLock` ждёт писателя, писатель ждёт внешнего читателя, который ждёт внутреннего. Взаимная блокировка, зависящая от тайминга, худший вид бага.

Хорошо: внутренняя версия без блокировки, которая требует, чтобы лок уже был взят.

```go
func (c *Cache) getLocked(k string) Item { return c.items[k] } // вызывать под c.mu
```
:::

## Once, OnceFunc, OnceValue

`sync.Once` гарантирует, что функция выполнится **ровно один раз**, сколько бы горутин ни вызвали `Do` одновременно. Остальные вызовы ждут, пока первый закончит, и после этого видят все его записи.

```go
var (
	dbOnce sync.Once
	db     *sql.DB
)

func DB() *sql.DB {
	dbOnce.Do(func() {
		db = mustOpen(os.Getenv("DATABASE_URL"))
	})
	return db
}
```

Две тонкости, обе из документации `Once.Do`:

- Если `f` внутри `Do` снова вызывает `Do` того же `Once`, это дедлок: `Do` не вернётся, пока не вернётся `f`.
- Если `f` **паникует**, `Once` считает, что она отработала. Повторных попыток не будет.

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var once sync.Once
	for i := range 3 {
		func() {
			defer func() { recover() }()
			once.Do(func() {
				fmt.Println("init", i)
				panic("сбой")
			})
		}()
	}
	fmt.Println("готово")
}
```

<Predict :options="['init 0, init 1, init 2, готово', 'init 0, готово', 'готово', 'init 0 и падение']" :correct="1">

Первый `Do` печатает `init 0` и паникует, `recover` в обёртке её гасит. Для `Once` вызов «состоялся», и следующие два `Do` ничего не делают. Итог: `init 0`, `готово`. Если инициализация может упасть и её нужно повторять, `Once` не подходит: нужен мьютекс и флаг «успешно».

</Predict>

С Go 1.21 есть обёртки, которые закрывают типичные сценарии без отдельной переменной `Once`:

- `sync.OnceFunc(f) func()`: функция, которая вызовет `f` только при первом вызове;
- `sync.OnceValue(f) func() T`: вычислит значение один раз и будет возвращать его;
- `sync.OnceValues(f) func() (T, error)`: то же для пары значение + ошибка.

```go
var config = sync.OnceValues(func() (*Config, error) {
	return loadConfig("config.yaml")
})

func handler() {
	cfg, err := config() // файл читается один раз, ошибка тоже запоминается
	// ...
}
```

И у них другая семантика паники: если `f` паникует, **каждый** вызов обёртки паникует тем же значением. Сбой не прячется.

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	calls := 0
	get := sync.OnceValue(func() int {
		calls++
		return 42
	})
	fmt.Println(get(), get(), calls)

	boom := sync.OnceFunc(func() {
		calls++
		panic("сбой")
	})
	for range 2 {
		func() {
			defer func() { fmt.Println("recover:", recover()) }()
			boom()
		}()
	}
	fmt.Println("calls:", calls)
}
```

<Predict :options="['42 42 1, recover: сбой, recover: <nil>, calls: 2', '42 42 1, recover: сбой, recover: сбой, calls: 2', '42 42 2, recover: сбой, recover: сбой, calls: 4', '42 42 1, recover: сбой, recover: сбой, calls: 3']" :correct="1">

`OnceValue` вызвал функцию один раз (`calls` стал 1) и вернул 42 дважды. `OnceFunc` вызвал `f` один раз (`calls` стал 2), а второй вызов `boom()` не запускает `f` заново, но **повторяет панику** с тем же значением. Поэтому оба `recover` печатают `сбой`, а итоговый `calls` равен 2. Сравни с `Once.Do`, где второй вызов молча ничего не делал.

</Predict>

## Cond: ожидание условия

`sync.Cond` это место, где горутины ждут, пока станет истинным какое-то условие над общими данными. Он всегда работает в паре с мьютексом.

- `c.Wait()`: атомарно отпускает мьютекс и засыпает; проснувшись, снова захватывает мьютекс.
- `c.Signal()`: будит одну ждущую горутину.
- `c.Broadcast()`: будит всех.

```go
type Queue struct {
	mu       sync.Mutex
	notEmpty *sync.Cond
	items    []int
}

func NewQueue() *Queue {
	q := &Queue{}
	q.notEmpty = sync.NewCond(&q.mu)
	return q
}

func (q *Queue) Get() int {
	q.mu.Lock()
	defer q.mu.Unlock()
	for len(q.items) == 0 { // for, а не if
		q.notEmpty.Wait()
	}
	v := q.items[0]
	q.items = q.items[1:]
	return v
}

func (q *Queue) Put(v int) {
	q.mu.Lock()
	q.items = append(q.items, v)
	q.mu.Unlock()
	q.notEmpty.Signal()
}
```

Условие проверяют **в цикле**: между `Signal` и моментом, когда разбуженная горутина снова захватит мьютекс, значение может забрать кто-то другой, кто пришёл позже и не спал. Документация `Cond.Wait` прямо говорит: пока `Wait` ждёт, мьютекс отпущен, поэтому после возврата нельзя считать условие истинным, и `Wait` зовут в цикле. В домашке это проверяет отдельный тест с 16 потребителями.

В прикладном коде `Cond` редок: почти всегда проще канал или закрытие канала. Он выигрывает, когда всех ждущих нужно будить многократно (`Broadcast` можно звать сколько угодно, а канал закрывается однажды) или когда ожидание завязано на сложное условие под мьютексом.

## Pool: переиспользование временных объектов

`sync.Pool` это набор временных объектов, которые можно взять (`Get`) и вернуть (`Put`), чтобы не аллоцировать их заново. Цель: снизить нагрузку на сборщик мусора на горячем пути. Классика: буферы для сериализации.

```go
var bufPool = sync.Pool{
	New: func() any { return new(bytes.Buffer) },
}

func render(w io.Writer, data any) error {
	buf := bufPool.Get().(*bytes.Buffer)
	buf.Reset() // объект из пула грязный, сбрось состояние
	defer bufPool.Put(buf)

	if err := json.NewEncoder(buf).Encode(data); err != nil {
		return err
	}
	_, err := w.Write(buf.Bytes())
	return err
}
```

Главное, что надо понимать: **пул не кеш**. Документация: любой объект в пуле может быть удалён в любой момент без уведомления. Пул чистится при сборках мусора. Отсюда правила:

- объект из `Get` мог прийти грязным от другой горутины, сбрасывай состояние;
- не храни в пуле то, что нельзя потерять (соединения, открытые файлы);
- не клади назад гигантские буферы, иначе пул будет держать эту память. `fmt`, например, не возвращает в пул буферы больше 64 КБ (`fmt/print.go`).

::: hood Как устроен Pool
У каждого `P` (логического процессора планировщика) свой локальный кусок пула: приватный слот на один объект плюс общая очередь, из которой могут красть другие `P`. `Get` сначала смотрит в свой приватный слот, потом в свою очередь, потом крадёт у соседей, потом заглядывает в victim-ярус, и только потом зовёт `New`. Поэтому в обычном случае `Get` и `Put` не требуют мьютекса и дешевле аллокации.

При каждой сборке мусора основной ярус перекладывается в victim, а старый victim выбрасывается. Объект, который не взяли за две сборки, гарантированно уходит. Отсюда нестабильный результат задачи в конце урока: он зависит от `P` горутины и числа сборок.
:::

## sync.Map

Обычная `map` не потокобезопасна: одновременная запись из двух горутин может закончиться `fatal error: concurrent map writes`. Стандартное решение: `map` + `Mutex` (или `RWMutex`). `sync.Map` это специализированная альтернатива, и документация прямо говорит, что большинству кода нужна обычная мапа с мьютексом: так типобезопаснее и проще поддерживать инварианты.

`sync.Map` выигрывает в двух сценариях (из документации):

1. запись по ключу происходит один раз, а чтений много (кеш, который только растёт);
2. разные горутины читают и пишут **непересекающиеся** наборы ключей.

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var m sync.Map
	v, loaded := m.LoadOrStore("a", 1)
	fmt.Println(v, loaded)
	v, loaded = m.LoadOrStore("a", 2)
	fmt.Println(v, loaded)
	old, loaded := m.Swap("a", 3)
	fmt.Println(old, loaded)
	n := 0
	m.Range(func(k, v any) bool { n++; return true })
	fmt.Println(n)
}
```

Вывод: `1 false`, `1 true`, `1 true`, `1`. `LoadOrStore` кладёт значение, если ключа нет (`1 false`: сохранили 1, загружено не было), иначе возвращает существующее (`1 true`, двойка не записалась). `Swap` записывает новое значение и возвращает предыдущее: `1 true`. В мапе один ключ, `Range` насчитал 1. Методы атомарны: «проверить и вставить» через `LoadOrStore` безопасно, а через `Load` + `Store` нет.

Ещё: ключи и значения типа `any` (нужен type assertion); `Range` не даёт консистентного снимка; `Clear` появился в Go 1.23; в Go 1.24 реализацию переписали на конкурентное хеш-дерево (HashTrieMap), запись стала быстрее.

## sync/atomic

Атомарная операция неделима: никто не увидит «половину» записи. Для одного числа или указателя это самый дешёвый способ синхронизации, без мьютекса и без засыпания.

С Go 1.19 в пакете есть **типизированные** атомики, и в новом коде используют их:

```go
var requests atomic.Int64

func handler() {
	requests.Add(1)
}

func metrics() int64 {
	return requests.Load()
}
```

Типы: `atomic.Int32`, `Int64`, `Uint32`, `Uint64`, `Uintptr`, `Bool`, `Pointer[T]`, плюс `atomic.Value` для произвольных значений. Методы у чисел: `Load`, `Store`, `Add`, `Swap`, `CompareAndSwap`, а с Go 1.23 ещё `And` и `Or` (битовые операции, возвращают старое значение).

Почему типы лучше старых функций `atomic.AddInt64(&n, 1)`:

- к полю `atomic.Int64` **нельзя** случайно обратиться неатомарно: `n++` не скомпилируется, а голый `int64` позволяет смешать `atomic.AddInt64(&n, 1)` и `n++`;
- `atomic.Int64` выровнен на 8 байт даже на 32-битных платформах;
- копирование ловит `go vet`.

Переписывать руками не надо: в Go 1.27 `go fix` умеет переводить старые вызовы на типы (модернизатор `atomictypes`). Я прогнал его на коде с `var n int64` и `atomic.AddInt64(&n, 1)`:

```diff
-	var n int64
+	var n atomic.Int64
 ...
-			atomic.AddInt64(&n, 1)
+			n.Add(1)
 ...
-	fmt.Println(atomic.LoadInt64(&n))
+	fmt.Println(n.Load())
```

### CompareAndSwap и цикл CAS

`CompareAndSwap(old, new)` атомарно делает: «если сейчас значение `old`, записать `new` и вернуть `true`, иначе ничего не менять и вернуть `false`». На этом строят любые обновления, которых нет готовыми, например «занять слот, если занято меньше лимита»:

```go
func tryAcquire(n *atomic.Int64, limit int64) bool {
	for {
		cur := n.Load()
		if cur >= limit {
			return false // мест нет
		}
		if n.CompareAndSwap(cur, cur+1) {
			return true // успели занять
		}
		// кто-то поменял значение между Load и CAS: перечитать и повторить
	}
}
```

Наивное `if n.Load() < limit { n.Add(1) }` превышает лимит: при `limit = 10` две горутины читают 9, обе видят свободное место, обе прибавляют, и занято 11. Каждая операция атомарна, а их **последовательность** нет. Это главный урок атомиков: атомарность одной операции не делает атомарной логику из нескольких.

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
)

func main() {
	var n atomic.Int64
	var wg sync.WaitGroup
	for range 1000 {
		wg.Go(func() { n.Add(1) })
	}
	wg.Wait()
	fmt.Println(n.Load())
	fmt.Println(n.CompareAndSwap(1000, 0), n.Load())
	fmt.Println(n.CompareAndSwap(1000, 5), n.Load())
}
```

Вывод: `1000`, `true 0`, `false 0`. `Add` атомарен, потерь нет. Первый CAS видит 1000, совпадает с ожидаемым, записывает 0. Второй CAS ожидает 1000, а там уже 0: ничего не меняет и возвращает `false`.

### Сколько это стоит

Я сравнил три способа увеличивать один общий счётчик, когда все 10 ядер ноутбука долбят его одновременно (`b.RunParallel`, Go 1.27):

| Способ | Время на операцию |
|---|---|
| `atomic.Int64.Add` | около 31-34 нс |
| `sync.Mutex` вокруг `n++` | около 149-159 нс |
| канал ёмкости 1 как замок | около 151-153 нс |

Под сильной конкуренцией атомик быстрее примерно в пять раз, но годится только для одного значения. Если инвариант охватывает несколько полей, нужен мьютекс: два атомика по отдельности не дают согласованного состояния.

::: hood atomic и модель памяти
Атомарные операции в Go последовательно согласованы: если эффект атомарной операции A наблюдается атомарной операцией B, то A «синхронизируется до» B. Это та же семантика, что у последовательно согласованных атомиков C++ (`memory_order_seq_cst`, их режим по умолчанию), но ослабленных режимов, как в C++, в Go нет вовсе. Практически: запись обычных данных, затем `ready.Store(true)` в одной горутине; `ready.Load() == true`, затем чтение данных в другой. Данные будут видны. На ARM и x86 компилятор вставляет нужные барьеры и инструкции (на x86, например, `LOCK XADD` для `Add`), поэтому atomic это не «просто запись в память».
:::

::: trap Копирование мьютекса через value receiver
Плохо: метод с получателем по значению.

```go
type Counter struct {
	mu sync.Mutex
	n  int
}

func (c Counter) Inc() { // c это копия, вместе с мьютексом
	c.mu.Lock()
	defer c.mu.Unlock()
	c.n++
}
```

Каждый вызов блокирует и увеличивает **свою копию**: я запустил `wg.Go(c.Inc)` 100 раз и получил `0`. `go vet` предупреждает: `Inc passes lock by value`, потому что `Counter contains sync.Mutex`.

Хорошо: указатель-получатель `func (c *Counter) Inc()`, и `go vet` в CI. Это относится ко всем типам `sync` и `atomic`: `Mutex`, `RWMutex`, `WaitGroup`, `Once`, `Cond`, `Map`, `Pool`, `atomic.Int64`.
:::

::: trap Отдать наружу то, что защищает мьютекс
Плохо: мьютекс защищает мапу, а метод возвращает саму мапу.

```go
func (c *Counter) Snapshot() map[string]int {
	c.mu.Lock()
	defer c.mu.Unlock()
	return c.m // вызывающий будет читать её без мьютекса
}
```

Мьютекс отпущен в момент `return`, а мапа уже у вызывающего, который читает её, пока другие горутины пишут через `Inc`. Гонка, а при одновременной записи `fatal error: concurrent map read and map write`. То же со слайсами и указателями на внутренние структуры.

Хорошо: вернуть копию, сделанную под мьютексом.

```go
func (c *Counter) Snapshot() map[string]int {
	c.mu.Lock()
	defer c.mu.Unlock()
	return maps.Clone(c.m)
}
```
:::

::: trap Медленная работа под замком
Плохо: под мьютексом идёт поход в сеть.

```go
c.mu.Lock()
defer c.mu.Unlock()
if v, ok := c.items[k]; ok {
	return v
}
v := fetchFromDB(k) // 50 мс, и все остальные горутины ждут
c.items[k] = v
return v
```

Один медленный ключ блокирует весь кеш. Хорошо: проверить под замком, отпустить, сходить в базу без замка, снова взять замок и записать, перепроверив, не успел ли кто-то раньше.

```go
c.mu.Lock()
v, ok := c.items[k]
c.mu.Unlock()
if ok {
	return v
}
v = fetchFromDB(k) // остальные горутины в это время работают
c.mu.Lock()
if cached, ok := c.items[k]; ok {
	v = cached // пока ходили в базу, значение уже положили
} else {
	c.items[k] = v
}
c.mu.Unlock()
return v
```

А чтобы десять горутин не пошли в базу за одним и тем же ключом, нужна дедупликация на ключ (`sync.Once` на запись или `golang.org/x/sync/singleflight`). Ровно эту задачу решаешь в домашке `Memoize`.
:::

## Что выбрать

| Задача | Инструмент |
|---|---|
| Передать данные или задачу другой горутине | канал |
| Сигнал «всем остановиться» | закрытие канала, `context` |
| Защитить структуру, мапу, несколько связанных полей | `Mutex` |
| То же, чтений сильно больше, секции не крошечные | `RWMutex` (по бенчмарку) |
| Один счётчик, флаг, указатель на конфиг | `atomic.Int64`, `atomic.Bool`, `atomic.Pointer[T]` |
| Ленивая инициализация один раз | `sync.OnceValue`/`OnceValues`/`Once` |
| Ждать сложного условия, будить всех много раз | `Cond` |
| Снизить аллокации временных объектов | `Pool` |
| Мапа «записал один раз, читают все» или непересекающиеся ключи | `sync.Map` |

## Что выведет программа?

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var mu sync.Mutex
	mu.Lock()
	fmt.Println("первый Lock")
	mu.Lock()
	fmt.Println("второй Lock")
}
```

<Predict :options="['первый Lock, второй Lock', 'первый Lock, затем fatal error: deadlock', 'panic: sync: lock of locked mutex', 'ошибка компиляции']" :correct="1">

Второй `Lock` ждёт, пока мьютекс освободят, а освободить может только эта же горутина, которая ждёт. Других горутин нет: `fatal error: all goroutines are asleep - deadlock!` с `goroutine 1 [sync.Mutex.Lock]`. Отдельной паники «двойной лок» не существует, а в сервисе с живыми горутинами рантайм дедлок не заметит, и горутина просто повиснет.

</Predict>

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	defer func() { fmt.Println("recover:", recover()) }()
	var mu sync.Mutex
	mu.Unlock()
}
```

<Predict :options="['recover: sync: unlock of unlocked mutex', 'fatal error: sync: unlock of unlocked mutex, recover не срабатывает', 'ничего, Unlock игнорируется', 'recover: <nil>']" :correct="1">

Это `fatal error`, а не `panic`: рантайм считает, что состояние синхронизации сломано и продолжать нельзя. `recover` такое не ловит, процесс завершается, и строка `recover:` не печатается. Та же категория, что и обнаруженный дедлок. Так что «перестраховаться лишним `Unlock`» нельзя, это убивает процесс.

</Predict>

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var mu sync.RWMutex
	mu.RLock()
	mu.RLock()
	fmt.Println("два RLock")
	mu.RUnlock()
	mu.RUnlock()
	mu.Lock()
	fmt.Println("Lock")
	mu.Unlock()
	mu.RLock()
	mu.Lock()
	fmt.Println("Lock под RLock")
}
```

<Predict :options="['все три строки', 'два RLock, Lock, затем дедлок', 'два RLock, затем дедлок', 'паника на втором RLock']" :correct="1">

Два `RLock` подряд совместимы, это читатели. После `RUnlock` писатель спокойно берёт `Lock`. А вот `Lock` при своём же `RLock` ждёт ухода всех читателей, включая себя: `fatal error: all goroutines are asleep - deadlock!` с `goroutine 1 [sync.RWMutex.Lock]`. «Апгрейда» чтения до записи нет: отпусти `RLock`, возьми `Lock` и **перепроверь** состояние, потому что за это время его могли поменять.

</Predict>

```go
package main

import (
	"fmt"
	"runtime"
	"sync"
)

func main() {
	created := 0
	p := sync.Pool{New: func() any { created++; return new(int) }}

	x := p.Get().(*int)
	*x = 42
	p.Put(x)
	runtime.GC()
	fmt.Println(*p.Get().(*int), created)
}
```

<Predict :options="['42 1', '0 2', 'недетерминировано: 42 1 или 0 2', 'паника: пул пуст']" :correct="2">

После одной сборки мусора объект может остаться (у пула есть «victim cache»: объекты переживают одну сборку во втором ярусе) и может пропасть. Я запустил эту программу 12 раз: 2 раза объект пережил GC (`42 1`, `New` вызван один раз), 10 раз пропал (`0 2`, `New` вызван снова). На это и рассчитан пул: он ускоряет, когда объект есть, и не ломает логику, когда объекта нет.

</Predict>

::: interview
<details><summary>Что будет, если вызвать Lock дважды из одной горутины? А Unlock незахваченного?</summary>

Мьютекс в Go не реентерабельный: второй `Lock` из той же горутины ждёт вечно. Если других горутин нет, рантайм завершит программу с `all goroutines are asleep - deadlock!`, если есть, горутина просто повиснет. `Unlock` незахваченного мьютекса это `fatal error: sync: unlock of unlocked mutex`, его нельзя перехватить `recover`. Мьютекс не привязан к горутине: захватить в одной и отпустить в другой разрешено.

</details>
<details><summary>Как устроен sync.Mutex? Что такое режим голодания?</summary>

Состояние в одном `int32` (захвачен, есть разбуженный, режим голодания, число ожидающих) плюс семафор. Быстрый путь: один CAS. Медленный: немного активного ожидания (spinning), затем сон на семафоре. В нормальном режиме разбуженная горутина соревнуется с новыми и часто проигрывает (зато высокая пропускная способность). Если ожидающий ждёт больше 1 мс, мьютекс переходит в режим голодания: владение передаётся строго по очереди, новые не пытаются захватить. Когда очередь иссякла, режим возвращается к нормальному.

</details>
<details><summary>Чем RWMutex отличается от Mutex и всегда ли он быстрее на чтениях?</summary>

`RWMutex` допускает много одновременных читателей (`RLock`) или одного писателя (`Lock`). Ждущий писатель блокирует новых читателей, чтобы не голодать, поэтому рекурсивный `RLock` может дать дедлок, а апгрейда `RLock` в `Lock` нет. Быстрее не всегда: реализация сложнее, и при коротких секциях обычный `Mutex` бывает не хуже. Выигрыш, когда чтений намного больше и секции чтения заметной длины. Решают бенчмарком.

</details>
<details><summary>Как ведёт себя sync.Once, если функция запаниковала? А OnceFunc?</summary>

`Once.Do` считает вызов состоявшимся, даже если `f` запаниковала: повторно `f` не вызовется, последующие `Do` ничего не делают. `OnceFunc`/`OnceValue`/`OnceValues` (Go 1.21) тоже вызывают `f` один раз, но при панике каждый последующий вызов обёртки паникует тем же значением, сбой не теряется. Ещё одна ловушка `Once`: вызов `Do` того же `Once` изнутри `f` даёт дедлок.

</details>
<details><summary>Когда использовать sync.Map вместо map с мьютексом?</summary>

По документации в двух случаях: ключ записывается один раз и много читается (растущий кеш), или горутины работают с непересекающимися наборами ключей. В остальных случаях лучше обычная мапа с `Mutex`/`RWMutex`: типобезопасность (у `sync.Map` всё `any`), проще держать инварианты. Атомарные операции `LoadOrStore`, `Swap`, `CompareAndSwap`, `LoadAndDelete` закрывают «проверить и изменить». В Go 1.24 реализацию переписали на конкурентное хеш-дерево, в 1.23 добавили `Clear`.

</details>
<details><summary>Что такое sync.Pool, зачем он и чем он не является?</summary>

Набор временных объектов для повторного использования: взял через `Get`, вернул через `Put`. Цель: меньше аллокаций на горячем пути и меньше работы сборщику мусора (буферы, энкодеры; так делает `fmt`). Любой объект в пуле может быть выброшен при любой сборке мусора без уведомления, поэтому `Get` иногда возвращает свежий объект из `New`. С Go 1.13 пул не очищается полностью на каждом GC: объекты сначала переезжают в victim cache и переживают одну сборку, а не взятые за две сборки уходят. Отсюда правила: это не кеш, состояние после `Get` сбрасывают, гигантские объекты назад не кладут. Соединения с базой или файлы хранить нельзя: пул выбросит их молча, без `Close`, и ресурс утечёт, а лимита на число объектов у пула нет. Для соединений нужен настоящий пул (как в `database/sql`) с закрытием и ограничением. Внутри: локальная часть на каждый `P`, кража у соседей, поэтому `Get`/`Put` обычно без мьютекса.

</details>
<details><summary>Почему atomic быстрее мьютекса и когда его недостаточно?</summary>

Атомик это одна процессорная инструкция (например, `LOCK XADD`), без засыпания, очередей и планировщика. Мьютекс в быстром пути тоже один CAS, но под конкуренцией горутины крутятся и засыпают. У меня на 10 ядрах под полной конкуренцией атомарный инкремент около 32 нс против 150 нс у мьютекса. Недостаточно, когда инвариант охватывает несколько переменных или нужна последовательность операций: атомарность каждой операции не делает атомарной их связку. Для «прочитать, вычислить, записать» нужен цикл CAS или мьютекс.

</details>
<details><summary>Зачем нужны типизированные atomic.Int64 и др., если есть atomic.AddInt64?</summary>

К полю `atomic.Int64` нельзя обратиться неатомарно, это защищает от смешивания `atomic.AddInt64(&n, 1)` и `n++`. Гарантировано выравнивание на 8 байт на 32-битных платформах. Копирование ловит `go vet`. Это рекомендованный способ с Go 1.19, а `go fix` в Go 1.27 умеет переписывать старые вызовы на типы (`atomictypes`).

</details>
:::
