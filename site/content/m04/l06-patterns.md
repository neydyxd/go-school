# Паттерны конкурентности

Горутины, каналы, `select`, `sync` и `context` это кирпичи. Из них собирается десяток устойчивых конструкций, которые встречаются в любом Go-бэкенде: скачать 10 000 картинок, но не больше 20 одновременно; прогнать данные через несколько стадий обработки; опросить три сервиса параллельно и упасть по первой ошибке; не долбить внешний API чаще 50 раз в секунду. Каждую из них можно написать с нуля, но если знаешь паттерн, пишешь правильно с первого раза и без утечек.

На собесе по Go почти всегда есть live-coding на конкурентность, и это одна из задач этого урока в разных обёртках: «напиши worker pool», «скачай список URL с ограничением параллелизма», «собери результаты в исходном порядке», «сделай так, чтобы ошибка останавливала остальных». Интервьюер смотрит на три вещи: нет ли гонок, нет ли утечек горутин, и кто закрывает каналы.

Сквозная идея урока: **у каждого канала есть владелец**. Владелец создаёт канал, пишет в него и закрывает его. Читатели только читают. Если держаться этого правила, половина ошибок с паникой `send on closed channel` и вечными блокировками исчезает сама.

## Генератор

Функция, которая возвращает канал и в отдельной горутине наполняет его значениями. Вызывающий получает «ленивую последовательность».

```go
func Gen(ctx context.Context, nums ...int) <-chan int {
	out := make(chan int)
	go func() {
		defer close(out) // владелец закрывает
		for _, n := range nums {
			select {
			case out <- n:
			case <-ctx.Done():
				return // читатель ушёл: не висим на отправке вечно
			}
		}
	}()
	return out
}
```

Три детали, на которых проверяют:

1. Функция возвращает `<-chan int` (только чтение). Компилятор не даст вызывающему ни писать, ни закрывать.
2. `defer close(out)`: читатель узнает о конце через `range` или `v, ok := <-out`.
3. Отправка внутри `select` с `ctx.Done()`. Без этого, если читатель прочитал два значения и ушёл, горутина генератора навсегда застрянет на `out <- n`. Это утечка горутины, о ней подробно в следующем уроке.

С Go 1.23 для «ленивых последовательностей» без конкурентности есть итераторы (`iter.Seq`, `range` по функции). Канальный генератор нужен, когда значения действительно производятся в другой горутине: читаются из сети, вычисляются параллельно.

## Pipeline: конвейер стадий

Конвейер это цепочка стадий, соединённых каналами. Каждая стадия: читает из входного канала, делает свою работу, пишет в выходной, а когда вход закончился, закрывает выход.

```go
func Square(ctx context.Context, in <-chan int) <-chan int {
	out := make(chan int)
	go func() {
		defer close(out)
		for n := range in {
			select {
			case out <- n * n:
			case <-ctx.Done():
				return
			}
		}
	}()
	return out
}

func main() {
	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()
	for v := range Square(ctx, Square(ctx, Gen(ctx, 1, 2, 3))) {
		fmt.Println(v) // 1, 16, 81
	}
}
```

Почему это удобно: стадии работают **одновременно**. Пока вторая стадия возводит в квадрат первое число, генератор уже отдаёт второе. Каждая стадия маленькая и тестируется отдельно. Закрытие входа само «протекает» по конвейеру: генератор закрыл свой канал, `range` в первой стадии закончился, она закрыла свой, и так до конца.

Отмена тоже протекает, но через контекст: `cancel()` в `main` заставляет все стадии выйти из `select`. Это решает главную проблему конвейеров: потребитель, который бросил чтение на середине, иначе оставил бы висеть все стадии выше по течению.

Обрати внимание: `for n := range in` в `Square` не слышит отмену, пока ждёт **вход**. В конвейере это нормально: стадия выше тоже слушает `ctx` и закроет канал. Но если вход приходит снаружи и его могут не закрыть, чтение тоже заворачивают в `select` (так требует задача 2 домашки).

## Fan-out и fan-in

**Fan-out**: несколько горутин читают из **одного** канала. Каждое значение достанется ровно одному читателю, так работа распределяется между воркерами. Ничего специального писать не нужно, это свойство канала.

**Fan-in**: значения из **нескольких** каналов сливаются в один. Тут уже нужен код:

```go
func Merge(ctx context.Context, cs ...<-chan int) <-chan int {
	out := make(chan int)
	var wg sync.WaitGroup
	for _, c := range cs {
		wg.Go(func() { // по горутине на вход: читаем все входы одновременно
			for v := range c {
				select {
				case out <- v:
				case <-ctx.Done():
					return
				}
			}
		})
	}
	go func() {
		wg.Wait()  // все входы исчерпаны
		close(out) // и только тогда закрываем выход
	}()
	return out
}
```

Отдельная горутина с `wg.Wait()` и `close(out)` это ключевой момент. Закрыть `out` может только тот, кто знает, что **все** писатели закончили. Ни один из писателей этого не знает, поэтому заводится «закрывальщик». Вызвать `wg.Wait()` прямо в `Merge` перед `return` нельзя: `Merge` не вернёт канал, пока все не допишут, а дописать они не смогут, потому что канал ещё никто не читает.

Fan-out и fan-in вместе:

```go
in := Gen(ctx, 1, 2, 3, 4, 5, 6)
// fan-out: три стадии делят один вход
w1, w2, w3 := Square(ctx, in), Square(ctx, in), Square(ctx, in)
// fan-in: сливаем обратно
for v := range Merge(ctx, w1, w2, w3) {
	fmt.Println(v) // все шесть квадратов, порядок НЕ гарантирован
}
```

Плата за параллельность: **порядок теряется**. Если он нужен, к значению прикладывают индекс и раскладывают результаты по местам (как в worker pool ниже).

```go
ch := make(chan int)
var wg sync.WaitGroup
for i := range 3 {
	wg.Go(func() { ch <- i })
}
wg.Wait()
close(ch)
for v := range ch {
	fmt.Println(v)
}
```

Канал небуферизованный: каждая из трёх горутин ждёт читателя на `ch <- i`. А `main` ждёт в `wg.Wait()`, пока горутины закончатся, и до чтения не доходит. Все стоят, рантайм видит, что ни одна горутина не может продолжить, и падает с `fatal error: all goroutines are asleep - deadlock!`. Лечение: `wg.Wait()` и `close(ch)` вынести в отдельную горутину, как в `Merge`, а читать в `main`.

## Worker pool

Самый частый паттерн в продакшне. Есть поток задач, обрабатываем их **фиксированным** числом воркеров. Зачем ограничивать, если горутины дешёвые? Потому что дорогие не горутины, а то, что они делают: соединения с базой (пул на 20 соединений), файловые дескрипторы, память под ответы, лимиты чужого API. 10 000 одновременных запросов в базу положат её быстрее, чем 20.

Классическая форма: канал задач, N воркеров читают из него (fan-out), результаты пишутся по индексу, чтобы сохранить порядок.

```go
func Pool[T, R any](jobs []T, workers int, fn func(T) R) []R {
	results := make([]R, len(jobs))
	idx := make(chan int)
	var wg sync.WaitGroup
	for range workers {
		wg.Go(func() {
			for i := range idx { // воркер берёт следующую задачу, пока канал не закрыт
				results[i] = fn(jobs[i])
			}
		})
	}
	for i := range jobs {
		idx <- i
	}
	close(idx) // задач больше не будет: воркеры выйдут из range
	wg.Wait()
	return results
}
```

Почему `results[i] = ...` без мьютекса не гонка: каждая горутина пишет в **свой** элемент слайса, это разные ячейки памяти. Гонкой был бы `results = append(results, r)` из нескольких горутин: `append` меняет общий заголовок слайса.

Альтернативная форма: **горутина на задачу плюс семафор**. Горутин столько же, сколько задач, но одновременно работают не больше N:

```go
sem := make(chan struct{}, workers)
var wg sync.WaitGroup
for i, job := range jobs {
	sem <- struct{}{} // занять слот; если все заняты, ждём
	wg.Go(func() {
		defer func() { <-sem }() // освободить слот
		results[i] = fn(job)
	})
}
wg.Wait()
```

Что выбрать. Пул удобен, когда задачи приходят потоком (из очереди, из канала) и у воркера есть состояние (своё соединение, буфер). Горутина-на-задачу с семафором проще, когда задачи известны заранее списком. Для миллиона задач пул экономнее: миллион горутин, пусть и спящих, это гигабайты стеков.

## errgroup: группа с ошибками и отменой

`sync.WaitGroup` умеет только ждать. В реальном коде нужно ещё: вернуть ошибку, а при первой ошибке остановить остальных. Это `golang.org/x/sync/errgroup`, пакет из «расширенной» стандартной библиотеки, который есть почти в каждом сервисе.

```go
import "golang.org/x/sync/errgroup"

func LoadDashboard(ctx context.Context, userID int64) (Dashboard, error) {
	g, ctx := errgroup.WithContext(ctx)
	var d Dashboard
	g.Go(func() error {
		var err error
		d.Profile, err = profiles.Get(ctx, userID)
		return err
	})
	g.Go(func() error {
		var err error
		d.Orders, err = orders.List(ctx, userID)
		return err
	})
	if err := g.Wait(); err != nil {
		return Dashboard{}, err // первая ошибка; второй запрос уже получил отмену
	}
	return d, nil
}
```

Что делает каждая часть:

- `g.Go(f)` запускает `f` в горутине.
- `g.Wait()` ждёт все горутины и возвращает **первую** ненулевую ошибку. Остальные ошибки теряются.
- `errgroup.WithContext(ctx)` возвращает производный контекст, который отменяется при первой ошибке. Его и нужно передавать в функции, иначе отмена ни до кого не дойдёт.
- `g.SetLimit(n)`: не больше `n` активных горутин. Следующий `g.Go` **блокируется**, пока не освободится слот. Это готовый worker pool с ошибками.
- `g.TryGo(f)`: как `Go`, но не ждёт, а возвращает `false`, если лимит исчерпан.

Ограниченная параллельная загрузка с сохранением порядка, классическая задача собеса, в errgroup пишется в 15 строк:

```go
func FetchAll(ctx context.Context, urls []string) ([]string, error) {
	g, ctx := errgroup.WithContext(ctx)
	g.SetLimit(8)
	bodies := make([]string, len(urls))
	for i, u := range urls {
		g.Go(func() error {
			b, err := fetch(ctx, u)
			if err != nil {
				return fmt.Errorf("fetch %s: %w", u, err)
			}
			bodies[i] = b
			return nil
		})
	}
	return bodies, g.Wait()
}
```

::: hood Как устроен errgroup
Весь пакет около сотни строк, загляни в исходник (`go doc -src golang.org/x/sync/errgroup.Group.Go`). Внутри:

```text
Group
  wg      sync.WaitGroup   ждать всех
  sem     chan token       лимит: буферизованный канал ёмкостью n (nil, если лимита нет)
  errOnce sync.Once        запомнить только первую ошибку
  err     error
  cancel  func(error)      из context.WithCancelCause
```

`Go` сначала кладёт токен в `sem` (поэтому блокируется на лимите), потом `wg.Add(1)` и запускает горутину. Горутина по завершении забирает токен обратно и делает `wg.Done()`. Первая ошибка через `errOnce` записывается в `err` и вызывает `cancel(err)`, поэтому `context.Cause(ctx)` в группе вернёт именно эту ошибку. `Wait` дожидается `wg` и тоже вызывает `cancel`.

Два следствия, о которых спрашивают:

1. Контекст группы **отменяется после `Wait`**, даже если ошибок не было. Использовать его после `Wait` бессмысленно.
2. Паники внутри `f` errgroup **не перехватывает**: в коде прямо написано, что пробрасывать их наверх создаёт больше проблем, чем решает. Паника в горутине уронит процесс, как и обычно.

А семафор на канале ты уже видел выше: `sem <- token{}` занимает слот, `<-sem` освобождает.
:::

```go
var g errgroup.Group
g.Go(func() error {
	time.Sleep(10 * time.Millisecond)
	return errors.New("A")
})
g.Go(func() error { return errors.New("B") })
g.Go(func() error { return nil })
fmt.Println(g.Wait())
```

## Семафор

Семафор ограничивает число одновременных владельцев ресурса. В Go самый простой семафор это буферизованный канал:

```go
sem := make(chan struct{}, 3) // 3 слота
sem <- struct{}{}             // Acquire: блокируется, если все 3 заняты
<-sem                         // Release
```

`struct{}` занимает 0 байт: нам важен сам факт занятости слота, а не данные.

Когда нужен ещё и **вес** (одна задача занимает 1 слот, тяжёлая 5) или отмена ожидания по контексту без своего `select`, берут `golang.org/x/sync/semaphore`:

```go
sem := semaphore.NewWeighted(10)      // например, 10 «единиц памяти»
if err := sem.Acquire(ctx, 3); err != nil {
	return err // контекст отменили, пока ждали
}
defer sem.Release(3)
```

Семафор, worker pool и `SetLimit` в errgroup это три формы одной идеи: **ограничить параллелизм**.

## Rate limiting: ограничение частоты

Не путай с предыдущим. Семафор ограничивает **сколько одновременно**, rate limiter ограничивает **сколько в единицу времени**. Внешний API разрешает 50 запросов в секунду: даже если каждый запрос длится 1 мс и одновременно идёт один, без лимитера ты сделаешь 1000 в секунду и получишь бан.

Простейший лимитер на тикере:

```go
tick := time.NewTicker(200 * time.Millisecond) // не чаще 5 раз в секунду
defer tick.Stop()
for _, req := range requests {
	<-tick.C
	call(req)
}
```

Минус тикера: нет всплесков. Если пользователь молчал минуту, а потом прислал 3 запроса, логично обслужить их сразу. Для этого есть **token bucket** (ведро токенов): в ведре помещается `b` токенов, они пополняются со скоростью `r` в секунду, каждый запрос забирает один токен. Пустое ведро значит «подожди». Готовая реализация: `golang.org/x/time/rate`:

```go
lim := rate.NewLimiter(rate.Every(100*time.Millisecond), 3) // 10 в секунду, всплеск до 3
for i := range 6 {
	if err := lim.Wait(ctx); err != nil { // ждёт токен или отмену ctx
		return err
	}
	fmt.Println(i, time.Since(start).Round(50*time.Millisecond))
}
// 0 0s
// 1 0s
// 2 0s
// 3 100ms
// 4 200ms
// 5 300ms
```

Первые три запроса проходят сразу (полное ведро), дальше по одному в 100 мс. Есть и неблокирующий вариант `lim.Allow()`: вернёт `false`, если токена нет. Так в HTTP-middleware отвечают `429 Too Many Requests` вместо ожидания. Лимитер на пользователя (по IP или токену) делают мапой лимитеров под мьютексом, подробнее в модуле про Gin и безопасность.

<details><summary>Напиши worker pool. Как сохранить порядок результатов?</summary>

N горутин читают задачи из общего канала (`for j := range jobs`), производитель кладёт задачи и закрывает канал, `WaitGroup` ждёт воркеров. Для порядка передают индекс задачи и пишут результат в `results[i]` заранее созданного слайса: разные элементы слайса это разные ячейки памяти, гонки нет. Альтернатива: результат с индексом в канал и сортировка в конце.

</details>
<details><summary>Как ограничить число одновременно выполняющихся горутин?</summary>

Три способа. Фиксированный пул из N воркеров. Семафор на буферизованном канале ёмкостью N (`sem <- struct{}{}` перед работой, `<-sem` после). `errgroup.Group.SetLimit(N)`. Для взвешенных ресурсов `golang.org/x/sync/semaphore.Weighted`.

</details>
<details><summary>Чем rate limiting отличается от ограничения параллелизма?</summary>

Ограничение параллелизма задаёт, сколько операций идёт одновременно (семафор, пул). Rate limiting задаёт, сколько операций начинается в единицу времени. Быстрые запросы по одному могут превысить rate limit, медленные при низкой частоте могут упереться в лимит параллелизма. Rate limiting делают тикером или token bucket (`golang.org/x/time/rate`: скорость пополнения и размер всплеска, методы `Wait` и `Allow`).

</details>
<details><summary>Чем errgroup лучше sync.WaitGroup?</summary>

Возвращает первую ошибку из горутин, через `WithContext` отменяет контекст остальных при первой ошибке, через `SetLimit` ограничивает параллелизм. Нюансы: возвращается только первая ошибка, паники не перехватываются, контекст группы отменяется после `Wait`, а `g.Go` после ошибки всё равно запускает функции, поэтому они должны проверять контекст.

</details>
<details><summary>Кто должен закрывать канал? Что будет, если закрыть дважды или писать в закрытый?</summary>

Закрывает владелец, то есть единственный писатель. Если писателей несколько, заводят отдельную горутину, которая ждёт их через `WaitGroup` и закрывает. Читатель канал не закрывает. Запись в закрытый канал и повторное закрытие вызывают панику. Чтение из закрытого возвращает остаток буфера, а затем нулевое значение и `ok == false`.

</details>
<details><summary>Что такое fan-in и fan-out?</summary>

Fan-out: несколько горутин читают из одного канала и делят между собой работу; каждое значение получает ровно один читатель. Fan-in: значения из нескольких каналов сливаются в один; по горутине на входной канал плюс горутина, которая после `wg.Wait()` закрывает выход. Порядок значений при этом не сохраняется.

</details>
<details><summary>Как в конвейере не допустить утечки горутин, если потребитель ушёл раньше?</summary>

Каждая стадия отправляет в `select` вместе с `<-ctx.Done()`, а потребитель при уходе вызывает `cancel()` (обычно `defer cancel()`). Тогда все стадии выйдут из блокирующей отправки и закроют свои каналы. Вариант без контекста: общий `done`-канал, который закрывают при уходе.

</details>
<details><summary>Почему бы не запускать горутину на каждый элемент без ограничений, раз они дешёвые?</summary>

Дёшевы сами горутины (несколько КБ стека), но не то, что они делают: соединения с базой, сокеты, дескрипторы файлов, память под ответы, лимиты внешних API. Миллион одновременных HTTP-запросов упрутся в лимит открытых файлов и положат того, к кому ты ходишь. Ограничение параллелизма делает нагрузку предсказуемой.

</details>
