# select и таймауты

Одиночная операция с каналом умеет ждать только одного события. А реальный бэкенд почти всегда ждёт **одного из нескольких**: пришёл ответ от базы или истёк таймаут; пришла задача или поступил сигнал остановки; освободилось место в очереди или клиент отключился. Для этого в Go есть `select`: оператор, который ждёт сразу на нескольких каналах и выполняет ту ветку, что готова первой.

Без `select` не написать ни таймаут запроса, ни graceful shutdown, ни воркер, которого можно остановить. С ним же связана пачка классических ловушек для собеседования: случайный выбор между готовыми ветками, `break`, который не выходит из цикла, `time.After` в цикле, вычисление выражений в ветках, которые не выбраны. В Go 1.23 к тому же поменялось поведение таймеров, и старые советы из статей теперь частично неверны.

## Синтаксис и правила выбора

```go
select {
case v := <-in:
	fmt.Println("получили", v)
case out <- x:
	fmt.Println("отправили", x)
case <-done:
	return
}
```

Каждая ветка `case` это одна операция с каналом: получение (можно с `v, ok :=`) или отправка. `select` работает так:

1. Если готова **ровно одна** ветка, выполняется она.
2. Если готовы **несколько**, выбирается одна **случайно и равновероятно**. Порядок веток в коде ни на что не влияет, приоритета нет.
3. Если не готова **ни одна**, `select` блокирует горутину, пока какая-то не станет готовой. Если есть ветка `default`, вместо блокировки выполняется она.

«Готова» значит: операция выполнилась бы прямо сейчас без ожидания. Получение готово, если в буфере есть значение, есть ждущий отправитель или канал закрыт. Отправка готова, если есть место в буфере или ждущий получатель (а отправка в закрытый канал «готова» и паникует).

Случайность легко увидеть:

```go
package main

import "fmt"

func main() {
	a := make(chan int, 10)
	b := make(chan int, 10)
	for range 10 {
		a <- 1
		b <- 2
	}
	var fromA, fromB int
	for range 10 {
		select {
		case <-a:
			fromA++
		case <-b:
			fromB++
		}
	}
	fmt.Println(fromA, fromB)
}
```

Вывод недетерминирован, в сумме всегда 10. У меня два запуска дали `4 6` и `5 5`. Обе ветки всё время готовы (в обоих буферах по 10 значений), поэтому на каждой итерации выбор случаен, и ветка `a` не получает приоритета от того, что стоит первой. Случайность не прихоть: при фиксированном порядке первая ветка могла бы навсегда «заморить голодом» вторую.

### Выражения в ветках вычисляются всегда

При входе в `select` Go вычисляет **все** выражения каналов и все отправляемые значения во всех ветках, по порядку сверху вниз, ровно один раз. Даже в ветках, которые в итоге не выберутся:

```go
package main

import "fmt"

func val(name string) int {
	fmt.Println("вычисляю", name)
	return 1
}

func main() {
	full := make(chan int) // никто не читает
	select {
	case full <- val("send"):
		fmt.Println("отправили")
	default:
		fmt.Println("default")
	}
}
```

Сначала вычисляется `val("send")` (печатает `вычисляю send`), потом проверяется готовность: получателя нет, выполняется `default`. Если отправляемое значение дорогое (запрос к базе, тяжёлая сериализация), оно посчитается, даже когда отправка не случится. Это важно и для `time.After(d)`: внутри ветки это вызов функции, и он создаёт новый таймер при каждом входе в `select`.

## default и неблокирующие операции

`select` с `default` никогда не блокируется. Ветка с одной операцией плюс `default` даёт неблокирующую версию любой операции с каналом:

```go
// Неблокирующая отправка: положить, если есть место, иначе отбросить.
select {
case events <- e:
default:
	dropped++ // очередь переполнена, не тормозим основной поток
}

// Неблокирующее получение: забрать, если есть.
select {
case job := <-jobs:
	handle(job)
default:
	// работы нет, занимаемся другим
}
```

Так делают отбрасывание метрик при перегрузке, «попробовать взять задачу», проверку сигнала остановки без ожидания.

```go
package main

import "fmt"

func main() {
	ch := make(chan int, 1)
	for i := range 4 {
		select {
		case ch <- i:
		default:
			fmt.Println("пропустили", i)
		}
	}
	fmt.Println(<-ch)
}
```

Вывод: `пропустили 1`, `пропустили 2`, `пропустили 3`, затем `0`. Буфер на одно значение: `0` помещается, а для остальных места нет, и срабатывает `default`. Это шаблон «первое не вытесняется последующими»: если нужно наоборот, хранить самое свежее значение, надо сначала вычитать старое неблокирующим получением.

::: trap default как активное ожидание
Плохо: `default` внутри `for` без паузы.

```go
for {
	select {
	case v := <-ch:
		handle(v)
	default:
		// ничего не пришло, крутимся дальше
	}
}
```

Это busy loop: горутина занимает ядро на 100%, проверяя канал миллионы раз в секунду. Хорошо: если ждать нечего другого, убери `default`, и горутина будет спать на канале, не тратя процессор.

```go
for v := range ch {
	handle(v)
}
```

`default` нужен, только когда есть другая полезная работа или когда блокироваться запрещено по смыслу.
:::

## Пустой select и nil-каналы

`select {}` без веток блокируется навсегда. В `main` без других горутин это дедлок, а в сервисе иногда так «усыпляют» `main`, пока работают фоновые горутины (лучше ждать сигнала ОС явно).

Ветка с nil-каналом никогда не готова. Отсюда главный трюк `select`: **присвоить каналу `nil`, чтобы выключить ветку**.

```go
package main

import "fmt"

func main() {
	var a, b chan int
	select {
	case v := <-a:
		fmt.Println("a", v)
	case b <- 1:
		fmt.Println("b")
	default:
		fmt.Println("default")
	}
}
// default
```

Обе ветки с nil-каналами не готовы ни сейчас, ни когда-либо, поэтому выполняется `default`. Без `default` это был бы дедлок.

Где это нужно: слияние двух каналов в один. Когда первый источник закрылся, чтение из него «готово» всегда (закрытый канал сразу отдаёт нулевое значение), и `select` начнёт крутиться вхолостую на этой ветке. Обнуляем канал, и ветка исчезает:

```go
case v, ok := <-a:
	if !ok {
		a = nil // ветка a больше не будет выбрана
		continue
	}
	out <- v
```

Цикл при этом крутится, пока жив хотя бы один источник: `for a != nil || b != nil`. Целиком слияние ты соберёшь в домашке, и её тест ловит вариант с флагами вместо `nil`: такой `select` продолжает выбирать закрытый канал и жжёт процессор.

## for-select и выход из цикла

Типичный воркер это бесконечный `for` с `select` внутри: ждём работу или сигнал остановки.

```go
func worker(jobs <-chan Job, done <-chan struct{}) {
	for {
		select {
		case j := <-jobs:
			process(j)
		case <-done:
			return
		}
	}
}
```

Выходить из такого цикла надо через `return` или `break` с меткой. Обычный `break` внутри `select` выходит **только из `select`**, а цикл продолжается. Как это выглядит в программе, смотри в задаче в конце урока. Правильный выход через метку:

```go
loop:
	for {
		select {
		case v, ok := <-ch:
			if !ok {
				break loop // выходит из for
			}
			handle(v)
		}
	}
```

## Таймауты

Ждать вечно в бэкенде нельзя: зависший внешний сервис не должен вешать твой. Стандартный таймаут на `select`:

```go
select {
case res := <-result:
	return res, nil
case <-time.After(2 * time.Second):
	return nil, errors.New("timeout")
}
```

`time.After(d)` возвращает канал, в который через `d` придёт текущее время. Это то же самое, что `time.NewTimer(d).C`.

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	ch := make(chan int)
	go func() {
		time.Sleep(50 * time.Millisecond)
		ch <- 42
	}()
	select {
	case v := <-ch:
		fmt.Println("получили", v)
	case <-time.After(10 * time.Millisecond):
		fmt.Println("таймаут")
	}
}
// таймаут
```

Обрати внимание на скрытую утечку в этом примере: после таймаута горутина пытается отправить `42` в небуферизованный канал, который больше никто не читает, и висит вечно. В `main` это неважно (процесс завершается), а в сервисе так течёт по горутине на каждый таймаут. Лечится буфером: `ch := make(chan int, 1)`.

В реальном коде таймауты чаще задают через `context.WithTimeout`: он передаётся вниз по стеку вызовов и отменяет сразу всё дерево операций. Это тема следующего урока.

::: trap time.After в цикле
Плохо: общий дедлайн «соберём, сколько успеем за секунду» через `time.After` внутри цикла.

```go
for {
	select {
	case v := <-in:
		out = append(out, v)
	case <-time.After(time.Second): // новый таймер на КАЖДОЙ итерации
		return out
	}
}
```

Вспомни правило: выражения веток вычисляются при каждом входе в `select`. Каждое пришедшее значение запускает новый цикл, а значит новый таймер на целую секунду. Если значения идут чаще раза в секунду, таймаут не наступит никогда. Здесь `time.After` означает «секунда тишины», а не «секунда всего».

Хорошо: один дедлайн на весь цикл, созданный **до** него. Например, через `context` (подробно в следующем уроке), у которого канал `Done()` закрывается по истечении срока:

```go
ctx, cancel := context.WithTimeout(ctx, time.Second)
defer cancel()
for {
	select {
	case v := <-in:
		out = append(out, v)
	case <-ctx.Done(): // один и тот же канал на каждой итерации
		return out
	}
}
```

Тот же приём работает и с таймером из пакета `time`: создай его один раз до цикла и жди его канал в той же ветке. Как именно, ты соберёшь сам в домашке `CollectUntil`.

Если по смыслу нужен именно таймаут простоя («секунда без новых значений»), `time.After` в цикле корректен, но тогда это осознанное решение, и его стоит подписать комментарием.

Раньше у этой ловушки была вторая половина: до Go 1.23 таймер `time.After` не собирался сборщиком мусора, пока не сработает. Цикл с `time.After(time.Hour)`, проходящий миллион итераций, держал в памяти миллион таймеров на час. С Go 1.23 неостановленные таймеры без ссылок сразу становятся доступны сборщику мусора и уходят на ближайшей сборке. Я проверил на Go 1.27: миллион итераций с `time.After(time.Hour)`, после `runtime.GC()` `HeapInuse` около 0 МБ. Утечки памяти больше нет, логическая ошибка с дедлайном осталась.
:::

## Таймеры в Go 1.23 и новее

В Go 1.23 таймеры (`time.Timer`, `time.Ticker`) получили два изменения, и о них спрашивают, потому что старые статьи учат обходным приёмам, которые теперь не нужны.

**Первое: сборка мусора.** Таймер или тикер, на который больше нет ссылок, собирается сразу, даже если `Stop` не вызвали. Документация `time.After` теперь прямо говорит: нет причин предпочитать `NewTimer`, когда хватает `After`. `Stop` всё ещё полезен как явное намерение и чтобы не держать таймер до сборки.

**Второе: канал таймера стал небуферизованным** (ёмкость 0 вместо 1). Главное следствие: после `Stop` или `Reset` из канала **гарантированно** не придёт устаревшее значение от старой настройки таймера.

Как было раньше: таймер срабатывал и клал время в буфер на одно значение. Если ты потом вызывал `Reset`, это старое значение оставалось в буфере, и следующий `<-t.C` срабатывал мгновенно, хотя новый срок не прошёл. Поэтому писали заклинание:

```go
if !t.Stop() {
	<-t.C // вычерпать старое значение
}
t.Reset(d)
```

И это заклинание само было ловушкой: если значение уже кто-то прочитал, `<-t.C` висел вечно.

Как стало. Проверь сам:

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	t := time.NewTimer(10 * time.Millisecond)
	time.Sleep(30 * time.Millisecond) // таймер уже сработал
	t.Reset(time.Hour)
	select {
	case <-t.C:
		fmt.Println("старое значение")
	default:
		fmt.Println("канал пуст")
	}
	fmt.Println(len(t.C), cap(t.C))
}
```

<Predict :options="['старое значение, затем 1 1', 'канал пуст, затем 0 0', 'канал пуст, затем 0 1', 'дедлок']" :correct="1">

В Go 1.23+ после `Reset` старое срабатывание отменяется, канал пуст, и `len`/`cap` канала таймера равны 0. До 1.23 здесь было бы `старое значение` и `1 1`. Ещё одно следствие: `t.Stop()` для таймера, который уже «сработал», но значение которого никто не прочитал, теперь возвращает `true` (я проверил: `Stop: true`, и канал после этого пуст). Документация `Timer.Stop`: если программа ещё не получила значение из `t.C` и таймер ещё не остановлен, `Stop` гарантированно вернёт `true`. Повторный `Stop` по-прежнему вернёт `false`. Поэтому `<-t.C` после `Stop` больше не нужен.

</Predict>

Нюанс совместимости. В Go 1.23-1.26 новое поведение включалось, только если в `go.mod` стоит `go 1.23` или новее, и его можно было откатить через `GODEBUG=asynctimerchan=1`. В Go 1.27 эту настройку удалили: каналы таймеров теперь синхронные всегда, независимо от версии в `go.mod`. Я проверил на модуле с `go 1.22` под тулчейном 1.27: вывод тот же, `канал пуст` и `0 0`. Ещё одно видимое изменение: проверка `len(t.C) > 0`, «пришло ли время», теперь всегда даёт ложь, вместо неё нужно неблокирующее получение через `select` с `default`.

### Готовое значение против мгновенного таймаута

Случайный выбор между готовыми ветками бьёт и по таймаутам. Что если значение уже лежит в канале, а таймаут нулевой?

```go
ch := make(chan int, 1)
ch <- 1
select {
case <-ch:
	// значение
case <-time.After(0):
	// таймаут
}
```

Обе ветки готовы почти сразу, и выбор случаен. Я прогнал это 10 000 раз: таймаут выиграл 4931 и 5003 раза на двух запусках, то есть примерно в половине случаев готовое значение «потерялось». Если готовое значение важнее, проверь его отдельно до ожидания: сначала неблокирующий `select` с `default`, потом `select` с таймером.

::: hood Как устроен select внутри
Компилятор сначала упрощает частные случаи. `select` с одной веткой без `default` это обычная операция с каналом. Одна ветка плюс `default` превращается в вызов `selectnbsend` или `selectnbrecv` из `runtime/chan.go`: та же отправка или получение, но с флагом «не блокироваться».

Общий случай обрабатывает `runtime.selectgo`:

1. **Порядок опроса (pollorder).** Ветки перемешиваются случайно (`cheaprandn`). Отсюда равновероятный выбор среди готовых.
2. **Порядок блокировки (lockorder).** Мьютексы всех каналов захватываются в порядке их адресов в памяти. Если бы две горутины делали `select` по одним и тем же каналам и захватывали их в разном порядке, они бы взаимно заблокировались; сортировка по адресу это исключает.
3. **Проход 1.** Под всеми замками каналы проверяются в случайном порядке опроса. Первая готовая ветка выполняется, замки отпускаются.
4. **Ничего не готово, есть `default`:** отпустить замки, выполнить `default`.
5. **Ничего не готово, нет `default`:** горутина встаёт в очередь ожидания **каждого** канала (свой `sudog` на каждую ветку) и паркуется.
6. **Пробуждение.** Когда какой-то канал сработал, горутина просыпается, снова захватывает все замки и убирает себя из очередей остальных каналов.

Поэтому `select` на десяти каналах дороже операции с одним каналом: замки всех каналов, перемешивание, постановка во все очереди. На горячем пути с огромным числом итераций это заметно, в обычном коде нет.
:::

## Что выведет программа?

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	timeouts := 0
	for range 10000 {
		ch := make(chan int, 1)
		ch <- 1
		select {
		case <-ch:
		case <-time.After(0):
			timeouts++
		}
	}
	fmt.Println(timeouts)
}
```

<Predict :options="['программа сразу завершится', 'fatal error: all goroutines are asleep - deadlock!', 'ошибка компиляции: пустой select', 'panic: empty select']" :correct="1">

Пустой `select` ждёт вечно. Других горутин нет, рантайм видит, что все спят: `fatal error: all goroutines are asleep - deadlock!` и `goroutine 1 [select (no cases)]`. Компилятор такое разрешает.

```go
package main

import "fmt"

func main() {
	ch := make(chan int)
	close(ch)
	n := 0
	for {
		select {
		case <-ch:
			n++
			if n == 3 {
				break
			}
		}
		if n > 1_000_000 {
			fmt.Println("цикл не прервался, n =", n)

		}

```

Закрытый канал всегда готов, `n` растёт, и выходим мы только через страховочное условие: `цикл не прервался, n = 1000001`. Без страховки программа крутилась бы вечно на 100% CPU. <details><summary>Как select выбирает ветку, если готовы несколько?</summary>

Случайно и равновероятно (спецификация: uniform pseudo-random selection). Порядок веток в коде роли не играет. Внутри `selectgo` ветки перемешиваются перед опросом. Сделано, чтобы ни одна ветка не голодала. Если приоритет нужен, его реализуют явно: сначала неблокирующий `select` по важному каналу, потом общий.

</details>
<details><summary>Что делает default в select и когда он опасен?</summary>

Если ни одна ветка не готова, выполняется `default` вместо блокировки. Так делают неблокирующие отправку и получение. Опасен в `for` без другой работы: получается busy loop на 100% CPU. Если ждать можно, `default` не нужен.

</details>
<details><summary>Что будет при select {} и при select, где все каналы nil?</summary>

`select {}` блокируется навсегда. Ветки с nil-каналами никогда не готовы, поэтому `select` из одних nil-веток без `default` тоже блокируется навсегда. Если других живых горутин нет, рантайм завершит программу с `all goroutines are asleep - deadlock!`. С `default` выполнится `default`.

</details>
<details><summary>Зачем присваивать каналу nil внутри for-select?</summary>

Чтобы выключить ветку. Закрытый канал всегда готов к чтению, и `select` будет снова и снова выбирать его, крутясь вхолостую. Присвоив переменной канала `nil`, ты делаешь ветку вечно неготовой, и `select` ждёт только на живых каналах. Классика: слияние нескольких каналов, где источники закрываются в разное время.

</details>
<details><summary>Почему break внутри select не выходит из цикла?</summary>

`break` без метки прерывает ближайший `for`, `switch` или `select`. Внутри `select` это сам `select`. Выйти из цикла можно через `return` или `break` с меткой на `for`.

</details>
<details><summary>Что не так с time.After внутри цикла?</summary>

Логически: выражения веток вычисляются при каждом входе в `select`, поэтому каждая итерация создаёт новый таймер, и дедлайн сбрасывается при каждом событии. Получается «таймаут простоя», а не «общий таймаут»; при частых событиях он не наступит никогда. Для общего дедлайна создают один `time.NewTimer` (или `context.WithTimeout`) до цикла. Исторически была ещё утечка памяти: до Go 1.23 таймер не собирался, пока не сработает. С 1.23 неостановленные таймеры без ссылок сразу становятся доступны сборщику мусора.

</details>
<details><summary>Что изменилось в таймерах в Go 1.23?</summary>

Два изменения. Первое: таймеры и тикеры без ссылок собираются GC, даже без `Stop`. Второе: канал таймера стал небуферизованным (`cap` 0), и после `Stop`/`Reset` гарантированно не придёт устаревшее значение. Ушло заклинание `if !t.Stop() { <-t.C }`: если значение ещё не прочитано и таймер не останавливали, `Stop` вернёт `true`. `len(t.C)` теперь всегда 0, проверять готовность надо неблокирующим получением. В 1.23-1.26 поведение зависело от версии в `go.mod` и `GODEBUG=asynctimerchan`, в 1.27 настройку удалили и поведение всегда новое.

</details>
<details><summary>Вычисляются ли выражения в невыбранных ветках select?</summary>

Да. При входе в `select` один раз и сверху вниз вычисляются все выражения каналов и все отправляемые значения, независимо от того, какая ветка выберется. Поэтому дорогое значение в `case ch <- expensive():` посчитается, даже если сработает `default`, а `time.After` создаст таймер при каждом входе.

</details>
<details><summary>Как сделать таймаут на операцию с каналом и не устроить утечку?</summary>

`select` с веткой результата и веткой `time.After` или `ctx.Done()`. Утечка возникает на стороне отправителя: если по таймауту мы ушли, горутина, которая позже попробует отправить результат в небуферизованный канал, зависнет навсегда. Решение: канал результата с буфером 1 (отправка всегда пройдёт) или отправка тоже через `select` с отменой.

</details>
:::
