# Планировщик GMP под капотом

Ты уже запускал тысячи горутин и ни разу не думал, на каком ядре и в каком потоке они исполняются. Это заслуга планировщика: части рантайма, которая раскладывает горутины по потокам операционной системы. Он вкомпилирован в каждый Go-бинарник, тот самый «рантайм» из урока про инструменты, из-за которого hello world весит 2 МБ.

Зачем бэкендеру знать, как он устроен? Во-первых, это один из самых частых вопросов на собесе: «расскажи про GMP», «что происходит, когда горутина делает блокирующий системный вызов», «как 10 000 соединений обслуживаются десятком потоков», «что такое GOMAXPROCS и почему в Kubernetes с ним были проблемы». Во-вторых, это объясняет реальные эффекты в продакшне: почему сервис в контейнере с лимитом в 2 CPU получал всплески задержек, почему в программе 40 потоков при `GOMAXPROCS=8`, почему бесконечный цикл без вызовов функций до Go 1.14 мог подвесить программу.

Урок плотный, но после него ты сможешь нарисовать схему планировщика на доске и объяснить каждую стрелку. Факты сверены с исходниками рантайма Go 1.27 (`src/runtime/proc.go`, `runtime2.go`), поэтому где-то будут ссылки на конкретные функции: открой и посмотри сам.

## Зачем Go свой планировщик

Поток операционной системы дорогой:

- стек фиксированного размера: от сотен килобайт до 8 МБ виртуальной памяти в зависимости от ОС;
- создание и уничтожение идут через ядро;
- переключение между потоками это переход в ядро, сохранение всех регистров, работа планировщика ОС: порядка микросекунд, плюс промахи кешей.

Горутина дешёвая:

- стек стартует с 2 КБ (`stackMin = 2048` в `runtime/stack.go`) и растёт по мере надобности;
- создаётся и переключается в пространстве пользователя, без ядра: сохранить надо всего несколько регистров (PC, SP и ещё пару);
- планировщик Go знает, **почему** горутина остановилась (ждёт канал, мьютекс, сеть), и будит её ровно тогда, когда событие случилось.

| | Поток ОС | Горутина |
|---|---|---|
| Стек | сотни КБ - 8 МБ, фиксированный | от 2 КБ, растёт |
| Создание | системный вызов | аллокация в рантайме |
| Переключение | через ядро, ~мкс | в user space, ~сотни нс |
| Сколько можно | тысячи | сотни тысяч и миллионы |
| Кто планирует | ОС, вытесняюще | рантайм Go |

Модель называется **M:N**: M горутин исполняются на N потоках ОС. Планировщик решает, какую горутину на каком потоке запустить.

## Три буквы: G, M, P

**G (goroutine)**: горутина. Структура `g` в `runtime2.go`: стек, сохранённые регистры (`gobuf`: PC, SP), статус и служебные поля. Основные статусы:

```text
_Grunnable   готова к запуску, стоит в очереди
_Grunning    исполняется прямо сейчас на каком-то M
_Gwaiting    заблокирована: канал, мьютекс, сеть, sleep
_Gsyscall    в системном вызове
_Gdead       завершилась (структура переиспользуется для новых горутин)
```

**M (machine)**: поток операционной системы. Именно M выполняет машинный код. Потоков может быть больше, чем ядер: часть сидит в системных вызовах, часть спит в резерве. Лимит по умолчанию 10 000 (`sched.maxmcount`), меняется через `debug.SetMaxThreads`; превышение роняет программу.

**P (processor)**: логический процессор, «право исполнять Go-код». У P есть:

- локальная очередь готовых горутин на 256 мест (`runq [256]guintptr`);
- слот `runnext` для одной «следующей» горутины;
- кеш памяти для аллокатора (`mcache`), таймеры и прочее.

Количество P равно `GOMAXPROCS`. Чтобы выполнять Go-код, M обязан держать P. Поэтому `GOMAXPROCS` это ровно «сколько горутин могут исполняться **одновременно**».

Аналогия, которая точно ложится на механику. P это **верстак** с инструментами и стопкой заказов. M это **рабочий**. G это **заказ**. Работать без верстака нельзя. Верстаков ровно `GOMAXPROCS`. Рабочих может быть больше: если рабочий ушёл ждать поставку (системный вызов), его верстак отдают другому рабочему, чтобы заказы не простаивали.

```text
          GOMAXPROCS = 3
   ┌──────────┐   ┌──────────┐   ┌──────────┐
   │   P0     │   │   P1     │   │   P2     │
   │ runnext  │   │ runnext  │   │ runnext  │
   │ [G][G][G]│   │ [G]      │   │ []       │   ← локальные очереди
   └────┬─────┘   └────┬─────┘   └────┬─────┘
        │              │              │
       M0             M3             M5           ← потоки ОС, держат P
       │              │              │
     G(run)         G(run)         G(run)

   глобальная очередь: [G][G]          M1, M2 в syscall, M4 спит (без P)
   sysmon: отдельный M без P, следит за всеми
```

### Зачем вообще нужен P

До Go 1.1 никакого P не было: потоки M брали горутины из одной **глобальной** очереди под одним мьютексом. На многоядерных машинах этот мьютекс становился бутылочным горлышком, а кеши аллокатора висели на каждом M, включая спящие в системных вызовах. Дмитрий Вьюков переписал планировщик: появился P с локальной очередью без блокировок, а ресурсы, нужные только для исполнения Go-кода, переехали с M на P. Поток, ушедший в системный вызов, отдаёт P вместе со всеми этими ресурсами.

## Очереди

У горутины, готовой к запуску, три возможных места:

1. **`runnext` текущего P**: одна горутина, которая пойдёт следующей.
2. **Локальная очередь P**: кольцевой буфер на 256 горутин. Владелец P кладёт и берёт без мьютекса, а другие P могут красть из неё атомарными операциями.
3. **Глобальная очередь**: связный список под мьютексом `sched.lock`. Туда попадают переполнение локальных очередей, вытесненные горутины, горутины, вернувшиеся из системного вызова без свободного P.

Что происходит на `go f()` (функции `newproc` и `runqput`):

- новая G кладётся в **`runnext`** текущего P;
- если там уже была горутина, прежняя переезжает в **хвост** локальной очереди;
- если локальная очередь полна (256), половина очереди (128) вместе с вытесненной горутиной переезжает в глобальную (`runqputslow`).

Зачем `runnext`? Типичный сценарий: горутина отправила значение в канал и разбудила получателя, или породила горутину и сейчас заблокируется в ожидании. Новая горутина, скорее всего, нужна прямо сейчас, и её данные ещё горячие в кеше. `runnext` даёт ей запуститься без очереди. Горутина из `runnext` наследует оставшийся квант времени текущей, поэтому две горутины, будящие друг друга по очереди, не могут бесконечно «съедать» P.

```go
runtime.GOMAXPROCS(1)
var wg sync.WaitGroup
for i := range 3 {
	wg.Go(func() { fmt.Print(i) })
}
wg.Wait()
fmt.Println()
```

## Как P ищет работу

Когда текущая горутина заблокировалась, завершилась или была вытеснена, M вызывает `schedule()`, а тот `findRunnable()`. Порядок поиска (сокращённо, по исходнику):

```text
findRunnable(P):
  1. каждый 61-й тик: одна G из ГЛОБАЛЬНОЙ очереди    ← честность
  2. runnext, затем голова ЛОКАЛЬНОЙ очереди
  3. ГЛОБАЛЬНАЯ очередь пачкой: до min(len/GOMAXPROCS+1, 128) горутин
  4. netpoll без ожидания: горутины, чьи сокеты готовы
  5. КРАЖА у других P (work stealing)
  6. ничего нет: ещё раз проверить всё, отдать P в список простаивающих,
     усыпить M (возможно, заблокировавшись в netpoll)
```

**Почему 61.** Если две горутины постоянно будят друг друга, локальная очередь никогда не опустеет, и до глобальной дело не дойдёт: горутина в ней будет голодать. Поэтому раз в 61 тик (тик это одно решение планировщика на этом P) P сначала смотрит в глобальную очередь. 61 простое число: так проверка не входит в резонанс с периодическими паттернами в программе. Комментарий в исходнике прямо говорит про эту проблему: «two goroutines can completely occupy the local runqueue by constantly respawning each other».

**Пачка из глобальной очереди.** Брать по одной горутине под глобальным мьютексом дорого, поэтому P забирает сразу несколько и перекладывает в свою локальную очередь. Делитель `GOMAXPROCS` нужен, чтобы один P не утащил всё и другим досталось.

## Work stealing

Если у P пусто везде, он ворует у соседей (`stealWork`):

- до 4 проходов по всем P в **случайном** порядке (случайность уменьшает конкуренцию: воры не ломятся к одной жертве);
- у жертвы забирается **половина** локальной очереди (`runqgrab`: `n - n/2`, с округлением вверх) одной атомарной операцией;
- `runnext` жертвы крадут только на последнем проходе и только если её очередь пуста: это последний резерв, ведь `runnext` скорее всего вот-вот запустится там, где лежит.

Почему половину, а не одну? Одна горутина: вор быстро опустеет и придёт снова, лишние атомарные операции. Всё: ограбленный P тут же сам пойдёт воровать. Половина выравнивает нагрузку за логарифмическое число краж.

**Spinning-потоки.** M, который ищет работу, некоторое время «крутится» (spinning), а не засыпает сразу: заснуть и проснуться дорого, а новая работа часто появляется через микросекунды. Чтобы не жечь CPU впустую, рантайм ограничивает число крутящихся M половиной занятых P. Когда появляется новая горутина и есть простаивающий P, а крутящихся потоков нет, рантайм будит или создаёт M (`wakep`).

## Когда горутина уступает процессор

Горутина отдаёт P в двух случаях.

**Сама, в точке переключения.** Блокирующая операция с каналом, мьютекс, `time.Sleep`, сетевой ввод-вывод, `runtime.Gosched()`, завершение горутины. Всё это вызовы в рантайм, который паркует горутину (`gopark`) и вызывает `schedule()`.

**Принудительно: вытеснение.** Горутина, которая просто считает и никуда не ходит, сама не уступит. Её вытесняет **sysmon**, фоновый поток без P (о нём ниже). Если горутина работает на одном P дольше **10 мс** (`forcePreemptNS` в `proc.go`), sysmon просит её уступить:

1. **Кооперативно.** Выставляет горутине флаг `stackguard0 = stackPreempt`. Каждая функция в прологе проверяет, хватает ли стека, и этот флаг делает проверку «неудачной»: горутина заходит в рантайм и вместо роста стека уступает P. Работает, только если горутина вызывает функции, и не любые: маленьким листовым функциям (которые сами никого не зовут) компилятор пролог с проверкой не вставляет.
2. **Асинхронно, с Go 1.14.** Если функций в цикле нет, кооперативная проверка никогда не сработает. Тогда sysmon посылает потоку сигнал (`SIGURG` на Unix, `sigPreempt` в `signal_unix.go`). Обработчик сигнала проверяет, что горутина в безопасной точке (где сборщик мусора может разобрать стек), и меняет сохранённый контекст потока так, будто горутина сама вызвала функцию `asyncPreempt`. Та сохраняет все регистры и уходит в планировщик.

Вытесненная горутина кладётся в **глобальную** очередь, чтобы не занять тот же P снова и дать шанс остальным.

```go
runtime.GOMAXPROCS(1)
go func() {
	for {
	}
}()
time.Sleep(10 * time.Millisecond)
fmt.Println("готово")
```

## Системные вызовы и handoff P

Горутина вызывает `read` для файла, и поток уходит в ядро. Пока ядро не ответит, **M заблокирован**, и Go ничего не может с этим сделать. Но P с очередью горутин простаивать не должен.

Механика (`entersyscall`, `exitsyscall`, `retake` в `proc.go`):

1. **Вход в вызов.** Горутина переходит в `_Gsyscall`, M продолжает формально держать P. Это оптимистичный путь: большинство системных вызовов короткие, и отдавать P на каждый было бы дорого.
2. **sysmon следит.** Если P застрял в системном вызове дольше одного тика sysmon (не меньше 20 мкс) и при этом есть чем заняться (локальная очередь не пуста или нет свободных P и крутящихся M), sysmon **отбирает P** и передаёт его другому M (`handoffp`): спящему из резерва или новому. Даже если работы нет, через 10 мс P всё равно отберут.
3. **Выход из вызова.** Поток вернулся из ядра и пытается продолжить:
   - свой P ещё при нём: просто продолжает, это быстрый путь;
   - P отобрали: пытается взять свой старый P, если тот свободен, или любой простаивающий;
   - свободных P нет: горутина уходит в **глобальную** очередь, а M засыпает в резерве.

Для вызовов, про которые заранее известно, что они долгие, рантайм отдаёт P сразу (`entersyscallblock`). Вызовы cgo устроены так же, как системные: поток уходит в C-код, P может быть передан.

Отсюда практический вывод: **потоков в Go-программе может быть намного больше, чем `GOMAXPROCS`**. Сотня горутин, читающих медленный NFS, это сотня заблокированных потоков. Посмотреть: `GODEBUG=schedtrace=1000` покажет `threads=...`.

## Netpoller: почему сеть не блокирует потоки

С сетью всё иначе, и это главный козырь Go для серверов. Сокеты рантайм переводит в **неблокирующий** режим. Когда горутина читает из сокета, а данных нет:

1. системный вызов `read` сразу возвращает `EAGAIN`, поток не блокируется;
2. горутина паркуется в состоянии `_Gwaiting`, а сокет зарегистрирован в **netpoller**: обёртке над `epoll` (Linux), `kqueue` (macOS, BSD) или IOCP (Windows);
3. M с P идут выполнять другие горутины;
4. когда ядро сообщает, что сокет готов, горутина снова становится `_Grunnable` и попадает в очередь.

Кто спрашивает netpoller, есть ли готовые сокеты:

- `findRunnable` перед кражей (шаг 4 выше) и в самом конце, когда работы нет: тогда M может заблокироваться в `epoll_wait` до первого события;
- sysmon, если сеть не опрашивали дольше 10 мс.

Итог: 10 000 открытых соединений это 10 000 горутин, спящих в netpoller, и несколько потоков. Код при этом выглядит синхронным (`conn.Read(buf)`), без колбэков и `async/await`. Вся асинхронность спрятана в рантайме.

С файлами на диске так не получится: `epoll` не работает с обычными файлами, поэтому чтение файла это настоящий блокирующий системный вызов с handoff P из предыдущего раздела.

## sysmon: надзиратель

`sysmon` это отдельный поток, работающий **без P** (ему не нужно исполнять Go-код пользователя). В цикле он спит от 20 мкс, а если долго ничего не происходит, удваивает паузу до 10 мс. Его обязанности:

- `retake`: вытеснять горутины, работающие дольше 10 мс, и отбирать P у потоков в системных вызовах;
- опрашивать netpoller, если его давно никто не опрашивал;
- запускать принудительный GC, если его не было 2 минуты;
- раз в секунду пересчитывать GOMAXPROCS по доступным CPU и cgroup-лимиту (с Go 1.25);
- будить фоновый возврат памяти ОС (scavenger).

Главный цикл планировщика:

```text
schedule():                    // выполняется на g0 текущего M
    gp := findRunnable()       // блокируется, пока не найдёт работу
    execute(gp):
        gp.status = _Grunning
        P.schedtick++          // если gp не унаследовал квант из runnext
        gogo(&gp.sched)        // восстановить регистры gp и прыгнуть в его код

горутина блокируется (канал, мьютекс...):
    gopark() → mcall(park_m)   // переключиться на g0
        gp.status = _Gwaiting
        schedule()             // и по кругу

горутину будят (другая горутина отправила в канал):
    goready(gp) → runqput(P, gp, next=true)   // в runnext будящего P
```

Переключение между горутинами это `mcall` (на системный стек `g0`) и `gogo` (на стек новой горутины): несколько инструкций на ассемблере, никакого ядра.
:::

## GOMAXPROCS и контейнеры

`GOMAXPROCS` задаёт число P. Узнать текущее значение: `runtime.GOMAXPROCS(0)` (аргумент меньше 1 ничего не меняет и просто возвращает текущее).

**По умолчанию** (документация `runtime.GOMAXPROCS`, Go 1.27) берётся минимум из:

- числа логических CPU, доступных процессу (с учётом CPU affinity);
- на Linux: **лимита CPU из cgroup** (квота / период), округлённого вверх; если лимит меньше 2, берётся 2 (но не больше, чем есть CPU).

Учёт cgroup появился в **Go 1.25**. До этого Go видел все ядра машины. Классическая проблема: под в Kubernetes с `limits.cpu: 2` на ноде с 64 ядрами получал `GOMAXPROCS=64`. CFS-квота считается за период (обычно 100 мс): 64 потока выедали квоту в 2 CPU × 100 мс за первые ~3 мс периода, а оставшиеся ~97 мс контейнер стоял **задушенным** (throttled). Снаружи это выглядело как случайные всплески задержки на десятки миллисекунд. Лечили библиотекой `go.uber.org/automaxprocs` или ручным `GOMAXPROCS` в env.

Детали поведения с 1.25:

- учитывается только **limit**, не **request**: request это гарантированный минимум, а без лимита контейнер может использовать свободные ядра ноды;
- рантайм **периодически** перепроверяет число CPU и лимит и меняет GOMAXPROCS на лету (sysmon, раз в секунду);
- всё это отключается, если GOMAXPROCS задан явно через env или `runtime.GOMAXPROCS(n)`; вернуть дефолт можно через `runtime.SetDefaultGOMAXPROCS()`;
- явные выключатели: `GODEBUG=containermaxprocs=0` и `updatemaxprocs=0`;
- новое поведение включается, только если в `go.mod` модуля стоит `go 1.25` или выше. Для старых значений директивы `go` по умолчанию остаётся `containermaxprocs=0`. Частая ловушка: обновил тулчейн, а `go.mod` не поднял.

Стоит ли ставить GOMAXPROCS больше числа ядер для I/O-нагрузки? Обычно нет. Горутины, ждущие сеть, P не занимают (они в netpoller), а для блокирующих системных вызовов рантайм сам отдаёт P другим потокам. Лишние P только добавят переключений.

## Как подсмотреть за планировщиком

**`GODEBUG=schedtrace=N`** печатает состояние раз в N миллисекунд. Вот строка из запуска с `schedtrace=500`: программа с 20 горутинами, которые 1.5 секунды крутят CPU, на маке с 10 ядрами, отметка 512 мс:

```text
SCHED 512ms: gomaxprocs=10 idleprocs=0 threads=11 spinningthreads=0 needspinning=1 idlethreads=0 runqueue=8 [ 0 0 0 1 0 0 0 1 0 0 ] schedticks=[ 21 16 17 18 18 18 18 19 20 21 ]
```

- `gomaxprocs=10`, `idleprocs=0`: все 10 P заняты;
- `threads=11`: 10 рабочих потоков плюс sysmon;
- `runqueue=8`: в **глобальной** очереди 8 горутин. Это вытесненные: 20 горутин на 10 P, каждые 10 мс sysmon выталкивает работающих в глобальную очередь;
- `[ 0 0 0 1 ... ]`: длины локальных очередей каждого P;
- `schedticks`: сколько решений принял каждый P: 16-21 за полсекунды, то есть горутина держит P в среднем 25-30 мс, а не 10. Причина в sysmon: он засекает время, когда сам впервые увидел новый тик, а если ему долго не приходится отбирать P у системных вызовов, он удлиняет сон до 10 мс. 10 мс это минимальный квант, а не точный.

С `scheddetail=1` добавятся строки про каждый P, M и G. **`go tool trace`** даёт визуальную временную шкалу: какая горутина на каком P когда работала, где блокировалась, где была пауза GC. Метрики `runtime/metrics` с префиксом `/sched/` (в Go 1.26 добавили счётчики горутин по состояниям и число потоков) годятся для дашбордов.

::: trap Порядок запуска горутин
```go
// Плохо: «в тестах всегда печатало по порядку»
for i := range 3 {
	go fmt.Println(i)
}
time.Sleep(100 * time.Millisecond)
```

```go
// Хорошо: если порядок важен, его задают явно
results := make([]string, 3)
var wg sync.WaitGroup
for i := range 3 {
	wg.Go(func() { results[i] = fmt.Sprint(i) })
}
wg.Wait()
fmt.Println(strings.Join(results, " "))
```
Порядок зависит от `runnext`, числа P, кражи и вытеснения. С `-race` рантайм нарочно рандомизирует решения планировщика, чтобы такие предположения ломались в тестах, а не в продакшне.
:::

::: trap runtime.Gosched как синхронизация
```go
// Плохо: «дам горутине время отработать»
go setup()
runtime.Gosched()
use() // setup мог не закончиться: Gosched лишь отправляет текущую G в очередь
```

```go

	close(done)

<-done

```
`Gosched` не даёт никаких гарантий happens-before. В прикладном коде он почти никогда не нужен.
:::

::: trap Старый go.mod в контейнере
```go

```
Сборка новым тулчейном не включит cgroup-aware GOMAXPROCS: дефолтные GODEBUG-настройки берутся по директиве `go`. В контейнере с `--cpus=2` на 64-ядерной машине снова получишь `GOMAXPROCS=64` и троттлинг.

```go

```
Проверить в рантайме: залогируй `runtime.GOMAXPROCS(0)` при старте сервиса.
:::

::: trap Тысячи потоков из-за блокирующих вызовов
```go
// Плохо: 20 000 горутин читают файлы с медленного сетевого диска.
// Каждая держит поток в системном вызове: потоков становится тысячи,
// после 10 000 программа падает: "thread exhaustion".
for _, path := range paths {
	go process(path)
}
```

```go
// Хорошо: ограничить параллелизм блокирующей работы (пул или семафор)
sem := make(chan struct{}, 64)
for _, path := range paths {
	sem <- struct{}{}
	go func() {
		defer func() { <-sem }()
		process(path)
	}()
}
```
Горутины дешёвые, пока ждут в netpoller или на каналах. Горутина в блокирующем системном вызове или cgo стоит целый поток ОС.
:::

## Что выведет программа?

```go
prev := runtime.GOMAXPROCS(2)
fmt.Println(prev == runtime.NumCPU(), runtime.GOMAXPROCS(0), runtime.GOMAXPROCS(-5))
```

<Predict :options="['true 2 2', 'true 0 -5', 'false 2 2', 'паника: отрицательный GOMAXPROCS']" :correct="0">

`GOMAXPROCS(n)` возвращает **предыдущее** значение. На ноутбуке без контейнера и без переменной окружения дефолт равен числу CPU, поэтому `true`. Вызов с `n < 1` ничего не меняет и просто возвращает текущее: `2` и `2`. На Linux в контейнере с лимитом CPU первое значение было бы `false`: дефолт взялся бы из cgroup.

</Predict>

```go
runtime.GOMAXPROCS(1)
go fmt.Println("горутина")
runtime.Gosched()
fmt.Println("main")
```

<Predict :options="['горутина, затем main', 'main, затем горутина', 'только main']" :correct="0">

Новая горутина лежит в `runnext`. `Gosched` отправляет `main` в **глобальную** очередь и зовёт планировщик, который берёт `runnext`: печатается `горутина`, затем очередь доходит до `main`. В шести запусках из шести у меня так. Но это знание устройства, а не контракт: с `-race` или другим числом P порядок может отличаться.

</Predict>

::: interview
<details><summary>Что такое G, M и P? Зачем нужен P?</summary>

G: горутина (стек, регистры, статус). M: поток ОС, исполняет код. P: логический процессор, право исполнять Go-код, с локальной очередью на 256 горутин, слотом `runnext` и кешем аллокатора; их ровно `GOMAXPROCS`. P появился в Go 1.1 (дизайн Вьюкова): до этого все M брали горутины из одной глобальной очереди под мьютексом, что не масштабировалось. P дал локальные очереди без блокировок и позволил потоку в системном вызове отдать ресурсы исполнения другому потоку.

</details>
<details><summary>Как планировщик выбирает следующую горутину?</summary>

`findRunnable`: каждый 61-й тик сначала глобальная очередь (против голодания); затем `runnext` и локальная очередь; затем пачка из глобальной; затем netpoller без ожидания; затем кража у других P (до 4 проходов в случайном порядке, половина очереди, `runnext` в последнюю очередь); если ничего нет, P уходит в простаивающие, M засыпает, возможно в блокирующем netpoll.

</details>
<details><summary>Что такое work stealing и почему крадут половину?</summary>

Простаивающий P забирает горутины из локальной очереди другого P. Половина (с округлением вверх) выравнивает нагрузку быстро: вор не придёт снова через мгновение, а у жертвы остаётся работа. Порядок обхода случайный, чтобы воры не дрались за одну жертву. Число крутящихся в поиске работы потоков ограничено половиной занятых P.

</details>
<details><summary>Что происходит, когда горутина делает блокирующий системный вызов?</summary>

Горутина переходит в `_Gsyscall`, M блокируется в ядре, но формально держит P. sysmon замечает застрявший P (после 20 мкс при наличии работы, или после 10 мс в любом случае) и передаёт его другому M (handoff), создавая поток при необходимости. По возвращении M пытается вернуть свой или взять свободный P; если свободных нет, горутина идёт в глобальную очередь, а M засыпает. Поэтому потоков бывает больше, чем GOMAXPROCS.

</details>
<details><summary>Почему сетевой ввод-вывод не блокирует потоки?</summary>

Сокеты неблокирующие. Если данных нет, горутина паркуется, а дескриптор регистрируется в netpoller (`epoll`/`kqueue`/IOCP). M продолжает выполнять другие горутины. Готовые сокеты проверяются в `findRunnable`, sysmon-ом и в блокирующем netpoll простаивающего M; разбуженные горутины встают в очередь. Код при этом выглядит синхронным.

</details>
<details><summary>Как работает вытеснение горутин? Что изменилось в Go 1.14?</summary>

sysmon помечает горутину, работающую дольше 10 мс. Кооперативно: выставляет `stackguard0 = stackPreempt`, и горутина уступит при следующем вызове функции (проверка в прологе). С Go 1.14 асинхронно: потоку отправляется сигнал `SIGURG`, обработчик в безопасной точке подменяет возврат на `asyncPreempt`, который сохраняет регистры и уходит в планировщик. Раньше цикл без вызовов функций мог занять P навсегда и задерживать паузы GC. Вытесненная горутина идёт в глобальную очередь.

</details>
<details><summary>Что такое GOMAXPROCS? Что поменялось в Go 1.25 для контейнеров?</summary>

Число P, то есть сколько горутин одновременно исполняют Go-код. По умолчанию число доступных CPU. С Go 1.25 на Linux учитывается лимит CPU cgroup (квота/период, округление вверх, минимум 2), только limit, не request; значение периодически пересчитывается. Отключается, если GOMAXPROCS задан явно, или через `GODEBUG=containermaxprocs=0`/`updatemaxprocs=0`; включается для модулей с `go 1.25`+ в `go.mod`. Раньше в контейнере брались все ядра ноды, что приводило к CFS-троттлингу и всплескам задержек; лечили `automaxprocs`.

</details>
<details><summary>Что такое runnext и зачем он нужен?</summary>

Слот на одну горутину в P, которую запустят следующей, раньше локальной очереди. Туда попадает свежесозданная или разбуженная горутина: она скорее всего нужна прямо сейчас, а её данные горячие в кеше. Горутина из `runnext` наследует квант текущей, поэтому пара горутин, будящих друг друга, не захватит P навсегда. При краже `runnext` трогают в последнюю очередь.

</details>
<details><summary>Чем горутина отличается от потока ОС?</summary>

Стек от 2 КБ с ростом против фиксированных сотен килобайт или мегабайт; создание и переключение в пространстве пользователя за сотни наносекунд против системных вызовов и микросекунд; планирует рантайм Go, который знает причину блокировки и не тратит поток на ожидание сети. Горутины исполняются поверх потоков по модели M:N.

</details>
:::

**Конкурентный чекер ссылок.** Утилита получает список URL, проверяет их параллельно с ограничением числа одновременных запросов, с таймаутом на каждый запрос и корректной отменой по Ctrl+C, а потом печатает отчёт в исходном порядке. Такие утилиты реально используют: проверить битые ссылки в документации, прогреть кеш, сделать smoke-тест после деплоя. В ней собран весь модуль: горутины, семафор или пул, `context` с таймаутами и отменой, сбор результатов по индексу, отсутствие утечек.

### Часть 1. Ядро с тестами

Пакет `homework/m04/project-linkcheck/`, файл `linkcheck.go`. Реализуй `Result.OK` и `Check(ctx, urls, opts)`. Контракт подробно описан в комментариях, кратко:

- результаты в порядке входа, `len(results) == len(urls)`;
- не больше `opts.Concurrency` запросов одновременно (меньше 1 значит 1);
- таймаут `opts.Timeout` на каждую ссылку, включая чтение тела;
- запросы через `opts.Client` (если `nil`, `http.DefaultClient`);
- при отмене `ctx` идущие запросы прерываются, новые не начинаются, `Check` возвращается сразу;
- ни одной горутины после возврата.

```bash
cd homework && go test -v -race ./m04/project-linkcheck/
```

Тесты используют настоящий `httptest.NewServer` и `httptest.NewTestServer` (Go 1.27) внутри `testing/synctest`: сеть в памяти, время фейковое, поэтому проверки «сервер видел ровно 3 одновременных запроса» и «Check вернулся ровно через 1.5 секунды после отмены» детерминированы. Если тест упал с `deadlock`, у тебя утекла горутина: смотри стек в выводе.

### Часть 2. CLI

Полного эталона нет, это твоя работа. Сделай `homework/m04/project-linkcheck/cmd/linkcheck/main.go`, который использует ядро.

Требования:

- запуск: `linkcheck [-c 8] [-timeout 5s] [файл]`. Без файла URL читаются из stdin. По одному URL в строке; пустые строки и строки, начинающиеся с `#`, пропускаются;
- флаги через пакет `flag`: `-c` (параллелизм, по умолчанию 8), `-timeout` (на одну ссылку, по умолчанию 5s, тип `time.Duration` через `flag.Duration`);
- Ctrl+C отменяет проверку через `signal.NotifyContext(ctx, os.Interrupt)`: утилита печатает отчёт по тому, что успела, и выходит;
- отчёт: по строке на ссылку в исходном порядке: `OK  200 https://go.dev` или `ERR 404 https://go.dev/nope` или `ERR   - http://localhost:1 (connection refused)`, в конце сводка `проверено 5, битых 2`;
- код выхода: 0, если все ссылки живые; 1, если есть битые или проверку прервали; 2 при ошибке аргументов (нет файла, неверный флаг);
- ошибки (файл не найден) в stderr, отчёт в stdout.

Чеклист приёмки (проверь каждый пункт руками):

- [ ] `go vet ./m04/project-linkcheck/...` чистый, тесты ядра зелёные с `-race`.
- [ ] Файл со строками `https://go.dev`, `https://go.dev/definitely-not-found`, `http://localhost:1`, пустой строкой и комментарием: две ошибки в отчёте, пустая строка и комментарий не проверялись, код выхода 1 (`echo $?`).
- [ ] `echo https://go.dev | go run ./m04/project-linkcheck/cmd/linkcheck` работает через stdin, код выхода 0.
- [ ] Таймаут: в соседнем терминале `nc -l 9999` (сервер принимает соединение и молчит). `-timeout 2s` с URL `http://localhost:9999` даёт ошибку таймаута примерно через 2 секунды, а не висит.
- [ ] Отмена: 20 URL на `http://localhost:9999` с `-timeout 1m -c 2`, через пару секунд Ctrl+C. Утилита сразу печатает отчёт, у всех ссылок ошибка отмены, код выхода 1.
- [ ] Параллелизм: 10 одинаковых медленных URL (тот же `nc` не подойдёт, он принимает одно соединение; напиши 10-строчный сервер с `time.Sleep(time.Second)` в хендлере) с `-c 5` проверяются примерно за 2 секунды, с `-c 1` примерно за 10.
- [ ] `-c 0`, `-c -3` не ломают утилиту (работает как 1), несуществующий файл даёт сообщение в stderr и код 2.
- [ ] Порядок строк в отчёте всегда совпадает с порядком во входном файле.

Со звёздочкой: флаг `-json` для вывода отчёта массивом JSON; дедупликация одинаковых URL (проверить один раз, вывести для всех строк); ограничение частоты запросов к одному хосту через `golang.org/x/time/rate`.
