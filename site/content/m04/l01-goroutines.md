# Горутины и WaitGroup

Конкурентность это то, ради чего Go вообще выбирают для бэкенда. HTTP-сервер на `net/http` обслуживает каждое соединение в отдельной горутине, фоновые воркеры River крутятся в горутинах, запросы к трём сервисам параллельно это три горутины. Ты будешь писать `go` почти в каждом сервисе, и почти каждая серьёзная авария в Go-коде связана с горутинами: утечки, гонки, паника в фоне, которая роняет весь процесс.

На собеседовании этот модуль спрашивают сильнее всего. Типовой набор: «чем горутина отличается от потока», «конкурентность и параллелизм это одно и то же?», «что выведет программа» с горутинами в цикле, «почему висит `wg.Wait()`». Отвечать надо не заученной фразой, а через механизм: что делает рантайм, когда ты пишешь `go f()`.

В этом уроке разбираем сами горутины и первый инструмент синхронизации: `sync.WaitGroup`, включая новый метод `wg.Go` из Go 1.25. Каналы, `select`, мьютексы и атомики идут в следующих уроках модуля.

## Горутина: функция, которая выполняется сама по себе

Горутина это функция, запущенная независимо от вызвавшего её кода. Синтаксис один: слово `go` перед вызовом.

```go
package main

import (
	"fmt"
	"time"
)

func say(s string) {
	for range 3 {
		fmt.Println(s)
		time.Sleep(10 * time.Millisecond)
	}
}

func main() {
	go say("горутина")
	say("main")
}
```

`go say("горутина")` не ждёт завершения `say`: оператор возвращается сразу, и `main` продолжает работу. Дальше две функции идут одновременно, и строки перемешаются в каком-то порядке. Каком именно, решает планировщик, и от запуска к запуску порядок может меняться.

Запомни три правила, на которых держится всё остальное:

1. **У горутины нет результата.** `x := go f()` не скомпилируется. Результат передают через канал, общую переменную под защитой или слайс, где у каждой горутины своя ячейка.
2. **Аргументы вычисляются сразу**, в вызывающей горутине, в момент выполнения оператора `go`. Сама функция выполнится позже.
3. **Программа живёт, пока живёт `main`.** Когда `main` возвращается, процесс завершается, и все остальные горутины умирают на месте, без `defer` и без предупреждений.

Третье правило самое коварное:

```go
package main

import "fmt"

func main() {
	go fmt.Println("из горутины")
}
```

<Predict :options="['из горутины', 'ничего не гарантировано, обычно пустой вывод', 'ошибка компиляции', 'fatal error: deadlock']" :correct="1">

`main` запускает горутину и тут же завершается, а вместе с ним процесс. Новая горутина почти никогда не успевает даже стартовать, поэтому на практике вывод пустой. Но формально это гонка: никакого обещания «не напечатает» язык не даёт. Правильный ответ на собесе: «вывод не гарантирован, нужно дождаться горутину, например через `WaitGroup`». Ставить `time.Sleep` в `main`, чтобы «подождать», это не синхронизация, а лотерея с хорошими шансами.

</Predict>

### Аргументы против замыкания

Второе правило полезно увидеть руками. Обычная функция с аргументом получает копию значения на момент `go`:

```go
package main

import (
	"fmt"
	"sync"
)

func show(wg *sync.WaitGroup, v int) {
	defer wg.Done()
	fmt.Println("аргумент:", v)
}

func main() {
	var wg sync.WaitGroup
	y := 1
	wg.Add(1)
	go show(&wg, y) // y вычислен здесь и сейчас
	y = 2
	wg.Wait()
	fmt.Println("y в main:", y)
}
```

Вывод всегда один и тот же: `аргумент: 1`, затем `y в main: 2`. Значение `y` скопировано в аргумент в момент оператора `go`, до `y = 2`, а гонки здесь нет вовсе: горутина не трогает переменную `y`, у неё своя копия. Будь вместо аргумента замыкание `go func() { fmt.Println(y) }()`, горутина читала бы ту же переменную, что `main` меняет, и это была бы гонка данных.

### Горутины в цикле и Go 1.22

Классика собеседований выглядела так:

```go
for i := 0; i < 3; i++ {
	go func() { fmt.Println(i) }()
}
```

До Go 1.22 переменная `i` была **одна на весь цикл**, все три замыкания ссылались на неё, и часто печаталось `3 3 3`. Лечили копией: `i := i` внутри тела или передачей `i` аргументом.

С Go 1.22 переменная цикла создаётся **заново на каждой итерации** (если в `go.mod` указано `go 1.22` или новее). Каждое замыкание захватывает свою копию, и проблема исчезла. Строки `i := i` в новом коде больше не нужны, но в старых проектах и на собесах ты их ещё встретишь, и надо уметь объяснить, зачем они были.

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var wg sync.WaitGroup
	for i := range 3 {
		wg.Add(1)
		go func() {
			defer wg.Done()
			fmt.Print(i, " ")
		}()
	}
	wg.Wait()
	fmt.Println()
}
```

<Predict :options="['3 3 3', '0 1 2 строго по порядку', '0 1 2 в любом порядке', 'ничего, main не ждёт']" :correct="2">

Каждая итерация (Go 1.22+) имеет свою `i`, поэтому напечатаются ровно 0, 1 и 2, каждое по разу. А вот порядок не гарантирован: горутины стартуют независимо. На трёх запусках у меня получилось `2 0 1`, `2 1 0`, `0 1 2`. Обрати внимание, как часто первой печатается последняя запущенная горутина, почему так, смотри в блоке «Под капотом» ниже. `wg.Wait()` гарантирует, что все три отработают до выхода из `main`.

</Predict>

## Конкурентность и параллелизм

Эти слова путают даже опытные разработчики, а на собесе это вопрос-фильтр.

- **Конкурентность (concurrency)** это способ **структурировать** программу: несколько независимых задач, которые могут выполняться вперемешку. Это свойство кода.
- **Параллелизм (parallelism)** это **одновременное выполнение** в один и тот же момент на нескольких ядрах. Это свойство исполнения.

Аналогия: один бариста, который принимает заказ, пока молоко греется, и снимает эспрессо, пока клиент платит, работает конкурентно. Два бариста у двух кофемашин работают параллельно. Конкурентная программа может выполняться и на одном ядре (задачи чередуются), и на десяти (тогда часть задач идёт параллельно). Роб Пайк сформулировал это так: конкурентность про то, как **иметь дело** со многими вещами сразу, параллелизм про то, как **делать** много вещей сразу.

В Go ты пишешь конкурентный код (горутины), а параллельно он выполнится или нет, решает рантайм. Сколько горутин могут **одновременно выполнять Go-код**, задаёт `GOMAXPROCS`:

```go
fmt.Println(runtime.NumCPU())        // логических ядер
fmt.Println(runtime.GOMAXPROCS(0))   // 0 значит «только прочитать»
fmt.Println(runtime.NumGoroutine())  // сколько горутин сейчас живо
```

По умолчанию `GOMAXPROCS` равен числу логических ядер. С Go 1.25 на Linux рантайм ещё и учитывает лимит CPU из cgroup: если контейнеру в Kubernetes дали `limits.cpu: 2` на машине с 32 ядрами, `GOMAXPROCS` по умолчанию будет 2, а не 32. До 1.25 Go брал все 32 ядра хоста, и сервис тормозил из-за троттлинга CFS; приходилось ставить библиотеку `automaxprocs` от Uber. Плюс с 1.25 рантайм периодически пересматривает значение, если лимит поменялся. Обе автоматики выключаются, если задать `GOMAXPROCS` руками (переменной окружения или вызовом `runtime.GOMAXPROCS`). Подробно про планировщик и контейнеры поговорим в уроке про GMP в конце модуля.

## Горутина против потока ОС

Горутина это не поток операционной системы. Это легковесная задача, которой управляет рантайм Go, а не ядро ОС.

| | Поток ОС | Горутина |
|---|---|---|
| Кто планирует | ядро ОС | планировщик Go в твоём же процессе |
| Стек | фиксированный, обычно мегабайты | стартует с ~2 КБ, растёт и сжимается по необходимости |
| Создание | системный вызов, микросекунды | обычный вызов в рантайме, сотни наносекунд |
| Переключение | через ядро, с сохранением всех регистров | в пространстве пользователя, дешевле |
| Сколько можно | тысячи | сотни тысяч и миллионы |
| Идентификатор | есть (TID) | намеренно скрыт от программиста |

Цифры для ощущения масштаба. Я запустил 100 000 горутин, каждая из которых просто ждёт на канале:

```go
block := make(chan struct{})
var wg sync.WaitGroup
for range 100_000 {
	wg.Go(func() { <-block })
}
// горутин: 100001
// стеки: 195 МБ, запуск занял 77ms
```

195 МБ на 100 тысяч это ровно по 2 КБ на стек. Сто тысяч потоков ОС с мегабайтными стеками на обычной машине не поместились бы. Поэтому в Go нормально запускать горутину на каждый входящий запрос, а в Java до виртуальных потоков так делать было нельзя.

Почему нет ID горутины, как `Thread.getId()`? Это осознанное решение авторов: ID провоцирует строить thread-local хранилища, а в Go данные запроса передают явно, через параметры и `context`.

::: hood Что происходит при go f()
Компилятор превращает `go f(x)` в вызов `runtime.newproc`. Тот делает три вещи:

1. Создаёт структуру `g` (сама горутина): стек, сохранённые регистры, состояние. Мёртвые `g` переиспользуются, поэтому создание дешёвое. Стартовый стек 2 КБ (`stackMin` в `runtime/stack.go`); с Go 1.19 рантайм подстраивает стартовый размер под средний размер стеков в программе.
2. Кладёт новую `g` в очередь готовых к запуску. Не в общую, а в локальную очередь текущего `P` (логического процессора), причём в особый слот `runnext`: «запустить следующей». Поэтому последняя запущенная горутина часто выполняется первой, это ты видел в задаче с циклом. Полагаться на это нельзя, это деталь реализации.
3. Если есть простаивающие процессоры, будит поток, чтобы тот забрал работу.

Стек горутины растёт: в начале почти каждой функции компилятор вставляет проверку «хватит ли стека». Не хватает, рантайм выделяет стек вдвое больше и копирует туда старый. Предел на 64-битных системах 1 ГБ, после чего бесконечная рекурсия падает с `goroutine stack exceeds 1000000000-byte limit`.

Модель «много горутин на несколько потоков» называется M:N. Буквы G (горутина), M (поток ОС) и P (процессор, их ровно `GOMAXPROCS`) разберём в уроке про планировщик.
:::

## WaitGroup: дождаться группы горутин

`sync.WaitGroup` это счётчик задач с операцией «ждать, пока счётчик станет нулём».

- `wg.Add(n)` увеличивает счётчик на `n`.
- `wg.Done()` уменьшает на 1 (это `Add(-1)`).
- `wg.Wait()` блокирует, пока счётчик не обнулится.

Классический шаблон до Go 1.25:

```go
var wg sync.WaitGroup
for _, url := range urls {
	wg.Add(1) // ДО запуска горутины
	go func() {
		defer wg.Done() // defer: Done выполнится даже при раннем return
		fetch(url)
	}()
}
wg.Wait()
```

### wg.Go в Go 1.25

Пара `Add(1)` + `go` + `defer Done()` встречается так часто и так часто ломается (забыли `Add`, поставили его не туда, забыли `Done`), что в Go 1.25 добавили метод `Go`:

```go
var wg sync.WaitGroup
for _, url := range urls {
	wg.Go(func() {
		fetch(url)
	})
}
wg.Wait()
```

`wg.Go(f)` сам делает `Add(1)`, запускает `f` в новой горутине и вызывает `Done`, когда `f` вернулась. Ошибиться с порядком `Add` больше нельзя. Это теперь основной способ, и документация пакета `sync` показывает его первым. Старый шаблон помнить всё равно надо: его полно в существующем коде.

Мигрировать вручную не придётся: `go fix` в Go 1.27 умеет это сам. Я прогнал его на коде со старым шаблоном:

```bash
go fix -diff ./...
```

```diff
-		wg.Add(1)
-		go func() {
-			defer wg.Done()
+		wg.Go(func() {
 			fmt.Println(i)
-		}()
+		})
```

Два ограничения `wg.Go` из документации:

- **`f` не должна паниковать.** Если паникует, `Wait` не разблокируется, а процесс упадёт (почему падает процесс, ниже). Нужна защита от паники, ставь `recover` внутри `f`.
- **`Go` должен случиться до `Wait`**, если группа пуста. Горутина, запущенная через `Go`, сама может звать `wg.Go`, пока счётчик не нулевой.

### Где вызывать Add

Правило: `Add` вызывается **в той горутине, которая потом вызовет `Wait`**, и **до** запуска новой горутины. Почему, видно на ошибке:

```go
for i := range 3 {
	go func() {
		wg.Add(1) // плохо: Add внутри новой горутины
		defer wg.Done()
		fmt.Println(i)
	}()
}
wg.Wait()
```

`main` может дойти до `wg.Wait()` раньше, чем хоть одна горутина выполнит `Add(1)`. Счётчик ноль, `Wait` сразу возвращается, программа завершается. У меня этот код на трёх запусках подряд не напечатал ни одной строки. Начиная с Go 1.25, `go vet` ловит такую ошибку:

```
a/main.go:12:10: WaitGroup.Add called from inside new goroutine
```

::: hood Как устроен WaitGroup
Внутри `WaitGroup` одно 64-битное атомарное поле состояния: в старших 32 битах счётчик задач, в младших число ждущих в `Wait` (с Go 1.25 один из младших битов отдан под флаг пакета `testing/synctest`). Плюс семафор рантайма, на котором ждущие спят. `Add` атомарно меняет счётчик; если он стал нулём и есть ждущие, `Add` будит их всех через семафор. `Wait` атомарно увеличивает число ждущих и засыпает на семафоре.

Отсюда два следствия. Первое: счётчик меньше нуля невозможен, `Add`, уводящий в минус, паникует `sync: negative WaitGroup counter`. Второе: копировать `WaitGroup` нельзя. Копия получает свой счётчик, и `Done` по копии не уменьшит оригинал. Чтобы `go vet` ловил копирование, внутри лежит пустая структура `noCopy`, на которую реагирует анализатор `copylocks`.

С точки зрения модели памяти `Done` (или возврат из `f` в `wg.Go`) «синхронизируется до» возврата из `Wait`. Поэтому после `wg.Wait()` можно безопасно читать всё, что горутины записали до `Done`, без мьютекса. Этим пользуется шаблон «каждая горутина пишет в свою ячейку слайса».
:::

## Передача результатов: каждой горутине своя ячейка

Раз у горутины нет возвращаемого значения, результаты надо куда-то складывать. Самый простой безопасный способ без каналов и мьютексов: заранее выделить слайс и дать каждой горутине **свой индекс**.

```go
func squares(nums []int) []int {
	out := make([]int, len(nums)) // длина известна заранее
	var wg sync.WaitGroup
	for i, n := range nums {
		wg.Go(func() {
			out[i] = n * n // разные горутины пишут в разные элементы
		})
	}
	wg.Wait() // после Wait все записи видны
	return out
}
```

Разные элементы слайса это разные переменные с точки зрения модели памяти, поэтому гонки нет. А вот `out = append(out, n*n)` из многих горутин это гонка: `append` читает и пишет общий заголовок слайса. Детектор гонок `-race` поймает её сразу, а без него ты получишь потерянные элементы.

## Паника в горутине

Паника в любой горутине, которую никто не перехватил, **роняет весь процесс**. Не только эту горутину, а всю программу, со всеми остальными горутинами, без выполнения их `defer`.

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	defer func() {
		if r := recover(); r != nil {
			fmt.Println("поймали:", r)
		}
	}()
	go func() {
		panic("boom")
	}()
	time.Sleep(100 * time.Millisecond)
	fmt.Println("конец main")
}
```

Программа падает с `panic: boom` и трейсом `goroutine N [running]` (номер горутины от запуска к запуску разный), ни `поймали:`, ни `конец main` не печатаются. `recover` работает только в той горутине, где случилась паника, и только внутри её `defer`. У анонимной горутины своего `recover` нет, поэтому паника доходит до вершины её стека и рантайм завершает процесс, не выполнив `defer` в `main`. В HTTP-сервере это значит: одна неосторожная фоновая горутина кладёт весь сервис. `net/http` перехватывает панику в обработчике запроса, но не в горутинах, которые обработчик сам запустил.

Поэтому в фоновых горутинах, где возможна паника (чужой код, разбор входных данных), ставят `recover` первой строкой:

```go
wg.Go(func() {
	defer func() {
		if r := recover(); r != nil {
			log.Printf("воркер упал: %v", r)
		}
	}()
	work()
})
```

С `wg.Go` это особенно важно. Посмотри, что делает Go 1.27, если `f` паникует: в исходниках `WaitGroup.Go` стоит `recover`, но не для спасения, а чтобы **не вызвать `Done`** и снова запаниковать. Иначе `Wait` в `main` проснулся бы и мог успеть завершить программу с кодом 0 раньше, чем паника её уронит. В выводе это видно по пометке:

```
panic: boom [recovered, repanicked]
```

::: trap Синхронизация через time.Sleep
Плохо: «подождём, пока горутины закончат».

```go
for _, job := range jobs {
	go process(job)
}
time.Sleep(time.Second) // авось успеют
```

На нагруженной машине или в CI не успеют, а на быстрой ты зря ждёшь секунду. Тесты с такими «ожиданиями» флапают.

Хорошо: явная синхронизация.

```go
var wg sync.WaitGroup
for _, job := range jobs {
	wg.Go(func() { process(job) })
}
wg.Wait()
```
:::

::: trap WaitGroup передан по значению
Плохо: функция принимает `sync.WaitGroup`, а не указатель.

```go
func worker(id int, wg sync.WaitGroup) {
	defer wg.Done() // уменьшает счётчик КОПИИ
	fmt.Println("worker", id)
}

func main() {
	var wg sync.WaitGroup
	wg.Add(1)
	go worker(1, wg)
	wg.Wait() // оригинал так и остался 1
	fmt.Println("done")
}
```

Программа печатает `worker 1` и падает: `fatal error: all goroutines are asleep - deadlock!`. Рантайм видит, что `main` ждёт на `WaitGroup`, а других живых горутин нет, и честно сообщает о дедлоке. `go vet` предупреждал заранее:

```
worker passes lock by value: sync.WaitGroup contains sync.noCopy
call of worker copies lock value: sync.WaitGroup contains sync.noCopy
```

Хорошо: передавать `*sync.WaitGroup`, а лучше вообще не передавать, а обернуть вызов: `wg.Go(func() { worker(1) })`. Тогда `worker` ничего не знает о синхронизации и его проще тестировать.
:::

::: trap Горутина, которая никогда не завершится
Горутина, заблокированная навсегда (ждёт канал, в который никто не напишет), не собирается сборщиком мусора. Она держит стек и всё, на что ссылается. Это **утечка горутин**, самая частая утечка памяти в Go-сервисах: на каждый запрос остаётся одна висящая горутина, и через сутки их миллион.

Плохо: воркер, у которого нет условия выхода. Каналы подробно разберём в следующем уроке, здесь достаточно знать, что `<-jobs` ждёт следующую задачу.

```go
func startWorker(jobs chan Job) {
	go func() {
		for {
			process(<-jobs) // когда задачи кончатся, будет ждать вечно
		}
	}()
}
```

Хорошо: горутина выходит, когда владелец закрыл канал задач, а владелец дожидается её через `WaitGroup`.

```go
func startWorker(wg *sync.WaitGroup, jobs <-chan Job) {
	wg.Go(func() {
		for job := range jobs { // цикл закончится после close(jobs)
			process(job)
		}
	})
}

// у владельца: close(jobs); wg.Wait()
```

Я запустил оба варианта в одной программе: после `close(jobs)` и `wg.Wait()` живых горутин осталось 2, это `main` и навсегда зависший первый воркер.

Правило: запуская горутину, сразу ответь себе, **когда и почему она завершится**. Если ответа нет, это баг. Инструменты поиска: `runtime.NumGoroutine()` в метриках, профиль `goroutine` в pprof и новый профиль `goroutineleak` (экспериментальный в Go 1.26, стал штатным в Go 1.27). Подробно об утечках поговорим в уроке про гонки, дедлоки и утечки.
:::

## Что выведет программа?

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var wg sync.WaitGroup
	wg.Add(1)
	wg.Done()
	wg.Done()
	fmt.Println("ok")
}
```

<Predict :options="['ok', 'panic: sync: negative WaitGroup counter', 'fatal error: deadlock', 'ничего']" :correct="1">

Второй `Done` уводит счётчик в -1, и `WaitGroup` паникует: `panic: sync: negative WaitGroup counter`. В реальном коде так бывает, когда `Done` вызывается и в `defer`, и вручную в ветке ошибки. С `wg.Go` такой ошибки не сделать.

</Predict>

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var wg sync.WaitGroup
	wg.Go(func() { panic("boom") })
	wg.Wait()
	fmt.Println("after wait")
}
```

<Predict :options="['after wait', 'panic: boom [recovered, repanicked], программа падает', 'дедлок: Wait ждёт вечно', 'boom, затем after wait']" :correct="1">

`wg.Go` перехватывает панику только для того, чтобы не вызвать `Done`, и паникует снова. Процесс падает, `after wait` не печатается. Документация прямо требует: функция, переданная в `Go`, не должна паниковать. Нужна устойчивость, ставь `recover` внутри.

</Predict>

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var mu sync.Mutex
	count := 0
	var wg sync.WaitGroup
	for range 1000 {
		wg.Go(func() {
			mu.Lock()
			count++
			mu.Unlock()
		})
	}
	fmt.Println(count)
	wg.Wait()
}
```

<Predict :options="['1000', '0', 'любое число от 0 до 1000', 'паника']" :correct="2">

Мьютекс защищает `count++`, но `fmt.Println(count)` стоит **до** `wg.Wait()` и читает `count` без мьютекса, пока горутины ещё работают. Это гонка, и напечатано может быть что угодно от 0 до 1000 (часть горутин уже отработала, часть нет). `go run -race` сообщит `WARNING: DATA RACE`. Мораль: результат читают после `Wait`, а не до.

</Predict>

::: interview
<details><summary>Чем горутина отличается от потока ОС?</summary>

Горутиной управляет рантайм Go в пространстве пользователя, а потоком ядро ОС. Горутина стартует со стеком около 2 КБ, который растёт и сжимается (до 1 ГБ на 64-битных системах), у потока стек фиксированный и обычно мегабайтный. Создание и переключение горутины на порядки дешевле: нет системного вызова, сохраняется меньше состояния. Поэтому горутин могут быть сотни тысяч, а потоков тысячи. Горутины мультиплексируются на небольшое число потоков ОС (модель M:N), числом потоков, одновременно исполняющих Go-код, управляет `GOMAXPROCS`. У горутины нет публичного ID, и её нельзя убить снаружи: она завершается только сама.

</details>
<details><summary>Конкурентность и параллелизм: в чём разница?</summary>

Конкурентность это структура программы: независимые задачи, которые могут выполняться вперемешку. Параллелизм это одновременное выполнение на нескольких ядрах. Конкурентная программа может работать и на одном ядре (задачи чередуются). В Go конкурентность выражается горутинами и каналами, а параллельно ли они исполнятся, решает рантайм с учётом `GOMAXPROCS` и числа ядер. Формулировка Пайка: concurrency is about dealing with lots of things at once, parallelism is about doing lots of things at once.

</details>
<details><summary>Что будет с горутинами, когда завершится main?</summary>

Процесс завершится, все горутины умрут немедленно. Их `defer` не выполнятся, незаписанные данные пропадут. Поэтому `main` (и любой код, запускающий горутины) обязан дождаться их явно: `WaitGroup`, каналы, `errgroup`. То же касается `os.Exit`: он завершает процесс, не выполняя даже `defer` самого `main`.

</details>
<details><summary>Как дождаться завершения нескольких горутин?</summary>

Основной способ `sync.WaitGroup`: с Go 1.25 через `wg.Go(f)` и `wg.Wait()`, в старом коде через `Add(1)` до `go`, `defer Done()` внутри и `Wait()`. Альтернативы: собрать по одному сигналу из канала от каждой горутины; `errgroup.Group` из `golang.org/x/sync`, если нужна первая ошибка и отмена остальных. `time.Sleep` синхронизацией не является.

</details>
<details><summary>Почему wg.Add нужно вызывать до go, а не внутри горутины?</summary>

`Wait` может выполниться раньше, чем новая горутина успеет сделать `Add`. Тогда счётчик ещё ноль, `Wait` вернётся сразу, и программа пойдёт дальше, не дождавшись работы. `Add` должен «случиться до» `Wait`, а это гарантировано, только если он вызван в той же горутине, что и `Wait`, перед запуском. `go vet` с Go 1.25 ловит `Add` внутри новой горутины, а `wg.Go` делает правильный порядок сам.

</details>
<details><summary>Можно ли копировать WaitGroup и Mutex?</summary>

Нет. Копия получает собственное состояние: `Done` по копии не уменьшит счётчик оригинала, и `Wait` повиснет. Типичная ошибка: передать `sync.WaitGroup` в функцию по значению или сделать метод с value receiver у структуры с мьютексом. `go vet` (анализатор `copylocks`) ловит это благодаря встроенной структуре `noCopy`. Передавай указатель или вообще не передавай `WaitGroup`, а оборачивай вызов в `wg.Go`.

</details>
<details><summary>Что будет при панике внутри горутины? Можно ли поймать её в main?</summary>

Неперехваченная паника в любой горутине завершает весь процесс. Поймать её из `main` нельзя: `recover` работает только в отложенной функции той горутины, где паника произошла. Поэтому фоновые горутины, где паника возможна, защищают `defer func() { if r := recover(); r != nil { ... } }()` первой строкой. Особый случай `wg.Go`: при панике в `f` он не вызывает `Done` и паникует снова, чтобы `Wait` не проснулся раньше времени.

</details>
<details><summary>Что изменилось с переменной цикла в Go 1.22 и при чём тут горутины?</summary>

До 1.22 переменная цикла `for` была одна на весь цикл, и замыкания в горутинах видели её последнее значение (`3 3 3` вместо `0 1 2`), плюс это была гонка. Лечили `i := i` или передачей аргументом. С 1.22 (при `go 1.22+` в `go.mod`) каждая итерация получает новую переменную, и замыкание захватывает свою копию. Порядок выполнения горутин при этом по-прежнему не гарантирован.

</details>
<details><summary>Что такое GOMAXPROCS и что поменялось в Go 1.25?</summary>

Максимальное число потоков ОС, одновременно выполняющих Go-код (число P в модели GMP). По умолчанию равно числу логических ядер. С Go 1.25 на Linux по умолчанию учитывается лимит CPU cgroup (например, `limits.cpu` в Kubernetes), и значение периодически обновляется при изменении лимита. Раньше в контейнере Go видел все ядра хоста, создавал лишнюю параллельность и упирался в троттлинг; для этого ставили `uber-go/automaxprocs`. Ручная установка `GOMAXPROCS` отключает автоматику.

</details>
:::
