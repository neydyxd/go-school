# Каналы

Горутины умеют работать одновременно, но пока не умеют договариваться. Канал это труба между горутинами: одна кладёт значение, другая забирает, и в момент передачи они синхронизируются. Девиз Go звучит так: «не общайтесь через общую память, а делитесь памятью через общение». Вместо того чтобы две горутины трогали одну переменную под мьютексом, одна передаёт другой значение, а вместе с ним и право им владеть.

На бэкенде каналы везде: очередь задач для пула воркеров, сигнал остановки при graceful shutdown, сбор результатов из параллельных запросов, конвейеры обработки данных. И на собесе каналы это главный источник задач «что выведет программа»: дедлоки, паники при закрытии, чтение из закрытого канала. Одна таблица из этого урока (поведение операций для nil, открытого и закрытого канала) спрашивается так часто, что её стоит знать наизусть и уметь вывести из механики.

## Создание и базовые операции

Канал создаётся через `make`, у него есть тип элементов:

```go
ch := make(chan int)       // небуферизованный
buf := make(chan int, 3)   // буферизованный, ёмкость 3
var nilCh chan int         // nil: нулевое значение канала
```

Три операции:

```go
ch <- v      // отправить (send)
v := <-ch    // получить (receive)
v, ok := <-ch // получить и узнать, не закрыт ли канал
close(ch)    // закрыть
```

Плюс `len(ch)` (сколько значений лежит в буфере сейчас) и `cap(ch)` (ёмкость буфера). Канал это ссылочный тип: переменная хранит указатель на структуру в рантайме, поэтому канал передают в функции по значению, и все копии указывают на один и тот же канал.

## Небуферизованный канал: рукопожатие

У небуферизованного канала нет места для хранения. Отправка блокируется, пока другая горутина не придёт за значением, и получение блокируется, пока кто-то не отправит. Передача происходит только при встрече обеих сторон. Это как передать посылку из рук в руки: курьер ждёт, пока ты откроешь дверь.

Из этого следует главное свойство: небуферизованный канал **синхронизирует**. После того как обмен состоялся, обе горутины знают, что другая дошла до этой точки.

```go
package main

import "fmt"

func main() {
	done := make(chan struct{})
	go func() {
		fmt.Println("A")
		done <- struct{}{}
	}()
	<-done
	fmt.Println("B")
}
```

<Predict :options="['A, затем B', 'B, затем A', 'недетерминировано', 'дедлок']" :correct="0">

Здесь порядок **гарантирован**. `main` не может напечатать `B`, пока не получит значение из `done`, а горутина отправляет его только после `Println("A")`. Модель памяти Go формулирует это так: отправка в канал «синхронизируется до» завершения соответствующего получения. Всё, что горутина сделала до отправки, видно получателю после получения. Это первый инструмент, который даёт гарантии порядка между горутинами.

</Predict>

`chan struct{}` это идиома для сигналов: пустая структура занимает ноль байт, и по типу сразу видно, что важен сам факт события, а не данные.

Самая частая ошибка новичка с небуферизованным каналом: отправить и получить в одной и той же горутине. Отправка ждёт получателя, который никогда не выполнится. Разберём в задаче в конце урока.

## Буферизованный канал: очередь

У буферизованного канала есть очередь фиксированной ёмкости (FIFO). Отправка блокируется, только когда буфер полон, получение, только когда пуст.

```go
ch := make(chan int, 2)
ch <- 1 // не блокируется: место есть
ch <- 2 // не блокируется
fmt.Println(len(ch), cap(ch)) // 2 2
ch <- 3 // блокируется: буфер полон (в main без читателя это дедлок)
```

Когда что брать:

- **Небуферизованный**, когда нужна синхронизация: «я знаю, что получатель взял значение». Это значение по умолчанию, и с него стоит начинать.
- **Буферизованный**, когда скорость отправителя и получателя временно расходится и нужен амортизатор, или когда заранее известно число значений (N горутин отправят ровно по одному результату, буфер N гарантирует, что ни одна не застрянет).

::: trap Буфер как лекарство от дедлока
Плохо: программа зависала, и буфер увеличили, «пока не заработало».

```go
ch := make(chan int, 100) // было make(chan int), и висло
for _, v := range data {
	ch <- v // при len(data) > 100 снова дедлок
}
close(ch)
for v := range ch {
	sum += v
}
```

На 100 значениях работает, на 101 падает с `all goroutines are asleep - deadlock!` (я проверил), только уже в продакшне. Причина не в размере буфера, а в том, что отправитель и получатель живут в одной горутине.

Хорошо: отправитель в своей горутине, буфер не нужен вовсе.

```go
ch := make(chan int)
go func() {
	defer close(ch)
	for _, v := range data {
		ch <- v
	}
}()
for v := range ch {
	sum += v
}
```

Размер буфера должен следовать из логики (сколько значений гарантированно будет отправлено), а не подбираться, «пока не перестанет виснуть». По умолчанию 0 или 1, другой размер с комментарием, почему именно он.
:::

## Закрытие канала

`close(ch)` сообщает: «значений больше не будет». Закрытие это не удаление: значения, уже лежащие в буфере, получатель прочитает. После того как буфер опустел, получение из закрытого канала **не блокируется** и сразу возвращает нулевое значение типа.

```go
package main

import "fmt"

func main() {
	ch := make(chan int, 2)
	ch <- 1
	ch <- 2
	close(ch)
	fmt.Println(<-ch, <-ch, <-ch)
	v, ok := <-ch
	fmt.Println(v, ok, len(ch), cap(ch))
}
```

<Predict :options="['1 2, затем дедлок', '1 2 0, затем 0 false 0 2', 'panic: receive from closed channel', '1 2 0, затем 0 true 0 2']" :correct="1">

Первые два получения забирают значения из буфера: закрытие их не стирает. Третье получает нулевое значение `0`, потому что канал закрыт и пуст. Форма `v, ok` различает два случая: `ok == true` значит «это настоящее значение», `ok == false` значит «канал закрыт и пуст, `v` это нулевое значение». `cap` после закрытия остаётся 2. Паники при чтении закрытого канала не бывает никогда.

</Predict>

Как отличить «отправили ноль» от «канал закрыт»? Только через `ok`. Проверить «закрыт ли канал», не пытаясь из него читать, в Go нельзя: такой функции нет намеренно. Даже если бы была, ответ устарел бы через наносекунду, потому что канал могут закрыть сразу после проверки.

### Кто закрывает канал

Закрывает **отправитель**, и только он. Получатель не знает, будут ли ещё значения, а отправка в закрытый канал паникует. Если отправителей несколько, ни один из них не может закрыть канал сам: нужен координатор, который дождётся всех (например, `WaitGroup`) и закроет один раз.

Закрывать канал **не обязательно**. Сборщик мусора уберёт незакрытый канал, на который больше никто не ссылается. Закрывают, чтобы сообщить получателям «конец данных»: например, чтобы завершился `range`.

### range по каналу

`for v := range ch` читает значения, пока канал не закрыт и не опустел:

```go
package main

import "fmt"

func main() {
	ch := make(chan int, 1)
	go func() {
		for i := range 3 {
			ch <- i
		}
		close(ch)
	}()
	for v := range ch {
		fmt.Print(v, " ")
	}
	fmt.Println()
}
// 0 1 2
```

Без `close(ch)` цикл после третьего значения ждал бы четвёртое вечно.

### Закрытие как широковещательный сигнал

Значение из канала получает ровно один получатель. А закрытие видят **все**: каждый, кто ждёт на `<-ch`, проснётся. Поэтому для сигнала «всем остановиться» канал закрывают, а не отправляют в него:

```go
stop := make(chan struct{})
for range 10 {
	go worker(stop) // внутри ждёт <-stop
}
close(stop) // проснутся все 10
```

Ровно так устроен `ctx.Done()` в пакете `context`, о нём отдельный урок.

## Направленные каналы

Тип канала может разрешать только одно направление:

- `chan<- int`: только отправка (send-only);
- `<-chan int`: только получение (receive-only).

Двунаправленный `chan int` неявно приводится к любому из них. Так в сигнатуре функции фиксируют роль, и компилятор следит за ней:

```go
// Генератор: создаёт канал, владеет им и закрывает.
// Наружу отдаёт только чтение.
func count(n int) <-chan int {
	out := make(chan int)
	go func() {
		defer close(out)
		for i := range n {
			out <- i
		}
	}()
	return out
}

func consume(ch <-chan int) {
	ch <- 1   // ошибка компиляции
	close(ch) // тоже ошибка компиляции
}
```

```
invalid operation: cannot send to receive-only channel <-chan int ch (variable of type <-chan int)
invalid operation: cannot close receive-only channel ch (variable of type <-chan int)
```

Обрати внимание: закрыть канал «только для чтения» нельзя. Это закрепляет правило «закрывает отправитель» на уровне типов. Шаблон «функция создаёт канал, запускает горутину-отправитель, возвращает `<-chan T`» называется генератором, он лежит в основе конвейеров (pipeline), которые разберём в уроке про паттерны.

## nil-канал

Нулевое значение канала `nil`. Операции с ним ведут себя необычно:

- отправка и получение блокируются **навсегда**;
- `close(nil)` паникует: `close of nil channel`;
- `len` и `cap` возвращают 0.

```go
package main

import "fmt"

func main() {
	var ch chan int
	go func() { ch <- 1 }()
	fmt.Println(<-ch)
}
```

Программа падает с `fatal error: all goroutines are asleep - deadlock!` и `goroutine 1 [chan receive (nil chan)]`. `ch` объявлен, но не создан через `make`, значит он `nil`. Отправка в nil-канал блокирует горутину навсегда, получение тоже. Обе горутины спят, рантайм сообщает о дедлоке. Паники здесь нет: паникует только `close` nil-канала. Забытый `make` (например, канал как поле структуры без конструктора) это частая причина таких зависаний.

Зачем такое поведение? Вечная блокировка звучит бесполезно, но в `select` это суперсила: если присвоить переменной канала `nil`, соответствующая ветка `select` больше никогда не сработает. Так «выключают» источник, который уже закрыт. Разберём в следующем уроке.

## Полная таблица поведения

Это нужно знать без запинки. Каждая клетка проверена запуском на Go 1.27.

| Операция | nil-канал | открытый | закрытый |
|---|---|---|---|
| `ch <- v` | блокируется навсегда | ждёт получателя или место в буфере | **паника** `send on closed channel` |
| `<-ch` | блокируется навсегда | берёт из буфера; если он пуст, ждёт отправителя | сначала остаток буфера, потом сразу нулевое значение, `ok == false` |
| `close(ch)` | **паника** `close of nil channel` | закрывает; ждущие получатели получают нулевое значение, ждущие отправители паникуют | **паника** `close of closed channel` |
| `len(ch)`, `cap(ch)` | 0, 0 | число в буфере, ёмкость | остаток в буфере, ёмкость |

Как запомнить через смысл, а не зубрёжкой:

- **nil-канала не существует**, поэтому ждать на нём можно вечно, а закрыть нечего (паника).
- **Закрытый канал это обещание «значений больше не будет»**. Нарушить обещание (отправить или закрыть повторно) нельзя, это паника. Читать можно сколько угодно: получишь остаток, а потом нулевые значения.
- Паникуют ровно три клетки: отправка в закрытый, закрытие закрытого, закрытие nil. Все три это ошибки программиста, а не ситуации времени выполнения, поэтому их не «обрабатывают», а исправляют дизайн.

Паника при отправке в закрытый канал случается даже при свободном месте в буфере:

```go
ch := make(chan int, 1)
close(ch)
ch <- 1 // panic: send on closed channel
```

::: hood Как устроен канал: hchan
`make(chan T, n)` выделяет в куче структуру `runtime.hchan` и возвращает указатель на неё. Основные поля (из `runtime/chan.go`, Go 1.27):

```
hchan
├─ qcount    сколько значений сейчас в буфере (это len)
├─ dataqsiz  ёмкость буфера (это cap)
├─ buf       кольцевой буфер на dataqsiz элементов
├─ sendx     индекс, куда писать следующее значение
├─ recvx     индекс, откуда читать следующее
├─ closed    флаг закрытия
├─ recvq     очередь горутин, ждущих получения
├─ sendq     очередь горутин, ждущих отправки
└─ lock      мьютекс рантайма, защищает всё вышеперечисленное
```

Ждущие горутины стоят в очередях не сами по себе, а в обёртках `sudog`: «горутина плюс указатель на значение, которое она отправляет или куда хочет получить».

**Отправка `ch <- v`:**

1. Захватить `lock`.
2. Если канал закрыт, отпустить и паниковать.
3. Если в `recvq` уже ждёт получатель, скопировать `v` **прямо в его стек**, минуя буфер, и разбудить его. Это единственное место в рантайме, где одна горутина пишет в стек другой.
4. Иначе, если в буфере есть место, скопировать `v` в `buf[sendx]` и сдвинуть `sendx` по кругу.
5. Иначе встать в `sendq` и уснуть (горутина «паркуется», планировщик берёт другую).

**Получение** симметрично. Тонкость: если буфер полон и в `sendq` кто-то ждёт, получатель берёт значение из головы буфера, а значение ждущего отправителя кладёт в хвост и будит его. Так сохраняется порядок FIFO.

**Закрытие** ставит `closed = 1` и будит **всех** из обеих очередей: получатели вернутся с нулевым значением, отправители проснутся и запаникуют.

Отсюда практические выводы. Канал это не «магия без блокировок»: каждая операция берёт мьютекс, и для простого счётчика канал заметно дороже атомика. Прямая передача ждущему получателю копирует значение один раз (из стека в стек), передача через буфер два раза (в буфер и из буфера). Подробнее про внутренности каналов и их цену поговорим в модуле про рантайм.
:::

::: hood Каналы и модель памяти
Модель памяти Go даёт каналам три гарантии, на них держится вся синхронизация через каналы:

1. Отправка «синхронизируется до» завершения соответствующего получения.
2. Закрытие канала «синхронизируется до» получения, которое вернуло нулевое значение из-за закрытия.
3. Для канала ёмкостью C k-е получение «синхронизируется до» завершения (k+C)-й отправки. Для небуферизованного (C = 0) это значит: получение завершается до того, как отправитель продолжит работу. Для буферизованного это правило превращает канал в **семафор**: буфер ёмкости N пропускает не больше N горутин одновременно.

Третье правило используется в домашке: мьютекс на канале ёмкости 1.
:::

::: trap Закрытие со стороны получателя
Плохо: получатель решил, что ему хватит, и закрыл канал.

```go
for v := range results {
	if v == target {
		close(results) // отправитель на следующей отправке запаникует
		break
	}
}
```

Хорошо: получатель сообщает отправителю через **отдельный** канал (или `context`), что пора остановиться, а канал данных закрывает сам отправитель, когда выходит. Конструкция `select` здесь ждёт сразу двух событий, её разбираем в следующем уроке:

```go
// отправитель
for _, v := range data {
	select {
	case results <- v:
	case <-stop:
		close(results)
		return
	}
}
close(results)
```

Правило: закрывает тот, кто пишет. Много писателей, значит закрывает координатор после `wg.Wait()`.
:::

::: trap Горутины, которым некому отдать результат
Плохо: берём самый быстрый ответ из трёх, а остальные горутины навсегда зависают на отправке в небуферизованный канал, который больше никто не читает.

```go
func first(names []string) string {
	ch := make(chan string)
	for _, n := range names {
		go func() { ch <- fetch(n) }()
	}
	return <-ch
}
```

Я проверил через `runtime.NumGoroutine()` после вызова: остаётся 3 горутины, `main` и две зависшие. В сервисе это утечка на каждый запрос.

Хорошо: буфер на число отправителей. Каждая горутина гарантированно положит результат и завершится, даже если его никто не прочитает, а канал потом соберёт GC.

```go
ch := make(chan string, len(names))
```

С этим исправлением после вызова живёт только `main`.
:::

::: trap Бесконечное чтение закрытого канала
Плохо: цикл читает канал без проверки `ok`.

```go
for {
	v := <-ch // после close это 0, 0, 0... без блокировки
	process(v)
}
```

После закрытия цикл превращается в горячую петлю на 100% CPU, обрабатывающую нули. Хорошо: `for v := range ch`, а если нужен ручной цикл, то `v, ok := <-ch; if !ok { return }`.
:::

## Что выведет программа?

```go
package main

import "fmt"

func main() {
	ch := make(chan int)
	ch <- 1
	fmt.Println(<-ch)
}
```

<Predict :options="['1', '0', 'fatal error: all goroutines are asleep - deadlock!', 'ничего']" :correct="2">

`ch <- 1` ждёт получателя, а получатель (`<-ch` в следующей строке) находится в той же горутине и никогда не выполнится. Других горутин нет, и рантайм, увидев, что все горутины спят, завершает программу: `fatal error: all goroutines are asleep - deadlock!` и `goroutine 1 [chan send]`. Это не паника, её нельзя перехватить `recover`. Важно: рантайм ловит дедлок, только когда спят **все** горутины. В HTTP-сервере, где живы горутины сети, такой код просто молча повиснет.

</Predict>

```go
package main

import "fmt"

func main() {
	ch := make(chan int, 3)
	ch <- 1
	ch <- 2
	for v := range ch {
		fmt.Println(v)
	}
	fmt.Println("конец")
}
```

<Predict :options="['1 2 конец', '1 2, затем дедлок', '1 2 0 конец', 'дедлок сразу']" :correct="1">

`range` читает, пока канал не **закрыт**, а не пока он не пуст. После двух значений буфер опустел, канал открыт, и `range` ждёт третье значение. Других горутин нет: печатается `1`, `2` и `fatal error: all goroutines are asleep - deadlock!`. `конец` не печатается. Исправление: `close(ch)` перед циклом (значения из буфера при этом не пропадут).

</Predict>

```go
package main

import "fmt"

func main() {
	var ch chan int
	fmt.Println(len(ch), cap(ch), ch == nil)
	close(ch)
}
```

<Predict :options="['0 0 true, затем panic: close of nil channel', '0 0 true и всё', 'паника уже на len(ch)', 'дедлок']" :correct="0">

`len` и `cap` у nil-канала безопасны и дают 0. А `close(nil)` это одна из трёх паникующих клеток таблицы: `panic: close of nil channel`.

```go
package main

import "fmt"

func main() {
	ch := make(chan int)
	close(ch)
	defer func() { fmt.Println("recover:", recover()) }()
	close(ch)
}
```

<Predict :options="['ничего, повторный close игнорируется', 'recover: close of closed channel', 'fatal error, recover не помогает', 'recover: <nil>']" :correct="1">

Повторное закрытие это паника `close of closed channel`, и, в отличие от дедлока, её можно перехватить: `recover` возвращает значение паники. Но «закрывать с recover на всякий случай» плохая идея, это лечение симптома. Если канал могут закрыть из нескольких мест, закрытие оборачивают в `sync.Once` (следующие уроки).

</Predict>

<details><summary>Расскажи поведение send, receive и close для nil, открытого и закрытого канала.</summary>

nil: send и receive блокируются навсегда, close паникует. Открытый: send ждёт получателя или место в буфере, receive ждёт значение, close закрывает и будит всех ждущих. Закрытый: send паникует, receive сначала отдаёт остаток буфера, затем сразу нулевое значение с `ok == false`, повторный close паникует. `len`/`cap` у nil равны нулю. Логика: nil-канала нет (ждать вечно, закрыть нечего), закрытый канал это обещание «больше значений не будет», его нельзя нарушить отправкой или повторным закрытием.

</details>
<details><summary>Чем буферизованный канал отличается от небуферизованного?</summary>

Небуферизованный не хранит значений: отправитель и получатель встречаются, передача синхронизирует их (после обмена каждый знает, что другой дошёл до этой точки). Буферизованный это очередь ёмкости N: отправка блокируется только на полном буфере, получение только на пустом, синхронизация ослабевает. Буфер выбирают по логике: известное число отправителей, сглаживание всплесков, семафор. Увеличивать буфер, чтобы «не висло», значит прятать ошибку.

</details>
<details><summary>Кто должен закрывать канал и обязательно ли закрывать?</summary>

Закрывает отправитель, потому что только он знает, что значений больше не будет, а отправка в закрытый канал паникует. При нескольких отправителях закрывает координатор, дождавшийся всех. Закрывать не обязательно: GC соберёт канал без ссылок. Закрывают, чтобы сообщить получателям «конец», например для завершения `range` или широковещательного сигнала остановки.

</details>
<details><summary>Как проверить, закрыт ли канал?</summary>

Без чтения никак, и это сделано намеренно: результат такой проверки устарел бы сразу. При чтении `v, ok := <-ch` значение `ok == false` означает «закрыт и пуст». Неблокирующую проверку делают через `select` с `default`, но она тоже съедает значение, если оно было. Если код хочет знать «закрыт ли канал», чтобы туда отправить, это ошибка дизайна: отправитель сам должен знать, закрывал ли он канал.

</details>
<details><summary>Зачем нужны направленные каналы?</summary>

Чтобы зафиксировать роль в сигнатуре и переложить проверку на компилятор: функция с `<-chan T` может только читать, с `chan<- T` только писать. Закрыть receive-only канал нельзя, ошибка компиляции, что закрепляет правило «закрывает отправитель». Двунаправленный канал приводится к направленному неявно, обратно нельзя. Типичный шаблон: генератор создаёт `chan T`, сам пишет и закрывает, наружу отдаёт `<-chan T`.

</details>
<details><summary>Для чего может пригодиться nil-канал?</summary>

Операции с nil-каналом блокируются навсегда, поэтому в `select` ветка с nil-каналом никогда не выбирается. Присвоив каналу `nil`, можно «выключить» ветку: например, при слиянии двух каналов, когда один уже закрыт, чтобы `select` не крутился на нём. Вне `select` nil-канал обычно признак ошибки (забыли `make`).

</details>
<details><summary>Как канал устроен внутри?</summary>

Указатель на `runtime.hchan` в куче: кольцевой буфер (`buf`, `dataqsiz`, `qcount`, `sendx`, `recvx`), флаг `closed`, очереди ждущих `recvq` и `sendq` из `sudog` и мьютекс `lock`. Отправка под мьютексом: если ждёт получатель, значение копируется прямо в его стек; если есть место, в буфер; иначе горутина встаёт в `sendq` и паркуется. Закрытие будит всех ждущих. Канал потокобезопасен именно благодаря этому мьютексу, и поэтому операция с каналом дороже атомика.

</details>
<details><summary>Что будет с горутинами, ждущими на канале, если его закрыть?</summary>

Все ждущие получатели проснутся и получат нулевое значение с `ok == false` (если буфер пуст). Все ждущие отправители проснутся и запаникуют `send on closed channel`. Поэтому закрывать канал, в который ещё кто-то может писать, нельзя.

</details>
<details><summary>Как найти утечку горутин на каналах?</summary>

Признак: растёт `runtime.NumGoroutine()` или профиль `goroutine` в pprof показывает тысячи горутин в состоянии `chan send` или `chan receive`. Типичные причины: отправка в небуферизованный канал, который больше не читают; `range` по каналу, который никто не закроет. С Go 1.27 есть профиль `goroutineleak`, он через сборщик мусора находит горутины, заблокированные на примитивах, до которых больше никто не может дотянуться. Лечение: буфер под известное число отправителей, сигнал остановки, `context`.

</details>

## Источники

- `RU` [Как устроены каналы в Go, Хабр](https://habr.com/ru/articles/308070/): перевод разбора реализации: `hchan`, очереди `recvq`/`sendq`, буфер, закрытие. Старая статья, но структура канала с тех пор принципиально не поменялась.
- `RU` [Go Channels Internals, Хабр (Онтико)](https://habr.com/ru/companies/oleg-bunin/articles/522742/): расшифровка доклада Егора Гришечко о внутренностях каналов, подробнее про `sudog` и планировщик.
- `RU` [Go в примерах: закрытие каналов](https://gobyexample.ru/closing-channels.html): короткий запускаемый пример; соседние страницы того же сайта («Перебор значений каналов», «Направления каналов») покрывают остальные разделы урока.
- `RU` [Go: нужно ли закрывать канал? Хабр](https://habr.com/ru/articles/861846/): эксперимент с трассировкой, подтверждающий, что GC собирает незакрытые каналы, а опасность в зависших горутинах.
- `EN` [Understanding Channels, Kavya Joshi (GopherCon 2017)](https://www.youtube.com/watch?v=KBZlN0izeiY): лучший доклад про устройство каналов, с картинками буфера и очередей.
- `EN` [Channel Axioms, Dave Cheney](https://dave.cheney.net/2014/03/19/channel-axioms): четыре аксиомы про отправку и получение для nil и закрытого канала: половина таблицы из урока с объяснением, почему так.
- `EN` [Спецификация: Channel types](https://go.dev/ref/spec#Channel_types) и [The Go Memory Model](https://go.dev/ref/mem): точные формулировки про направления, закрытие и гарантии синхронизации.
