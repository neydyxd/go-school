# Kafka и RabbitMQ обзорно

River закрывает фоновые задачи внутри одного сервиса. Но как только событие «заказ оплачен» нужно сразу пяти сервисам (склад, доставка, бонусы, аналитика, уведомления), написанным разными командами на разных языках, очередь в своей базе перестаёт подходить: остальным сервисам туда не дотянуться, и каждое событие надо было бы вставлять пять раз. Здесь появляются **брокеры сообщений**: отдельная система, через которую сервисы обмениваются сообщениями, не зная друг о друге.

На собеседованиях Go-бэкендера почти всегда спрашивают про Kafka (иногда про RabbitMQ): что такое партиция, как устроены consumer groups, когда коммитить оффсет, что значит at-least-once у брокера, чем Kafka отличается от RabbitMQ. Поднимать брокеры в этом уроке не будем, это обзор с механикой и кодом на популярных Go-клиентах (`segmentio/kafka-go` и `rabbitmq/amqp091-go`) как иллюстрацией. Код в уроке компилируется с актуальными версиями клиентов (kafka-go v0.4.51, amqp091-go v1.16.0), но запуск требует живого брокера.

## Две модели

**RabbitMQ это умный почтальон.** Сообщение приходит в обменник (exchange), правила маршрутизации раскладывают его по очередям, потребитель забирает сообщение, подтверждает, и оно **удаляется** из очереди. Брокер следит за каждым сообщением: кому отдано, подтверждено ли.

**Kafka это журнал.** Сообщения дописываются в конец лога и **хранятся** заданное время (например, 7 дней) независимо от того, прочитали их или нет. Потребитель сам помнит, до какого места дочитал (оффсет). Брокер почти ничего не знает о потребителях, поэтому любой новый сервис может прочитать поток с начала.

Из этой разницы следует почти всё: Kafka даёт огромную пропускную способность, хранение и перечитывание, порядок внутри партиции; RabbitMQ даёт гибкую маршрутизацию, подтверждение каждого сообщения, приоритеты, отложенную доставку и «очередь задач» в классическом смысле.

## Kafka

### Топики, партиции, оффсеты

**Топик** это именованный поток событий (`orders`). Топик делится на **партиции**: каждая партиция это отдельный упорядоченный журнал на диске, только для дописывания. У каждого сообщения в партиции свой **оффсет**, порядковый номер: 0, 1, 2...

```text
топик orders, 3 партиции
партиция 0: [0][1][2][3][4][5] <- дописываем сюда
партиция 1: [0][1][2]
партиция 2: [0][1][2][3]
```

Партиция это единица параллелизма и единица порядка:

- **порядок гарантирован только внутри партиции**, между партициями порядка нет;
- партиции топика раскладываются по разным брокерам кластера, поэтому запись и чтение масштабируются;
- каждую партицию копирует несколько брокеров (**репликация**): один лидер принимает запись, фолловеры догоняют. Набор реплик, которые не отстали, называется ISR (in-sync replicas).

### Ключ сообщения

У сообщения есть ключ. Продюсер выбирает партицию по ключу: хеш от ключа по модулю числа партиций. Все сообщения с ключом `user-42` попадут в одну партицию и будут прочитаны в том порядке, в каком записаны. Так получают порядок «по сущности»: события одного заказа идут по порядку, события разных заказов обрабатываются параллельно.

```go
func produce(ctx context.Context) error {
	w := &kafka.Writer{
		Addr:         kafka.TCP("localhost:9092"),
		Topic:        "orders",
		Balancer:     &kafka.Murmur2Balancer{}, // как Java-клиент: один ключ, одна партиция
		RequiredAcks: kafka.RequireAll,         // ждать подтверждения всех in-sync реплик
	}
	defer w.Close()
	return w.WriteMessages(ctx, kafka.Message{
		Key:   []byte("user-42"),
		Value: []byte(`{"order_id":1001,"status":"paid"}`),
	})
}
```

::: trap Ключ есть, а порядка нет
У `kafka-go` балансировщик по умолчанию **round-robin**: ключ сообщения при выборе партиции игнорируется, и события одного заказа разлетаются по разным партициям. Нужен `kafka.Hash`, `kafka.Murmur2Balancer` (совместим с Java-клиентом, важно, если в топик пишут сервисы на разных языках) или `kafka.CRC32Balancer` (совместим с librdkafka). И второе: `RequiredAcks` в `kafka-go` по умолчанию `RequireNone`, запись «отправил и забыл». В официальном Java-клиенте с Kafka 3.0 по умолчанию `acks=all` и идемпотентный продюсер, в Go-клиентах проверяй дефолты сам.
:::

```go
	return int(h.Sum32() % uint32(n))

}
```

### Consumer groups

Потребители объединяются в **группу** с общим `group.id`. Внутри группы каждая партиция отдаётся **ровно одному** потребителю. Разные группы читают топик независимо, каждая со своими оффсетами: склад и аналитика получают все события каждый.

```text
топик orders: партиции 0 1 2 3 4 5

группа billing (3 потребителя)        группа analytics (1 потребитель)
  c1: 0 1                               a1: 0 1 2 3 4 5
  c2: 2 3
  c3: 4 5
```

Следствия:

- параллелизм внутри группы ограничен числом партиций: 6 партиций и 8 потребителей дают 2 простаивающих;
- порядок внутри партиции сохраняется, потому что её читает один потребитель.

**Ребалансировка.** Потребитель пришёл, ушёл или перестал присылать heartbeat: группа перераспределяет партиции. Как именно, зависит от протокола. **Eager**-ребалансировка (assignor-ы range, round-robin, sticky) останавливает всю группу: каждый потребитель отдаёт все свои партиции, коммитит оффсеты и ждёт новых назначений (stop-the-world). **Cooperative** (cooperative-sticky, Kafka 2.4, KIP-429) работает инкрементально: забирают и передают только те партиции, которые меняют владельца, остальные читаются дальше. В Kafka 4.0 стал общедоступным новый протокол групп (KIP-848, на клиенте `group.protocol=consumer`): назначение считает брокер, тоже без остановки всей группы. Частые ребалансировки (долгая обработка без heartbeat, падения подов) в любом случае дают паузы на переданных партициях и повторную обработку.

```go
// RangeAssign из домашки: 5 партиций, участники [b a]
fmt.Println(RangeAssign(5, []string{"b", "a"}))
```

### Коммит оффсетов

Потребитель периодически сохраняет в Kafka (в служебный топик `__consumer_offsets`) свой **оффсет**: номер **следующего** сообщения, которое надо прочитать. После рестарта или ребалансировки чтение продолжится с закоммиченного оффсета. Момент коммита определяет гарантию:

| Когда коммитим | Сбой между чтением и обработкой | Гарантия |
|---|---|---|
| до обработки | сообщение потеряно | at-most-once |
| после обработки | сообщение обработают ещё раз | at-least-once |

```go
func consume(ctx context.Context, handle func(context.Context, kafka.Message) error) error {
	r := kafka.NewReader(kafka.ReaderConfig{
		Brokers: []string{"localhost:9092"},
		GroupID: "billing",
		Topic:   "orders",
	})
	defer r.Close()
	for {
		m, err := r.FetchMessage(ctx) // читает, но НЕ коммитит
		if errors.Is(err, io.EOF) || errors.Is(err, context.Canceled) {
			return nil
		}
		if err != nil {
			return err
		}
		if err := handle(ctx, m); err != nil {
			return err // не коммитим: после рестарта сообщение придёт снова
		}
		if err := r.CommitMessages(ctx, m); err != nil { // коммит ПОСЛЕ обработки
			return err
		}
	}
}
```

::: trap ReadMessage коммитит за тебя
```go
// плохо: в consumer group ReadMessage коммитит оффсет сразу при чтении
m, _ := r.ReadMessage(ctx)
process(m) // упали здесь: сообщение уже считается обработанным
```

Документация `kafka-go` прямо предупреждает: оффсет может быть закоммичен до полной обработки. Для at-least-once используй `FetchMessage` и `CommitMessages` после обработки. В Java-клиенте то же самое делает `enable.auto.commit=true`: коммит по таймеру, независимо от того, обработал ли ты сообщения.
:::

**Параллельная обработка внутри партиции.** Если сообщения одной партиции обрабатывать горутинами, они заканчиваются не по порядку. Оффсет коммитят только до первой «дыры»: сообщения 5 и 7 готовы, 6 ещё в работе, коммитить можно 6 (следующее непрочитанное), а не 8. Ровно это делает `OffsetTracker` в домашке.

::: hood Что такое exactly-once в Kafka
Kafka умеет две вещи. **Идемпотентный продюсер**: брокер помнит id продюсера и номер последовательности в каждой партиции и отбрасывает дубли, которые возникают при повторной отправке после потерянного ответа. С Kafka 3.0 он включён по умолчанию в Java-клиенте. **Транзакции**: продюсер атомарно пишет в несколько партиций и коммитит оффсеты потребителя в той же транзакции, а потребители с `isolation.level=read_committed` не видят незакоммиченное. Это даёт exactly-once для цепочки «прочитал из Kafka, обработал, записал в Kafka» (Kafka Streams). Как только эффект уходит наружу (база, письмо, HTTP), снова нужен идемпотентный потребитель.
:::

### Что ещё стоит знать про Kafka

- Хранение: по времени (`retention.ms`) или размеру. **Compacted**-топики хранят последнее сообщение для каждого ключа: так хранят «текущее состояние сущности».
- С Kafka 4.0 кластер работает только в режиме **KRaft**: метаданные хранит сама Kafka, ZooKeeper больше не нужен.
- Kafka не очередь задач: нет подтверждения отдельного сообщения, нет отложенной доставки, одно «ядовитое» сообщение останавливает партицию (дальше не продвинуться, пока его не обработать или не пропустить). Ретраи делают отдельными топиками (`orders.retry`, `orders.dlq`). В 4.0 в раннем доступе появились share groups (KIP-932), «очереди для Kafka» с подтверждением отдельных сообщений.

## RabbitMQ

### Exchange, binding, queue

Продюсер публикует сообщение не в очередь, а в **exchange** с ключом маршрутизации (routing key). Exchange по **привязкам** (bindings) решает, в какие очереди положить копии.

| Тип exchange | Как маршрутизирует |
|---|---|
| `direct` | в очереди, чей ключ привязки совпадает с routing key |
| `fanout` | во все привязанные очереди, ключ игнорируется |
| `topic` | по шаблону с `*` (одно слово) и `#` (ноль и больше слов): `order.*.paid`, `order.#` |
| `headers` | по заголовкам сообщения вместо ключа |

Безымянный exchange по умолчанию (`""`) это `direct`, к которому каждая очередь привязана по своему имени: «опубликовать в очередь `emails`» на самом деле значит «в exchange `""` с ключом `emails`».

**Очереди**: classic (одна копия на узле), **quorum** (реплицируются по Raft, рекомендуемый вариант для надёжности) и streams (журнал в стиле Kafka). Зеркалирование classic-очередей удалено в RabbitMQ 4.0, вместо него quorum.

### Подтверждения и prefetch

Потребитель получает сообщение и должен подтвердить его:

- `Ack`: обработано, удалить;
- `Nack(requeue=true)` или `Reject(requeue=true)`: вернуть в очередь;
- `Nack(requeue=false)`: выбросить или отправить в dead letter exchange;
- соединение или канал закрылся без подтверждения: все неподтверждённые сообщения возвращаются в очередь и будут доставлены снова с флагом `Redelivered`.

С `autoAck=true` брокер считает сообщение доставленным в момент отправки: это at-most-once, упал потребитель, сообщение потеряно.

**Prefetch** (`basic.qos`) ограничивает число неподтверждённых сообщений на потребителя. Без него брокер отдаст одному потребителю всю очередь, и остальные будут простаивать, а память процесса раздуется. Типичное значение от 10 до нескольких сотен, подбирается по времени обработки.

```go
func consume(ch *amqp.Channel, handle func(amqp.Delivery) error) error {
	if err := ch.Qos(10, 0, false); err != nil { // не больше 10 неподтверждённых
		return err
	}
	msgs, err := ch.Consume("emails", "mailer-1", false, false, false, false, nil) // autoAck=false
	if err != nil {
		return err
	}
	for d := range msgs {
		if err := handle(d); err != nil {
			_ = d.Nack(false, false) // requeue=false: в dead letter exchange
			continue
		}
		_ = d.Ack(false)
	}
	return nil
}
```

**Publisher confirms**: продюсер переводит канал в режим подтверждений, и брокер подтверждает каждое сообщение, когда принял его (для персистентных сообщений в durable-очереди после записи на диск, для quorum после репликации на большинство). Без confirms `Publish` возвращается, как только данные ушли в сокет, и потерю сообщения ты не заметишь.

```go
func publish(ctx context.Context, ch *amqp.Channel, body []byte) error {
	if err := ch.Confirm(false); err != nil { // режим publisher confirms
		return err
	}
	dc, err := ch.PublishWithDeferredConfirmWithContext(ctx, "notifications", "email", false, false, amqp.Publishing{
		DeliveryMode: amqp.Persistent,
		MessageId:    "welcome-42", // ключ для дедупликации у потребителя
		ContentType:  "application/json",
		Body:         body,
	})
	if err != nil {
		return err
	}
	ok, err := dc.WaitContext(ctx)
	if err != nil {
		return err
	}
	if !ok {
		return errors.New("брокер не принял сообщение (nack)")
	}
	return nil
}
```

### Dead letter exchange

Сообщение уходит в **DLX**, если его отвергли без возврата (`Nack`/`Reject` с `requeue=false`), истёк его TTL, очередь переполнена или превышен лимит доставок. DLX это обычный exchange, указанный аргументом очереди:

```go
_, err := ch.QueueDeclare("emails", true, false, false, false, amqp.Table{
	"x-queue-type":           "quorum",
	"x-dead-letter-exchange": "dlx",
	"x-delivery-limit":       5,
})
```

В DLQ (очередь за DLX) складываются «ядовитые» сообщения: их смотрят руками, чинят причину и переотправляют. У quorum-очередей с RabbitMQ 4.0 есть лимит повторных доставок по умолчанию (20): сообщение, которое раз за разом не удаётся обработать, удаляется или уходит в DLX, если он настроен, а не крутится в очереди вечно.

::: trap Бесконечный requeue
```go
// плохо: ошибка в данных, сообщение возвращается в голову очереди,
// тут же доставляется снова и снова, CPU 100%, остальные сообщения ждут
if err := handle(d); err != nil {
	d.Nack(false, true)
}
```

```go
// хорошо: постоянная ошибка в DLQ, временная тоже в DLX, но с задержкой
if err := handle(d); err != nil {
	d.Nack(false, false)
}
```

Повтор с задержкой в RabbitMQ делают через отдельную очередь с TTL, у которой DLX указывает обратно на основную (сообщение «отлёживается» и возвращается), или плагином отложенных сообщений. Мгновенный requeue без задержки и без лимита это та же ошибка, что ретрай без backoff.
:::

## Гарантии доставки у обоих

Схема одинакова для любого брокера:

```text
продюсер --(1)--> брокер --(2)--> потребитель --(3)--> эффект
```

1. **Продюсер → брокер.** Повторяем отправку, пока брокер не подтвердит (Kafka `acks=all`, RabbitMQ publisher confirms). Повторы дают дубли, Kafka умеет отбрасывать их сама (идемпотентный продюсер), в RabbitMQ дедупликация на стороне потребителя по `MessageId`.
2. **Хранение.** Kafka: репликация, `min.insync.replicas`, `acks=all`. RabbitMQ: durable quorum-очередь и persistent-сообщения.
3. **Брокер → потребитель.** Подтверждение (коммит оффсета или `Ack`) после обработки: at-least-once.
4. **Эффект.** Идемпотентный потребитель: ключ дедупликации в базе, уникальный индекс, ключ у внешнего API.

И отдельно про вход в систему: если событие рождается из изменения в базе, публикуй его через **transactional outbox** (урок 1), иначе двойная запись.

## Что выбрать

| Задача | Выбор |
|---|---|
| Фоновые задачи своего сервиса: письма, отчёты, интеграции | очередь в Postgres (River) |
| Событие нужно многим сервисам, нужен порядок по ключу, большой поток, хранение и перечитывание, аналитика | Kafka |
| Очередь задач между сервисами, сложная маршрутизация, приоритеты, подтверждение каждого сообщения, RPC поверх очереди | RabbitMQ |
| Событие из изменения в базе нужно отдать в брокер | outbox в своей базе + ретранслятор (или CDC) |

На собеседовании ценится не «Kafka лучше», а умение назвать цену: Kafka это кластер, мониторинг лагов, схема сообщений, выбор числа партиций, ретраи через отдельные топики. RabbitMQ проще для задач, но сложнее масштабируется по объёму и не хранит историю. Очередь в Postgres проще всех, атомарна с данными, но нагружает базу.

<details><summary>Что такое партиция в Kafka и зачем она нужна?</summary>

Упорядоченный журнал внутри топика, только для дописывания, со своими оффсетами. Партиции дают масштабирование (раскладываются по брокерам, читаются параллельно) и порядок: внутри партиции сообщения упорядочены, между партициями нет. Партиция реплицируется: лидер и фолловеры, синхронные реплики образуют ISR.

</details>
<details><summary>Как гарантировать порядок событий одного заказа?</summary>

Писать их с одинаковым ключом (id заказа): партиция выбирается хешем ключа, все события заказа попадут в одну партицию, её читает один потребитель группы по порядку. Проверить балансировщик клиента (в kafka-go по умолчанию round-robin), не менять число партиций без плана, обрабатывать сообщения одного ключа последовательно.

</details>
<details><summary>Как работают consumer groups и ребалансировка?</summary>

Потребители с одним `group.id` делят партиции топика: каждая партиция у ровно одного потребителя группы, разные группы читают независимо. При входе или выходе потребителя (или пропущенном heartbeat) происходит ребалансировка: партиции перераспределяются, при eager-стратегиях (range, round-robin, sticky) вся группа на это время останавливается, cooperative-sticky (KIP-429) передаёт только меняющиеся партиции. Потребителей больше, чем партиций, значит, лишние простаивают. В Kafka 4.0 новый протокол групп (KIP-848) переносит распределение на брокер и избавляет от остановки всей группы.

</details>
<details><summary>Когда коммитить оффсет?</summary>

После обработки: тогда при сбое сообщение обработают повторно (at-least-once), а потребитель должен быть идемпотентным. До обработки получится at-most-once с потерями. Автокоммит по таймеру не связан с обработкой и может дать оба эффекта. При параллельной обработке коммитить только до первого необработанного сообщения.

</details>
<details><summary>Какие типы exchange есть в RabbitMQ?</summary>

`direct` (точное совпадение routing key), `fanout` (во все привязанные очереди), `topic` (шаблоны с `*` и `#`), `headers` (по заголовкам). Плюс безымянный default exchange, который маршрутизирует по имени очереди.

</details>
<details><summary>Что такое prefetch и зачем он нужен?</summary>

`basic.qos`: максимум неподтверждённых сообщений на потребителя (или канал). Без него брокер отдаёт одному потребителю всё, что есть, остальные простаивают, память растёт. С небольшим prefetch нагрузка распределяется, а брокер не отдаёт новое, пока потребитель не подтвердит старое.

</details>
<details><summary>Что такое DLQ и когда сообщение туда попадает?</summary>

Dead letter queue: очередь, куда попадают сообщения, которые не удалось обработать. В RabbitMQ через dead letter exchange: при `Nack`/`Reject` без requeue, истечении TTL, переполнении очереди, превышении лимита доставок у quorum-очереди. В Kafka это просто отдельный топик, куда потребитель сам перекладывает сообщение после N неудач. DLQ разбирают руками и переотправляют после исправления.

</details>
<details><summary>Чем Kafka отличается от RabbitMQ?</summary>

Kafka это распределённый журнал: сообщения хранятся заданное время, потребители сами ведут оффсеты, можно перечитать, порядок в партиции, очень высокая пропускная способность, масштабирование через партиции. RabbitMQ это брокер с маршрутизацией: сообщение удаляется после подтверждения, гибкие exchange, приоритеты, TTL, DLX, подтверждение каждого сообщения. Kafka для потоков событий и интеграции многих сервисов, RabbitMQ для очередей задач и маршрутизации.

</details>
<details><summary>Есть ли exactly-once в Kafka?</summary>

Есть в пределах Kafka: идемпотентный продюсер отбрасывает дубли отправки, транзакции атомарно пишут в несколько партиций и коммитят оффсеты, потребители с `read_committed` не видят незакоммиченное. Это exactly-once для «прочитал из Kafka, записал в Kafka». Для внешних эффектов (база, письмо) остаётся at-least-once плюс идемпотентность потребителя.

</details>
:::
