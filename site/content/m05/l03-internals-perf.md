# Каналы и мапы изнутри, оптимизация

Каналы и мапы ты используешь каждый день, и в модулях про язык и конкурентность мы уже заглядывали им под капот. Здесь спустимся на уровень исходников рантайма: как именно канал передаёт значение и будит горутину, что делает `select`, почему мапа на swiss-таблицах проверяет 8 слотов одной операцией и почему её нельзя писать из двух горутин. Вторая половина урока практическая: как найти и убрать лишние аллокации с помощью профилировщика и бенчмарков.

На собесах по Go это самые «глубокие» вопросы: «как устроен канал», «что такое sudog», «как select выбирает ветку», «почему map не потокобезопасна и что будет при гонке», «как устроена map с Go 1.24». А на работе знание устройства превращается в решения: когда канал, а когда мьютекс, когда `sync.Pool` поможет, а когда навредит, почему `fmt.Sprintf` в горячем цикле стоит денег.

Исходники для этого урока: `runtime/chan.go`, `runtime/select.go`, `runtime/runtime2.go` (`sudog`), `internal/runtime/maps` (`map.go`, `table.go`, `group.go`), все из Go 1.27.3. Открывай их параллельно с чтением: код рантайма хорошо прокомментирован.

## Канал изнутри

### Что создаёт make(chan T, n)

`make(chan T, n)` вызывает `runtime.makechan` и возвращает указатель на структуру `hchan`. Поэтому канал, как и мапа, передаётся в функции «по ссылке»: копируется указатель. Структура в Go 1.27.3:

```go
type hchan struct {
	qcount   uint           // сколько элементов сейчас в буфере (len)
	dataqsiz uint           // размер кольцевого буфера (cap)
	buf      unsafe.Pointer // массив на dataqsiz элементов
	elemsize uint16
	closed   uint32
	timer    *timer // для каналов из пакета time
	elemtype *_type
	sendx    uint   // куда писать следующий элемент
	recvx    uint   // откуда читать следующий
	recvq    waitq  // очередь ждущих получателей
	sendq    waitq  // очередь ждущих отправителей
	bubble   *synctestBubble // для testing/synctest
	lock     mutex
}
```

Сколько аллокаций стоит создание, зависит от типа элемента (`makechan`):

- буфер нулевого размера (небуферизованный канал или `chan struct{}`): одна аллокация, только `hchan`;
- элементы **без указателей**: одна аллокация, `hchan` и буфер лежат подряд в одном блоке, и GC этот блок не сканирует;
- элементы **с указателями**: две аллокации, отдельно `hchan` и буфер, потому что буфер нужно сканировать.

Проверено `testing.AllocsPerRun` на Go 1.27.3: `make(chan int, 10)` даёт 1 аллокацию, `make(chan *int, 10)` даёт 2, `make(chan int)` даёт 1.

### Кольцевой буфер

Буфер это массив, по которому `sendx` и `recvx` ходят по кругу:

```text
cap = 4, в канал отправили 1, 2, 3, получили 1, отправили 4, 5

buf:   [ 5 | 2 | 3 | 4 ]
             ^ recvx = 1 и sendx = 1; qcount = 4: буфер полон, следующим получим 2
```

Обрати внимание: при `sendx == recvx` буфер может быть и пуст, и полон. Отличить помогает `qcount`. И индексы в рантайме не берутся по модулю, а сбрасываются: `c.sendx++; if c.sendx == c.dataqsiz { c.sendx = 0 }`. Сравнение и сброс дешевле деления по модулю: ёмкость канала не обязана быть степенью двойки, поэтому `%` был бы настоящим делением.

### sudog: горутина в очереди

Когда горутина не может отправить или получить сразу, она встаёт в очередь `sendq` или `recvq`. В очереди лежит не сама горутина `g`, а обёртка `sudog` (из `runtime2.go`, основное):

```go
type sudog struct {
	g        *g      // ждущая горутина
	next     *sudog  // двусвязный список очереди
	prev     *sudog
	elem     ...     // указатель на значение: что отправить или куда положить
	isSelect bool    // горутина ждёт внутри select
	success  bool    // true: операция прошла; false: разбудили закрытием канала
	c        ...     // канал, на котором ждём
	// поля для семафоров, времени блокировки и т.д.
}
```

Зачем отдельная структура: одна горутина может ждать **сразу на нескольких** каналах (в `select`), и на каждом канале нужен свой элемент очереди. `sudog` берутся из кеша на P (`sudogcache`), чтобы блокировка на канале не аллоцировала.

`elem` указывает прямо в стек ждущей горутины: на её локальную переменную, куда нужно положить полученное значение, или откуда взять отправляемое.

### Отправка: chansend

Алгоритм `chansend` по шагам:

1. Канал `nil`: заблокироваться навсегда (`gopark` без шанса проснуться). Внутри `select` с `default` просто вернуть «не получилось».
2. **Быстрый путь для неблокирующей отправки** (`select` с `default`): если канал не закрыт и полон, вернуть false **без захвата мьютекса**. Два чтения по одному машинному слову (`c.closed` и заполненность буфера), никаких блокировок. В комментарии к `chansend` объясняется, почему такая проверка без мьютекса корректна.
3. Захватить `c.lock`.
4. Канал закрыт: отпустить мьютекс, паника `send on closed channel`.
5. В `recvq` есть ждущий получатель: **отдать значение прямо ему**, минуя буфер (`send`, затем `sendDirect`). Значение копируется в стек получателя по адресу из его `sudog.elem`. Это единственное место в рантайме, где одна горутина пишет в стек другой, и поэтому там отдельный барьер записи. Получатель переводится в состояние «готов» (`goready`).
6. В буфере есть место: скопировать значение в `buf[sendx]`, сдвинуть `sendx`, увеличить `qcount`.
7. Неблокирующая операция: вернуть false.
8. Иначе взять `sudog`, заполнить (`g`, `elem` на отправляемое значение), поставить в `sendq` и уснуть (`gopark`). Мьютекс канала отпускается уже после того, как горутина припаркована. Проснувшись, проверить `success`: если false, канал закрыли, паника.

### Получение: chanrecv

Симметрично, с одной тонкостью в шаге «есть ждущий отправитель»:

- канал **небуферизованный**: значение копируется прямо со стека отправителя;
- канал **буферизованный и полный**, и отправитель ждёт: получатель забирает значение из **головы** буфера (`buf[recvx]`), а значение ждущего отправителя кладёт в освободившийся слот, то есть в **хвост**. После этого `recvx` сдвигается, и `sendx = recvx`. Так сохраняется FIFO: значение ждущего отправителя встаёт в очередь после всех, кто уже в буфере.

Ещё деталь: после чтения из буфера слот обнуляется (`typedmemclr`). Иначе буфер держал бы указатель на уже выданный объект, и сборщик мусора не смог бы его освободить. В домашке ты повторишь это в своём кольцевом буфере.

### Закрытие: closechan

Под мьютексом: `closed = 1`, затем все `sudog` из **обеих** очередей собираются в список, у каждого `success = false`, получателям в `elem` записывается нулевое значение. После отпускания мьютекса все эти горутины будятся. Получатели вернутся с нулевым значением и `ok == false`, отправители проснутся и запаникуют. Повторное закрытие и закрытие `nil`-канала это паника.

### select изнутри

`select` с несколькими ветками компилируется в вызов `runtime.selectgo` (`select.go`). Две перестановки веток:

- **pollorder**: случайный порядок опроса (перемешивание через `cheaprandn`). Если готовы несколько веток, выбирается первая готовая в этом случайном порядке. Это и даёт равномерный выбор и защищает от голодания одной ветки.
- **lockorder**: порядок захвата мьютексов, отсортированный **по адресам** каналов. Все каналы `select` блокируются в одном глобальном порядке, поэтому два `select` на одних и тех же каналах не устроят взаимоблокировку.

Алгоритм: захватить мьютексы всех каналов в `lockorder`, пройти ветки в `pollorder` и выполнить первую готовую. Если готовых нет и есть `default`, выполнить его. Иначе создать по `sudog` на **каждый** канал, встать во все очереди, уснуть. Когда одна из операций сработала, горутина просыпается, снова блокирует все каналы и убирает свои `sudog` из остальных очередей.

Отсюда практический вывод: `select` на 10 каналах дороже `select` на двух, и каждый проход блокирует все каналы.

::: hood Сколько стоит канал
Каждая операция с каналом берёт мьютекс и копирует значение, блокирующая ещё и паркует горутину через планировщик. Замер на Go 1.27.3 (Apple M4, одна горутина без конкуренции, если не сказано иное):

| Операция | Время |
|---|---|
| `atomic.Int64.Add` | ~1.9 нс |
| `sync.Mutex` Lock + инкремент + Unlock | ~2.0 нс |
| буферизованный канал: отправить и сразу получить | ~15 нс |
| пинг-понг между двумя горутинами по небуферизованным каналам | ~170-190 нс |

Канал на порядок дороже мьютекса даже без ожидания, а передача между горутинами это ещё и переключение через планировщик. Каналы нужны, чтобы передавать владение данными и синхронизировать горутины, а защищать счётчик или мапу дешевле мьютексом или атомиком.
:::

## Мапа изнутри: swiss-таблицы

Основы устройства мапы (группы по 8 слотов, контрольное слово, H1 и H2, надгробия, каталог таблиц) мы разобрали в уроке [Мапы](../m01/l07-maps). Здесь три вещи, которых там не было: как именно сравниваются 8 слотов за раз, как идёт пробирование и почему мапа не потокобезопасна.

### Заголовок мапы

`map[K]V` это указатель на `maps.Map` (`internal/runtime/maps/map.go`):

```go
type Map struct {
	used        uint64         // число элементов, это len(m); поле первое, len читает его напрямую
	seed        uintptr        // случайная соль хеш-функции, своя у каждой мапы
	dirPtr      unsafe.Pointer // каталог таблиц, или сразу одна группа для маленькой мапы
	dirLen      int
	globalDepth uint8          // сколько старших бит хеша выбирают таблицу
	globalShift uint8
	writing     uint8          // флаг «идёт запись», для обнаружения гонок
	tombstonePossible bool
	clearSeq    uint64
}
```

Ключи и значения больше 128 байт (`MapMaxKeyBytes`, `MapMaxElemBytes` в `internal/abi/map.go`) в слотах не хранятся: в слоте лежит указатель на отдельно выделенный объект.

### 8 сравнений за одну операцию

Контрольное слово группы это 8 байт, байт на слот: `0x80` пустой, `0xFE` удалён, `0hhhhhhh` занят, и `hhhhhhh` это 7 младших бит хеша ключа (H2). Чтобы найти кандидатов на ключ с хешем H2, нужно найти в слове все байты, равные H2. Делать это циклом по байтам медленно. Трюк называется SWAR (SIMD within a register): обработать 8 байт одним 64-битным регистром.

Переносимая версия из `group.go` Go 1.27.3:

```go
const (
	bitsetLSB = 0x0101010101010101
	bitsetMSB = 0x8080808080808080
)

func ctrlGroupMatchH2(g ctrlGroup, h uintptr) bitset {
	v := uint64(g) ^ (bitsetLSB * uint64(h))
	// ...вариант для arm64 опущен
	return bitset(((v - bitsetLSB) &^ v) & bitsetMSB)
}
```

По шагам:

1. `bitsetLSB * h` размножает H2 во все 8 байт: при `h = 0x11` получится `0x1111111111111111`.
2. XOR с контрольным словом **обнуляет ровно те байты**, где слот совпал.
3. `(v - 0x0101...01) &^ v` выставляет старший бит у нулевых байтов: из нулевого байта вычитание единицы делает `0xFF` (старший бит 1), а `&^ v` убирает байты, у которых старший бит и так был.
4. `& 0x8080...80` оставляет только старшие биты. Результат: в байте `i` стоит `0x80`, если слот `i` кандидат.

У этого трюка есть известный дефект, и комментарий в исходнике его признаёт: заём при вычитании может перетечь в соседний байт, и тогда байт, следующий за совпавшим и отличающийся от H2 только младшим битом, тоже покажется совпавшим. Это ложное срабатывание не ломает корректность: каждый кандидат всё равно проверяется полным сравнением ключа, а случайное совпадение 7 бит и так бывает с вероятностью 1/128. На arm64 используется точный вариант без заёма, а на amd64 эта функция вообще заменяется SIMD-инструкциями (интринсик компилятора). Точную версию ты напишешь в домашке.

Найденные кандидаты перебираются от младшего: номер слота это `bits.TrailingZeros64(match) / 8`, затем младший установленный бит сбрасывается.

### Пробирование

Если в стартовой группе ключа нет, а пустых слотов тоже нет, ключ может лежать дальше. Следующая группа выбирается **треугольной** последовательностью (`probeSeq` в `table.go`):

```text
p(i) = (H1 + (i*i + i) / 2) mod число_групп
смещения: 0, 1, 3, 6, 10, 15...
```

Число групп в таблице всегда степень двойки, и при этом условии последовательность обходит каждую группу ровно один раз. Поиск останавливается на первой группе, где есть **пустой** слот: значит, при вставке ключ дошёл бы сюда и не дальше. Поэтому таблица никогда не заполняется целиком (максимум 7/8), и поэтому удаление из полной группы ставит надгробие, а не «пусто»: иначе поиск других ключей обрывался бы раньше времени.

### Почему мапа не потокобезопасна

Так решили авторы языка: в большинстве случаев мапа используется из одной горутины, и встроенная блокировка замедлила бы всех ради меньшинства. Синхронизацию добавляет тот, кому она нужна.

Но запись в мапу меняет несколько слов сразу: контрольный байт, ключ, значение, счётчик, а при росте ещё и каталог. Две одновременные записи могут оставить структуру в несогласованном состоянии, и это уже не «потерянное обновление», а порча памяти рантайма. Поэтому мапа **пытается** заметить гонку. Перед записью рантайм переключает флаг `m.writing ^= 1`, после записи переключает обратно. Если операция видит флаг, выставленный другой горутиной, она вызывает `fatal("concurrent map writes")` или `fatal("concurrent map read and map write")`.

Это именно `fatal`, а не `panic`: `recover` не поможет, процесс завершается. Проверено на Go 1.27.3: программа с `defer recover()` в `main` и двумя горутинами, пишущими в одну мапу, падает с `fatal error: concurrent map writes`, и отложенная функция не выполняется. Проверка не гарантирует обнаружения (флаг обычный, не атомарный), гарантированно гонки ловит только `-race`.

Что делать:

- `sync.Mutex` или `sync.RWMutex` вокруг мапы: стандартный выбор;
- `sync.Map`: оптимизирована для двух случаев из документации: ключ записывается один раз и много раз читается (кеш, который только растёт), или разные горутины работают с непересекающимися наборами ключей. В остальных случаях обычная мапа с мьютексом не хуже и типобезопаснее;
- шардирование: N мап с N мьютексами, шард по хешу ключа. Меньше конкуренции за один мьютекс.

::: trap Мапа под «почти только чтением» без блокировки
```go
// Плохо: читатели без блокировки, «писатель же редкий»
var cache = map[string]string{}

func Get(k string) string { return cache[k] } // из многих горутин

func Refresh(k, v string) { cache[k] = v } // раз в минуту
```

Редкая запись во время чтения это всё равно гонка, и когда-нибудь процесс упадёт с `fatal error: concurrent map read and map write` без шанса на `recover`.

```go
// Хорошо: RWMutex, читатели не мешают друг другу
var (
	mu    sync.RWMutex
	cache = map[string]string{}
)

func Get(k string) string {
	mu.RLock()
	defer mu.RUnlock()
	return cache[k]
}

func Refresh(k, v string) {
	mu.Lock()
	defer mu.Unlock()
	cache[k] = v
}
```

Если данные целиком обновляются редко, ещё лучше подменять мапу целиком: строить новую и публиковать через `atomic.Pointer[map[string]string]`. Читатели вообще без блокировок, но старую мапу после публикации менять нельзя.
:::

## Оптимизация на практике

Правило номер один: **сначала измерь**. Оптимизация без профиля это гадание, и чаще всего гадание неверное. Цикл работы:

1. Бенчмарк, который воспроизводит горячий путь, с `-benchmem`.
2. Профиль (CPU и память), чтобы найти, где время и аллокации.
3. Гипотеза и одно изменение.
4. Бенчмарк «после» и сравнение через `benchstat` на 10 прогонах.
5. Повторить, пока есть смысл.

Инструменты ты видел в модуле про тесты, здесь пройдём цикл целиком на примере.

### Пример: отчёт по пользователям

Функция строит текст «id=… name=…» по слайсу пользователей. Первая версия, как её пишут в первый день:

```go
func RenderV0(users []User) string {
	s := ""
	for _, u := range users {
		s += fmt.Sprintf("id=%d name=%s\n", u.ID, u.Name)
	}
	return s
}
```

Бенчмарк на 1000 пользователей:

```go
func BenchmarkRenderV0(b *testing.B) {
	for b.Loop() {
		RenderV0(users)
	}
}
```

```bash
go test -run=^$ -bench=Render -benchmem -memprofile=mem.out -cpuprofile=cpu.out .
```

```text
BenchmarkRenderV0-10    1518    848266 ns/op    11228771 B/op    4012 allocs/op
```

11 МБ и 4012 аллокаций на тысячу строк по ~22 байта. Профиль памяти показывает виновную строку:

```bash
go tool pprof -sample_index=alloc_space -list 'RenderV0' mem.out
```

```text
   13.66GB    13.70GB     17:		s += fmt.Sprintf("id=%d name=%s\n", u.ID, u.Name)
```

Почему так много: `s += x` каждый раз создаёт новую строку длины `len(s) + len(x)` и копирует в неё всё накопленное. Для 1000 строк это сумма арифметической прогрессии, квадратичный объём копирования. Плюс `Sprintf` на каждой итерации: упаковка `u.ID` в `any` (аллокация, если ID не меньше 256), упаковка `u.Name` в `any` (аллокация заголовка строки) и итоговая строка. Итого около 4 аллокаций на пользователя.

Если в CPU-профиле сервиса заметную долю занимают `mallocgc`, `gcBgMarkWorker`, `gcAssistAlloc`, смотри профиль памяти.

У профиля памяти четыре среза, их переключает `-sample_index`, и путать их нельзя:

- `alloc_space` и `alloc_objects`: сколько байт и объектов **выделено** с начала работы, включая давно освобождённые. Отвечает на вопрос «кто мусорит и нагружает GC». Его мы смотрели выше.
- `inuse_space` и `inuse_objects` (по умолчанию для профиля `heap`): что **живо сейчас**, по данным последней сборки мусора. Отвечает на вопрос «кто держит память». Им ищут утечки: кеш без ограничения, растущая мапа, забытые горутины со своими данными.

Профиль сэмплирующий: по умолчанию записывается в среднем одна аллокация на каждые 512 КБ выделенной памяти (`runtime.MemProfileRate`), поэтому числа в нём это оценка, а не точный подсчёт.

**Шаг 1.** Убрать квадратичную конкатенацию: `strings.Builder` накапливает байты в растущем буфере и в `String()` отдаёт его без копирования.

```go
func RenderV1(users []User) string {
	var b strings.Builder
	for _, u := range users {
		fmt.Fprintf(&b, "id=%d name=%s\n", u.ID, u.Name)
	}
	return b.String()
}
```

```text
BenchmarkRenderV1-10   20160     60254 ns/op      107383 B/op    2010 allocs/op
```

В 14 раз быстрее, памяти в 100 раз меньше. Но 2010 аллокаций остались: ровно две на пользователя. Это упаковка аргументов `Fprintf` в `any`. `Fprintf` принимает `...any`, и компилятор не может доказать, что `fmt` не сохранит аргументы.

**Шаг 2.** Убрать `fmt` из горячего пути, писать байты напрямую, заранее выделить память:

```go
func RenderV2(users []User) string {
	var b strings.Builder
	b.Grow(len(users) * 32) // оценка размера: одна аллокация вместо серии ростов
	var num [20]byte         // буфер для числа на стеке
	for _, u := range users {
		b.WriteString("id=")
		b.Write(strconv.AppendInt(num[:0], int64(u.ID), 10))
		b.WriteString(" name=")
		b.WriteString(u.Name)
		b.WriteByte('\n')
	}
	return b.String()
}
```

Одна аллокация на весь отчёт. `strconv.AppendInt` пишет цифры в переданный слайс, а слайс смотрит в массив `num` на стеке. 32768 байт вместо 32000 из `Grow`: округление до класса размера, вспомни прошлый урок.

### Приёмы сокращения аллокаций

- **Предвыделение.** `make([]T, 0, n)`, когда размер известен или оценивается: `append` не будет перевыделять и копировать. `make(map[K]V, n)` сразу создаёт таблицы нужного размера. `strings.Builder.Grow`, `bytes.Buffer.Grow`.
- **Append-функции вместо возвращающих строку**: `strconv.AppendInt`, `strconv.AppendQuote`, `time.Time.AppendFormat`, `fmt.Appendf`. Пишут в твой буфер, а буфер можно держать на стеке или переиспользовать.
- **Переиспользование слайса**: `buf = buf[:0]` обнуляет длину, но сохраняет ёмкость. Цикл, который каждый раз собирает временный слайс, может работать с одним.
- **Меньше интерфейсов в горячем пути**: `fmt` в цикле, `any` в структурах, `errors.New` в цикле (ошибку-значение объявляют один раз в переменной пакета).
- **Значения вместо указателей в больших коллекциях**: `[]Point` вместо `[]*Point`. Одна аллокация на весь слайс вместо одной на элемент, и GC не сканирует объекты без указателей вовсе.
- **`sync.Pool`** для временных объектов, которые дорого создавать и которые нужны многим горутинам: буферы, кодировщики. Подробно ниже.
- **PGO** (profile-guided optimization, по умолчанию с Go 1.21): положи CPU-профиль из продакшна в `default.pgo` рядом с `main`, и компилятор сам будет агрессивнее встраивать горячие функции. Иногда это убирает и аллокации: после встраивания объект может перестать убегать.

### sync.Pool

`sync.Pool` это потокобезопасный набор временных объектов для переиспользования. Типичный случай: буфер для сериализации ответа в HTTP-хендлере.

```go
var bufPool = sync.Pool{
	New: func() any { return new(bytes.Buffer) },
}

func Encode(w io.Writer, u User) {
	buf := bufPool.Get().(*bytes.Buffer)
	buf.Reset() // объект из пула грязный: сбрось состояние
	writeUser(buf, u)
	w.Write(buf.Bytes())
	bufPool.Put(buf) // вернуть, только когда буфер больше не используется
}
```

Бенчмарк с `b.RunParallel` на 10 P (Go 1.27.3):

```text
BenchmarkEncodeNoPool-10    68148096    15.75 ns/op    64 B/op    1 allocs/op
BenchmarkEncodePool-10     122648146    11.81 ns/op     0 B/op    0 allocs/op
```

Выигрыш по времени скромный, главное, что исчезла аллокация, а с ней и работа для GC.

::: hood Как устроен sync.Pool
У каждого P свой локальный кеш (`poolLocal`): приватный слот на один объект и общий список, из которого могут воровать другие P. `Get` сначала смотрит свой приватный слот, потом свой список, потом ворует у других P, потом смотрит **кеш жертв** (victim), и только затем вызывает `New`. Блокировок на быстром пути нет.

Пул **очищается при каждой сборке мусора**: текущее содержимое переезжает в кеш жертв, а прошлый кеш жертв выбрасывается. Значит, объект, к которому не обращались, живёт в пуле максимум два цикла GC. Кеш жертв появился в Go 1.13: до этого пул опустошался целиком на каждом цикле, и после каждой сборки все горутины разом шли в `New`.
:::

::: trap Пул как кеш и грязные объекты
```go
// Плохо: пул как кеш соединений и забытый Reset
var connPool = sync.Pool{New: func() any { return dial() }}

func handle() {
	c := connPool.Get().(*Conn) // соединение может исчезнуть из пула при любом GC
	defer connPool.Put(c)       // и закрыто оно не будет: утечка дескрипторов
	// ...
}

func render() []byte {
	buf := bufPool.Get().(*bytes.Buffer) // без Reset: в буфере данные прошлого запроса
	defer bufPool.Put(buf)
	buf.WriteString("...")
	return buf.Bytes() // и наружу уходит слайс, который после Put достанется другой горутине
}
```

Пул может выбросить объект в любой момент без уведомления, поэтому в нём хранят только то, что не требует закрытия. Для соединений нужен настоящий пул с ограничением и закрытием (как в `database/sql` или `http.Transport`).

```go
// Хорошо: сброс после Get, копия наружу, Put в самом конце
func render() []byte {
	buf := bufPool.Get().(*bytes.Buffer)
	buf.Reset()
	defer bufPool.Put(buf)
	buf.WriteString("...")
	return bytes.Clone(buf.Bytes())
}
```

Ещё две тонкости. Класть в пул указатели, а не значения: `Put` принимает `any`, и значение (например, слайс `[]byte`) упаковывается с аллокацией, сводя смысл пула на нет (статический анализатор staticcheck ругается на это правилом SA6002). И не возвращай в пул гигантские буферы: один запрос на 100 МБ оставит в пуле буфер на 100 МБ навсегда. Проверяй `buf.Cap()` перед `Put` и выбрасывай слишком большие.
:::

::: trap Оптимизация без профиля
```go
// Плохо: «sync.Pool ускоряет», завернули в пул структуру из двух полей
var pointPool = sync.Pool{New: func() any { return new(Point) }}

func dist(x, y float64) float64 {
	p := pointPool.Get().(*Point)
	defer pointPool.Put(p)
	p.X, p.Y = x, y
	return math.Hypot(p.X, p.Y)
}
```

Без пула `Point` здесь вообще жил бы на стеке, ноль аллокаций. С пулом добавились приведение типа, обращения к локальному кешу P и `defer`. Код стал медленнее и сложнее.

```go
// Хорошо: сначала -gcflags=-m и бенчмарк, потом решение
func dist(x, y float64) float64 {
	p := Point{x, y}
	return math.Hypot(p.X, p.Y)
}
```

Порядок всегда один: профиль показывает проблему, бенчмарк подтверждает выигрыш.
:::

## Что выведет программа?

```go
m := map[float64]int{}
m[math.NaN()] = 1
m[math.NaN()] = 2
_, ok := m[math.NaN()]
fmt.Println(len(m), ok)
```

<Predict :options="['1 true', '2 false', '1 false', 'паника: NaN нельзя использовать как ключ']" :correct="1">

`NaN != NaN`, поэтому каждая вставка не находит «равного» ключа и добавляет новый элемент: `len` равен 2. Поиск по `NaN` тоже никогда не находит равного ключа: `false`. Хеш NaN к тому же случайный (так сделано специально, чтобы такие ключи не скапливались в одной группе). Достать эти элементы можно только обходом `range`, удалить только `clear(m)`.

</Predict>

```go
a, b := make(chan int, 1), make(chan int, 1)
na, nb := 0, 0
for range 10_000 {
	a <- 1
	b <- 1
	select {
	case <-a:
		na++
		<-b
	case <-b:
		nb++
		<-a
	}
}
fmt.Println(na > 4000, nb > 4000)
```

<Predict :options="['true false', 'false true', 'true true', 'каждый раз по-разному']" :correct="2">

Обе ветки готовы на каждой итерации. `selectgo` перемешивает порядок опроса (`pollorder`) случайно, поэтому ветки выбираются примерно поровну, около 5000 раз каждая. Вероятность, что одна из них наберёт меньше 4000 из 10 000, ничтожна. Порядок веток в исходнике на выбор не влияет.

</Predict>

```go
var sink any

func main() {
	a := testing.AllocsPerRun(100, func() { sink = make(chan int, 10) })
	b := testing.AllocsPerRun(100, func() { sink = make(chan *int, 10) })
	fmt.Println(a, b)
}
```

<Predict :options="['1 1', '1 2', '2 2', '0 1']" :correct="1">

Для элементов без указателей `makechan` выделяет `hchan` и буфер одним блоком, который GC не сканирует. Для элементов с указателями буфер нужно сканировать, поэтому он выделяется отдельно с информацией о типе: две аллокации.

</Predict>

<details><summary>Как устроен канал в Go?</summary>

`make(chan T, n)` создаёт в куче структуру `hchan`: кольцевой буфер на `n` элементов (`buf`, `sendx`, `recvx`, `qcount`, `dataqsiz`), флаг `closed`, две очереди ждущих горутин `sendq` и `recvq` и мьютекс `lock`, который защищает всё это. Ждущие горутины стоят в очередях в обёртках `sudog`, где есть указатель на значение в их стеке. Отправка: под мьютексом проверить закрытие (паника), отдать значение напрямую ждущему получателю (копирование в его стек), или положить в буфер, или встать в `sendq` и уснуть. Получение симметрично. Закрытие будит всех ждущих.

</details>
<details><summary>Что такое sudog и зачем он нужен?</summary>

Элемент очереди ожидания: горутина плюс указатель на значение (откуда отправить или куда получить) плюс служебные поля (`isSelect`, `success`, канал). Отдельная структура нужна, потому что одна горутина в `select` ждёт сразу на нескольких каналах и стоит в нескольких очередях. `sudog` переиспользуются через кеш на P. Поле `success` после пробуждения говорит, прошла операция или канал закрыли.

</details>
<details><summary>Что происходит, когда отправитель пишет в канал, где уже ждёт получатель?</summary>

Значение копируется напрямую в стек получателя по адресу из его `sudog`, минуя буфер, даже если канал буферизованный (буфер в этот момент заведомо пуст). Получатель помечается готовым к запуску. Это единственное место, где одна горутина пишет в стек другой. Копирование одно, а через буфер их было бы два.

</details>
<details><summary>Как select выбирает ветку, если готовы несколько?</summary>

Случайно и равномерно: `selectgo` перемешивает порядок опроса веток (`pollorder`) и берёт первую готовую. Мьютексы каналов захватываются в порядке адресов каналов (`lockorder`), чтобы не было взаимоблокировок между разными `select`. Если готовых нет и нет `default`, горутина ставит по `sudog` в очередь каждого канала и засыпает, а проснувшись, убирает себя из остальных очередей.

</details>
<details><summary>Почему map не потокобезопасна и что будет при одновременной записи?</summary>

Синхронизация замедлила бы все мапы ради меньшинства, поэтому её нет. Запись меняет несколько слов, одновременные записи ломают структуру. Рантайм пытается обнаружить гонку флагом `writing` и при обнаружении вызывает `fatal error: concurrent map writes` (или `concurrent map read and map write`). Это не паника, `recover` не перехватит, процесс завершится. Обнаружение не гарантировано, надёжно ловит только `-race`. Решения: мьютекс, `sync.Map` для её двух сценариев, шардирование.

</details>
<details><summary>Как устроена map начиная с Go 1.24?</summary>

Swiss-таблицы с открытой адресацией. Слоты собраны в группы по 8 с контрольным словом: байт на слот, в занятом 7 младших бит хеша (H2). Поиск: H1 (старшие 57 бит) выбирает стартовую группу, H2 сравнивается сразу со всеми 8 байтами одной операцией (SWAR или SIMD), кандидаты проверяются полным сравнением ключа, следующие группы выбираются квадратичным (треугольным) пробированием до группы с пустым слотом. Загрузка не больше 7/8, удаление из полной группы ставит надгробие. Мапа делится на таблицы до 1024 слотов, выбираемые старшими битами хеша через каталог (extendible hashing): рост затрагивает одну таблицу, а не всю мапу. Мапа до 8 элементов это одна группа без таблиц.

</details>
<details><summary>Как ты будешь искать причину высокого потребления CPU или памяти в Go-сервисе?</summary>

Снять профили с работающего сервиса через `net/http/pprof` (CPU за 30 секунд, `heap`, `allocs`) или из бенчмарка. В CPU-профиле смотреть `-top -cum` и `-list` по своим функциям; заметная доля `mallocgc`, `gcBgMarkWorker`, `gcAssistAlloc` значит, что проблема в аллокациях. Тогда профиль `allocs` с `-sample_index=alloc_space` или `alloc_objects` укажет строки. Дальше бенчмарк на горячий путь, изменение, сравнение `benchstat`. Типичные лекарства: убрать `fmt` и конкатенацию из циклов, предвыделить слайсы и мапы, переиспользовать буферы, `sync.Pool` для временных объектов. Если растёт `heap` (живые объекты), искать, кто держит ссылки: кеши без ограничения, утёкшие горутины.

</details>
<details><summary>Когда sync.Pool помогает, а когда вредит?</summary>

Помогает для временных объектов, которые дорого создавать и которые часто нужны многим горутинам: буферы сериализации, кодировщики. Убирает аллокации и нагрузку на GC. Вредит или бесполезен, если объект и так живёт на стеке, если объект требует закрытия (пул выбрасывает объекты при каждом GC без уведомления), если в пул кладут значения вместо указателей (аллокация при упаковке в `any`), если забывают сбрасывать состояние или возвращают гигантские буферы. Внутри: локальный кеш на каждом P, воровство у соседей, очистка при каждом GC с кешем жертв на один цикл.

</details>

```bash
cd homework && go test -race -count=5 -v ./m05/l03-internals-perf/ -run TestMiniChan
```

</Hw>
