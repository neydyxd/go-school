# Как работает веб: от TCP до REST

Ты много лет смотрел на HTTP из браузера: вкладка Network, `fetch`, статусы, CORS-ошибки в консоли. Теперь ты будешь по ту сторону. Сервер не видит «запрос из `fetch`», он видит поток байтов из сокета, который надо разобрать, проверить и превратить в ответ. И почти все загадочные баги бэкенда живут в этом зазоре: «почему фронт получает CORS-ошибку, хотя сервер ответил 200», «почему повтор запроса списал деньги дважды», «почему кеш отдал чужие данные».

На собесе на джуна вопросы про HTTP звучат почти всегда, и ответ «ну, GET для получения, POST для отправки» засчитывают как незнание. Спрашивают, что такое идемпотентность и почему PUT идемпотентен, а POST нет; чем 401 отличается от 403; что такое preflight; как работает ETag. Это не теория ради теории: от этих ответов зависит, как ты спроектируешь ретраи, кеширование и обработку ошибок.

Этот урок без `net/http`-магии: разбираем путь запроса от DNS до байтов ответа, а в домашке пишешь парсер HTTP-запроса руками. Со следующего урока начнём писать сервер на стандартной библиотеке, и ты будешь понимать, что именно она делает за тебя.

## Путь запроса: от URL до байтов

Что происходит, когда клиент делает `GET https://api.example.com/users/42`:

1. **DNS**: имя `api.example.com` превращается в IP-адрес.
2. **TCP**: клиент открывает соединение с этим IP на порт 443.
3. **TLS**: поверх TCP договариваются о шифровании и проверяют сертификат сервера.
4. **HTTP**: по зашифрованному каналу уходит запрос, приходит ответ.
5. Соединение остаётся открытым для следующих запросов (keep-alive).

Каждый шаг стоит времени, и бэкендеру важно понимать, сколько.

### DNS

DNS это распределённая телефонная книга. Клиент спрашивает резолвер (обычно у провайдера, в облаке или `8.8.8.8`), тот при необходимости идёт к корневым серверам, потом к серверам зоны `.com`, потом к серверам `example.com` и возвращает запись:

- `A`: IPv4-адрес, `AAAA`: IPv6-адрес;
- `CNAME`: «это имя на самом деле псевдоним вот того»;
- `MX`, `TXT` и другие для почты и проверок.

У каждой записи есть **TTL**: сколько секунд её можно кешировать. Поэтому смена IP у сервиса «доезжает» до клиентов не мгновенно. Посмотреть руками:

```bash
dig +short go.dev
dig go.dev A    # полный ответ с TTL
```

В Go резолвинг делает пакет `net`: либо собственной реализацией на Go, либо через системную библиотеку (переключается `GODEBUG=netdns=go` или `netdns=cgo`). Тебе это понадобится, когда в контейнере «вдруг» не резолвится имя.

### TCP: надёжная труба

IP доставляет отдельные пакеты и ничего не гарантирует: пакеты теряются, дублируются, приходят не по порядку. **TCP** строит поверх этого надёжный упорядоченный поток байтов: нумерует байты, ждёт подтверждений, перепосылает потерянное, регулирует скорость.

Перед передачей данных стороны делают **тройное рукопожатие**:

```text
клиент                     сервер
  | ---- SYN ---------------> |
  | <--- SYN-ACK ------------ |
  | ---- ACK + данные ------> |
```

Это один полный круг (RTT) до первого байта запроса. Если сервер в другом полушарии и RTT 150 мс, только открытие соединения стоит 150 мс. Отсюда главное правило клиента: **переиспользуй соединения**, не открывай новое на каждый запрос. Вернёмся к этому в уроке про `http.Client`.

Важно для собеса: TCP отдаёт **поток байтов, а не сообщения**. Один `write` на клиенте может прийти двумя `read` на сервере и наоборот. Поэтому HTTP нужны правила, где кончается запрос: пустая строка после заголовков и `Content-Length`.

### TLS: шифрование и проверка, с кем говоришь

HTTPS это HTTP поверх TLS. TLS решает две задачи:

- **Конфиденциальность и целостность**: трафик зашифрован, подменить байт незаметно нельзя.
- **Аутентичность**: сервер показывает сертификат, подписанный удостоверяющим центром, которому доверяет клиент. Сертификат выписан на имя (`api.example.com`), и клиент сверяет его с тем, куда хотел попасть.

В TLS 1.3 рукопожатие занимает один RTT поверх TCP-шного: клиент сразу отправляет свои ключевые параметры, сервер отвечает своими и сертификатом, и дальше всё шифруется. В TLS 1.2 было два RTT. Итого новое HTTPS-соединение стоит примерно 2 RTT до первого байта запроса. Посмотреть рукопожатие можно так:

```bash
openssl s_client -connect go.dev:443 -servername go.dev </dev/null | head -20
curl -v https://go.dev -o /dev/null   # строки "SSL connection using TLSv1.3"
```

::: hood Где TLS живёт в Go
TLS реализован в пакете `crypto/tls` на чистом Go, без OpenSSL. `http.ListenAndServeTLS` поднимает TLS-листенер, а `http.Client` по умолчанию проверяет сертификат по системному хранилищу корневых сертификатов. Флаг `InsecureSkipVerify: true` в `tls.Config` выключает эту проверку, и тогда шифрование есть, а уверенности, что ты говоришь со своим сервером, нет. В продакшене такой флаг это баг безопасности, даже если «на тесте работало».

В реальных системах TLS часто заканчивается на балансировщике или ingress (TLS termination), а до Go-сервиса доходит обычный HTTP по внутренней сети. Поэтому сервис на Go часто слушает простой `:8080`.
:::

## HTTP/1.1 побайтно

HTTP/1.1 текстовый протокол. Вот запрос целиком, как его видит сервер в сокете (`\r\n` это два байта: возврат каретки и перевод строки):

```text
POST /api/links HTTP/1.1\r\n
Host: sho.rt\r\n
Content-Type: application/json\r\n
Content-Length: 27\r\n
\r\n
{"url":"https://go.dev/doc"}
```

Структура:

1. **Стартовая строка**: метод, цель (путь и query), версия протокола. Три части через один пробел.
2. **Заголовки**: строки `Имя: значение`. Имена регистронезависимы: `content-type` и `Content-Type` одно и то же.
3. **Пустая строка** `\r\n`: заголовки кончились.
4. **Тело**: ровно `Content-Length` байт. Не символов, байт.

Ответ устроен так же, только вместо стартовой строки **строка статуса**:

```text
HTTP/1.1 201 Created\r\n
Content-Type: application/json\r\n
Location: https://sho.rt/abc\r\n
Content-Length: 61\r\n
\r\n
{"code":"abc","short_url":"https://sho.rt/abc","url":"..."}
```

Несколько деталей, которые важны серверу:

- **`Host` обязателен в HTTP/1.1.** На одном IP живёт много сайтов (виртуальные хосты), и только по `Host` сервер понимает, кому адресован запрос. Запрос HTTP/1.1 без `Host` сервер обязан отклонить с 400.
- **Длина тела** задаётся либо `Content-Length`, либо `Transfer-Encoding: chunked` (тело кусками, у каждого куска своя длина, в конце кусок нулевой длины). Если сервер не знает заранее размер ответа (стриминг), он шлёт chunked. Go делает это сам, если ты не выставил `Content-Length` и ответ не влез в буфер.
- **Keep-alive** в HTTP/1.1 включён по умолчанию: после ответа соединение не закрывается и ждёт следующий запрос. `Connection: close` просит закрыть.

Как Go называет заголовки: пакет `net/http` хранит их в `http.Header`, это `map[string][]string` с ключами в **каноническом виде** (каждое слово с заглавной: `X-Request-Id`). Методы `Get`, `Set`, `Add` канонизируют имя сами, а прямой доступ к мапе нет:

```go
h := http.Header{}
h.Set("content-type", "text/plain")
h.Add("X-request-id", "1")
fmt.Println(h.Get("CONTENT-TYPE"), h["content-type"], len(h["X-Request-Id"]))
```

<Predict :options="['text/plain [text/plain] 1', 'text/plain [] 1', '[] [] 0', 'text/plain [] 0']" :correct="1">

`Set` положил значение под ключ `Content-Type`, `Get` канонизировал `CONTENT-TYPE` в то же самое и нашёл. А обращение к мапе напрямую по `"content-type"` ничего не канонизирует, такого ключа нет, отсюда пустой срез. `X-request-id` после канонизации стал `X-Request-Id`. Мораль: работай с заголовками только через методы.

</Predict>

::: trap Content-Length в символах
Длина тела считается в байтах. Кириллица в UTF-8 занимает 2 байта на букву, эмодзи 4. Если вручную выставить длину по числу символов, получишь обрезанное тело (сервер прочитает меньше) или зависание (сервер ждёт байты, которые не придут).

```go
// плохо: 6 символов, а байтов 12
w.Header().Set("Content-Length", strconv.Itoa(utf8.RuneCountInString(body)))

// хорошо: len у строки и так считает байты, а чаще всего
// длину вообще не надо выставлять руками: net/http посчитает сам
w.Header().Set("Content-Length", strconv.Itoa(len(body)))
```
:::

::: hood Request smuggling: почему парсер должен быть занудой
Между клиентом и Go-сервисом обычно стоит прокси или балансировщик. Если прокси и сервер **по-разному** определяют границу запроса, атакующий может «пронести» второй запрос внутри тела первого. Классика: запрос с одновременно `Content-Length` и `Transfer-Encoding: chunked`, или с пробелом перед двоеточием `Transfer-Encoding : chunked`, который один парсер игнорирует, а другой понимает. Прокси считает, что запрос один, сервер видит два, и второй исполняется от имени чужого соединения.

Поэтому RFC 9112 требует отвергать заголовки с пробелом перед двоеточием и конфликтующие длины, а `net/http` строг в разборе. В домашке ты напишешь такой строгий парсер сам.
:::

### Посмотреть руками

`curl -v` показывает запрос и ответ вместе с заголовками (строки с `>` ушли на сервер, с `<` пришли от него):

```bash
curl -v https://go.dev/ -o /dev/null
```

А `nc` (netcat) позволяет отправить сырые байты без всякого HTTP-клиента:

```bash
printf 'GET / HTTP/1.1\r\nHost: example.com\r\nConnection: close\r\n\r\n' | nc example.com 80
```

Это лучший способ понять, что HTTP это просто текст в TCP-сокете.

## HTTP/2 и HTTP/3 коротко

У HTTP/1.1 есть беда: **одно соединение обслуживает один запрос за раз**. Пока ответ не пришёл целиком, следующий запрос по этому соединению ждёт (head-of-line blocking). Браузеры обходят это, открывая до 6 соединений на хост, а это лишние рукопожатия.

**HTTP/2** (2015) сохраняет смысл HTTP (методы, статусы, заголовки те же), но меняет передачу:

- **Бинарные фреймы** вместо текста.
- **Мультиплексирование**: много параллельных запросов (потоков, streams) по одному TCP-соединению, фреймы разных потоков перемешиваются.
- **Сжатие заголовков HPACK**: повторяющиеся заголовки (cookie, user-agent) не гоняются каждый раз целиком.

Остаётся проблема на уровне TCP: если потерялся один пакет, ждут все потоки. **HTTP/3** переезжает на QUIC поверх UDP, где потеря пакета тормозит только свой поток, а рукопожатие транспорта и TLS совмещено.

Для Go-разработчика это почти прозрачно: `net/http` сам включает HTTP/2 для TLS-серверов и клиентов, твои хендлеры не меняются. С Go 1.24 у `http.Server` и `http.Transport` есть поле `Protocols`, которым можно, например, разрешить HTTP/2 без TLS внутри доверенной сети. HTTP/3 в стандартной библиотеке нет, для него берут сторонние пакеты.

## Методы: семантика, безопасность, идемпотентность

Метод говорит серверу, **что** клиент хочет сделать с ресурсом. Два свойства из RFC 9110 спрашивают на каждом собесе:

- **Безопасный** (safe) метод семантически только читает: клиент не просит ничего менять. Сервер может при этом писать логи и метрики, но клиент за это не «отвечает». Безопасные: `GET`, `HEAD`, `OPTIONS`, `TRACE`.
- **Идемпотентный** метод: повтор того же запроса оставляет сервер в том же состоянии, что и один запрос. Все безопасные плюс `PUT` и `DELETE`.

| Метод | Зачем | Безопасный | Идемпотентный | Тело запроса |
|---|---|---|---|---|
| `GET` | получить ресурс | да | да | не используется |
| `HEAD` | как GET, но без тела ответа | да | да | нет |
| `OPTIONS` | что можно с ресурсом (в т.ч. CORS preflight) | да | да | редко |
| `POST` | создать, запустить действие | нет | нет | да |
| `PUT` | заменить ресурс целиком | нет | да | да |
| `PATCH` | изменить часть ресурса | нет | нет | да |
| `DELETE` | удалить | нет | да | обычно нет |

Почему `PUT` идемпотентен: «положи вот этот документ по адресу `/users/42`». Сделай это пять раз, результат тот же. Почему `POST` нет: «создай заказ». Пять раз значит пять заказов. `DELETE /users/42` дважды: первый удалит, второй вернёт 404, но **состояние** сервера одинаковое (пользователя нет), поэтому идемпотентен. Идемпотентность про состояние, а не про одинаковый ответ.

`PATCH` в общем случае не идемпотентен: `{"op":"increment","field":"balance"}` при повторе прибавит ещё раз. Конкретный PATCH «выставь имя Иван» идемпотентен по факту, но клиент без договорённости этого знать не может.

Зачем это бэкендеру на практике:

- **Ретраи.** Сеть оборвалась после отправки запроса. Дошёл он или нет? Для идемпотентного метода ответ не важен: повторяем. Для `POST` повтор может создать дубль. Отсюда заголовок `Idempotency-Key`: клиент генерирует ключ, сервер запоминает результат по ключу и на повтор отдаёт тот же ответ, не выполняя действие второй раз. Так делают платёжные API.
- **Кеши и прокси** вправе повторить или закешировать безопасный запрос. Если твой `GET /logout` разлогинивает пользователя, то браузер, предзагрузивший ссылку, разлогинит его без клика.

```go
resp, _ := http.Head(srv.URL) // сервер на любой запрос пишет "привет"
body, _ := io.ReadAll(resp.Body)
resp.Body.Close()
fmt.Println(resp.StatusCode, resp.ContentLength, len(body))
```

<Predict :options="['200 0 0', '200 12 12', '200 12 0', '405 0 0']" :correct="2">

`HEAD` должен вернуть те же заголовки, что и `GET`, но без тела. `net/http` сам выкинул тело, хотя хендлер его записал, а `Content-Length: 12` (байты слова «привет») оставил: клиент может узнать размер ресурса, не скачивая его. Ни `405`, ни отдельного хендлера для `HEAD` не понадобилось.

</Predict>

## Статусы

Первая цифра задаёт класс:

- **1xx** информационные (`100 Continue`, `101 Switching Protocols` для WebSocket).
- **2xx** успех.
- **3xx** перенаправление.
- **4xx** ошибка клиента: повторять тот же запрос бессмысленно, надо его исправить.
- **5xx** ошибка сервера: клиент ни при чём, иногда помогает повтор.

Коды, которые надо знать наизусть и уметь различать:

| Код | Когда |
|---|---|
| `200 OK` | успех с телом |
| `201 Created` | создан ресурс; хорошо бы `Location` с его адресом |
| `204 No Content` | успех без тела (DELETE, PUT без ответа) |
| `301` / `308` | переехал навсегда (браузер кеширует); 308 сохраняет метод и тело |
| `302` / `307` | временно в другом месте; 307 сохраняет метод и тело |
| `304 Not Modified` | у клиента свежая копия, тела нет |
| `400 Bad Request` | запрос не разобрать: битый JSON, нет обязательного заголовка |
| `401 Unauthorized` | **не аутентифицирован**: нет токена или он невалиден |
| `403 Forbidden` | аутентифицирован, но **нет прав** |
| `404 Not Found` | ресурса нет (или не скажем, что он есть) |
| `405 Method Not Allowed` | путь есть, метод не тот; обязателен заголовок `Allow` |
| `409 Conflict` | конфликт с состоянием: email уже занят, версия устарела |
| `413 Content Too Large` | тело больше лимита |
| `415 Unsupported Media Type` | не тот `Content-Type` |
| `422 Unprocessable Content` | JSON валиден, но данные не проходят проверку |
| `429 Too Many Requests` | превышен лимит; часто с `Retry-After` |
| `500 Internal Server Error` | баг или непредвиденная ошибка сервера |
| `502 Bad Gateway` | прокси получил плохой ответ от бэкенда |
| `503 Service Unavailable` | перегружен или на обслуживании; часто с `Retry-After` |
| `504 Gateway Timeout` | прокси не дождался ответа бэкенда |

Названия 413 и 422 в RFC 9110 обновили (раньше Payload Too Large и Unprocessable Entity), в коде Go константы остались старыми: `http.StatusRequestEntityTooLarge`, `http.StatusUnprocessableEntity`.

::: trap 200 с ошибкой внутри
Самая частая ошибка API, особенно у бывших фронтендеров: всегда отвечать 200, а успех или ошибку класть в тело.

```json
// плохо: HTTP 200
{"success": false, "error": "user not found"}
```

Мониторинг считает такие ответы успешными, прокси и клиентские библиотеки не знают, что надо повторить, кеш может закешировать ошибку. Хорошо: **правильный статус плюс тело ошибки в едином формате**.

```json
// хорошо: HTTP 404
{"error": {"code": "not_found", "message": "user not found"}}
```

Обратная ошибка: 500 на любую проблему, включая битый JSON от клиента. 500 означает «у нас баг», будит дежурного и запускает ретраи, а клиенту надо было просто исправить запрос (400).
:::

## Заголовки, которые нужны каждый день

- **`Content-Type`**: формат тела. `application/json` для API. Клиент обязан ставить его на запросах с телом, сервер на ответах.
- **`Accept`**: какие форматы клиент примет в ответ.
- **`Authorization`**: учётные данные, обычно `Bearer <токен>`.
- **`Location`**: куда смотреть (после 201 и в редиректах).
- **`User-Agent`**, **`X-Request-Id`**: кто пришёл и сквозной ID для логов.
- **`Retry-After`**: через сколько секунд (или когда) повторить, для 429 и 503.
- **`X-Forwarded-For`** / **`Forwarded`**: исходный IP клиента, если сервис за прокси. Доверять можно только тому, что добавил **твой** прокси: клиент может прислать любой `X-Forwarded-For` сам.

## Кеширование

Кеш снимает нагрузку и ускоряет ответы, но кешировать неправильно хуже, чем не кешировать: пользователь увидит чужие или устаревшие данные. Кеши бывают в браузере, на CDN, на прокси. Управляет ими сервер заголовками ответа.

**`Cache-Control`** задаёт политику:

- `max-age=3600`: ответ свежий час, можно отдавать без запроса к серверу.
- `no-cache`: хранить можно, но перед каждым использованием **сверяться** с сервером. Название обманчивое: это не «не кешировать».
- `no-store`: не сохранять вообще. Для персональных и секретных данных.
- `private`: только браузер пользователя, не общие кеши (CDN). `public`: можно всем.

**Валидация через ETag.** Сервер отдаёт ресурс с меткой версии:

```text
HTTP/1.1 200 OK
ETag: "v42"
Cache-Control: no-cache
```

В следующий раз клиент спрашивает условно:

```text
GET /api/catalog HTTP/1.1
If-None-Match: "v42"
```

Если версия не изменилась, сервер отвечает `304 Not Modified` **без тела**: клиент берёт копию из кеша. Экономится трафик и, если сервер умеет дёшево узнать версию, работа сервера. ETag бывает **сильным** (`"v42"`, байт-в-байт тот же ответ) и **слабым** (`W/"v42"`, семантически тот же). Для `If-None-Match` используется слабое сравнение: префикс `W/` отбрасывается. Аналог по времени: `Last-Modified` и `If-Modified-Since`.

В Go `http.ServeContent` и `http.FileServer` умеют отвечать 304 по `If-None-Match` и `If-Modified-Since` сами. В JSON API это делаешь руками, и в домашке ты напишешь проверку `If-None-Match`.

**`Vary`** говорит кешу, от каких заголовков запроса зависит ответ. Если ответ разный для разных `Accept-Encoding` или `Origin`, а `Vary` не выставлен, кеш отдаст gzip-ответ клиенту без поддержки gzip или CORS-ответ для одного сайта другому.

::: trap Кеширование персональных ответов
```text
// плохо: ответ /api/me с данными пользователя
Cache-Control: public, max-age=300
```

CDN закеширует профиль первого пришедшего и пять минут будет отдавать его всем. Для персонального: `Cache-Control: private, no-cache` (или `no-store`, если данные чувствительные).
:::

## CORS со стороны сервера

Фронтендером ты видел CORS как ошибку в консоли. Теперь главное, что надо понять: **CORS не защищает сервер**. Его исполняет браузер, чтобы защитить **пользователя**: скрипт с `evil.example` не должен читать ответы `bank.example`, которые браузер получает с куками пользователя.

Механизм:

1. Скрипт со страницы `https://app.example.com` делает `fetch("https://api.example.com/items")`. Это **cross-origin** запрос: origin это схема, хост и порт целиком, и они отличаются.
2. Браузер добавляет заголовок `Origin: https://app.example.com`.
3. Сервер отвечает как обычно и, если доверяет этому origin, добавляет `Access-Control-Allow-Origin: https://app.example.com`.
4. Браузер **уже получил** ответ, но отдаст его скрипту, только если `Access-Control-Allow-Origin` совпал. Иначе ошибка в консоли.

Отсюда следствие: запрос до сервера **дошёл и выполнился**. Если это был «простой» `POST` формы, деньги уже списались, просто скрипт не увидел ответ. От таких атак (CSRF) защищают другие механизмы: SameSite-куки, токены, проверка `Origin`. С Go 1.25 для этого есть `http.CrossOriginProtection`, который отклоняет небезопасные кросс-доменные запросы браузера по заголовкам Fetch metadata.

**Preflight.** Для «непростых» запросов браузер сначала спрашивает разрешения отдельным `OPTIONS`:

```text
OPTIONS /api/items HTTP/1.1
Origin: https://app.example.com
Access-Control-Request-Method: DELETE
Access-Control-Request-Headers: authorization, content-type
```

Непростой это, например, метод не `GET`/`HEAD`/`POST`, заголовок `Authorization`, или `Content-Type: application/json` (простыми считаются только `text/plain`, `multipart/form-data` и `application/x-www-form-urlencoded`). То есть почти любой вызов JSON API из браузера идёт с preflight. Сервер отвечает:

```text
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST, PUT, PATCH, DELETE
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Max-Age: 600
Vary: Origin
```

`Max-Age` разрешает браузеру запомнить ответ на preflight и не спрашивать 10 минут.

::: trap Звёздочка и куки
```go
// плохо: отражать любой Origin и разрешать куки
w.Header().Set("Access-Control-Allow-Origin", r.Header.Get("Origin"))
w.Header().Set("Access-Control-Allow-Credentials", "true")
```

Это эквивалент «любой сайт в интернете может читать ответы с куками пользователя». Звёздочку `*` вместе с `Allow-Credentials: true` браузер не примет, поэтому люди «чинят» ошибку отражением `Origin`, а это дыра.

```go
// хорошо: белый список и Vary
if slices.Contains(allowed, origin) {
	w.Header().Set("Access-Control-Allow-Origin", origin)
}
w.Header().Add("Vary", "Origin")
```
:::

## REST и его типичные ошибки

REST это стиль, а не протокол: **ресурсы** с адресами (существительные), над которыми выполняются стандартные **методы**. Для джуна достаточно практических правил:

```text
GET    /api/users            список (фильтры и пагинация в query: ?limit=20&cursor=...)
POST   /api/users            создать → 201 + Location: /api/users/42
GET    /api/users/42         один ресурс → 200 или 404
PUT    /api/users/42         заменить целиком
PATCH  /api/users/42         изменить часть
DELETE /api/users/42         удалить → 204
GET    /api/users/42/orders  вложенный ресурс
```

Типичные ошибки:

- **Глаголы в URL**: `POST /api/createUser`, `GET /api/getUser?id=42`. Действие уже выражено методом.
- **`GET`, который меняет состояние**: `GET /api/users/42/delete`. Его выполнит краулер, префетчер или прокси при ретрае.
- **200 на всё** и ошибка в теле (см. выше).
- **Неверные коды**: 500 на валидацию, 404 на «нет прав» без осознанного решения, 400 вместо 409 на конфликт.
- **Разный формат ошибок** в разных ручках: клиенту приходится писать парсер под каждую.
- **Неидемпотентные ретраи**: клиент повторяет `POST` при таймауте и создаёт дубли.
- **Отдача внутренних полей**: хеш пароля, внутренние ID, стектрейсы в 500.
- **Отсутствие версии** у публичного API, когда ломающие изменения неизбежны (`/api/v1/...` или заголовок).

Действия, которые плохо ложатся на CRUD (`отправить письмо`, `отменить заказ`), моделируют как ресурс или под-ресурс: `POST /api/orders/42/cancellation`. Спорить о «чистоте REST» на собесе не нужно, нужно показать, что ты знаешь последствия.

<details><summary>Что происходит, когда в браузере вводишь URL и жмёшь Enter?</summary>

Разбор URL; DNS-резолвинг имени (кеш браузера, ОС, резолвер, при необходимости корневые и авторитетные серверы); TCP-рукопожатие SYN, SYN-ACK, ACK; для HTTPS TLS-рукопожатие с проверкой сертификата (в TLS 1.3 один RTT); отправка HTTP-запроса; сервер (часто через балансировщик) обрабатывает и отвечает; браузер парсит HTML, догружает ресурсы по тем же или новым соединениям. Соединение остаётся открытым (keep-alive) для следующих запросов. На собесе ценят, если назовёшь, сколько RTT стоит каждый шаг и зачем переиспользуют соединения.

</details>
<details><summary>Чем безопасный метод отличается от идемпотентного? Приведи примеры.</summary>

Безопасный семантически только читает (`GET`, `HEAD`, `OPTIONS`, `TRACE`). Идемпотентный при повторе оставляет сервер в том же состоянии, что и одиночный вызов: все безопасные плюс `PUT` и `DELETE`. Все безопасные идемпотентны, обратное неверно: `DELETE` меняет состояние, но повтор ничего не добавляет. `POST` и в общем случае `PATCH` ни то, ни другое. Практический смысл: идемпотентные запросы можно автоматически повторять при сетевых сбоях, а для POST нужен `Idempotency-Key`.

</details>
<details><summary>DELETE второй раз возвращает 404. Он всё ещё идемпотентен?</summary>

Да. Идемпотентность определена через состояние сервера, а не через ответ. После первого и после второго вызова ресурса нет, состояние одинаковое. Ответы могут отличаться (204, потом 404), это допустимо.

</details>
<details><summary>Чем 401 отличается от 403? А 400 от 422?</summary>

401: сервер не знает, кто ты (нет или невалиден токен); по стандарту ответ содержит `WWW-Authenticate`. 403: знает, кто ты, но прав нет; повторная аутентификация не поможет. 400: запрос синтаксически неверен, его не удалось разобрать (битый JSON, не тот тип поля). 422: разобрать удалось, но данные не проходят бизнес-валидацию (email без @, возраст -5). Многие API отвечают 400 на всё, это тоже допустимо, главное, единообразно и задокументировано.

</details>
<details><summary>Что такое preflight-запрос и когда браузер его делает?</summary>

`OPTIONS`-запрос с `Origin`, `Access-Control-Request-Method` и иногда `Access-Control-Request-Headers`, которым браузер спрашивает разрешения перед «непростым» кросс-доменным запросом. Непростой: метод кроме GET/HEAD/POST, нестандартные заголовки (например, `Authorization`), `Content-Type` кроме трёх «формовых» (а `application/json` в их число не входит). Сервер отвечает разрешёнными origin, методами, заголовками и `Max-Age`. Только после этого браузер шлёт настоящий запрос.

</details>
<details><summary>Защищает ли CORS сервер от запросов с чужих сайтов?</summary>

Нет. CORS исполняет браузер, и он ограничивает **чтение ответа** скриптом, а не отправку запроса. curl, сервер-сервер, мобильное приложение CORS не применяют вовсе. Простые запросы (например, POST формы) браузер отправит, и сервер их выполнит. От CSRF защищают SameSite-куки, CSRF-токены, проверка `Origin`/`Sec-Fetch-Site` (в Go 1.25+ `http.CrossOriginProtection`), а от неавторизованного доступа аутентификация.

</details>
<details><summary>Как работает ETag и зачем 304?</summary>

Сервер отдаёт ресурс с `ETag` (метка версии). Клиент кеширует и при следующем запросе шлёт `If-None-Match` с этой меткой. Если версия та же, сервер отвечает `304 Not Modified` без тела, клиент использует кеш. Экономится трафик, а если версию можно узнать без построения ответа, ещё и работа сервера. Слабые теги (`W/"..."`) означают семантическую эквивалентность, для `If-None-Match` сравнение слабое. Вместе с этим нужен корректный `Cache-Control` (`no-cache` значит «сверяйся перед использованием»).

</details>
<details><summary>Чем HTTP/2 отличается от HTTP/1.1?</summary>

Семантика та же (методы, статусы, заголовки), меняется транспорт: бинарные фреймы вместо текста, мультиплексирование многих запросов по одному TCP-соединению вместо «один запрос за раз на соединение», сжатие заголовков HPACK, приоритизация потоков. Head-of-line blocking на уровне HTTP уходит, но остаётся на уровне TCP: потеря пакета тормозит все потоки. Это решает HTTP/3 на QUIC поверх UDP. В Go HTTP/2 включается автоматически для TLS.

</details>
<details><summary>Почему GET не должен менять состояние?</summary>

Потому что GET безопасный, и вся инфраструктура этим пользуется: браузеры делают префетч ссылок, краулеры обходят всё подряд, прокси и клиенты повторяют GET при сбоях, кеши отдают ответ без похода на сервер. `GET /items/42/delete` удалит данные при обходе поисковиком или не удалит, потому что ответ взят из кеша. Действия делают через POST/PUT/PATCH/DELETE.

</details>
:::
