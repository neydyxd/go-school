# Пакет testing и табличные тесты

В Go тесты не нужно «подключать»: фреймворк лежит в стандартной библиотеке (пакет `testing`), запускалка встроена в команду `go test`, а соглашения настолько простые, что их можно выучить за вечер. Поэтому на Go-собесе никто не спрашивает «каким фреймворком вы тестируете». Спрашивают другое: чем `t.Error` отличается от `t.Fatal`, зачем `t.Helper`, что сломается, если поставить `t.Parallel` в подтест, и как ты построишь табличный тест для функции с пятью граничными случаями.

В бэкенд-работе тесты это страховка при каждом изменении. Сервис живёт годами, его правят десятки людей, и единственное, что не даёт сломать расчёт скидки при рефакторинге логирования, это зелёный `go test ./...` в CI. Хороший тест к тому же документация: открыл `_test.go` и увидел, как функцию задумывали использовать и какие крайние случаи автор держал в голове.

В этом уроке разберём устройство `go test`, табличные тесты и подтесты, хелперы, параллельность, очистку ресурсов, golden-файлы и коротко testify. А в домашке появится новый формат: ты будешь не только писать функции, но и писать тесты, которые проверяются автоматически.

## Первый тест

Тесты живут рядом с кодом в файлах с суффиксом `_test.go`. Обычная сборка их не видит, `go test` собирает их вместе с пакетом в отдельный тестовый бинарник и запускает.

```go
// grade.go
package grade

// Grade переводит баллы в оценку.
func Grade(score int) string {
	if score < 0 || score > 100 {
		return "ошибка"
	}
	if score >= 90 {
		return "отлично"
	}
	if score >= 60 {
		return "зачёт"
	}
	return "незачёт"
}
```

```go
// grade_test.go
package grade

import "testing"

func TestGrade(t *testing.T) {
	got := Grade(95)
	if got != "отлично" {
		t.Errorf("Grade(95) = %q, want %q", got, "отлично")
	}
}
```

Правила, которые проверяет сам `go test`:

- функция называется `TestXxx`, где после `Test` идёт заглавная буква или ничего;
- единственный параметр `t *testing.T`, результатов нет;
- файл заканчивается на `_test.go`.

В Go нет `assert`-конструкций в языке: проверка это обычный `if`, а об ошибке сообщают методы `t`. Сообщение принято строить по шаблону `Func(args) = got, want want`. Через полгода, когда тест упадёт в CI, такая строка сразу скажет, что вызвали, что получили и что ждали.

```bash
go test ./...                 # все пакеты модуля
go test -v ./grade/           # подробно: каждый тест и его вывод
go test -run TestGrade ./...  # только тесты, чьё имя подходит под регулярку
go test -count=1 ./...        # без кеша результатов
```

Если пакет не менялся, `go test` покажет `ok ... (cached)` и не будет запускать тесты заново. Кеш учитывает исходники, флаги, переменные окружения и файлы, которые тест открывал. Принудительно перезапустить: `-count=1`.

### Error или Fatal

У `t` две группы методов для сообщения о провале:

| Метод | Что делает |
|---|---|
| `t.Error`, `t.Errorf` | помечает тест упавшим и **продолжает** выполнение |
| `t.Fatal`, `t.Fatalf` | помечает упавшим и **останавливает** текущий тест (через `runtime.Goexit`) |
| `t.Log`, `t.Logf` | просто пишет в лог теста; видно с `-v` или если тест упал |
| `t.Skip` | пропускает тест (например, «нет Docker») |

Правило выбора простое: если после провала проверки дальше идти бессмысленно (не открылся файл, функция вернула ошибку, а ты собираешься читать результат), то `Fatal`. Если проверки независимы (сверяешь пять полей структуры), то `Error`: увидишь все расхождения за один прогон.

```go
func TestErrorfFatal(t *testing.T) {
	t.Errorf("первая")
	fmt.Println("после Errorf")
	t.Fatalf("вторая")
	fmt.Println("после Fatalf")
}
```

<Predict :options="['«после Errorf» и «после Fatalf», в отчёте две ошибки', '«после Errorf», в отчёте две ошибки', 'ничего не напечатает, в отчёте одна ошибка «первая»', '«после Errorf», в отчёте одна ошибка «вторая»']" :correct="1">

`Errorf` только помечает тест упавшим, поэтому строка «после Errorf» печатается. `Fatalf` записывает вторую ошибку и останавливает горутину теста, до «после Fatalf» дело не доходит. В отчёте обе строки: `a_test.go:N: первая` и `a_test.go:M: вторая`.

</Predict>

## Табличные тесты

Один `if` на одну проверку быстро превращается в простыню копипасты. Идиома Go: описать кейсы данными, а проверку написать один раз.

```go
func TestGrade(t *testing.T) {
	tests := []struct {
		name  string
		score int
		want  string
	}{
		{"отлично", 95, "отлично"},
		{"ровно 90", 90, "отлично"},
		{"зачёт", 70, "зачёт"},
		{"ровно 60", 60, "зачёт"},
		{"незачёт", 59, "незачёт"},
		{"отрицательные баллы", -1, "ошибка"},
		{"больше ста", 101, "ошибка"},
	}
	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			if got := Grade(tt.score); got != tt.want {
				t.Errorf("Grade(%d) = %q, want %q", tt.score, got, tt.want)
			}
		})
	}
}
```

Почему это лучше пачки отдельных функций:

- **новый кейс это одна строка**, а не копия теста. Нашёл баг: добавил строку, увидел красное, починил;
- **кейсы видны целиком**: глазами легко заметить, что граница 90 есть, а 89 нет;
- **проверка одна**, и улучшать сообщение об ошибке надо в одном месте.

Как придумывать кейсы. Новички пишут «обычный случай» и успокаиваются. Тестировщики думают **классами эквивалентности** и **граничными значениями**: разбей вход на группы, внутри которых функция ведёт себя одинаково (меньше 0, 0-59, 60-89, 90-100, больше 100), и возьми по представителю из каждой группы плюс значения ровно на границах (59, 60, 89, 90, 100, 101). Ошибка на единицу (`>` вместо `>=`) живёт именно на границах. Отдельный чеклист для строк и слайсов: пусто, nil, один элемент, юникод, очень длинное.

### Подтесты и t.Run

`t.Run(name, func(t *testing.T))` запускает подтест со своим `t`. Это даёт три вещи:

1. **Имя в отчёте**: `--- FAIL: TestGrade/ровно_60`. Пробелы в именах заменяются на `_`.
2. **Изоляцию провалов**: `t.Fatal` внутри подтеста останавливает только этот подтест, остальные кейсы выполнятся.
3. **Точечный запуск**: `-run` понимает путь через слеш.

```bash
go test -run 'TestGrade/ровно_60' -v ./grade/
go test -run 'TestGrade/ровно' -v ./grade/   # оба кейса с «ровно» в имени
```

Каждый уровень `-run` это отдельная регулярка, части разделяются `/`. Подтесты можно вкладывать (группа, внутри кейсы), но больше двух уровней читать тяжело.

::: hood Как go test находит и запускает тесты
1. `go test` собирает пакет вместе с его `_test.go` файлами и генерирует маленький `main`, в котором перечислены все найденные `TestXxx`, `BenchmarkXxx`, `FuzzXxx` и `ExampleXxx`.
2. Перед запуском прогоняется облегчённый `go vet` (анализаторы `atomic`, `bools`, `buildtag`, `directive`, `errorsas`, `ifaceassert`, `nilfunc`, `printf`, `stdversion`, `stringintconv`, `tests`). Если он что-то нашёл, тесты не запускаются. Выключить: `-vet=off`.
3. Бинарник запускается; каждый тест выполняется в своей горутине. `t.Fatal` вызывает `runtime.Goexit`: горутина теста завершается, её `defer` отрабатывают, а запускалка видит, что тест закончился с провалом.
4. Паника в тесте роняет **весь** тестовый бинарник: остальные тесты пакета не выполнятся. Поэтому на заготовках домашки ты видишь одну панику `TODO`, а не все красные тесты сразу.
:::

## t.Helper: куда указывает ошибка

Проверки быстро обрастают хелперами вроде `assertEqual`. Проблема: при провале Go печатает файл и строку того места, где вызван `t.Errorf`, а это строка внутри хелпера. Все падения указывают в одно место, и непонятно, какая проверка сломалась.

```go
func checkNoHelper(t *testing.T, got, want int) {
	if got != want {
		t.Errorf("got %d, want %d", got, want) // строка 7
	}
}

func checkHelper(t *testing.T, got, want int) {
	t.Helper()
	if got != want {
		t.Errorf("got %d, want %d", got, want)
	}
}

func TestSum(t *testing.T) {
	checkNoHelper(t, 1+1, 3) // строка 19
	checkHelper(t, 1+1, 3)   // строка 20
}
```

```text
--- FAIL: TestSum (0.00s)
    h_test.go:7: got 2, want 3
    h_test.go:20: got 2, want 3
```

`t.Helper()` помечает функцию как вспомогательную, и при печати места ошибки рантайм пропускает её кадр стека, показывая строку вызова в тесте. Правило: **каждый тестовый хелпер начинается с `t.Helper()`**.

Хелперы принято принимать как `testing.TB`, интерфейс, общий для `*testing.T`, `*testing.B` и `*testing.F`. Тогда один хелпер работает и в тестах, и в бенчмарках.

## Очистка: t.Cleanup и t.TempDir

Тесту часто нужен ресурс: временный файл, тестовый сервер, подключение к базе. Его надо закрыть, даже если тест упал. В обычном коде для этого `defer`, но у `defer` в тестах есть ограничение: он привязан к функции, а хелпер, который создал ресурс, заканчивается раньше теста.

`t.Cleanup(f)` регистрирует функцию, которая выполнится **после завершения теста и всех его подтестов**. Хелпер может сам за собой прибрать:

```go
func newTestServer(t testing.TB) *Server {
	t.Helper()
	s := StartServer()
	t.Cleanup(s.Stop) // вызывающему не нужно помнить про Stop
	return s
}
```

Несколько `Cleanup` выполняются в обратном порядке, как `defer`:

```go
func TestCleanupLIFO(t *testing.T) {
	t.Cleanup(func() { fmt.Println("cleanup 1") })
	t.Cleanup(func() { fmt.Println("cleanup 2") })
	defer fmt.Println("defer")
	fmt.Println("тело")
}
```

<Predict :options="['тело, cleanup 1, cleanup 2, defer', 'тело, defer, cleanup 2, cleanup 1', 'тело, defer, cleanup 1, cleanup 2', 'тело, cleanup 2, cleanup 1, defer']" :correct="1">

Сначала заканчивается функция теста, и срабатывают её `defer`. Потом запускалка вызывает зарегистрированные `Cleanup` в порядке LIFO: последний зарегистрированный первым.

</Predict>

Готовые помощники на базе `Cleanup`:

- `t.TempDir()` создаёт уникальный временный каталог и удаляет его после теста. Каждый вызов даёт новый каталог.
- `t.Setenv("KEY", "v")` ставит переменную окружения и возвращает старое значение после теста.
- `t.Chdir(dir)` (с Go 1.24) меняет рабочий каталог на время теста.
- `t.Context()` (с Go 1.24) возвращает контекст, который отменяется после теста, но **до** запуска `Cleanup`-функций. Удобно передавать в код, который принимает `context.Context`: про контексты подробно будет в модуле о конкурентности.

## Параллельные тесты: t.Parallel

По умолчанию тесты одного пакета выполняются последовательно (пакеты при этом гоняются параллельно, отдельными процессами). Вызов `t.Parallel()` говорит: этот тест можно запускать одновременно с другими параллельными. Сколько одновременно, решает флаг `-parallel` (по умолчанию `GOMAXPROCS`).

Механика, которую спрашивают на собесах: `t.Parallel()` **ставит тест на паузу**, пока не закончит выполнение функция родителя (для верхнеуровневых тестов: пока не пройдут все последовательные тесты). Только потом параллельные подтесты продолжаются вместе.

```go
func TestOrder(t *testing.T) {
	defer fmt.Println("defer родителя")
	t.Cleanup(func() { fmt.Println("cleanup родителя") })
	for _, name := range []string{"A", "B"} {
		t.Run(name, func(t *testing.T) {
			t.Parallel()
			fmt.Println("подтест", name)
		})
	}
	fmt.Println("конец функции родителя")
}
```

<Predict :options="['подтесты → конец функции → defer → cleanup', 'конец функции → defer → подтесты → cleanup', 'конец функции → подтесты → defer → cleanup', 'подтесты → конец функции → cleanup → defer']" :correct="1">

С `-v` видно `=== PAUSE TestOrder/A` и `=== PAUSE TestOrder/B`: подтесты стартовали и сразу встали на паузу. Функция родителя доходит до конца и отрабатывает свой `defer`. Затем `=== CONT`: подтесты выполняются. `Cleanup` родителя ждёт завершения всех подтестов, поэтому он последний. Вывод: если родитель готовит ресурс для параллельных подтестов, закрывать его надо в `t.Cleanup`, а не в `defer`. С `defer` ресурс закроется раньше, чем подтесты начнут с ним работать.

</Predict>

::: trap Переменная цикла и t.Parallel в старом коде
До Go 1.22 переменная цикла была одна на весь цикл. Параллельный подтест запускался после окончания цикла и видел последнее значение: все подтесты проверяли последний кейс, а тест был зелёным. Поэтому в старом коде и статьях встречается заклинание `tt := tt`.

```go
// go.mod: go 1.21
for _, name := range []string{"A", "B"} {
	t.Run(name, func(t *testing.T) {
		t.Parallel()
		fmt.Println("подтест", name) // напечатает «подтест B» дважды
	})
}
```

С Go 1.22 переменная создаётся на каждую итерацию, и копия не нужна. Но поведение зависит от директивы `go` в `go.mod` модуля, а не от версии компилятора: модуль с `go 1.21` собирается по старым правилам даже новым Go. На старых версиях `go vet` предупреждает: `loop variable name captured by func literal`.

```go
// хорошо: go.mod с go 1.22 или новее, копия не нужна
for _, tt := range tests {
	t.Run(tt.name, func(t *testing.T) {
		t.Parallel()
		check(t, tt)
	})
}
```
:::

Когда `t.Parallel` уместен: тесты, которые ждут (сеть, `time.Sleep`, внешние процессы), и большие таблицы медленных кейсов. Когда нельзя: тест меняет глобальное состояние (переменную пакета, `os.Setenv`, текущий каталог). `t.Setenv` и `t.Chdir` сами паникуют, если вызваны в параллельном тесте: это защита от гонок.

## Golden-файлы

Некоторые функции выдают большой текст: отчёт, HTML, JSON-ответ, SQL-запрос. Держать ожидаемый результат строкой в тесте неудобно: он огромный, а любое изменение формата требует руками переписать десятки строк. Решение: хранить эталон в файле `testdata/<имя>.golden` и сравнивать с ним.

```go
var update = flag.Bool("update", false, "перезаписать golden-файлы")

func TestRenderGolden(t *testing.T) {
	got := Render([]string{"Гофер", "Пайк"})
	path := filepath.Join("testdata", t.Name()+".golden")
	if *update {
		if err := os.WriteFile(path, []byte(got), 0o644); err != nil {
			t.Fatal(err)
		}
	}
	want, err := os.ReadFile(path)
	if err != nil {
		t.Fatalf("нет golden-файла, запусти с -update: %v", err)
	}
	if got != string(want) {
		t.Errorf("Render() не совпал с %s\ngot:\n%s\nwant:\n%s", path, got, want)
	}
}
```

Рабочий цикл: поменял формат, запустил `go test -update ./report/`, **посмотрел `git diff` по golden-файлу глазами**, закоммитил вместе с кодом. Каталог `testdata` инструменты Go игнорируют как пакет, поэтому туда можно класть что угодно. Тест запускается с рабочим каталогом, равным каталогу пакета, так что относительный путь `testdata/...` работает.

::: trap -update превращает тест в фотоаппарат
Golden-тест проверяет только то, что вывод не изменился. Если запустить `-update` на сломанном коде и не посмотреть дифф, тест «запомнит» баг и станет зелёным. Golden-файл это часть кода: его изменения читают на ревью так же внимательно, как изменения логики.

Ещё одна мелочь: флаг `-update` объявлен только в пакете с golden-тестом. Команда `go test ./... -update` упадёт на остальных пакетах с `flag provided but not defined: -update`. Запускай с флагом конкретный пакет.
:::

## testify коротко

Самая популярная сторонняя библиотека для тестов. Сравни:

```go
import (
	"github.com/stretchr/testify/assert"
	"github.com/stretchr/testify/require"
)

func TestTestify(t *testing.T) {
	got := []int{1, 2}
	require.Len(t, got, 2)              // при провале t.FailNow: дальше не идём
	assert.Equal(t, []int{1, 3}, got)   // при провале t.Errorf: идём дальше
}
```

```text
Error:      	Not equal:
            	expected: []int{1, 3}
            	actual  : []int{1, 2}
            	Diff:
            	...
```

- `assert.*` это аналог `t.Errorf`, `require.*` аналог `t.Fatalf`. Путают постоянно, на собесе любят спросить.
- Порядок аргументов: **сначала expected, потом actual**. Перепутаешь, и сообщение об ошибке будет врать.
- Плюс: красивый дифф структур и слайсов, меньше бойлерплейта. Минус: внешняя зависимость и свой мини-язык из сотни функций.

Многие команды (и сама стандартная библиотека Go) пишут тесты без testify: `if` + `t.Errorf` + `cmp.Diff` из `github.com/google/go-cmp` для сравнения структур. Оба стиля нормальные. В этом курсе домашка написана на чистом `testing`, чтобы ты знал базу; на работе используй то, что принято в проекте.

## Внутренний и внешний тестовый пакет

Тестовый файл может объявить тот же пакет (`package grade`) или пакет с суффиксом `_test` (`package grade_test`). Во втором случае это отдельный пакет, который импортирует твой как обычный пользователь и видит только экспортированное.

- `package grade`: тестируешь внутренности, удобно для юнит-тестов неэкспортированных функций.
- `package grade_test`: тест проверяет публичный API глазами пользователя. Так пишут `Example`-функции и тесты, которые иначе создали бы цикл импортов.

::: trap Тест, который проверяет сам себя
Частая ошибка в табличных тестах: ожидаемое значение вычисляется тем же кодом, что проверяется.

```go
// плохо: want считается той же функцией, тест не может упасть
{"зачёт", 70, Grade(70)},
```

```go
// хорошо: ожидание записано руками, независимо от реализации
{"зачёт", 70, "зачёт"},
```

Тот же грех в мягкой форме: скопировать текущий вывод функции в `want`, не проверив его головой. Тест фиксирует поведение, а не правильность. Ожидаемое значение должно приходить из спецификации, а не из кода.
:::

## Как устроена домашка, где ты пишешь тесты

До сих пор домашка выглядела так: тест готов, ты пишешь функцию. В этом модуле появляется обратная задача: функция готова, ты пишешь тесты. Как проверить автоматически, что тесты хорошие? Через **мутационное тестирование**.

**Мутант** это копия функции с маленькой намеренной ошибкой: `>=` заменили на `>`, забыли перевести в нижний регистр, не проверили пустую строку. Хороший набор тестов **убивает** мутанта: хотя бы один кейс на нём падает. Если мутант выжил, значит в тестах есть дыра, через которую такой баг прошёл бы в прод.

Формат заданий «охота на мутантов»:

1. В файле задания лежит готовая правильная функция (например, `Slug`) и пустая таблица кейсов `slugCases`.
2. В `_test.go` лежат мутанты и проверка, которую ты не меняешь. Она делает две вещи: гоняет твою таблицу против настоящей функции (кейсы должны быть верными) и против каждого мутанта (каждый должен упасть хотя бы на одном кейсе).
3. Ты заполняешь таблицу. Тест печатает имена выживших мутантов, например `--- FAIL: TestSlugMutants/теряет_цифры`, это подсказка, какого класса входов не хватает.

Пустая таблица красная (все мутанты живы), полная таблица зелёная. Подглядывать в код мутантов можно, но полезнее сначала придумать кейсы по классам эквивалентности и границам, а потом сверить. На работе мутантов тебе никто не подготовит.

Второй формат, **проверка-функция**, появится в следующих уроках: ты пишешь функцию вида `CheckX(f) error`, которая сама гоняет свои проверки против переданной реализации. Тест подаёт в неё правильную реализацию (ошибки быть не должно) и мутантов (ошибка обязательна). Это тот же тест, только упакованный в функцию, чтобы его можно было запустить против разных реализаций.

## Что выведет программа?

```go
// go.mod: go 1.21
func TestOrder(t *testing.T) {
	for _, name := range []string{"A", "B"} {
		t.Run(name, func(t *testing.T) {
			t.Parallel()
			fmt.Println("подтест", name)
		})
	}
}
```

<Predict :options="['подтест A, подтест B', 'подтест B, подтест B', 'подтест A, подтест A', 'ошибка компиляции']" :correct="1">

В модуле с `go 1.21` действует старая семантика: одна переменная `name` на весь цикл. Параллельные подтесты стоят на паузе, пока цикл не закончится, а к этому моменту `name == "B"`. С директивой `go 1.22` и новее каждая итерация получает свою переменную, и напечатаются A и B.

</Predict>

```go
func TestCtx(t *testing.T) {
	ctx := t.Context()
	t.Cleanup(func() { fmt.Println("в cleanup:", ctx.Err()) })
	fmt.Println("в тесте:", ctx.Err())
}
```

<Predict :options="['в тесте: <nil>, в cleanup: <nil>', 'в тесте: <nil>, в cleanup: context canceled', 'в тесте: context canceled, в cleanup: context canceled', 'паника: Context нельзя вызывать в тесте']" :correct="1">

Контекст из `t.Context()` (Go 1.24+) отменяется, когда тест закончился, но **до** вызова `Cleanup`-функций. Так очистка может дождаться, пока код, слушающий этот контекст, корректно остановится.

</Predict>

<details><summary>Чем t.Error отличается от t.Fatal?</summary>

Оба помечают тест упавшим. `Error` продолжает выполнение теста, `Fatal` останавливает его через `runtime.Goexit` (отложенные функции при этом выполняются). `Fatal` нужен, когда дальнейшие проверки бессмысленны, например не удалось открыть файл или функция вернула ошибку. Важная деталь: `Fatal` нельзя вызывать из горутины, которую запустил тест, только из горутины самого теста; из другой горутины используют `Error` и выходят из неё сами.

</details>
<details><summary>Что такое табличный тест и зачем он нужен?</summary>

Кейсы описываются данными (слайс структур с именем, входом и ожиданием), а проверка пишется один раз в цикле, обычно с `t.Run` на каждый кейс. Плюсы: новый кейс добавляется одной строкой, все случаи видны вместе (легко заметить пропущенную границу), сообщение об ошибке единообразно, отдельный кейс можно запустить через `-run 'TestX/имя'`.

</details>
<details><summary>Зачем нужен t.Helper?</summary>

Без него ошибка, вызванная в хелпере, указывает на строку внутри хелпера, и все провалы выглядят одинаково. `t.Helper()` помечает функцию вспомогательной, и при печати места ошибки её кадр пропускается: видна строка теста, который вызвал хелпер. Вызывается первой строкой хелпера.

</details>
<details><summary>Как работает t.Parallel и какие с ним бывают ошибки?</summary>

Тест с `t.Parallel()` встаёт на паузу до тех пор, пока не закончится функция родителя, затем выполняется одновременно с другими параллельными тестами того же уровня; ограничение задаёт `-parallel` (по умолчанию `GOMAXPROCS`). Ошибки: (1) закрывать общий ресурс в `defer` родителя, он сработает до подтестов, нужен `t.Cleanup`; (2) захват переменной цикла в модулях с `go` ниже 1.22; (3) параллельные тесты, которые трогают глобальное состояние: переменные пакета, окружение, текущий каталог.

</details>
<details><summary>Чем t.Cleanup лучше defer?</summary>

`Cleanup` привязан к тесту, а не к функции. Хелпер может создать ресурс и сам зарегистрировать его закрытие, вызывающему не нужно ничего помнить. Cleanup выполняется после теста и всех его подтестов, включая параллельные, а `defer` родителя выполнится раньше параллельных подтестов. Порядок выполнения LIFO, как у `defer`. На `Cleanup` построены `t.TempDir`, `t.Setenv`, `t.Chdir`.

</details>
<details><summary>Что такое golden-файлы и в чём их риск?</summary>

Эталонный вывод хранится в `testdata/*.golden`, тест сравнивает с ним результат. Флаг вроде `-update` перезаписывает эталон. Удобно для больших текстовых результатов: отчётов, шаблонов, сериализации. Риск: обновить эталон на сломанном коде и закрепить баг. Поэтому изменения golden-файлов обязательно читаются в диффе.

</details>
<details><summary>assert или require в testify?</summary>

`assert.*` при провале вызывает `t.Errorf` и тест продолжается, `require.*` вызывает `t.FailNow` и тест останавливается. `require` для предусловий (нет ошибки, длина слайса нужная, иначе следующая строка упадёт с паникой), `assert` для независимых проверок. Порядок аргументов: сначала expected, потом actual.

</details>
<details><summary>Чем package foo отличается от package foo_test в тестовом файле?</summary>

`package foo` компилируется вместе с пакетом и видит неэкспортированные идентификаторы. `package foo_test` это отдельный пакет в том же каталоге: импортирует `foo` и видит только экспортированное, то есть тестирует публичный API как настоящий пользователь. Внешний тестовый пакет также помогает разорвать цикл импортов, когда тесту нужен пакет, который сам импортирует `foo`.

</details>
<details><summary>Почему go test иногда пишет (cached) и как это отключить?</summary>

`go test` кеширует успешные результаты для пакетов, если не изменились исходники, флаги, переменные окружения и файлы, которые тест читал. Повторный запуск печатает `(cached)` мгновенно. Отключить для запуска: `-count=1`. Кеширование работает только в режиме списка пакетов (`go test ./...`), а не при запуске без аргументов в каталоге.

</details>
:::
