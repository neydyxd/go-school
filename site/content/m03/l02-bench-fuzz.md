# Бенчмарки, фаззинг, покрытие и Example-тесты

Пакет `testing` умеет больше, чем «проверить, что 2+2 равно 4». В нём есть ещё три инструмента, которые на бэкенде используются постоянно: **бенчмарки** отвечают на вопрос «а это быстро?», **фаззинг** ищет входные данные, о которых ты не подумал, а **покрытие** показывает, какие строки тесты вообще не трогали. Плюс **Example-функции**: документация, которая проверяется компилятором и тестами.

Почему это важно для джуна. Споры «`+=` или `strings.Builder`», «map или слайс», «стоит ли кешировать» решаются не мнениями, а замерами, и на ревью от тебя будут ждать цифры из бенчмарка. Фаззинг находит падения парсеров на кривом вводе до того, как их найдёт злоумышленник. А процент покрытия спрашивают почти на каждом собесе вместе с вопросом «и что он на самом деле показывает».

Отдельная тема для собесов: с Go 1.24 бенчмарки пишутся по-новому, через `b.Loop()`. Старый стиль с `b.N` ещё живёт в тоннах кода, поэтому разберём оба и поймём, чем новый лучше.

## Бенчмарки

Бенчмарк это функция `BenchmarkXxx(b *testing.B)` в `_test.go` файле. Обычный `go test` их не запускает, нужен флаг `-bench` с регуляркой.

```go
func concat(words []string) string {
	s := ""
	for _, w := range words {
		s += w
	}
	return s
}

func BenchmarkConcat(b *testing.B) {
	words := strings.Fields(strings.Repeat("go ", 1000)) // подготовка
	for b.Loop() {
		concat(words) // измеряемый код
	}
}

func BenchmarkBuilder(b *testing.B) {
	words := strings.Fields(strings.Repeat("go ", 1000))
	for b.Loop() {
		var sb strings.Builder
		for _, w := range words {
			sb.WriteString(w)
		}
		_ = sb.String()
	}
}
```

```bash
go test -run=^$ -bench='Concat|Builder' -benchmem .
```

```text
goos: darwin
goarch: arm64
pkg: x
cpu: Apple M4
BenchmarkConcat-10     	    7449	    165645 ns/op	 1063870 B/op	     999 allocs/op
BenchmarkBuilder-10    	  203125	      6038 ns/op	    5368 B/op	      10 allocs/op
```

Как читать строку:

| Колонка | Смысл |
|---|---|
| `BenchmarkConcat-10` | имя и `GOMAXPROCS` во время прогона |
| `7449` | сколько итераций сделал раннер (`b.N`) |
| `165645 ns/op` | среднее время одной итерации |
| `1063870 B/op` | сколько байт выделено в куче за итерацию (`-benchmem`) |
| `999 allocs/op` | сколько аллокаций за итерацию (`-benchmem`) |

`-run=^$` означает «не запускать обычные тесты»: регулярка, под которую не подходит ни одно имя. Без неё перед бенчмарками прогонятся все тесты пакета.

Здесь видно, почему `+=` в цикле плох: строки неизменяемы, каждая конкатенация создаёт новую строку и копирует в неё всё накопленное. 1000 слов дают 999 аллокаций и квадратичный объём копирования. `strings.Builder` дописывает в растущий буфер и отдаёт его как строку без копирования.

Полезные флаги:

- `-benchtime=3s` или `-benchtime=100x`: дольше мерить или ровно 100 итераций (по умолчанию 1 секунда);
- `-count=10`: повторить каждый бенчмарк 10 раз, нужно для статистики;
- `-cpu=1,4,8`: прогнать с разным `GOMAXPROCS`;
- `b.ReportAllocs()` внутри бенчмарка включает колонки памяти без `-benchmem`.

### Старый стиль: b.N

До Go 1.24 бенчмарк выглядел так:

```go
func BenchmarkOld(b *testing.B) {
	words := setup()
	b.ResetTimer() // чтобы setup не попал в замер
	for range b.N {
		concat(words)
	}
}
```

Раннер не знает заранее, сколько итераций нужно, чтобы набрать секунду. Поэтому он **вызывает всю функцию несколько раз** с растущим `b.N`: 1, 100, 10000, ... пока время не станет достаточным. Я посчитал вызовы на своей машине:

```text
BenchmarkN вызов, b.N = 1
BenchmarkN вызов, b.N = 100
BenchmarkN вызов, b.N = 10000
BenchmarkN вызов, b.N = 113803
BenchmarkLoop вызов, b.N = 90232
```

Функция в стиле `b.N` вызвана четыре раза, и подготовка выполнилась четыре раза. Версия с `b.Loop()` вызвана **ровно один раз**: цикл сам решает, сколько итераций прокрутить, а подготовка до цикла выполняется однажды.

::: hood Что делает b.Loop и почему он честнее
Из документации и release notes Go 1.24 и 1.26:

1. **Функция бенчмарка выполняется один раз на каждый `-count`.** Дорогая подготовка (загрузить файл, поднять базу) не повторяется.
2. **Таймер управляется сам:** первый вызов `b.Loop()` сбрасывает таймер, а когда `Loop` возвращает `false`, таймер останавливается. `b.ResetTimer` и `b.StopTimer` вокруг цикла больше не нужны.
3. **Результаты не выбрасываются компилятором.** Аргументы и результаты вызовов внутри `for b.Loop() { ... }` удерживаются живыми (компилятор оборачивает их в `runtime.KeepAlive`). Работает только если условие написано буквально `b.Loop()`.
4. В Go 1.26 убрали побочный эффект: `b.Loop` больше не мешает инлайнингу тела цикла, поэтому все бенчмарки можно переводить с `b.N` на `b.Loop` без потерь.

Пункт 3 важнее, чем кажется. Вот два бенчмарка одной и той же функции:

```go
func popcount(x uint64) int { return bits.OnesCount64(x) }

func BenchmarkPopN(b *testing.B) {
	for i := range b.N {
		popcount(uint64(i)) // результат никуда не идёт
	}
}

func BenchmarkPopLoop(b *testing.B) {
	i := uint64(0)
	for b.Loop() {
		popcount(i)
		i++
	}
}
```

```text
BenchmarkPopN-10         	1000000000	         0.4792 ns/op
BenchmarkPopLoop-10      	358037061	         3.355 ns/op
```

Полнаносекунды это меньше двух тактов процессора: компилятор заинлайнил `popcount`, увидел, что результат не используется, и выкинул вычисление. Бенчмарк мерил пустой цикл. В стиле `b.N` с этим боролись присваиванием результата в глобальную переменную (`sink = popcount(...)`), `b.Loop` делает это за тебя.
:::

::: trap Бенчмарк меряет не то
Плохо: подготовка внутри измеряемого цикла.

```go
func BenchmarkSort(b *testing.B) {
	for b.Loop() {
		data := loadFixture("big.json") // чтение файла попадает в замер
		slices.Sort(data)
	}
}
```

Хорошо: подготовка вне цикла, а если каждой итерации нужна свежая копия данных, копируй дешёвым способом и помни, что это копирование тоже мерится.

```go
func BenchmarkSort(b *testing.B) {
	orig := loadFixture("big.json")
	data := make([]int, len(orig))
	for b.Loop() {
		copy(data, orig) // сортировка портит данные, восстанавливаем
		slices.Sort(data)
	}
}
```

И второе правило: один прогон бенчмарка ничего не доказывает. Ноутбук троттлит, браузер шумит, GC срабатывает не вовремя. Сравнивают так: по 6-10 прогонов каждой версии и `benchstat`.
:::

### Сравнение версий: benchstat

`benchstat` из `golang.org/x/perf` сравнивает две серии прогонов и говорит, значима ли разница.

```bash
go test -run=^$ -bench=Join -benchmem -count=6 . > old.txt
# меняем реализацию
go test -run=^$ -bench=Join -benchmem -count=6 . > new.txt
go run golang.org/x/perf/cmd/benchstat@latest old.txt new.txt
```

```text
        │    old.txt     │              new.txt               │
        │     sec/op     │   sec/op     vs base               │
Join-10   160.923µ ± 63%   6.155µ ± 4%  -96.18% (p=0.002 n=6)

        │   old.txt   │              new.txt              │
        │  allocs/op  │ allocs/op   vs base               │
Join-10   999.00 ± 0%   10.00 ± 0%  -99.00% (p=0.002 n=6)
```

`± 63%` у старой версии это разброс между прогонами: замер шумный. `p=0.002` это вероятность увидеть такую разницу случайно; если `p` больше 0.05, benchstat пишет `~` вместо процента, и честный вывод «разницы не видно». Такая таблица в описании PR убеждает лучше любых слов.

### Подбенчмарки и AllocsPerRun

Чтобы мерить на разных размерах входа, используют `b.Run`, так же как `t.Run` в тестах:

```go
func BenchmarkJoin(b *testing.B) {
	for _, n := range []int{10, 1000, 100000} {
		b.Run(fmt.Sprintf("n=%d", n), func(b *testing.B) {
			words := makeWords(n)
			for b.Loop() {
				join(words)
			}
		})
	}
}
```

А если нужно не мерить, а **гарантировать** число аллокаций в обычном тесте, есть `testing.AllocsPerRun(runs, f)`: прогоняет функцию (один раз для разогрева, потом `runs` раз) и возвращает среднее число аллокаций. На нём построено первое задание домашки.

```go
allocs := testing.AllocsPerRun(100, func() { JoinInts(nums, ", ") })
if allocs > 1 {
	t.Errorf("JoinInts: %.0f аллокаций, want не больше 1", allocs)
}
```

## Фаззинг

Табличный тест проверяет кейсы, которые ты придумал. Фаззер генерирует кейсы, которые ты не придумал: мутирует входные данные, следит за покрытием кода и сохраняет входы, открывающие новые ветки. Встроен в `go test` с Go 1.18.

```go
func Reverse(s string) string {
	b := []byte(s)
	for i, j := 0, len(b)-1; i < j; i, j = i+1, j-1 {
		b[i], b[j] = b[j], b[i]
	}
	return string(b)
}

func FuzzReverse(f *testing.F) {
	f.Add("hello") // семя: стартовый вход
	f.Fuzz(func(t *testing.T, s string) {
		rev := Reverse(s)
		if Reverse(rev) != s {
			t.Errorf("двойной разворот %q дал %q", s, Reverse(rev))
		}
		if utf8.ValidString(s) && !utf8.ValidString(rev) {
			t.Errorf("Reverse(%q) = %q: невалидный UTF-8", s, rev)
		}
	})
}
```

Устройство:

- `FuzzXxx(f *testing.F)` это **фазз-тест**; функция, переданная в `f.Fuzz`, это **фазз-цель**. Первый параметр цели `*testing.T`, дальше один или несколько случайных аргументов.
- Типы аргументов: `string`, `[]byte`, целые (`int`, `int8`...`int64`, `uint`...`uint64`, включая `rune` и `byte`), `float32`, `float64`, `bool`.
- `f.Add(...)` добавляет **семена** (seed corpus). Типы в `Add` должны точно совпадать с параметрами цели.

Два режима:

```bash
go test ./...                                          # цель гоняется только на семенах, как обычный тест
go test -run=^$ -fuzz=FuzzReverse -fuzztime=30s .       # настоящий фаззинг: генерирует входы
```

Наша `Reverse` разворачивает байты. На семени `"hello"` всё хорошо, обычный `go test` зелёный. А фаззер за доли секунды находит контрпример:

```text
fuzz: elapsed: 0s, gathering baseline coverage: 1/1 completed, now fuzzing with 10 workers
fuzz: minimizing 34-byte failing input file
--- FAIL: FuzzReverse (0.04s)
    --- FAIL: FuzzReverse (0.00s)
        r_test.go:16: Reverse("ϲ") = "\xb2\xcf": невалидный UTF-8

    Failing input written to testdata/fuzz/FuzzReverse/02a837c529e04b28
    To re-run:
    go test -run=FuzzReverse/02a837c529e04b28
```

Фаззер нашёл двухбайтовую руну, **минимизировал** вход (сначала было 34 байта) и сохранил его в `testdata/fuzz/FuzzReverse/`. Файл выглядит так:

```text
go test fuzz v1
string("ϲ")
```

С этого момента обычный `go test` тоже падает: файлы из `testdata/fuzz/<Имя>` автоматически становятся семенами. Найденный баг превратился в регрессионный тест. Такие файлы коммитят.

::: hood Как фаззер выбирает входы
С флагом `-fuzz` тестовый бинарник собирается с **инструментацией покрытия**: компилятор вставляет счётчики в каждую ветку кода. Координатор запускает воркеры (по умолчанию по числу `GOMAXPROCS`), те мутируют входы из корпуса (переставляют, вставляют, меняют байты) и сообщают, какие ветки задел каждый вход. Вход, открывший новую ветку, сохраняется в кеш (`$GOCACHE/fuzz`) и становится основой для следующих мутаций. Это **coverage-guided fuzzing**: генерация не вслепую, а в сторону ещё не исследованного кода.

Ограничения: за один запуск фаззится одна цель в одном пакете (`-fuzz` должен совпадать ровно с одним фазз-тестом), без `-fuzztime` фаззер работает бесконечно, пока не найдёт ошибку или не нажмёшь Ctrl+C.
:::

### Что проверять в фазз-цели

Вход случайный, поэтому ожидаемый ответ ты не знаешь. Проверяют **свойства**, верные для любого входа:

1. **Не паникует.** Самое простое и самое полезное для парсеров: фаззер считает панику провалом.
2. **Обратимость (round-trip):** `Decode(Encode(x)) == x`, `Reverse(Reverse(s)) == s`, `Unmarshal(Marshal(v))` даёт `v`.
3. **Инварианты результата:** длина сохраняется, результат отсортирован, валидный UTF-8 остаётся валидным.
4. **Сравнение с эталоном:** быстрая хитрая реализация против медленной очевидной.
5. **Корректная обработка мусора:** невалидный вход даёт ошибку, а не мусорный результат.

Это и есть **property-based testing**. Во втором и третьем задании домашки ты сначала починишь `Reverse`, а потом напишешь проверку свойств сам и прогонишь её против мутантов.

::: trap Фазз-цель, которая сама ломается
Фазз-цель должна быть детерминированной и быстрой: никаких обращений к сети, глобальных счётчиков между вызовами, `time.Now()` и случайных чисел внутри проверки. Иначе фаззер найдёт «падение», которое не воспроизводится по сохранённому входу.

```go
// плохо: результат зависит от предыдущих вызовов
var seen = map[string]bool{}

f.Fuzz(func(t *testing.T, s string) {
	if seen[s] {
		t.Fatal("повтор")
	}
	seen[s] = true
})
```

```go
// хорошо: каждый вызов проверяет только свой вход
f.Fuzz(func(t *testing.T, s string) {
	out, err := Parse(s)
	if err != nil {
		return // мусор на входе: ошибка допустима
	}
	if again, err := Parse(out.String()); err != nil || again != out {
		t.Fatalf("round-trip для %q: %v, %v", s, again, err)
	}
})
```
:::

## Покрытие кода

```bash
go test -cover ./...
# ok  	example.com/text	0.381s	coverage: 84.6% of statements

go test -coverprofile=c.out ./...
go tool cover -func=c.out    # процент по функциям
go tool cover -html=c.out    # открыть в браузере: зелёное покрыто, красное нет
```

```text
example.com/text/text.go:6:	Initials	100.0%
example.com/text/text.go:17:	Grade		71.4%
total:				(statements)	84.6%
```

Как это работает: при `-cover` команда `go` переписывает исходник перед компиляцией и вставляет счётчик в начало каждого **базового блока** (последовательности операторов без ветвлений). После тестов счётчики сбрасываются в профиль. Режимы `-covermode`: `set` (выполнялся ли блок, по умолчанию), `count` (сколько раз), `atomic` (`count`, безопасный для параллельного кода; включается по умолчанию с `-race`).

С Go 1.22 `go test -cover` показывает `coverage: 0.0% of statements` и для пакетов без тестовых файлов, а раньше такие пакеты просто пропускались, и общая картина выглядела лучше, чем есть.

`-coverpkg=./...` учитывает покрытие всех пакетов модуля, а не только тестируемого: полезно, когда интеграционный тест в одном пакете гоняет код из других.

```go
func Grade(score int) string {
	if score < 0 || score > 100 {
		return "ошибка"
	}
	if score >= 90 {
		return "отлично"
	}
	if score >= 60 {
		return "зачёт"
	}
	return "незачёт"
}

func TestGrade(t *testing.T) {
	if Grade(95) != "отлично" || Grade(70) != "зачёт" {
		t.Error("плохо")
	}
}
```

<Predict :options="['100%, все if выполнились', '71.4%', '50%', '57.1%']" :correct="1">

Покрытие считается по операторам (statements). В `Grade` их 7: три `if` и четыре `return`. Тест выполнил все три `if` и два `return` («отлично» и «зачёт»), не выполнил `return "ошибка"` и `return "незачёт"`. 5 из 7 это 71.4%, именно это показывает `go tool cover -func`.

</Predict>

::: trap 100% покрытия не значит «всё проверено»
Покрытие отвечает на вопрос «выполнялась ли строка», а не «проверен ли результат». Тест без единой проверки даёт то же покрытие:

```go
// плохо: 100% покрытия, ноль пользы
func TestGrade(t *testing.T) {
	for _, s := range []int{-1, 50, 70, 95} {
		Grade(s)
	}
}
```

И наоборот, условие `score < 0 || score > 100` это один оператор: если тест проверил только `-1`, вторая половина условия не выполнялась, а покрытие всё равно засчитано. Поэтому покрытие полезно как **поиск непротестированного** (красные строки в `-html`), а как цель («у нас 90%!») оно быстро превращается в тесты ради цифры. Качество тестов честнее меряют мутациями: ровно это ты делаешь в домашке с мутантами.

```go
// хорошо: каждый вызов с проверкой и границами
{"ровно 100", 100, "отлично"},
{"101", 101, "ошибка"},
```
:::

## Example-тесты

Пример использования, который одновременно документация и тест:

```go
func ExampleInitials() {
	fmt.Println(Initials("Иван Петров"))
	fmt.Println(Initials("  Роб   Пайк  "))
	// Output:
	// И.П.
	// Р.П.
}
```

- `go test` запускает функцию и сравнивает её стандартный вывод с комментарием `// Output:` (пробелы по краям игнорируются). Не совпало, тест упал:

```text
--- FAIL: ExampleGrade (0.00s)
got:
отлично
want:
отлично!
```

- `// Unordered output:` сравнивает строки без учёта порядка: для вывода из мапы.
- **Без комментария `Output` пример компилируется, но не запускается.** Удобно для примеров, которые ходят в сеть.
- Имена связывают пример с API: `Example()` для пакета, `ExampleInitials` для функции, `ExampleUser_Name` для метода `Name` типа `User`, суффикс через подчёркивание с маленькой буквы для нескольких примеров: `ExampleInitials_empty`.
- `go doc` и pkg.go.dev показывают примеры рядом с функцией. Обычно их пишут во внешнем тестовом пакете (`package text_test`), чтобы пример выглядел ровно как код пользователя.

С Go 1.24 анализатор `tests` (часть `go vet`, который запускается внутри `go test`) ловит пример с именем несуществующего идентификатора:

```text
./text_test.go:21:1: ExampleNoOutput refers to unknown identifier: NoOutput
```

<details><summary>Чем b.Loop лучше цикла по b.N?</summary>

(1) Функция бенчмарка выполняется один раз на `-count`, а не несколько раз с растущим `b.N`, поэтому подготовка не повторяется. (2) Таймер сбрасывается при первом вызове `Loop` и останавливается после последнего, `ResetTimer` не нужен. (3) Аргументы и результаты вызовов внутри цикла удерживаются живыми, компилятор не может выкинуть измеряемый код как мёртвый. Появился в Go 1.24, с 1.26 больше не мешает инлайнингу.

</details>
<details><summary>Как раннер выбирает b.N?</summary>

В стиле `b.N` он вызывает функцию с `b.N = 1`, оценивает время итерации и повторяет с большим `N`, пока общее время не достигнет `-benchtime` (по умолчанию 1 секунда). В стиле `b.Loop` то же решение принимается внутри одного вызова: `Loop` возвращает `true`, пока не набрано нужное число итераций. После цикла `b.N` содержит итоговое число итераций.

</details>
<details><summary>Как сравнить производительность двух версий кода?</summary>

Запустить бенчмарк каждой версии несколько раз (`-count=6` или 10) с `-benchmem`, сохранить в файлы и сравнить `benchstat old.txt new.txt`. Он покажет медиану, разброс и p-value; если разница статистически незначима, напишет `~`. Мерить на спокойной машине, без параллельных тяжёлых процессов.

</details>
<details><summary>Что такое фаззинг и что проверяют в фазз-цели?</summary>

Автоматическая генерация входов с обратной связью по покрытию: фаззер мутирует входы из корпуса и сохраняет те, что открывают новые ветки кода. Так как ожидаемого ответа нет, проверяют свойства: отсутствие паник, обратимость (decode(encode(x)) == x), инварианты результата, совпадение с эталонной реализацией, ошибку на невалидном входе. Найденный падающий вход сохраняется в `testdata/fuzz/<Имя>` и становится регрессионным тестом.

</details>
<details><summary>Чем отличается go test от go test -fuzz для фазз-теста?</summary>

Без `-fuzz` фазз-цель вызывается только на семенах (`f.Add` и файлы из `testdata/fuzz/<Имя>`), как обычный табличный тест, быстро и детерминированно; так фазз-тесты работают в CI. С `-fuzz=Имя` бинарник собирается с инструментацией покрытия и генерирует входы, пока не найдёт ошибку или не истечёт `-fuzztime`. За раз фаззится одна цель одного пакета.

</details>
<details><summary>Что показывает процент покрытия и почему 100% не цель?</summary>

Долю операторов, которые выполнились хотя бы раз во время тестов. Он не говорит, проверялся ли результат, и не различает половинки сложного условия. Полезен, чтобы найти непротестированный код (красное в `go tool cover -html`). Как KPI провоцирует тесты без проверок. Качество тестов лучше оценивает мутационное тестирование.

</details>
<details><summary>Что такое Example-функции?</summary>

Функции `ExampleXxx` в тестовых файлах. С комментарием `// Output:` они выполняются и их вывод сравнивается с ожидаемым, без комментария только компилируются. Отображаются в `go doc` и на pkg.go.dev как примеры использования, имя связывает пример с функцией, типом или методом. Это документация, которая не может устареть незаметно.

</details>
<details><summary>Как проверить, что функция не аллоцирует лишнего?</summary>

В бенчмарке: `-benchmem` или `b.ReportAllocs()` дают `allocs/op` и `B/op`. В обычном тесте: `testing.AllocsPerRun(n, f)` возвращает среднее число аллокаций и позволяет зафиксировать потолок, чтобы регресс поймал CI. Где именно аллоцируется, покажет профиль памяти (`-memprofile`) и `go build -gcflags=-m` (анализ убегания), это темы следующих уроков.

</details>
:::
