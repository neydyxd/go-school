# Линтеры, race detector, pprof и trace

Тесты проверяют то, о чём ты подумал. Остальное ловят инструменты, которые смотрят на код или на работающую программу без твоих подсказок. **Статические анализаторы** (`go vet`, staticcheck, golangci-lint) читают исходник и находят баги, которые компилируются: перепутанный глагол в `Printf`, проигнорированную ошибку, вызов функции без использования результата. **Детектор гонок** во время выполнения ловит одновременный доступ к памяти из разных горутин. **Профилировщик** pprof показывает, где программа тратит процессор и память, а **трассировщик** trace показывает, что происходило во времени: кто ждал, кто работал, когда пришёл сборщик мусора.

На работе это выглядит так: в CI стоит `golangci-lint run` и `go test -race ./...`, и пулл-реквест не вливается, пока они красные. Когда сервис начинает тормозить или есть память, ты снимаешь профиль с работающего инстанса через `/debug/pprof/` и смотришь, какая функция виновата. На собесе спросят: что такое data race и как его найти, чем race отличается от race condition, как снять профиль и что такое flame graph.

Горутины и синхронизацию мы подробно разберём в модуле про конкурентность. Здесь хватит двух вещей: `go f()` запускает функцию конкурентно, а `sync.WaitGroup` позволяет дождаться, пока запущенные функции закончатся.

## go vet: встроенный анализатор

`go vet` входит в тулчейн и ищет конструкции, которые компилируются, но почти наверняка ошибочны.

```go
func main() {
	name := "Гофер"
	fmt.Printf("%d\n", name)
}
```

```bash
go run .
# %!d(string=Гофер)
go vet .
# ./main.go:10:14: fmt.Printf format %d has arg name of wrong type string
```

`go run` и `go build` vet не запускают, программа спокойно печатает мусор. Что ещё ловит `vet` (полный список: `go tool vet help`):

| Анализатор | Что ловит |
|---|---|
| `printf` | несовпадение глаголов и аргументов в `Printf`-подобных функциях; с Go 1.27 ещё и `%w` с указателем на тип ошибки |
| `copylocks` | копирование `sync.Mutex` по значению (мьютекс перестаёт защищать) |
| `unusedresult` | выброшенный результат `fmt.Sprintf`, `errors.New` и подобных |
| `structtag` | кривые теги структур: `json:name` вместо `json:"name"` |
| `tests` | (Go 1.24) неправильные имена и сигнатуры тестов, бенчмарков, примеров |
| `waitgroup` | (Go 1.25) `wg.Add` внутри запускаемой горутины, а не перед ней |
| `stdversion` | использование функций библиотеки новее, чем версия Go в `go.mod` |

Помнишь из урока про `testing`: `go test` сам запускает облегчённый vet (`printf`, `stdversion`, `tests` и ещё несколько), и при находке тесты не стартуют. Полный `go vet ./...` в CI запускают отдельно.

## staticcheck: глубже, чем vet

[Staticcheck](https://staticcheck.dev/) это сторонний анализатор, де-факто стандарт в сообществе. Проверки разбиты на группы с кодами: `SA` (баги), `S` (упрощения), `ST` (стиль), `QF` (быстрые исправления), `U1000` (неиспользуемый код).

```bash
go install honnef.co/go/tools/cmd/staticcheck@latest   # поставить в ~/go/bin
staticcheck ./...
# или без установки:
go run honnef.co/go/tools/cmd/staticcheck@latest ./...
```

Находки на коде из домашки этого урока:

```text
ex2_lint.go:22:26: cutset contains duplicate characters (SA1024)
ex2_lint.go:23:29: cutset contains duplicate characters (SA1024)
ex2_lint.go:30:2: this value of err is never used (SA4006)
ex2_lint.go:46:2: TrimSpace doesn't have side effects and its return value is ignored (SA4017)
```

Каждая это настоящий баг, а не придирка к стилю:

- **SA1024**: `strings.TrimLeft(u, "https://")` удаляет не префикс, а все символы из **набора** `h t p s : /` с начала строки. `"https://stripe.com"` превращается в `"ripe.com"`. Нужен `strings.TrimPrefix`.
- **SA4006**: ошибку из `strconv.Atoi` присвоили и тут же перезаписали следующим присваиванием, не проверив.
- **SA4017**: строки неизменяемы, `strings.TrimSpace(tag)` возвращает новую строку, а вызов без присваивания ничего не делает. Анализатор `unusedresult` из `go vet` такое пропускает: он знает только фиксированный список функций (`fmt.Sprintf`, `errors.New`, функции пакетов `slices` и `maps`), а `strings` в нём нет.

У каждой проверки есть страница с объяснением: `https://staticcheck.dev/docs/checks/#SA1024`.

## golangci-lint: все линтеры одной командой

golangci-lint это **мета-линтер**: запускает десятки анализаторов (включая vet и staticcheck) за один проход, с общим кешем и одним конфигом. Именно он стоит в CI большинства Go-проектов.

```bash
brew install golangci-lint
golangci-lint run ./...
```

По умолчанию включён набор `standard`: `errcheck`, `govet`, `ineffassign`, `staticcheck`, `unused`. На том же файле из домашки он находит баг, которого staticcheck не видит. Под каждой находкой golangci-lint ещё печатает строку исходника с указателем `^`, здесь эти строки опущены:

```text
ex2_lint.go:39:17: Error return value of `io.WriteString` is not checked (errcheck)
ex2_lint.go:30:5: ineffectual assignment to err (ineffassign)
ex2_lint.go:22:26: SA1024: cutset contains duplicate characters (staticcheck)
ex2_lint.go:23:29: SA1024: cutset contains duplicate characters (staticcheck)
ex2_lint.go:46:2: SA4017: TrimSpace doesn't have side effects and its return value is ignored (staticcheck)
5 issues:
* errcheck: 1
* ineffassign: 1
* staticcheck: 3
```

Находку SA4006 golangci-lint не дублирует: ту же проблему уже сообщил `ineffassign`.

`errcheck` ловит самый частый баг Go-кода: проигнорированную ошибку. Запись в файл могла не пройти (диск полон), а функция вернула `nil`.

Конфиг лежит в корне проекта в `.golangci.yml`. С версии 2 у файла новый формат с обязательным полем `version`:

```yaml
version: "2"

linters:
  default: standard
  enable:
    - bodyclose    # не закрыт resp.Body
    - errorlint    # сравнение ошибок через == вместо errors.Is
    - gocritic     # большой набор проверок на баги и стиль
    - revive       # стиль и соглашения об именах
  exclusions:
    rules:
      - path: _test\.go
        linters:
          - errcheck

formatters:
  enable:
    - gofmt
    - goimports
```

```bash
golangci-lint config verify   # проверить конфиг
golangci-lint linters         # какие линтеры включены
golangci-lint fmt             # отформатировать код включёнными форматтерами
```

::: trap Линтер выключили, вместо того чтобы прочитать
Плохо: линтер ругается, и его заглушают комментарием или отключают целиком.

```go
//nolint
func WriteLines(w io.Writer, lines []string) error {
	for _, l := range lines {
		io.WriteString(w, l+"\n")
	}
	return nil
}
```

Хорошо: разобраться, что он говорит. Обычно это баг, и правка в две строки.

```go
func WriteLines(w io.Writer, lines []string) error {
	for _, l := range lines {
		if _, err := io.WriteString(w, l+"\n"); err != nil {
			return err
		}
	}
	return nil
}
```

Бывают и ложные срабатывания, например `errcheck` на `defer resp.Body.Close()`, где ошибку обработать нечем. Тогда исключение делают точечно: `//nolint:errcheck // причина` на одной строке или правило в `exclusions` конфига. Голый `//nolint` без имени линтера и без причины на ревью не пропускают.
:::

## Race detector

**Data race** (гонка данных) это ситуация, когда две горутины обращаются к одной переменной одновременно, хотя бы одна из них пишет, и между обращениями нет синхронизации. Результат такой программы не определён: она может работать неделю и сломаться под нагрузкой.

```go
func main() {
	counter := 0
	var wg sync.WaitGroup
	for range 1000 {
		wg.Go(func() { // запускает функцию в горутине и учитывает её в wg (Go 1.25)
			counter++
		})
	}
	wg.Wait()
	fmt.Println(counter)
}
```

Три запуска на моей машине дали `973`, `957`, `935`. `counter++` это три операции (прочитать, прибавить, записать), и когда две горутины читают одно и то же старое значение, один инкремент теряется.

Детектор включается флагом `-race` у `go test`, `go run` и `go build`:

```bash
go run -race .
```

```text
==================
WARNING: DATA RACE
Read at 0x00c0001a86f0 by goroutine 19:
  main.main.func1()
      /path/main.go:13 +0x...

Previous write at 0x00c0001a86f0 by goroutine 57:
  main.main.func1()
      /path/main.go:13 +0x...

Goroutine 19 (running) created at:
  sync.(*WaitGroup).Go()
  ...
==================
857
Found 2 data race(s)
exit status 66
```

Отчёт показывает адрес, **два конфликтующих доступа** со стеками и где были созданы обе горутины. Программа с найденной гонкой завершается с кодом 66, а `go test -race` помечает тест упавшим (`race detected during execution of test`).

::: hood Как работает детектор
Детектор построен на ThreadSanitizer (библиотека из LLVM). С флагом `-race` компилятор вставляет вызов рантайма перед **каждым** чтением и записью памяти. Для памяти программы рантайм ведёт «теневую» память: какие горутины обращались к адресу последними и в какой момент их логического времени. Логическое время это **векторные часы**: у каждой горутины свой счётчик событий плюс знание о счётчиках других, полученное через синхронизацию (мьютекс, канал, `WaitGroup`). Если два доступа к одному адресу не упорядочены отношением **happens-before** (ни один не «случился раньше» другого через синхронизацию) и хотя бы один из них запись, это гонка.

Отсюда свойства, которые спрашивают на собесах:

- **Ложных срабатываний нет**: если детектор сообщил о гонке, она реально была в этом запуске.
- **Пропуски есть**: детектор видит только гонки, которые **случились** в этом прогоне. Код, который тесты не выполнили, не проверен. Поэтому `-race` гоняют на тестах с хорошим покрытием и под нагрузкой (`-count=10`).
- **Дорого**: по документации память растёт в 5-10 раз, время выполнения в 2-20 раз. В CI и на стейджинге включают, в проде обычно нет.
:::

::: trap «Без -race тест зелёный, значит гонки нет»
Гонка не обязана проявиться: на одном ядре или при удачном расписании горутин счётчик сойдётся. А иногда рантайм сам замечает конкурентную запись в `map` и роняет программу с `fatal error: concurrent map writes`, но это best-effort проверка, а не гарантия.

```bash
# плохо: CI гоняет тесты без детектора
go test ./...
```

```bash
# хорошо: детектор в CI на всех тестах
go test -race ./...
```

Чинят гонку синхронизацией, а не «подбором» порядка. Для счётчика: `sync.Mutex` вокруг доступа или `atomic.Int64`. Подробно в модуле про конкурентность.
:::

**Data race и race condition** это разные вещи. Data race про память: несинхронизированный одновременный доступ, его ловит детектор. Race condition про логику: результат зависит от порядка событий. Пример race condition без data race: два запроса одновременно проверяют «остаток на счёте больше 100?», оба видят «да», оба списывают. Каждое обращение к балансу под мьютексом, детектор молчит, а деньги ушли в минус. Такое ловят транзакциями и правильным дизайном, а не флагом компилятора.

## pprof: где тратится время и память

Профилировщик отвечает на вопрос «какая функция медленная». Оптимизировать без профиля это гадать.

### Как снять профиль

**Из тестов и бенчмарков**, самый частый способ при разработке:

```bash
go test -run=^$ -bench=CountWords -benchmem -cpuprofile=cpu.out -memprofile=mem.out ./m03/l04-quality/
```

**С работающего сервиса** через `net/http/pprof`: пустой импорт регистрирует обработчики `/debug/pprof/` в стандартном `http.DefaultServeMux`.

```go
import _ "net/http/pprof"

func main() {
	go func() {
		log.Println(http.ListenAndServe("localhost:6060", nil))
	}()
	// ...основная программа
}
```

```bash
go tool pprof 'http://localhost:6060/debug/pprof/profile?seconds=30'  # CPU за 30 секунд
go tool pprof http://localhost:6060/debug/pprof/heap                  # память
curl 'http://localhost:6060/debug/pprof/goroutine?debug=2'            # стеки всех горутин
```

Порт с pprof **никогда не выставляют наружу**: через него видно внутренности программы, а снятие профиля нагружает процесс. Слушают на `localhost` или на отдельном внутреннем порту.

Виды профилей:

| Профиль | Что показывает |
|---|---|
| `profile` (CPU) | где процессор проводит время |
| `heap` | живые объекты в куче (кто держит память) |
| `allocs` | все аллокации с начала работы (кто мусорит) |
| `goroutine` | стеки всех горутин: ищем утечки и зависания |
| `block`, `mutex` | где горутины ждут на каналах и мьютексах (включаются отдельно) |

### Как читать

```bash
go tool pprof -top -cum cpu.out
```

```text
      flat  flat%   sum%        cum   cum%
         0     0%     0%      680ms 76.40%  runtime.systemstack
         0     0%     0%      490ms 55.06%  runtime.gcStart.func4
...
         0     0% 55.06%      220ms 24.72%  x.CountWords
         0     0% 55.06%      170ms 19.10%  regexp.MustCompile
         0     0% 55.06%      170ms 19.10%  regexp.compile
```

- **flat**: время в самой функции, без вызванных из неё;
- **cum** (cumulative): время в функции вместе со всем, что она вызвала.

Здесь видно: из 220 мс в `CountWords` 170 мс уходят на `regexp.MustCompile`, то есть на компиляцию регулярки. Заметную долю (в моём прогоне больше половины сэмплов) занимают служебные части цикла сборки мусора (`gcStart`), а циклов GC много, потому что программа много мусорит. Оговорка: на macOS CPU-профили шумнее, чем на Linux. Здесь почти всё время `gcStart` ушло в системный вызов `kevent` при перезапуске мира после паузы, а не в саму пометку объектов, и `Total samples` в шапке профиля заметно меньше длительности прогона. Поэтому сравнивай профили, снятые на одной машине, и не придавай значения мелким процентам. Профиль памяти подтверждает и показывает строку:

```bash
go tool pprof -sample_index=alloc_space -list CountWords mem.out
```

```text
         .   345.19MB     27:		re := regexp.MustCompile(`[\p{L}\p{N}]+`)
         .    18.70MB     28:		for _, w := range re.FindAllString(line, -1) {
```

Регулярка компилируется заново на каждой строке текста. Это и есть задание домашки.

Самый наглядный вид: веб-интерфейс.

```bash
go tool pprof -http=localhost:8080 cpu.out
```

С Go 1.26 он открывается сразу на **flame graph**: каждая полоса это функция, ширина пропорциональна времени, а над ней полосы функций, которые она вызвала. Ищешь широкие полосы наверху «пламени», это горячие места.

::: hood Как pprof собирает профили
**CPU-профиль сэмплирующий.** Рантайм просит ОС присылать сигнал `SIGPROF` 100 раз в секунду процессорного времени (константа `hz = 100` в `runtime/pprof`). По каждому сигналу записывается стек текущей горутины. Функция, которая работает 30% времени, попадёт примерно в 30% сэмплов. Отсюда следствия: накладные расходы маленькие (можно снимать в проде), короткие профили неточны (за секунду всего 100 сэмплов на ядро), а время ожидания (сеть, мьютекс) в CPU-профиль не попадает, для него есть `block`, `mutex` и trace.

**Профиль памяти тоже сэмплирующий**: `runtime.MemProfileRate = 512 * 1024`, то есть в среднем записывается одна аллокация на каждые 512 КБ выделенной памяти, со стеком места выделения. Числа в профиле масштабируются обратно до оценки полного объёма.
:::

::: trap Оптимизация без профиля
Плохо: «тут наверняка медленно» и переписывание кода на хитрый, но нечитаемый.

```go
// «оптимизировал» склейку двух коротких строк, которая занимает 0.01% времени
var b strings.Builder
b.Grow(len(first) + 1 + len(last))
b.WriteString(first)
b.WriteByte(' ')
b.WriteString(last)
name := b.String()
```

Хорошо: бенчмарк воспроизводит медленный сценарий, профиль показывает горячую функцию, правится она, `benchstat` подтверждает выигрыш. В примере выше одна правка (вынести компиляцию регулярки из цикла или заменить её на `strings.FieldsFunc`) даёт больше, чем любые микрооптимизации вокруг.

```go
name := first + " " + last // читаемо, и это не горячее место
```
:::

## trace: что происходило во времени

pprof отвечает «где тратится время» в сумме. Трассировщик отвечает «что происходило в каждый момент»: когда какая горутина работала, на каком процессоре (P), когда ждала сеть или мьютекс, когда шёл GC и сколько стоил stop-the-world.

```bash
go test -run=TestHitsConcurrent -trace=trace.out ./m03/l04-quality/
go tool trace trace.out   # откроет веб-интерфейс в браузере
```

В коде трассировку пишут через `runtime/trace` (`trace.Start(w)` и `trace.Stop()`) или снимают с сервиса: `/debug/pprof/trace?seconds=5`. С Go 1.25 есть **flight recorder** (`trace.FlightRecorder`): трасса постоянно пишется в кольцевой буфер в памяти, а когда случилось что-то странное (запрос шёл 5 секунд), программа сохраняет последние секунды в файл. С Go 1.27 `go tool trace -http=:6060` слушает только localhost, как и pprof.

Когда брать trace, а когда pprof: если CPU загружен и надо найти тяжёлую функцию, это pprof. Если CPU свободен, а запросы всё равно медленные (горутины ждут, мало параллелизма, долгие паузы GC), это trace. Читать трассы по-настоящему научимся в модуле про конкурентность и рантайм.

```go
func main() {
	fmt.Printf("%d\n", "Гофер")
}
```

```bash
go run .
```

```go
	counter := 0
	var wg sync.WaitGroup
	for range 1000 {
		wg.Go(func() { counter++ })
	}
	wg.Wait()
	fmt.Println(counter)
}
```

```bash
go vet . && go run .
```

<Predict :options="['vet найдёт гонку и программа не запустится', 'всегда 1000', 'число, обычно меньше 1000, разное от запуска к запуску', 'всегда 0: горутины не успеют запуститься']" :correct="2">

`go vet` гонки не ищет, это статический анализатор, а гонка свойство конкретного выполнения. `wg.Wait()` дожидается всех горутин, так что 0 не будет, но несинхронизированный `counter++` теряет инкременты: у меня было 973, 957, 935. `go run -race .` напечатает `WARNING: DATA RACE` и завершится с `exit status 66`.

</Predict>

<details><summary>Что такое data race и чем он отличается от race condition?</summary>

Data race: две горутины одновременно обращаются к одной памяти, хотя бы одна пишет, и доступы не упорядочены синхронизацией. Поведение не определено, ловится race detector'ом. Race condition: логическая ошибка, когда результат зависит от порядка событий (проверил баланс, потом списал, а между ними списал кто-то ещё). Может быть без data race, если каждое обращение синхронизировано; детектор её не видит.

</details>
<details><summary>Как работает race detector и какие у него ограничения?</summary>

Включается флагом `-race`, основан на ThreadSanitizer. Компилятор инструментирует каждый доступ к памяти, рантайм отслеживает happens-before через векторные часы и сообщает о конфликтующих доступах без синхронизации. Ложных срабатываний нет, но находит только гонки, которые случились в данном прогоне. Дорогой: память в 5-10 раз, время в 2-20 раз, поэтому используется в тестах и CI. Процесс с найденной гонкой завершается с кодом 66.

</details>
<details><summary>Чем go vet отличается от staticcheck и golangci-lint?</summary>

`go vet` входит в тулчейн, проверяет немного, но почти без ложных срабатываний; его подмножество запускается в `go test`. Staticcheck сторонний, проверок намного больше (баги, упрощения, стиль, неиспользуемый код). golangci-lint это мета-линтер: запускает vet, staticcheck, errcheck и десятки других за один проход с единым конфигом, стандарт для CI.

</details>
<details><summary>Как найти, почему сервис медленный?</summary>

Сначала воспроизвести и измерить (бенчмарк или нагрузочный тест). Снять CPU-профиль: в тесте `-cpuprofile`, на работающем сервисе через `net/http/pprof` (`/debug/pprof/profile?seconds=30`). Открыть `go tool pprof -http`, посмотреть flame graph или `-top -cum`, найти горячую функцию, `-list` покажет строки. Если CPU не загружен, а латентность высокая, смотреть `block`/`mutex` профили и trace. После правки подтвердить выигрыш бенчмарком и `benchstat`.

</details>
<details><summary>Что значат flat и cum в pprof?</summary>

`flat`: время (или память), потраченное в самой функции. `cum`: в функции вместе со всем, что она вызвала. Функция с маленьким flat и большим cum сама дешёвая, но вызывает дорогое; с большим flat горячая сама по себе.

</details>
<details><summary>Как устроен CPU-профилировщик Go?</summary>

Сэмплирующий: рантайм через сигнал `SIGPROF` 100 раз в секунду процессорного времени записывает стек выполняющейся горутины. Доля сэмплов функции приближает долю её времени. Накладные расходы малы, поэтому профиль можно снимать в проде. Время ожидания (I/O, блокировки) в CPU-профиль не попадает.

</details>
<details><summary>Чем heap-профиль отличается от allocs?</summary>

Оба из одних данных, разный взгляд по умолчанию. `heap` показывает живые объекты на момент последнего GC (`inuse_space`): кто держит память, ищем утечки. `allocs` показывает все аллокации с начала работы (`alloc_space`): кто больше всех выделяет и нагружает GC. В `go tool pprof` переключается через `-sample_index`.

</details>
<details><summary>Зачем нужен go tool trace, если есть pprof?</summary>

pprof агрегирует: сколько всего времени в каждой функции. Trace показывает события во времени: когда каждая горутина работала, ждала, на каком P, когда шёл GC и паузы. Нужен для проблем латентности и параллелизма, когда CPU не загружен, а работа идёт медленно. С Go 1.25 есть flight recorder для снятия последних секунд трассы по событию.

</details>
