# Деревья и рекурсия

Дерево это первая нелинейная структура в треке: у элемента не один сосед справа, а несколько детей. Почти все задачи на деревья решаются рекурсией в три строчки, поэтому на собесах их любят: по тому, как ты пишешь рекурсию, сразу видно, понимаешь ли ты стек вызовов, базовый случай и асимптотику.

В бэкенде деревья повсюду, даже если ты их не строишь руками. JSON-документ и DOM это деревья. Файловая система, иерархия категорий в магазине, ветки комментариев, оргструктура компании: деревья. Индекс в PostgreSQL это B-дерево (мы разбирали его в уроке про индексы), а маршрутизатор HTTP-запросов во многих фреймворках, включая Gin, хранит пути в префиксном дереве. Когда ты пишешь рекурсивный CTE для «всех подкатегорий», ты обходишь дерево.

В уроке: рекурсия и стек вызовов, двоичное дерево на указателях, три обхода в глубину рекурсивно и на явном стеке, обход по уровням через очередь, высота и «две величины из одного обхода», двоичное дерево поиска (поиск, вставка, проверка) и наименьший общий предок.

## Рекурсия и стек вызовов

Рекурсивная функция вызывает саму себя на задаче поменьше. У неё всегда две части:

- **базовый случай**: задача настолько мала, что ответ известен сразу (пустой список, `nil`-узел, `n == 0`);
- **шаг**: свести задачу к той же задаче меньшего размера и собрать ответ.

```go
// сумма элементов слайса: пустой слайс даёт 0, иначе первый плюс сумма хвоста
func sum(a []int) int {
	if len(a) == 0 {
		return 0
	}
	return a[0] + sum(a[1:])
}
```

Чтобы поверить, что рекурсия работает, не надо мысленно раскручивать все вызовы. Достаточно проверить базовый случай и убедиться, что шаг верен, **если** рекурсивный вызов вернул правильный ответ для меньшей задачи. Это обычная математическая индукция, и именно так стоит рассуждать вслух на собесе.

Каждый вызов функции получает свой **кадр стека**: аргументы, локальные переменные, адрес возврата. Пока `sum([3 1 4])` ждёт ответа от `sum([1 4])`, её кадр лежит в стеке:

```
sum([3 1 4])   ждёт: 3 + ?
  sum([1 4])   ждёт: 1 + ?
    sum([4])   ждёт: 4 + ?
      sum([])  базовый случай, возвращает 0
    sum([4])   = 4
  sum([1 4])   = 5
sum([3 1 4])   = 8
```

Глубина рекурсии равна максимальному числу одновременно живых кадров. Это и есть дополнительная память рекурсивного решения: O(глубина), даже если ты не завёл ни одного слайса. Для дерева глубина рекурсии равна его высоте `h`.

::: hood Стек горутины: растёт до гигабайта, но не бесконечно
В Go у каждой горутины свой стек. Он стартует маленьким (минимум 2 КБ, с Go 1.19 рантайм подбирает стартовый размер по среднему размеру стеков, которые видел сборщик мусора) и растёт: когда кадр не помещается, рантайм выделяет стек вдвое больше и копирует туда старый. Поэтому рекурсия глубиной в миллион вызовов в Go работает без настроек, хотя в C или Java с настройками по умолчанию она бы упала.

Предел всё же есть: на 64-битных платформах 1 ГБ на стек горутины (`maxstacksize` в `runtime/proc.go`). Я запустил простую рекурсию `depth(n-1) + 1`: миллион уровней прошёл, сто миллионов закончились так:

```
runtime: goroutine stack exceeds 1000000000-byte limit
fatal error: stack overflow
```

Это `fatal error`, а не паника: `recover` его не поймает, процесс падает целиком. Хвостовую рекурсию Go не оптимизирует (стандарт этого не обещает), поэтому «переписать рекурсию в хвостовую» не спасает. Если глубина может быть огромной (дерево-«палка» из пользовательских данных, граф на миллионы вершин), пиши итеративно на явном стеке: слайс в куче ограничен только памятью.
:::

### Рекурсивные замыкания

В задачах на деревья часто нужна вспомогательная рекурсивная функция, которая видит переменные внешней (например, лучший найденный ответ). В Go это замыкание, и у него есть синтаксическая ловушка: `dfs := func(...)` не может вызвать само себя, потому что имя `dfs` появляется только после конца выражения. Сначала объяви переменную, потом присвой:

```go
best := 0
var dfs func(n *TreeNode) int // объявили
dfs = func(n *TreeNode) int {  // присвоили: внутри dfs уже видна
	if n == nil {
		return 0
	}
	return 1 + max(dfs(n.Left), dfs(n.Right))
}
```

## Двоичное дерево на указателях

В двоичном дереве у каждого узла не больше двух детей. В Go узел это структура с указателями на детей, а пустое дерево это `nil`:

```go
type TreeNode struct {
	Val   int
	Left  *TreeNode
	Right *TreeNode
}

root := &TreeNode{Val: 1,
	Left:  &TreeNode{Val: 2, Left: &TreeNode{Val: 4}, Right: &TreeNode{Val: 5}},
	Right: &TreeNode{Val: 3},
}
```

```
        1          корень: узел без родителя
       / \
      2   3        3 это лист: узел без детей
     / \
    4   5
```

Словарь, который надо знать:

- **глубина узла**: число рёбер от корня до него (у корня 0);
- **высота дерева**: длина самого длинного пути от корня до листа. Тут две конвенции: в рёбрах или в узлах. LeetCode в задаче «Maximum Depth» считает в узлах (у одного узла 1, у пустого дерева 0), так же делаем в домашке. На собесе уточни;
- **полное (complete)** дерево: все уровни заполнены, кроме, может быть, последнего, а последний заполнен слева. Так устроена куча из следующего урока;
- **сбалансированное**: высоты поддеревьев любого узла отличаются не больше чем на 1. Высота такого дерева O(log n);
- **вырожденное**, «палка»: у каждого узла один ребёнок. Это по сути связный список, высота `n`.

Рекурсивное определение «дерево это либо `nil`, либо узел с двумя деревьями» и есть причина, почему рекурсия здесь так естественна: функция от дерева почти всегда выглядит как «база для `nil`, плюс комбинация ответов для левого и правого поддерева».

### Метод на nil-получателе

Go-специфичный приём: метод с указательным получателем можно вызвать на `nil`, и если метод это проверяет, получается очень чистая рекурсия без проверок у вызывающего.

```go
func (n *TreeNode) Size() int {
	if n == nil {
		return 0
	}
	return 1 + n.Left.Size() + n.Right.Size()
}
```

`n.Left.Size()` для отсутствующего ребёнка не паникует: вызов метода не разыменовывает указатель, паника случится только при обращении к полю `nil`-указателя. В задачах с LeetCode сигнатуры заданы функциями, но в своём коде этот приём удобен.

## Обходы в глубину

Обойти дерево значит посетить каждый узел ровно один раз. Три классических порядка различаются только тем, когда мы «обрабатываем» узел относительно его поддеревьев:

```go
func preorder(n *TreeNode, out *[]int) { // корень, левое, правое
	if n == nil {
		return
	}
	*out = append(*out, n.Val)
	preorder(n.Left, out)
	preorder(n.Right, out)
}

func inorder(n *TreeNode, out *[]int) { // левое, корень, правое
	if n == nil {
		return
	}
	inorder(n.Left, out)
	*out = append(*out, n.Val)
	inorder(n.Right, out)
}

func postorder(n *TreeNode, out *[]int) { // левое, правое, корень
	if n == nil {
		return
	}
	postorder(n.Left, out)
	postorder(n.Right, out)
	*out = append(*out, n.Val)
}
```

Для дерева выше: pre-order `1 2 4 5 3`, in-order `4 2 5 1 3`, post-order `4 5 2 3 1`.

Зачем три порядка:

- **pre-order**: сначала родитель, потом дети. Копирование и сериализация дерева (родителя надо создать раньше детей), печать структуры каталогов с отступами;
- **in-order**: в двоичном дереве поиска выдаёт значения **по возрастанию**. На этом держатся проверка BST, k-й наименьший элемент и итераторы по дереву;
- **post-order**: сначала дети, потом родитель. Всё, где ответ узла зависит от ответов детей: высота, размер поддерева, удаление дерева, подсчёт размера каталога.

Все три работают за O(n) по времени (каждый узел посещаем один раз) и O(h) дополнительной памяти на стек вызовов.

## Обходы без рекурсии: явный стек

Рекурсия прячет стек в рантайме. Его можно завести руками: слайс, `append` кладёт на вершину, срез `s[:len(s)-1]` снимает. Это нужно, когда дерево может быть очень глубоким, и это любимая просьба интервьюера после рекурсивного решения: «а теперь без рекурсии».

**Pre-order** проще всех: снимаем узел, обрабатываем, кладём детей. Правого кладём первым, чтобы левый оказался на вершине и обработался раньше.

```go
func preorderIter(root *TreeNode) []int {
	var res []int
	stack := []*TreeNode{root}
	for len(stack) > 0 {
		n := stack[len(stack)-1]
		stack = stack[:len(stack)-1]
		if n == nil {
			continue
		}
		res = append(res, n.Val)
		stack = append(stack, n.Right, n.Left)
	}
	return res
}
```

**In-order**: идём влево до упора, складывая путь в стек. Когда влево некуда, снимаем узел, обрабатываем и переходим в его правое поддерево, где повторяем то же самое.

```go
func inorderIter(root *TreeNode) []int {
	var res []int
	var stack []*TreeNode
	cur := root
	for cur != nil || len(stack) > 0 {
		for cur != nil {
			stack = append(stack, cur)
			cur = cur.Left
		}
		cur = stack[len(stack)-1]
		stack = stack[:len(stack)-1]
		res = append(res, cur.Val)
		cur = cur.Right
	}
	return res
}
```

**Post-order** самый хитрый: узел можно вывести, только когда оба поддерева уже выведены. Два распространённых способа. Первый: сделать «зеркальный pre-order» (корень, правое, левое) и развернуть результат. Работает, но держит весь ответ до разворота. Второй, честный: тот же спуск влево, что в in-order, но узел с вершины стека снимаем, только если правого поддерева нет или оно только что обработано. «Только что обработано» отслеживаем указателем `prev` на последний выведенный узел. Его ты напишешь в домашке.

## Обход по уровням: очередь

Обход в ширину (BFS) посещает узлы по уровням: корень, потом все узлы глубины 1 слева направо, потом глубины 2. Стек здесь не подходит, нужна **очередь**: первым пришёл, первым ушёл. Дети узла встают в конец очереди и будут обработаны после всех узлов текущего уровня.

Чтобы разделить ответ по уровням, удобно обрабатывать уровень целиком: текущий уровень это слайс, следующий собираем в новый слайс.

```go
func levelOrder(root *TreeNode) [][]int {
	if root == nil {
		return nil
	}
	var res [][]int
	level := []*TreeNode{root}
	for len(level) > 0 {
		var vals []int
		var next []*TreeNode
		for _, n := range level {
			vals = append(vals, n.Val)
			if n.Left != nil {
				next = append(next, n.Left)
			}
			if n.Right != nil {
				next = append(next, n.Right)
			}
		}
		res = append(res, vals)
		level = next
	}
	return res
}
```

Каждый узел попадает в очередь один раз: O(n) по времени, O(ширина дерева) памяти. Для полного дерева нижний уровень содержит около `n/2` узлов, так что BFS по памяти может быть дороже DFS (O(h) = O(log n)). Для «палки» наоборот: ширина 1, а глубина `n`.

Классические задачи на уровни: правый вид дерева (последний узел каждого уровня), зигзаг, среднее по уровням, минимальная глубина (BFS останавливается на первом листе и не ходит в глубокие ветки).

## Высота и две величины из одного обхода

Высота в узлах:

```go
func maxDepth(n *TreeNode) int {
	if n == nil {
		return 0
	}
	return 1 + max(maxDepth(n.Left), maxDepth(n.Right))
}
```

Это post-order: ответ узла собирается из ответов детей. Теперь задача посложнее, **диаметр**: самый длинный путь между любыми двумя узлами (в рёбрах). Самый длинный путь, который «перегибается» в узле `n`, равен `height(n.Left) + height(n.Right)`. Наивно: для каждого узла посчитать высоты детей заново. Но высота сама стоит O(размер поддерева), и на «палке» выходит 1 + 2 + ... + n = O(n²).

Приём, который встретится ещё много раз: **функция возвращает одно, а попутно обновляет другое**. Рекурсия возвращает высоту (её нужно знать родителю), а лучший диаметр копится во внешней переменной замыкания:

```go
func diameter(root *TreeNode) int {
	best := 0
	var height func(n *TreeNode) int
	height = func(n *TreeNode) int {
		if n == nil {
			return 0
		}
		l, r := height(n.Left), height(n.Right)
		best = max(best, l+r) // путь через n
		return 1 + max(l, r)
	}
	height(root)
	return best
}
```

Один обход, O(n). Тот же приём решает проверку сбалансированности (возвращаем высоту или `-1` как знак «уже несбалансировано»), максимальную сумму пути и наименьшего общего предка ниже.

## Двоичное дерево поиска (BST)

BST это двоичное дерево с порядком: для **каждого** узла все значения в левом поддереве меньше его значения, а все значения в правом больше. Слово «все» важно: недостаточно, чтобы левый ребёнок был меньше родителя.

```
        8
      /   \
     4     12
    / \   /  \
   2   6 10   14
```

### Поиск и вставка

Поиск как бинарный поиск по слайсу: сравнили с узлом и ушли в одно поддерево, второе отбросили целиком.

```go
func search(n *TreeNode, x int) *TreeNode {
	for n != nil && n.Val != x {
		if x < n.Val {
			n = n.Left
		} else {
			n = n.Right
		}
	}
	return n
}
```

Вставка: тот же спуск до `nil`, на его месте новый лист. Цикл, а не рекурсия: так нет риска переполнить стек на вырожденном дереве и проще не потерять связь с родителем.

Обе операции стоят **O(h)**. Для сбалансированного дерева это O(log n), для «палки» O(n). А «палку» получить проще простого: вставь в пустое BST числа `1, 2, 3, ..., n` по порядку, и каждое новое уйдёт вправо. Поэтому в реальных системах используют **самобалансирующиеся** деревья: AVL, красно-чёрные (на них построены `TreeMap` в Java и обычно `std::map` в C++), B-деревья в базах данных. Они после вставки делают повороты и держат высоту O(log n). Писать их на собесе джуна не просят, но знать, зачем они нужны, надо.

В стандартной библиотеке Go упорядоченной map нет: `map` хеш-таблица без порядка. Если нужны «ключи по порядку», обычно хватает `map` плюс `slices.Sorted(maps.Keys(m))` или отсортированного слайса с бинарным поиском; для частых вставок с порядком берут стороннюю реализацию B-дерева или skip-list.

Удаление из BST разбирают реже, но схему надо знать: лист просто отрезаем; у узла с одним ребёнком ставим ребёнка на его место; у узла с двумя детьми копируем в него следующий по порядку элемент (самый левый в правом поддереве) и удаляем уже тот узел, у которого не больше одного ребёнка.

### Проверка, что дерево это BST

Самая частая ошибка собеса: сравнить узел только с детьми. Вот дерево, которое такую проверку проходит, но BST не является:

```
      5
     / \
    4   6
       / \
      3   7      3 < 5, а лежит справа от 5
```

Правильная идея: у каждого узла есть **допустимый интервал**, унаследованный от предков. Корень может быть любым; уходя влево, сужаем верхнюю границу до значения родителя, уходя вправо, нижнюю.

```go
func isBST(n *TreeNode, lo, hi *int) bool {
	if n == nil {
		return true
	}
	if (lo != nil && n.Val <= *lo) || (hi != nil && n.Val >= *hi) {
		return false
	}
	return isBST(n.Left, lo, &n.Val) && isBST(n.Right, &n.Val, hi)
}

// вызов: isBST(root, nil, nil)
```

Границы указателями, а не `math.MinInt` и `math.MaxInt`: со строгим сравнением сторож ломается на узле, значение которого совпадает со сторожем. Второй способ проверки проще: in-order обход BST идёт строго по возрастанию, так что достаточно сравнивать каждый узел с предыдущим.

### Наименьший общий предок

LCA (lowest common ancestor) двух узлов это самый глубокий узел, у которого оба в поддереве. Узел считается предком самого себя. Применение: ближайший общий руководитель в оргструктуре, общий каталог двух файлов, точка ветвления двух версий.

**В BST** порядок подсказывает направление. Если оба значения меньше текущего, LCA слева; если оба больше, справа; иначе пути разошлись (или один из узлов и есть текущий), и текущий узел это ответ. O(h), без рекурсии:

```go
func lcaBST(root, p, q *TreeNode) *TreeNode {
	for root != nil {
		switch {
		case p.Val < root.Val && q.Val < root.Val:
			root = root.Left
		case p.Val > root.Val && q.Val > root.Val:
			root = root.Right
		default:
			return root
		}
	}
	return nil
}
```

**В обычном дереве** значения ничего не говорят, и нужен обход. Снова post-order, где функция возвращает «что нашла в поддереве»: `nil`, если ни `p`, ни `q` там нет; сам `p` или `q`, если нашла один; LCA, если нашла оба. Если левое и правое поддеревья вернули не `nil`, то `p` и `q` по разные стороны, и текущий узел это ответ. Один обход, O(n). Узлы сравниваем **указателями**: значения в обычном дереве могут повторяться. Код напишешь в домашке.

## Разбор: зеркало дерева

> Дан корень двоичного дерева. Отрази дерево: у каждого узла поменяй местами левое и правое поддеревья. Верни корень. Аналог: [LeetCode 226](https://leetcode.com/problems/invert-binary-tree/).

**Уточняем.** Пустое дерево возвращаем как есть. Новые узлы не создаём, меняем указатели на месте.

**Идея.** Отражённое дерево это корень, у которого слева отражённое правое поддерево, а справа отражённое левое. Это прямая рекурсия, порядок обхода любой.

```go
func invert(n *TreeNode) *TreeNode {
	if n == nil {
		return nil
	}
	n.Left, n.Right = invert(n.Right), invert(n.Left)
	return n
}
```

Множественное присваивание Go сначала вычисляет обе правые части, потом присваивает, поэтому временная переменная не нужна. **Проверка** на дереве `1 / (2, 3)`: получаем `1 / (3, 2)`. На `nil` сразу возвращаем `nil`. **Сложность** O(n) по времени и O(h) памяти на стек. Если интервьюер боится глубоких деревьев, тот же код пишется через очередь: достаём узел, меняем детей местами, кладём детей в очередь.

::: trap Проверка BST только по детям
Плохо: каждый узел сравнивается только со своими детьми.

```go
func isBST(n *TreeNode) bool {
	if n == nil {
		return true
	}
	if n.Left != nil && n.Left.Val >= n.Val {
		return false
	}
	if n.Right != nil && n.Right.Val <= n.Val {
		return false
	}
	return isBST(n.Left) && isBST(n.Right)
}
// дерево 5 / (4, 6 / (3, 7)) признано корректным, а 3 лежит справа от 5
```

Хорошо: передавать вниз допустимый интервал `(lo, hi)` или сравнивать соседей в in-order обходе (код выше).
:::

::: trap Сторожа math.MinInt и math.MaxInt
Плохо: интервал по умолчанию «от минус до плюс бесконечности» через крайние значения `int` и строгое сравнение.

```go
func ok(n *TreeNode, lo, hi int) bool {
	if n == nil {
		return true
	}
	if n.Val <= lo || n.Val >= hi {
		return false
	}
	return ok(n.Left, lo, n.Val) && ok(n.Right, n.Val, hi)
}
// ok(root, math.MinInt, math.MaxInt) для одного узла со значением math.MaxInt вернёт false
```

Хорошо: границы как `*int` (нет границы, значит `nil`) или проверка через in-order с указателем на предыдущий узел. На LeetCode в задаче 98 значения узлов как раз доходят до краёв 32-битного `int`, и решения со сторожем `math.MaxInt32` там падают.
:::

::: trap Пересчёт высоты в каждом узле
Плохо: диаметр (или сбалансированность) через вызов отдельной функции высоты в каждом узле.

```go
func diameter(n *TreeNode) int {
	if n == nil {
		return 0
	}
	through := maxDepth(n.Left) + maxDepth(n.Right) // O(размер поддерева)
	return max(through, diameter(n.Left), diameter(n.Right))
}
// на «палке» из 100 000 узлов это около 5·10⁹ шагов
```

Хорошо: одна post-order функция возвращает высоту и попутно обновляет ответ (код в разделе про высоту). Общий признак: если рекурсия внутри себя вызывает **другую** рекурсию по тому же поддереву, почти наверняка выходит O(n²).
:::

::: trap Рекурсивное замыкание через :=
Плохо: имя ещё не объявлено, когда компилируется тело.

```go
fact := func(n int) int {
	if n <= 1 {
		return 1
	}
	return n * fact(n-1) // ошибка компиляции: undefined: fact
}
```

Хорошо: `var fact func(int) int`, потом `fact = func(n int) int { ... }`. Или обычная функция верхнего уровня, если внешние переменные не нужны.
:::

::: trap Сравнение узлов по значению
В задаче про LCA в обычном дереве (и в любой задаче, где передают «узел») сравнивай указатели: `n == p`. Сравнение `n.Val == p.Val` ломается, как только значения повторяются, а в обычном дереве это разрешено. Указатель однозначно определяет узел, значение нет.
:::

## Что выведет программа?

```go
// дерево:  1
//         / \
//        2   3
//       / \
//      4   5
var out []int
inorder(root, &out) // левое, корень, правое
fmt.Println(out)
```

<Predict :options="['[1 2 4 5 3]', '[4 2 5 1 3]', '[4 5 2 3 1]', '[1 2 3 4 5]']" :correct="1">

In-order уходит влево до упора: сначала 4, потом его родитель 2, потом правый ребёнок 5. Левое поддерево корня закончилось, выводим корень 1 и обходим правое: 3. Первый вариант это pre-order, третий post-order, четвёртый обход по уровням.

</Predict>

```go
type Node struct{ Left, Right *Node }

func (n *Node) Size() int {
	if n == nil {
		return 0
	}
	return 1 + n.Left.Size() + n.Right.Size()
}

func main() {
	var root *Node
	fmt.Println(root.Size())
	root = &Node{Left: &Node{}}
	fmt.Println(root.Size())
}
```

<Predict :options="['паника: nil pointer dereference', '0, затем 2', '0, затем 1', 'ошибка компиляции']" :correct="1">

Вызов метода с указательным получателем на `nil` законен: внутрь метода просто приходит `n == nil`, и метод сам это проверяет. Паника была бы при обращении к полю (`n.Left`) без проверки. Во втором случае два узла: корень и его левый ребёнок, у обоих `nil`-дети дают 0.

</Predict>

```go
var root *TreeNode
for v := 1; v <= 5; v++ {
	root = insert(root, v) // обычная вставка в BST без балансировки
}
fmt.Println(height(root)) // высота в узлах
```

<Predict :options="['3', '5', '2', '1']" :correct="1">

Каждое следующее число больше всех предыдущих, поэтому уходит вправо до самого конца: получается «палка» 1, 2, 3, 4, 5, высота 5. Сбалансированное дерево из 5 узлов имело бы высоту 3. Именно поэтому без балансировки поиск в BST в худшем случае O(n).

</Predict>

::: interview
<details><summary>Чем рекурсия опасна в Go и когда переписывать её на явный стек?</summary>

Каждый вызов занимает кадр стека, глубина рекурсии это дополнительная память O(глубина). Стек горутины в Go растёт динамически (стартует с пары килобайт и копируется в больший при нехватке), предел 1 ГБ на 64-битных платформах. Переполнение это `fatal error: stack overflow`, его не поймать `recover`. Хвостовую рекурсию Go не оптимизирует. На явный стек переписывают, когда глубина зависит от входных данных и может быть огромной: вырожденное дерево из пользовательского ввода, обход графа на миллионы вершин, разбор глубоко вложенного JSON.

</details>
<details><summary>Чем отличаются pre-order, in-order и post-order и где каждый нужен?</summary>

Порядком обработки узла относительно поддеревьев. Pre-order (корень, левое, правое): копирование и сериализация, родитель создаётся раньше детей. In-order (левое, корень, правое): в BST выдаёт значения по возрастанию, отсюда проверка BST и k-й наименьший. Post-order (левое, правое, корень): когда ответ узла зависит от ответов детей: высота, размер, удаление, подсчёт размера каталога. Все O(n) по времени и O(h) по памяти.

</details>
<details><summary>Как обойти дерево по уровням и сколько памяти это займёт?</summary>

Очередь: кладём корень, затем по одному достаём узел и кладём его детей в конец. Чтобы разделить уровни, обрабатываем очередь порциями по её текущей длине или храним текущий и следующий уровни отдельными слайсами. Время O(n). Память O(максимальная ширина): для полного дерева это около n/2 на последнем уровне, для «палки» 1. DFS наоборот тратит O(h).

</details>
<details><summary>Почему поиск в BST O(log n) только «в среднем» и как это исправляют?</summary>

Поиск идёт по одной ветке, его стоимость O(h). У сбалансированного дерева h = O(log n), но если вставлять ключи по порядку, дерево вырождается в список и h = n. Исправляют самобалансирующимися деревьями: AVL и красно-чёрные делают повороты после вставки и удаления и гарантируют высоту O(log n). В базах данных B-деревья: много ключей в узле, очень маленькая высота, мало чтений с диска.

</details>
<details><summary>Как проверить, что двоичное дерево является деревом поиска?</summary>

Не сравнивать узел только с детьми: условие касается всех потомков. Способ 1: передавать вниз допустимый интервал (lo, hi), уходя влево, сужать hi до значения узла, вправо сужать lo. Границы лучше хранить указателями, чтобы не ломаться на значениях, равных сторожу. Способ 2: in-order обход BST строго возрастает, достаточно сравнивать каждый узел с предыдущим. Оба O(n).

</details>
<details><summary>Как найти диаметр дерева за O(n)?</summary>

Самый длинный путь через узел равен сумме высот его левого и правого поддеревьев. Одна post-order функция возвращает высоту поддерева и попутно обновляет глобальный максимум суммы высот детей. Если считать высоту отдельно в каждом узле, на вырожденном дереве будет O(n²).

</details>
<details><summary>Как найти наименьшего общего предка двух узлов в BST и в обычном дереве?</summary>

В BST: спускаемся от корня; если оба значения меньше текущего, идём влево, если оба больше, вправо, иначе текущий узел ответ. O(h), O(1) памяти. В обычном дереве: рекурсия возвращает найденный в поддереве узел (p, q или уже LCA). Если и слева, и справа вернулось не nil, текущий узел ответ; иначе пробрасываем наверх то, что не nil. O(n). Узлы сравниваем по указателям.

</details>
<details><summary>Почему в Go нет упорядоченной map и что использовать вместо TreeMap?</summary>

Встроенная map это хеш-таблица, порядок ключей в ней не определён и перемешивается при каждом обходе. Упорядоченного дерева в стандартной библиотеке нет. Если ключи по порядку нужны изредка, сортируют ключи: `slices.Sorted(maps.Keys(m))`. Если данные меняются редко, а запросов по диапазону много, держат отсортированный слайс и бинарный поиск. Если нужно и то и другое часто, берут стороннюю реализацию B-дерева или skip-list.

</details>
:::
