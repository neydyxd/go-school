# Динамика и жадные алгоритмы

Динамическое программирование (ДП) пугает названием, но идея простая: если задача распадается на подзадачи, которые **повторяются**, решай каждую один раз и запоминай ответ. Жадный алгоритм ещё проще: на каждом шаге бери то, что выглядит лучшим прямо сейчас, и не оглядывайся. Сложность обеих техник не в коде (он обычно короче, чем в задачах на графы), а в том, чтобы правильно придумать состояние и доказать, что жадность не ошибается.

С ДП ты сталкиваешься каждый день, не замечая. `git diff` и `diff` строят разницу файлов через задачу о наибольшей общей подпоследовательности строк (точнее, через близкий к ней алгоритм Майерса). Подсказки «возможно, вы имели в виду» считают расстояние редактирования, тоже ДП по двум строкам. Кеш результатов дорогих вычислений по ключу аргументов это мемоизация, только в масштабе сервиса. Жадность живёт в планировщиках: выбрать максимум непересекающихся бронирований переговорки, раздать задачи воркерам, выдать сдачу банкоматом.

В уроке: от рекурсии к мемоизации и таблице, как придумывать динамику, классика (лестница, грабитель, монеты, рюкзак 0/1, наибольшая общая и наибольшая возрастающая подпоследовательности), когда жадный алгоритм верен, а когда нет, с контрпримерами.

## От рекурсии к мемоизации и таблице

Числа Фибоначчи: `F(0) = 0`, `F(1) = 1`, `F(n) = F(n-1) + F(n-2)`. Прямая запись определения:

```go
func fib(n int) int {
	if n < 2 {
		return n
	}
	return fib(n-1) + fib(n-2)
}
```

Код верный, но дерево вызовов ветвится надвое на каждом уровне, и одни и те же значения считаются снова и снова:

```
                fib(5)
            /           \
        fib(4)          fib(3)
       /     \          /    \
   fib(3)   fib(2)  fib(2)  fib(1)
   /    \    ...     ...
fib(2) fib(1)
```

`fib(3)` вычисляется дважды, `fib(2)` трижды, и с ростом `n` это растёт экспоненциально. Я посчитал вызовы: для `fib(20)` их 21 891, для `fib(30)` уже 2 692 537, а `fib(40)` у меня считался 445 мс. Число вызовов растёт примерно в 1.6 раза на каждую единицу `n`, то есть O(φⁿ).

**Мемоизация** (сверху вниз): та же рекурсия, но перед вычислением смотрим в кеш, после вычисления кладём в кеш.

```go
func fibMemo(n int, memo map[int]int) int {
	if n < 2 {
		return n
	}
	if v, ok := memo[n]; ok {
		return v
	}
	v := fibMemo(n-1, memo) + fibMemo(n-2, memo)
	memo[n] = v
	return v
}
```

Каждое `n` считается один раз: O(n) времени и O(n) памяти (кеш плюс глубина рекурсии).

**Таблица** (снизу вверх): раз мы знаем, что `F(n)` зависит только от меньших, заполним ответы по возрастанию, без рекурсии.

```go
func fibTable(n int) int {
	if n < 2 {
		return n
	}
	dp := make([]int, n+1)
	dp[1] = 1
	for i := 2; i <= n; i++ {
		dp[i] = dp[i-1] + dp[i-2]
	}
	return dp[n]
}
```

И последний шаг, **сжатие памяти**: `dp[i]` нужны только два предыдущих значения, значит, хватит двух переменных и O(1) памяти.

```go
prev, cur := 0, 1
for i := 2; i <= n; i++ {
	prev, cur = cur, prev+cur
}
```

Это и есть весь путь, который стоит проговаривать на собесе: «рекурсия экспоненциальна, потому что подзадачи пересекаются; добавляю кеш, получаю O(n); переписываю таблицей снизу вверх; замечаю, что нужны только два последних значения, и убираю таблицу».

| Подход | Плюсы | Минусы |
|---|---|---|
| Мемоизация | Пишется из рекурсии почти механически, считает только нужные подзадачи | Глубина рекурсии, накладные расходы на вызовы и кеш |
| Таблица | Нет рекурсии, быстрая, легко сжать память | Надо понять порядок заполнения, считает все подзадачи |

::: hood Мемоизация в Go: map против слайса
Ключ мемоизации по двум индексам удобно сделать массивом `[2]int`: массивы сравнимы, значит, годятся в ключ `map`. Но хеш-таблица на каждом обращении считает хеш и ищет группу, а на миллионах состояний это заметно. Я сравнил три реализации наибольшей общей подпоследовательности для двух строк по 2000 рун (4 миллиона состояний), Go 1.27.3, Apple M-серии:

```
мемоизация, map[[2]int]int:    532 мс
мемоизация, [][]int:            36 мс
таблица снизу вверх, 2 строки:   8 мс
```

Разница в 15 раз между `map` и слайсом это цена хеширования и промахов кеша процессора. Таблица ещё быстрее: нет рекурсивных вызовов, и проход по строкам идёт подряд по памяти. Вывод: если состояния это небольшие целые числа, кеш делай слайсом; `map` бери, когда состояния разреженные или не числа (строки, подмножества). В домашке мемоизация на `map` укладывается в лимит, но с небольшим запасом.
:::

## Как придумать динамику

Пять вопросов, на которые надо ответить вслух:

1. **Состояние**: что означает `dp[i]` (или `dp[i][j]`)? Формулировка должна быть точной: «наибольшая сумма, которую можно унести из первых `i` домов», а не «ответ для `i`».
2. **Переход**: как `dp[i]` выражается через меньшие состояния? Обычно это перебор последнего решения: «взяли последний дом или нет».
3. **База**: ответы для самых маленьких состояний, `dp[0]`, пустая строка, нулевая сумма.
4. **Порядок**: в каком порядке заполнять, чтобы все нужные состояния были уже посчитаны.
5. **Ответ**: где он лежит, `dp[n]`, `dp[n][m]` или максимум по всем `dp[i]`.

Признаки задачи на ДП: «сколько способов», «минимум или максимум чего-то», «можно ли», и перебор вариантов, где решение строится шагами, а будущее зависит только от текущего состояния, а не от того, как мы в него пришли.

### Лестница

Сколькими способами подняться на `n` ступенек, шагая на 1 или 2? На ступеньку `i` можно прийти только с `i-1` или с `i-2`, поэтому `ways(i) = ways(i-1) + ways(i-2)`. Это Фибоначчи со сдвигом. Узнать знакомую рекуррентность в новой задаче половина успеха.

### Грабитель

Дома вдоль улицы, в каждом сколько-то денег, нельзя грабить два соседних. Состояние: `dp[i]` лучшая сумма из первых `i` домов. Переход по последнему дому: либо не грабим его (`dp[i-1]`), либо грабим, и тогда предыдущий пропускаем (`dp[i-2] + nums[i-1]`).

```go
func rob(nums []int) int {
	prev, cur := 0, 0 // dp[i-2], dp[i-1]
	for _, v := range nums {
		prev, cur = cur, max(cur, prev+v)
	}
	return cur
}
```

Почему не «все чётные или все нечётные дома»: на `[2 1 1 2]` выгодно взять первый и последний, пропустив два подряд. Перебор по последнему решению такие варианты учитывает сам.

## Монеты

### Минимум монет

Набрать сумму `amount` наименьшим числом монет, монет каждого номинала сколько угодно. Состояние: `dp[s]` минимум монет для суммы `s`. Переход: последней взяли какую-то монету `c`, до неё набрали `s - c` оптимально.

```go
func coinChange(coins []int, amount int) int {
	dp := make([]int, amount+1)
	for s := 1; s <= amount; s++ {
		dp[s] = amount + 1 // «бесконечность»: больше amount монет не бывает
		for _, c := range coins {
			if c <= s {
				dp[s] = min(dp[s], dp[s-c]+1)
			}
		}
	}
	if dp[amount] > amount {
		return -1
	}
	return dp[amount]
}
```

O(amount · k) по времени, где k число номиналов. «Бесконечность» здесь `amount + 1`, а не `math.MaxInt`: к `math.MaxInt` прибавляют 1, и он переполняется в отрицательное число, которое тут же становится «лучшим» ответом.

### Число способов: порядок циклов

Сколькими способами набрать сумму, если `1+2` и `2+1` это один способ? Тот же массив, но складываем вместо минимума, и решает **порядок циклов**:

```go
dp := make([]int, amount+1)
dp[0] = 1 // пустой набор
for _, c := range coins {         // снаружи монеты
	for s := c; s <= amount; s++ { // внутри суммы
		dp[s] += dp[s-c]
	}
}
```

Монеты снаружи значит «сначала решаем всё только монетами первого номинала, потом добавляем второй». Каждый набор строится в фиксированном порядке номиналов и считается один раз. Если поменять циклы местами (суммы снаружи, монеты внутри), на каждой сумме последней может стать любая монета, и посчитаются **перестановки**: для монет `{1, 2, 5}` и суммы 5 получится 9 вместо 4. Обе задачи существуют (перестановки это «лестница» с шагами из `coins`), поэтому уточни на собесе, что именно считается разными способами.

## Рюкзак 0/1

Есть предметы с весами `w[i]` и ценностями `v[i]` и рюкзак вместимостью `W`. Каждый предмет можно взять **не больше одного раза**. Максимизировать ценность. Это прототип огромного класса задач: бюджет на рекламные кампании, выбор задач в спринт по оценке и важности, разбиение множества на две части с равной суммой.

Состояние: `dp[i][c]` лучшая ценность из первых `i` предметов при вместимости `c`. Переход по предмету `i`: не берём (`dp[i-1][c]`) или берём, если влезает (`dp[i-1][c - w[i]] + v[i]`).

```go
dp := make([][]int, n+1)
for i := range dp {
	dp[i] = make([]int, W+1)
}
for i := 1; i <= n; i++ {
	for c := 0; c <= W; c++ {
		dp[i][c] = dp[i-1][c]
		if w[i-1] <= c {
			dp[i][c] = max(dp[i][c], dp[i-1][c-w[i-1]]+v[i-1])
		}
	}
}
// ответ dp[n][W]
```

O(n · W) по времени и памяти. Строка `i` зависит только от строки `i-1`, поэтому память сжимается до одного слайса длины `W+1`. Но тогда **вес надо перебирать сверху вниз**:

```go
dp := make([]int, W+1)
for i := range n {
	for c := W; c >= w[i]; c-- {
		dp[c] = max(dp[c], dp[c-w[i]]+v[i])
	}
}
```

Идя сверху вниз, мы читаем `dp[c - w[i]]`, который ещё хранит значение **предыдущей** строки, то есть без предмета `i`. Если идти снизу вверх, `dp[c - w[i]]` уже обновлён с учётом предмета `i`, и предмет может попасть в рюкзак несколько раз. Это другая задача, неограниченный рюкзак, и ровно так устроен цикл в задаче про монеты выше.

Заметь сложность: O(n · W) зависит от **значения** `W`, а не от размера входа. Если вес до 10⁹, таблица невозможна. Такие алгоритмы называют псевдополиномиальными; сама задача о рюкзаке NP-трудная, и для больших весов точного быстрого решения не известно.

## Наибольшая общая подпоследовательность (LCS)

Подпоследовательность получается вычёркиванием символов без перестановки. Для строк `a` и `b` найти длину самой длинной общей. Состояние по двум префиксам: `dp[i][j]` ответ для `a[:i]` и `b[:j]`. Переход по последним символам:

- если `a[i-1] == b[j-1]`, этот символ можно сделать последним в общей подпоследовательности: `dp[i-1][j-1] + 1`;
- иначе один из последних символов в ответ не входит: `max(dp[i-1][j], dp[i][j-1])`.

```go
func lcs(a, b string) int {
	ra, rb := []rune(a), []rune(b) // символы, а не байты
	dp := make([][]int, len(ra)+1)
	for i := range dp {
		dp[i] = make([]int, len(rb)+1)
	}
	for i := 1; i <= len(ra); i++ {
		for j := 1; j <= len(rb); j++ {
			if ra[i-1] == rb[j-1] {
				dp[i][j] = dp[i-1][j-1] + 1
			} else {
				dp[i][j] = max(dp[i-1][j], dp[i][j-1])
			}
		}
	}
	return dp[len(ra)][len(rb)]
}
```

Таблица для `"abcde"` и `"ace"`:

```
        ""  a  c  e
    ""   0  0  0  0
    a    0  1  1  1
    b    0  1  1  1
    c    0  1  2  2
    d    0  1  2  2
    e    0  1  2  3
```

O(n · m) по времени. Если нужна только длина, хватает двух строк таблицы, O(m) памяти. Если нужна сама подпоследовательность, держим полную таблицу и идём из `dp[n][m]` назад: совпали символы, значит, символ в ответе и шаг по диагонали; иначе шаг туда, где значение больше. Так устроено **восстановление ответа** в любой табличной динамике.

Близкая задача, **расстояние редактирования** (Левенштейн): минимум вставок, удалений и замен, чтобы превратить одну строку в другую. Та же таблица по префиксам, переход из трёх соседних клеток.

## Наибольшая возрастающая подпоследовательность (LIS)

Найти длину самой длинной строго возрастающей подпоследовательности. Простая динамика: `dp[i]` длина LIS, которая **заканчивается** в `nums[i]`. Перебираем, за каким элементом `j < i` она продолжается:

```go
best := 0
dp := make([]int, len(nums))
for i := range nums {
	dp[i] = 1
	for j := range i {
		if nums[j] < nums[i] {
			dp[i] = max(dp[i], dp[j]+1)
		}
	}
	best = max(best, dp[i])
}
```

O(n²). На 200 000 чисел это 2·10¹⁰ шагов, нужно быстрее. Приём O(n log n): слайс `tails`, где `tails[k]` это **наименьший возможный последний элемент** возрастающей подпоследовательности длины `k+1`. Он всегда отсортирован (более длинная подпоследовательность не может заканчиваться меньшим числом, чем лучшая более короткая). Для каждого `x` бинарным поиском находим первый хвост `>= x` и заменяем его на `x` (теперь подпоследовательность этой длины заканчивается меньшим числом, это не хуже). Если такого нет, `x` удлиняет самую длинную.

```go
var tails []int
for _, x := range nums {
	i := sort.SearchInts(tails, x) // первый индекс с tails[i] >= x
	if i == len(tails) {
		tails = append(tails, x)
	} else {
		tails[i] = x
	}
}
// ответ len(tails)
```

Важная тонкость, о которой спрашивают: `tails` в конце **не является** самой подпоследовательностью. Для `[3 4 1]` получится `tails = [1 4]`, а такой подпоследовательности во входе нет (1 стоит после 4). Длина при этом верная: 2. Чтобы восстановить саму LIS, запоминают для каждого элемента индекс предыдущего.

## Жадные алгоритмы

Жадный алгоритм на каждом шаге делает локально лучший выбор и никогда его не пересматривает. Он работает, если у задачи есть два свойства: **жадный выбор** (существует оптимальное решение, начинающееся с жадного шага) и **оптимальная подструктура** (после этого шага остаётся та же задача меньшего размера). Второе общее с ДП; первое и есть то, что надо доказывать.

Стандартный способ доказательства, **аргумент обмена**: берём любое оптимальное решение и показываем, что его первый шаг можно заменить на жадный, не ухудшив ответ.

### Интервалы: где жадность работает

Дано множество отрезков (бронирования переговорки), выбрать наибольшее число попарно непересекающихся. Жадное правило: сортировать по **концу** и брать отрезок, если он начинается не раньше конца последнего взятого.

```go
slices.SortFunc(iv, func(a, b [2]int) int { return cmp.Compare(a[1], b[1]) })
count, end := 0, math.MinInt
for _, x := range iv {
	if x[0] >= end {
		count++
		end = x[1]
	}
}
```

Почему это верно: пусть оптимальное решение начинается с отрезка `X`, а жадный взял `G`, который заканчивается раньше всех. Заменим `X` на `G`: `G` кончается не позже `X`, значит, не пересекается ни с кем из остальных выбранных. Решение осталось допустимым и того же размера, то есть существует оптимум, начинающийся с жадного шага. Дальше то же рассуждение для оставшихся отрезков. O(n log n) на сортировку.

Правила, которые кажутся разумными, но неверны: сортировка по **началу** (длинный отрезок, который начался раньше всех, перекрывает много коротких), выбор **самого короткого** (короткий может пересечь два длинных, которые между собой совместимы). На каждое такое правило есть контрпример из трёх-четырёх отрезков, и на собесе сильный ход сначала попробовать сломать своё жадное правило, а потом уже доказывать.

### Размен монет: где жадность ломается

Жадный размен: бери самую крупную монету, которая влезает. Для рублей (1, 2, 5, 10, 50, 100 и так далее) и центов США (1, 5, 10, 25) он оптимален. Но для монет `{1, 3, 4}` и суммы 6 жадный берёт `4 + 1 + 1` (три монеты), а оптимум `3 + 3` (две). Для `{1, 5, 10, 20, 25}` (так выглядел бы набор с монетой в 20 центов) на сумме 40 жадный даёт `25 + 10 + 5`, а оптимум `20 + 20`. Наборы, где жадный всегда оптимален, называют **каноническими**. Проверить набор можно перебором сумм: если контрпример существует, наименьший из них меньше суммы двух самых крупных номиналов (теорема Козена и Закса, 1994). Так что на собесе ответ на «почему не жадно?» звучит так: «для произвольных номиналов жадность неверна, вот контрпример `{1, 3, 4}`, поэтому ДП».

### Признаки жадной задачи

- Есть естественный порядок (по концу, по дедлайну, по удельной ценности), и после сортировки достаточно одного прохода.
- Решение можно «улучшить обменом» соседних элементов, пока они не встанут в жадный порядок.
- Удаётся быстро доказать или хотя бы не удаётся опровергнуть на маленьких контрпримерах.

Классические верные жадности: выбор интервалов по концу, минимум стрел для лопания шаров, прыжки по массиву (`Jump Game`), коды Хаффмана, задача о непрерывном рюкзаке (предметы можно резать: бери по убыванию цены за килограмм). Для рюкзака 0/1 та же жадность по удельной ценности **неверна**: предметы `(вес 6, цена 7)`, `(5, 5)`, `(5, 5)` и рюкзак 10: жадный возьмёт первый (7), оптимум два вторых (10).

## Разбор: числа Фибоначчи и лестница вслух

> Ты на ступеньке 0, за шаг можно подняться на 1 или 2. Сколько способов дойти до ступеньки n? Аналог: [LeetCode 70](https://leetcode.com/problems/climbing-stairs/).

**Уточняем.** Порядок шагов важен (1+2 и 2+1 разные). n от 1 до 45 на LeetCode; при n около 92 ответ перестанет помещаться в `int64`.

**Брутфорс.** Рекурсия «последний шаг был 1 или 2»: `f(n) = f(n-1) + f(n-2)`, `f(1) = 1`, `f(2) = 2`. Экспоненциально, потому что подзадачи повторяются.

**Оптимизация.** Состояние `f(i)` число способов дойти до `i`. Заполняем снизу вверх, храним два последних значения.

```go
func climbStairs(n int) int {
	prev, cur := 1, 1 // f(0), f(1)
	for i := 2; i <= n; i++ {
		prev, cur = cur, prev+cur
	}
	return cur
}
```

**Проверка**: n = 1 даёт 1, n = 2 даёт 2, n = 3 даёт 3 (1+1+1, 1+2, 2+1), n = 5 даёт 8. **Сложность** O(n) и O(1) памяти. Интервьюер может продолжить: «а если шаги из множества `steps`?» Тогда `f(i) = Σ f(i - s)` по всем `s`, O(n · |steps|), и это уже задача про перестановки монет из раздела выше.

::: trap Рекурсия без мемоизации
Плохо: определение задачи переписано рекурсией, подзадачи пересекаются.

```go
func climb(n int) int {
	if n <= 2 {
		return n
	}
	return climb(n-1) + climb(n-2) // для n = 90 не закончится никогда
}
```

Хорошо: мемоизация или таблица. Признак беды: в дереве вызовов один и тот же аргумент встречается много раз. Перед тем как писать рекурсию, спроси себя, сколько **различных** состояний у задачи: если их мало, а вызовов экспоненциально много, нужен кеш.
:::

::: trap Прямой цикл в рюкзаке 0/1
Плохо: одномерная таблица, вес снизу вверх.

```go
for i := range n {
	for c := w[i]; c <= W; c++ {
		dp[c] = max(dp[c], dp[c-w[i]]+v[i])
	}
}
// предмет (вес 2, цена 3), рюкзак 5: ответ 6, предмет взят дважды
```

Хорошо: `for c := W; c >= w[i]; c--`. Сверху вниз ячейка `dp[c-w[i]]` ещё «не видела» предмет `i`. Снизу вверх это решение неограниченного рюкзака, где каждый предмет можно брать сколько угодно раз.
:::

::: trap Порядок циклов при подсчёте способов
Плохо: суммы снаружи, монеты внутри, когда разными считаются только наборы.

```go
for s := 1; s <= amount; s++ {
	for _, c := range coins {
		if c <= s {
			dp[s] += dp[s-c]
		}
	}
}
// coins {1, 2, 5}, amount 5: 9 вместо 4
```

Хорошо: монеты снаружи, суммы внутри. Запомни: «монеты снаружи считают наборы, суммы снаружи считают последовательности».
:::

::: trap «Бесконечность» через math.MaxInt
Плохо: `dp[s] = math.MaxInt` и потом `dp[s-c] + 1`. Для недостижимой суммы `math.MaxInt + 1` переполняется в `math.MinInt`, и минимум выбирает его. Хорошо: брать «бесконечность» с запасом, которого точно хватает и который не переполняется (`amount + 1` для монет), или проверять недостижимость явно перед сложением.
:::

::: trap Байты вместо рун в строковых динамиках
Плохо: `a[i-1] == b[j-1]` по строкам на русском сравнивает байты. У «а» и «б» в UTF-8 общий первый байт `d0`, и LCS строк «аб» и «ба» по байтам выходит 2 вместо 1. Хорошо: `ra, rb := []rune(a), []rune(b)` один раз в начале и индексы по рунам. Размеры таблицы тоже считай в рунах.
:::

::: trap Жадность без доказательства
Плохо: «беру самую крупную монету», «беру самый ценный предмет», «беру отрезок, который начинается раньше». Все три звучат правдоподобно и все три неверны. Хорошо: прежде чем писать жадный код, попробуй сломать правило на 3-4 элементах (`{1, 3, 4}` и сумма 6; отрезки `[1, 100]`, `[2, 3]`, `[3, 4]`). Не сломалось, тогда ищи доказательство обменом. Не получается доказать, пиши ДП.
:::

::: interview
<details><summary>Что такое динамическое программирование и чем оно отличается от «разделяй и властвуй»?</summary>

Оба метода сводят задачу к подзадачам. В «разделяй и властвуй» (сортировка слиянием, бинарный поиск) подзадачи не пересекаются, каждая решается один раз сама собой. В ДП подзадачи повторяются, и их ответы запоминают, чтобы не считать заново. Нужна ещё оптимальная подструктура: оптимальный ответ собирается из оптимальных ответов подзадач.

</details>
<details><summary>Мемоизация или таблица: что выбрать?</summary>

Мемоизация пишется прямо из рекурсивного определения и считает только достижимые состояния, но тратит стек и время на вызовы и кеш (в Go `map` в кеше заметно медленнее слайса). Таблица снизу вверх быстрее, без рекурсии, и в ней легко сжать память до нескольких строк, но надо понять порядок заполнения, и она считает все состояния. На собесе нормально начать с мемоизации и затем переписать таблицей.

</details>
<details><summary>Как придумать решение динамикой?</summary>

Определить состояние (точный смысл dp[i] или dp[i][j]), переход (обычно перебор последнего решения), базу, порядок вычисления и где лежит ответ. Затем оценить число состояний и стоимость перехода: их произведение и есть сложность. Проверить на маленьком примере руками, заполнив таблицу.

</details>
<details><summary>Какая сложность у рюкзака 0/1 и почему её называют псевдополиномиальной?</summary>

O(n · W) по времени и O(W) по памяти с одномерной таблицей. Она полиномиальна от значения W, а не от длины его записи: при W до 10⁹ таблица невозможна, хотя вход занимает всего несколько чисел. Сама задача NP-трудна. В одномерной таблице вес перебирают сверху вниз, иначе предмет берётся многократно.

</details>
<details><summary>Как найти наибольшую возрастающую подпоследовательность за O(n log n)?</summary>

Держать слайс tails, где tails[k] наименьший последний элемент возрастающей подпоследовательности длины k+1; он отсортирован. Для каждого x бинарным поиском найти первый элемент не меньше x и заменить его (или дописать x в конец). Ответ len(tails). Сам tails не обязательно подпоследовательность входа; для восстановления хранят индексы предшественников.

</details>
<details><summary>Чем жадный алгоритм отличается от ДП и как доказать, что жадность верна?</summary>

Жадный алгоритм делает один локально лучший выбор и не пересматривает его, ДП перебирает все варианты последнего решения. Жадность верна, если существует оптимальное решение, начинающееся с жадного шага, и после шага остаётся та же задача. Доказывают аргументом обмена: в любом оптимальном решении первый шаг можно заменить жадным без потерь. Прежде чем доказывать, полезно поискать контрпример на 3-4 элементах.

</details>
<details><summary>Почему жадный размен монет иногда ошибается?</summary>

Крупная монета может «съесть» сумму так, что остаток неудобно добивать. Монеты {1, 3, 4}, сумма 6: жадный даёт 4+1+1, оптимум 3+3. Для канонических систем (рубли, центы США) жадность оптимальна. Для произвольных номиналов нужна динамика O(amount · k). Проверить, каноническая ли система, можно перебором сумм до суммы двух крупнейших номиналов.

</details>
<details><summary>Как выбрать максимум непересекающихся интервалов?</summary>

Отсортировать по правому концу и идти слева направо, беря интервал, если он начинается не раньше конца последнего взятого. O(n log n). Корректность: отрезок с самым ранним концом можно поставить первым в любое оптимальное решение, он никому не мешает больше, чем тот, кого заменил. Сортировка по началу или по длине даёт неверные ответы. Минимум удалений до непересекающихся это n минус найденный максимум.

</details>
<details><summary>Как в задаче LCS восстановить саму подпоследовательность, а не только длину?</summary>

Сохранить полную таблицу dp[i][j] и пройти назад из dp[n][m]: если символы a[i-1] и b[j-1] равны, символ в ответе, шаг по диагонали; иначе шаг в соседнюю клетку с большим значением (вверх или влево). Собранные символы развернуть. Для одной длины хватает двух строк таблицы, для восстановления нужна вся таблица O(n · m) памяти (или более хитрый алгоритм Хиршберга).

</details>
:::
