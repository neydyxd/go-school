# Бинарный поиск

Бинарный поиск знают все: возьми середину, сравни, отбрось половину. И почти все пишут его с ошибкой. Зацикливание на двух элементах, промах на единицу в границе, переполнение при вычислении середины: эти баги жили в учебниках и стандартных библиотеках десятилетиями. Поэтому на собесе бинарный поиск спрашивают не ради идеи, а ради **аккуратности**: умеешь ли ты держать инвариант и доказать, что цикл закончится и вернёт то, что нужно.

В бэкенде бинарный поиск повсюду, просто под капотом. Индекс в PostgreSQL это B-дерево, и внутри страницы ключи ищутся бинарным поиском. `git bisect` ищет коммит, сломавший тест, бинарным поиском по истории. Найти в отсортированном по времени логе все записи за интервал, найти версию конфига, действовавшую в момент `t` (по смыслу похоже на чтение старой версии в MVCC, хотя PostgreSQL выбирает версию строки проверкой видимости по снимку, а не бинпоиском), подобрать минимальный размер пула или лимит, при котором сервис укладывается в SLA: всё это бинпоиск.

В уроке разберём инварианты и два стиля границ, универсальный шаблон «первое `true`», lower и upper bound, функции `sort.Search` и `slices.BinarySearch`, поиск в повёрнутом массиве и самый мощный приём: бинарный поиск **по ответу**.

## Идея

Есть отсортированный слайс и искомое значение. Смотрим на середину: если там меньше искомого, то и всё левее середины меньше (слайс отсортирован), левую половину можно выкинуть целиком. Иначе выкидываем правую. Каждый шаг вдвое сокращает область поиска, поэтому шагов не больше `log₂ n + 1`: для миллиарда элементов это 30 сравнений вместо миллиарда.

Главное условие: **монотонность**. Не обязательно отсортированный массив, а любое свойство, которое на отрезке сначала ложно, а потом истинно (или наоборот) и больше не меняется. Отсортированность даёт такое свойство: «`nums[i] >= x`» сначала ложно, потом истинно.

## Инвариант и границы

Почти все баги бинпоиска оттого, что автор не решил, **что значат** `lo` и `hi`. Реши это до написания кода и проговори вслух, на собесе это производит хорошее впечатление.

### Стиль 1: отрезок [lo, hi] включительно

Инвариант: если ответ есть, то он лежит в `nums[lo..hi]`. Пустой отрезок это `lo > hi`, поэтому цикл идёт, пока `lo <= hi`.

```go
func search(nums []int, target int) int {
	lo, hi := 0, len(nums)-1
	for lo <= hi {
		mid := lo + (hi-lo)/2
		switch {
		case nums[mid] == target:
			return mid
		case nums[mid] < target:
			lo = mid + 1 // mid и левее точно не ответ
		default:
			hi = mid - 1 // mid и правее точно не ответ
		}
	}
	return -1
}
```

Каждая ветка **исключает** `mid` (`mid + 1`, `mid - 1`), поэтому отрезок всегда сужается и цикл закончится. Стиль удобен, когда ищем конкретное значение и можем выйти, как только нашли.

### Стиль 2: полуинтервал [lo, hi)

Здесь `[lo, hi)` это **неизвестная зона**: всё левее `lo` точно не подходит, всё начиная с `hi` точно подходит, а про `[lo, hi)` мы ещё не знаем. Цикл идёт, пока зона не пуста (`lo < hi`), а когда `lo == hi`, неизвестных не осталось, и ответ это `lo`: первый подходящий индекс (или `n`, если подходящих нет). Этот стиль естественен для Go, где срезы `s[lo:hi]` устроены так же, и именно он в стандартной библиотеке.

### Универсальный шаблон: первое true

Почти любую задачу на бинпоиск можно свести к одному вопросу: есть предикат `pred(i)`, который на `[0, n)` выглядит как `false false ... false true true ... true`. Найди первое `true` (или `n`, если `true` нет).

```go
// firstTrue возвращает первый i из [0, n), где pred(i) истинно, или n.
func firstTrue(n int, pred func(int) bool) int {
	lo, hi := 0, n // левее lo всё false, с hi всё true; hi = n значит «true нет»
	for lo < hi {
		mid := lo + (hi-lo)/2
		if pred(mid) {
			hi = mid // mid подходит, но может есть левее; mid не выкидываем
		} else {
			lo = mid + 1 // mid не подходит, и всё левее тоже
		}
	}
	return lo
}
```

Почему не зациклится: при `lo < hi` середина `mid` строго меньше `hi` (деление округляет вниз), поэтому и `hi = mid`, и `lo = mid + 1` сужают отрезок. Почему вернёт правильное: инвариант «всё левее `lo` даёт `false`, `hi` либо `n`, либо даёт `true`» сохраняется на каждом шаге, а в конце `lo == hi`.

Этот шаблон ровно то, что делает `sort.Search` из стандартной библиотеки. Выучи его один раз, и большинство задач превращаются в вопрос «какой предикат».

::: hood Как устроен sort.Search
Вот исходник из `sort/search.go` (Go 1.27), комментарии авторов сохранены:

```go
func Search(n int, f func(int) bool) int {
	// Define f(-1) == false and f(n) == true.
	// Invariant: f(i-1) == false, f(j) == true.
	i, j := 0, n
	for i < j {
		h := int(uint(i+j) >> 1) // avoid overflow when computing h
		// i ≤ h < j
		if !f(h) {
			i = h + 1 // preserves f(i-1) == false
		} else {
			j = h // preserves f(j) == true
		}
	}
	// i == j, f(i-1) == false, and f(j) (= f(i)) == true  =>  answer is i.
	return i
}
```

Тот же шаблон «первое true», а инвариант записан прямо в комментариях. Середина считается как `uint(i+j) >> 1`: сумма двух неотрицательных `int` в беззнаковом виде не переполняется, а сдвиг на 1 это деление на 2. `slices.BinarySearch` внутри устроен так же, только предикат зашит: `x[h] >= target`.
:::

### Lower bound и upper bound

Два самых нужных частных случая (названия из C++, в Go их делают через `sort.Search`):

- **lower bound**: первый индекс, где `nums[i] >= x`. Это позиция первого вхождения `x`, а если `x` нет, место, куда его вставить с сохранением порядка.
- **upper bound**: первый индекс, где `nums[i] > x`. Это позиция сразу **после** последнего вхождения.

```
nums = [1 2 2 2 5]      x = 2
lower = 1               upper = 4           количество двоек = upper - lower = 3
```

Через `firstTrue`:

```go
lower := firstTrue(len(nums), func(i int) bool { return nums[i] >= x })
upper := firstTrue(len(nums), func(i int) bool { return nums[i] > x })
```

Пара lower/upper решает целый класс задач: число вхождений, первое и последнее вхождение (домашка), сколько чисел попадает в диапазон `[a, b]` (это `upper(b) - lower(a)`), куда вставить элемент, чтобы слайс остался отсортированным.

## Бинпоиск в стандартной библиотеке

Руками писать бинпоиск в рабочем коде не надо, есть три готовых инструмента.

| Функция | Что возвращает | Когда брать |
|---|---|---|
| `sort.Search(n, f)` | первый `i` с `f(i) == true`, или `n` | любой монотонный предикат, в том числе не по слайсу |
| `slices.BinarySearch(s, x)` | lower bound и `found` | слайс упорядоченных значений (`cmp.Ordered`) |
| `slices.BinarySearchFunc(s, x, cmp)` | lower bound и `found` | слайс структур, ключ сравнивается функцией |

Пример из жизни: отсортированные по `ID` пользователи, найти по `ID`.

```go
users := []User{{3, "a"}, {8, "b"}, {15, "c"}} // отсортированы по ID
i, ok := slices.BinarySearchFunc(users, 8, func(u User, id int) int {
	return cmp.Compare(u.ID, id)
})
fmt.Println(i, ok) // 1 true
```

Обрати внимание на порядок аргументов в функции сравнения: сначала **элемент слайса**, потом **искомое**, и типы могут быть разные (здесь `User` и `int`). Для отсутствующего `ID` 9 вернётся `2 false`: позиция, куда его вставить.

Ещё пример: записи лога отсортированы по времени, нужно взять все за интервал `[from, to]`. Два вызова `sort.Search` дают границы, дальше срез без копирования.

```go
l := sort.Search(len(logs), func(i int) bool { return !logs[i].At.Before(from) }) // первый >= from
r := sort.Search(len(logs), func(i int) bool { return logs[i].At.After(to) })     // первый > to
window := logs[l:r]
```

Есть и `sort.Find(n, cmp)` (Go 1.19): как `Search`, но функция возвращает знак сравнения, а результат дополнен флагом `found`. Удобно, когда ищешь по слайсу, который не является `[]T` (например, по методу `At(i)` какой-то структуры).

## Бинпоиск без отсортированного массива

Монотонность бывает не только у отсортированного слайса. Это открывает задачи, которые на первый взгляд к бинпоиску не относятся.

### Разбор 1: первая плохая версия

> Версии продукта пронумерованы `1..n`. Начиная с какой-то версии все сборки сломаны. Есть функция `isBad(v)`, вызов которой дорог (это сборка и прогон тестов). Найди первую плохую версию за минимальное число вызовов. Аналог: [LeetCode 278](https://leetcode.com/problems/first-bad-version/).

Это буквально `git bisect`. Предикат `isBad` монотонен: `false ... false true ... true`. Ищем первое `true`.

```go
func firstBad(n int, isBad func(int) bool) int {
	lo, hi := 1, n // ответ в [lo, hi]: версия n точно плохая по условию
	for lo < hi {
		mid := lo + (hi-lo)/2
		if isBad(mid) {
			hi = mid
		} else {
			lo = mid + 1
		}
	}
	return lo
}
```

Для `n = 1000` и первой плохой 737 функция вызывает `isBad` 10 раз. Линейный перебор вызвал бы её 737 раз. Если каждая сборка идёт 5 минут, это разница между часом и двумя с половиной сутками.

### Разбор 2: пик

> Дан слайс, соседние элементы различны. Найди индекс любого **пика**: элемента, который больше соседей (за границами считаем минус бесконечность). Нужно O(log n). Аналог: [LeetCode 162](https://leetcode.com/problems/find-peak-element/).

**Уточняем.** Массив не отсортирован. Пиков может быть несколько, вернуть любой.

**Идея.** Посмотри на `mid` и его правого соседа. Если `nums[mid] < nums[mid+1]`, мы на подъёме: справа от `mid` **точно** есть пик (идём вправо, пока растёт; либо где-то начнётся спуск, и там пик, либо дойдём до конца, а последний элемент больше «минус бесконечности» за границей). Значит, левую часть вместе с `mid` можно выкинуть. Иначе мы на спуске, и пик есть в `[lo, mid]`.

```go
func findPeak(nums []int) int {
	lo, hi := 0, len(nums)-1
	for lo < hi {
		mid := lo + (hi-lo)/2 // mid < hi, значит mid+1 существует
		if nums[mid] < nums[mid+1] {
			lo = mid + 1
		} else {
			hi = mid
		}
	}
	return lo
}
```

**Проверка:** `[1 2 1 3 5 6 4]` даёт 5 (значение 6), `[1 2 3]` даёт 2, `[3 2 1]` даёт 0. Монотонного предиката по всему массиву здесь нет, но есть **гарантия, что ответ останется в выбранной половине**. Это и есть настоящее требование бинпоиска.

### Поиск в повёрнутом массиве

Отсортированный слайс циклически сдвинули: `[4 5 6 7 0 1 2]`. Это две отсортированные части с «обрывом» между ними. Задача (в домашке) найти элемент за O(log n).

Ключевое наблюдение: при любом `mid` **хотя бы одна** из половин `[lo, mid]` и `[mid, hi]` отсортирована целиком, и это видно по её концам. Если `nums[lo] <= nums[mid]`, то отсортирована левая.

```
[4 5 6 7 0 1 2],  lo=0, mid=3, hi=6
 4 <= 7: левая половина [4 5 6 7] отсортирована
 target = 5: лежит между 4 и 7, значит, идём влево
 target = 1: не лежит между 4 и 7, значит, он в правой половине
```

В отсортированной половине проверить «лежит ли `target` внутри» можно двумя сравнениями с её концами. Если лежит, идём туда, иначе в другую половину. Каждый шаг выкидывает половину, итого O(log n). Похожая задача про минимум сдвинутого массива решается сравнением `nums[mid]` с `nums[hi]`: если `nums[mid] > nums[hi]`, обрыв правее `mid`.

## Бинпоиск по ответу

Самый мощный и самый «неочевидный» приём. Признак: просят найти **минимальное** (или максимальное) значение параметра, при котором что-то возможно. И проверка «возможно ли при значении `v`» делается легко, а вот найти оптимальное `v` напрямую трудно.

Если при `v` возможно, то и при любом большем `v` возможно (монотонность). Значит, предикат `feasible(v)` выглядит как `false ... false true ... true`, и мы ищем первое `true` бинпоиском по **значениям**, а не по индексам массива.

### Разбор 3: минимальная скорость обработки

> Есть `n` пачек задач, в пачке `piles[i]` задач. Воркер за час берёт одну пачку и обрабатывает из неё до `v` задач (если в пачке меньше, остаток часа простаивает). Найди минимальную скорость `v`, при которой всё обработается за `h` часов, `h >= n`. Аналог: [LeetCode 875](https://leetcode.com/problems/koko-eating-bananas/) (там обезьяна и бананы).

**Уточняем.** Скорость целая, не меньше 1. Пачки до 10⁹, их до 10⁴.

**Брутфорс.** Перебирать `v = 1, 2, 3, ...` и для каждого считать часы: O(max · n), при пачках до 10⁹ это безнадёжно.

**Оптимизация.** Часы при скорости `v`: сумма `ceil(piles[i] / v)`. Чем больше `v`, тем меньше часов: монотонно. Ответ лежит в `[1, max(piles)]`: со скоростью `max` каждая пачка уходит за час, а `h >= n`. Ищем первое `v`, при котором часов не больше `h`.

```go
func minSpeed(piles []int, h int) int {
	lo, hi := 1, slices.Max(piles)
	for lo < hi {
		mid := lo + (hi-lo)/2
		if hoursAt(piles, mid) <= h {
			hi = mid // успеваем, пробуем медленнее
		} else {
			lo = mid + 1
		}
	}
	return lo
}

func hoursAt(piles []int, v int) int {
	total := 0
	for _, p := range piles {
		total += (p + v - 1) / v // деление с округлением вверх без float
	}
	return total
}
```

**Проверка:** `[3 6 7 11]`, `h = 8` даёт 4: при 4 часы `1+2+2+3 = 8`, при 3 уже `1+2+3+4 = 10`. `[30 11 23 4 20]`, `h = 5` даёт 30 (пачек столько же, сколько часов, каждую надо закрыть за час), а при `h = 6` уже 23.

**Сложность:** O(n · log max). Для 10⁴ пачек и `max = 10⁹` это около 3·10⁵ операций.

Шаблон «бинпоиск по ответу» в двух словах: 1) найди границы ответа `[lo, hi]`; 2) напиши `feasible(v)` за O(n) или около того; 3) убедись, что он монотонен; 4) ищи первое `true`. В домашке так решается задача про грузовик, а в жизни: минимальный размер пула, минимальная пропускная способность канала, максимальная задержка батча, при которой укладываемся в SLA.

::: trap Вечный цикл из-за округления середины
Плохо: ищем **последний** `i`, где `pred(i)` истинно, и пишем `lo = mid`.

```go
lo, hi := 0, n-1
for lo < hi {
	mid := lo + (hi-lo)/2 // при hi = lo+1 mid == lo
	if pred(mid) {
		lo = mid // lo не сдвинулся: вечный цикл
	} else {
		hi = mid - 1
	}
}
```

На двух элементах `mid == lo`, и если `pred(lo)` истинно, `lo` остаётся на месте навсегда. Хорошо: когда пишешь `lo = mid`, округляй середину **вверх**.

```go
mid := lo + (hi-lo+1)/2 // при hi = lo+1 mid == hi
```

Правило: ветка, которая не исключает `mid` (`lo = mid` или `hi = mid`), должна быть с той стороны, куда **не** округляется середина. Проверяй любой бинпоиск руками на отрезке из двух элементов. Тесты домашки этого урока прогоняют даже маленькие кейсы с таймаутом, чтобы вечный цикл давал падение, а не зависание.
:::

::: trap Переполнение при вычислении середины и в проверке
Плохо: `(lo + hi) / 2`. В Go `int` 64-битный, и для индексов слайса переполниться ему негде, но в бинпоиске по ответу границы бывают огромными, а в `int32` переполнение наступает уже на двух миллиардах.

```go
var lo, hi int32 = 1_500_000_000, 2_000_000_000
fmt.Println((lo + hi) / 2) // -397483648
```

Хорошо: `lo + (hi-lo)/2`, разность не переполняется. Вторая ловушка в самой проверке: в задаче про корень `mid*mid <= x` переполняет `int` при `mid` больше 3·10⁹. Пиши `mid <= x/mid` или ограничь `hi` заранее.

Об этой ошибке есть знаменитая статья Джошуа Блоха «Nearly All Binary Searches and Mergesorts are Broken»: баг `(low + high) / 2` девять лет прожил в `Arrays.binarySearch` из JDK.
:::

::: trap sort.Search возвращает n, а не -1
Плохо: считать результат `sort.Search` найденным элементом.

```go
i := sort.Search(len(nums), func(i int) bool { return nums[i] >= x })
return nums[i] // паника, если все меньше x (i == len(nums)); неверно, если x нет
```

Хорошо: `sort.Search` ищет **позицию**, а не значение. Проверяй и границу, и равенство, или бери `slices.BinarySearch`, который возвращает флаг.

```go
i := sort.Search(len(nums), func(i int) bool { return nums[i] >= x })
if i < len(nums) && nums[i] == x {
	return i
}
return -1
```
:::

::: trap Немонотонный предикат
Плохо: передать в `sort.Search` проверку на равенство.

```go
sort.Search(len(nums), func(i int) bool { return nums[i] == x })
```

Предикат «равно» имеет вид `false false true false false`, и бинпоиск на нём ведёт себя непредсказуемо: в зависимости от положения элемента найдёт его или вернёт `n` (задача «что выведет» ниже). Предикат обязан быть `>=` (или `>`), а равенство проверяется после.
:::

::: trap math.Sqrt вместо целочисленного корня
`int(math.Sqrt(float64(x)))` выглядит как решение, но у `float64` только 53 бита мантиссы, а у `int` 63. При `x` порядка 10¹⁸ число округляется при переводе во `float64`, и ответ уезжает на единицу: для `x = 10¹⁸ - 1` получится 10⁹ вместо 999 999 999. Целочисленный корень пиши бинпоиском, в домашке это проверяется.
:::

<details><summary>Какие условия нужны для бинарного поиска?</summary>

Не обязательно отсортированный массив, а монотонность: предикат, который на области поиска сначала ложен, потом истинен (или гарантия, что ответ остаётся в выбранной половине, как в задаче о пике). Ещё нужен доступ к середине за O(1): поэтому бинпоиск по связному списку не даёт O(log n), до середины надо дойти за O(n).

</details>
<details><summary>Как написать бинпоиск без ошибок?</summary>

Сначала решить инвариант: что означают `lo` и `hi` (ответ в `[lo, hi]` или в `[lo, hi)`), и отсюда условие цикла (`lo <= hi` или `lo < hi`). Каждая ветка должна сужать отрезок: если ветка оставляет `mid` (`hi = mid`), середина округляется в другую сторону. Середину считать как `lo + (hi-lo)/2`. Проверить руками на пустом входе, на одном и на двух элементах и на значениях за границами.

</details>
<details><summary>Что такое lower bound и upper bound?</summary>

Lower bound: первая позиция, где элемент `>= x`. Upper bound: первая позиция, где элемент `> x`. Обе возвращают `n`, если такой нет. Разность это количество `x` в слайсе, lower bound это первое вхождение или место вставки, upper bound минус один последнее вхождение. В Go: `sort.Search` с предикатом `>=` или `>`, или `slices.BinarySearch` (это lower bound плюс флаг).

</details>
<details><summary>Чем отличаются sort.Search и slices.BinarySearch?</summary>

`sort.Search(n, f)` ищет первое `i`, где `f(i)` истинно, и ничего не знает о слайсе: подходит для любого монотонного предиката, в том числе бинпоиска по ответу. Возвращает `n`, если `true` нет. `slices.BinarySearch(s, x)` (Go 1.21) работает с упорядоченным слайсом, возвращает lower bound и флаг «найдено», не нужно проверять равенство руками. `slices.BinarySearchFunc` то же для структур с функцией сравнения.

</details>
<details><summary>Как найти элемент в отсортированном, но циклически сдвинутом массиве за O(log n)?</summary>

На каждом шаге одна из половин `[lo, mid]` или `[mid, hi]` отсортирована, это видно по концам: если `nums[lo] <= nums[mid]`, то левая. Проверяем, лежит ли `target` между концами отсортированной половины. Если да, ищем там, иначе в другой половине. Каждый шаг выкидывает половину. С дубликатами (`[1 1 1 0 1]`) понять, какая половина отсортирована, иногда нельзя, и худший случай деградирует до O(n).

</details>
<details><summary>Что такое бинарный поиск по ответу? Пример.</summary>

Когда нужно найти минимальное (максимальное) значение параметра, при котором выполнимо условие, а проверка «выполнимо ли при `v`» простая и монотонна по `v`. Ищем первое `v` с `feasible(v) == true` в диапазоне возможных ответов. Пример: минимальная грузоподъёмность, чтобы отвезти посылки за `d` дней: проверка жадная за O(n), диапазон `[max, sum]`, итого O(n log sum). Другие: минимальная скорость обработки, корень числа, минимальный размер пула под SLA.

</details>
<details><summary>Почему (lo+hi)/2 может быть ошибкой и как правильно?</summary>

Сумма двух больших индексов переполняет целое: в Java это знаменитый баг стандартной библиотеки, в Go `int` 64-битный и на индексах слайса не переполнится, но в `int32` и в бинпоиске по ответу с огромными границами переполнится. Go не паникует, значение заворачивается в отрицательное. Правильно: `lo + (hi-lo)/2`, или как в стандартной библиотеке `int(uint(lo+hi) >> 1)`.

</details>
<details><summary>Сколько шагов делает бинарный поиск по миллиарду элементов и почему это важно для БД?</summary>

`ceil(log₂(10⁹))` это 30 шагов. Для БД важнее другое: на диске дорог каждый переход по странице, поэтому индексы делают B-деревьями с сотнями ключей в узле. Высота дерева 3-4, то есть 3-4 чтения страниц, а внутри страницы ключ ищется бинарным поиском в памяти. Так бинарный поиск сочетается с большим ветвлением.

</details>
:::
