# Big-O и как решать задачу вслух

Алгоритмическая секция есть почти в каждом собеседовании на бэкендера: в крупных компаниях это отдельный этап, в небольших пара задач в середине технического интервью. Проверяют не знание редких алгоритмов, а три навыка: оценить, сколько стоит код, найти решение быстрее перебора и спокойно довести его до работающего кода, рассуждая вслух.

В работе это тоже нужно каждый день, просто выглядит иначе. Обработчик, который для каждого из 10 000 заказов ищет клиента линейным поиском по слайсу клиентов, делает 10⁸ сравнений и тормозит под нагрузкой. Тот же код с `map` делает 10⁴ операций. Ревьюер, который видит `s += ...` в цикле по миллиону строк, просит переписать на `strings.Builder`. Это и есть Big-O, только без формул.

Этот урок открывает параллельный трек по алгоритмам. Здесь две темы: язык оценки сложности и сценарий, по которому решают задачу на собесе. В конце разберём, сколько стоят встроенные операции Go: `append`, `map`, конкатенация строк. Темп трека: 2-3 задачи в неделю. У каждой задачи домашки есть аналог на LeetCode, там можно прорешать её ещё раз и посмотреть чужие решения.

## Что такое Big-O

Big-O описывает, **как растёт** время работы (или память) при росте размера входа `n`. Не сколько миллисекунд, а форму кривой: удвоили вход, время удвоилось, учетверилось или почти не изменилось.

Посчитаем элементарные операции в поиске максимума:

```go
func maxOf(nums []int) int {
	best := nums[0]             // 1 операция
	for _, x := range nums[1:] { // n-1 итераций
		if x > best {            // сравнение на каждой
			best = x             // присваивание иногда
		}
	}
	return best
}
```

Получается что-то вроде `2n + 1` операций, но точное число зависит от процессора, компилятора и того, что считать «операцией». Поэтому константы и младшие слагаемые выбрасывают и говорят: время **O(n)**, линейное. Это честно, потому что на больших `n` форма кривой важнее множителя: алгоритм `100n` обгонит `n²` уже при `n > 100`.

Формально: `f(n) = O(g(n))`, если существуют константа `c > 0` и порог `n₀`, начиная с которого `f(n) ≤ c·g(n)`. То есть O это **верхняя граница** с точностью до множителя. Рядом живут Ω (нижняя граница) и Θ (точная оценка, и сверху, и снизу). На собесе почти всегда говорят «O», имея в виду точную оценку: «линейный поиск работает за O(n)». Сказать «за O(n³)» формально тоже верно, но бесполезно.

### Классы сложности, которые надо узнавать

| Класс | Название | Типичный пример | При n = 10⁶ |
|---|---|---|---|
| O(1) | константа | `nums[i]`, `len(s)`, чтение из `map` | мгновенно |
| O(log n) | логарифм | бинарный поиск, цикл с `i *= 2` | ~20 шагов |
| O(n) | линейная | один проход по слайсу | 10⁶ шагов |
| O(n log n) | линейно-логарифмическая | сортировка | ~2·10⁷ |
| O(n²) | квадратичная | два вложенных цикла по всем парам | 10¹², не дождёшься |
| O(2ⁿ) | экспонента | перебор всех подмножеств | только n до 20-25 |
| O(n!) | факториал | перебор всех перестановок | только n до 10-11 |

Логарифм появляется, когда на каждом шаге задача уменьшается в разы: делим пополам, умножаем счётчик на два. Основание логарифма в O не пишут: `log₂ n` и `log₁₀ n` отличаются постоянным множителем, а множители мы выбрасываем.

```go
n, cnt := 100, 0
for i := 1; i < n; i *= 2 {
	cnt++
}
fmt.Println(cnt)
```

<Predict :options="['100', '7', '50', '6']" :correct="1">

`i` пробегает 1, 2, 4, 8, 16, 32, 64: семь значений, следующее 128 уже не меньше 100. Это `⌈log₂ 100⌉ = 7`. Удвоение `n` добавит всего одну итерацию, вот что значит O(log n).

</Predict>

### Правила подсчёта

1. **Константы долой.** `3n + 5` это O(n). Два прохода по слайсу подряд это всё ещё O(n), а не O(2n).
2. **Младшие слагаемые долой.** `n² + n` это O(n²).
3. **Последовательные куски складываются.** Сортировка, затем проход: `O(n log n + n) = O(n log n)`.
4. **Вложенные циклы перемножаются.** Цикл по `n` внутри цикла по `n`: O(n²). Но смотри, сколько раз **на самом деле** выполняется внутреннее тело, а не сколько циклов написано (пример ниже).
5. **Разные входы, разные буквы.** Цикл по `a` внутри цикла по `b` это `O(len(a)·len(b))`, пишут `O(n·m)`. Свести к O(n²) нельзя: если `m` маленькое, это почти линейно.

```go
n, cnt := 4, 0
for i := 0; i < n; i++ {
	for j := i; j < n; j++ {
		cnt++
	}
}
fmt.Println(cnt)
```

<Predict :options="['16', '10', '4', '6']" :correct="1">

Внутренний цикл делает 4, 3, 2, 1 итерацию: всего 10 = `n(n+1)/2`. Это половина от `n²`, но половина это константа, поэтому сложность всё равно O(n²). Типичная ловушка собеса: «внутренний цикл же начинается с `i`, значит быстрее». Быстрее в два раза, но не асимптотически.

</Predict>

### Память

Пространственная сложность считается так же, но обычно имеют в виду **дополнительную** память: сколько алгоритм выделяет сверх входа. Проход с парой переменных: O(1) дополнительной памяти. Копия слайса или `map` на все элементы: O(n). Если функция возвращает новый слайс длины `n`, ответ тоже занимает O(n); на собесе уточни, считаешь ли ты его. Рекурсия тратит память на стек: глубина `d` означает O(d) памяти, даже если ничего не выделяешь явно.

Частый размен: память на время. Решение за O(n²) без памяти против решения за O(n) с `map` на O(n) элементов. На собесе стоит назвать оба и сказать, что выбираешь.

### Лучший, средний, худший и амортизированный случаи

- **Худший случай**: гарантия. Если не сказано иное, на собесе говорят о нём.
- **Средний случай**: ожидание на «обычных» данных. Так оценивают хеш-таблицы: O(1) в среднем, хотя при неудачных коллизиях поиск деградирует.
- **Лучший случай** почти бесполезен: линейный поиск находит элемент с первой попытки, но гарантий это не даёт.
- **Амортизированная сложность**: средняя стоимость операции в длинной последовательности операций. Одна операция иногда дорогая, но редко, и в сумме на `n` операций выходит O(n). Классика: `append`, разберём ниже.

## Ограничения подсказывают нужную асимптотику

В задачах на собесе и на LeetCode почти всегда указаны ограничения: `1 ≤ n ≤ 10⁵`. Это прямая подсказка, какое решение от тебя ждут. Ориентир: обычный компьютер выполняет порядка 10⁸-10⁹ простых операций в секунду, а лимит времени у задач около секунды.

| Ограничение на n | Приемлемая сложность |
|---|---|
| до 10-12 | O(n!), перебор перестановок |
| до 20-25 | O(2ⁿ), перебор подмножеств |
| до 500 | O(n³) |
| до 5 000 | O(n²) |
| до 10⁶ | O(n log n) или O(n) |
| больше 10⁶, до 10⁹ и выше | O(n) по входу, O(log n) или O(1) по значению |

Видишь `n ≤ 10⁵` и придумал два вложенных цикла: это 10¹⁰ операций, решение не пройдёт. Значит, ищи сортировку, хеш-таблицу, два указателя или окно. Тесты домашки в этом треке устроены так же: в каждой задаче есть «большой» вход с таймаутом в 3 секунды (под `-race` в 5 раз больше, детектор гонок замедляет код), на котором решение с неверной асимптотикой падает.

## Как решать задачу на собесе вслух

Интервьюер оценивает не только итоговый код, но и ход мысли. Молчаливые 20 минут и затем идеальный код оцениваются хуже, чем рассуждения вслух с одной исправленной ошибкой. Вот сценарий, который работает почти всегда.

1. **Уточни условие.** Повтори задачу своими словами. Спроси про размер входа, диапазон значений (могут ли быть отрицательные, может ли сумма переполнить `int`), пустой вход, дубликаты, отсортирован ли вход, можно ли его менять, строки в ASCII или в Unicode. Каждый ответ меняет решение.
2. **Разбери пример руками.** Возьми пример из условия и придумай свой, включая крайний случай. Часто на этом шаге видно закономерность.
3. **Назови брутфорс и его сложность.** «В лоб: перебрать все пары, это O(n²) по времени и O(1) по памяти». Даже если сразу видишь оптимум, этот шаг показывает, что ты понимаешь цену решений, и даёт запасной вариант.
4. **Оптимизируй.** Спроси себя: какую работу брутфорс повторяет? Что можно запомнить (`map`, префиксные суммы)? Поможет ли сортировка? Есть ли монотонность (два указателя, окно, бинарный поиск)? Проговори идею и оценку **до** кода и дождись кивка.
5. **Напиши код.** Понятные имена, без хитростей. Проговаривай инварианты: «`l` указывает на начало окна, в окне нет повторов».
6. **Протестируй руками.** Прогони код на примере построчно, затем на крайних случаях: пустой вход, один элемент, все одинаковые, ответ в начале и в конце.
7. **Назови итоговую сложность** по времени и памяти и что можно улучшить.

### Разбор 1: хорошие пары

> Дан слайс чисел. Пара индексов `(i, j)` хорошая, если `i < j` и `nums[i] == nums[j]`. Посчитай число хороших пар. Аналог: [LeetCode 1512](https://leetcode.com/problems/number-of-good-pairs/).

**Уточняем.** «Какой размер слайса? Может ли он быть пустым? Какие значения?» Допустим, `n` до 10⁵, числа любые `int`, пустой слайс возможен, ответ для него 0.

**Пример.** `[1 2 3 1 1 3]`: единицы стоят на позициях 0, 3, 4 и дают пары (0,3), (0,4), (3,4); тройки на 2 и 5 дают (2,5). Итого 4.

**Брутфорс.** Перебрать все пары `i < j`:

```go
func numIdenticalPairsBrute(nums []int) int {
	count := 0
	for i := 0; i < len(nums); i++ {
		for j := i + 1; j < len(nums); j++ {
			if nums[i] == nums[j] {
				count++
			}
		}
	}
	return count
}
```

O(n²) по времени, O(1) по памяти. При `n = 10⁵` это 5·10⁹ сравнений: не пройдёт.

**Оптимизируем.** Что брутфорс делает лишнего? Для каждого `j` он заново просматривает все предыдущие элементы, чтобы посчитать, сколько среди них равных `nums[j]`. Это число можно **помнить**: заведём `map` «значение → сколько раз уже встречали». Тогда `nums[j]` образует пары ровно с `seen[nums[j]]` предыдущими.

```go
func numIdenticalPairs(nums []int) int {
	seen := make(map[int]int, len(nums)) // число -> сколько раз уже встречали
	count := 0
	for _, x := range nums {
		count += seen[x] // x образует пару с каждым предыдущим x
		seen[x]++
	}
	return count
}
```

**Тестируем руками** на `[1 2 3 1 1 3]`: `count` растёт на 0, 0, 0, 1 (вторая единица), 2 (третья единица), 1 (вторая тройка). Итого 4. Пустой слайс: цикл не выполнится, 0. Все одинаковые `[1 1 1 1]`: 0+1+2+3 = 6 = `4·3/2`, верно.

**Сложность:** O(n) по времени в среднем (каждая операция `map` в среднем O(1)), O(n) по памяти в худшем случае, когда все числа разные. Дополнительно можно сказать: если значения маленькие (например, от 1 до 100), вместо `map` подойдёт массив `[101]int`, это быстрее на константу.

### Разбор 2: пересечение двух массивов

> Даны два слайса `a` и `b`. Верни различные числа, которые есть в обоих. Аналог: [LeetCode 349](https://leetcode.com/problems/intersection-of-two-arrays/).

Здесь важно, что входов **два**, и сложность пишется через `n = len(a)` и `m = len(b)`.

- **Брутфорс**: для каждого элемента `b` искать его в `a` линейно. O(n·m) по времени.
- **Сортировка**: отсортировать оба и пройти двумя указателями. O(n log n + m log m) по времени, O(1) дополнительной памяти, если сортировать на месте (и если вход менять можно, это надо уточнить).
- **Хеш-множество**: сложить `a` в `map`, пройти по `b`. O(n + m) в среднем, O(n) памяти.

```go
func intersection(a, b []int) []int {
	inA := make(map[int]bool, len(a))
	for _, x := range a {
		inA[x] = true
	}
	var res []int
	for _, x := range b {
		if inA[x] {
			res = append(res, x)
			inA[x] = false // чтобы не добавить x второй раз
		}
	}
	return res
}
```

Какое решение лучше, зависит от условий: если память ограничена или входы уже отсортированы, выигрывает второе. Сказать это вслух и есть «показать мышление».

### Разбор 3: оцени фрагмент

Интервьюер показывает код и спрашивает сложность. Главное правило: **смотри, сколько раз выполняется тело, и что стоит каждая строка внутри**.

```go
// A
for _, w := range words {
	if slices.Contains(seen, w) { // линейный поиск по слайсу
		continue
	}
	seen = append(seen, w)
}
```

Цикл один, но `slices.Contains` внутри проходит по слайсу целиком. Итого O(n²) в худшем случае (все слова разные). Замена `seen` на `map[string]bool` даёт O(n).

```go
// B
j := 0
for i := 0; i < n; i++ {
	for j < n && nums[j] < nums[i]+k {
		j++
	}
	// ...
}
```

Два вложенных цикла, но `j` **никогда не уменьшается**: за всю работу он пройдёт от 0 до `n` один раз. Суммарно внутреннее тело выполнится не больше `n` раз, итого O(n). Это идея двух указателей, она ждёт тебя в следующем уроке.

```go
// C
for len(nums) > 0 {
	nums = nums[1:]
}
```

Срез `nums[1:]` не копирует данные, это O(1). Весь цикл O(n). А вот `nums = append(nums[:0], nums[1:]...)` копирует хвост, и тот же цикл стал бы O(n²).

## Big-O в Go: сколько стоят встроенные операции

Оценивать свой код невозможно, если не знаешь цену строительных блоков. Шпаргалка для Go 1.27:

| Операция | Стоимость |
|---|---|
| `len(s)`, `cap(s)`, `s[i]`, `s[a:b]` для слайса | O(1), срез не копирует данные |
| `append(s, x)` | O(1) амортизированно, O(n) в худшем случае |
| `copy(dst, src)`, `make([]T, n)` | O(n): копирование и обнуление |
| `slices.Contains`, `slices.Index` | O(n) |
| `slices.Insert`, `slices.Delete` в середине | O(n): сдвиг хвоста |
| `slices.Sort`, `sort.Ints` | O(n log n) |
| `m[k]`, `m[k] = v`, `delete(m, k)` | O(1) в среднем |
| `for k, v := range m` | O(n) и больше: проход по внутренней таблице |
| `len(str)`, `str[i]` (байт), `str[a:b]` | O(1), подстрока не копирует данные |
| `a + b` для строк | O(len(a) + len(b)): новая строка |
| `[]rune(str)`, `[]byte(str)`, `string(bs)` | O(n): выделение и копирование |
| `utf8.RuneCountInString(str)` | O(n): надо пройти все байты |
| `strings.Contains`, `strings.Index`, `strings.Count` | не O(1): внутри цикл по строке |

`slices.Sort` и `slices.Contains` это обобщённые функции: они работают со слайсами разных типов. Как такие функции пишутся, разберём в уроке про дженерики, пользоваться ими можно уже сейчас.

### append: почему O(1), если иногда копирует всё

Пока в слайсе есть свободная ёмкость (`len < cap`), `append` просто пишет элемент в следующую ячейку: O(1). Когда ёмкость кончилась, рантайм выделяет новый массив большего размера и **копирует все элементы**: O(n). Звучит плохо, но новая ёмкость больше старой **в разы**, а не на единицу.

Представь, что ёмкость удваивается. До `n` элементов копирования были на размерах 1, 2, 4, ..., n/2, их сумма меньше `n`. Значит, на `n` вызовов `append` приходится меньше `n` копирований элементов, в среднем меньше одного на вызов. Это и есть амортизированное O(1). Если бы ёмкость росла на фиксированную величину (скажем, +10), копирований было бы около `n²/20`, и `append` стал бы амортизированно O(n).

::: hood Как растёт ёмкость в Go 1.27
Новую ёмкость считает функция `nextslicecap` в `runtime/slice.go`. Если нужно больше, чем удвоенная старая ёмкость, берётся ровно нужная. Иначе пока старая ёмкость меньше 256, она удваивается, а дальше растёт по формуле `newcap += (newcap + 3*256) / 4`: множитель плавно уменьшается от 2 к 1.25. Затем размер округляется вверх до ближайшего класса размеров аллокатора, поэтому большие числа «неровные». Слайс `[]int` в глобальной переменной (он в куче с первого `append`) при добавлении по одному элементу у меня рос так:

```
1 2 4 8 16 32 64 128 256 512 848 1280 1792 2560 3408
```

Например, из 512 формула даёт 512 + (512 + 768) / 4 = 832 элемента, это 6656 байт, ближайший класс размеров 6784 байта, отсюда 848.

С маленькими ёмкостями всё сложнее, и заучивать их не надо. В последних версиях Go (у меня 1.27.3) компилятор держит первые элементы растущего через `append` слайса в 32-байтовом буфере на стеке. Пока данные помещаются в буфер, рантайм (`growsliceBuf` в `runtime/slice.go`) поднимает ёмкость не вдвое, а до следующего класса размеров: 8, 16, 24, 32 байта, то есть 1, 2, 3, 4 элемента. Поэтому тот же цикл в локальной переменной, которую функция потом возвращает через `return`, даёт `1 2 3 4 8 16 ...`, а слайс, который вообще не покидает функцию, сразу получает весь буфер: первый `append` даёт ёмкость 4, дальше `4 8 16 ...`. Это деталь реализации, она меняется от версии к версии. Стабильно другое: рост **геометрический**, поэтому `append` амортизированно O(1).
:::

Если итоговый размер известен заранее, выдели память сразу: `make([]int, 0, n)`. Асимптотика та же, но не будет промежуточных копирований и лишнего мусора для сборщика.

### map: O(1) в среднем

Чтение, запись и удаление в `map` в среднем стоят O(1): по хешу ключа рантайм сразу прыгает в нужное место таблицы, а не перебирает элементы. «В среднем», потому что разные ключи могут попасть в одно место (коллизия), и тогда приходится проверять несколько кандидатов. Подробно устройство разберём в уроке про хеш-таблицы, здесь важны три вывода для оценки сложности:

- поиск в `map` дешевле поиска в слайсе: O(1) против O(n), поэтому `map` главный инструмент оптимизации брутфорса;
- константа у `map` заметно больше, чем у индексации слайса: хеширование, сравнение ключа, промахи кеша. Если ключи это маленькие целые числа, массив или слайс-счётчик быстрее;
- обход `map` идёт по внутренней таблице, и порядок обхода специально случайный. Полагаться на порядок нельзя.

::: hood Почему O(1) не превращается в O(n) в Go
Начиная с Go 1.24 `map` реализована как Swiss Table: слоты сгруппированы по 8, у каждой группы есть контрольное слово с 7 младшими битами хеша каждого слота, и одна операция сравнивает сразу все 8 кандидатов. Таблица растёт, когда заполнена в среднем на 7/8. У каждой `map` свой случайный seed хеш-функции, поэтому подобрать ключи, которые нарочно сталкиваются (атака hash flooding), снаружи нельзя. Чтобы рост не вызывал долгих пауз, большая `map` состоит из нескольких таблиц до 1024 слотов, и при росте перестраивается только одна из них. Обратная сторона: при удалении элементов таблица не сжимается (кода сжатия в `internal/runtime/maps` нет, даже `clear(m)` не уменьшает каталог таблиц, там стоит `TODO: shrink directory?`), так что `map`, которую раздули до миллиона элементов и почистили, продолжает занимать память.
:::

### Строки: конкатенация в цикле

Строка в Go неизменяема. `s += "ab"` не дописывает в конец, а создаёт **новую** строку длины `len(s)+2` и копирует в неё старую. В цикле на `n` итераций копируется `2 + 4 + 6 + ... + 2n` байт, это O(n²).

```go
s := ""
for range n {
	s += "ab" // каждый раз копирует всю накопленную строку
}
```

Я замерил на Go 1.27.3: при `n = 10 000` такой цикл занял около 12 мс, при `n = 100 000` около 720 мс. Данных в 10 раз больше, время почти в 60 раз больше: вот как выглядит квадрат на практике. `strings.Builder` на тех же данных: 42 мкс и 375 мкс, примерно в 9 раз, то есть линейно.

`strings.Builder` внутри держит `[]byte` и растит его как `append`, геометрически, поэтому каждая запись амортизированно стоит O(длины куска). Метод `String()` не копирует буфер.

```go
var b strings.Builder
b.Grow(2 * n) // необязательно: выделить память сразу
for range n {
	b.WriteString("ab")
}
s := b.String()
```

Если части уже лежат в слайсе, ещё проще `strings.Join(parts, sep)`: он сам считает итоговую длину и копирует один раз.

::: trap Конкатенация строк в цикле
Плохо: O(n²) по времени и тысячи выброшенных промежуточных строк.

```go
func joinIDs(ids []int) string {
	res := ""
	for i, id := range ids {
		if i > 0 {
			res += ","
		}
		res += strconv.Itoa(id)
	}
	return res
}
```

Хорошо: O(n), одна растущая область памяти.

```go
func joinIDs(ids []int) string {
	var b strings.Builder
	for i, id := range ids {
		if i > 0 {
			b.WriteByte(',')
		}
		b.WriteString(strconv.Itoa(id))
	}
	return b.String()
}
```

Пара `+` вне цикла это нормально и читается лучше Builder. Проблема только в накоплении внутри цикла.
:::

::: trap Скрытый линейный поиск внутри цикла
Цикл один, а сложность квадратичная: `slices.Contains` проходит весь слайс.

```go
// Плохо: O(n·m)
for _, order := range orders {
	if slices.Contains(blockedUsers, order.UserID) {
		reject(order)
	}
}
```

```go
// Хорошо: O(n + m) в среднем
blocked := make(map[int]bool, len(blockedUsers))
for _, id := range blockedUsers {
	blocked[id] = true
}
for _, order := range orders {
	if blocked[order.UserID] {
		reject(order)
	}
}
```

То же касается `strings.Contains`, `strings.Count`, `slices.Index` и удаления из середины слайса: у всех внутри цикл.
:::

::: trap Байты против символов
`len(s)` возвращает число **байтов**, а не символов. Кириллическая буква в UTF-8 занимает 2 байта, эмодзи 4. Индексация `s[i]` даёт байт, а не символ. Если в задаче про строки сказано «символ», уточни, ASCII ли это. Если нет, работай с рунами: `for _, r := range s` декодирует символы по одному, а `[]rune(s)` даёт слайс символов за O(n) времени и памяти.
:::

Поэтому два вложенных цикла не всегда означают O(n²): считай, сколько раз реально выполняется тело.

<details><summary>Что такое Big-O и почему константы отбрасывают?</summary>

Big-O описывает, как растёт время (или память) алгоритма при росте входа, с точностью до постоянного множителя: `f(n) = O(g(n))`, если с некоторого `n₀` выполняется `f(n) ≤ c·g(n)`. Константы отбрасывают, потому что они зависят от железа, компилятора и того, что считать операцией, а на больших входах решает форма кривой: `100n` меньше `n²` уже при `n > 100`. Константы важны на практике, но сравнивают их бенчмарком, а не нотацией.

</details>
<details><summary>Чем отличаются худший, средний и амортизированный случаи? Приведи пример из Go.</summary>

Худший случай: гарантия на любом входе. Средний: ожидание на типичных данных, так оценивают `map` (O(1) в среднем, хотя при массовых коллизиях поиск медленнее). Амортизированный: средняя цена операции в длинной последовательности, где редкие дорогие операции «размазываются» по дешёвым. Пример: `append` обычно O(1), иногда O(n) из-за копирования в новый массив, но ёмкость растёт геометрически, поэтому `n` вызовов стоят O(n), то есть O(1) на вызов.

</details>
<details><summary>Почему append амортизированно O(1), а не O(n)?</summary>

При нехватке ёмкости рантайм выделяет массив в несколько раз больше (для маленьких слайсов вдвое, для больших примерно в 1.25 раза) и копирует элементы. При геометрическом росте суммарное число скопированных элементов за `n` добавлений ограничено `c·n`. Если бы ёмкость росла на константу, копирований было бы порядка `n²`. Практический вывод: если размер известен, делай `make([]T, 0, n)`, это убирает промежуточные копии.

</details>
<details><summary>Какая сложность у операций с map в Go? Бывает ли хуже?</summary>

Чтение, запись и удаление: O(1) в среднем, обход: O(n) и больше, потому что идёт по всей внутренней таблице, а она не сжимается после удалений. Теоретический худший случай поиска O(n), если все ключи попали в одно место, но в Go у каждой `map` случайный seed хеш-функции, поэтому специально подобрать такие ключи снаружи нельзя. С Go 1.24 внутри Swiss Table: группы по 8 слотов с контрольным словом из 7-битных частей хеша.

</details>
<details><summary>Оцени сложность: в цикле по n строкам выполняется s += line. Как исправить?</summary>

Строки неизменяемы, каждое `+=` создаёт новую строку и копирует всю накопленную, поэтому суммарно O(L·n) или O(L²) от общей длины, по сути квадрат. Исправление: `strings.Builder` (внутри растущий `[]byte`, амортизированно линейно) или `strings.Join`, если части уже в слайсе. Можно ещё вызвать `b.Grow(total)`, если итоговая длина известна.

</details>
<details><summary>В условии n ≤ 10⁵. Какое решение от тебя ждут?</summary>

O(n log n) или O(n): 10⁵·17 ≈ 2·10⁶ или 10⁵ операций укладываются в лимит с запасом, а O(n²) это 10¹⁰, слишком много при ориентире 10⁸-10⁹ простых операций в секунду. Значит, нужны сортировка, хеш-таблица, два указателя, окно или бинарный поиск, а не перебор пар.

</details>
<details><summary>Почему в O(log n) не указывают основание логарифма?</summary>

`log_a n = log_b n / log_b a`, то есть логарифмы по разным основаниям отличаются постоянным множителем, а множители в O отбрасываются. O(log₂ n) и O(log₁₀ n) это один класс.

</details>
<details><summary>Как ты действуешь, если на собесе не видишь оптимального решения?</summary>

Уточняю условие и ограничения, разбираю пример руками, называю брутфорс с оценкой и пишу его, если время поджимает: работающее медленное решение лучше пустого листа. Затем ищу, какую работу брутфорс повторяет: можно ли запомнить промежуточные результаты (`map`, префиксные суммы), помогает ли сортировка, есть ли монотонность для двух указателей или окна. Рассуждаю вслух: интервьюер часто подсказывает, если видит направление мысли.

</details>
<details><summary>Сколько стоит slices.Sort и стабильна ли сортировка?</summary>

O(n log n) сравнений. `slices.SortFunc` и `sort.Sort` не гарантируют стабильность: элементы, равные с точки зрения функции сравнения, могут поменяться местами. Если важен порядок равных (например, сортировка заказов по дате с сохранением исходного порядка внутри дня), нужен `slices.SortStableFunc` или `sort.Stable`. Отдельно стоит помнить, что сортировка входа сама по себе O(n log n), и решение «сортируем, потом линейный проход» не бывает быстрее O(n log n).

</details>
