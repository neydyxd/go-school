# Сортировки

В рабочем коде сортировку не пишут: вызывают `slices.Sort` или `slices.SortFunc` и идут дальше. Зачем тогда урок? Затем, что на собесе спросят «как работает быстрая сортировка и какой у неё худший случай», «что такое устойчивость», «чем `sort.Slice` хуже `slices.SortFunc`», и попросят отсортировать структуры по трём ключам без ошибки в компараторе. А ещё сортировка это первый шаг огромного числа задач: после неё дубли стоят рядом, пересекающиеся интервалы соседствуют, а бинпоиск и два указателя становятся возможны.

В бэкенде сортировки работают у тебя под ногами. `ORDER BY` в PostgreSQL сортирует в памяти быстрой сортировкой, а если данные не влезают в `work_mem`, переходит на внешнюю сортировку слиянием с временными файлами на диске. В выводе `EXPLAIN ANALYZE` это видно прямо строкой `Sort Method: quicksort` или `Sort Method: external merge`, а для `ORDER BY ... LIMIT` бывает `top-N heapsort`. Понимая алгоритмы, ты понимаешь, почему запрос внезапно стал писать на диск.

В уроке разберём быструю сортировку (выбор опорного и худший случай), сортировку слиянием, сортировку подсчётом, устойчивость, что внутри `slices.Sort` и как правильно писать компараторы в Go.

## Сколько стоит сортировка

Любая сортировка, которая только **сравнивает** элементы, в худшем случае делает не меньше `log₂(n!)` сравнений, а это порядка `n log n`. Интуиция: перестановок `n!`, каждое сравнение отвечает «да/нет» и в лучшем случае делит оставшиеся варианты пополам. Поэтому O(n log n) это предел для сравнений, и быстрее можно только если пользоваться структурой ключей (сортировка подсчётом, поразрядная).

| Алгоритм | Среднее | Худшее | Память | Устойчива |
|---|---|---|---|---|
| Вставками | O(n²) | O(n²) | O(1) | да |
| Быстрая (quick sort) | O(n log n) | O(n²) | O(log n) стек | нет |
| Слиянием (merge sort) | O(n log n) | O(n log n) | O(n) | да |
| Пирамидальная (heap sort) | O(n log n) | O(n log n) | O(1) | нет |
| Подсчётом (counting sort) | O(n + k) | O(n + k) | O(n + k) | да (в правильной реализации) |
| pdqsort (`slices.Sort`) | O(n log n) | O(n log n) | O(log n) | нет |

### Вставками: медленная, но нужная

Сортировка вставками берёт очередной элемент и сдвигает его влево, пока он меньше соседа. O(n²) в худшем случае, но на **маленьких** и **почти отсортированных** массивах она быстрее всех: никаких рекурсий и лишних копирований, а на отсортированном входе это O(n). Поэтому все промышленные сортировки, включая Go, на кусках до десятка элементов переключаются именно на вставки.

```go
for i := 1; i < len(a); i++ {
	for j := i; j > 0 && a[j] < a[j-1]; j-- {
		a[j], a[j-1] = a[j-1], a[j]
	}
}
```

## Быстрая сортировка

Идея «разделяй и властвуй»: выбрать **опорный** элемент (pivot), переставить массив так, чтобы слева от некой границы были элементы меньше опорного, справа больше (это **разбиение**, partition), и рекурсивно отсортировать обе части. Слияния нет: после разбиения части уже на своих местах относительно друг друга.

### Разбиение Ломуто

Самое простое для запоминания. Опорный это последний элемент. Указатель `i` отмечает границу «меньших», `j` идёт по массиву:

```go
func quickSort(a []int) {
	if len(a) < 2 {
		return
	}
	p, i := a[len(a)-1], 0 // опорный: последний
	for j := range len(a) - 1 {
		if a[j] < p {
			a[i], a[j] = a[j], a[i]
			i++
		}
	}
	a[i], a[len(a)-1] = a[len(a)-1], a[i] // опорный на своё место
	quickSort(a[:i])
	quickSort(a[i+1:])
}
```

Заметь, как удобно в Go передавать подслайсы: `a[:i]` и `a[i+1:]` смотрят в тот же массив, поэтому сортировка идёт на месте, и не нужно таскать индексы `lo, hi`.

### Почему худший случай O(n²)

Время быстрой сортировки зависит от того, насколько ровно опорный делит массив. Если пополам, глубина рекурсии `log n`, на каждом уровне O(n) работы, итого O(n log n). Если опорный всегда **минимум или максимум**, одна часть пустая, другая короче всего на один элемент: глубина `n`, работа `n + (n-1) + ... + 1 = O(n²)`.

С опорным «последний элемент» это случается на **уже отсортированном** массиве: последний всегда максимум. А отсортированные данные в жизни встречаются постоянно (выборка из БД с `ORDER BY`, логи по времени). Миллион элементов превращается в 5·10¹¹ сравнений и миллион уровней рекурсии.

Как защищаются:

- **Случайный опорный.** Никакой фиксированный вход не будет худшим: вероятность получить O(n²) ничтожна. Это ожидаемое O(n log n) на **любом** входе.
- **Медиана трёх** (первый, средний, последний). Ломает худший случай на отсортированном и развёрнутом. Go для больших кусков берёт «медиану медиан трёх» (ninther Тьюки).
- **Ограничение глубины** (introsort): если рекурсия слишком глубокая, переключиться на пирамидальную сортировку с гарантией O(n log n). Go делает похоже, но считает не глубину, а число неудачных (несбалансированных) разбиений, подробно в блоке про pdqsort ниже.

### Одинаковые элементы

Второй худший случай, о котором часто забывают: массив из **одинаковых** чисел. Ломуто с условием `a[j] < p` кладёт все равные опорному в правую часть, и разбиение опять вырождается: O(n²), даже со случайным опорным. Статусы заказов, коды ответов, флаги: в реальных данных дубликатов полно.

Решение: **трёхчастное разбиение** (флаг Нидерландов, Дейкстра). Делим на «меньше», «равно», «больше», а в рекурсию отправляем только крайние части. Равные опорному сразу встают на место, и массив из одинаковых сортируется за один проход.

```go
// [0, lt) < p,  [lt, i) == p,  [i, gt) ещё не смотрели,  [gt, n) > p
lt, i, gt := 0, 0, len(a)
for i < gt {
	switch {
	case a[i] < p:
		a[lt], a[i] = a[i], a[lt]
		lt++
		i++
	case a[i] > p:
		gt--
		a[gt], a[i] = a[i], a[gt] // пришедший с конца не проверен: i не двигаем
	default:
		i++
	}
}
```

Это ровно задача «отсортировать нули, единицы и двойки за один проход» из домашки, там опорный это 1. Разбиение Хоара (два указателя навстречу, останавливаются на **равных** опорному) тоже справляется с дубликатами, но его сложнее написать без ошибки.

Ещё одна деталь из промышленных реализаций: рекурсивно сортировать **меньшую** часть, а большую обрабатывать циклом. Тогда глубина стека не больше `log n` даже при неудачных разбиениях.

### Разбор 1: k-й по величине

> Найди k-й по величине элемент неотсортированного слайса (k = 1 это максимум). Аналог: [LeetCode 215](https://leetcode.com/problems/kth-largest-element-in-an-array/).

**Уточняем.** Дубликаты считаются: в `[3 2 3 1 2 4 5 5 6]` 4-й по величине 4. Переставлять входной слайс можно.

**Брутфорс.** Отсортировать и взять `nums[n-k]`: O(n log n). Для собеса нормальный первый ответ.

**Оптимизация: quickselect.** Разбиение ставит опорный (и равные ему) **на их окончательные места**. Если нужная позиция `n-k` попала в «равные», ответ найден. Иначе продолжаем только в **одной** части, где лежит позиция. В среднем размер куска каждый раз уменьшается вдвое: `n + n/2 + n/4 + ... = 2n`, то есть O(n) в среднем.

```go
func findKthLargest(nums []int, k int) int {
	target := len(nums) - k // позиция в отсортированном по возрастанию
	lo, hi := 0, len(nums)
	for {
		p := nums[lo+rand.IntN(hi-lo)]
		lt, gt := partition3(nums[lo:hi], p) // трёхчастное разбиение из раздела выше
		lt, gt = lt+lo, gt+lo
		switch {
		case target < lt:
			hi = lt
		case target >= gt:
			lo = gt
		default:
			return p // target в блоке равных опорному
		}
	}
}
```

**Сложность:** O(n) в среднем, O(n²) в худшем (вероятность ничтожна при случайном опорном). Альтернатива с кучей размера `k` даёт O(n log k) и работает на потоке данных, её разберём в уроке про кучи.

## Сортировка слиянием

Обратная идея: сначала рекурсивно отсортировать половины, потом **слить** их двумя указателями (как в уроке про два указателя). Всё время O(n log n): `log n` уровней, на каждом слияние всех элементов за O(n). Худшего случая нет.

```go
func mergeSort(a, buf []int) { // buf той же длины, что a: общий буфер на все слияния
	if len(a) < 2 {
		return
	}
	mid := len(a) / 2
	mergeSort(a[:mid], buf[:mid])
	mergeSort(a[mid:], buf[mid:])
	copy(buf, a)
	i, j := 0, mid
	for k := range a {
		if j >= len(a) || (i < mid && buf[i] <= buf[j]) { // <= : при равенстве берём из левой
			a[k] = buf[i]
			i++
		} else {
			a[k] = buf[j]
			j++
		}
	}
}
```

Цена: O(n) дополнительной памяти на буфер. Плюсы, ради которых её выбирают:

- **Устойчивость.** При равенстве берём элемент из левой половины (`<=`, а не `<`), и равные сохраняют исходный порядок.
- **Предсказуемость.** O(n log n) всегда, без случайностей.
- **Последовательный доступ.** Слияние читает обе половины подряд. Поэтому её используют для **внешней** сортировки, когда данные не влезают в память: отсортировать куски, записать на диск, слить. Это и есть `external merge` в PostgreSQL.
- **Связные списки.** Слияние списков не требует буфера, а произвольного доступа, нужного быстрой сортировке, у списков нет.

## Сортировка подсчётом

Если ключи это небольшие целые числа (возраст 0-150, оценка 1-5, код ответа HTTP, приоритет 0-2), сравнивать вообще не нужно. Считаем, сколько раз встречается каждый ключ, и раскладываем по местам. O(n + k), где `k` размер диапазона ключей. Это быстрее O(n log n), но только когда `k` не намного больше `n`.

Простая версия для чисел (просто выписать каждое значение `count[v]` раз) теряет связь с объектами. Для структур нужна **устойчивая** версия через префиксные суммы: `count[v]` превращаем в позицию, с которой начинаются элементы с ключом `v`, и раскладываем входные элементы слева направо.

```
ключи:      2 0 2 1 0           count по ключам:  0:2  1:1  2:2
позиции начала: 0:0  1:2  2:3   (префиксные суммы)
раскладка слева направо: 2→3, 0→0, 2→4, 1→2, 0→1
результат:  0 0 1 2 2, равные в исходном порядке
```

Код этой раскладки ты напишешь в домашке. Её развитие, поразрядная сортировка (radix sort), сортирует длинные ключи (например, `uint64`) несколькими проходами подсчёта по разрядам, и каждый проход обязан быть устойчивым, иначе предыдущие разряды перемешаются.

### Разбор 2: индекс Хирша

> У учёного `n` статей, `citations[i]` число цитирований статьи. Индекс Хирша `h` это наибольшее число, такое что есть хотя бы `h` статей, у каждой не меньше `h` цитирований. Аналог: [LeetCode 274](https://leetcode.com/problems/h-index/).

**Брутфорс через сортировку.** Отсортировать по убыванию и найти последнее `i`, где `citations[i] >= i+1`: O(n log n).

**Оптимизация.** Ответ не больше `n` (статей всего `n`). Значит, цитирования больше `n` можно считать за `n`, и диапазон ключей `0..n`: сортировка подсчётом, только раскладывать даже не надо, хватит счётчиков. Идём от `h = n` вниз и копим, сколько статей имеют не меньше `h` цитирований.

```go
func hIndex(citations []int) int {
	n := len(citations)
	cnt := make([]int, n+1)
	for _, c := range citations {
		cnt[min(c, n)]++ // всё, что больше n, кладём в корзину n
	}
	papers := 0
	for h := n; h >= 0; h-- {
		papers += cnt[h] // статей с цитированиями >= h
		if papers >= h {
			return h
		}
	}
	return 0
}
```

**Проверка:** `[3 0 6 1 5]` даёт 3 (статьи с 3, 5, 6 цитированиями), `[100]` даёт 1, `[0]` даёт 0. **Сложность:** O(n) времени и памяти.

## Устойчивость

Сортировка **устойчивая**, если элементы с равными ключами остаются в том же порядке, что были во входе. Для чисел это незаметно, для структур важно.

Пример: список заказов уже отсортирован по времени, и пользователь нажал «сортировать по статусу». Он ожидает, что внутри каждого статуса заказы остались по времени. Устойчивая сортировка по статусу это гарантирует, неустойчивая нет. Отсюда классический приём сортировки по нескольким ключам: устойчиво отсортировать по второстепенному ключу, потом по главному. Но в Go проще и быстрее один проход с составным компаратором (ниже).

Устойчивые: вставками, слиянием, подсчётом (с префиксными суммами). Неустойчивые: быстрая, пирамидальная, и значит `slices.Sort`, `slices.SortFunc`, `sort.Slice`. Устойчивые варианты в Go: `slices.SortStableFunc` и `sort.SliceStable`.

## Сортировка в Go

### Что есть в стандартной библиотеке

| Функция | Что делает | Заметки |
|---|---|---|
| `slices.Sort(s)` | по возрастанию для `cmp.Ordered` | pdqsort, Go 1.21+ |
| `slices.SortFunc(s, cmp)` | по функции сравнения | неустойчива |
| `slices.SortStableFunc(s, cmp)` | по функции сравнения, устойчиво | |
| `slices.IsSorted`, `slices.IsSortedFunc` | проверка | |
| `sort.Ints`, `sort.Strings` | старые обёртки | с Go 1.22 просто вызывают `slices.Sort` |
| `sort.Slice(s, less)` | по функции `less(i, j int) bool` | через рефлексию, медленнее |
| `sort.Sort(data)` | по интерфейсу `Len/Less/Swap` | для своих коллекций |

### sort.Slice против slices.SortFunc

`sort.Slice` появился до дженериков. Он принимает `any`, а меняет элементы местами через `reflectlite.Swapper`, функцию сравнения получает по **индексам** и вынужден лезть в слайс через замыкание. `slices.SortFunc` дженерик: компилятор знает тип элементов, функция сравнения получает сами **значения**. Документация `sort.Slice` прямо советует: «in many situations, the newer slices.SortFunc function is more ergonomic and runs faster».

На ноутбуке автора миллион случайных `int` (лучший из пяти прогонов, Go 1.27): `slices.Sort` 57 мс, `slices.SortFunc` с `cmp.Compare` 80 мс, `sort.Slice` 92 мс, `slices.SortStableFunc` 172 мс. А уже отсортированный миллион `slices.Sort` прошёл за полмиллисекунды: pdqsort распознаёт готовый порядок.

Вывод: в новом коде `slices.Sort` для простых типов, `slices.SortFunc` для структур, `slices.SortStableFunc`, когда нужна устойчивость. `sort.Slice` встретишь в старом коде.

### Функция сравнения и cmp.Compare

Контракт `slices.SortFunc`: `cmp(a, b)` возвращает отрицательное число, если `a` меньше `b`, ноль, если равны, положительное, если больше. Для упорядоченных типов есть готовая `cmp.Compare` (Go 1.21), она возвращает -1, 0 или +1 и корректно обращается с `NaN`.

```go
slices.SortFunc(users, func(a, b User) int {
	return cmp.Compare(a.Age, b.Age)
})
```

Для убывания поменяй аргументы местами: `cmp.Compare(b.Age, a.Age)`. Для строк есть ещё `strings.Compare`, результат тот же. Не пиши `a.Age - b.Age`: на больших числах разность переполняется (грабли ниже).

Функция сравнения обязана задавать **строгий слабый порядок**. Три условия: асимметрия (если `a < b`, то не `b < a`), транзитивность (если `a < b` и `b < c`, то `a < c`) и транзитивность **равенства** (если `a` равно `b` и `b` равно `c` в смысле компаратора, то `a` равно `c`). Третье условие нарушает популярный компаратор «числа равны, если отличаются меньше чем на `eps`»: при `eps = 0.1` получается 1.00 = 1.06 и 1.06 = 1.12, но 1.00 < 1.12. Компаратор, который нарушает эти условия или отвечает по-разному на одну и ту же пару (случайный, зависящий от изменяемого состояния), даёт непредсказуемый результат.

### Сортировка по нескольким ключам

Задача: отсортировать по отделу, внутри отдела по зарплате по убыванию, при равной зарплате по имени. Сравниваем ключи по очереди и возвращаем первый ненулевой результат. `cmp.Or` (Go 1.22) возвращает первый аргумент, не равный нулевому значению, и это ровно то, что нужно:

```go
slices.SortFunc(es, func(a, b Employee) int {
	return cmp.Or(
		cmp.Compare(a.Dept, b.Dept),
		cmp.Compare(b.Salary, a.Salary), // по убыванию: аргументы наоборот
		cmp.Compare(a.Name, b.Name),
	)
})
```

Небольшой нюанс: `cmp.Or` вычисляет **все** аргументы, потому что это обычная функция, а не оператор. Для трёх полей это неважно; если сравнение ключа дорогое, пиши цепочку `if c := ...; c != 0 { return c }`.

### Разбор 3: сортировка по частоте

> Отсортируй числа по возрастанию частоты, а числа с одинаковой частотой по убыванию значения. `[1 1 2 2 2 3]` даёт `[3 1 1 2 2 2]`. Аналог: [LeetCode 1636](https://leetcode.com/problems/sort-array-by-increasing-frequency/).

Сначала посчитать частоты в `map` (урок про хеширование), потом отсортировать с составным ключом:

```go
func frequencySort(nums []int) []int {
	freq := make(map[int]int)
	for _, v := range nums {
		freq[v]++
	}
	slices.SortFunc(nums, func(a, b int) int {
		return cmp.Or(
			cmp.Compare(freq[a], freq[b]), // реже раньше
			cmp.Compare(b, a),             // при равной частоте больше раньше
		)
	})
	return nums
}
```

**Проверка:** `[2 3 1 3 2]` даёт `[1 3 3 2 2]`: у 1 частота 1, у 2 и 3 по 2, и 3 идёт раньше 2. **Сложность:** O(n log n), `freq` O(n) памяти. Компаратор читает из `map` дважды на каждое сравнение; если это узкое место, заранее разложи пары «значение, частота» в слайс структур.

::: hood Что внутри slices.Sort: pdqsort
С Go 1.19 сортировка в стандартной библиотеке это **pdqsort** (pattern-defeating quicksort, Orson Peters), а `slices` (Go 1.21) использует ту же реализацию в дженерик-варианте. Читать в `slices/zsortordered.go` и `zsortanyfunc.go`:

- Куски длиной до 12 (`maxInsertion = 12`) сортируются вставками.
- Опорный: на кусках от 8 элементов медиана трёх, от 50 (`shortestNinther`) медиана трёх медиан, «ninther» Тьюки.
- Если при выборе опорного не понадобилось ни одной перестановки, кусок, похоже, уже отсортирован, и алгоритм пробует **частичную сортировку вставками** с ограничением на число сдвигов. Получилось, кусок готов за O(n). Отсюда полмиллисекунды на отсортированном миллионе. Если же все сравнения сказали «по убыванию», кусок сначала разворачивается.
- Если предыдущее разбиение вышло сильно несбалансированным (меньшая часть короче восьмой доли), вызывается `breakPatterns`: несколько элементов переставляются, чтобы сломать «плохой» шаблон во входе, и уменьшается счётчик `limit`.
- `limit` стартует с `bits.Len(n)`, это примерно `log₂ n`. Когда он кончился, кусок досортировывается **пирамидальной** сортировкой. Это гарантия O(n log n) в худшем случае, как в introsort.
- Рекурсия идёт в меньшую часть, а большая обрабатывается в том же цикле: глубина стека O(log n).
- Если опорный равен элементу перед куском, все равные ему собираются отдельно (`partitionEqual`), поэтому массив из одинаковых не вырождается.

Устойчивая `slices.SortStableFunc` устроена иначе: блоки по 20 элементов сортируются вставками, потом сливаются алгоритмом SymMerge **на месте**, без буфера. Это O(n log n) сравнений, но O(n log² n) перестановок, поэтому в замере выше она примерно вдвое медленнее неустойчивой.
:::

::: trap Компаратор через вычитание
Плохо: «короткий» компаратор `a - b`.

```go
xs := []int{math.MinInt64, 1}
slices.SortFunc(xs, func(a, b int) int { return a - b })
fmt.Println(xs) // [1 -9223372036854775808]
```

`math.MinInt64 - 1` переполняется в `math.MaxInt64`, то есть «больше нуля», и сортировка решает, что минимальное число больше единицы. На обычных возрастах и ценах не проявится, на ID, временных метках в наносекундах и разностях это ловушка. Хорошо: `cmp.Compare(a, b)`, никакой арифметики.
:::

::: trap Быстрая сортировка, которая вырождается
Плохо: опорный «первый» или «последний» элемент, разбиение Ломуто со строгим `<`.

```go
p := a[len(a)-1] // на отсортированном входе это всегда максимум: O(n²)
for j := range len(a) - 1 {
	if a[j] < p { // все равные опорному уходят вправо: O(n²) на одинаковых
		...
	}
}
```

Хорошо: случайный опорный (`rand.IntN`) и трёхчастное разбиение, а рекурсия в меньшую часть. Тест в домашке гоняет миллион уже отсортированных, развёрнутых и одинаковых чисел.
:::

::: trap Надежда на устойчивость
Плохо: отсортировать по времени, потом по статусу через `slices.SortFunc` и ждать, что внутри статуса порядок по времени сохранится.

```go
slices.SortFunc(orders, byTime)
slices.SortFunc(orders, byStatus) // неустойчива: порядок по времени внутри статуса не гарантирован
```

На маленьких тестовых данных это часто «работает» (куски до 12 элементов сортируются вставками, а они устойчивы), а на продовых объёмах ломается. Хорошо: один составной компаратор через `cmp.Or`, или `slices.SortStableFunc` для второго прохода.
:::

::: trap Сравнение индексов не того слайса в sort.Slice
Плохо: `less` получает индексы и легко обратиться не к тому слайсу.

```go
sorted := slices.Clone(users)
sort.Slice(sorted, func(i, j int) bool {
	return users[i].Age < users[j].Age // сравниваем исходный слайс, а переставляем копию
})
```

Компилятор не поможет: типы сходятся. Результат выглядит почти правильным и случайно ломается. Хорошо: `slices.SortFunc`, где компаратор получает **значения**, и такую ошибку не написать.
:::

<Predict :options="['0 \'\'', '-1 b', '1 c', 'ошибка компиляции: разные типы']" :correct="1">

::: interview
<details><summary>Как работает быстрая сортировка и какой у неё худший случай?</summary>

Выбираем опорный, разбиением переставляем элементы на «меньше опорного» и «больше», рекурсивно сортируем части. В среднем O(n log n), памяти O(log n) на стек. Худший случай O(n²), когда опорный раз за разом минимум или максимум: например, опорный «последний» на отсортированном массиве, или разбиение Ломуто на массиве одинаковых элементов. Защита: случайный опорный или медиана трёх, трёхчастное разбиение для дубликатов, ограничение глубины с переходом на heap sort (introsort, pdqsort).

</details>
<details><summary>Чем сортировка слиянием лучше быстрой и чем хуже?</summary>

Лучше: всегда O(n log n), устойчива, читает данные последовательно, поэтому годится для внешней сортировки (данные на диске) и для связных списков. Хуже: O(n) дополнительной памяти и больше копирований, поэтому на массивах в памяти обычно медленнее быстрой. PostgreSQL сортирует в памяти быстрой, а при нехватке `work_mem` переходит на внешнее слияние.

</details>
<details><summary>Что такое устойчивая сортировка и когда она нужна?</summary>

Устойчивая сохраняет исходный порядок элементов с равными ключами. Нужна, когда сортируешь структуры и порядок равных что-то значит: последовательная сортировка по нескольким ключам, «сортировать по статусу, не ломая порядок по времени». Устойчивы вставки, слияние, подсчёт; неустойчивы быстрая, пирамидальная и `slices.Sort`/`SortFunc`. В Go устойчиво сортирует `slices.SortStableFunc`.

</details>
<details><summary>Можно ли сортировать быстрее O(n log n)?</summary>

Сравнениями нельзя: нижняя граница `log₂(n!)`, то есть порядка `n log n` сравнений. Без сравнений можно, если ключи особые: сортировка подсчётом за O(n + k) для целых из небольшого диапазона `k`, поразрядная за O(d·(n + основание)) для ключей из `d` разрядов, блочная (bucket sort) для равномерно распределённых чисел.

</details>
<details><summary>Какой алгоритм внутри slices.Sort?</summary>

pdqsort (pattern-defeating quicksort), с Go 1.19 в `sort` и с 1.21 в `slices`. Быстрая сортировка с выбором опорного медианой трёх или ninther, вставки на кусках до 12 элементов, распознавание уже отсортированных кусков, перемешивание при плохих разбиениях и переход на пирамидальную сортировку после `log n` плохих опорных. Худший случай O(n log n), неустойчива. Устойчивая `SortStableFunc` это вставки по блокам плюс слияние на месте (SymMerge).

</details>
<details><summary>Чем sort.Slice отличается от slices.SortFunc?</summary>

`sort.Slice(x any, less func(i, j int) bool)` старее дженериков: принимает `any`, меняет элементы через рефлексию (`reflectlite.Swapper`), компаратор работает с индексами через замыкание. `slices.SortFunc(s, cmp func(a, b E) int)` дженерик, без рефлексии, компаратор получает значения и возвращает -1/0/+1. Он быстрее (документация прямо это говорит) и защищает от ошибки «сравнили индексы не того слайса». Обе неустойчивы.

</details>
<details><summary>Как отсортировать структуры по нескольким полям в Go?</summary>

`slices.SortFunc` с компаратором, который сравнивает поля по очереди и возвращает первый ненулевой результат. Удобно через `cmp.Or(cmp.Compare(a.X, b.X), cmp.Compare(b.Y, a.Y), ...)`: для убывания аргументы меняются местами. Не вычитать числа (переполнение), не делать несколько неустойчивых проходов подряд.

</details>
<details><summary>Как найти k-й по величине элемент быстрее сортировки?</summary>

Quickselect: разбиение как в быстрой сортировке, но рекурсия (или цикл) только в ту часть, где лежит нужная позиция. В среднем O(n), в худшем O(n²) при неудачных опорных. Альтернатива: куча на `k` элементов, O(n log k), работает и на потоке. Ещё есть детерминированный алгоритм медианы медиан с гарантией O(n), но на практике он медленнее.

</details>
:::
