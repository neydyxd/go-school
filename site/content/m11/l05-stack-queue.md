# Стек, очередь, монотонный стек

Стек и очередь это самые простые структуры данных после массива: положить элемент, взять элемент. Вся разница в том, **какой** элемент берём. Стек отдаёт последний положенный (LIFO, last in first out), очередь отдаёт первый (FIFO, first in first out). Из этой разницы вырастает огромный класс задач: от проверки скобок до максимума в скользящем окне за O(n).

В бэкенде ты пользуешься ими каждый день, даже если не называешь их так. Стек вызовов горутины, порядок выполнения `defer`, разбор вложенного JSON, отмена действий (undo): это стек. Очередь задач на обработку, буферизованный канал, буфер последних N строк лога или N замеров latency для метрик, обход графа в ширину: это очередь. А монотонный стек решает задачи вида «для каждого дня найди ближайший день с большей нагрузкой» за один проход вместо вложенного цикла, и на собесах его любят именно потому, что без знания приёма задача кажется квадратичной.

В уроке соберём стек и очередь на слайсах, разберём три способа сделать очередь (на слайсе, на двух стеках, кольцевой буфер) и их цену, а потом монотонный стек и монотонную очередь с разбором задач.

## Стек

Стек на Go это просто слайс, у которого «вершина» в конце. `append` кладёт, срез `[:len-1]` снимает. Обе операции O(1) (`append` амортизированно, это разбирали в уроке про Big-O).

```go
var st []int
st = append(st, 1)  // push
st = append(st, 2)  // push
top := st[len(st)-1] // peek: 2
st = st[:len(st)-1]  // pop
fmt.Println(top, st) // 2 [1]
```

Вершина в конце, а не в начале, потому что добавление и удаление в конце слайса ничего не сдвигает. Если держать вершину в `st[0]`, каждая операция двигала бы весь слайс: O(n).

Для собственного типа удобно завернуть это в дженерик:

```go
type Stack[T any] struct{ items []T }

func (s *Stack[T]) Push(v T) { s.items = append(s.items, v) }

func (s *Stack[T]) Pop() (T, bool) {
	var zero T
	if len(s.items) == 0 {
		return zero, false
	}
	v := s.items[len(s.items)-1]
	s.items[len(s.items)-1] = zero // не держим ссылку: сборщик мусора сможет освободить объект
	s.items = s.items[:len(s.items)-1]
	return v, true
}
```

Обнуление снятого элемента важно, когда в стеке указатели или большие структуры: срез `[:len-1]` не трогает базовый массив, и снятый объект остаётся достижимым из него, пока ячейку не перезапишут. Для `int` это не важно, для `*Request` это утечка.

### Когда нужен стек

Признак простой: **последнее открытое закрывается первым**. Скобки, теги HTML, вложенные вызовы функций, вложенные директории в пути. Ещё стек нужен, когда рекурсию переписывают в цикл: рекурсия это и есть стек вызовов, просто неявный.

- Проверка скобок, валидация вложенности (домашка).
- Вычисление выражений: обратная польская запись, калькулятор (домашка).
- Нормализация пути, undo/redo, история навигации «назад».
- Итеративный обход дерева и обход графа в глубину.
- «Ближайший слева/справа больший или меньший элемент»: монотонный стек, о нём ниже.

### Разбор 1: упростить путь

> Дан абсолютный путь в стиле Unix. Верни канонический: без `.`, с отработанными `..`, без повторных и завершающих `/`. Аналог: [LeetCode 71](https://leetcode.com/problems/simplify-path/).

**Уточняем.** `..` из корня остаётся в корне? Да: `/../` даёт `/`. Пустые части от `//` пропускаем. Имена могут содержать точки, например `...` это обычное имя.

**Идея.** Каждая папка, в которую мы «зашли», может быть отменена `..`. Отменяется всегда **последняя** зашедшая: это стек.

```go
func simplifyPath(p string) string {
	var st []string
	for _, part := range strings.Split(p, "/") {
		switch part {
		case "", ".": // пустая часть от "//" или текущая папка
		case "..":
			if len(st) > 0 {
				st = st[:len(st)-1]
			}
		default:
			st = append(st, part)
		}
	}
	return "/" + strings.Join(st, "/")
}
```

**Проверка руками:** `/a/./b/../../c/` разбивается на `"" a . b .. .. c ""`. Стек: `[a]`, `[a b]`, `[a]`, `[]`, `[c]`. Ответ `/c`.

**Сложность:** O(n) по времени и памяти. В реальном коде так писать не надо: в стандартной библиотеке есть `path.Clean`, который делает то же самое (а `filepath.Clean` с учётом ОС). Но на собесе именно эту задачу и спросят.

## Очередь

Очередь сложнее стека, потому что элементы уходят с **другого** конца. Есть три реализации, и разница между ними хороший вопрос на собесе.

### Вариант 1: слайс и срез с начала

```go
var q []int
q = append(q, 1, 2, 3) // enqueue
front := q[0]          // dequeue
q = q[1:]
```

Работает, каждая операция амортизированно O(1). Но у `q = q[1:]` есть цена: срез сдвигает начало **окна** в базовый массив, а сам массив остаётся. Ячейки перед `q[0]` больше не видны, но память не освобождается, пока `append` не решит перевыделить массив. Ёмкость окна при этом уменьшается с каждым снятием, и перевыделение случится раньше, чем ты ожидаешь (это задача «что выведет» ниже). В задачах на собесе и в BFS это нормально. В долгоживущей очереди сервиса, где снятые элементы это указатели, нужны аккуратность (обнулять снятые ячейки) или другой способ.

::: hood Что происходит с массивом при q = q[1:]
```
q = append(q, a, b, c, d)        массив: [a b c d]   окно q: [a b c d]  cap 4
q = q[1:]                         массив: [a b c d]   окно q:   [b c d]  cap 3
q = q[1:]                         массив: [a b c d]   окно q:     [c d]  cap 2
q = append(q, e, f)               новый массив: [c d e f], старый станет мусором
```

Ячейки `a` и `b` до перевыделения остаются в памяти и держат то, на что указывают. Ёмкость окна считается до конца **массива**, а не от его начала, поэтому после `q[1:]` она уменьшается на единицу.
:::

### Вариант 2: очередь на двух стеках

Классика собесов. Держим два стека: `in`, куда только кладём, и `out`, откуда только снимаем. Когда `out` пуст, а нужно снять элемент, перекладываем **весь** `in` в `out`. При перекладывании порядок разворачивается, и самый старый элемент оказывается на вершине `out`.

```
Push 1, 2, 3:   in = [1 2 3]   out = []
Pop:            in пуст после переноса: out = [3 2 1], снимаем 1
Push 4:         in = [4]       out = [3 2]
Pop:            out не пуст, снимаем 2 (in не трогаем!)
```

Почему это амортизированно O(1): каждый элемент за свою жизнь **один раз** кладётся в `in`, **один раз** перекладывается в `out` и **один раз** снимается. Отдельный Pop может стоить O(n), но n операций в сумме стоят O(n). Это тот же аргумент, что у `append`.

Ошибка, которую ловит тест в домашке: перекладывать обратно из `out` в `in` после каждого Pop. Тогда каждый Pop это O(n), а n операций O(n²).

Зачем вообще так делать, если есть слайс? На собесе это проверка понимания амортизации. В жизни приём встречается в функциональных языках с неизменяемыми списками и в задачах «очередь с минимумом»: если оба стека умеют отдавать минимум за O(1) (как `MinStack` из домашки), то и очередь умеет.

### Вариант 3: кольцевой буфер

Если максимальный размер очереди известен, лучше всего кольцевой буфер (ring buffer, циклическая очередь). Один слайс фиксированной длины, индекс головы и число элементов. Хвост вычисляется по модулю: когда индекс доходит до конца слайса, он переходит в начало.

```
len(buf) = 5, head = 3, n = 4

индекс:   0   1   2   3   4
buf:     [c] [d] [ ] [a] [b]
                      ^ head

порядок в очереди: a(3) b(4) c(0) d(1)
следующий Push пишет в (head+n)%5 = (3+4)%5 = 2
```

```go
type Ring struct {
	buf     []int
	head, n int
}

func (r *Ring) Push(v int) bool {
	if r.n == len(r.buf) {
		return false // полон
	}
	r.buf[(r.head+r.n)%len(r.buf)] = v
	r.n++
	return true
}

func (r *Ring) Pop() (int, bool) {
	if r.n == 0 {
		return 0, false
	}
	v := r.buf[r.head]
	r.head = (r.head + 1) % len(r.buf)
	r.n--
	return v, true
}
```

Память выделяется один раз, никаких сдвигов и аллокаций, каждая операция строго O(1), а не амортизированно. Поэтому кольцевые буферы стоят там, где важна предсказуемость: буферы сетевых карт, аудио, очереди логов, «последние N запросов» для метрик. Что делать при переполнении, решаешь сам: отказать (как у нас), перезаписать самый старый элемент (так хранят «последние N»), заблокировать писателя (так делает буферизованный канал).

::: hood Буферизованный канал это кольцевой буфер
Внутри `make(chan T, n)` лежит структура `hchan` из `runtime/chan.go`. У неё есть `buf` (массив на `n` элементов), `dataqsiz` (размер, в комментарии он прямо назван «size of the circular queue»), `sendx` и `recvx` (индексы записи и чтения), `qcount` (сколько элементов сейчас). Отправка пишет в `buf[sendx]` и сдвигает `sendx` по кругу, получение читает `buf[recvx]`. Когда буфер полон, отправитель паркуется в очереди ожидающих `sendq`, а не получает `false`, как наш `Push`. Подробно каналы изнутри разбираются в модуле про конкурентность и производительность.

В стандартной библиотеке есть ещё `container/ring`, но это кольцевой **двусвязный список** с `any` внутри, а не буфер на массиве. Для очереди он неудобен и медленнее слайса.
:::

### Дек

Дек (deque, double-ended queue) умеет класть и снимать с **обоих** концов. В стандартной библиотеке Go дека нет. Для задач хватает слайса: снимать с начала через `q[1:]`, с конца через `q[:len-1]`. В продакшн-коде дек делают кольцевым буфером с ростом (когда полон, копируем в массив вдвое больше).

## Монотонный стек

Задача: для каждого элемента найти **ближайший справа больший**. `[2 1 2 4 3]` даёт `[4 2 4 -1 -1]` (если нет, -1). Брутфорс для каждого `i` идёт вправо до первого большего: O(n²) на убывающем массиве.

Посмотри на элементы, которые ещё **ждут** ответа. Если `5` ждёт и `3` правее неё тоже ждёт, то `3 < 5`: иначе `3` уже была бы ответом для `5`. Значит, ждущие элементы всегда образуют **убывающую** последовательность, если читать слева направо. Это и есть монотонный стек.

Новый элемент `v` приходит справа. Все ждущие, которые меньше `v`, получают ответ `v` и уходят из стека. Остальные больше или равны `v`, они ждут дальше, а `v` встаёт на вершину. Убывание сохраняется.

```go
res := make([]int, len(nums))
var st []int // индексы, значения по ним убывают снизу вверх
for i, v := range nums {
	res[i] = -1
	for len(st) > 0 && nums[st[len(st)-1]] < v {
		res[st[len(st)-1]] = v // v первый больший для вершины
		st = st[:len(st)-1]
	}
	st = append(st, i)
}
```

Почему O(n), хотя внутри цикла цикл: каждый индекс **один раз** кладётся в стек и не больше одного раза снимается. Всего снятий не больше `n`, значит, суммарная работа внутреннего цикла O(n) на весь проход. Тот же аргумент, что у двух указателей.

В стеке храним **индексы**, а не значения: по индексу всегда можно достать значение, а наоборот нельзя, и многим задачам нужно расстояние (сколько дней до потепления) или ширина (гистограмма).

### Четыре варианта одного шаблона

| Ищем | Порядок обхода | Стек хранит | Снимаем, пока вершина |
|---|---|---|---|
| ближайший больший справа | слева направо | убывающие | `< v` |
| ближайший меньший справа | слева направо | возрастающие | `> v` |
| ближайший больший слева | слева направо | убывающие | `<= v`, после снятия вершина это ответ для `v` |
| ближайший меньший слева | слева направо | возрастающие | `>= v`, после снятия вершина это ответ для `v` |

Строгое или нестрогое сравнение решает, что делать с **равными**. «Строго больший» снимает только меньших, равные остаются ждать. Перепутать `<` и `<=` это самая частая ошибка в этих задачах (грабли ниже).

### Как узнать задачу на монотонный стек

- «Для каждого элемента найди ближайший больший/меньший слева или справа», «через сколько дней», «сколько дней подряд до этого».
- Нужно знать, **докуда** элемент остаётся минимумом или максимумом: гистограмма, сумма минимумов всех подотрезков, «вода между столбиками».
- Брутфорс это вложенный цикл «иди вправо/влево, пока не встретишь больший».

### Разбор 2: размах цены

> Поток дневных цен акции. Для каждой новой цены верни размах: сколько дней подряд, включая сегодня, цена была не выше сегодняшней. Для `100 80 60 70 60 75 85` ответы `1 1 1 2 1 4 6`. Аналог: [LeetCode 901](https://leetcode.com/problems/online-stock-span/).

**Уточняем.** Данные приходят потоком: метод `Next(price)` вызывается для каждой цены, весь массив заранее не известен.

**Брутфорс.** Хранить все цены и для каждой новой идти назад, пока цена не больше: O(n) на запрос, O(n²) на поток из возрастающих цен.

**Оптимизация.** Это «ближайший строго больший **слева**». Если сегодня 75, то все дни, которые 75 «перекрыла», больше никогда не понадобятся: любая будущая цена, которая перекроет 75, перекроет и их. Значит, их можно схлопнуть в 75 вместе с их размахом. В стеке храним пары «цена, размах» с убывающими ценами.

```go
type StockSpanner struct {
	prices, spans []int // параллельные стеки
}

func (s *StockSpanner) Next(price int) int {
	span := 1
	for len(s.prices) > 0 && s.prices[len(s.prices)-1] <= price {
		span += s.spans[len(s.spans)-1] // забираем размах перекрытого дня
		s.prices = s.prices[:len(s.prices)-1]
		s.spans = s.spans[:len(s.spans)-1]
	}
	s.prices = append(s.prices, price)
	s.spans = append(s.spans, span)
	return span
}
```

**Проверка** на `100 80 60 70 60 75 85`. 100: стек пуст, 1. 80, 60: меньше вершины, по 1. 70: снимает 60 (размах 1), ответ 2, стек `100 80 70`. 60: 1. 75: снимает 60 (1) и 70 (2), ответ 4. 85: снимает 75 (4) и 80 (1), ответ 6.

**Сложность:** амортизированно O(1) на вызов, каждая цена кладётся и снимается один раз. Память O(n) в худшем случае (убывающие цены).

### Разбор 3: максимум в скользящем окне

> Дан слайс замеров latency и `k`. Верни максимум в каждом окне из `k` подряд идущих замеров. Для `[1 3 -1 -3 5 3 6 7]`, `k = 3` ответ `[3 3 5 5 6 7]`. Аналог: [LeetCode 239](https://leetcode.com/problems/sliding-window-maximum/).

Скользящее окно из прошлого урока здесь не спасает напрямую: сумму окна можно поправить при сдвиге, а максимум нельзя (ушёл максимальный элемент, кто следующий?). Брутфорс O(n·k).

**Идея: монотонная очередь.** Держим индексы кандидатов в максимум, значения по ним убывают. Если пришёл `v`, все кандидаты меньше `v` больше никогда не станут максимумом: `v` правее, значит, проживёт в окне дольше них, и он больше. Снимаем их с **конца**. А с **начала** снимаем кандидата, который вышел за левую границу окна. Максимум окна всегда в начале.

```go
func maxSlidingWindow(nums []int, k int) []int {
	var dq []int // индексы, значения по ним убывают
	var res []int
	for i, v := range nums {
		if len(dq) > 0 && dq[0] <= i-k { // голова вышла из окна
			dq = dq[1:]
		}
		for len(dq) > 0 && nums[dq[len(dq)-1]] <= v {
			dq = dq[:len(dq)-1] // эти уже никогда не будут максимумом
		}
		dq = append(dq, i)
		if i >= k-1 {
			res = append(res, nums[dq[0]])
		}
	}
	return res
}
```

**Проверка** на замерах `[120 80 95 300 90 85 70]`, `k = 3`: окна дают `120 300 300 300 90`. На шаге с 300 очередь схлопывается до одного элемента, а на последнем окне `[90 85 70]` голова 300 вышла за границу, и максимумом стало 90.

**Сложность:** O(n), каждый индекс один раз входит и один раз выходит. Это дек: снимаем с обоих концов. `dq[1:]` здесь допустим, массив перевыделится при росте.

### Гистограмма: монотонный стек на максималках

Задача из домашки (самый большой прямоугольник в гистограмме) классика собесов уровня «посложнее». Подсказка к подходу: прямоугольник высоты `h[i]` можно растянуть влево и вправо до ближайших **более низких** столбиков. Значит, для каждого столбика нужны ближайший меньший слева и ближайший меньший справа. Оба даёт один проход возрастающего стека: когда столбик снимается с вершины, текущий `i` это его ближайший меньший справа, а новая вершина стека его ближайший меньший слева. Чтобы в конце снять всё, что осталось, удобно добавить фиктивный столбик высоты 0.

::: trap Pop из пустого стека
Плохо: стек пуст, `len(st)-1` равно -1.

```go
top := st[len(st)-1] // panic: runtime error: index out of range [-1]
```

В задаче про скобки это случается на строке `")("`: закрывающая пришла, когда открытых нет. Хорошо: проверять длину перед каждым снятием и решать, что это значит для задачи.

```go
if len(st) == 0 || st[len(st)-1] != want {
	return false // закрывать нечего или не та скобка
}
st = st[:len(st)-1]
```

И не забудь проверку **после** цикла: `"(("` пройдёт все шаги без ошибок, но стек останется непустым.
:::

::: trap Строгое и нестрогое сравнение в монотонном стеке
Задача «ближайший **строго** больший справа», вход `[7 7 8]`. Плохо: снимаем вершину при `<=`.

```go
for len(st) > 0 && nums[st[len(st)-1]] <= v { // равный тоже снимается
	res[st[len(st)-1]] = i
	st = st[:len(st)-1]
}
// для [7 7 8] получим [1 2 -1]: вторая семёрка «больше» первой
```

Хорошо: снимаем только строго меньших, равные остаются ждать.

```go
for len(st) > 0 && nums[st[len(st)-1]] < v {
	...
}
// [2 2 -1]
```

Проверяй каждое решение на входе из одинаковых элементов: там видно сразу, какой знак нужен. В гистограмме, наоборот, равные можно снимать (`>=`): площадь посчитает последний из равных.
:::

::: trap Очередь, которая держит память
Плохо: долгоживущая очередь указателей на `q[1:]`. Снятые задачи остаются в базовом массиве, сборщик мусора их не освободит до перевыделения.

```go
type Queue struct{ items []*Job }

func (q *Queue) Pop() *Job {
	j := q.items[0]
	q.items = q.items[1:] // ячейку с j больше не видно, но указатель на Job остался в массиве
	return j
}
```

Хорошо: обнулить ячейку перед сдвигом, а для очереди с известным пределом сразу взять кольцевой буфер.

```go
func (q *Queue) Pop() *Job {
	j := q.items[0]
	q.items[0] = nil // теперь Job может быть собран
	q.items = q.items[1:]
	return j
}
```
:::

::: trap Полный и пустой кольцевой буфер неразличимы по индексам
Плохо: хранить только `head` и `tail`. При пустом буфере `head == tail`, и при полном тоже `head == tail`.

```go
func (r *Ring) Empty() bool { return r.head == r.tail }
func (r *Ring) Full() bool  { return r.head == r.tail } // то же условие!
```

Хорошо: хранить число элементов `n` (как в разборе выше) или держать один слот всегда пустым и считать буфер полным при `(tail+1)%cap == head`. Первый способ проще и не тратит ячейку.
:::

## Что выведет программа?

```go
q := make([]int, 0, 4)
q = append(q, 1, 2, 3, 4)
q = q[1:]
fmt.Println(len(q), cap(q))
q = append(q, 5)
fmt.Println(len(q), cap(q))
```

</Predict>

```go
nums := []int{2, 1, 2, 4, 3}
var st []int
for _, v := range nums {
	for len(st) > 0 && st[len(st)-1] <= v {
		st = st[:len(st)-1]
	}
	st = append(st, v)
}
fmt.Println(st)
```

<Predict :options="['[2 1 2 4 3]', '[4 3]', '[4]', '[1 2 3]']" :correct="1">

Стек хранит строго убывающую последовательность. 2; 1 меньше, кладём; следующая 2 снимает 1 и равную 2; 4 снимает 2; 3 меньше 4, кладём. В стеке остались элементы, у которых справа **нет** большего: `[4 3]`.

</Predict>

```go
for i := range 3 {
	defer fmt.Print(i)
}
```

<Predict :options="['012', '210', '333', '222']" :correct="1">

Отложенные вызовы складываются в стек и выполняются при выходе из функции в обратном порядке: последний `defer` первым. Аргументы `fmt.Print(i)` вычисляются в момент `defer`, поэтому сохранены значения 0, 1, 2. Печать `210`.

::: interview
<details><summary>Чем стек отличается от очереди и где они встречаются в бэкенде?</summary>

Стек отдаёт последний добавленный элемент (LIFO), очередь первый (FIFO). Стек: стек вызовов, порядок `defer`, разбор вложенных структур (JSON, скобки, теги), undo, обход в глубину. Очередь: очереди задач и сообщений, буферизованные каналы, обход в ширину, буферы последних N событий.

</details>
<details><summary>Как сделать стек и очередь на слайсе в Go и какая у операций сложность?</summary>

Стек: вершина в конце, `append` и `s[:len(s)-1]`, обе амортизированно O(1). Очередь: `append` в конец и `q[1:]` с начала, тоже амортизированно O(1), но снятые элементы остаются в базовом массиве до перевыделения, а ёмкость окна уменьшается. Для указателей снятые ячейки стоит обнулять. Если размер ограничен, лучше кольцевой буфер.

</details>
<details><summary>Как сделать очередь на двух стеках и почему это O(1)?</summary>

Стек `in` для записи, стек `out` для чтения. Pop берёт из `out`, а если тот пуст, перекладывает в него весь `in` (порядок разворачивается, старейший оказывается на вершине). Отдельный Pop может стоить O(n), но каждый элемент перекладывается ровно один раз за жизнь, поэтому n операций стоят O(n), амортизированно O(1). Обратно из `out` в `in` перекладывать нельзя, иначе получится O(n) на операцию.

</details>
<details><summary>Как сделать стек, который возвращает минимум за O(1)?</summary>

Рядом с каждым элементом хранить минимум всего стека на момент его добавления: второй слайс `mins`, где `mins[i] = min(v, mins[i-1])`. Push и Pop двигают оба слайса, Min читает вершину `mins`. Память O(n). Вариант экономнее: класть в `mins` только значения, которые не больше текущего минимума, и снимать оттуда, когда снимается равный.

</details>
<details><summary>Что такое кольцевой буфер и где он применяется?</summary>

Массив фиксированного размера, индекс головы и счётчик элементов, позиции считаются по модулю размера. Push и Pop строго O(1) без аллокаций. Применяется, когда размер ограничен и важна предсказуемость: буферизованные каналы Go (`hchan` с `sendx`/`recvx`), буферы ввода-вывода, «последние N событий» для логов и метрик. При переполнении либо отказывают, либо перезаписывают старое, либо блокируют писателя.

</details>
<details><summary>Что такое монотонный стек и почему он работает за O(n)?</summary>

Стек, в котором значения (по хранимым индексам) всегда идут по убыванию или по возрастанию. Перед добавлением нового элемента снимаем все, что нарушают порядок, и в момент снятия у снятого элемента находится ответ: новый элемент это его ближайший больший (или меньший) справа. Каждый индекс один раз кладётся и не больше одного раза снимается, поэтому суммарно O(n), хотя внутри цикла цикл.

</details>
<details><summary>Как найти максимум в каждом скользящем окне длины k за O(n)?</summary>

Монотонной очередью (деком) индексов с убывающими значениями. При новом элементе снимаем с конца всех, кто не больше его: они уже никогда не станут максимумом. С начала снимаем индекс, вышедший за окно. Максимум окна всегда в голове. Каждый индекс входит и выходит один раз: O(n). Альтернатива проще в коде, но медленнее: куча с ленивым удалением, O(n log n).

</details>
<details><summary>Как найти самый большой прямоугольник в гистограмме?</summary>

Для каждого столбика прямоугольник его высоты тянется до ближайших более низких столбиков слева и справа. Их даёт возрастающий монотонный стек: когда столбик снимается, текущий индекс это правая граница, новая вершина левая, площадь `h * (i - left - 1)`. Фиктивный столбик высоты 0 в конце выталкивает всё оставшееся. O(n) по времени и памяти. Брутфорс с расширением от каждого столбика O(n²).

</details>
:::
