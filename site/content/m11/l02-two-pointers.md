# Два указателя и префиксные суммы

Две самые «дешёвые» техники алгоритмических задач: никаких новых структур данных, только индексы и один вспомогательный слайс. При этом они превращают O(n²) в O(n) в огромном классе задач на массивы и строки, и именно с них интервьюеры любят начинать.

В бэкенде обе встречаются постоянно, просто под другими именами. Слить два отсортированных списка ID из разных шардов, выкинуть дубли из отсортированной выборки, пройтись по двум отсортированным таблицам одновременно (так работает merge join в PostgreSQL): это два указателя. Посчитать заранее накопленные итоги, чтобы любой отчёт «продажи с 3 по 17 число» отвечал за O(1), а не суммировал строки заново: это префиксные суммы, те же предагрегаты, что лежат в аналитических таблицах.

В уроке разберём обе техники: интуицию, как узнать их по формулировке, шаблоны кода на Go, разбор задач и грабли, особенно с байтами и рунами в строках.

## Два указателя: идея

Брутфорс в задачах «найди пару» перебирает все пары `(i, j)`: O(n²). Два указателя тоже рассматривают пары, но каждый шаг **отбрасывает** сразу много пар, которые точно не подходят, и сдвигает один из индексов. Ключевое свойство: указатели двигаются только в одну сторону. Каждый пройдёт не больше `n` шагов, значит, вся работа O(n).

Отбрасывать пары можно, когда в данных есть **монотонность**: чаще всего вход отсортирован, и сдвиг указателя гарантированно увеличивает или уменьшает какую-то величину.

### Вариант 1: навстречу друг другу

Указатели стоят на концах и сходятся к середине. Классика: в отсортированном слайсе найти пару с суммой `target`.

```go
l, r := 0, len(nums)-1
for l < r {
	sum := nums[l] + nums[r]
	switch {
	case sum == target:
		return l, r
	case sum < target:
		l++ // nums[l] слишком мал для любого r: левее r числа ещё меньше
	default:
		r-- // nums[r] слишком велик для любого l
	}
}
return -1, -1
```

Почему ничего не теряем: если `nums[l] + nums[r] < target`, то `nums[l]` в паре с **любым** элементом левее `r` даст сумму ещё меньше (массив отсортирован). Значит, `nums[l]` не входит ни в одну подходящую пару, и его можно выкинуть, сдвинув `l`. Один шаг отбросил до `n` пар разом.

Тот же каркас решает проверку палиндрома (сравниваем символы с концов), разворот слайса на месте и задачу «сосуд с наибольшим объёмом» из домашки.

### Вариант 2: в одном направлении

Оба указателя идут слева направо, но с разной скоростью. Самая частая форма: **указатель чтения и указатель записи**. Читающий `i` проходит каждый элемент, пишущий `w` отмечает, куда положить следующий «хороший» элемент. Так фильтруют слайс на месте за O(n) и O(1) памяти.

```go
w := 0
for _, v := range nums {
	if keep(v) {
		nums[w] = v
		w++
	}
}
nums = nums[:w]
```

Другая форма: два указателя по **двум** отсортированным слайсам, как в слиянии при сортировке слиянием. И третья: «быстрый и медленный», когда один индекс убегает вперёд, пока не выполнится условие, а второй догоняет. Это уже скользящее окно, ему посвящён отдельный урок.

### Как узнать задачу на два указателя

- Вход **отсортирован** (или его можно отсортировать без потери смысла), и ищут пару или тройку с суммой, разностью, ближайшим значением.
- Требуют работать **на месте** и с O(1) дополнительной памяти: удалить, сдвинуть, переставить.
- Сравнивают начало и конец: палиндромы, развороты.
- Нужно пройти по **двум** отсортированным последовательностям: слить, пересечь, сравнить.
- Брутфорс это два вложенных цикла, но внутренний индекс можно не сбрасывать.

### Разбор 1: квадраты отсортированного массива

> Дан отсортированный по неубыванию слайс целых чисел, возможно с отрицательными. Верни отсортированный слайс их квадратов. Аналог: [LeetCode 977](https://leetcode.com/problems/squares-of-a-sorted-array/).

**Уточняем.** Пустой вход возможен, ответ пустой. Значения до 10⁴ по модулю, квадрат влезает в `int`.

**Пример.** `[-4 -1 0 3 10]` даёт `[0 1 9 16 100]`. Видно, что после возведения в квадрат порядок ломается: отрицательные «переворачиваются».

**Брутфорс.** Возвести всё в квадрат и отсортировать: O(n log n). Работает, но не использует то, что вход уже отсортирован.

**Оптимизация.** Где лежит **самый большой** квадрат? На одном из концов: либо у самого отрицательного числа, либо у самого большого положительного. Ставим указатели на концы, сравниваем модули, больший квадрат пишем в **конец** ответа и сдвигаем этот указатель.

```go
func sortedSquares(nums []int) []int {
	res := make([]int, len(nums))
	l, r := 0, len(nums)-1
	for w := len(nums) - 1; w >= 0; w-- { // заполняем с конца
		if abs(nums[l]) > abs(nums[r]) {
			res[w] = nums[l] * nums[l]
			l++
		} else {
			res[w] = nums[r] * nums[r]
			r--
		}
	}
	return res
}

func abs(x int) int {
	if x < 0 {
		return -x
	}
	return x
}
```

**Проверка руками** на `[-4 -1 0 3 10]`: 10 больше 4, пишем 100; 4 больше 3, пишем 16; 3 больше 1, пишем 9; 1 больше 0, пишем 1; остался 0. Ответ `[0 1 9 16 100]`. Пустой вход: цикл не выполнится, вернётся пустой слайс.

**Сложность:** O(n) по времени, O(n) на ответ, O(1) дополнительно.

### Разбор 2: слить два отсортированных слайса

> Даны два отсортированных слайса. Верни один отсортированный, содержащий элементы обоих. Аналог: [LeetCode 88](https://leetcode.com/problems/merge-sorted-array/) (там слияние на месте в первый массив).

Брутфорс: склеить и отсортировать, O((n+m) log(n+m)). Два указателя: на каждом шаге берём меньший из текущих элементов и двигаем его указатель.

```go
func merge(a, b []int) []int {
	res := make([]int, 0, len(a)+len(b))
	i, j := 0, 0
	for i < len(a) && j < len(b) {
		if a[i] <= b[j] { // <= сохраняет порядок равных: сначала из a
			res = append(res, a[i])
			i++
		} else {
			res = append(res, b[j])
			j++
		}
	}
	res = append(res, a[i:]...) // один из хвостов пуст
	res = append(res, b[j:]...)
	return res
}
```

O(n + m) по времени. Забытые хвосты после цикла это самая частая ошибка в этой задаче: цикл заканчивается, как только **один** слайс исчерпан.

::: hood Два указателя по UTF-8 строке
Строка в Go это байты в UTF-8, у символов разная длина: латиница 1 байт, кириллица 2, эмодзи 4. Поэтому `s[i]` и `s[len(s)-1]` дают байты, а не символы, и указатели нельзя двигать на единицу.

```
"шалаш" в байтах:  d1 88 | d0 b0 | d0 bb | d0 b0 | d1 88
                   ш       а       л       а       ш
```

Первый байт `d1`, последний `88`. Сравнение байтов с концов скажет, что это не палиндром.

Два решения. Простое: `rs := []rune(s)` и обычные индексы по рунам, это O(n) дополнительной памяти. Без копии: пакет `unicode/utf8` умеет декодировать руну **с начала** (`utf8.DecodeRuneInString(s[i:])`) и **с конца** (`utf8.DecodeLastRuneInString(s[:j])`), обе функции возвращают руну и её длину в байтах. Двигаешь `i` вперёд на длину левой руны, `j` назад на длину правой. Подстроки `s[i:]` и `s[:j]` не копируют данные, так что выходит O(1) дополнительной памяти.
:::

## Префиксные суммы

Задача: дан массив и много запросов «сумма с `l` по `r`». Каждый запрос циклом стоит O(n), `q` запросов стоят O(n·q). При `n = q = 10⁵` это 10¹⁰.

Идея: один раз посчитать накопленные суммы, а потом отвечать на любой запрос вычитанием.

```
nums    =     3   1   4   1   5
prefix  = 0   3   4   8   9  14
          ^ prefix[0] = 0: сумма пустого начала
```

`prefix[i]` это сумма **первых `i` элементов**, то есть `nums[0..i-1]`. Длина `prefix` на единицу больше длины `nums`. Тогда сумма на отрезке `[l, r]` включительно:

```
sum(l..r) = prefix[r+1] - prefix[l]
```

Например, `nums[1..3] = 1 + 4 + 1 = 6`, и `prefix[4] - prefix[1] = 9 - 3 = 6`.

```go
prefix := make([]int, len(nums)+1)
for i, v := range nums {
	prefix[i+1] = prefix[i] + v
}
// сумма nums[l..r] включительно:
sum := prefix[r+1] - prefix[l]
```

Предподсчёт O(n), каждый запрос O(1), памяти O(n).

Почему `prefix[0] = 0` и лишняя ячейка: так формула работает и для `l = 0`, без отдельной ветки. Удобно думать о полуинтервалах `[l, r)`: сумма на них равна `prefix[r] - prefix[l]`, а пустой отрезок `[l, l)` даёт 0. Полуинтервалы в Go и так везде: `s[l:r]` устроен именно так.

### Как узнать задачу на префиксные суммы

- Много запросов суммы (количества, среднего) на отрезках неизменного массива.
- «Сумма подотрезка равна `k`», «сколько подотрезков с суммой...»: префиксные суммы плюс `map`, это следующий урок.
- «Индекс, где сумма слева равна сумме справа», «разбить массив на части с равными суммами».
- Вместо суммы может быть любая операция, у которой есть обратная: произведение без нулей, XOR. А вот для минимума и максимума префиксы не работают: «минимум на `[l, r]`» не вычисляется из двух префиксных минимумов.

### Разбор 3: произведение всех, кроме себя

> Дан слайс `nums`. Верни слайс `res`, где `res[i]` равен произведению всех элементов, кроме `nums[i]`. Делить нельзя. Аналог: [LeetCode 238](https://leetcode.com/problems/product-of-array-except-self/).

**Уточняем.** Почему нельзя делить? Потому что могут быть нули: `[-1 1 0 -3 3]`. Длина от 2 до 10⁵, произведения влезают в `int`.

**Брутфорс.** Для каждого `i` перемножить остальные: O(n²).

**Оптимизация.** `res[i]` это (произведение всего **левее** `i`) × (произведение всего **правее** `i`). Первое это префиксное произведение, второе суффиксное. Можно не заводить два слайса: первым проходом записать в `res` префиксы, вторым, справа налево, домножить на суффикс, который держим в одной переменной.

```go
func productExceptSelf(nums []int) []int {
	n := len(nums)
	res := make([]int, n)
	left := 1 // произведение nums[0..i-1]
	for i := 0; i < n; i++ {
		res[i] = left
		left *= nums[i]
	}
	right := 1 // произведение nums[i+1..n-1]
	for i := n - 1; i >= 0; i-- {
		res[i] *= right
		right *= nums[i]
	}
	return res
}
```

**Проверка** на `[1 2 3 4]`: после первого прохода `res = [1 1 2 6]`, после второго `[24 12 8 6]`. На `[-1 1 0 -3 3]` получается `[0 0 9 0 0]`: ненулевое значение только на месте нуля, ведь в его произведение сам ноль не входит.

**Сложность:** O(n) по времени, O(1) дополнительной памяти, если не считать ответ.

### Обратная операция: разностный массив

Если задача наоборот, много раз «прибавь `x` ко всем элементам с `l` по `r`», а в конце нужен итоговый массив, используют разностный массив: `diff[l] += x`, `diff[r+1] -= x`, а в конце один проход префиксной суммы по `diff` восстанавливает значения. Каждое обновление O(1) вместо O(n). Пример из жизни: сколько бронирований активно в каждый день, если известны даты заезда и выезда.

::: trap Сравнение байтов вместо символов
Плохо: работает на латинице и ломается на кириллице, потому что `s[i]` это байт.

```go
func isPal(s string) bool {
	for i, j := 0, len(s)-1; i < j; i, j = i+1, j-1 {
		if s[i] != s[j] {
			return false
		}
	}
	return true
}
// isPal("шалаш") == false
```

Хорошо: указатели по рунам.

```go
func isPal(s string) bool {
	rs := []rune(s)
	for i, j := 0, len(rs)-1; i < j; i, j = i+1, j-1 {
		if rs[i] != rs[j] {
			return false
		}
	}
	return true
}
```

Отдельно помни, что `strings.ToLower` и `unicode.ToLower` работают с Unicode, а сравнение «буква ли это» через `c >= 'a' && c <= 'z'` выкинет все русские буквы. Для этого есть `unicode.IsLetter` и `unicode.IsDigit`.
:::

::: trap Off-by-one в префиксных суммах
Плохо: `prefix` той же длины, что `nums`, и формула «на глаз».

```go
prefix := make([]int, len(nums))
prefix[0] = nums[0] // паника на пустом nums
for i := 1; i < len(nums); i++ {
	prefix[i] = prefix[i-1] + nums[i]
}
sum := prefix[r] - prefix[l] // теряет nums[l]; для l = 0 нужна отдельная ветка
```

Хорошо: длина `n+1`, `prefix[0] = 0`, одна формула на все случаи.

```go
prefix := make([]int, len(nums)+1)
for i, v := range nums {
	prefix[i+1] = prefix[i] + v
}
sum := prefix[r+1] - prefix[l]
```

Проверяй формулу на отрезке из одного элемента `l == r` и на `l = 0`: там ошибки видны сразу.
:::

::: trap Удаление из слайса внутри цикла
Плохо: каждое удаление сдвигает хвост, это O(n) на удаление и O(n²) в сумме. Плюс легко пропустить элемент, который съехал на место удалённого.

```go
for i := 1; i < len(nums); i++ {
	if nums[i] == nums[i-1] {
		nums = append(nums[:i], nums[i+1:]...)
		i-- // без этого пропустим соседа
	}
}
```

Хорошо: указатели чтения и записи, один проход.

```go
w := 1
for i := 1; i < len(nums); i++ {
	if nums[i] != nums[w-1] {
		nums[w] = nums[i]
		w++
	}
}
nums = nums[:w]
```
:::

::: trap Переполнение сумм
`int` в Go на 64-битных платформах занимает 64 бита и вмещает примерно ±9.2·10¹⁸. Сумма 10⁵ чисел по 10⁹ это 10¹⁴, влезает. А вот в `int32` (если слайс объявлен `[]int32`) сумма переполнится уже на трёх числах по 10⁹, и Go **не сообщит** об этом: значение молча «завернётся». Уточняй диапазоны и считай суммы в `int` или `int64`.
:::

## Что выведет программа?

```go
s := "шалаш"
fmt.Println(s[0] == s[len(s)-1])
```

`s[0]` это первый байт буквы «ш» (`0xd1`), а `s[len(s)-1]` последний байт той же буквы (`0x88`). Байты разные, поэтому `false`, хотя слово палиндром. Индексация строки работает с байтами, для символов нужны руны.

```go
nums := []int{3, 1, 4, 1, 5}
prefix := make([]int, len(nums)+1)
for i, v := range nums {
	prefix[i+1] = prefix[i] + v
}
fmt.Println(prefix[4]-prefix[1], prefix)
```

<Predict :options="['5 [3 4 8 9 14]', '6 [0 3 4 8 9 14]', '9 [0 3 4 8 9 14]', '6 [3 4 8 9 14 0]']" :correct="1">

`prefix = [0 3 4 8 9 14]`. Разность `prefix[4] - prefix[1]` это сумма `nums[1..3]` = 1 + 4 + 1 = 6. Запомни соответствие: `prefix[r+1] - prefix[l]` даёт отрезок `[l, r]` включительно.

</Predict>

```go
nums := []int{1, 1, 2, 3, 3}
k := 1
for i := 1; i < len(nums); i++ {
	if nums[i] != nums[k-1] {
		nums[k] = nums[i]
		k++
	}
}
fmt.Println(k, nums)
```

<Predict :options="['3 [1 2 3]', '3 [1 2 3 3 3]', '3 [1 2 3 0 0]', '5 [1 1 2 3 3]']" :correct="1">

Уникальные значения переносятся в начало: `nums[:3] = [1 2 3]`. Длина слайса при этом не меняется, а хвост остаётся «мусором» от старых значений: `[1 2 3 3 3]`. Поэтому такие функции возвращают `k`, а вызывающий код делает `nums = nums[:k]`.

</Predict>

::: interview
<details><summary>Почему два указателя работают за O(n), хотя внутри цикла есть ещё цикл?</summary>

Потому что указатели двигаются только в одну сторону и никогда не сбрасываются. Каждый может сделать не больше `n` шагов, поэтому суммарное число итераций всех циклов не больше `2n`. Сложность считают по общему числу выполнений тела, а не по числу вложенных `for`.

</details>
<details><summary>Почему в задаче «пара с суммой в отсортированном массиве» сдвиг указателя не теряет ответ?</summary>

Если `nums[l] + nums[r] < target`, то для любого `j ≤ r` сумма `nums[l] + nums[j]` не больше текущей, то есть тоже меньше `target`. Значит, `nums[l]` не участвует ни в одной подходящей паре среди оставшихся, и его можно отбросить. Симметрично для `r`, когда сумма больше. Каждый шаг отбрасывает целую строку или столбец матрицы пар.

</details>
<details><summary>Есть неотсортированный массив и задача найти пару с суммой. Два указателя или хеш-таблица?</summary>

Два варианта. Отсортировать и пройти двумя указателями: O(n log n) времени, O(1) дополнительной памяти, но индексы исходного массива теряются (если нужны индексы, сортируют пары «значение, индекс»). Хеш-таблица: O(n) времени в среднем и O(n) памяти, индексы сохраняются. Если память не жмёт, обычно выбирают `map`. Если вход уже отсортирован, только два указателя.

</details>
<details><summary>Что такое префиксные суммы и когда они нужны?</summary>

`prefix[i]` это сумма первых `i` элементов, `prefix[0] = 0`. Тогда сумма на `[l, r]` равна `prefix[r+1] - prefix[l]` за O(1). Нужны, когда много запросов сумм на отрезках неизменного массива: предподсчёт O(n), потом каждый запрос O(1) вместо O(n). Ещё они основа задач «подотрезок с суммой k» в паре с хеш-таблицей.

</details>
<details><summary>Почему префиксные суммы не работают для минимума на отрезке?</summary>

Сумма обратима: из суммы большего префикса можно вычесть сумму меньшего. Минимум необратим: зная минимум на `[0, r]` и на `[0, l)`, нельзя узнать минимум на `[l, r]`, если минимум всего префикса лежит левее `l`. Для таких запросов нужны другие структуры: разреженная таблица или дерево отрезков.

</details>
<details><summary>Как проверить палиндром для строки на русском языке без лишней памяти?</summary>

Двумя указателями по байтовым позициям, декодируя руны: слева `utf8.DecodeRuneInString(s[i:])`, справа `utf8.DecodeLastRuneInString(s[:j])`. Обе возвращают руну и её длину в байтах, на эту длину и двигаем указатели. Подстроки не копируют данные, поэтому дополнительная память O(1). Вариант проще: `[]rune(s)` и индексы по рунам, но это O(n) памяти.

</details>
<details><summary>Оцени сложность: удаление дубликатов из отсортированного слайса через append(nums[:i], nums[i+1:]...) в цикле.</summary>

Каждое удаление сдвигает хвост, это O(n). Если дубликатов порядка `n`, итог O(n²). Решение через указатели чтения и записи делает то же за один проход: O(n) времени и O(1) памяти.

</details>
<details><summary>Как найти тройки с нулевой суммой быстрее, чем за O(n³)?</summary>

Отсортировать, затем для каждого `i` искать пару с суммой `-nums[i]` двумя указателями на отрезке правее `i`. Это O(n) на каждое `i`, итого O(n²). Дубли троек отсекаются пропуском одинаковых соседей: и для `i`, и для левого указателя после найденной тройки.

</details>
:::
