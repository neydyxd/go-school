# Связные списки

Связный список: цепочка узлов, где каждый узел хранит значение и указатель на следующий. В отличие от слайса, элементы не лежат подряд в памяти, и к пятому элементу нельзя прыгнуть по индексу, надо пройти четыре предыдущих. Зато вставить или удалить узел, если у тебя уже есть указатель на соседа, можно за O(1), ничего не сдвигая.

В прикладном Go-коде списки встречаются редко, и это правильно: слайс почти всегда быстрее (почему, разберём в конце). Но списки живут внутри инфраструктуры, которой ты пользуешься каждый день: очереди горутин, ждущих на канале, в рантайме это связные списки (`waitq` с полями `first` и `last` в `runtime/chan.go`), LRU-кеши строят на двусвязном списке плюс хеш-таблице, планировщики и аллокаторы держат свободные блоки списками. А на собесе задачи на списки любят за другое: они проверяют, умеешь ли ты аккуратно работать с указателями. Одна перепутанная строка, и хвост списка потерян или список зациклился.

В уроке разберём устройство односвязного списка на Go, приём с фиктивной головой, разворот и слияние, технику быстрого и медленного указателей (середина, цикл, n-й с конца) с доказательствами, и пакет `container/list`: как он устроен и почему его редко стоит брать.

## Устройство

```go
type ListNode struct {
	Val  int
	Next *ListNode
}
```

Список задаётся указателем на первый узел, **голову**. Пустой список это `nil`. У последнего узла `Next == nil`. Других «объектов списка» нет: любой указатель на узел это голова списка, который начинается с этого узла.

```
head
 │
 ▼
┌───┬───┐   ┌───┬───┐   ┌───┬─────┐
│ 1 │ ●─┼──▶│ 2 │ ●─┼──▶│ 3 │ nil │
└───┴───┘   └───┴───┘   └───┴─────┘
```

Обход:

```go
for n := head; n != nil; n = n.Next {
	fmt.Println(n.Val)
}
```

Вставка узла `x` после узла `p`: сначала подцепить хвост к `x`, потом `x` к `p`. Порядок важен.

```go
x.Next = p.Next // 1. x знает, что за ним
p.Next = x      // 2. p указывает на x
```

Если поменять строки местами, `p.Next` перезапишется до того, как мы его прочитали, и весь хвост после `p` потерян. Удаление узла после `p` это одна строка: `p.Next = p.Next.Next`, сборщик мусора заберёт выброшенный узел сам.

| Операция | Слайс | Односвязный список |
|---|---|---|
| Доступ по индексу | O(1) | O(n) |
| Вставка/удаление в начале | O(n) | O(1) |
| Вставка/удаление после известного узла | O(n) | O(1) |
| Вставка в конец | амортизированно O(1) | O(1), если хранить указатель на хвост |
| Поиск значения | O(n) | O(n) |
| Память на элемент | только значение | значение, указатель и заголовок аллокации |

### Фиктивная голова

Половина ошибок в задачах на списки связана с головой: удаление первого узла, вставка перед первым, пустой список. Голове не на что «опереться» слева, и код обрастает особыми случаями. Приём: создать **фиктивный** узел (dummy, sentinel) перед головой. Теперь у каждого настоящего узла есть предыдущий, и особых случаев нет. В конце возвращаем `dummy.Next`.

### Разбор 1: удалить все узлы со значением

> Удали из списка все узлы со значением `val` и верни новую голову. Аналог: [LeetCode 203](https://leetcode.com/problems/remove-linked-list-elements/).

**Уточняем.** Подряд могут идти несколько удаляемых, в том числе в начале: `7 7 1 7 2 7` при `val = 7` даёт `1 2`. Все узлы могут быть удалены, тогда ответ `nil`.

Без фиктивной головы нужен отдельный цикл «пока голова удаляемая, сдвигай голову». С ней одна логика на всё:

```go
func removeElements(head *ListNode, val int) *ListNode {
	dummy := &ListNode{Next: head}
	for prev := dummy; prev.Next != nil; {
		if prev.Next.Val == val {
			prev.Next = prev.Next.Next // prev остаётся: новый сосед тоже может быть удаляемым
		} else {
			prev = prev.Next
		}
	}
	return dummy.Next
}
```

Обрати внимание: после удаления `prev` **не** двигаем. Иначе в `7 7` вторая семёрка проскочит проверку. Сложность O(n), памяти O(1).

## Разворот списка

Самая частая задача на списки и кирпичик для многих других (палиндром, переупорядочивание, сложение чисел). Идём по списку и разворачиваем каждый указатель назад. Нужно три переменные: `prev` (уже развёрнутая часть), `cur` (текущий узел), `next` (сохранённый хвост).

```go
func reverse(head *ListNode) *ListNode {
	var prev *ListNode
	for cur := head; cur != nil; {
		next := cur.Next // 1. запомнить хвост, пока не потеряли
		cur.Next = prev  // 2. развернуть указатель
		prev, cur = cur, next // 3. шаг вперёд
	}
	return prev // новая голова: бывший последний узел
}
```

```
шаг 0:  nil   1 → 2 → 3 → nil      prev = nil, cur = 1
шаг 1:  nil ← 1   2 → 3 → nil      prev = 1,   cur = 2
шаг 2:  nil ← 1 ← 2   3 → nil      prev = 2,   cur = 3
шаг 3:  nil ← 1 ← 2 ← 3            prev = 3,   cur = nil, конец
```

Бывшая голова `1` на первом шаге получила `Next = prev = nil`: она стала хвостом. Это не мелочь: если её забыть, `1` и `2` будут указывать друг на друга, и получится цикл.

Рекурсивная версия короче, но тратит O(n) памяти на стек вызовов:

```go
func reverseRec(head *ListNode) *ListNode {
	if head == nil || head.Next == nil {
		return head
	}
	newHead := reverseRec(head.Next)
	head.Next.Next = head // следующий узел теперь указывает на меня
	head.Next = nil       // а я пока хвост; без этой строки будет цикл
	return newHead
}
```

В Go стек горутины растёт динамически (по умолчанию до 1 000 000 000 байт на 64-битных системах, константа `maxstacksize` в `runtime/proc.go`), поэтому рекурсия на миллион узлов не упадёт со stack overflow, как в C, но потратит десятки мегабайт стека. На собесе пиши итеративную и упомяни, что знаешь рекурсивную.

## Слияние двух отсортированных списков

Тот же алгоритм, что слияние слайсов в уроке про два указателя, только вместо копирования значений мы **перецепляем узлы**. Фиктивная голова убирает вопрос «кто первый», а в конце остаток непустого списка цепляется целиком одной строкой, без цикла: это преимущество списка перед слайсом. Забыть этот остаток значит потерять хвост, тест в домашке это ловит.

## Быстрый и медленный указатели

Два указателя идут по списку с разной скоростью: медленный на один узел за шаг, быстрый на два. Приём решает задачи, где в слайсе мы бы просто посчитали индекс, а в списке длина заранее не известна.

### Середина за один проход

Когда быстрый дошёл до конца, медленный прошёл ровно половину.

```go
slow, fast := head, head
for fast != nil && fast.Next != nil {
	slow = slow.Next
	fast = fast.Next.Next
}
// slow: середина; при чётной длине второй из двух средних
```

Условие цикла задаёт, какую из двух середин получим при чётной длине. `fast != nil && fast.Next != nil` даёт **вторую** (у `1 2 3 4` узел 3). `fast.Next != nil && fast.Next.Next != nil` даёт **первую** (узел 2), это удобно, когда нужно разрезать список пополам: `slow` будет последним узлом первой половины. Порядок проверок в `&&` важен: сначала `fast != nil`, иначе `fast.Next` разыменует `nil`.

### Цикл: алгоритм Флойда

Если в списке есть цикл, обход `for n != nil` никогда не закончится. Как узнать о цикле за O(1) памяти? Проще всего хранить посещённые узлы в `map[*ListNode]bool`, но это O(n) памяти.

Алгоритм Флойда, «черепаха и заяц»: запускаем медленный и быстрый указатели. Если цикла нет, быстрый дойдёт до `nil`. Если есть, оба зайдут в цикл, и там быстрый догоняет медленного на **один узел за шаг** (он делает два шага, медленный один). Расстояние между ними уменьшается на 1 каждый шаг, поэтому быстрый не может «перепрыгнуть» медленного: они обязательно встретятся, не позже чем через длину цикла шагов после входа медленного в цикл. Итого O(n) времени и O(1) памяти.

```go
slow, fast := head, head
for fast != nil && fast.Next != nil {
	slow = slow.Next
	fast = fast.Next.Next
	if slow == fast { // сравниваем указатели, а не значения: значения могут повторяться
		return true
	}
}
return false
```

### Где начинается цикл

Вторая половина алгоритма Флойда. Пусть от головы до начала цикла `a` узлов, длина цикла `c`, а встретились указатели в `b` шагах от начала цикла. Медленный прошёл `a + b`, быстрый вдвое больше: `2(a + b)`. Разница между ними целое число кругов: `2(a + b) - (a + b) = a + b = k·c`. Значит, `a = k·c - b`.

Что это означает: если из точки встречи пройти ещё `a` шагов, окажемся в `b + a = k·c` от начала цикла, то есть **ровно в начале цикла**. А из головы за `a` шагов тоже попадаем в начало цикла. Поэтому: после встречи ставим один указатель на голову и двигаем оба **по одному** шагу. Встретятся они в начале цикла.

```
голова → x → x → [S] → x → x
                  ↑          ↓
                  x ← [M] ← x
a = 3 (до начала цикла S), встреча в M
```

Это задача из домашки, а доказательство спрашивают на собесах чаще, чем код.

### n-й с конца

Чтобы удалить n-й с конца узел за один проход, пусти два указателя с **отставанием** на `n`: сначала быстрый уходит на `n` узлов вперёд, потом оба идут вместе. Когда быстрый на последнем узле, медленный стоит прямо **перед** удаляемым. Фиктивная голова здесь спасает от особого случая «удаляем голову» (когда `n` равно длине).

### Разбор 2: переупорядочить список

> Дан список `L0 → L1 → ... → Ln`. Переставь узлы в порядке `L0 → Ln → L1 → Ln-1 → L2 → ...` на месте, значения не меняй. Аналог: [LeetCode 143](https://leetcode.com/problems/reorder-list/).

**Уточняем.** `1 2 3 4` становится `1 4 2 3`, `1 2 3 4 5` становится `1 5 2 4 3`. Новые узлы создавать нельзя, слайс узлов тоже не хотим: O(1) памяти.

**Брутфорс.** Сложить узлы в слайс и собрать заново по индексам: O(n) памяти. Или на каждом шаге искать последний узел: O(n²).

**Оптимизация.** Это три уже знакомых шага: 1) найти середину (первую из двух, чтобы разрезать); 2) развернуть вторую половину; 3) поочерёдно сшить две половины.

```go
func reorderList(head *ListNode) {
	if head == nil || head.Next == nil {
		return
	}
	slow, fast := head, head
	for fast.Next != nil && fast.Next.Next != nil {
		slow, fast = slow.Next, fast.Next.Next
	}
	second := reverse(slow.Next)
	slow.Next = nil // разрезали: первая половина кончается на slow
	for first := head; second != nil; {
		n1, n2 := first.Next, second.Next // сохраняем оба хвоста до перецепления
		first.Next = second
		second.Next = n1
		first, second = n1, n2
	}
}
```

**Проверка** на `1 2 3 4 5`: середина 3, половины `1 2 3` и развёрнутая `5 4`. Сшиваем: `1 5 2 4 3`. На `1 2 3 4`: `1 2` и `4 3`, получаем `1 4 2 3`. Один узел и два узла не меняются.

**Сложность:** O(n) времени, O(1) памяти. Без `slow.Next = nil` первая половина продолжала бы указывать на бывший третий узел, и вышел бы цикл.

### Разбор 3: пересечение двух списков

> Два списка в какой-то момент сливаются и дальше идут общим хвостом (общие **узлы**, а не равные значения). Найди первый общий узел или `nil`. Аналог: [LeetCode 160](https://leetcode.com/problems/intersection-of-two-linked-lists/).

**Брутфорс.** Положить все узлы первого списка в `map` и идти по второму: O(n + m) времени и O(n) памяти.

**Красивое решение за O(1) памяти.** Два указателя идут каждый по своему списку, а дойдя до конца, переходят на **начало другого**. Пусть до слияния у первого `a` узлов, у второго `b`, общий хвост `c`. Первый указатель пройдёт `a + c + b` и окажется в точке слияния, второй `b + c + a`, тоже в ней. Длины путей равны, значит, они придут туда одновременно. Если пересечения нет, оба одновременно станут `nil` после `a + b` шагов.

```go
func getIntersectionNode(a, b *ListNode) *ListNode {
	p, q := a, b
	for p != q {
		if p == nil {
			p = b
		} else {
			p = p.Next
		}
		if q == nil {
			q = a
		} else {
			q = q.Next
		}
	}
	return p // общий узел или nil
}
```

## container/list и почему он редко нужен

В стандартной библиотеке есть `container/list`: **двусвязный** список, где каждый `*list.Element` знает и следующий, и предыдущий элементы.

```go
l := list.New()
e := l.PushBack(1)
l.PushFront(0)
l.InsertAfter(2, e)
l.MoveToFront(e)
for e := l.Front(); e != nil; e = e.Next() {
	fmt.Print(e.Value.(int), " ") // 1 0 2
}
```

Его сила: если у тебя есть `*Element`, то удалить его, переставить в начало или конец можно за O(1). Именно это нужно LRU-кешу: `map` от ключа к элементу даёт поиск за O(1), а список хранит порядок использования. При обращении к ключу элемент переезжает в начало (`MoveToFront`), а при переполнении вытесняется хвост (`Back` и `Remove`). Это задача из домашки и классика собесов.

Почему в остальных случаях лучше слайс:

- **Значения хранятся как `any`.** Пакет появился до дженериков и так и не стал обобщённым: каждое `e.Value` нужно приводить через `e.Value.(int)`, а типовые ошибки ловятся только в рантайме.
- **Аллокация на каждый элемент.** Каждый `PushBack` создаёт `Element` в куче, а значение не указательного типа в `any` часто аллоцируется ещё раз. На ноутбуке автора список из миллиона `int` сделал около двух миллионов аллокаций и занял около 56 байт на элемент против 8 у слайса. Больше объектов значит больше работы сборщику мусора.
- **Плохая локальность.** Узлы разбросаны по куче, процессор не может предугадать следующий адрес, кеш промахивается. Обход того же миллиона в списке в том же замере был в 4 раза медленнее, чем в слайсе, и это на свежей куче, где узлы ещё лежат почти подряд.
- **Вставка в середину слайса O(n), но очень быстрая.** `copy` сдвигает непрерывный кусок памяти, для тысяч элементов это быстрее, чем искать нужное место в списке.

Правило: бери список, только когда нужны частые удаления и перестановки **по уже имеющемуся указателю** на элемент (LRU, очереди с отменой), и при этом не нужен доступ по индексу. В остальных случаях слайс.

::: hood Как устроен container/list
Внутри `List` хранит не голову, а **корневой фиктивный элемент** `root`, и список замкнут в кольцо: `root.next` это первый элемент, `root.prev` последний, а у последнего `next` указывает обратно на `root`. Тот самый приём с фиктивной головой: вставка и удаление никогда не проверяют «а вдруг это голова». Наружу кольцо не видно: `Element.Next()` возвращает `nil`, когда следующий это `root`.

Каждый `Element` хранит указатель на свой список (`e.list`). `Remove` проверяет `e.list == l` и молча ничего не делает, если элемент из другого списка, вместо того чтобы испортить чужую структуру. А после удаления зануляет `e.next`, `e.prev` и `e.list` (в исходнике с комментарием «avoid memory leaks»). Отсюда грабли ниже: у удалённого элемента `Next()` возвращает `nil`.

Нулевое значение `list.List` готово к работе: при первой вставке вызывается `lazyInit`, который замыкает `root` сам на себя.
:::

::: trap Потеря хвоста
Плохо: перезаписали `Next` до того, как сохранили.

```go
for cur != nil {
	cur.Next = prev
	prev = cur
	cur = cur.Next // это уже prev, а не следующий узел: хвост потерян
}
```

Хорошо: каждый раз, когда переписываешь указатель, спроси себя, где теперь живёт то, на что он указывал. Сохрани это в переменную **до** перезаписи.

```go
for cur != nil {
	next := cur.Next
	cur.Next = prev
	prev, cur = cur, next
}
```

В тестах домашки списки собираются из известных узлов, и проверяется длина результата: потерянный хвост виден сразу.
:::

::: trap Случайный цикл
Плохо: рекурсивный разворот без обнуления указателя бывшей головы.

```go
newHead := reverseRec(head.Next)
head.Next.Next = head
return newHead // head.Next всё ещё указывает на второй узел: 1 ⇄ 2
```

Обход такого списка не закончится никогда. Хорошо: `head.Next = nil` после перецепления. Общее правило: у последнего узла результата `Next` обязан быть `nil`, проверяй это. Тесты домашки обходят результат с ограничением на число шагов и падают с сообщением «в списке цикл», а не зависают.
:::

::: trap Разыменование nil
Плохо: проверять только `fast.Next`.

```go
for fast.Next != nil { // пустой список: fast == nil, паника сразу
	slow, fast = slow.Next, fast.Next.Next // при чётной длине fast станет nil...
} // ...и следующая проверка fast.Next тоже паникует
```

Хорошо: `for fast != nil && fast.Next != nil`. Порядок условий важен, `&&` вычисляется слева направо и останавливается на первом `false`. Проверяй каждую функцию на `nil`, одном узле и двух узлах.
:::

::: trap Удаление элементов container/list в цикле
Плохо: удалить элемент и потом взять у него `Next()`.

```go
for e := l.Front(); e != nil; e = e.Next() {
	if bad(e) {
		l.Remove(e) // Remove обнулил e.next, цикл закончится здесь
	}
}
```

Хорошо: сохранить следующий до удаления.

```go
for e := l.Front(); e != nil; {
	next := e.Next()
	if bad(e) {
		l.Remove(e)
	}
	e = next
}
```
:::

## Что выведет программа?

```go
l := list.New()
for i := range 4 {
	l.PushBack(i)
}
for e := l.Front(); e != nil; e = e.Next() {
	if e.Value.(int)%2 == 0 {
		l.Remove(e)
	}
}
fmt.Println(l.Len())
```

<Predict :options="['2', '3', '4', 'паника: nil pointer dereference']" :correct="1">

Первый элемент 0 чётный и удаляется. `Remove` зануляет у него `next`, поэтому `e.Next()` возвращает `nil`, и цикл заканчивается после первой же итерации. Удалён только 0, длина 3. Паники нет: `Element.Next()` для удалённого элемента аккуратно возвращает `nil`.

</Predict>

```go
type Node struct {
	Val  int
	Next *Node
}

n3 := Node{Val: 3}
n2 := Node{Val: 2, Next: &n3}
n1 := Node{Val: 1, Next: &n2}
cur := n1
cur.Next = nil
fmt.Println(n1.Next != nil)
```

<Predict :options="['true', 'false', 'ошибка компиляции', 'паника']" :correct="0">

`cur := n1` копирует **структуру**, а не создаёт ссылку на `n1`. Обнулили `Next` у копии, у `n1` он по-прежнему указывает на `n2`. В коде со списками узлы почти всегда передают как `*Node`, иначе изменения теряются.

</Predict>

```go
// 1 → 2 → 3 → 4
slow, fast := head, head
for fast.Next != nil && fast.Next.Next != nil {
	slow, fast = slow.Next, fast.Next.Next
}
fmt.Println(slow.Val)
```

<Predict :options="['2', '3', '4', 'паника']" :correct="0">

С условием `fast.Next != nil && fast.Next.Next != nil` быстрый указатель останавливается, когда до конца меньше двух шагов: после одного шага `slow = 2`, `fast = 3`, а у 3 нет `Next.Next`. При чётной длине это **первая** из двух середин. С условием `fast != nil && fast.Next != nil` получилась бы вторая, 3.

</Predict>

::: interview
<details><summary>Когда связный список лучше слайса, а когда хуже?</summary>

Лучше, когда много вставок и удалений в произвольных местах **по уже известному узлу**: это O(1) без сдвига. Хуже почти во всём остальном: нет доступа по индексу (O(n)), аллокация на каждый узел, лишние указатели в памяти, плохая локальность кеша процессора, нагрузка на сборщик мусора. На практике слайс быстрее даже для вставок в середину на тысячах элементов, потому что `copy` непрерывной памяти очень дешёвый.

</details>
<details><summary>Как развернуть односвязный список? Сложность?</summary>

Итеративно тремя указателями: сохранить `next := cur.Next`, развернуть `cur.Next = prev`, сдвинуть `prev, cur = cur, next`. В конце `prev` это новая голова. O(n) времени, O(1) памяти. Рекурсивно тоже можно, но это O(n) памяти на стек, и легко забыть обнулить `Next` бывшей головы, получив цикл.

</details>
<details><summary>Как найти середину списка за один проход?</summary>

Быстрый и медленный указатели: медленный на шаг, быстрый на два. Когда быстрый дошёл до конца, медленный в середине. Условие цикла определяет, какую из двух середин получишь при чётной длине: `fast != nil && fast.Next != nil` даёт вторую, `fast.Next != nil && fast.Next.Next != nil` первую (удобно для разрезания пополам).

</details>
<details><summary>Как определить, есть ли в списке цикл, за O(1) памяти? Почему это работает?</summary>

Алгоритм Флойда: медленный и быстрый указатели. Без цикла быстрый дойдёт до `nil`. С циклом оба окажутся в цикле, и там быстрый приближается к медленному ровно на один узел за шаг, поэтому не может его перепрыгнуть и обязательно догонит за число шагов не больше длины цикла. O(n) времени. Альтернатива с `map` посещённых узлов проще, но O(n) памяти.

</details>
<details><summary>Как найти узел, с которого начинается цикл?</summary>

После встречи в алгоритме Флойда поставить один указатель на голову и двигать оба по одному шагу, встреча будет в начале цикла. Доказательство: если до цикла `a` узлов, встреча в `b` от начала цикла, длина цикла `c`, то медленный прошёл `a + b`, быстрый `2(a + b)`, разница кратна `c`: `a + b = k·c`. Значит, от точки встречи до начала цикла `a` шагов по модулю `c`, столько же, сколько от головы.

</details>
<details><summary>Зачем нужна фиктивная голова (dummy node)?</summary>

Чтобы у каждого настоящего узла был предыдущий и не нужно было обрабатывать голову отдельно: удаление первого узла, вставка перед первым, сборка нового списка при слиянии. Создаём узел перед головой, работаем единообразно, возвращаем `dummy.Next`. `container/list` использует этот же приём: корневой элемент `root` замыкает список в кольцо.

</details>
<details><summary>Как устроен LRU-кеш и почему там двусвязный список?</summary>

Хеш-таблица от ключа к узлу двусвязного списка и сам список в порядке использования: спереди свежие, сзади давно не используемые. Get: найти узел по `map`, переставить в начало. Put: обновить или вставить в начало, при переполнении удалить хвост и его ключ из `map` (поэтому в узле хранится и ключ). Все операции O(1). Двусвязный нужен, чтобы вырезать узел из середины за O(1): в односвязном для этого нужен предыдущий, а его не найти быстрее O(n). В Go это `map[K]*list.Element` плюс `container/list`.

</details>
<details><summary>Почему container/list редко используют в Go?</summary>

Значения хранятся как `any`, нужны приведения типов и нет проверки на этапе компиляции, пакет так и не стал дженериком. Каждый элемент это отдельная аллокация, память разбросана по куче, обход медленнее слайса в разы. Он оправдан, когда нужны удаления и перестановки по имеющемуся `*Element` за O(1): LRU, очереди с отменой задач.

</details>
:::
