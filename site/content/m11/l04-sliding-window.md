# Скользящее окно

Скользящее окно это два указателя, которые ограничивают **непрерывный** кусок массива или строки и едут по нему слева направо. Вместо того чтобы пересчитывать каждый подотрезок заново, мы обновляем состояние окна: добавили элемент справа, убрали слева. Задачи «самая длинная подстрока, где...», «самый короткий подотрезок, где...», «сколько подотрезков, где...» в большинстве своём решаются именно так, за O(n) вместо O(n²) или O(n³).

На бэкенде окно встречается буквально. Rate limiter «не больше 100 запросов за последние 60 секунд» держит окно по времени. Метрики вида «среднее время ответа за последние 5 минут» и алерты «больше 50 ошибок за любые 10 минут» считаются окном по логам. Даже в TCP есть «скользящее окно» неподтверждённых пакетов, хотя это уже протокол, а не алгоритм.

В уроке: фиксированное и переменное окно, как понять, что окно применимо (и когда нет), какие состояния держать внутри окна, разбор трёх задач, включая знаменитую «минимальное окно со всеми символами», и типичные ошибки с инициализацией, `map` и рунами.

## Идея

Брутфорс в задаче про подотрезки перебирает все пары `(l, r)`, это O(n²) окон, и ещё O(n) на подсчёт каждого, если считать в лоб. Окно опирается на два наблюдения:

1. Соседние окна почти одинаковы. Окно `[l, r+1]` отличается от `[l, r]` одним элементом, поэтому его характеристику (сумму, счётчики символов) можно **обновить** за O(1), а не считать заново.
2. Часто не нужно смотреть все пары. Если окно `[l, r]` уже «плохое», то и все более широкие окна с тем же `l` плохие, и `l` можно двигать вперёд, не возвращаясь.

Каждый элемент один раз входит в окно (при сдвиге `r`) и один раз выходит (при сдвиге `l`). Поэтому весь алгоритм O(n), даже если в коде два вложенных цикла.

```
nums:  2  3  1  2  4  3
          [l ... r]          окно [1, 3], сумма 6
          ^l       ^r
шаг r:    [l ...... r]       +nums[4]: сумма 10
шаг l:       [l ... r]       -nums[1]: сумма 7
```

### Фиксированное окно

Длина окна задана, `k`. Сначала считаем первое окно, затем сдвигаем на один: прибавляем входящий `nums[r]`, вычитаем выходящий `nums[r-k]`.

```go
sum := 0
for _, v := range nums[:k] {
	sum += v
}
best := sum
for r := k; r < len(nums); r++ {
	sum += nums[r] - nums[r-k] // вошёл nums[r], вышел nums[r-k]
	best = max(best, sum)
}
```

Сразу проверь границы: `k <= 0` и `k > len(nums)` требуют отдельной обработки, иначе `nums[:k]` запаникует или ответ получится бессмысленным.

### Переменное окно

Длина не задана, окно растёт и сжимается по условию. Два шаблона.

**Самое длинное хорошее окно.** Расширяем `r` на каждом шаге; пока окно плохое, сжимаем `l`; после сжатия окно хорошее, обновляем ответ.

```go
l := 0
for r := 0; r < len(a); r++ {
	add(a[r])
	for windowIsBad() {
		remove(a[l])
		l++
	}
	best = max(best, r-l+1)
}
```

**Самое короткое хорошее окно.** Расширяем `r`; пока окно хорошее, обновляем ответ и пробуем сжать `l`.

```go
l := 0
for r := 0; r < len(a); r++ {
	add(a[r])
	for windowIsGood() {
		best = min(best, r-l+1)
		remove(a[l])
		l++
	}
}
```

Есть и третий частый вопрос: **сколько** окон хорошие. Если «хорошесть» сохраняется при сужении (подокно хорошего окна тоже хорошее), то для каждого `r` хороши все окна `[l..r], [l+1..r], ..., [r..r]`, их ровно `r - l + 1`. Прибавляем это число к ответу на каждом шаге.

### Когда окно работает, а когда нет

Окну нужна **монотонность**: расширение окна только «портит» его (или только «чинит»), а сужение наоборот. Например:

- «сумма не больше `S`» при **неотрицательных** числах: добавили элемент, сумма не уменьшилась. Работает.
- «не больше `k` различных символов»: добавили символ, различных не стало меньше. Работает.
- «сумма ровно `k`» при числах **любого знака**: добавили отрицательное число, сумма упала, и было ли окно хорошим, уже непонятно. Не работает. Здесь нужны префиксные суммы с `map` из прошлого урока.

### Как узнать задачу на окно

- Речь о **подотрезке** или **подстроке**, то есть о непрерывном куске (не о подпоследовательности).
- Спрашивают «самый длинный», «самый короткий», «сколько», «максимальная сумма длины `k`».
- Есть ограничение, которое монотонно по длине окна: «не больше `k` различных», «не больше `k` замен», «без повторов», «сумма не меньше `target`» при положительных числах.
- Брутфорс перебирает пары `(l, r)` и пересчитывает каждое окно.

### Состояние окна

Чтобы обновлять окно за O(1), нужно держать его характеристику:

| Нужно знать | Держим |
|---|---|
| сумму | `sum int` |
| сколько каких символов | `cnt map[rune]int` или `[26]int` |
| сколько различных | `len(cnt)`, удаляя ключи с нулевым счётчиком |
| совпадает ли окно с образцом | счётчик расхождений `missing` или `bad` |
| максимум в окне | монотонная очередь (дек), разберём в уроке про стек и очередь |

Последняя строка важна: сумму и счётчики легко «откатить» при удалении элемента слева, а максимум нет. Для максимума в окне нужна отдельная структура.

## Разбор задач

### Разбор 1: окна длины k со средним не меньше порога

> Сколько подотрезков длины `k` имеют среднее значение не меньше `threshold`? Аналог: [LeetCode 1343](https://leetcode.com/problems/number-of-sub-arrays-of-size-k-and-average-greater-than-or-equal-to-threshold/).

**Уточняем.** Числа неотрицательные, до 10⁴, длина до 10⁵. Может ли `k` быть больше длины? Тогда ответ 0.

**Брутфорс.** Для каждого начала посчитать сумму `k` элементов: O(n·k), при `k ≈ n/2` это O(n²).

**Оптимизация.** Фиксированное окно, сумма обновляется за O(1). Ещё один приём: сравниваем не среднее, а сумму с `k * threshold`. Так обходимся без деления и `float64`, а значит, без ошибок округления.

```go
func numOfSubarrays(arr []int, k, threshold int) int {
	if k > len(arr) {
		return 0
	}
	need := k * threshold // сравниваем сумму, а не среднее: без деления и float
	sum := 0
	for _, v := range arr[:k] {
		sum += v
	}
	count := 0
	if sum >= need {
		count++
	}
	for r := k; r < len(arr); r++ {
		sum += arr[r] - arr[r-k]
		if sum >= need {
			count++
		}
	}
	return count
}
```

**Проверка.** `[2 2 2 2 5 5 5 8], k=3, threshold=4`: суммы окон 6, 6, 9, 12, 15, 18; нужно не меньше 12; подходят три последних. Ответ 3.

**Сложность:** O(n) по времени, O(1) памяти.

### Разбор 2: минимальное окно со всеми символами

> Даны строки `s` и `t`. Найди самую короткую подстроку `s`, которая содержит все символы `t` с учётом количества. Если такой нет, верни пустую строку. Аналог: [LeetCode 76](https://leetcode.com/problems/minimum-window-substring/), одна из самых частых «сложных» задач на собесе.

**Уточняем.** Учитываем ли повторы в `t`? Да: для `t = "aa"` в окне нужны две `a`. Регистр различается. Символы любые, считаем руны.

**Брутфорс.** Перебрать все подстроки (O(n²)) и для каждой проверить счётчики (ещё O(n)): O(n³).

**Оптимизация.** Ищем **самое короткое хорошее** окно, хорошесть монотонна: если окно содержит все символы `t`, то и любое более широкое тоже. Значит, шаблон «расширяем `r`, пока хорошо, сжимаем `l`».

Осталось проверять «окно хорошее» за O(1), а не сравнивать счётчики целиком. Заведём `need[r]`: сколько ещё символа `r` не хватает в окне (может уйти в минус, если в окне лишние). И `missing`: сколько **разных** символов ещё не набраны полностью. Окно хорошее, когда `missing == 0`.

```go
func minWindow(s, t string) string {
	sr := []rune(s)
	need := make(map[rune]int)
	for _, r := range t {
		need[r]++
	}
	missing := len(need) // сколько разных рун ещё не набрано в нужном количестве
	bestL, bestLen := 0, -1
	l := 0
	for r, c := range sr {
		need[c]--
		if need[c] == 0 {
			missing--
		}
		for missing == 0 { // окно валидно: сужаем слева
			if bestLen == -1 || r-l+1 < bestLen {
				bestL, bestLen = l, r-l+1
			}
			need[sr[l]]++
			if need[sr[l]] > 0 {
				missing++
			}
			l++
		}
	}
	if bestLen == -1 {
		return ""
	}
	return string(sr[bestL : bestL+bestLen])
}
```

Почему `need[c]--` делаем для **любого** символа, а не только для символов из `t`: для «чужих» символов `need` уходит в минус и никогда не становится положительным, так что на `missing` они не влияют. Это убирает лишние проверки.

**Проверка.** `minWindow("ADOBECODEBANC", "ABC")` даёт `"BANC"`; `minWindow("a", "aa")` даёт `""`, потому что второй `a` нет; `minWindow("привет, мир", "рим")` даёт `"мир"`. Строку переводим в `[]rune` один раз в начале, поэтому индексы окна это номера символов, и срез `sr[bestL : bestL+bestLen]` не разрежет букву пополам.

**Сложность:** O(|s| + |t|) по времени, O(размер алфавита) памяти плюс O(|s|) на `[]rune`.

### Разбор 3: пик нагрузки за любые 60 секунд

Задача из бэкенда: есть отсортированные метки времени запросов (в секундах). Какое наибольшее число запросов попадало в какое-нибудь окно длины 60 секунд? Это вопрос, который задают, когда подбирают лимит для rate limiter.

Окно здесь по **значениям** времени, а не по числу элементов: событие `l` выпадает из окна, когда `times[r] - times[l] >= 60`.

```go
func maxInWindow(times []int64, window int64) int {
	best, l := 0, 0
	for r := range times {
		for times[r]-times[l] >= window {
			l++ // событие l выпало из окна
		}
		best = max(best, r-l+1)
	}
	return best
}
```

Для `[0 10 20 59 60 61 119 200]` и окна 60 ответ 5: метки 10, 20, 59, 60, 61 укладываются в 60 секунд. Внутренний цикл не выйдет за `r`: при `l == r` разность равна 0 и меньше окна. O(n) после сортировки; если метки приходят несортированными, добавится O(n log n).

Настоящие rate limiter'ы не хранят все метки: популярный приём «sliding window counter» держит счётчики двух соседних фиксированных интервалов и взвешивает их. Но в основе та же идея окна.

::: hood Почему окно линейное, хотя циклов два
Посчитаем не итерации внешнего цикла, а события «элемент вошёл» и «элемент вышел». `r` пробегает от 0 до `n-1` ровно один раз: `n` входов. `l` только растёт и никогда не обгоняет `r + 1`: не больше `n` выходов. Каждое событие стоит O(1) (сложение, изменение счётчика в `map`). Итого O(n), это **амортизированный** анализ: отдельная итерация внешнего цикла может сжать окно на сотню элементов, но в сумме сжатий не больше `n`.

Отсюда же видно, как сломать линейность: если на каждом шаге пересчитывать что-то по всему окну (например, `len` от строки окна в рунах через `utf8.RuneCountInString(s[l:r])`, или проверять «все ли счётчики совпали» перебором всего алфавита большой Unicode-строки), то шаг стоит O(размера окна) и всё снова O(n²). Поэтому держим состояние, которое обновляется за O(1): сумму, счётчики, `missing`.
:::

::: trap Начальное значение ответа
Плохо: `best := 0` для максимальной суммы. Если все числа отрицательные, ответ останется 0, хотя такого окна нет.

```go
best := 0
sum := 0
for r := range nums {
	sum += nums[r]
	if r >= k {
		sum -= nums[r-k]
	}
	if r >= k-1 {
		best = max(best, sum)
	}
}
// MaxSumK([-5 -2 -8 -1], 2): вернёт 0 вместо -7
```

Хорошо: начать с суммы первого окна.

```go
sum := 0
for _, v := range nums[:k] {
	sum += v
}
best := sum
for r := k; r < len(nums); r++ {
	sum += nums[r] - nums[r-k]
	best = max(best, sum)
}
```

Для минимума аналогично: не `math.MaxInt` «на глаз», а первое реальное значение или явный флаг «ответа ещё нет».
:::

::: trap Левая граница уехала назад
Ускоренная версия «подстроки без повторов» хранит последнюю позицию каждого символа и прыгает `l` сразу за неё. Но эта позиция может лежать **левее** текущего окна.

```go
// Плохо: на "abba" вернёт 3
if p, ok := last[c]; ok {
	l = p + 1
}
```

```go
// Хорошо: l только растёт
if p, ok := last[c]; ok && p >= l {
	l = p + 1
}
```

На `"abba"`: на второй `b` окно становится `[2, 2]`, затем последняя `a` видит позицию 0 и без проверки отбрасывает `l` назад на 1, окно `"bba"` с повтором.
:::

::: trap len(map) без delete
Плохо: счётчик опустился до нуля, но ключ остался, и `len(cnt)` считает символ, которого в окне уже нет.

```go
cnt[fruits[l]]--
l++
// len(cnt) по-прежнему включает сорт со счётчиком 0
```

Хорошо: удалять ключ, когда счётчик стал нулём.

```go
cnt[fruits[l]]--
if cnt[fruits[l]] == 0 {
	delete(cnt, fruits[l])
}
l++
```

Альтернатива: держать отдельную переменную `distinct` и менять её при переходах счётчика через ноль.
:::

::: trap Окно на числах любого знака
«Самый короткий подотрезок с суммой не меньше `target`» решается окном, только если числа положительные. С отрицательными сужение окна может **увеличить** сумму, и окно пропустит ответ.

```go
// Шаблон «самое короткое хорошее окно» на target = 5 и [-10 3 4 -10 5]
// вернёт 0: сумма окна ни разу не дойдёт до 5, потому что -10 в начале
// тянет её вниз, а сжимать окно цикл начинает только при sum >= target.
// При этом отрезок [5] (и [3 4]) подходит, правильный ответ 1.
```

Если в условии числа любого знака, это сигнал перейти к префиксным суммам: с `map` для «ровно `k`», с монотонной очередью для «не меньше `target`». Всегда уточняй знак чисел до выбора техники.
:::

::: trap Позиции в байтах вместо рун
`for i, c := range s` по строке даёт `i` как **байтовое** смещение. Если задача просит позиции символов (как «найди все анаграммы» в домашке), для `"кот ток окт"` байтовые позиции будут `0 7 14`, а символьные `0 4 8`. Переведи строку в `[]rune` один раз в начале и работай с индексами рун.
:::

```go
k := 2
sum := nums[0] + nums[1]
for r := k; r < len(nums); r++ {
	sum += nums[r] - nums[r-k+1]
	fmt.Print(sum, " ")

```

```go
best, l := 0, 0
for r, c := range s {
```

Правильный ответ для «самой длинной подстроки без повторов» в `"abba"` это 2, но код печатает 3. На последней `a` он находит её прошлую позицию 0 и ставит `l = 1`, хотя окно уже начиналось с 2. Нужно условие `p >= l`.

```go

}
fmt.Println(p)
```

<Predict :options="['100000000000000000000', '7766279631452241920', 'паника: переполнение', 'ошибка компиляции']" :correct="1">

10²⁰ не помещается в 64-битный `int` (максимум около 9.2·10¹⁸). Go не паникует при переполнении целых, значение молча берётся по модулю 2⁶⁴, и получается мусор. В задачах на произведение в окне мало держать инвариант «произведение окна меньше `k`»: если `k` и элементы большие, переполнится уже следующее умножение. Проверяй заранее делением: `prod*v < k` равносильно `prod <= (k-1)/v`, и только потом умножай.

</Predict>

<details><summary>Как понять, что задачу можно решить скользящим окном?</summary>

Спрашивают про непрерывный подотрезок или подстроку (самый длинный, самый короткий, сколько), и условие монотонно по длине: если окно плохое, то и все шире с тем же началом плохие (или наоборот для «хорошего»). Примеры: «не больше `k` различных», «без повторов», «сумма не меньше `target` при положительных числах», «фиксированная длина `k`». Если числа любого знака или нужна подпоследовательность, а не подотрезок, окно обычно не подходит.

</details>
<details><summary>Почему окно работает за O(n), если в коде два вложенных цикла?</summary>

Каждый элемент входит в окно один раз (сдвиг `r`) и выходит один раз (сдвиг `l`), а `l` никогда не уменьшается. Всего не больше `2n` сдвигов, каждый O(1), если состояние окна обновляется за O(1). Это амортизированная оценка: отдельная итерация может быть дорогой, но сумма ограничена.

</details>
<details><summary>Чем фиксированное окно отличается от переменного?</summary>

В фиксированном длина `k` задана, на каждом шаге один элемент входит и один выходит, никаких внутренних циклов. В переменном длина определяется условием: `r` расширяет окно, внутренний цикл сжимает `l`, пока окно плохое (для поиска самого длинного) или пока хорошее (для поиска самого короткого).

</details>
<details><summary>Почему окно не работает для «сумма подотрезка равна k» с отрицательными числами? Как решать?</summary>

Окно полагается на монотонность: расширение не уменьшает сумму. С отрицательными числами добавление элемента может уменьшить сумму, и решение о сдвиге `l` становится неверным. Решение: префиксные суммы и `map` частот префиксов, на каждом шаге прибавлять к ответу число префиксов, равных `prefix - k`. O(n) в среднем.

</details>
<details><summary>Как в задаче про анаграммы в окне проверять совпадение счётчиков за O(1)?</summary>

Держать не только счётчики, но и число «расхождений»: сколько символов имеют в окне не то количество, что в образце. При изменении счётчика символа пересчитывать расхождение только для него: стал совпадать, уменьшаем, перестал, увеличиваем. Окно совпадает с образцом, когда расхождений 0. Тогда каждый шаг O(1), а не O(размер алфавита).

</details>
<details><summary>Как посчитать число подотрезков, где ровно k различных чисел?</summary>

«Ровно `k`» не монотонно, а «не больше `k`» монотонно. Поэтому считаем `atMost(k) - atMost(k-1)`, где `atMost` это окно, которое на каждом шаге прибавляет `r - l + 1` (все хорошие окна, заканчивающиеся в `r`). Каждое `atMost` работает за O(n).

</details>
<details><summary>Как найти максимум в каждом окне длины k за O(n)?</summary>

Сумму можно «откатить» вычитанием, максимум нельзя. Нужна монотонная очередь (дек) индексов, в которой значения убывают: новый элемент выталкивает с конца все меньшие себя, а с начала уходят индексы, вышедшие за окно. Голова очереди всегда максимум окна. Каждый индекс входит и выходит один раз, итого O(n). Подробно в уроке про стек и очередь.

</details>
<details><summary>Какие алгоритмы rate limiting ты знаешь и при чём тут окно?</summary>

Fixed window: счётчик на каждую минуту, просто, но на стыке минут можно пропустить двойной всплеск. Sliding log: хранить метки всех запросов за последнее окно и выкидывать старые, это ровно скользящее окно по времени, точно, но память O(запросов). Sliding window counter: взвешенная сумма счётчиков текущего и предыдущего интервалов, компромисс точности и памяти. Ещё token bucket и leaky bucket, они про скорость пополнения, а не про окно.

</details>
