# Графы

Граф это множество вершин и связей между ними. Дерево из прошлого урока частный случай графа: связный и без циклов. В общем случае у вершины сколько угодно соседей, связи могут быть направленными, иметь вес, образовывать циклы, а граф может распадаться на несвязные куски. Поэтому всё, что в дереве давала структура (нет циклов, есть корень), в графе приходится обеспечивать самому: в первую очередь отмечать посещённые вершины.

В бэкенде графы встречаются чаще, чем кажется. Зависимости пакетов (`go mod graph` печатает именно граф) и порядок сборки, миграции и задачи, которые зависят друг от друга, вызовы между микросервисами, друзья и подписчики в соцсети, маршруты доставки. Детектор взаимоблокировок в PostgreSQL ищет цикл в графе «транзакция ждёт транзакцию». Когда планировщик задач решает, что запускать первым, он делает топологическую сортировку.

В уроке: как хранить граф, обход в ширину и кратчайший путь в невзвешенном графе, обход в глубину, компоненты связности и острова в сетке, поиск цикла, топологическая сортировка двумя способами и обзорно алгоритм Дейкстры на `container/heap`.

## Словарь

- **Вершины** (vertices, V) и **рёбра** (edges, E). Сложность алгоритмов на графах пишут через оба числа: O(V + E).
- **Неориентированный** граф: ребро `u - v` работает в обе стороны (дружба). **Ориентированный**: ребро `u -> v` только в одну (подписка, зависимость).
- **Взвешенный**: у ребра есть вес (длина дороги, задержка сети).
- **Степень** вершины: число рёбер. В ориентированном графе отдельно входящая и исходящая.
- **Путь**, **цикл** (путь, который возвращается в начало), **DAG**: ориентированный граф без циклов (directed acyclic graph). Граф зависимостей обязан быть DAG, иначе его нельзя выполнить.
- **Связный** граф: из любой вершины можно дойти до любой. Несвязный распадается на **компоненты связности**.

## Как хранить граф

### Список смежности

Для каждой вершины список её соседей. Вершины пронумерованы `0..n-1`, поэтому это слайс слайсов. Чаще всего граф приходит списком рёбер, и первое, что ты пишешь, это построение списка смежности:

```go
// n вершин, рёбра неориентированные
adj := make([][]int, n)
for _, e := range edges {
	adj[e[0]] = append(adj[e[0]], e[1])
	adj[e[1]] = append(adj[e[1]], e[0]) // для ориентированного этой строки нет
}
```

Память O(V + E), перебор соседей вершины за O(её степени). Это представление по умолчанию: почти все реальные графы **разреженные**, у вершины десятки соседей, а не миллионы. Если вершины это строки (имена сервисов, пакетов), то `map[string][]string`.

### Матрица смежности

`m[u][v] == 1`, если есть ребро. Проверка ребра за O(1), но память O(V²), и перебор соседей тоже O(V) даже для вершины без рёбер. Подходит для маленьких **плотных** графов, где рёбер порядка V². Граф на 100 000 вершин матрицей не хранят: это 10¹⁰ ячеек.

### Список рёбер и неявный граф

Просто слайс пар `{u, v}`: так граф приходит на вход, и так удобно сортировать рёбра по весу (алгоритм Краскала). А иногда граф вообще не хранится: **сетка** это неявный граф, где вершина это клетка `(r, c)`, а соседи вычисляются на лету.

```go
dirs := [4][2]int{{1, 0}, {-1, 0}, {0, 1}, {0, -1}} // вниз, вверх, вправо, влево
for _, d := range dirs {
	r, c := cur[0]+d[0], cur[1]+d[1]
	if r < 0 || r >= rows || c < 0 || c >= cols {
		continue // за краем сетки
	}
	// (r, c) это сосед
}
```

| Представление | Память | Есть ли ребро u-v | Соседи u |
|---|---|---|---|
| Список смежности | O(V + E) | O(deg u) | O(deg u) |
| Матрица смежности | O(V²) | O(1) | O(V) |
| Список рёбер | O(E) | O(E) | O(E) |

## Обход в ширину (BFS)

BFS расходится от старта волнами: сначала все вершины на расстоянии 1, потом на расстоянии 2 и так далее. Инструмент тот же, что в обходе дерева по уровням: **очередь**. Отличие от дерева одно, но важное: в графе можно прийти в вершину повторно (через другой путь или по циклу), поэтому нужен массив посещённых.

```go
func bfs(adj [][]int, start int) []int {
	dist := make([]int, len(adj))
	for i := range dist {
		dist[i] = -1 // -1 значит «ещё не видели»
	}
	dist[start] = 0
	queue := []int{start}
	for len(queue) > 0 {
		u := queue[0]
		queue = queue[1:]
		for _, v := range adj[u] {
			if dist[v] == -1 { // отмечаем при постановке в очередь
				dist[v] = dist[u] + 1
				queue = append(queue, v)
			}
		}
	}
	return dist
}
```

Каждая вершина попадает в очередь один раз, каждое ребро просматривается один (ориентированный) или два раза: **O(V + E)**.

Главное свойство: в **невзвешенном** графе BFS находит кратчайшие пути по числу рёбер. Очередь всегда содержит вершины не больше чем двух соседних уровней, `d` и `d+1`, и все вершины уровня `d` извлекаются раньше любой вершины уровня `d+1`. Поэтому в момент, когда мы впервые видим вершину, мы пришли в неё по самому короткому пути, и `dist[v]` дальше не меняется.

### Восстановление пути

Расстояние часто мало, нужен сам путь. Заводим `parent[v]`: из какой вершины мы впервые пришли в `v`. Путь восстанавливается с конца по цепочке родителей и разворачивается:

```go
// в BFS при первом посещении: parent[v] = u
func path(parent []int, start, target int) []int {
	var p []int
	for v := target; v != -1; v = parent[v] {
		p = append(p, v)
		if v == start {
			slices.Reverse(p)
			return p
		}
	}
	return nil // target недостижима
}
```

Здесь `parent` заполнен `-1` до обхода. Тот же приём работает в DFS и в Дейкстре.

::: hood Очередь на слайсе: что происходит с памятью
`queue = queue[1:]` не копирует данные: новый заголовок слайса смотрит на тот же массив со сдвигом на один элемент, это O(1). Длина и ёмкость при этом уменьшаются на 1 (ёмкость считается от нового начала). Снятые элементы остаются в старом массиве, пока на него ссылается слайс, и сборщик мусора не может их освободить.

```
массив:  [a b c d _ _ _ _]
queue:      ^ len 3, cap 7   после queue = queue[1:]
```

Когда `append` упирается в ёмкость, он выделяет новый массив и копирует туда только живую часть очереди, а старый массив со «съеденным» началом становится мусором. Итог: амортизированно O(1) на операцию, а лишняя память ограничена константой от наибольшего размера очереди: если очередь выросла до миллиона и опустела до десятка элементов, массив на миллион живёт, пока `append` снова не упрётся в ёмкость. Для алгоритмических задач это лучший вариант. `container/list` (двусвязный список) тоже работает, но каждый элемент там отдельная аллокация, и на практике он заметно медленнее. Если очередь живёт долго (сервис, а не функция), лучше кольцевой буфер.
:::

## Обход в глубину (DFS)

DFS идёт вглубь, пока есть непосещённые соседи, и откатывается назад, когда их нет. Рекурсивно это три строчки:

```go
visited := make([]bool, n)
var dfs func(u int)
dfs = func(u int) {
	visited[u] = true
	for _, v := range adj[u] {
		if !visited[v] {
			dfs(v)
		}
	}
}
```

Тоже O(V + E). Глубина рекурсии может дойти до V (цепочка), поэтому на огромных графах пишут итеративно на явном стеке. Простая итеративная версия похожа на BFS, только вместо очереди стек: для поиска компонент её хватает. Но топологической сортировке и поиску цикла нужен момент **выхода** из вершины (все потомки обработаны), а такой обход его не даёт ни при каком способе отметки. Поэтому там либо пишут рекурсивно, либо кладут в стек пару «вершина, индекс следующего соседа» и снимают вершину, только когда соседи кончились.

Что выбрать:

- **BFS**: кратчайший путь по числу рёбер, «ближайший» объект, обход по слоям («друзья друзей»), распространение от нескольких источников сразу (все гнилые апельсины гниют одновременно).
- **DFS**: связность и компоненты, поиск цикла, топологическая сортировка, перебор путей с откатом (backtracking). DFS **не** находит кратчайший путь: он идёт по первой попавшейся ветке.
- Если подходит любой, бери тот, что проще написать без ошибок. На сетке BFS безопаснее по стеку.

## Компоненты связности

Чтобы посчитать компоненты, запускаем обход из каждой ещё не посещённой вершины. Каждый запуск открывает новую компоненту и помечает её целиком.

```go
count := 0
for u := range n {
	if !visited[u] {
		count++
		dfs(u) // помечает всю компоненту u
	}
}
```

Суммарно O(V + E): каждая вершина помечается один раз за весь цикл, а не за каждый запуск. Внешний цикл по всем вершинам критичен для любого алгоритма на несвязном графе: если запустить обход только из вершины 0, вторая компонента останется непроверенной. Задача про двудольность из домашки как раз ловит это.

### Острова в сетке

Классика собеса: сетка из `'1'` (суша) и `'0'` (вода), посчитать острова, соединённые по горизонтали и вертикали. Это те же компоненты связности на неявном графе. Посещённую сушу удобно «затапливать», записывая `'0'` прямо в сетку: тогда отдельный массив `visited` не нужен (если менять вход разрешено, уточни на собесе).

```go
for i := range grid {
	for j := range grid[i] {
		if grid[i][j] == '1' {
			count++
			sink(grid, i, j) // DFS или BFS, заливает остров нулями
		}
	}
}
```

O(rows · cols). Рекурсивный `sink` на сплошной суше 1000×1000 уходит в глубину до миллиона вызовов. В Go это работает (стек горутины растёт до 1 ГБ), в домашке такой тест есть, и рекурсивное решение его проходит. Но BFS через очередь здесь надёжнее, и интервьюер может об этом спросить.

## Поиск цикла

### В неориентированном графе

DFS, который пришёл в уже посещённую вершину, нашёл цикл, **если это не ребро назад к родителю**: ребро `u - v` в списке смежности записано с обеих сторон, и из `v` мы сразу видим `u`. Поэтому передаём в DFS, откуда пришли:

```go
var hasCycle func(u, parent int) bool
hasCycle = func(u, parent int) bool {
	visited[u] = true
	for _, v := range adj[u] {
		if v == parent {
			continue
		}
		if visited[v] || hasCycle(v, u) {
			return true
		}
	}
	return false
}
```

Кратные рёбра между одной парой вершин этот код пропустит (оба ребра ведут к родителю); если они возможны, пропускай не вершину-родителя, а конкретное ребро по его номеру. Альтернатива без DFS: система непересекающихся множеств (union-find): если концы нового ребра уже в одном множестве, ребро замыкает цикл.

### В ориентированном графе: три цвета

Здесь «пришли в посещённую вершину» ещё не цикл. В «ромбе» `0 -> 1 -> 3` и `0 -> 2 -> 3` вершину 3 видим дважды, но цикла нет. Цикл есть, только если мы вернулись в вершину, **из которой ещё не вышли**, то есть в вершину на текущем пути DFS. Поэтому у вершин три состояния:

- **белая**: ещё не были;
- **серая**: вошли и сейчас обходим её потомков (она на текущем пути);
- **чёрная**: полностью обошли, цикла через неё нет.

```go
state := make([]int8, n) // 0 белая, 1 серая, 2 чёрная
var hasCycle func(u int) bool
hasCycle = func(u int) bool {
	state[u] = 1
	for _, v := range adj[u] {
		if state[v] == 1 {
			return true // ребро в вершину на текущем пути
		}
		if state[v] == 0 && hasCycle(v) {
			return true
		}
	}
	state[u] = 2
	return false
}
```

Чёрный цвет нужен не только для правильности, но и для скорости: в чёрную вершину не заходим повторно. Если просто «снимать отметку» при выходе (как в переборе путей), правильность сохранится, но DFS начнёт заново обходить общие части графа, и на графе с большим числом путей время станет экспоненциальным.

## Топологическая сортировка

Дан DAG зависимостей: ребро `a -> b` значит «`a` до `b`». Нужно выстроить вершины в линию так, чтобы все рёбра смотрели вперёд. Так `make` решает, что собирать первым, так планировщик миграций выбирает порядок, так Go-компилятор упорядочивает инициализацию пакетов (сначала импортируемые). Порядок обычно не единственный. Если в графе есть цикл, порядка нет вовсе.

### Алгоритм Кана

Интуиция: первой можно выполнить задачу, у которой нет невыполненных зависимостей, то есть входящая степень 0. Выполнили, вычеркнули её рёбра, у соседей уменьшилась входящая степень, кто-то из них стал свободен.

```go
func kahn(n int, edges [][2]int) []int {
	adj := make([][]int, n)
	indeg := make([]int, n)
	for _, e := range edges { // e[0] -> e[1]
		adj[e[0]] = append(adj[e[0]], e[1])
		indeg[e[1]]++
	}
	var order []int
	for u := range n {
		if indeg[u] == 0 {
			order = append(order, u)
		}
	}
	for i := 0; i < len(order); i++ { // order служит и очередью
		for _, v := range adj[order[i]] {
			indeg[v]--
			if indeg[v] == 0 {
				order = append(order, v)
			}
		}
	}
	if len(order) < n {
		return nil // часть вершин так и не освободилась: цикл
	}
	return order
}
```

O(V + E). Бонус: проверка на цикл бесплатно. Вершины на цикле (и всё, что от них зависит) никогда не получат нулевую входящую степень, и в ответ попадёт меньше `n` вершин. Если нужна конкретная из допустимых сортировок, например лексикографически наименьшая, очередь меняют на кучу из следующего урока.

### Через DFS

Вершина в post-order DFS заканчивается только после всех вершин, достижимых из неё. Значит, если записывать вершины в момент выхода, все зависимые от неё окажутся записаны раньше. Развернув этот список, получаем топологический порядок. Поиск цикла тремя цветами встраивается в тот же обход: ребро в серую вершину значит, что порядка нет.

```go
func topoDFS(adj [][]int) []int {
	state := make([]int8, len(adj)) // 0 белая, 1 серая, 2 чёрная
	order := make([]int, 0, len(adj))
	var visit func(u int) bool // false, если нашли цикл
	visit = func(u int) bool {
		state[u] = 1
		for _, v := range adj[u] {
			if state[v] == 1 || (state[v] == 0 && !visit(v)) {
				return false
			}
		}
		state[u] = 2
		order = append(order, u) // момент выхода: все зависимые уже записаны
		return true
	}
	for u := range adj {
		if state[u] == 0 && !visit(u) {
			return nil
		}
	}
	slices.Reverse(order)
	return order
}
```

Оба способа равноценны по асимптотике, O(V + E). Кан проще объяснить и не упирается в глубину рекурсии; DFS удобен, когда обход уже написан для чего-то ещё.

## Алгоритм Дейкстры обзорно

Во **взвешенном** графе BFS не работает: путь из трёх дешёвых рёбер может быть короче одного дорогого. Дейкстра обобщает BFS: вместо очереди «по слоям» берём из кандидатов вершину с наименьшим известным расстоянием. Для неотрицательных весов это расстояние уже окончательное: любой другой путь в неё проходит через вершину, до которой не ближе, и дальше веса только добавляются.

Шаг алгоритма называется **релаксацией**: если через `u` до `v` выходит короче, чем известно, обновляем `dist[v]` и кладём `v` в очередь с приоритетом. Очередь с приоритетом это куча, в Go `container/heap` (подробно в следующем уроке).

```go
type item struct{ node, dist int }
type minHeap []item

func (h minHeap) Len() int           { return len(h) }
func (h minHeap) Less(i, j int) bool { return h[i].dist < h[j].dist }
func (h minHeap) Swap(i, j int)      { h[i], h[j] = h[j], h[i] }
func (h *minHeap) Push(x any)        { *h = append(*h, x.(item)) }
func (h *minHeap) Pop() any {
	old := *h
	x := old[len(old)-1]
	*h = old[:len(old)-1]
	return x
}

type edge struct{ to, w int }

func dijkstra(adj [][]edge, start int) []int {
	dist := make([]int, len(adj))
	for i := range dist {
		dist[i] = math.MaxInt
	}
	dist[start] = 0
	h := &minHeap{{start, 0}}
	for h.Len() > 0 {
		cur := heap.Pop(h).(item)
		if cur.dist > dist[cur.node] {
			continue // устаревшая запись: вершину уже достали ближе
		}
		for _, e := range adj[cur.node] {
			if d := cur.dist + e.w; d < dist[e.to] {
				dist[e.to] = d
				heap.Push(h, item{e.to, d})
			}
		}
	}
	return dist
}
```

У `container/heap` нет операции «уменьшить приоритет» по значению, поэтому используют **ленивое удаление**: кладём вершину повторно с новым расстоянием, а устаревшие записи пропускаем при извлечении. Записей в куче не больше E, итого **O((V + E) log V)**. Наивный вариант без кучи (каждый раз искать ближайшую вершину перебором) стоит O(V²): для плотных графов это даже нормально, для разреженных на сотни тысяч вершин нет.

Ограничения, о которых спрашивают:

- **Отрицательные веса.** Классическая Дейкстра, которая помечает извлечённую вершину обработанной и больше её не трогает, на отрицательном ребре даёт неверный ответ: «окончательная» вершина может потом подешеветь. Вариант с ленивым удалением из кода выше ответ сохранит (подешевевшая вершина снова попадёт в кучу и будет извлечена повторно), но гарантия O((V + E) log V) пропадает: вершины извлекаются много раз, в худшем случае время растёт экспоненциально, а на отрицательном цикле код не остановится вовсе. Для отрицательных весов берут Беллмана-Форда (O(V·E)), он же находит отрицательные циклы.
- Если все веса 0 или 1, хватает 0-1 BFS на деке, без кучи.
- Для поиска пути к одной цели на карте используют A*: Дейкстра плюс эвристика «примерно сколько осталось».

## Разбор: гниющие апельсины

> Сетка: `0` пусто, `1` свежий апельсин, `2` гнилой. Каждую минуту гнилой портит свежих соседей по четырём направлениям. Через сколько минут сгниют все? Если какой-то свежий не сгниёт никогда, верни -1. Аналог: [LeetCode 994](https://leetcode.com/problems/rotting-oranges/).

**Уточняем.** Если свежих нет с самого начала, ответ 0. Сетка непустая, до 10×10 на LeetCode, но решаем за O(rows · cols).

**Брутфорс.** Каждую минуту проходить всю сетку и портить соседей гнилых: до rows·cols минут по rows·cols клеток, O((rc)²).

**Идея.** Гниль распространяется волнами, ровно как BFS по слоям. Отличие от обычного BFS: источников несколько. Кладём **все** гнилые в очередь сразу, это «слой 0». Номер слоя, на котором сгнил последний свежий, и есть ответ.

```go
func orangesRotting(grid [][]int) int {
	var queue [][2]int
	fresh := 0
	for i := range grid {
		for j, v := range grid[i] {
			switch v {
			case 2:
				queue = append(queue, [2]int{i, j})
			case 1:
				fresh++
			}
		}
	}
	minutes := 0
	for len(queue) > 0 && fresh > 0 {
		next := [][2]int{}
		for _, c := range queue {
			for _, d := range [4][2]int{{1, 0}, {-1, 0}, {0, 1}, {0, -1}} {
				r, k := c[0]+d[0], c[1]+d[1]
				if r >= 0 && r < len(grid) && k >= 0 && k < len(grid[r]) && grid[r][k] == 1 {
					grid[r][k] = 2 // отметка «посещён» прямо в сетке
					fresh--
					next = append(next, [2]int{r, k})
				}
			}
		}
		queue = next
		minutes++
	}
	if fresh > 0 {
		return -1
	}
	return minutes
}
```

**Проверка** на `[[2 1 1] [1 1 0] [0 1 1]]`: слой за слоем гниль доходит до правого нижнего угла за 4 минуты. На `[[2 1 1] [0 1 1] [1 0 1]]` левый нижний апельсин отрезан, ответ -1. **Сложность** O(rows · cols): каждая клетка попадает в очередь не больше одного раза.

::: trap Отметка «посещён» при извлечении, а не при постановке
Плохо: вершина помечается, когда её достали из очереди.

```go

	queue = queue[1:]

		continue
	}
	visited[u] = true
	for _, v := range adj[u] {
		if !visited[v] {
			queue = append(queue, v) // v может встать в очередь много раз
		}
	}
}
```

Ответ останется правильным, но одна вершина попадёт в очередь столько раз, сколько у неё уже обработанных соседей. На плотных графах и сетках очередь раздувается до O(E) записей, а если по ходу считаются расстояния или счётчики, легко посчитать вершину дважды. Хорошо: помечать сразу при `append` в очередь, как в коде BFS выше.
:::

::: trap Два цвета вместо трёх в ориентированном графе

::: trap Дейкстра: «посещён» при добавлении в кучу
Плохо: вершину помечают окончательной, как только положили в кучу, как в BFS.


<details><summary>Чем BFS отличается от DFS и когда что использовать?</summary>

BFS идёт слоями от старта через очередь, DFS уходит вглубь через стек (явный или рекурсию). Оба O(V + E). BFS находит кратчайший путь по числу рёбер, удобен для «ближайшего» и многоисточникового распространения, но держит в памяти целый слой. DFS естественен для связности, поиска цикла, топологической сортировки и перебора с откатом, память O(глубина), но кратчайший путь не находит.

</details>
<details><summary>Почему BFS даёт кратчайший путь в невзвешенном графе?</summary>

Вершины извлекаются из очереди в порядке неубывания расстояния: в очереди одновременно лежат вершины не больше двух соседних уровней, d и d+1, и все уровня d уходят раньше. Значит, когда вершину видят впервые, её родитель на минимально возможном расстоянии, и путь через него кратчайший. С весами это ломается: меньше рёбер не значит дешевле.

</details>
<details><summary>Список смежности или матрица смежности?</summary>

Список смежности: память O(V + E), перебор соседей за степень вершины, подходит для разреженных графов, то есть почти всегда. Матрица: O(V²) памяти, проверка ребра за O(1), но перебор соседей за O(V). Берут для маленьких плотных графов или когда нужна частая проверка «есть ли ребро» (например, алгоритм Флойда на сотнях вершин).

</details>
<details><summary>Как найти цикл в ориентированном и в неориентированном графе?</summary>

Неориентированный: DFS, цикл при встрече посещённой вершины, которая не является родителем текущей (или union-find: ребро внутри одного множества). Ориентированный: DFS с тремя цветами, цикл при ребре в серую вершину, то есть в вершину на текущем пути. Альтернатива для ориентированного: алгоритм Кана, если в топологический порядок попали не все вершины, есть цикл.

</details>
<details><summary>Что такое топологическая сортировка и как её получить?</summary>

Порядок вершин DAG, в котором каждое ребро идёт слева направо: зависимость раньше зависящего. Кан: очередь вершин с нулевой входящей степенью, извлекаем, уменьшаем степени соседей, освободившиеся в очередь. DFS: записываем вершины при выходе и разворачиваем список. Оба O(V + E). Существует только для графа без циклов; порядок обычно не единственный.

</details>
<details><summary>Как работает алгоритм Дейкстры и какая у него сложность?</summary>

Расстояния до старта 0, остальных бесконечность. Каждый раз извлекаем из кучи вершину с минимальным расстоянием, это расстояние окончательное, и релаксируем её рёбра: если через неё до соседа короче, обновляем и кладём соседа в кучу. С двоичной кучей и ленивым удалением O((V + E) log V), с перебором минимума O(V²). Гарантии корректности классической версии и этой сложности есть только для неотрицательных весов.

</details>
<details><summary>Почему Дейкстра не работает с отрицательными весами и что тогда использовать?</summary>

Классическая версия считает извлечённую вершину окончательной, полагаясь на то, что дальнейшие рёбра путь только удлиняют. Отрицательное ребро может сделать уже «закрытую» вершину дешевле, и ответ окажется неверным. Версия с ленивым удалением (без отметки «обработана») ответ сохранит, если нет отрицательного цикла, но вершины будут извлекаться повторно, и оценка O((V + E) log V) перестаёт работать: в худшем случае время экспоненциальное, а на отрицательном цикле алгоритм не завершится. Беллман-Форд: V-1 раз релаксировать все рёбра, O(V·E); дополнительный проход находит отрицательный цикл. Для весов 0 и 1 хватает 0-1 BFS на деке.

</details>
<details><summary>Как посчитать острова в сетке и что может пойти не так?</summary>

Перебрать все клетки, из каждой непосещённой суши запустить DFS или BFS, который пометит весь остров; число запусков и есть ответ. O(rows · cols). Что ломается: забыли пометить посещённые (бесконечный обход), соединили по диагонали, вышли за границу сетки, рекурсивный DFS на огромной сетке упёрся в глубину стека (в Go предел 1 ГБ, в других языках намного раньше).

</details>
<details><summary>Как найти кратчайший путь сразу от нескольких источников?</summary>

Многоисточниковый BFS: положить все источники в очередь с расстоянием 0 и запустить обычный BFS. Он считает расстояние до ближайшего источника для каждой вершины за O(V + E). Примеры: гниющие апельсины, расстояние до ближайшего склада, распространение пожара.

</details>
:::
