# Куча и top-K

Куча (heap) это структура, которая умеет одно, но очень быстро: отдавать минимальный (или максимальный) элемент, пока в неё добавляют новые. Вставка и извлечение минимума за O(log n), просмотр минимума за O(1). Полный порядок она не поддерживает и поэтому дешевле сортировки: сортированный слайс дал бы минимум за O(1), но вставку за O(n).

В бэкенде кучи работают там, где есть «следующий по приоритету». Очередь задач с приоритетами и таймерами: таймеры самого Go (`time.AfterFunc`, `time.Sleep`, таймауты контекста) лежат в куче у каждого P планировщика, причём в 4-арной. Алгоритм Дейкстры из прошлого урока. Top-K: десять самых медленных запросов в логе на миллиард строк, самые частые ошибки за час. Слияние k отсортированных файлов во внешней сортировке и при слиянии сегментов в LSM-хранилищах. Медиана задержки по потоку метрик.

В уроке: как куча устроена в массиве, просеивание вверх и вниз, построение кучи за O(n), пирамидальная сортировка, пакет `container/heap` и его интерфейс, top-K за O(n log k), слияние k списков и медиана потока на двух кучах.

## Как устроена куча

Двоичная куча это **полное** двоичное дерево (все уровни заполнены, последний слева направо) с **свойством кучи**: значение в каждом узле не больше значений детей (это куча минимумов, min-heap). Значит, минимум всегда в корне. Между братьями и между разными ветками порядка нет.

Полное дерево не нужно хранить на указателях: его узлы ложатся в массив по уровням без дыр.

```
            1                 индекс:  0  1  2  3  4  5  6
          /   \               значение: 1  3  2  7  4  5  8
         3     2
        / \   / \             для узла i:
       7   4 5   8              дети  2i+1 и 2i+2
                                родитель (i-1)/2
```

Проверь на примере: у узла с индексом 1 (значение 3) дети с индексами 3 и 4 (значения 7 и 4), родитель (1-1)/2 = 0. Никаких указателей, только арифметика, а значит хорошая локальность в кеше процессора. Высота полного дерева из n узлов равна ⌊log₂ n⌋, отсюда все логарифмы.

## Операции

### Push: просеивание вверх

Новый элемент кладём в конец массива: дерево остаётся полным, но свойство кучи может нарушиться между новым элементом и его родителем. Чиним: пока элемент меньше родителя, меняем их местами (sift up).

```go
func (h *MinHeap) Push(x int) {
	h.data = append(h.data, x)
	i := len(h.data) - 1
	for i > 0 {
		p := (i - 1) / 2
		if h.data[p] <= h.data[i] {
			break // родитель не больше: порядок восстановлен
		}
		h.data[p], h.data[i] = h.data[i], h.data[p]
		i = p
	}
}
```

Элемент поднимается не выше корня, то есть не больше чем на высоту: O(log n).

### Pop: просеивание вниз

Минимум в корне. Забираем его, а на его место ставим **последний** элемент массива (дерево снова полное). Теперь в корне, скорее всего, большое значение. Опускаем его (sift down): сравниваем с **меньшим** из детей и меняемся с ним, пока элемент больше этого ребёнка.

```go
func (h *MinHeap) Pop() (int, bool) {
	if len(h.data) == 0 {
		return 0, false
	}
	top := h.data[0]
	last := len(h.data) - 1
	h.data[0] = h.data[last]
	h.data = h.data[:last]
	siftDown(h.data, 0)
	return top, true
}

func siftDown(a []int, i int) {
	n := len(a)
	for {
		small := i
		if l := 2*i + 1; l < n && a[l] < a[small] {
			small = l
		}
		if r := 2*i + 2; r < n && a[r] < a[small] {
			small = r
		}
		if small == i {
			return
		}
		a[i], a[small] = a[small], a[i]
		i = small
	}
}
```

Почему меняться именно с меньшим ребёнком: он станет родителем другого ребёнка, и только меньший из двух не нарушит свойство кучи. Тоже O(log n).

`Peek` это просто `data[0]`, O(1). Найти произвольный элемент в куче можно только перебором O(n): куча не дерево поиска.

### Heapify: построить кучу за O(n)

Из готового массива кучу можно собрать n вставками за O(n log n). Но есть способ лучше: листья (вторая половина массива) уже кучи из одного элемента, поэтому идём от последнего узла с детьми к корню и каждый просеиваем вниз.

```go
func heapify(a []int) {
	for i := len(a)/2 - 1; i >= 0; i-- {
		siftDown(a, i)
	}
}
```

Почему это O(n), хотя просеиваний n/2 по O(log n) каждое? Потому что почти все узлы низко. Узел на высоте h над листьями опускается не больше чем на h. Узлов высоты 1 около n/4, высоты 2 около n/8, высоты h около n/2^(h+1). Сумма n/4·1 + n/8·2 + n/16·3 + ... = n · Σ h/2^(h+1) ≤ n. Наивный вариант, когда каждый элемент **поднимают** при вставке, дорог именно потому, что дорого поднимать нижние элементы, а их большинство.

Направление важно: если идти от корня к листьям, просеивая вниз, кучи не получится. Минимум, лежащий в последнем листе, не сможет подняться выше своего родителя.

### Пирамидальная сортировка

Куча даёт сортировку на месте за O(n log n) в худшем случае и O(1) памяти. Строим кучу **максимумов**, затем n-1 раз меняем корень (текущий максимум) с последним элементом неотсортированной части и просеиваем новый корень вниз в укороченной куче. Отсортированный хвост растёт справа.

```
[5 3 8 1]  heapify max  [8 3 5 1]
swap 8<->1  [1 3 5 | 8]  sift  [5 3 1 | 8]
swap 5<->1  [1 3 | 5 8]  sift  [3 1 | 5 8]
swap 3<->1  [1 | 3 5 8]
```

Heapsort не стабильна (равные элементы могут поменяться местами) и на практике медленнее quicksort из-за прыжков по памяти. Но у неё гарантированный худший случай, поэтому её используют как страховку: `slices.Sort` в Go это pdqsort, и в исходниках (`slices/zsortordered.go`) видно, что при слишком многих неудачных опорных элементах он переключается на `heapSortOrdered`. Так худший случай остаётся O(n log n).

## container/heap

В стандартной библиотеке нет готового типа «куча». Есть пакет `container/heap`, который реализует алгоритмы просеивания поверх **твоего** типа, если тот реализует интерфейс:

```go
type Interface interface {
	sort.Interface // Len() int, Less(i, j int) bool, Swap(i, j int)
	Push(x any)    // добавить x в конец (len станет Len()+1)
	Pop() any      // убрать и вернуть последний элемент
}
```

Классическая куча целых:

```go
type IntHeap []int

func (h IntHeap) Len() int           { return len(h) }
func (h IntHeap) Less(i, j int) bool { return h[i] < h[j] }
func (h IntHeap) Swap(i, j int)      { h[i], h[j] = h[j], h[i] }
func (h *IntHeap) Push(x any)        { *h = append(*h, x.(int)) }
func (h *IntHeap) Pop() any {
	old := *h
	n := len(old)
	x := old[n-1]
	*h = old[:n-1]
	return x
}

h := &IntHeap{5, 2, 8}
heap.Init(h)    // heapify за O(n)
heap.Push(h, 1) // O(log n)
for h.Len() > 0 {
	fmt.Print(heap.Pop(h), " ") // 1 2 5 8
}
```

Главное, что надо понять про этот API:

- **Твои** методы `Push` и `Pop` не про кучу, они только про «положить в конец» и «снять с конца». Кучу поддерживают функции пакета: `heap.Push(h, x)` вызывает твой `Push`, а потом поднимает элемент; `heap.Pop(h)` меняет корень с последним, опускает новый корень и только потом вызывает твой `Pop`, который забирает бывший корень с конца.
- Поэтому вызывать `h.Push(x)` напрямую нельзя: элемент просто окажется в конце, и свойство кучи сломается молча.
- `Push` и `Pop` меняют длину, им нужен **указательный** получатель. `Len`, `Less`, `Swap` обычно на значении.
- Куча максимумов это та же куча с `Less`, который сравнивает наоборот: `h[i] > h[j]`.
- Ещё две функции: `heap.Fix(h, i)` после изменения приоритета элемента `i` и `heap.Remove(h, i)`. Чтобы знать индекс элемента, в документации пакета есть пример `PriorityQueue`, где каждый элемент хранит свой `index` и обновляет его в `Swap`.
- Сам слайс кучи **не отсортирован**. `fmt.Println(*h)` покажет порядок массива, а не порядок извлечения.

Обобщённой кучи `heap.Heap[T]` в стандартной библиотеке нет и в Go 1.27 (проверено `go doc container/heap`): только интерфейс на `any`. Поэтому в каждом решении пишут эти пять методов; для задач на собесе это нормально, а в рабочем коде можно сделать свою дженерик-обёртку.

::: hood Цена any в container/heap
`heap.Push(h, x any)` и твой `Pop() any` гоняют значения через интерфейс. Положить `int` в `any` значит сохранить указатель на значение, и для этого значение обычно приходится разместить в куче (памяти). Я замерил `testing.AllocsPerRun` для `IntHeap`:

```
значение 7:    Push 0 аллокаций, Pop 0
значение 1000: Push 1 аллокация, Pop 1
```

Маленькие числа бесплатны благодаря оптимизации рантайма: функция `convT64` (`runtime/iface.go`) для значений меньше 256 не выделяет память, а отдаёт указатель на элемент заранее заготовленного массива `staticuint64s`. Всё, что больше, это аллокация на каждую операцию. Для задач на собесе это неважно, а в горячем коде сервиса (своя очередь задач на миллионы операций в секунду) пишут кучу на дженериках без `any` или кладут в кучу указатели.
:::

## Top-K

Найти k самых больших из n элементов. Три подхода, и на собесе ждут, что ты назовёшь все.

1. **Отсортировать** и взять последние k: O(n log n). Просто, но сортирует то, что не нужно.
2. **Куча размера k**: O(n log k) по времени и O(k) памяти. Работает на потоке, когда все n элементов в память не помещаются.
3. **Quickselect**: разбиение как в quicksort, но рекурсия только в ту половину, где лежит k-й элемент. O(n) в среднем, O(n²) в худшем случае; меняет порядок входа и требует его целиком в памяти.

Ключевой момент подхода с кучей, на котором путаются все: для k **наибольших** нужна куча **минимумов**. Она хранит k лучших кандидатов, а на её вершине самый слабый из них. Новый элемент сравниваем с вершиной: если он больше, вытесняет слабейшего.

```go
func topK(nums []int, k int) []int {
	h := &IntHeap{}
	for _, x := range nums {
		if h.Len() < k {
			heap.Push(h, x)
		} else if x > (*h)[0] {
			(*h)[0] = x      // заменили слабейшего
			heap.Fix(h, 0) // и опустили на место
		}
	}
	return *h // k наибольших в порядке кучи
}
```

`(*h)[0] = x` плюс `heap.Fix` дешевле, чем `heap.Pop` плюс `heap.Push`: одно просеивание вместо двух. После прохода вершина кучи это k-й по величине элемент, отсюда задача «k-й наибольший». Самое частое неверное решение: k раз найти максимум перебором и выкинуть его. Это O(n·k), и при k порядка n уже квадрат.

Top-K по частоте (самые частые значения, самые частые ошибки) это то же самое после подсчёта в `map`: куча размера k по частоте, O(n + d log k), где d число различных значений. Есть и линейный вариант: «корзины» по частоте, слайс длины n+1, где в ячейке f лежат значения с частотой f.

## Слияние k отсортированных списков

Даны k отсортированных последовательностей общим размером N, нужна одна отсортированная. Слияние двух ты знаешь по уроку про два указателя. Для k «головы» всех списков кладём в кучу минимумов: на вершине наименьшая из голов, это следующий элемент ответа. Забрали его, и на его место встаёт следующий элемент того же списка.

```
списки:   [1 4 5]   [1 3 4]   [2 6]
куча голов: 1(a) 1(b) 2(c)
забрали 1(a), положили 4(a):  1(b) 2(c) 4(a)
забрали 1(b), положили 3(b):  2(c) 3(b) 4(a)
...
```

В куче не больше k элементов, каждый из N элементов проходит через неё один раз: **O(N log k)**. Наивный вариант, когда на каждом шаге перебираются все k голов, стоит O(N·k). Склеить всё и отсортировать (O(N log N)) работает, пока данные помещаются в память, а слияние кучей работает и на потоках: так устроена внешняя сортировка файлов, которые больше оперативной памяти, и слияние сегментов в LSM-деревьях.

## Медиана потока: две кучи

Числа приходят по одному, после каждого нужна медиана. Держим две кучи:

- `low`: куча **максимумов** с меньшей половиной чисел;
- `high`: куча **минимумов** с большей половиной.

Инварианты: каждый элемент `low` не больше каждого элемента `high`, и размеры отличаются не больше чем на 1 (пусть `low` может быть на один больше). Тогда медиана это вершина `low` при нечётном количестве или среднее вершин при чётном: O(1). Добавление с сохранением инвариантов:

```go
heap.Push(low, x)                // сначала в нижнюю половину
heap.Push(high, heap.Pop(low))   // её максимум переезжает наверх
if high.Len() > low.Len() {      // восстанавливаем баланс размеров
	heap.Push(low, heap.Pop(high))
}
```

Три операции с кучами, O(log n) на число. Перекладка через `high` гарантирует первый инвариант без отдельных сравнений: в `high` всегда уезжает наибольший из `low` вместе с новым числом.

## Разбор: k ближайших точек

> Даны точки на плоскости и число k. Верни k точек, ближайших к началу координат, в любом порядке. Аналог: [LeetCode 973](https://leetcode.com/problems/k-closest-points-to-origin/).

**Уточняем.** Расстояние евклидово, но корень можно не извлекать: сравнение квадратов даёт тот же порядок и обходится без `float64`. Координаты до 10⁴, квадраты помещаются в `int`.

**Брутфорс.** Отсортировать по расстоянию: O(n log n).

**Идея.** Это top-K «наименьших», значит, куча **максимумов** размера k: на вершине самая дальняя из кандидатов, её и вытесняем.

```go
type pt struct{ x, y, d int }
type farHeap []pt

func (h farHeap) Len() int           { return len(h) }
func (h farHeap) Less(i, j int) bool { return h[i].d > h[j].d } // куча максимумов
func (h farHeap) Swap(i, j int)      { h[i], h[j] = h[j], h[i] }
func (h *farHeap) Push(x any)        { *h = append(*h, x.(pt)) }
func (h *farHeap) Pop() any {
	old := *h
	x := old[len(old)-1]
	*h = old[:len(old)-1]
	return x
}

func kClosest(points [][2]int, k int) [][2]int {
	h := &farHeap{}
	for _, p := range points {
		d := p[0]*p[0] + p[1]*p[1]
		if h.Len() < k {
			heap.Push(h, pt{p[0], p[1], d})
		} else if d < (*h)[0].d {
			(*h)[0] = pt{p[0], p[1], d}
			heap.Fix(h, 0)
		}
	}
	res := make([][2]int, 0, k)
	for _, p := range *h {
		res = append(res, [2]int{p.x, p.y})
	}
	return res
}
```

**Проверка** на `[[3 3] [5 -1] [-2 4]]`, k = 2: квадраты расстояний 18, 26, 20. Ответ `[3 3]` и `[-2 4]`. **Сложность** O(n log k) по времени и O(k) памяти.

::: trap h.Push вместо heap.Push
Плохо: вызвать метод своего типа напрямую.

```go
h := &IntHeap{3, 1, 2}
heap.Init(h)                         // [1 3 2]
h.Push(0)                     // просто append: [1 3 2 0]
a, b := heap.Pop(h), heap.Pop(h) // 1, затем 0
```

Ноль лежит в конце и не поднялся, поэтому первым извлекается 1. Хорошо: всегда `heap.Push(h, x)` и `heap.Pop(h)`, свои `Push` и `Pop` вызывает только пакет.
:::

::: trap Не та куча для top-K
Плохо: для k наибольших взять кучу **максимумов** размера k и выкидывать вершину при переполнении.

```go
heap.Push(h, x) // h это куча максимумов
if h.Len() > k {
	heap.Pop(h) // выкинули самый БОЛЬШОЙ
}
// в куче остались k наименьших
```

Хорошо: для k наибольших куча минимумов (вытесняем самого маленького из лучших), для k наименьших куча максимумов. Проговори правило вслух: «на вершине должен быть худший из кандидатов».
:::

::: trap Слайс кучи считают отсортированным
Плохо: напечатать или вернуть `*h` как «отсортированные top-K» или брать `(*h)[1]` как второй минимум.

```go
h := &IntHeap{5, 2, 8, 1}
heap.Init(h)
fmt.Println(*h) // [1 2 8 5], а не [1 2 5 8]
```

Хорошо: гарантирован только `(*h)[0]`. Нужен порядок, извлекай `heap.Pop` по очереди или отсортируй результат.
:::

::: trap Медиана целочисленным делением
Плохо: `float64((a + b) / 2)` сначала делит целые, `(1 + 2) / 2` даёт 1, а не 1.5. Хорошо: `float64(a+b) / 2`. И уточни диапазон: если числа близки к краям `int`, `a+b` переполнится, тогда считай `float64(a)/2 + float64(b)/2`.
:::

`heap.Init` превращает `[5 2 8]` в кучу `[2 5 8]`: 5 опускается на место меньшего ребёнка 2. `heap.Push` дописывает 1 в конец: `[2 5 8 1]`, затем поднимает: родитель индекса 3 это индекс 1 (значение 5), меняем, получаем `[2 1 8 5]`; родитель индекса 1 это корень 2, снова меняем: `[1 2 8 5]`. Слайс кучи не отсортирован, гарантирован только минимум в начале.

</Predict>

```go
h := &IntHeap{3, 1, 2}
heap.Init(h)
h.Push(0) // метод напрямую, не heap.Push
a, b := heap.Pop(h), heap.Pop(h)
fmt.Println(a, b, *h)
```

После `Init` массив `[1 3 2]`. Прямой вызов метода только дописывает: `[1 3 2 0]`, ноль не поднят. Первый `heap.Pop` меняет корень 1 с последним 0, опускает 0 (он меньше детей, остаётся в корне) и снимает с конца 1. Второй `heap.Pop` уже честно отдаёт 0. Остаётся `[2 3]`.
```go
nums := []int{4, 1, 7, 3, 9, 2}
h := &IntHeap{}
for _, x := range nums {
	heap.Push(h, x)
	if h.Len() > 3 {
		heap.Pop(h)
	}
}
fmt.Println((*h)[0])
```

Куча минимумов размера 3 выкидывает наименьший, как только элементов становится 4. В итоге в ней три наибольших: 4, 7, 9, а на вершине наименьший из них, 4. Это и есть третий по величине элемент: так решается «k-й наибольший» за O(n log k).

</Predict>

::: interview
<details><summary>Как устроена двоичная куча и почему её хранят в массиве?</summary>

Это полное двоичное дерево со свойством: родитель не больше детей (для кучи минимумов). Полное дерево без дыр ложится в массив по уровням: дети узла i в 2i+1 и 2i+2, родитель в (i-1)/2. Указатели не нужны, память компактная и дружелюбная к кешу, высота ⌊log₂ n⌋.

</details>
<details><summary>Какова сложность операций кучи?</summary>

Минимум (peek) O(1). Вставка O(log n): элемент в конец и просеивание вверх. Извлечение минимума O(log n): последний элемент в корень и просеивание вниз. Построение из массива O(n) через heapify. Поиск или удаление произвольного элемента по значению O(n), если не хранить индексы; с известным индексом удаление и изменение приоритета O(log n) (`heap.Remove`, `heap.Fix`).

</details>
<details><summary>Почему heapify работает за O(n), а не за O(n log n)?</summary>

Просеиваем вниз только узлы с детьми, начиная с нижних. Узел на высоте h опускается не больше чем на h, а узлов на высоте h примерно n/2^(h+1). Сумма n·Σ h/2^(h+1) сходится и не превышает n. Большинство узлов внизу и почти ничего не стоят. Если строить вставками с просеиванием вверх, дорогими оказываются как раз нижние элементы, и выходит O(n log n).

</details>
<details><summary>Как найти k наибольших элементов и какая куча нужна?</summary>

Куча минимумов размера k: на вершине худший из кандидатов. Каждый новый элемент больше вершины вытесняет её. O(n log k) времени, O(k) памяти, работает на потоке. Альтернативы: сортировка O(n log n) и quickselect O(n) в среднем (O(n²) в худшем, нужен весь массив в памяти). k раз искать максимум перебором это O(n·k).

</details>
<details><summary>Как работает container/heap и почему нельзя вызывать h.Push напрямую?</summary>

Пакет реализует просеивание поверх типа, который реализует `heap.Interface`: `sort.Interface` плюс `Push(any)` и `Pop() any`. Методы типа лишь добавляют в конец и снимают с конца, а порядок кучи поддерживают функции `heap.Init`, `heap.Push`, `heap.Pop`, `heap.Fix`, `heap.Remove`. Прямой вызов `h.Push(x)` кладёт элемент в конец без просеивания, свойство кучи ломается молча. `Push` и `Pop` нужны с указательным получателем, потому что меняют длину слайса.

</details>
<details><summary>Как найти медиану потока чисел?</summary>

Две кучи: куча максимумов для меньшей половины и куча минимумов для большей, размеры отличаются не больше чем на 1. Медиана: вершина большей кучи или среднее двух вершин, O(1). Добавление: положить в нижнюю, перенести её максимум в верхнюю, при перекосе вернуть минимум верхней обратно. O(log n) на число.

</details>
<details><summary>Как слить k отсортированных списков и сколько это стоит?</summary>

Куча из голов всех списков: извлекаем минимальную голову, добавляем в ответ, кладём в кучу следующий элемент её списка. В куче не больше k элементов, итого O(N log k), где N общее число элементов. Работает на потоках без загрузки всего в память, это основа внешней сортировки и слияния сегментов в LSM. Перебор голов на каждом шаге стоит O(N·k).

</details>
<details><summary>Стабильна ли пирамидальная сортировка и где она используется?</summary>

Нет: обмен корня с концом переставляет равные элементы. Она O(n log n) в худшем случае и O(1) по памяти, но медленнее quicksort из-за прыжков по памяти. Поэтому её используют как страховку от худшего случая: интросорт в других языках переключается на heapsort, когда рекурсия разбиения становится слишком глубокой, а pdqsort в `slices.Sort` после примерно log n неудачных (несбалансированных) разбиений.

</details>
<details><summary>Куча, дерево поиска или отсортированный слайс для очереди с приоритетом?</summary>

Отсортированный слайс: минимум O(1), но вставка O(n). Сбалансированное дерево поиска: всё O(log n), плюс можно искать и обходить по порядку, но больше памяти и сложнее. Куча: вставка и извлечение минимума O(log n), построение O(n), компактный массив. Если нужен только «следующий по приоритету», куча проще и быстрее; если нужен ещё поиск по ключу или диапазону, дерево.

</details>
:::
