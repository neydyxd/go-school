# Redis и кеширование

PostgreSQL отвечает за миллисекунды, и для большинства запросов этого достаточно. Но бывают данные, которые читают тысячи раз в секунду и почти не меняют (карточка товара, настройки, профиль), счётчики, которые инкрементируют на каждый запрос (лимиты API, просмотры), и короткоживущие ключи (сессии, коды подтверждения, блокировки). Гонять всё это через Postgres дорого. Для таких задач почти в каждом бэкенде рядом с базой стоит **Redis**.

Redis это хранилище «ключ-значение» в оперативной памяти, отвечающее за десятки микросекунд, со структурами данных вместо простых строк. На собесе по нему спрашивают структуры и их применение, TTL и вытеснение, почему Redis однопоточный и что из этого следует, как устроить кеш и что такое cache stampede, как сделать rate limiter и почему распределённая блокировка на Redis сложнее, чем кажется.

Учебный Redis уже поднят вместе с Postgres (`cd homework && docker compose up -d`), консоль:

```bash
docker compose exec redis redis-cli
```

## Зачем Redis и чем он не является

| Задача | Чем помогает Redis |
|---|---|
| Кеш | ответ за десятки микросекунд, TTL из коробки |
| Сессии, коды из SMS, токены | ключи с автоматическим истечением |
| Rate limiting, счётчики | атомарный `INCR` |
| Рейтинги, топы | sorted set держит порядок сам |
| Простые очереди, pub/sub | списки, `BLPOP`, каналы, Streams |
| Распределённые блокировки | `SET NX PX` (с оговорками, ниже) |

Чем Redis **не является**: основной базой для важных данных. Данные живут в памяти, а на диск попадают снимками (RDB) или журналом команд (AOF). В нашем контейнере включены только снимки (`save 3600 1 300 100 60 10000`: при N изменениях за M секунд), значит, при падении теряются изменения за последние минуты. Транзакций в смысле ACID и внешних ключей нет. Правило: в Redis лежит то, что можно восстановить из основной базы или потерять без катастрофы.

## Структуры данных

Ключ всегда строка, а значение одного из типов. Имена ключей принято строить через двоеточие: `product:42`, `user:7:sessions`, `rl:api:203.0.113.5`.

### Строки и TTL

```
> SET greeting "привет" EX 60
OK
> GET greeting
"привет"
> TTL greeting
(integer) 60
> SET nottl x
OK
> TTL nottl
(integer) -1
> TTL missing
(integer) -2
```

`TTL` возвращает секунды до истечения, `-1` если срока нет, `-2` если ключа нет. Строка хранит до 512 МБ любых байт: текст, JSON, сериализованные структуры. Строка, похожая на число, хранится как число, и с ней работают атомарные счётчики:

```
> INCR counter
(integer) 1
> INCRBY counter 10
(integer) 11
```

Установить, только если ключа нет, одной командой:

```
> SET lock token123 NX PX 30000
OK
> SET lock other NX PX 30000
(nil)
```

### Хеши

Объект с полями, как маленькая таблица на один ключ. Удобно менять отдельное поле, не перезаписывая весь JSON:

```
> HSET user:42 name "Анна" city "Казань" visits 1
(integer) 3
> HINCRBY user:42 visits 1
(integer) 2
> HGETALL user:42
1) "name"
2) "Анна"
3) "city"
4) "Казань"
5) "visits"
6) "2"
```

TTL ставится на весь ключ, а не на поле (в Redis 7.4 появились команды `HEXPIRE` для отдельных полей).

### Списки

Двусвязный список: вставка и извлечение с концов за O(1), доступ по индексу за O(n).

```
> RPUSH queue job1 job2 job3
(integer) 3
> LPOP queue
"job1"
> LRANGE queue 0 -1
1) "job2"
2) "job3"
```

`RPUSH` + `LPOP` это очередь, `LPUSH` + `LPOP` стек. `BLPOP` блокирует клиента, пока в списке не появится элемент: простая очередь задач без опроса. Для надёжных очередей с подтверждениями в Redis есть Streams, а в нашем курсе будет River поверх Postgres.

### Множества

Уникальные элементы без порядка, проверка вхождения за O(1), операции над множествами:

```
> SADD tags:1 go sql redis
(integer) 3
> SADD tags:2 go docker
(integer) 2
> SINTER tags:1 tags:2
1) "go"
> SISMEMBER tags:1 sql
(integer) 1
```

Применения: уникальные посетители за день, теги, «кто лайкнул», чёрные списки.

### Упорядоченные множества (sorted sets)

Каждый элемент со счётом (score), множество всегда отсортировано по счёту. Вставка, удаление, поиск позиции за O(log n): внутри большого множества skip list плюс хеш-таблица (маленькие хранятся компактным списком listpack).

```
> ZADD leaders 120 anna 95 boris 140 vera
(integer) 3
> ZINCRBY leaders 30 boris
"125"
> ZREVRANGE leaders 0 1 WITHSCORES
1) "vera"
2) "140"
3) "boris"
4) "125"
> ZRANK leaders anna
(integer) 0
```

Таблицы рекордов, «топ товаров за неделю», очереди с приоритетом, отложенные задачи (score это время запуска), скользящее окно для rate limiting (score это время запроса).

## TTL, истечение и вытеснение

Ключи с TTL удаляются двумя способами: **лениво** (при обращении Redis видит, что срок вышел, и удаляет) и **активно** (фоновый процесс много раз в секунду проверяет случайную выборку ключей с TTL). Поэтому истёкший ключ сразу перестаёт быть виден (ленивая проверка при обращении), но память освобождается не мгновенно.

Когда память кончается (`maxmemory`), Redis поступает согласно `maxmemory-policy`:

| Политика | Что делает |
|---|---|
| `noeviction` | отказывает в записи с ошибкой OOM. **По умолчанию** |
| `allkeys-lru` | вытесняет давно не использованные ключи среди всех |
| `allkeys-lfu` | вытесняет редко используемые |
| `volatile-lru`, `volatile-lfu`, `volatile-ttl` | то же, но только среди ключей с TTL |
| `allkeys-random`, `volatile-random` | случайные |

```
> CONFIG GET maxmemory-policy
1) "maxmemory-policy"
2) "noeviction"
> CONFIG GET maxmemory
1) "maxmemory"
2) "0"
```

`maxmemory 0` значит «без лимита» (в контейнере Redis съест память хоста). Для Redis, который служит только кешем, ставят лимит и `allkeys-lru` или `allkeys-lfu`: старые данные вытесняются сами. Для Redis с сессиями или очередями `noeviction`, иначе он молча выбросит важное. LRU в Redis приближённый: сравниваются не все ключи, а случайная выборка.

## Однопоточность и атомарность

Команды Redis выполняет **один поток** по очереди, в цикле событий. Сеть может обслуживаться дополнительными потоками (`io-threads` с Redis 6), но сами команды над данными всегда исполняются строго последовательно. Отсюда главное свойство: **каждая команда атомарна**. Два клиента, одновременно сделавшие `INCR`, никогда не потеряют инкремент: в отличие от `count++` в Go без мьютекса.

Почему это быстро, а не медленно: данные в памяти, команды короткие (микросекунды), нет блокировок и переключений контекста. Узкое место обычно сеть, а не CPU.

Обратная сторона: **одна медленная команда останавливает всех**. `KEYS *` на миллионе ключей, `HGETALL` на хеше в сотни тысяч полей, `SMEMBERS` огромного множества, тяжёлый Lua-скрипт: пока они работают, Redis не отвечает никому. Вместо `KEYS` используют итеративный `SCAN` (так тестовый хелпер курса чистит ключи с префиксом), а «большие ключи» дробят.

::: hood Атомарность на нескольких командах
Каждая команда атомарна, но последовательность команд нет: между `GET` и `SET` другой клиент может вклиниться. Три инструмента:

- **MULTI/EXEC**: команды копятся в очереди и выполняются подряд, без вклинивания. Отката нет: если одна команда упала (например, `INCR` по строке-не-числу), остальные всё равно выполнятся. Внутри нельзя использовать результат предыдущей команды для решения.
- **WATCH**: оптимистичная блокировка. `WATCH key`, прочитать, `MULTI ... EXEC`; если ключ изменился после `WATCH`, `EXEC` вернёт пустой ответ, повтори.
- **Lua-скрипты** (`EVAL`): скрипт выполняется целиком атомарно, может читать, ветвиться и писать. Самый гибкий вариант:

```
> EVAL "local v = redis.call('INCR', KEYS[1]); if v == 1 then redis.call('EXPIRE', KEYS[1], ARGV[1]) end; return v" 1 rl 60
(integer) 1
> TTL rl
(integer) 60
```

Имена ключей передают в `KEYS`, остальное в `ARGV`: в кластере Redis по `KEYS` понимает, на какой узел отправить скрипт. В Redis 7 появились ещё и Functions: те же Lua-скрипты, но загруженные в сервер заранее.
:::

## Rate limiting на INCR

Ограничим API: не больше 100 запросов в минуту с одного IP. **Фиксированное окно**: ключ на окно, `INCR`, у нового ключа TTL на длину окна.

```
INCR rl:203.0.113.5         -> 1, 2, 3 ...
EXPIRE rl:203.0.113.5 60 NX -> TTL только у нового окна
```

Если результат `INCR` больше лимита, отвечаем `429 Too Many Requests`. Детали, на которых ошибаются:

- **TTL ставить один раз**, а не на каждом запросе. Иначе активный клиент продлевает окно бесконечно и никогда не получит новую квоту. `EXPIRE ... NX` (Redis 7) ставит срок, только если его нет.
- **INCR и EXPIRE надёжно вместе**. Процесс упал между ними, и у ключа нет TTL: клиент заблокирован навсегда. Решение: `MULTI/EXEC`, Lua или `EXPIRE NX` в той же транзакции.
- **Граница окна**: фиксированное окно пропускает до 2x лимита на стыке (100 запросов в 12:00:59 и 100 в 12:01:00). Если это важно, используют **скользящее окно** на sorted set: `ZADD` время запроса, `ZREMRANGEBYSCORE` всё старше окна, `ZCARD` это число запросов за последние 60 секунд. Или **token bucket**: ведро на N жетонов, пополняемое с постоянной скоростью (так работает `golang.org/x/time/rate`, но в памяти одного процесса).

## Pipelining

Каждая команда это поход по сети: отправить, дождаться ответа. Даже в локальной сети это десятки-сотни микросекунд, а сама команда выполняется за единицы. **Pipelining** отправляет пачку команд, не дожидаясь ответов, и потом читает все ответы разом:

```go
start := time.Now()
for range 1000 {
	rdb.Incr(ctx, "demo:seq")
}
fmt.Println(time.Since(start)) // 105ms

start = time.Now()
cmds, err := rdb.Pipelined(ctx, func(p redis.Pipeliner) error {
	for range 1000 {
		p.Incr(ctx, "demo:pipe")
	}
	return nil
})
fmt.Println(time.Since(start)) // 1ms
```

1000 команд за 105 мс по одной и за 1 мс пачкой (локально, через Docker на маке; цифры у тебя будут другими, порядок разницы тот же). Pipelining **не атомарен**: команды других клиентов могут вклиниться между твоими. Атомарная пачка это `TxPipelined` (MULTI/EXEC внутри).

## go-redis

Официальный клиент `github.com/redis/go-redis/v9` (уже в `homework/go.mod`):

```go
rdb := redis.NewClient(&redis.Options{Addr: "localhost:56379"})
defer rdb.Close()

err := rdb.Set(ctx, "demo:k", "v", time.Minute).Err()
val, err := rdb.Get(ctx, "demo:missing").Result()
fmt.Printf("%q %v %v\n", val, err, errors.Is(err, redis.Nil))
// "" redis: nil true
```

Ключевые моменты:
- `*redis.Client` это **пул соединений** (по умолчанию `PoolSize = 10 * GOMAXPROCS`), создаётся один раз и используется из многих горутин, как `pgxpool`.
- Каждая команда возвращает объект `*Cmd`: `.Result()` даёт значение и ошибку, `.Val()` только значение, `.Err()` только ошибку.
- **Отсутствие ключа это ошибка `redis.Nil`**, а не пустая строка. Её нужно отличать от настоящих ошибок (Redis недоступен) через `errors.Is(err, redis.Nil)`.
- Атомарная пачка:

```go
var incr *redis.IntCmd
_, err := rdb.TxPipelined(ctx, func(p redis.Pipeliner) error {
	incr = p.Incr(ctx, "demo:rl")
	p.ExpireNX(ctx, "demo:rl", time.Minute)
	return nil
})
fmt.Println(incr.Val(), err, rdb.TTL(ctx, "demo:rl").Val()) // 1 <nil> 1m0s
```

- Lua: `redis.NewScript(src)` и `script.Run(ctx, rdb, keys, args...)`. Клиент сначала пробует `EVALSHA` по хешу скрипта и отправляет текст, только если сервер его ещё не видел.
- Хуки (`rdb.AddHook`) перехватывают каждую команду: так подключают логирование, метрики и трейсинг. Тест домашки на cache stampede считает через хук команды `GET`.

::: trap redis.Nil как ошибка сервера
Плохо: любой `err` считать поломкой.

```go
v, err := rdb.Get(ctx, key).Result()
if err != nil {
	return Product{}, err // промах кеша превращается в 500
}
```

Хорошо: промах это нормальная ветка.

```go
v, err := rdb.Get(ctx, key).Result()
switch {
case errors.Is(err, redis.Nil):
	// промах: идём в базу
case err != nil:
	// Redis недоступен: тоже идём в базу, но пишем в лог и метрику
default:
	// попадание
}
```
:::

## Кеширование

### Стратегии

- **Cache-aside** (ленивая загрузка): приложение сначала смотрит в кеш; промах, читает из базы и кладёт в кеш с TTL. Самая частая схема. Плюсы: в кеше только то, что реально читают; Redis упал, приложение работает (медленнее). Минус: первый запрос после промаха медленный.
- **Read-through**: то же, но загрузку делает сам кеш-слой (библиотека), приложение видит только кеш.
- **Write-through**: при записи приложение пишет и в базу, и в кеш. Кеш всегда горячий, но в нём оказываются данные, которые никто не читает, и есть окно рассинхронизации, если одна из записей упала.
- **Write-behind** (write-back): пишем в кеш, в базу асинхронно пачками. Быстро, но риск потерять данные при падении кеша. Для счётчиков просмотров годится, для денег нет.

Схема cache-aside по шагам (код целиком ты напишешь в домашке):

```go
func (c *ProductCache) Get(ctx context.Context, id int64) (Product, error) {
	raw, err := c.rdb.Get(ctx, c.key(id)).Bytes()
	// err == nil: разобрать JSON и вернуть (не разобрался: считать промахом)
	// errors.Is(err, redis.Nil): промах, идём дальше
	// другая ошибка: Redis лежит, вернуть c.load(ctx, id) без кеша
	// промах: p, err := c.load(ctx, id); ошибку вернуть и НЕ кешировать
	// иначе SET ключа с JSON и TTL c.ttl, ошибку записи проглотить
}
```

### Инвалидация

«В программировании две сложные вещи: инвалидация кеша и придумывание имён». Варианты:

1. **Только TTL**: данные устаревают максимум на TTL. Просто и надёжно, подходит, если пять минут устаревания не страшны.
2. **Удалить ключ после записи в базу** (`DEL product:42` после `UPDATE`). Следующее чтение загрузит свежие данные. Это стандарт для cache-aside, TTL оставляют как страховку.
3. **Обновить ключ после записи** (`SET` новым значением). Кажется лучше, но опасно: два параллельных обновления могут записать в кеш в обратном порядке, и в кеше навсегда (до TTL) останется старая версия. Удаление такой гонки не имеет: худший случай это лишний промах.

Порядок важен: сначала база, потом удаление из кеша. Удалишь до коммита, и параллельный читатель успеет положить в кеш старое значение из базы. Но и «база, потом DEL» оставляет маленькое окно: читатель прочитал старое из базы до коммита, а записал в кеш после `DEL`. Поэтому TTL нужен всегда, даже при явной инвалидации.

### Cache stampede

Популярный ключ (главная страница, товар из рекламы) протух. В следующие 50 мс приходят 1000 запросов, все промахиваются и все идут в базу за одним и тем же. База, которую кеш защищал, получает пик и может лечь, а с ней и всё остальное. Это **cache stampede** (эффект толпы, dog-piling).

Защиты:
- **singleflight** внутри процесса: одновременные промахи по одному ключу ждут один запрос к базе;
- **распределённая блокировка** на пересчёт: один инстанс считает, остальные ждут или отдают устаревшее;
- **разброс TTL** (jitter): `ttl + rand(0..10%)`, чтобы прогретые одновременно ключи не протухали в одну секунду;
- **раннее обновление**: отдавать текущее значение и в фоне обновлять ключ незадолго до истечения (stale-while-revalidate).

`golang.org/x/sync/singleflight` (уже в `go.mod`):

```go
var g singleflight.Group
v, err, shared := g.Do("product:42", func() (any, error) {
	return loadFromDB(ctx, 42) // выполнится один раз на всех одновременных вызывающих
})
```

`Do` с одинаковым ключом: первый вызов выполняет функцию, остальные, пришедшие до её завершения, ждут и получают тот же результат (`shared == true`). Если 10 горутин вызвали `Do`, пока первый вызов ещё шёл, функция выполнится один раз. После завершения ключ забывается: singleflight не кеш, он только склеивает **одновременные** вызовы.

::: trap Singleflight без повторной проверки кеша
Плохо:

```go
if p, ok := c.cached(ctx, id); ok {
	return p, nil
}
v, err, _ := c.group.Do(key, func() (any, error) {
	return c.load(ctx, id) // сразу в базу
})
```

Горутина промахнулась, пока предыдущий «полёт» шёл, а вошла в `Do` уже после его завершения: начнётся новый полёт и новый поход в базу, хотя значение уже в кеше. Хорошо: внутри `Do` сначала снова проверить кеш (проще всего вызвать там весь cache-aside `Get`).

Ещё одна тонкость: функция внутри `Do` получает контекст **первого** вызывающего. Он отменился, и все ждущие получат `context canceled`. Если это проблема, внутри используют `context.WithoutCancel(ctx)` с собственным таймаутом.
:::

## Распределённые блокировки

Задача: из пяти инстансов сервиса ночной отчёт должен строить только один. Наивно: `SETNX lock 1`, получилось, работаем, потом `DEL lock`. Проблемы по очереди:

1. **Процесс упал, лок вечный**. Нужен TTL. Но `SETNX` и `EXPIRE` двумя командами снова оставляют окно: упал между ними, лок вечный. Решение: одна команда `SET lock token NX PX 30000`.
2. **Снял чужой лок**. Процесс A взял лок на 30 секунд и задумался на 40 (GC-пауза, медленный запрос, сеть). Лок истёк, его взял B. A проснулся и делает `DEL lock`, снимая лок B. Теперь работать может C. Решение: в значение кладут случайный **токен владельца**, а снимают Lua-скриптом «удалить, только если значение мой токен»:

```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
end
return 0
```

Проверка и удаление двумя командами (`GET`, потом `DEL`) снова оставляют окно, поэтому Lua.
3. **Работа дольше TTL**. Даже с токеном A, проснувшись после истечения, может **продолжить работу** параллельно с B: он не знает, что лок уже не его. Продлевать лок фоновой горутиной можно, но GC-пауза остановит и её. Надёжное решение это **fencing token**: при взятии лока выдаётся монотонно растущий номер, и хранилище, куда пишется результат, отвергает записи с номером меньше уже виденного. Мартин Клеппман разбирает это в статье про Redlock.
4. **Отказ Redis**. Лок записан на мастер, мастер упал до репликации, реплика стала мастером без лока. Алгоритм Redlock (большинство из 5 независимых Redis) пытается это решить, но опирается на предположения о времени, которые Клеппман считает ненадёжными.

Практический вывод для собеса: лок на Redis годится как **оптимизация** (не делать одну работу дважды, ничего страшного, если изредка сделаем), а не как гарантия корректности. Если корректность важна и у тебя уже есть Postgres, бери его: `SELECT ... FOR UPDATE`, `pg_advisory_xact_lock` или уникальное ограничение. Там лок живёт ровно столько, сколько транзакция, и умирает вместе с соединением.

<details><summary>Для чего используют Redis? Почему его не делают основной базой?</summary>

Кеш, сессии, короткоживущие ключи, счётчики и rate limiting, рейтинги на sorted set, простые очереди и pub/sub, распределённые блокировки. Основной базой не делают: данные в памяти, персистентность через снимки или AOF с возможной потерей последних изменений, нет ACID-транзакций, внешних ключей и сложных запросов, объём ограничен памятью.

</details>
<details><summary>Какие структуры данных есть в Redis и где каждую применить?</summary>

Строки (кеш, счётчики `INCR`, флаги и блокировки `SET NX`), хеши (объекты с отдельно изменяемыми полями), списки (очереди, последние N событий), множества (уникальные посетители, теги, пересечения), sorted sets (рейтинги, скользящее окно, отложенные задачи). Ещё есть Streams, HyperLogLog, битовые карты и геоиндексы.

</details>
<details><summary>Redis однопоточный. Почему он быстрый и что из этого следует?</summary>

Данные в памяти, команды короткие, нет блокировок и переключений контекста; узкое место обычно сеть. Следствия: каждая команда атомарна (два `INCR` не потеряют обновление), но одна медленная команда (`KEYS *`, огромный `HGETALL`, долгий Lua) останавливает всех клиентов. Вместо `KEYS` используют `SCAN`, большие ключи дробят.

</details>
<details><summary>Как работают TTL и вытеснение?</summary>

Истёкшие ключи удаляются лениво при обращении и активно фоновой выборкой. При достижении `maxmemory` действует `maxmemory-policy`: по умолчанию `noeviction` (ошибка на запись), для чистого кеша ставят `allkeys-lru` или `allkeys-lfu`, `volatile-*` вытесняют только ключи с TTL.

</details>
<details><summary>Как сделать rate limiter на Redis?</summary>

Фиксированное окно: `INCR key`, у нового ключа `EXPIRE key window NX`, обе команды в `MULTI/EXEC` или Lua, сравнить результат с лимитом. Недостаток: до двух лимитов на стыке окон. Скользящее окно: sorted set с временем запросов, `ZREMRANGEBYSCORE` старых, `ZCARD`, `ZADD`. Token bucket на Lua для сглаженного лимита.

</details>
<details><summary>Чем pipelining отличается от MULTI/EXEC?</summary>

Pipelining отправляет пачку команд без ожидания ответов и экономит сетевые задержки, но не атомарен: команды других клиентов могут вклиниться. MULTI/EXEC выполняет пачку подряд без вклиниваний, но без отката при ошибке одной команды. В go-redis это `Pipelined` и `TxPipelined`.

</details>
<details><summary>Опиши cache-aside. Как инвалидировать кеш?</summary>

Читаем из кеша; при промахе из базы и кладём в кеш с TTL. При изменении данных сначала пишем в базу, потом удаляем ключ (не обновляем: два конкурентных обновления могут записать в кеш в неверном порядке). TTL оставляем всегда как страховку от рассинхронизации. Ошибки загрузки не кешируем (или кешируем «нет такого» отдельно и коротко).

</details>
<details><summary>Что такое cache stampede и как с ним бороться?</summary>

Протух популярный ключ, множество запросов одновременно промахиваются и идут в базу за одним и тем же. Защиты: singleflight в процессе с повторной проверкой кеша, распределённая блокировка на пересчёт, разброс TTL, фоновое раннее обновление.

</details>
<details><summary>Почему распределённая блокировка на SETNX сложнее, чем кажется?</summary>

Нужен TTL, иначе упавший владелец держит лок вечно, а значит, одна команда `SET NX PX`. Нужен токен владельца и атомарное снятие Lua-скриптом, иначе снимешь чужой лок после истечения своего. Даже так владелец после паузы может продолжать работу параллельно с новым: нужен fencing token. Плюс потеря лока при failover. Поэтому лок на Redis годится как оптимизация, а для корректности лучше блокировки Postgres.

</details>
:::
