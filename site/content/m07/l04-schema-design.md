# Проектирование схем

Запросы можно переписать за вечер, а схему базы переделать на живом проекте очень дорого: миграции данных, обратная совместимость, простой. Поэтому на бэкенде схему проектируют до кода, и на собеседовании (особенно на system design) часто просят: «спроектируй таблицы для интернет-магазина / чата / бронирования».

Хорошая схема делает две вещи. Во-первых, не даёт данным противоречить друг другу: email клиента хранится в одном месте, заказ не может ссылаться на несуществующего клиента, цена не бывает отрицательной. Во-вторых, перекладывает проверки с кода на базу. Код на Go может забыть проверку в одном из десяти обработчиков, а ограничение в базе не забудет никогда, даже если данные правят руками через psql.

В этом уроке разбираем нормализацию на примерах, выбор ключей, связи между таблицами, ограничения и то, как их нарушения выглядят для Go-кода, и типы PostgreSQL, на которых чаще всего ошибаются: время, деньги, строки, JSON и перечисления.

## Аномалии: почему одна большая таблица плоха

Представь, что заказы хранятся одной таблицей, как в Excel:

```text
legacy_orders
 order_no | customer_email   | customer_name | customer_city | product   | price | qty
----------+------------------+---------------+---------------+-----------+-------+-----
      101 | anna@example.com | Анна Смирнова | Москва        | Дюна      | 990   | 1
      101 | anna@example.com | Анна Смирнова | Москва        | Солярис   | 650   | 2
      102 | anna@example.com | Анна Смирнова | Москва        | Дюна      | 990   | 1
      103 | boris@example.ru | Борис Петров  | СПб           | Солярис   | 650   | 1
```

Данные об Анне повторены трижды, о «Дюне» дважды. Это рождает три аномалии:

- **Аномалия обновления.** Анна переехала в Казань. Надо обновить три строки, а если обновишь две, у одного клиента окажется два города, и непонятно, какой верный.
- **Аномалия вставки.** Новый товар нельзя добавить, пока его никто не купил: в таблице нет строки «товар без заказа».
- **Аномалия удаления.** Борис отменил единственный заказ, удаляем строку, и вместе с ней пропадает знание, что «Солярис» стоит 650.

Лечится это **нормализацией**: разрезанием таблицы так, чтобы каждый факт хранился ровно в одном месте.

## Нормальные формы

Нормальные формы это ступени: каждая следующая включает требования предыдущей. Для практики хватает первых трёх.

### 1NF: атомарные значения

В каждой ячейке одно значение, без списков и повторяющихся групп колонок.

```text
плохо                                      хорошо
 customer | phones                          customer | phone
----------+----------------------          ----------+-------------
 Анна     | +7 900 111, +7 900 222          Анна     | +7 900 111
                                            Анна     | +7 900 222

плохо: phone1, phone2, phone3 (а если телефонов четыре?)
```

Список в строке нельзя нормально искать (`LIKE '%222%'`?), индексировать и ограничивать. Оговорка: PostgreSQL умеет массивы и `jsonb`, и хранить в них, например, набор тегов допустимо, если ты не ссылаешься на элементы внешними ключами и не обновляешь их по одному. Но по умолчанию начинай с отдельной таблицы.

### 2NF: всё зависит от всего ключа

Требование актуально для составного ключа: каждая неключевая колонка зависит от **всего** ключа, а не от его части.

Возьмём позиции заказа с ключом `(order_no, product)`:

```text
 order_no | product | qty | product_price
----------+---------+-----+---------------
      101 | Дюна    |   1 |           990
      101 | Солярис |   2 |           650
```

`qty` зависит от пары (сколько этого товара в этом заказе), а `product_price` только от `product`. Значит, цена товара переезжает в таблицу товаров. Это нарушение 2NF.

### 3NF: нет транзитивных зависимостей

Неключевые колонки зависят только от ключа, а не друг от друга. В таблице заказов `order_no -> customer_email -> customer_name`: имя зависит от клиента, а не от заказа. Клиент со своими данными уходит в отдельную таблицу, в заказе остаётся ссылка.

Неформальная формулировка всех трёх форм, которую удобно сказать на собесе: «каждая колонка описывает ключ, весь ключ и ничего, кроме ключа».

После нормализации `legacy_orders` превращается в:

```text
users       (id, email, name, city)
products    (id, title, price)
orders      (id, user_id -> users, created_at)
order_items (order_id -> orders, product_id -> products, qty, price)
```

Обрати внимание: в `order_items` снова есть `price`. Это не нарушение: `products.price` это текущая цена товара, а `order_items.price` это цена, по которой его купили. Цена в каталоге поменяется, а сумма старого заказа не должна. Это разные факты, просто с похожими названиями.

Существуют и более строгие формы (BCNF, 4NF, 5NF), но в прикладной работе их почти не обсуждают. Достаточно знать, что они есть.

## Ключи

**Первичный ключ** (`PRIMARY KEY`) однозначно идентифицирует строку: он уникален и не бывает `NULL`. Под него автоматически создаётся уникальный индекс.

### Естественный или суррогатный

- **Естественный ключ** берётся из предметной области: email, ИНН, номер паспорта, ISBN.
- **Суррогатный ключ** не значит ничего, кроме «номер строки»: `id`, который выдаёт база.

Естественные ключи соблазнительны, но реальность их ломает: email меняют, ИНН бывает с ошибкой и его исправляют, у старых книг нет ISBN. Если естественный ключ первичный, его изменение каскадом трогает все ссылающиеся таблицы. Поэтому стандартная практика: **суррогатный первичный ключ плюс `UNIQUE` на естественный**. `users.id` для ссылок, `users.email UNIQUE` для бизнес-правила «один аккаунт на адрес».

Исключение: таблицы-связки вроде `order_items` и `product_tags`. Там естественный составной ключ `(order_id, product_id)` и есть правильный первичный ключ: он заодно запрещает дубли.

### identity, serial или uuid

```sql
id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY   -- современный стандарт SQL
id bigserial PRIMARY KEY                             -- старый способ PostgreSQL
id uuid PRIMARY KEY DEFAULT gen_random_uuid()        -- случайный UUID v4
```

`bigserial` это сокращение: колонка `bigint` с умолчанием `nextval('users_id_seq')` и отдельной последовательностью, имя которой собирается по правилу `<таблица>_<колонка>_seq`. `IDENTITY` делает то же, но по стандарту SQL, а с `ALWAYS` ещё и запрещает вставлять свой `id` без явного `OVERRIDING SYSTEM VALUE`. В новых схемах используй identity.

Чем `uuid` хорош и плох:

| | `bigint` identity | `uuid` |
|---|---|---|
| Размер | 8 байт | 16 байт |
| Можно сгенерировать на клиенте до вставки | нет, номер выдаёт база | да |
| Угадываемость в URL (`/orders/1001`, `/orders/1002`) | да, видно объём бизнеса | нет |
| Слияние данных из разных баз | конфликты | без конфликтов |
| Вставка в B-tree индекс | всегда в конец, компактно | v4 случайный: в случайное место, индекс пухнет и хуже кешируется |

```text
goschool=# SELECT pg_column_size(gen_random_uuid()) AS uuid_bytes,
goschool-#        pg_column_size(1::bigint) AS bigint_bytes,
goschool-#        pg_column_size(1::int) AS int_bytes;
 uuid_bytes | bigint_bytes | int_bytes
------------+--------------+-----------
         16 |            8 |         4
(1 row)
```

Проблему случайной вставки решает UUID версии 7: в начале у него метка времени, и новые значения идут по порядку. В PostgreSQL 18 появилась встроенная функция `uuidv7()`; в 17 его генерируют в приложении (например, пакетом `github.com/google/uuid`). Практичный выбор по умолчанию: `bigint` identity внутри, а если идентификатор светится наружу или создаётся на клиенте, `uuid` (лучше v7).

`int` вместо `bigint` экономит 4 байта, но 2,1 миллиарда строк заканчиваются быстрее, чем кажется (логи, события), а смена типа ключа на большой таблице это долгая блокирующая миграция. Для ключей бери `bigint`.

## Связи

```text
1-1   users ──── user_profiles          у пользователя не больше одного профиля
      user_profiles.user_id PRIMARY KEY REFERENCES users(id)

1-N   users ───< orders                 у пользователя много заказов
      orders.user_id REFERENCES users(id)

N-N   orders >──< products              в заказе много товаров, товар во многих заказах
      order_items(order_id REFERENCES orders, product_id REFERENCES products,
                  PRIMARY KEY (order_id, product_id))
```

- **Один к одному.** Внешний ключ в зависимой таблице, плюс уникальность на нём. Проще всего сделать внешний ключ первичным ключом: `user_profiles.user_id PRIMARY KEY REFERENCES users(id)`. Зачем вообще разносить по двум таблицам? Редко нужные или тяжёлые данные (био, аватар, настройки) не тащатся в каждый запрос к `users`, а права доступа к ним можно разделить.
- **Один ко многим.** Внешний ключ на стороне «многих»: `orders.user_id`.
- **Многие ко многим.** Отдельная таблица-связка с двумя внешними ключами и составным первичным ключом. На связке часто живут свои данные: количество и цена в `order_items`, дата добавления метки в `product_tags`.

## Ограничения

Ограничения это правила, которые база проверяет при каждой вставке и изменении.

```sql
CREATE TABLE products (
    id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    title text NOT NULL,
    price numeric(12, 2) NOT NULL CHECK (price >= 0),
    sku   text UNIQUE
);
```

| Ограничение | Что запрещает | Код ошибки |
|---|---|---|
| `NOT NULL` | отсутствие значения | `23502` not_null_violation |
| `UNIQUE` | повтор значения (несколько `NULL` разрешены) | `23505` unique_violation |
| `PRIMARY KEY` | повтор и `NULL` | `23505` или `23502` |
| `CHECK (условие)` | строку, где условие `false` (`NULL` проходит!) | `23514` check_violation |
| `FOREIGN KEY` / `REFERENCES` | ссылку на несуществующую строку и удаление того, на что ссылаются | `23503` foreign_key_violation |

Как это выглядит в psql (с `\set VERBOSITY verbose`, чтобы видеть код):

```text
goschool=# INSERT INTO users (email, name) VALUES ('anna@example.com', 'Анна 2');
ERROR:  23505: duplicate key value violates unique constraint "users_email_key"
DETAIL:  Key (email)=(anna@example.com) already exists.

goschool=# INSERT INTO products (title, price) VALUES ('Книга', -5);
ERROR:  23514: new row for relation "products" violates check constraint "products_price_check"
DETAIL:  Failing row contains (1, Книга, -5.00, null).

goschool=# INSERT INTO orders (user_id) VALUES (42);
ERROR:  23503: insert or update on table "orders" violates foreign key constraint "orders_user_id_fkey"
DETAIL:  Key (user_id)=(42) is not present in table "users".
```

Обрати внимание на `CHECK`: условие с `NULL` даёт `NULL`, а `CHECK` отвергает только `false`. Поэтому `CHECK (price >= 0)` пропустит `price = NULL`, и для обязательной цены нужен ещё `NOT NULL`.

### Ошибки ограничений в Go

Пятизначный код (SQLSTATE) это то, на что смотрит Go-код. pgx возвращает ошибку сервера как `*pgconn.PgError`, где есть `Code`, `ConstraintName`, `Detail`:

```go
var pgErr *pgconn.PgError
if errors.As(err, &pgErr) && pgErr.Code == "23505" && pgErr.ConstraintName == "users_email_key" {
	return ErrEmailTaken // обработчик превратит это в 409 Conflict
}
```

Так проверка уникальности становится надёжной: «сначала `SELECT`, есть ли такой email, потом `INSERT`» между двумя запросами может проиграть гонку параллельному запросу, а уникальный индекс не проиграет никогда. Подробно работу с ошибками и транзакциями из Go разберём в уроке «Go и БД»; в домашке этого урока тесты ловят именно эти коды.

### ON DELETE: что делать со ссылками

Что должно произойти с заказами, если удалить пользователя? Решаешь ты, в объявлении внешнего ключа:

| Действие | Что происходит при удалении родителя | Когда уместно |
|---|---|---|
| `NO ACTION` (по умолчанию) | ошибка, если есть ссылки (проверка в конце оператора) | почти всегда разумное умолчание |
| `RESTRICT` | ошибка, если есть ссылки (проверка сразу) | то же, явно |
| `CASCADE` | дочерние строки удаляются вместе с родителем | части целого: позиции заказа, профиль пользователя |
| `SET NULL` | в ссылке ставится `NULL` | необязательная связь: у задачи удалили исполнителя |
| `SET DEFAULT` | ставится значение по умолчанию | редко |

```text
goschool=# DELETE FROM users WHERE id = 1;
ERROR:  23503: update or delete on table "users" violates foreign key constraint "orders_user_id_fkey" on table "orders"
DETAIL:  Key (id)=(1) is still referenced from table "orders".
```

Разница `NO ACTION` и `RESTRICT` тонкая: `NO ACTION` можно сделать отложенным (`DEFERRABLE`) до конца транзакции, `RESTRICT` нельзя. Для бизнеса выбор обычно между «запретить» и «каскадом».

::: trap CASCADE везде «чтобы не мешало»
`ON DELETE CASCADE` на всех внешних ключах превращает одно случайное удаление в лавину: удалили пользователя, исчезли его заказы, позиции, платежи и отчёты бухгалтерии.

```sql
-- плохо: удаление клиента молча стирает историю денег
user_id bigint NOT NULL REFERENCES users (id) ON DELETE CASCADE

-- хорошо: удалить клиента с заказами нельзя; для «удаления» аккаунта
-- обычно делают мягкое удаление (deleted_at) или анонимизацию
user_id bigint NOT NULL REFERENCES users (id) ON DELETE RESTRICT
```

`CASCADE` оставляй для настоящих частей целого, которые без родителя не имеют смысла: позиции заказа, профиль, связи в таблице-связке.
:::

::: hood Как устроен внешний ключ
Внешний ключ реализован системными триггерами. Для `orders.customer_id` из учебной базы их четыре:

```text
goschool=# SELECT tgname, tgrelid::regclass AS on_table, tgisinternal FROM pg_trigger
goschool-# WHERE tgconstraint = (SELECT oid FROM pg_constraint WHERE conname = 'orders_customer_id_fkey')
goschool-# ORDER BY tgname;
            tgname            | on_table  | tgisinternal
------------------------------+-----------+--------------
 RI_ConstraintTrigger_a_41977 | customers | t
 RI_ConstraintTrigger_a_41978 | customers | t
 RI_ConstraintTrigger_c_41979 | orders    | t
 RI_ConstraintTrigger_c_41980 | orders    | t
(4 rows)
```

Триггеры на `orders` при вставке и изменении проверяют, что клиент существует: ищут его по первичному ключу `customers`, там индекс есть всегда. Триггеры на `customers` при удалении и изменении `id` ищут ссылающиеся заказы: выполняют что-то вроде `SELECT 1 FROM orders WHERE customer_id = $1`. А вот индекса на `orders.customer_id` PostgreSQL **автоматически не создаёт**:

```text
goschool=# \d orders
...
Indexes:
    "orders_pkey" PRIMARY KEY, btree (id)
Foreign-key constraints:
    "orders_customer_id_fkey" FOREIGN KEY (customer_id) REFERENCES customers(id)
```

Только `orders_pkey`. Без индекса каждое удаление клиента сканирует всю таблицу заказов, а запросы «все заказы клиента» тоже идут полным перебором. Правило: на колонки внешних ключей почти всегда создают индекс вручную (`CREATE INDEX ON orders (customer_id)`). Индексы разберём в следующем уроке.
:::

## Типы PostgreSQL, на которых ошибаются

### timestamptz против timestamp

Название обманчиво: `timestamptz` (`timestamp with time zone`) **не хранит** часовой пояс. Он хранит момент времени в UTC, а при вводе и выводе переводит из пояса сессии и в пояс сессии. `timestamp` (`without time zone`) хранит «показания настенных часов» без привязки к поясу и ничего не переводит.

```text
goschool=# SET timezone = 'Europe/Moscow';
goschool=# SELECT '2024-03-05 12:00:00+00'::timestamptz AS tz, '2024-03-05 12:00:00+00'::timestamp AS no_tz;
           tz           |        no_tz
------------------------+---------------------
 2024-03-05 15:00:00+03 | 2024-03-05 12:00:00
(1 row)

goschool=# SET timezone = 'Asia/Novosibirsk';
goschool=# SELECT '2024-03-05 12:00:00+00'::timestamptz AS tz, '2024-03-05 12:00:00+00'::timestamp AS no_tz;
           tz           |        no_tz
------------------------+---------------------
 2024-03-05 19:00:00+07 | 2024-03-05 12:00:00
(1 row)
```

`timestamptz` показывает один и тот же момент по-разному в разных поясах, и это правильно. `timestamp` молча выбросил `+00` при вводе: какой это был пояс, уже не узнать. Если сервер, приложение и пользователи окажутся в разных поясах (а они окажутся), `timestamp` начнёт сдвигать события на часы.

Правило: для моментов («когда создан заказ», «когда истекает токен») всегда `timestamptz`. В Go это `time.Time`, и pgx корректно переводит его в момент и обратно. `timestamp` уместен редко, для «настенного» времени без пояса вроде «будильник в 7:00 по местному времени». Для дат без времени есть `date`.

### Деньги: numeric

```text
goschool=# SELECT sum(0.1::float8) AS float_sum, sum(0.1::numeric) AS numeric_sum FROM generate_series(1, 10);
     float_sum      | numeric_sum
--------------------+-------------
 0.9999999999999999 |         1.0
(1 row)
```

Десять раз по 10 копеек во `float8` не дают рубля. Варианты, которые работают:

- `numeric(12, 2)`: точное десятичное число, 12 цифр всего, 2 после запятой (до 9 999 999 999.99). Лишние знаки округляются при записи: `19.999` сохранится как `20.00`.
- `bigint` в минимальных единицах (копейках): быстро и просто, но о делении на 100 при выводе надо помнить везде.

Тип `money` в PostgreSQL есть, но его формат вывода зависит от локали сервера (`lc_monetary`), он хранит одну валюту без указания какой, и его не рекомендуют. `real` и `double precision` для денег не подходят никогда.

### text против varchar(n)

В PostgreSQL `text`, `varchar` и `varchar(n)` хранятся одинаково, и разницы в скорости нет, кроме проверки длины у `varchar(n)`. `varchar(255)` это привычка из MySQL, где длина влияла на хранение. Здесь ограничение длины это просто проверка, и неудачная: менять её потом означает миграцию. Если ограничение по смыслу нужно, `text` с `CHECK (length(title) <= 200)` выразит его явно.

А ещё приведение типа к `varchar(n)` молча обрезает строку, тогда как вставка в колонку падает:

```text
goschool=# SELECT 'abcdef'::varchar(3) AS cast_truncates;
 cast_truncates
----------------
 abc
(1 row)

goschool=# INSERT INTO v VALUES ('abcdef');
ERROR:  value too long for type character varying(3)
```

### jsonb

`jsonb` хранит JSON в разобранном бинарном виде: ключи без дублей (последний побеждает), без лишних пробелов, с поддержкой индексов (GIN) и операторов. `json` хранит исходный текст как есть.

```text
goschool=# SELECT '{"b": 1, "a": 2, "a": 3}'::json AS json, '{"b": 1, "a": 2, "a": 3}'::jsonb AS jsonb;
           json           |      jsonb
--------------------------+------------------
 {"b": 1, "a": 2, "a": 3} | {"a": 3, "b": 1}
(1 row)

goschool=# SELECT '{"pages": 704, "tags": ["sf", "classic"]}'::jsonb -> 'tags' ->> 0 AS first_tag,
goschool-#        '{"pages": 704}'::jsonb @> '{"pages": 704}' AS contains;
 first_tag | contains
-----------+----------
 sf        | t
(1 row)
```

`->` достаёт значение как `jsonb`, `->>` как текст, `@>` проверяет «содержит ли документ этот фрагмент». Почти всегда выбирай `jsonb`.

Когда `jsonb` уместен: произвольные атрибуты товаров разных категорий (у книги страницы, у футболки размер), настройки, сырые ответы внешних API. Когда нет: если по полю постоянно фильтруют, соединяют, на него ссылаются или его нужно ограничить. Тогда это кандидат в обычную колонку. `jsonb` для всего подряд это та же «одна большая таблица», только спрятанная.

### Перечисления: enum, CHECK или справочник

Статус заказа принимает одно из нескольких значений. Три способа:

```sql
-- 1. CHECK: просто и гибко
status text NOT NULL CHECK (status IN ('new', 'paid', 'shipped', 'cancelled'))

-- 2. enum-тип: 4 байта, значения упорядочены по объявлению
CREATE TYPE order_status AS ENUM ('new', 'paid', 'shipped', 'cancelled');
status order_status NOT NULL DEFAULT 'new'

-- 3. справочник: отдельная таблица и внешний ключ
CREATE TABLE order_statuses (code text PRIMARY KEY, title text NOT NULL);
status text NOT NULL REFERENCES order_statuses (code)
```

Неверное значение для enum даёт ошибку другого класса, чем для `CHECK`:

```text
goschool=# INSERT INTO e VALUES ('lost');
ERROR:  22P02: invalid input value for enum order_status: "lost"
```

Сравнение способов:

- **enum**: компактно, значения сравниваются в порядке объявления (`'paid' < 'shipped'` истинно). Добавить (`ALTER TYPE ... ADD VALUE`) и переименовать (`ALTER TYPE ... RENAME VALUE`) значение можно, а удалить нельзя вовсе: только пересоздать тип и перевести на него колонку.
- **CHECK**: поменять список это одна миграция с пересозданием ограничения. Хороший выбор по умолчанию для коротких стабильных списков.
- **справочник**: значения меняются без миграций схемы, можно хранить к ним данные (название для интерфейса, порядок, флаг активности). Выбор, когда список правят бизнес-пользователи.

## Денормализация

Нормализация убирает дублирование, но за это платишь соединениями при чтении. Иногда дублирование вводят сознательно, чтобы ускорить чтение. Это и есть денормализация, и она оправдана, когда:

- **Чтение много чаще записи, и соединение дорого.** Счётчик `comments_count` в `posts` вместо `count(*)` на каждый показ ленты. Цена: счётчик надо обновлять в той же транзакции, что и вставку комментария, иначе он разъедется.
- **Нужен снимок на момент события.** Адрес доставки и цена в заказе копируются, потому что клиент сменит адрес, а цена в каталоге поменяется, а заказ должен остаться таким, каким был. Строго говоря, это даже не денормализация, а отдельный факт.
- **Отчёты и аналитика.** Широкие предрасчитанные таблицы или материализованные представления (`CREATE MATERIALIZED VIEW`), которые обновляют по расписанию.

Правило: сначала нормализованная схема, денормализация только под измеренную проблему и с понятным механизмом синхронизации.

::: trap timestamp без пояса для моментов времени
```sql
-- плохо: при смене пояса сервера или приложения все времена «съедут»
created_at timestamp NOT NULL DEFAULT now()

-- хорошо: хранится момент, вывод в поясе сессии
created_at timestamptz NOT NULL DEFAULT now()
```

`now()` возвращает `timestamptz`. При записи в колонку `timestamp` PostgreSQL отбросит пояс, оставив время в поясе текущей сессии. Две сессии с разным `timezone` запишут один и тот же момент разными значениями.
:::

::: trap Деньги во float и money
```sql
-- плохо: ошибки округления накапливаются в суммах
price double precision NOT NULL
-- плохо: формат зависит от локали сервера, валюта неизвестна
price money NOT NULL

-- хорошо: точное десятичное с фиксированной точностью
price numeric(12, 2) NOT NULL CHECK (price >= 0)
```

В Go `numeric` не сканируется в `float64` без потерь в общем случае: используют `pgtype.Numeric`, библиотеку десятичных чисел (например, `shopspring/decimal`) или целые копейки.
:::

## Что выведет программа?

```sql
CREATE TABLE a (email text UNIQUE);
INSERT INTO a VALUES (NULL), (NULL);
SELECT count(*) FROM a;
```

<Predict :options="['ошибка unique_violation на второй вставке', '1', '2', '0']" :correct="2">

Для `UNIQUE` два `NULL` не равны (оба неизвестны), поэтому обе строки вставятся: `2`. Чтобы разрешить только один `NULL`, с PostgreSQL 15 есть `UNIQUE NULLS NOT DISTINCT`, тогда вторая вставка упадёт с `23505`. Если колонка обязательна, правильный ответ на вопрос «а как же NULL» это `NOT NULL`.

</Predict>

```sql
SELECT 19.999::numeric(12, 2) AS a;
```

<Predict :options="['19.999', '19.99', '20.00', 'ошибка: слишком много знаков']" :correct="2">

`numeric(12, 2)` хранит ровно 2 знака после запятой, лишние округляются по обычным правилам: `20.00`. Ошибка будет, только если не помещается целая часть (больше 10 цифр до запятой).

</Predict>

```sql
CREATE TABLE p (price numeric NOT NULL CHECK (price > 0));
INSERT INTO p VALUES (NULL);
```

<Predict :options="['вставится: CHECK пропускает NULL', 'ошибка 23514 check_violation', 'ошибка 23502 not_null_violation', 'вставится 0']" :correct="2">

`CHECK` сам по себе `NULL` пропустил бы (условие даёт `NULL`, а отвергается только `false`), но раньше сработает `NOT NULL`: ошибка `23502`. Без `NOT NULL` строка с ценой `NULL` спокойно вставилась бы, несмотря на `CHECK (price > 0)`.

</Predict>

::: interview
<details><summary>Что такое нормализация и зачем нужны 1NF, 2NF, 3NF?</summary>

Нормализация это разбиение данных на таблицы так, чтобы каждый факт хранился один раз, и не было аномалий обновления, вставки и удаления. 1NF: значения атомарны, нет списков в ячейке и повторяющихся колонок. 2NF: каждая неключевая колонка зависит от всего составного ключа, а не от его части. 3NF: неключевые колонки зависят только от ключа, а не друг от друга (нет транзитивных зависимостей). Коротко: «колонка описывает ключ, весь ключ и ничего, кроме ключа».

</details>
<details><summary>Суррогатный или естественный ключ?</summary>

Естественный ключ (email, ИНН) берётся из предметной области и со временем меняется или оказывается не уникальным, а изменение первичного ключа тянет за собой все ссылки. Поэтому обычно первичный ключ суррогатный (`bigint` identity или `uuid`), а естественный защищают `UNIQUE`. Исключение: таблицы-связки, где составной ключ из внешних ключей естественен и запрещает дубли.

</details>
<details><summary>uuid или bigint для первичного ключа?</summary>

`bigint` identity: 8 байт, монотонно растёт, вставка в индекс компактна, но значения угадываемы и выдаются только базой. `uuid`: 16 байт, можно генерировать на клиенте и сливать данные из разных источников, не раскрывает объёмы. UUID v4 случаен и вставляется в B-tree индекс в случайные места, что ухудшает кеширование и раздувает индекс; UUID v7 начинается с метки времени и этой проблемы почти не имеет. В PostgreSQL 18 есть встроенная `uuidv7()`.

</details>
<details><summary>Чем timestamptz отличается от timestamp?</summary>

`timestamptz` хранит момент времени (внутри в UTC) и переводит его в пояс сессии при выводе и из пояса при вводе; пояс как таковой не хранится. `timestamp` хранит дату и время без пояса и ничего не переводит. Для моментов событий нужен `timestamptz`: иначе при разных поясах сервера, приложения и пользователей время начинает съезжать.

</details>
<details><summary>Как хранить деньги?</summary>

В `numeric(p, s)` с фиксированным числом знаков после запятой или в целых минимальных единицах (`bigint` копеек). Не во `float`/`double precision` (двоичные дроби, ошибки округления в суммах) и не в `money` (зависит от локали сервера, нет валюты). Плюс `CHECK (amount >= 0)`, если отрицательные суммы невозможны, и отдельная колонка валюты, если валют несколько.

</details>
<details><summary>Какие бывают ограничения и что такое ON DELETE CASCADE?</summary>

`NOT NULL`, `UNIQUE`, `PRIMARY KEY`, `CHECK`, `FOREIGN KEY` (и `EXCLUDE` для особых случаев вроде непересекающихся интервалов). У внешнего ключа задаётся поведение при удалении родителя: `NO ACTION`/`RESTRICT` запрещают удаление, пока есть ссылки, `CASCADE` удаляет дочерние строки, `SET NULL`/`SET DEFAULT` обнуляют ссылку. `CASCADE` уместен для частей целого (позиции заказа), но опасен для данных с собственной ценностью (заказы пользователя).

</details>
<details><summary>Создаёт ли PostgreSQL индекс на внешний ключ?</summary>

На ссылающейся колонке нет. Индекс есть только на стороне родителя, потому что внешний ключ обязан ссылаться на первичный ключ или уникальную колонку. Индекс на `orders.user_id` надо создать самому, иначе удаление пользователя и выборки «заказы пользователя» будут сканировать всю таблицу заказов.

</details>
<details><summary>Когда оправдана денормализация?</summary>

Когда чтение сильно преобладает над записью и соединения или агрегации стали измеримой проблемой (счётчики, предрасчитанные витрины), и когда нужно зафиксировать снимок данных на момент события (цена и адрес в заказе). Денормализация всегда требует механизма синхронизации: обновления в той же транзакции, триггера или периодического пересчёта.

</details>
<details><summary>enum, CHECK или справочная таблица для статусов?</summary>

`CHECK (status IN (...))` прост и легко меняется миграцией. enum компактен и упорядочен, значения можно добавлять и переименовывать, но удалить значение нельзя. Справочная таблица с внешним ключом позволяет менять список без изменения схемы и хранить метаданные значений. Для стабильных технических статусов подходит `CHECK` или enum, для списков, которые правит бизнес, справочник.

</details>
:::

<Hw id="ex8" title="Нормализуй на бумаге" level="со звёздочкой">

Таблица учёта курсов в онлайн-школе: `enrollments(student_email, student_name, student_city, course_code, course_title, teacher_name, teacher_email, enrolled_at, grade)`, первичный ключ `(student_email, course_code)`. У курса один преподаватель, преподаватель может вести несколько курсов. Найди нарушения 2NF и 3NF, назови аномалии, которые они вызывают, и приведи схему к 3NF: какие таблицы, ключи, внешние ключи и действия `ON DELETE`. Напиши DDL и сравни с эталоном.

::: details Эталонное решение
Нарушение 2NF: `student_name`, `student_city` зависят только от `student_email`, а `course_title`, `teacher_*` только от `course_code`, то есть от части составного ключа. Нарушение 3NF: `teacher_email` зависит от `teacher_name` (или наоборот) через курс: `course_code -> teacher -> teacher_email`. Аномалии: смена города студента требует обновить все его записи; курс без студентов негде хранить; удаление последней записи курса теряет, кто его ведёт.

```sql
CREATE TABLE students (
    id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email text NOT NULL UNIQUE,
    name  text NOT NULL,
    city  text
);

CREATE TABLE teachers (
    id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email text NOT NULL UNIQUE,
    name  text NOT NULL
);

CREATE TABLE courses (
    id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    code       text NOT NULL UNIQUE,
    title      text NOT NULL,
    teacher_id bigint NOT NULL REFERENCES teachers (id) ON DELETE RESTRICT
);

CREATE TABLE enrollments (
    student_id  bigint NOT NULL REFERENCES students (id) ON DELETE CASCADE,
    course_id   bigint NOT NULL REFERENCES courses (id) ON DELETE RESTRICT,
    enrolled_at timestamptz NOT NULL DEFAULT now(),
    grade       smallint CHECK (grade BETWEEN 1 AND 5),
    PRIMARY KEY (student_id, course_id)
);
CREATE INDEX ON enrollments (course_id);
CREATE INDEX ON courses (teacher_id);
```

`grade` может быть `NULL` (оценки ещё нет), и `CHECK` это пропустит. Удаление студента уносит его записи на курсы, а курс с записями и преподавателя с курсами удалить нельзя. Индекс по `student_id` не нужен: он первая колонка первичного ключа.
:::

</Hw>
