# Транзакции, изоляция, MVCC

Пока с базой работает один пользователь, транзакции кажутся формальностью: `BEGIN`, пара запросов, `COMMIT`. Проблемы начинаются, когда одновременно приходят сотни запросов: два перевода с одного счёта, два покупателя на последнее место, два врача, которые одновременно уходят с дежурства. Каждый запрос по отдельности корректен, а вместе они ломают данные. Такие баги не воспроизводятся локально, проявляются раз в неделю под нагрузкой и стоят денег.

На собесе на бэкендера тема транзакций обязательна: ACID, уровни изоляции и аномалии, как Postgres реализует изоляцию через MVCC, `SELECT FOR UPDATE`, взаимоблокировки, оптимистичная блокировка. Хорошая новость: всё это можно увидеть своими глазами в двух окнах `psql`. Плохая: стандарт SQL и Postgres понимают уровни изоляции по-разному, и ответ «по учебнику» на собесе по Postgres будет неточным.

Для экспериментов открой два терминала с `psql` (из папки `homework`: `docker compose exec postgres psql -U goschool`). В одном окне создай таблицы:

```sql
CREATE SCHEMA IF NOT EXISTS lab06; SET search_path = lab06;
CREATE TABLE accounts (id int PRIMARY KEY, owner text, balance int);
CREATE TABLE doctors (id int PRIMARY KEY, name text, on_call bool);
```

Во втором окне выполни только `SET search_path = lab06;`. Примеры меняют данные, поэтому **перед каждым примером** возвращай исходное состояние (в любом окне, вне транзакции):

```sql
TRUNCATE accounts, doctors;
INSERT INTO accounts VALUES (1, 'alice', 1000), (2, 'bob', 1000);
INSERT INTO doctors VALUES (1, 'Алиса', true), (2, 'Боб', true);
```

Ниже окна обозначены `A>` и `B>`, команды идут по времени сверху вниз. Номера транзакций у тебя будут другими.

## ACID

Транзакция это группа операций, которая выполняется как одно целое. Четыре гарантии:

- **Atomicity (атомарность)**: либо все изменения транзакции, либо ни одного. Перевод денег не может списать со счёта и не зачислить. В Postgres откат почти бесплатный: новые версии строк просто остаются невидимыми (как, увидим в разделе про MVCC).
- **Consistency (согласованность)**: транзакция переводит базу из одного корректного состояния в другое. Корректность задаёшь ты: `CHECK`, `UNIQUE`, `FOREIGN KEY`, `NOT NULL`. База гарантирует, что закоммиченные данные этим ограничениям удовлетворяют.
- **Isolation (изоляция)**: параллельные транзакции не мешают друг другу. Насколько «не мешают», определяет **уровень изоляции**, и это самая сложная буква.
- **Durability (долговечность)**: после `COMMIT` данные переживут падение сервера. Postgres сначала пишет изменения в журнал предзаписи (**WAL**) и сбрасывает его на диск (`fsync`), и только потом отвечает «закоммичено». Сами страницы таблиц пишутся на диск позже, при падении их восстановят из WAL.

Без `BEGIN` каждый оператор выполняется в своей транзакции (**autocommit**). Внутри транзакции после любой ошибки все команды отвергаются до `ROLLBACK`:

```sql
A> BEGIN;
A> SELECT 1/0;
   ERROR:  division by zero
A> SELECT 1;
   ERROR:  current transaction is aborted, commands ignored until end of transaction block
A> COMMIT;   -- фактически выполнится ROLLBACK
```

Если нужно пережить ошибку внутри транзакции, используют `SAVEPOINT имя` и `ROLLBACK TO SAVEPOINT имя`. В коде это встречается редко.

## Аномалии

Изоляция защищает от **аномалий**: ситуаций, когда результат параллельного выполнения не совпадает ни с одним последовательным порядком.

| Аномалия | Что происходит |
|---|---|
| **Грязное чтение** (dirty read) | читаем изменения чужой незакоммиченной транзакции, которая потом откатится |
| **Неповторяющееся чтение** (non-repeatable read) | читаем строку дважды и получаем разные значения: между чтениями её изменили и закоммитили |
| **Фантомное чтение** (phantom read) | повторный запрос с тем же условием возвращает другой набор строк: кто-то вставил или удалил подходящие |
| **Потерянное обновление** (lost update) | две транзакции читают значение, обе вычисляют новое и пишут: одна запись затирает другую |
| **Несогласованная запись** (write skew) | две транзакции читают пересекающиеся данные, проверяют условие и меняют **разные** строки; вместе нарушают инвариант |

Стандарт SQL определяет четыре уровня через первые три аномалии. Postgres реализует их строже стандарта:

| Уровень | Грязное | Неповторяющееся | Фантомы | Потерянное обновление | Write skew |
|---|---|---|---|---|---|
| Read Uncommitted (в Postgres = Read Committed) | нет | да | да | да | да |
| **Read Committed** (по умолчанию) | нет | да | да | да | да |
| **Repeatable Read** | нет | нет | нет | нет (ошибка 40001) | да |
| **Serializable** | нет | нет | нет | нет | нет (ошибка 40001) |

«Да» значит «аномалия возможна». Две вещи, которые отличают ответ знающего человека: в Postgres **нет грязного чтения вообще**, и **Repeatable Read не допускает фантомов**, хотя стандарт это разрешает.

## Read Committed

Уровень по умолчанию. Каждый **оператор** видит снимок данных на момент своего начала: всё, что закоммичено до него.

```sql
A> BEGIN;
A> SELECT balance FROM accounts WHERE id = 1;
   1000
B> UPDATE accounts SET balance = balance - 100 WHERE id = 1;   -- autocommit
A> SELECT balance FROM accounts WHERE id = 1;
   900
A> COMMIT;
```

Неповторяющееся чтение: внутри одной транзакции два одинаковых запроса дали разное. Для большинства веб-запросов это нормально, но отчёт, который считает итог несколькими запросами, может получить несогласованные цифры.

Read Uncommitted в Postgres существует только для совместимости и работает как Read Committed:

```sql
A> BEGIN ISOLATION LEVEL READ UNCOMMITTED;
B> BEGIN;
B> UPDATE accounts SET balance = 0 WHERE id = 1;
A> SELECT balance FROM accounts WHERE id = 1;
   1000          -- чужое незакоммиченное не видно
B> ROLLBACK;
```

Это следствие MVCC: чтение всегда идёт по снимку, а в снимок попадают только закоммиченные версии. Читать «грязные» версии механизм просто не умеет.

### Что делает UPDATE, если строку уже меняют

Если `UPDATE` в Read Committed натыкается на строку, которую изменила незакоммиченная транзакция, он **ждёт** её. После её `COMMIT` он берёт **новую** версию строки и заново проверяет `WHERE`:

```sql
A> BEGIN;
A> UPDATE accounts SET balance = balance - 100 WHERE id = 1;
B> UPDATE accounts SET balance = balance * 2 WHERE balance = 1000 RETURNING id, balance;
   -- B ждёт: строка 1 заблокирована A
A> COMMIT;
B>  id | balance
   ----+---------
     2 |    2000   -- строка 1 после COMMIT A уже 900, условие не выполнено
```

Строка 2 обновилась, строка 1 нет, хотя в снимке B на момент начала оператора у неё было 1000. Это удобно (атомарный `UPDATE ... SET x = x - 100` никогда не теряет чужие изменения), но означает, что даже один оператор в Read Committed не видит строго согласованный снимок.

## Потерянное обновление

Классическая ошибка «прочитать, посчитать в коде, записать»:

```go
var balance int
tx.QueryRow(ctx, `SELECT balance FROM accounts WHERE id = 1`).Scan(&balance)
// ... в это время другая транзакция списала 100 и закоммитила
tx.Exec(ctx, `UPDATE accounts SET balance = $1 WHERE id = 1`, balance-50)
```

Обе транзакции прочитали 1000, одна записала 900, другая 950. Сто рублей списания потерялись. Способы защиты, от простого к сложному:

1. **Атомарный UPDATE**: `UPDATE accounts SET balance = balance - 50 WHERE id = 1 AND balance >= 50`. Вычисление внутри базы на актуальной версии строки. Лучший вариант, если логика выражается в SQL.
2. **Пессимистичная блокировка**: `SELECT ... FOR UPDATE` блокирует строку до конца транзакции, второй читатель ждёт и потом видит новое значение.
3. **Repeatable Read**: вторая транзакция при попытке записать получит ошибку 40001, её нужно повторить.
4. **Оптимистичная блокировка**: колонка `version`, `UPDATE ... WHERE version = $прочитанная`. Ниже подробно.

## Repeatable Read

Снимок берётся один раз, на **первом операторе транзакции**, и все запросы видят базу на тот момент.

```sql
A> BEGIN ISOLATION LEVEL REPEATABLE READ;
A> SELECT balance FROM accounts WHERE id = 1;
   1000
B> UPDATE accounts SET balance = balance - 100 WHERE id = 1;
B> INSERT INTO accounts VALUES (3, 'carol', 500);
A> SELECT balance FROM accounts WHERE id = 1;
   1000          -- неповторяющегося чтения нет
A> SELECT count(*) FROM accounts;
   2             -- фантома тоже нет
A> UPDATE accounts SET balance = balance + 1 WHERE id = 1;
   ERROR:  could not serialize access due to concurrent update
A> ROLLBACK;
```

Последняя строка важна. Транзакция A видит баланс 1000, но строку уже изменила закоммиченная транзакция B. Записать поверх A не может (это было бы потерянное обновление), поэтому Postgres отменяет её с ошибкой **40001 serialization_failure**. Приложение обязано быть к этому готово и **повторить транзакцию целиком**, с начала, а не только упавший оператор. Как писать такой ретрай в Go, разберём в следующем уроке.

Repeatable Read хорош для отчётов и выгрузок: все запросы видят одно согласованное состояние, и при этом не блокируют пишущих.

## Write skew и Serializable

Больница, инвариант «хотя бы один врач на дежурстве». Каждый врач перед уходом проверяет, что дежурных больше одного:

```sql
A> BEGIN ISOLATION LEVEL REPEATABLE READ;
B> BEGIN ISOLATION LEVEL REPEATABLE READ;
A> SELECT count(*) FROM doctors WHERE on_call;
   2
B> SELECT count(*) FROM doctors WHERE on_call;
   2
A> UPDATE doctors SET on_call = false WHERE id = 1;
B> UPDATE doctors SET on_call = false WHERE id = 2;
A> COMMIT;
B> COMMIT;
A> SELECT count(*) FROM doctors WHERE on_call;
   0
```

Ни одного дежурного. Repeatable Read не помог: транзакции меняли **разные** строки, конфликта записи не было. Каждая приняла решение по данным, которые к моменту коммита устарели. Это **write skew**. Похожие случаи: бронирование переговорки на пересекающееся время, лимит «не больше 3 активных подписок», уникальность логина без `UNIQUE`.

Тот же сценарий в Serializable:

```sql
A> BEGIN ISOLATION LEVEL SERIALIZABLE;
B> BEGIN ISOLATION LEVEL SERIALIZABLE;
A> SELECT count(*) FROM doctors WHERE on_call;   -- 2
B> SELECT count(*) FROM doctors WHERE on_call;   -- 2
A> UPDATE doctors SET on_call = false WHERE id = 1;
B> UPDATE doctors SET on_call = false WHERE id = 2;
A> COMMIT;
B> COMMIT;
   ERROR:  could not serialize access due to read/write dependencies among transactions
A> SELECT count(*) FROM doctors WHERE on_call;
   1
```

Serializable гарантирует: результат такой же, как при **каком-то** последовательном выполнении транзакций. Если такого порядка нет, одна из транзакций получает 40001.

::: hood Как работает Serializable в Postgres (SSI)
Postgres не блокирует чтения, а следит за зависимостями. Это **Serializable Snapshot Isolation**: поверх Repeatable Read каждая serializable-транзакция ставит «предикатные блокировки» (SIREAD) на то, что прочитала: строки, страницы индекса или всю таблицу. Они ничего не блокируют, а только регистрируют факт чтения. Когда другая транзакция пишет в прочитанное, фиксируется зависимость «A прочитала то, что потом изменила B» (rw-конфликт). Если находится опасная структура из двух таких зависимостей подряд (A -> B -> C, где C закоммитилась первой), одну транзакцию отменяют.

Следствия:
- бывают **ложные срабатывания**: структура опасна, но реальной аномалии нет. Особенно при Seq Scan, где блокировка ставится на всю таблицу. Хорошие индексы уменьшают их число;
- защищены только serializable-транзакции между собой: транзакция в Read Committed свои чтения не регистрирует;
- ретраи обязательны, это часть контракта уровня;
- транзакция `READ ONLY DEFERRABLE` ждёт безопасного снимка и потом никогда не отменяется: удобно для длинных отчётов.
:::

Как ещё лечить write skew без Serializable: материализовать конфликт. Заблокировать все строки, по которым принимается решение (`SELECT ... FROM doctors WHERE on_call FOR UPDATE`), тогда вторая транзакция будет ждать первую и после её коммита увидит одного дежурного. Или превратить инвариант в ограничение базы: `UNIQUE`, `EXCLUDE` для пересекающихся интервалов, триггер.

## MVCC: как Postgres хранит версии строк

**MVCC** (Multi-Version Concurrency Control) это способ, которым Postgres даёт каждому свой снимок без блокировок на чтение. Главная идея: `UPDATE` не перезаписывает строку, а создаёт **новую версию**, старая остаётся на месте. Читатели видят ту версию, которая была актуальна для их снимка. Поэтому **читатели не блокируют писателей, а писатели не блокируют читателей**.

У каждой версии строки есть служебные поля:
- `xmin`: номер транзакции, которая создала версию;
- `xmax`: номер транзакции, которая её удалила или заменила (0, если версия живая).

```sql
A> SELECT xmin, xmax, ctid, id, balance FROM accounts;
    xmin | xmax | ctid  | id | balance
   ------+------+-------+----+---------
    5289 |    0 | (0,1) |  1 |    1000
    5289 |    0 | (0,2) |  2 |    1000
A> BEGIN;
A> SELECT pg_current_xact_id();
   5290
A> UPDATE accounts SET balance = 900 WHERE id = 1;
A> SELECT xmin, xmax, ctid, id, balance FROM accounts;
    5289 |    0 | (0,2) |  2 |    1000
    5290 |    0 | (0,3) |  1 |     900    -- A видит свою новую версию
B> SELECT xmin, xmax, ctid, id, balance FROM accounts;
    5289 | 5290 | (0,1) |  1 |    1000    -- B видит старую: 5290 ещё не закоммичена
    5289 |    0 | (0,2) |  2 |    1000
A> COMMIT;
```

В странице теперь три версии: старая `(0,1)` с `xmax = 5290`, `(0,2)` и новая `(0,3)`. Это видно через `pageinspect`:

```sql
SELECT lp, t_xmin, t_xmax, t_ctid FROM heap_page_items(get_raw_page('accounts', 0));
 lp | t_xmin | t_xmax | t_ctid
----+--------+--------+--------
  1 |   5289 |   5290 | (0,3)    -- старая версия ссылается на новую
  2 |   5289 |      0 | (0,2)
  3 |   5290 |      0 | (0,3)
```

`DELETE` просто проставляет `xmax`. `ROLLBACK` вообще ничего не переписывает: статус транзакции 5290 в журнале статусов (CLOG) станет «отменена», и все её версии автоматически станут невидимыми. Поэтому откат в Postgres мгновенный при любом объёме изменений.

### Снимок

Какие версии видны, решает **снимок** (snapshot). Его можно посмотреть:

```sql
B> BEGIN;
B> SELECT pg_current_xact_id();          -- 5331, B ещё не закоммичена
C> UPDATE accounts SET balance = balance + 1 WHERE id = 2 RETURNING xmin;   -- 5332, autocommit
A> BEGIN ISOLATION LEVEL REPEATABLE READ;
A> SELECT pg_current_snapshot();
   5331:5333:5331
```

Формат `xmin:xmax:список`. Всё, что меньше 5331, завершено (видно, если закоммичено). Всё, что начиная с 5333, ещё не началось на момент снимка (не видно). Между ними видно то, что закоммичено, кроме транзакций из списка активных (5331, это B). Итого A видит изменения C, но не увидит изменений B, даже когда та закоммитится.

::: hood Правило видимости версии
Версия строки видна снимку, если:
1. транзакция `xmin` закоммичена и «в прошлом» для снимка (меньше `xmax` снимка и не в списке активных), или `xmin` это сама текущая транзакция;
2. и при этом `xmax` пустой, или транзакция `xmax` отменена, или она «в будущем» для снимка.

Чтобы не ходить в CLOG за статусом каждой транзакции, Postgres кеширует его прямо в заголовке версии строки (**hint bits**): первый же читатель после коммита проставит «xmin committed». Поэтому первый `SELECT` после большой загрузки иногда пишет на диск: он проставляет hint bits.

В Read Committed снимок берётся заново для каждого оператора, в Repeatable Read и Serializable один раз на транзакцию. Это главное различие RC и RR в том, что транзакция видит. Ещё два отличия не про видимость: при конфликте записи RC ждёт и перепроверяет условие на новой версии строки, а RR падает с 40001; Serializable добавляет поверх RR отслеживание rw-зависимостей (SSI).
:::

## VACUUM и bloat

Старые версии строк сами не исчезают. Каждый `UPDATE` оставляет «мёртвую» версию:

```sql
UPDATE accounts SET balance = balance + 1;   -- трижды
SELECT lp, lp_flags, t_xmin, t_xmax, t_ctid FROM heap_page_items(get_raw_page('accounts', 0));
 lp | lp_flags | t_xmin | t_xmax | t_ctid
----+----------+--------+--------+--------
  1 |        1 |   5303 |   5304 | (0,3)
  2 |        1 |   5303 |   5304 | (0,4)
  3 |        1 |   5304 |   5305 | (0,5)
  4 |        1 |   5304 |   5305 | (0,6)
  5 |        1 |   5305 |   5306 | (0,7)
  6 |        1 |   5305 |   5306 | (0,8)
  7 |        1 |   5306 |      0 | (0,7)
  8 |        1 |   5306 |      0 | (0,8)
```

Две живые строки занимают восемь мест. **VACUUM** находит версии, которые уже не нужны **ни одному** снимку, и освобождает место:

```sql
VACUUM accounts;
-- lp 1, 2: lp_flags = 2 (redirect: перенаправление на актуальную версию HOT-цепочки)
-- lp 3-6:  lp_flags = 0 (свободно, сюда лягут новые версии)
-- lp 7, 8: живые строки
```

Обычный `VACUUM` не уменьшает файл таблицы, а помечает место свободным для повторного использования, и работает параллельно с запросами. Запускать его руками не нужно: этим занимается **autovacuum**, когда доля мёртвых строк превышает порог (по умолчанию 20% таблицы плюс 50 строк). Ещё VACUUM обновляет карту видимости (нужна для Index Only Scan) и «замораживает» старые версии, чтобы 32-битный счётчик транзакций мог безопасно пойти по кругу (**xid wraparound**).

**Bloat** (распухание) это таблица или индекс, где много мёртвого или пустого места. Причины:
- autovacuum не успевает за частыми `UPDATE`;
- **долгая транзакция**. VACUUM не может удалить версию, пока жив хоть один снимок, которому она может понадобиться. Транзакция, открытая на час (или забытый в `psql` `BEGIN`), держит «горизонт» всей базы, и мёртвые версии во всех таблицах копятся час. В тестах урока про индексы ты мог это заметить: Index Only Scan не появляется, пока параллельные транзакции держат горизонт.

`VACUUM FULL` переписывает таблицу целиком и возвращает место ОС, но берёт эксклюзивную блокировку: таблица недоступна даже на чтение. На проде вместо него используют расширение `pg_repack`.

::: trap Транзакция, которая ждёт пользователя
Плохо: открыть транзакцию, сходить во внешний API или ждать ответа пользователя, потом закоммитить.

```go
tx, _ := pool.Begin(ctx)
tx.Exec(ctx, `UPDATE orders SET status = 'paying' WHERE id = $1`, id)
resp := paymentAPI.Charge(ctx, amount) // 30 секунд таймаута
tx.Exec(ctx, `UPDATE orders SET status = $1 WHERE id = $2`, resp.Status, id)
tx.Commit(ctx)
```

Строка заказа заблокирована, соединение из пула занято, горизонт VACUUM стоит. Хорошо: транзакции короткие и только с базой, внешние вызовы между ними, состояние «в процессе» записано отдельной транзакцией. Подстраховка на сервере: `idle_in_transaction_session_timeout`.
:::

## Блокировки строк

Изменение строки (`UPDATE`, `DELETE`) автоматически блокирует её до конца транзакции. Читатели не ждут (MVCC), а второй писатель ждёт. Заблокировать строку заранее, ещё при чтении, можно явно:

| Режим | Что блокирует | Типичное применение |
|---|---|---|
| `FOR UPDATE` | любое изменение и любые другие блокировки строки | прочитать и потом изменить или удалить |
| `FOR NO KEY UPDATE` | то же, но не мешает `FOR KEY SHARE` | берёт сам `UPDATE`, если не меняет ключ |
| `FOR SHARE` | изменения, но не другие `FOR SHARE` | «строка не должна измениться, пока я работаю» |
| `FOR KEY SHARE` | удаление и изменение ключа | берёт проверка внешнего ключа при вставке в дочернюю таблицу |

Модификаторы ожидания:

```sql
A> BEGIN;
A> SELECT * FROM accounts WHERE id = 1 FOR UPDATE;
B> SELECT * FROM accounts WHERE id = 1 FOR UPDATE NOWAIT;
   ERROR:  could not obtain lock on row in relation "accounts"
B> SELECT id FROM accounts ORDER BY id FOR UPDATE SKIP LOCKED;
   2
```

- **NOWAIT**: не ждать, сразу ошибка 55P03. Для интерфейсов «документ сейчас редактирует другой пользователь».
- **SKIP LOCKED**: пропустить заблокированные строки. Основа очередей в базе: несколько воркеров берут задачи и не мешают друг другу:

```sql
UPDATE jobs SET status = 'running', worker = $1
WHERE id = (
    SELECT id FROM jobs WHERE status = 'queued'
    ORDER BY id LIMIT 1
    FOR UPDATE SKIP LOCKED
)
RETURNING id, payload;
```

Так устроены очереди River, о которой будет отдельный модуль, и многие другие.

Блокировки строк хранятся не в памяти, а прямо в версии строки (в поле `xmax` и битах заголовка). Поэтому можно заблокировать миллион строк без расхода памяти, но `SELECT ... FOR UPDATE` пишет на диск. Ожидающая транзакция ждёт не строку, а **завершения транзакции-владельца**: это видно в `pg_locks` как ожидание `ShareLock` на `transactionid`.

## Взаимоблокировки

Перевод 1 -> 2 и встречный 2 -> 1:

```sql
A> BEGIN;
B> BEGIN;
A> UPDATE accounts SET balance = balance - 10 WHERE id = 1;
B> UPDATE accounts SET balance = balance - 10 WHERE id = 2;
A> UPDATE accounts SET balance = balance + 10 WHERE id = 2;   -- ждёт B
B> UPDATE accounts SET balance = balance + 10 WHERE id = 1;   -- ждёт A
   ERROR:  deadlock detected
   DETAIL:  Process 8386 waits for ShareLock on transaction 5310; blocked by process 8384.
            Process 8384 waits for ShareLock on transaction 5311; blocked by process 8386.
```

Каждая ждёт другую, сами они не разойдутся. Postgres не проверяет граф ожиданий постоянно: процесс, который ждёт дольше `deadlock_timeout` (1 секунда по умолчанию), запускает проверку, находит цикл и отменяет **одну** транзакцию с ошибкой **40P01**. Вторая продолжает работу. Это значит, что каждая взаимоблокировка стоит минимум секунду ожидания.

Как избежать:
1. **Единый порядок блокировок**. Все переводы блокируют счета по возрастанию `id`, независимо от направления: `SELECT ... WHERE id IN ($1, $2) ORDER BY id FOR UPDATE`. Цикла не может быть, если все берут блокировки в одном порядке.
2. Короткие транзакции: меньше держишь, меньше шансов пересечься.
3. Ретрай на 40P01 как последняя линия обороны.

::: trap Блокировки в порядке аргументов
Плохо: порядок зависит от направления перевода.

```go
tx.Exec(ctx, `UPDATE accounts SET balance = balance - $2 WHERE id = $1`, from, amount)
tx.Exec(ctx, `UPDATE accounts SET balance = balance + $2 WHERE id = $1`, to, amount)
// Transfer(1, 2) и Transfer(2, 1) одновременно: deadlock
```

Хорошо: сначала заблокировать обе строки в порядке id, потом менять.

```go
rows, _ := tx.Query(ctx,
	`SELECT id, balance FROM accounts WHERE id IN ($1, $2) ORDER BY id FOR UPDATE`, from, to)
```
:::

## Оптимистичная блокировка

Пессимистичная блокировка (`FOR UPDATE`) держит строку, пока транзакция работает. Но бывает, что между чтением и записью проходят минуты: пользователь открыл карточку товара в админке, правит, сохраняет. Держать транзакцию всё это время нельзя. Решение: колонка-версия.

```sql
-- при открытии формы
SELECT id, title, version FROM docs WHERE id = 1;          -- version = 7
-- при сохранении
UPDATE docs SET title = $1, version = version + 1
WHERE id = 1 AND version = 7
RETURNING version;
```

Если кто-то успел сохранить раньше, версия уже 8, `UPDATE` затронет 0 строк, и приложение отвечает «документ изменён другим пользователем, обновите страницу» (в HTTP обычно `409 Conflict`). Важно, что проверка и запись это **один** оператор: если сначала прочитать версию, сравнить в Go и потом обновить, между этими шагами снова окно для гонки. В HTTP-API та же идея реализуется через заголовки `ETag` и `If-Match`.

Когда что выбирать: пессимистичная блокировка, когда конфликты частые и транзакция короткая (перевод денег); оптимистичная, когда конфликты редкие или «думает» человек (редактирование).

## Advisory locks

Иногда нужна блокировка не на строку, а на произвольное понятие: «отчёт за март сейчас строится», «миграции выполняет один инстанс». Postgres даёт **рекомендательные блокировки** по числу:

```sql
B> SELECT pg_try_advisory_lock(42);   -- true
A> SELECT pg_try_advisory_lock(42);   -- false, занято
B> SELECT pg_advisory_unlock(42);     -- true
A> SELECT pg_try_advisory_lock(42);   -- true
```

`pg_advisory_lock` ждёт, `pg_try_advisory_lock` сразу отвечает. Обычные версии живут до явного unlock или конца сессии, `pg_advisory_xact_lock` до конца транзакции (безопаснее с пулом соединений: сессионная блокировка останется на соединении, которое вернулось в пул). Этим механизмом goose умеет защищать миграции от одновременного запуска несколькими инстансами (опция `WithSessionLocker`), о нём в уроке про миграции. «Рекомендательные» значит, что база их ни к чему не привязывает: работают, только если все участники договорились их брать.

## Что выведет программа?

Таблицы из урока в исходном состоянии (`balance = 1000` у обоих счетов).

```sql
A> BEGIN;   -- Read Committed
A> SELECT balance FROM accounts WHERE id = 1;
B> UPDATE accounts SET balance = balance - 100 WHERE id = 1;
A> SELECT balance FROM accounts WHERE id = 1;
```

<Predict :options="['1000 и 1000', '1000 и 900', 'второй SELECT ждёт B', 'ошибка 40001']" :correct="1">

В Read Committed каждый оператор берёт свежий снимок. B закоммитилась (autocommit) до второго `SELECT`, поэтому он видит 900. Это неповторяющееся чтение. В Repeatable Read оба раза было бы 1000.

</Predict>

```sql
A> BEGIN ISOLATION LEVEL REPEATABLE READ;
A> SELECT count(*) FROM accounts;
B> INSERT INTO accounts VALUES (3, 'carol', 500);
A> SELECT count(*) FROM accounts;
```

<Predict :options="['2 и 2', '2 и 3', 'второй SELECT ждёт B', 'ошибка 40001']" :correct="0">

Снимок в Repeatable Read берётся на первом операторе транзакции и не меняется. Новая строка от B для него «в будущем». Стандарт SQL разрешает на этом уровне фантомы, но Postgres их не допускает.

</Predict>

```sql
A> BEGIN ISOLATION LEVEL REPEATABLE READ;
B> BEGIN ISOLATION LEVEL REPEATABLE READ;
A> SELECT count(*) FROM doctors WHERE on_call;   -- 2
B> SELECT count(*) FROM doctors WHERE on_call;   -- 2
A> UPDATE doctors SET on_call = false WHERE id = 1;
B> UPDATE doctors SET on_call = false WHERE id = 2;
A> COMMIT;
B> COMMIT;
SELECT count(*) FROM doctors WHERE on_call;
```

<Predict :options="['1: COMMIT B упадёт с 40001', '0', '1: второй UPDATE будет ждать', '2']" :correct="1">

Write skew: транзакции меняли разные строки, конфликтов записи нет, Repeatable Read обе пропускает. Дежурных 0. В Serializable `COMMIT` B упал бы с `could not serialize access due to read/write dependencies among transactions`.

</Predict>

```sql
A> BEGIN ISOLATION LEVEL READ UNCOMMITTED;
B> BEGIN;
B> UPDATE accounts SET balance = 0 WHERE id = 1;
A> SELECT balance FROM accounts WHERE id = 1;
```

<Predict :options="['0', '1000', 'SELECT ждёт B', 'ошибка: уровень не поддерживается']" :correct="1">

В Postgres Read Uncommitted работает как Read Committed: снимок содержит только закоммиченные версии. Грязного чтения не бывает. Читатель не ждёт писателя: он просто читает старую версию строки.

</Predict>

::: interview
<details><summary>Расшифруй ACID. Как Postgres обеспечивает D?</summary>

Атомарность (всё или ничего), согласованность (ограничения выполняются после каждой транзакции), изоляция (параллельные транзакции не мешают друг другу в рамках уровня), долговечность (закоммиченное не теряется). Долговечность через WAL: перед ответом на `COMMIT` запись журнала сбрасывается на диск, страницы данных пишутся позже и восстанавливаются из WAL после сбоя. `synchronous_commit = off` ослабляет это ради скорости.

</details>
<details><summary>Какие уровни изоляции есть в Postgres и от каких аномалий они защищают?</summary>

Read Committed (по умолчанию): нет грязного чтения, возможны неповторяющееся чтение, фантомы, потерянные обновления, write skew. Repeatable Read: снимок на всю транзакцию, нет неповторяющегося чтения и фантомов, при конфликте записи ошибка 40001, write skew возможен. Serializable: результат эквивалентен последовательному выполнению, при опасных зависимостях 40001. Read Uncommitted существует только синтаксически и равен Read Committed.

</details>
<details><summary>Что такое MVCC и что лежит в xmin и xmax?</summary>

Многоверсионность: изменение создаёт новую версию строки, старая остаётся, каждый читатель видит версии, подходящие его снимку. `xmin` это транзакция, создавшая версию, `xmax` удалившая или заменившая её. Читатели не блокируют писателей и наоборот. Цена: мёртвые версии, которые чистит VACUUM.

</details>
<details><summary>Зачем нужен VACUUM и что будет, если его не делать?</summary>

Удаляет версии строк, не нужные ни одному снимку, обновляет карту видимости и карту свободного места, замораживает старые xid. Без него таблицы и индексы пухнут, Index Only Scan не работает, а при приближении к переполнению счётчика транзакций Postgres в итоге перестанет выдавать новые xid, чтобы не потерять данные. Обычно хватает autovacuum, главный враг это долгие транзакции, держащие горизонт.

</details>
<details><summary>Что такое потерянное обновление и как от него защититься?</summary>

Две транзакции читают значение, вычисляют новое в приложении и записывают, вторая затирает первую. Защита: атомарный `UPDATE SET x = x + ...`, `SELECT FOR UPDATE` перед вычислением, Repeatable Read с ретраем на 40001, оптимистичная блокировка через колонку `version`.

</details>
<details><summary>Что такое write skew? Приведи пример.</summary>

Две транзакции читают пересекающиеся данные, по ним проверяют условие и изменяют разные строки. По отдельности каждая корректна, вместе нарушают инвариант. Пример: два дежурных врача одновременно уходят, увидев «нас двое». Repeatable Read не спасает. Решения: Serializable с ретраями, `FOR UPDATE` на все строки, участвующие в проверке, или ограничение в базе (UNIQUE, EXCLUDE).

</details>
<details><summary>Чем FOR UPDATE отличается от FOR SHARE? Что такое SKIP LOCKED?</summary>

`FOR UPDATE` эксклюзивно блокирует строку: другие не могут её изменить или заблокировать любым режимом. `FOR SHARE` разделяемая: несколько транзакций могут держать её одновременно, но никто не может изменить строку. `NOWAIT` даёт ошибку вместо ожидания, `SKIP LOCKED` пропускает заблокированные строки: так строят очереди задач в базе.

</details>
<details><summary>Как Postgres обнаруживает взаимоблокировки и как их избегать?</summary>

Процесс, ждущий блокировку дольше `deadlock_timeout` (1 с), строит граф ожиданий, находит цикл и отменяет одну транзакцию с ошибкой 40P01. Избегать: брать блокировки в едином порядке (например, по возрастанию id), держать транзакции короткими, на 40P01 повторять транзакцию.

</details>
<details><summary>Оптимистичная или пессимистичная блокировка: когда что?</summary>

Пессимистичная (`FOR UPDATE`) блокирует заранее, подходит при частых конфликтах и короткой транзакции. Оптимистичная (колонка `version`, `UPDATE ... WHERE version = $v`) ничего не держит и обнаруживает конфликт при записи, подходит при редких конфликтах и долгом «думании» между чтением и записью, например в форме редактирования.

</details>
<details><summary>Почему при Repeatable Read и Serializable нужен ретрай и что именно повторять?</summary>

На этих уровнях Postgres не ждёт и не сливает конфликтующие изменения, а отменяет транзакцию с 40001. Повторять нужно всю транзакцию с начала, включая чтения, потому что решение принималось по устаревшему снимку. Повтор одного упавшего оператора невозможен: транзакция уже отменена.

</details>
:::
