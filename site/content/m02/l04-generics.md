# Дженерики

Десять лет Go жил без дженериков, и это было главной претензией к языку. Нужна функция «максимум» для `int` и для `float64`? Пиши две. Нужно множество строк и множество ID? Копируй код или используй `interface{}` с утверждениями типов и паниками в рантайме. В Go 1.18 появились **параметры типов**, и теперь `slices.Contains`, `maps.Keys`, `min`/`max` работают с любыми подходящими типами, а ошибки типов ловит компилятор.

Ты знаешь дженерики по TypeScript: `function first<T>(xs: T[]): T`. Идея та же, но есть важное отличие. В Go ограничение описывает не только методы, но и **набор типов**: «любой целый тип», «любой тип с базовым типом `string`». Это нужно, чтобы внутри дженерика работали операторы `+` и `<`, ведь методов у `int` нет.

На собесе спросят синтаксис, что такое `~` и `comparable`, чем дженерик отличается от интерфейса и, главное, когда дженерики **не нужны**. Последний вопрос важнее всех: Go-сообщество осторожно относится к абстракциям, и код, где дженерики стоят там, где хватило бы интерфейса, на ревью не пройдёт.

## Параметры типов

```go
func Max[T cmp.Ordered](a, b T) T {
	if a > b {
		return a
	}
	return b
}

Max(3, 7)              // 7, T выведен как int
Max("груша", "яблоко") // "яблоко"
Max[float64](1, 2.5)   // 2.5, T указан явно
```

- `[T cmp.Ordered]` это **список параметров типов**. `T` имя параметра, `cmp.Ordered` его **ограничение** (constraint).
- При вызове компилятор **выводит** `T` из аргументов. Явно указывать нужно, когда выводить не из чего: `MaxOf[string]()` без аргументов.
- Параметров может быть несколько: `func Map[T, U any](s []T, f func(T) U) []U`.

Выведение работает и с нетипизированными константами: если смешать `1` и `2.5`, компилятор выберет тип, в который помещаются обе.

```go
fmt.Println(Max(1, 2.5))
fmt.Printf("%T\n", Max(1, 2.5))
```

<Predict :options="['ошибка компиляции: разные типы', '2.5 и float64', '2 и int', '2.5 и int']" :correct="1">

`1` и `2.5` нетипизированные константы. С Go 1.21 выведение типов для таких случаев выбирает «самый широкий» вид констант среди аргументов, здесь вещественный, и `T` становится `float64`. Если бы один аргумент был переменной типа `int`, а другой `2.5`, была бы ошибка компиляции.

</Predict>

### Дженерик-типы

Параметры могут быть и у типов:

```go
type Stack[T any] struct {
	items []T
}

func (s *Stack[T]) Push(v T) { s.items = append(s.items, v) }

func (s *Stack[T]) Pop() (T, bool) {
	var zero T
	if len(s.items) == 0 {
		return zero, false
	}
	v := s.items[len(s.items)-1]
	s.items[len(s.items)-1] = zero // не держим ссылку для сборщика мусора
	s.items = s.items[:len(s.items)-1]
	return v, true
}

var s Stack[int]
s.Push(1)
```

Обрати внимание:

- **Нулевое значение `T`** получают через `var zero T`. Литерала «ноль любого типа» нет, а `nil` годится только для типов, у которых нулевое значение `nil`: указателей, слайсов, мап, каналов, функций и интерфейсов.
- Методы объявляются с `[T]` в получателе: `func (s *Stack[T]) Push`.
- Для типов аргументы **не выводятся** из литерала: `Pair{Key: "b", Val: 2}` не скомпилируется (`cannot use generic type Pair[K comparable, V any] without instantiation`), нужно `Pair[string, int]{...}`.

### Дженерик-методы (Go 1.27)

До Go 1.27 у метода не могло быть **своих** параметров типов, только параметры типа-получателя. Метод `MapTo` у `Stack[T]` ниже раньше пришлось бы делать свободной функцией `MapStack[T, U any](s *Stack[T], f func(T) U) []U`. В стандартной библиотеке пример из release notes: в `math/rand/v2` раньше была только функция `rand.N[Int intType](Int) Int`, а с 1.27 есть ещё и метод `(*Rand) N[Int intType](Int) Int`. С Go 1.27 так можно:

```go
func (s *Stack[T]) MapTo[U any](f func(T) U) []U {
	out := make([]U, 0, len(s.items))
	for _, v := range s.items {
		out = append(out, f(v))
	}
	return out
}

s.MapTo(func(n int) string { return fmt.Sprint(n * 10) }) // [10 20]
```

Ограничения: у методов **интерфейсов** параметров типов по-прежнему нет (`interface method must have no type parameters`), и дженерик-метод не может реализовать метод интерфейса. В старом коде и статьях до августа 2026 ты будешь читать, что дженерик-методов в Go нет: это устарело.

## Ограничения

Ограничение в Go это интерфейс. Но с дженериками интерфейсы научились описывать не только методы, а **набор типов** (type set).

```go
// Только методы: как обычный интерфейс.
func Join[T fmt.Stringer](xs []T) string { ... }

// Объединение типов: T может быть только int или float64.
type Number interface {
	int | float64
}

// И методы, и типы сразу.
type StringableInt interface {
	~int
	String() string
}
```

Внутри дженерика разрешены те операции, которые поддерживают **все** типы из набора. `+` есть и у `int`, и у `float64`, значит в `func Sum[T Number]` можно складывать. У `any` набор типов это вообще все типы, поэтому с `T any` можно только присваивать, передавать и класть в интерфейс. Даже `==` нельзя:

```go
func Bad[T any](a, b T) bool { return a == b }
// invalid operation: a == b (incomparable types in type set)
```

Интерфейс с перечислением типов (`int | float64`) или с `~` можно использовать **только как ограничение**. Переменную такого типа объявить нельзя: `cannot use type Number outside a type constraint: interface contains type constraints`.

### Тильда: ~T

Объединение `int | float64` значит «ровно `int` или ровно `float64`». А у тебя в коде полно своих типов:

```go
type Celsius float64
type UserID int
```

Базовый (underlying) тип у `Celsius` это `float64`, но сам `Celsius` уже другой тип. В ограничение `int | float64` он не входит:

```go
type MyInt int

func Double[T int | float64](x T) T { return x * 2 }

func main() {
	fmt.Println(Double(MyInt(3)))
}
```

<Predict :options="['6', 'ошибка компиляции', 'паника в рантайме', '3']" :correct="1">

`MyInt does not satisfy int | float64 (possibly missing ~ for int in int | float64)`. Компилятор прямо подсказывает лекарство: `~int` означает «любой тип, у которого базовый тип `int`», и тогда `MyInt` подойдёт.

</Predict>

С тильдой:

```go
type Number interface {
	~int | ~int64 | ~float64
}

func Sum[T Number](xs []T) T {
	var s T
	for _, x := range xs {
		s += x
	}
	return s
}

fmt.Println(Sum([]Celsius{20.5, 1.5})) // 22
fmt.Printf("%T\n", Sum([]Celsius{20.5, 1.5})) // main.Celsius
```

Результат имеет тип `Celsius`, а не `float64`: дженерик сохраняет твой тип, и методы `Celsius` остаются доступны. Правило для практики: в ограничениях из встроенных типов почти всегда пиши `~`. Так устроены все ограничения стандартной библиотеки.

То же для составных типов. Функции пакета `slices` объявлены так: `func Sort[S ~[]E, E cmp.Ordered](x S)`. Благодаря `S ~[]E` в них можно передать `type IDs []int`, и результат будет того же типа `IDs`, а не `[]int`.

### cmp.Ordered и встроенные min/max

С Go 1.21 в стандартной библиотеке есть пакет `cmp`:

```go
type Ordered interface {
	~int | ~int8 | ~int16 | ~int32 | ~int64 |
		~uint | ~uint8 | ~uint16 | ~uint32 | ~uint64 | ~uintptr |
		~float32 | ~float64 |
		~string
}
```

Это все типы, которые поддерживают `<`, `<=`, `>`, `>=`. Плюс функции `cmp.Compare(a, b)` (возвращает -1, 0, +1) и `cmp.Less`, которые удобно передавать в `slices.SortFunc`. В том же релизе появились встроенные `min` и `max` для любых упорядоченных типов: `min(3, 1, 2)` даёт 1, `max("b", "a")` даёт `"b"`.

::: trap NaN и сравнение вещественных
`cmp.Ordered` включает `float64`, а у вещественных есть `NaN`, который не больше, не меньше и не равен ничему, даже себе. Самописный максимум через `>` даёт результат, зависящий от позиции `NaN`:

```go
// Плохо: если NaN первый, он «выиграет», если в середине, будет пропущен.
func maxOf[T cmp.Ordered](xs []T) T {
	m := xs[0]
	for _, x := range xs[1:] {
		if x > m { // NaN > 1 == false, 1 > NaN == false
			m = x
		}
	}
	return m
}

// Хорошо: встроенные max/min и slices.Max документированно возвращают NaN,
// если он есть среди аргументов; cmp.Compare считает NaN меньше любого числа.
m := slices.Max(xs)
```

Если в данных бывают `NaN`, реши заранее, как с ними обходиться, и используй `cmp.Compare` вместо голых операторов.
:::

### comparable

`comparable` это встроенное ограничение «тип поддерживает `==` и `!=`». Оно нужно для ключей мап и множеств:

```go
type Set[T comparable] struct {
	m map[T]struct{}
}
```

Тонкость, о которой спрашивают на собесах. До Go 1.20 интерфейсные типы (`any`, `error`) **не** удовлетворяли `comparable`, хотя `==` для них компилируется. С Go 1.20 удовлетворяют, но цена такая: сравнение может запаниковать в рантайме, если внутри окажется несравнимое значение (мы разбирали это в уроке про устройство интерфейсов).

```go
func Eq[T comparable](a, b T) bool { return a == b }

fmt.Println(Eq[any](1, 1))               // true
fmt.Println(Eq[any]([]int{1}, []int{1})) // panic: runtime error: comparing uncomparable type []int
```

Если `T` конкретный тип (`string`, структура из сравнимых полей), паники быть не может: компилятор проверил всё статически.

## Тип внутри дженерика не узнать switch-ом

Иногда хочется внутри дженерика сделать что-то особенное для `string`. Прямой type switch по значению типа `T` запрещён:

```go
func F[T any](x T) {
	switch x.(type) { // cannot use type switch on type parameter value x
	}
}
```

Можно через `any(x).(type)`, это работает:

```go
func Describe[T any](v T) string {
	switch x := any(v).(type) {
	case int:
		return "int " + strconv.Itoa(x)
	case string:
		return "string " + x
	}
	return fmt.Sprintf("%T", v)
}
```

Но если ты так делаешь, скорее всего, дженерик тут не нужен: смысл дженерика в том, что код **одинаковый** для всех `T`. Ветвление по типам это работа для интерфейса с методами или для отдельных функций.

## Когда дженерики не нужны

Ян Лэнс Тейлор (один из авторов дженериков в Go) сформулировал правило: **пиши код, а не типы**. Не начинай с параметров типов. Начни с конкретной функции, и если появится вторая почти такая же для другого типа, тогда обобщай.

Дженерики хороши, когда:

- функция работает с **контейнерами любого типа**: слайсы, мапы, каналы (`slices.Contains`, `maps.Keys`, свой `Filter`);
- пишешь **структуру данных общего назначения**: множество, стек, кеш, очередь с приоритетом;
- реализация одинаковая для всех типов, и нужен **оператор** (`<`, `+`), которого нет у интерфейсов.

Дженерики не нужны, когда:

- достаточно **вызвать метод**. Если функция просто вызывает `w.Write`, принимай `io.Writer`, а не `[W io.Writer]`. Интерфейс проще читать, и он не плодит инстанциации.
- реализация **разная для разных типов**. Тогда нужен интерфейс с методом, который каждый тип реализует по-своему.
- тип **один**. «Вдруг пригодится» не причина.

```go
// Плохо: дженерик ради дженерика. Читается хуже, пользы ноль.
func WriteAll[W io.Writer](w W, data []byte) error {
	_, err := w.Write(data)
	return err
}

// Хорошо: обычный интерфейс.
func WriteAll(w io.Writer, data []byte) error {
	_, err := w.Write(data)
	return err
}
```

::: hood Как компилятор реализует дженерики
Есть два классических подхода. **Мономорфизация** (C++, Rust): для каждого набора типов компилятор генерирует отдельную копию функции. Быстро, но раздувает бинарник и время сборки. **Боксинг** (Java): одна функция работает со всем через указатели и проверки в рантайме. Компактно, но медленнее.

Go выбрал гибрид: **GC shape stenciling с словарями**. Типы группируются по «форме» (shape): грубо говоря, по базовому типу, а все указательные типы имеют одну общую форму. Для каждой формы генерируется одна копия функции, а то, что различается между типами одной формы (дескрипторы типов, адреса методов), передаётся скрытым параметром, **словарём**.

```text
Sum[int], Sum[UserID]         ──► одна копия для формы int
Sum[float64], Sum[Celsius]    ──► одна копия для формы float64
Print[*User], Print[*Order]   ──► одна копия для всех указателей + словарь
```

Практическое следствие: для числовых типов дженерик обычно так же быстр, как написанная руками функция. А вызов **метода** у значения типа-параметра (например, `v.String()` при `T fmt.Stringer`) идёт косвенно через словарь для любой формы: одну форму делят несколько типов (`int`, `UserID`, а `time.Duration` с базовым `int64` делит форму с `int64`), и адреса их методов разные. У указателей все типы делят вообще одну форму. Поэтому такой вызов обычно **не быстрее**, а иногда медленнее, чем вызов через обычный интерфейс. Не используй дженерики «для скорости» без бенчмарка. Детали в дизайн-документе по ссылке в источниках.
:::

::: trap Дженерик-обёртка над any
```go
// Плохо: T нигде не используется для проверки, это any в костюме дженерика.
func ToJSON[T any](v T) ([]byte, error) {
	return json.Marshal(v)
}

// Хорошо: json.Marshal и так принимает any, обёртка не нужна вовсе.
b, err := json.Marshal(v)
```

Если параметр типа встречается в сигнатуре один раз и сразу уходит в функцию, принимающую `any`, дженерик ничего не проверяет и не даёт. Параметр типа полезен, когда связывает несколько мест: вход и выход (`func Max[T](a, b T) T`), элемент и контейнер.
:::

## Что выведет программа?

```go
type IDs []int

func Clone1[E any](s []E) []E     { return append([]E(nil), s...) }
func Clone2[S ~[]E, E any](s S) S { return append(S(nil), s...) }

func main() {
	ids := IDs{1, 2}
	fmt.Printf("%T %T\n", Clone1(ids), Clone2(ids))
}
```

<Predict :options="['main.IDs main.IDs', '[]int main.IDs', '[]int []int', 'ошибка компиляции в Clone1']" :correct="1">

`Clone1` принимает `[]E`: `IDs` присваивается в `[]int`, `E` выводится как `int`, и результат имеет тип `[]int`, методы `IDs` потеряны. `Clone2` с ограничением `S ~[]E` выводит `S = IDs` и возвращает тот же тип. Именно поэтому функции пакета `slices` объявлены через `S ~[]E`.

</Predict>

```go
func Count[T comparable](xs []T, v T) int {
	n := 0
	for _, x := range xs {
		if x == v {
			n++
		}
	}
	return n
}

func main() {
	fmt.Println(Count([]any{1, "1", int64(1), 1.0, 1}, any(1)))
}
```

<Predict :options="['5', '4', '2', 'ошибка компиляции: any не comparable']" :correct="2">

`T` здесь `any`, и `==` сравнивает интерфейсы: равны только значения с тем же динамическим типом `int`. `"1"` это строка, `int64(1)` другой тип, а нетипизированная константа `1.0`, попав в `any`, становится `float64`. Совпали два элемента `1`.

</Predict>

```go
func First[T any](xs []T) T {
	var zero T
	if len(xs) == 0 {
		return zero
	}
	return xs[0]
}

func main() {
	fmt.Println(First([]*int{}) == nil, First([]string{}) == "", First[int](nil))
}
```

<Predict :options="['true true 0', 'паника: индекс вне диапазона', 'false true 0', 'ошибка компиляции: nil вместо слайса']" :correct="0">

`var zero T` даёт нулевое значение любого типа: `nil` для указателя, `""` для строки, `0` для `int`. В последнем вызове `T` указан явно, а `nil` подходит как значение типа `[]int`. Без явного `[int]` компилятору было бы не из чего вывести `T`.

</Predict>

::: interview
<details><summary>Что такое ограничение (constraint) в Go и чем оно отличается от обычного интерфейса?</summary>

Ограничение это интерфейс, который задаёт набор допустимых типов для параметра типа. Кроме методов, оно может перечислять типы через `|` и использовать `~T`. Такие интерфейсы с элементами-типами можно использовать только как ограничения, не как тип переменной. Внутри дженерика разрешены операции, которые поддерживают все типы из набора.

</details>
<details><summary>Что означает ~ в ограничении?</summary>

`~T` означает «любой тип, базовый (underlying) тип которого `T`». Без тильды `int` пускает только сам `int`, с тильдой ещё и `type UserID int`. Поэтому в ограничениях из встроенных типов почти всегда пишут `~`: иначе пользователи с именованными типами не смогут вызвать функцию. Тильду можно ставить только перед типом, который сам является своим базовым (встроенные и литералы типов вроде `[]E`).

</details>
<details><summary>Что такое comparable и какой подвох с интерфейсами?</summary>

Встроенное ограничение: тип поддерживает `==` и `!=`. Нужно для ключей мап и множеств. С Go 1.20 ему удовлетворяют и интерфейсные типы (`any`, `error`), хотя их сравнение может запаниковать в рантайме, если внутри несравнимое значение (слайс, мапа). Для конкретных типов всё проверяется на этапе компиляции.

</details>
<details><summary>Чем cmp.Ordered отличается от comparable?</summary>

`comparable` даёт только `==`/`!=`, в него входят структуры, указатели, каналы, интерфейсы. `cmp.Ordered` даёт `<`, `<=`, `>`, `>=` и состоит из целых, вещественных и строк (с `~`). Ни структуры, ни указатели в `Ordered` не входят. Для сортировки сложных типов используют `slices.SortFunc` с функцией сравнения.

</details>
<details><summary>Когда использовать дженерики, а когда интерфейсы?</summary>

Дженерики, когда код одинаковый для всех типов и работает с самими значениями: контейнеры, структуры данных, функции над слайсами и мапами, операторы. Интерфейсы, когда нужно вызвать метод и поведение у типов разное. Если функция только вызывает методы параметра, интерфейс проще и обычно не медленнее. Правило: начни с конкретного кода и обобщай, когда появилось реальное дублирование.

</details>
<details><summary>Как Go реализует дженерики: мономорфизация или боксинг?</summary>

Гибрид: GC shape stenciling со словарями. Код генерируется по одной копии на «форму» типа (типы с одинаковым базовым типом делят форму, все указатели одну), а различия передаются скрытым словарём. Это компромисс между размером бинарника и скоростью. Следствие: вызов метода у значения типа-параметра идёт через словарь (у любой формы), поэтому дженерик с вызовами методов обычно не быстрее интерфейса.

</details>
<details><summary>Можно ли сделать type switch по параметру типа?</summary>

Напрямую нет: `cannot use type switch on type parameter value`. Можно через `any(v).(type)`. Но ветвление по типам внутри дженерика обычно означает, что нужен не дженерик, а интерфейс с методом или отдельные функции.

</details>
<details><summary>Есть ли в Go дженерик-методы?</summary>

С Go 1.27 есть: метод может объявить собственные параметры типов (`func (s *Stack[T]) MapTo[U any](...)`). Но у методов интерфейсов параметров типов быть не может, и дженерик-метод не реализует метод интерфейса. До 1.27 вместо такого метода писали свободную функцию (пример из стандартной библиотеки: `rand.N` в `math/rand/v2`, а с 1.27 появился и метод `(*Rand).N`). Не путай с `slices.Sort` и `maps.Keys`: они функции по другой причине. Они работают со встроенными безымянными типами `[]E` и `map[K]V`, а методы можно объявить только у определённого (именованного) типа своего пакета, с дженериками или без.

</details>
:::
