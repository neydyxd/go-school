# Интерфейсы

Интерфейс в Go это список методов. Любой тип, у которого есть эти методы, автоматически ему удовлетворяет: без `implements`, без наследования, без регистрации. Звучит как мелочь, но на этом держится вся архитектура Go-сервисов: `io.Reader` читает из файла, сети и gzip-архива одинаково, `http.Handler` обслуживает любой твой тип, а репозиторий в тестах подменяется фейком в десять строк.

Если ты пришёл из TypeScript, многое покажется знакомым: там тоже структурная типизация, и объект подходит под `interface`, если у него есть нужные поля. Разница в том, что в Go интерфейс описывает только **поведение** (методы), а не форму данных, и проверка частично переезжает в рантайм: интерфейсное значение знает, какой конкретный тип в нём лежит, и его можно оттуда достать.

В этом уроке разберём, как интерфейсы выглядят и как ими пользоваться в коде: неявная реализация, маленькие интерфейсы, правило «принимай интерфейсы, возвращай структуры», type assertion и type switch. Как интерфейс устроен в памяти и откуда берётся знаменитая ловушка с `nil`, будет в следующем уроке.

## Интерфейс как контракт

```go
type Shape interface {
	Area() float64
	Perimeter() float64
}

type Rect struct{ W, H float64 }

func (r Rect) Area() float64      { return r.W * r.H }
func (r Rect) Perimeter() float64 { return 2 * (r.W + r.H) }

func Describe(s Shape) string {
	return fmt.Sprintf("площадь %.1f, периметр %.1f", s.Area(), s.Perimeter())
}

func main() {
	fmt.Println(Describe(Rect{3, 4})) // площадь 12.0, периметр 14.0
}
```

`Rect` нигде не говорит «я Shape». Компилятор видит, что у `Rect` есть оба метода с нужными сигнатурами, и разрешает передать его в `Describe`. Это и есть **неявная реализация** (duck typing, но проверенный компилятором).

Что это даёт на практике:

- **Интерфейс можно объявить после типа и в другом пакете.** Ты пишешь функцию, которой нужен «кто-то, кто умеет `Read`», объявляешь интерфейс у себя, и под него подходит `*os.File` из стандартной библиотеки, хотя её авторы о твоём интерфейсе не знали.
- **Нет зависимости от пакета с интерфейсом.** Тип `Rect` не импортирует пакет, где объявлен `Shape`. Граф зависимостей остаётся плоским.
- **Совпадение должно быть точным.** Имя метода, типы параметров и результатов. `Area() int` вместо `Area() float64` уже не подходит.

### Проверка на этапе компиляции

Раз связь неявная, легко случайно сломать реализацию: переименовал метод, и тип молча перестал подходить под интерфейс. Ошибка всплывёт только там, где тип передают в интерфейс. Идиоматичная страховка:

```go
var _ Shape = Rect{}         // Rect должен реализовывать Shape
var _ io.Writer = (*Buf)(nil) // *Buf должен реализовывать io.Writer
```

Пустой идентификатор `_` значит «значение не нужно», но проверка типов при этом выполняется. Такие строки встречаются в каждом серьёзном проекте.

### Методы со значением и с указателем

Тут первая ловушка, на которой спотыкаются все. Набор методов (**method set**) у типа `T` и у `*T` разный:

| Получатель метода | Есть у `T` | Есть у `*T` |
|---|---|---|
| `func (t T) M()` | да | да |
| `func (t *T) M()` | нет | да |

Указатель «видит» все методы, а значение только методы со значимым получателем. Почему так: если в интерфейс положить значение `T`, там окажется **копия**, и метод с `*T` изменял бы эту копию, а не твою переменную. Чтобы не плодить незаметные баги, язык просто запрещает такую конструкцию.

```go
type Speaker interface{ Speak() string }
type Dog struct{}

func (d *Dog) Speak() string { return "Гав" }

func main() {
	var s Speaker = Dog{}
	fmt.Println(s.Speak())
}
```

<Predict :options="['Гав', 'ошибка компиляции', 'паника: nil pointer dereference', 'пустая строка']" :correct="1">

`Dog does not implement Speaker (method Speak has pointer receiver)`. Метод объявлен на `*Dog`, значит под интерфейс подходит только `&Dog{}`. Исправить можно двумя способами: `var s Speaker = &Dog{}` или сделать получатель значимым `func (d Dog) Speak()`.

</Predict>

Правило для практики: если хоть один метод типа меняет состояние и поэтому принимает `*T`, делай указатели получателями у всех методов и передавай в интерфейсы `&T{}`. Смешивать можно, но читать такой код тяжело.

## Маленькие интерфейсы

Посмотри на самые известные интерфейсы стандартной библиотеки:

```go
type Reader interface {
	Read(p []byte) (n int, err error)
}

type Writer interface {
	Write(p []byte) (n int, err error)
}

type Stringer interface {
	String() string
}

type error interface {
	Error() string
}
```

По одному методу. Роб Пайк сформулировал это как пословицу: *the bigger the interface, the weaker the abstraction*. Чем больше методов, тем меньше типов могут интерфейсу удовлетворить и тем сложнее написать фейк для теста. Интерфейс с одним методом реализует кто угодно.

Большие интерфейсы в Go собирают **встраиванием** маленьких:

```go
type ReadWriter interface {
	Reader
	Writer
}

type ReadWriteCloser interface {
	Reader
	Writer
	Closer
}
```

Набор методов `ReadWriter` это объединение наборов `Reader` и `Writer`. Функция, которой нужно только читать, должна просить `io.Reader`, а не `io.ReadWriteCloser`: так её проще переиспользовать и тестировать.

Ещё одна конвенция: интерфейс с одним методом называют по методу с суффиксом `-er`: `Reader`, `Writer`, `Closer`, `Stringer`, `Flusher`. Не `IReader` и не `ReaderInterface`.

### Пустой интерфейс

Интерфейс без методов `interface{}` удовлетворяется любым типом. С Go 1.18 у него есть встроенный псевдоним `any`, пиши его. `any` нужен там, где тип действительно заранее неизвестен: `fmt.Println(a ...any)`, разбор произвольного JSON, контейнеры до дженериков. В бизнес-логике `any` почти всегда признак того, что типы спроектированы не до конца: компилятор перестаёт тебе помогать, и проверки уезжают в рантайм.

## Принимай интерфейсы, возвращай структуры

Главное правило проектирования API в Go:

```go
// Плохо: возвращаем интерфейс, объявленный рядом с реализацией.
type UserStore interface {
	Get(id int) (User, error)
	Save(u User) error
	Delete(id int) error
	List() ([]User, error)
}

func NewPostgresStore(db *sql.DB) UserStore { ... }

// Хорошо: возвращаем конкретный тип.
type PostgresStore struct{ db *sql.DB }

func NewPostgresStore(db *sql.DB) *PostgresStore { ... }
```

Почему возвращать структуру:

- Вызывающий получает **всё**: все методы, а не только те, что попали в интерфейс. Если завтра у `PostgresStore` появится метод `Ping`, его сразу можно вызвать.
- Добавить метод в конкретный тип безопасно. Добавить метод в экспортированный интерфейс значит сломать всех, кто его реализует.
- Переход по коду в редакторе ведёт к реализации, а не к интерфейсу.

Почему принимать интерфейс: функция говорит, **что ей нужно**, и ничего лишнего.

```go
// Сервису регистрации нужно только получать и сохранять пользователей.
type userRepo interface {
	Get(id int) (User, error)
	Save(u User) error
}

type SignupService struct {
	repo userRepo
}

func NewSignupService(repo userRepo) *SignupService {
	return &SignupService{repo: repo}
}
```

Интерфейс `userRepo` объявлен **на стороне потребителя** (в пакете сервиса), маленький и даже неэкспортированный. `*PostgresStore` под него подходит автоматически, а в тестах сервиса подойдёт фейк на мапе. Это отличие Go от Java и C#, где интерфейс обычно лежит рядом с реализацией: в Go интерфейс принадлежит тому, кто его **использует**.

Пример из стандартной библиотеки: `bufio.NewReader(rd io.Reader) *bufio.Reader`. Принимает интерфейс, возвращает конкретную структуру. Так устроено почти всё в `io`, `bufio`, `compress/*`.

## Интерфейсы-обёртки

Раз функции просят маленький интерфейс, их легко обернуть. Классический приём: тип, который сам реализует `io.Writer` и внутри держит другой `io.Writer`.

```go
type CountingWriter struct {
	w io.Writer
	n int64
}

func (c *CountingWriter) Write(p []byte) (int, error) {
	n, err := c.w.Write(p)
	c.n += int64(n)
	return n, err
}

func main() {
	cw := &CountingWriter{w: os.Stdout}
	fmt.Fprintf(cw, "привет\n")
	fmt.Println(cw.n) // 13: 6 букв по 2 байта и перевод строки
}
```

`fmt.Fprintf` понятия не имеет о `CountingWriter`, он просит `io.Writer`. Так устроены middleware в HTTP-серверах, `gzip.Writer`, `io.TeeReader`, `io.LimitReader`: цепочки обёрток над одним маленьким интерфейсом. Это ты напишешь в домашке.

## Type assertion: достаём конкретный тип

Интерфейсное значение помнит, какой конкретный тип в нём лежит (его называют **динамическим типом**). Достать значение обратно можно через **type assertion** `x.(T)`:

```go
var x any = 42

n := x.(int)        // 42
s, ok := x.(string) // "", false: в x не string
n2, ok := x.(int)   // 42, true
```

Две формы:

- `v := x.(T)` паникует, если в `x` не `T`.
- `v, ok := x.(T)` не паникует: при несовпадении `ok == false`, а `v` нулевое значение `T`.

### Утверждение к интерфейсу: «а умеешь ли ты ещё?»

`T` в `x.(T)` может быть не только конкретным типом, но и другим интерфейсом. Тогда вопрос звучит так: «есть ли у значения внутри ещё и эти методы?». На этом построен паттерн **необязательных возможностей**:

```go
type Flusher interface{ Flush() error }

func finish(w io.Writer) error {
	if f, ok := w.(Flusher); ok {
		return f.Flush() // умеет сбрасывать буфер: сбрасываем
	}
	return nil // не умеет: и не надо
}
```

Стандартная библиотека делает так постоянно. `io.Copy` проверяет, не реализует ли источник `io.WriterTo` (тогда копирование идёт без промежуточного буфера), а HTTP-обработчики проверяют, умеет ли `ResponseWriter` быть `http.Flusher`, чтобы стримить ответ. Функция просит минимальный интерфейс, но пользуется большим, если повезло.

## Type switch

Когда вариантов несколько, цепочку утверждений заменяет **type switch**:

```go
func describe(x any) string {
	switch v := x.(type) {
	case nil:
		return "nil"
	case error:
		return "ошибка: " + v.Error()
	case fmt.Stringer:
		return "stringer: " + v.String()
	case int:
		return fmt.Sprintf("int, удвоенное %d", v*2)
	case string, []byte:
		return fmt.Sprintf("текст типа %T", v)
	default:
		return fmt.Sprintf("неизвестно: %T", v)
	}
}
```

Правила, которые спрашивают на собесах:

- `x.(type)` можно писать **только** внутри `switch`.
- В ветке с одним типом `v` имеет этот тип: в `case int` можно писать `v*2`.
- В ветке с несколькими типами (`case string, []byte`) и в `default` у `v` тип самого `x`, то есть интерфейс. Компилятор не знает, какой из типов пришёл.
- Ветки проверяются **по порядку**, срабатывает первая подходящая. Если тип реализует и `error`, и `fmt.Stringer`, сработает ветка, которая стоит выше.
- `case nil` ловит nil-интерфейс (в нём нет ни типа, ни значения). Не путай с пустым интерфейсом `any`: это тип без методов.

```go
var x any = int64(5)
switch v := x.(type) {
case int, int64:
	fmt.Println(v + 1)
}
```

<Predict :options="['6', 'ошибка компиляции', 'ничего не выведет', 'panic']" :correct="1">

`invalid operation: v + 1 (mismatched types any and untyped int)`. В ветке с двумя типами `v` имеет тип `any`, и складывать его с числом нельзя. Разнеси типы по отдельным веткам или сделай утверждение внутри ветки.

</Predict>

::: trap Type switch вместо полиморфизма
Если в нескольких местах кода стоят одинаковые type switch по одним и тем же твоим типам, ты вручную пишешь то, что должен делать интерфейс.

```go
// Плохо: добавишь Triangle и забудешь поправить один из switch.
func area(s any) float64 {
	switch v := s.(type) {
	case Rect:
		return v.W * v.H
	case Circle:
		return math.Pi * v.R * v.R
	}
	return 0
}

// Хорошо: каждый тип сам знает свою площадь.
type Shape interface{ Area() float64 }

func total(shapes []Shape) (sum float64) {
	for _, s := range shapes {
		sum += s.Area()
	}
	return sum
}
```

Type switch уместен на границах системы, где типы действительно чужие и заранее неизвестны: разбор JSON в `any`, обработка ошибок разных пакетов, `fmt`.
:::

## Интерфейсы, которые встретишь каждый день

| Интерфейс | Пакет | Метод | Где встречается |
|---|---|---|---|
| `error` | встроенный | `Error() string` | везде, подробно в уроке «Ошибки» |
| `fmt.Stringer` | `fmt` | `String() string` | как значение печатается в `%v` и `Println` |
| `io.Reader` / `io.Writer` | `io` | `Read`, `Write` | файлы, сеть, HTTP-тела, сжатие |
| `io.Closer` | `io` | `Close() error` | всё, что держит ресурс |
| `sort.Interface` | `sort` | `Len`, `Less`, `Swap` | сортировка своих коллекций |
| `http.Handler` | `net/http` | `ServeHTTP(w, r)` | любой HTTP-обработчик |
| `context.Context` | `context` | `Deadline`, `Done`, `Err`, `Value` | отмена и дедлайны, модуль про конкурентность |

`fmt.Stringer` стоит знать особенно: если у типа есть `String() string`, `fmt` печатает его результат вместо полей структуры. И здесь снова работают наборы методов: если `String` объявлен на `*T`, значение `T` печатается как обычная структура (задача на это ниже).

::: trap Интерфейс «на всякий случай»
Новички, особенно после Java, заводят интерфейс на каждую структуру: `UserService` и `UserServiceImpl`, `Repository` и `RepositoryImpl`, при единственной реализации.

```go
// Плохо: интерфейс рядом с единственной реализацией, «чтобы было».
type Notifier interface{ Notify(msg string) error }
type notifierImpl struct{ client *smtp.Client }
func NewNotifier(c *smtp.Client) Notifier { return &notifierImpl{c} }

// Хорошо: конкретный тип. Интерфейс появится у потребителя,
// когда он реально понадобится (второй реализацией или фейком в тесте).
type EmailNotifier struct{ client *smtp.Client }
func NewEmailNotifier(c *smtp.Client) *EmailNotifier { return &EmailNotifier{c} }
```

В Go говорят *don't design with interfaces, discover them*: интерфейсы не проектируют заранее, их обнаруживают, когда появляется второй потребитель или нужна подмена в тестах.
:::

::: trap Интерфейс хранит копию значения
Когда значение (не указатель) кладётся в интерфейс, туда попадает его копия. Дальнейшие изменения исходной переменной интерфейс не видит.

```go
type Counter struct{ n int }

func (c Counter) Value() int { return c.n }

c := Counter{n: 1}
var v interface{ Value() int } = c
c.n = 100
fmt.Println(v.Value(), c.Value()) // 1 100
```

Если нужно, чтобы интерфейс «смотрел» на живой объект, клади указатель: `var v ... = &c` (и тогда метод может быть и на `*Counter`).
:::

::: hood Почему проверка «реализует ли» дешёвая
Компилятор проверяет реализацию интерфейса статически везде, где может: при присваивании `var s Shape = Rect{}` он сравнивает наборы методов и заодно заранее строит таблицу методов для пары `(Shape, Rect)`. Когда такой пары нет на этапе компиляции, например при утверждении `w.(Flusher)`, рантайм ищет нужную таблицу в глобальном кеше, а если её нет, строит один раз и запоминает. Поэтому повторные утверждения и type switch быстрые. Как именно выглядят эти таблицы (`itab`) и само интерфейсное значение, разберём в следующем уроке «[Интерфейсы под капотом](./l02-interfaces-internals)».
:::

## Что выведет программа?

```go
var x any = "5"
n := x.(int)
fmt.Println(n)
```

<Predict :options="['5', '0', 'ошибка компиляции', 'panic: interface conversion: interface {} is string, not int']" :correct="3">

Однозначная форма без `ok` паникует при несовпадении типа. Компилятор не может это поймать: динамический тип известен только во время выполнения. Строку `"5"` в число так не превратить, для этого есть `strconv.Atoi`. В рабочем коде почти всегда используй форму с `ok`.

</Predict>

```go
type T struct{}

func (t *T) String() string { return "ptr" }

func main() {
	fmt.Println(T{}, &T{})
}
```

<Predict :options="['ptr ptr', '{} ptr', '{} {}', 'ошибка компиляции']" :correct="1">

`String` объявлен на `*T`. Значение `T{}` не реализует `fmt.Stringer`, и `fmt` печатает его как обычную структуру `{}`. А `&T{}` реализует и печатается как `ptr`. Ошибки компиляции нет: `Println` принимает `...any`, подходит что угодно.

</Predict>

```go
var x any = 42
s, ok := x.(string)
fmt.Printf("%q %v\n", s, ok)
switch v := x.(type) {
case fmt.Stringer:
	fmt.Println("stringer", v)
case int:
	fmt.Println("int", v*2)
default:
	fmt.Printf("другое %T\n", v)
}
```

<Predict :options="['паника на x.(string)', 'пустая строка, false, затем int 84', 'строка 42, true, затем int 84', 'пустая строка, false, затем другое int']" :correct="1">

Форма с `ok` не паникует: `s` получает нулевое значение `""`, `ok == false`. В type switch `int` не реализует `fmt.Stringer`, поэтому срабатывает ветка `int`, где `v` уже имеет тип `int` и умножается на 2.

</Predict>

::: interview
<details><summary>Как тип реализует интерфейс в Go? Чем это отличается от Java?</summary>

Неявно: если у типа есть все методы интерфейса с точно совпадающими сигнатурами, он интерфейсу удовлетворяет. Ключевого слова `implements` нет. Следствия: интерфейс можно объявить позже и в другом пакете, чем тип; тип не зависит от пакета с интерфейсом; интерфейсы объявляют на стороне потребителя. Проверить соответствие на этапе компиляции можно строкой `var _ I = (*T)(nil)`.

</details>
<details><summary>Что такое method set? Почему значение T не подходит под интерфейс, если метод объявлен на *T?</summary>

Method set типа `T` включает только методы со значимым получателем, а `*T` включает и значимые, и указательные. Когда значение кладётся в интерфейс, внутри оказывается копия. Если бы туда можно было положить `T` и вызвать метод на `*T`, метод менял бы копию, а не исходную переменную, и это был бы скрытый баг. Поэтому язык это запрещает: ошибка «method has pointer receiver».

</details>
<details><summary>Что значит «принимай интерфейсы, возвращай структуры»?</summary>

Функции и конструкторы принимают параметры минимального интерфейсного типа (то, что им реально нужно), а возвращают конкретные типы. Принимая интерфейс, функция становится гибкой и легко тестируется подменой. Возвращая структуру, ты отдаёшь вызывающему все методы, можешь добавлять новые без поломки чужого кода, а интерфейс вызывающий объявит сам, если понадобится. Исключения бывают: `error` всегда возвращают интерфейсом, а фабрики, которые выбирают реализацию в рантайме, вынуждены возвращать интерфейс.

</details>
<details><summary>Почему в Go любят маленькие интерфейсы?</summary>

Чем меньше методов, тем больше типов интерфейсу удовлетворяют и тем проще написать фейк для теста. `io.Reader` с одним методом реализуют файлы, сокеты, буферы, архивы, HTTP-тела, и всё это совместимо между собой. Большие интерфейсы собирают встраиванием маленьких (`io.ReadWriteCloser`). Пословица: «чем больше интерфейс, тем слабее абстракция».

</details>
<details><summary>Чем отличаются две формы type assertion?</summary>

`v := x.(T)` паникует, если динамический тип не `T` (или не реализует интерфейс `T`). `v, ok := x.(T)` не паникует: при несовпадении `ok == false`, `v` нулевое значение `T`. В рабочем коде почти всегда нужна вторая форма. Паникующую оправдывает только инвариант, который нарушиться не может.

</details>
<details><summary>Какой тип у переменной в ветке type switch?</summary>

В ветке с одним типом переменная имеет этот тип. В ветке с несколькими типами через запятую и в `default` переменная имеет тип исходного выражения, то есть интерфейс. Ветки проверяются сверху вниз, и срабатывает первая подходящая, поэтому порядок важен, если тип реализует несколько интерфейсов из веток. `case nil` срабатывает для nil-интерфейса, в котором нет ни типа, ни значения.

</details>
<details><summary>Что такое any и когда его стоит использовать?</summary>

`any` это встроенный псевдоним для `interface{}` (с Go 1.18), ему удовлетворяет любой тип. Использовать стоит, когда тип действительно неизвестен заранее: форматированный вывод, разбор произвольного JSON, обобщённые контейнеры в старом коде. В бизнес-логике `any` отключает проверку типов компилятором; часто вместо него нужен конкретный интерфейс с методами или дженерик.

</details>
<details><summary>Где в Go принято объявлять интерфейс: рядом с реализацией или у потребителя?</summary>

У потребителя. Пакет, которому нужна зависимость, сам объявляет маленький интерфейс с нужными ему методами. Реализация о нём не знает. Так зависимости направлены правильно, интерфейс не раздувается чужими методами, а в тестах потребителя легко подставить фейк. Исключение: широко используемые абстракции вроде `io.Reader` или `http.Handler`, которые живут в общем пакете.

</details>
<details><summary>Как проверить, что значение «умеет» дополнительный метод, если функция принимает только io.Writer?</summary>

Утверждением к интерфейсу: `if f, ok := w.(interface{ Flush() error }); ok { f.Flush() }`. Это паттерн необязательных возможностей, на нём работают `io.Copy` (проверяет `io.WriterTo` и `io.ReaderFrom`) и `http.Flusher` в HTTP-сервере.

</details>
:::
