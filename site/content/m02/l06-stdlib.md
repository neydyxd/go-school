# Стандартная библиотека, которую надо знать

Стандартная библиотека Go закрывает большую часть того, на что в Node.js ставят пакеты: HTTP-сервер и клиент, JSON, работа с файлами и временем, криптография, тесты. Код на Go во многом это умение собирать программу из маленьких кирпичиков `io`, `bufio`, `fmt`, `os`, `time`, `strconv`, `encoding/json`, которые прекрасно стыкуются друг с другом через интерфейсы.

Этот урок не справочник по всем пакетам: справочник есть на pkg.go.dev. Здесь то, что встречается в каждом сервисе и о чём спрашивают на собесе: контракт `io.Reader`, зачем нужен `bufio` и где у него грабли, основные глаголы `fmt`, `os` для файлов и окружения, ловушки `time` (их много, и они реально ломают продакшен), `strconv` и основы `encoding/json`.

В конце урока мини-проект модуля: ядро утилит в духе `wc` и `grep`, которое работает с любым `io.Reader`, хоть с файлом, хоть с сетью.

## io.Reader и io.Writer

Ты уже знаешь интерфейсы из первых уроков модуля. Два главных:

```go
type Reader interface {
	Read(p []byte) (n int, err error)
}

type Writer interface {
	Write(p []byte) (n int, err error)
}
```

`Read` **заполняет** переданный тобой буфер `p` и говорит, сколько байт записал. Не возвращает новый слайс: память выделяет вызывающий, и один буфер можно переиспользовать миллион раз. Это сделано ради производительности.

### Контракт Read

В документации `io.Reader` описаны правила, которые нужно знать наизусть:

1. `Read` возвращает `0 <= n <= len(p)` и может прочитать **меньше**, чем `len(p)`, даже если данные ещё будут. Сеть отдаёт то, что пришло.
2. Данные и ошибка могут прийти **одновременно**: `n > 0` и `err == io.EOF` в одном вызове. Поэтому **сначала обработай `n` байт, потом смотри на ошибку**.
3. `io.EOF` означает нормальный конец данных, это не авария.
4. Возврат `0, nil` разрешён, но означает «ничего не произошло», а не конец.
5. Реализация не должна запоминать `p` после возврата.

Правильный цикл чтения:

```go
buf := make([]byte, 4096)
for {
	n, err := r.Read(buf)
	process(buf[:n]) // сначала данные, даже если err != nil
	if err == io.EOF {
		break
	}
	if err != nil {
		return err
	}
}
```

::: trap Ошибка раньше данных
```go
// Плохо: если reader вернул последние байты вместе с io.EOF, они потеряются.
n, err := r.Read(buf)
if err != nil {
	return err
}
process(buf[:n])

// Хорошо: обработать n байт, потом разбираться с ошибкой (цикл выше).
```

Часто писать такой цикл руками вообще не нужно: `io.ReadAll`, `io.Copy`, `bufio.Scanner` уже соблюдают контракт. Пиши цикл сам, только если обрабатываешь поток кусками.
:::

### Кирпичики пакета io

| Функция | Что делает |
|---|---|
| `io.Copy(dst, src)` | перекачивает всё из Reader в Writer буфером 32 КБ, возвращает число байт |
| `io.ReadAll(r)` | читает всё в память (осторожно с большими входами) |
| `io.ReadFull(r, buf)` | читает ровно `len(buf)` байт или возвращает ошибку |
| `io.LimitReader(r, n)` | отдаёт не больше `n` байт: защита от огромного тела запроса |
| `io.MultiReader(r1, r2)` | склеивает несколько источников в один поток |
| `io.TeeReader(r, w)` | всё прочитанное из `r` попутно пишет в `w` |
| `io.MultiWriter(w1, w2)` | пишет одно и то же сразу в несколько мест |
| `io.Discard` | Writer, который всё выбрасывает |
| `io.Pipe()` | синхронная труба: что пишут в один конец, читают из другого |

Они собираются в конвейеры:

```go
r := io.MultiReader(strings.NewReader("раз "), strings.NewReader("два\n"))
var copyOf strings.Builder
tee := io.TeeReader(r, &copyOf)
n, err := io.Copy(os.Stdout, io.LimitReader(tee, 100))
// раз два
fmt.Println(n, err, copyOf.Len()) // 14 <nil> 14
```

Что реализует `io.Reader` в стандартной библиотеке: `*os.File`, `*strings.Reader`, `*bytes.Buffer`, `*bytes.Reader`, тело HTTP-запроса и ответа (`r.Body`), `net.Conn`, `*gzip.Reader`, `*bufio.Reader`. Функция, которая принимает `io.Reader`, работает со всем этим без изменений, и тестировать её можно на `strings.NewReader`.

::: hood Почему Read принимает буфер, а не возвращает
Если бы `Read` возвращал `[]byte`, каждый вызов выделял бы память, и сборщик мусора работал бы на каждый пакет из сети. С переданным буфером вызывающий решает, сколько памяти и когда: `io.Copy` берёт один буфер на 32 КБ и гоняет через него гигабайты. Пакет `testing/iotest` помогает проверить, что твой код не полагается на «удобное» поведение источника: `iotest.OneByteReader` отдаёт данные по байту, `iotest.HalfReader` по половине запрошенного, `iotest.DataErrReader` возвращает последние данные вместе с `io.EOF`, а `iotest.TestReader` проверяет твою реализацию `Read` на соответствие контракту. Всё это ты используешь в домашке и мини-проекте.
:::

## bufio: буферизация и построчное чтение

Каждый `Read` у файла или сокета это системный вызов. Читать по байту из файла напрямую в тысячи раз медленнее, чем большими кусками. `bufio.Reader` и `bufio.Writer` держат буфер (4096 байт по умолчанию) и ходят в нижний источник редко.

### Scanner

Самый удобный способ читать построчно:

```go
sc := bufio.NewScanner(os.Stdin)
for sc.Scan() {
	line := sc.Text() // строка без \n (и без \r перед ним)
	fmt.Println(len(line))
}
if err := sc.Err(); err != nil { // ошибку проверяем ПОСЛЕ цикла
	return err
}
```

`sc.Split(bufio.ScanWords)` переключает на слова, `bufio.ScanRunes` на руны.

::: trap Scanner и длинные строки
По умолчанию `Scanner` не принимает токен длиннее 64 КБ (`bufio.MaxScanTokenSize`). На длинной строке (минифицированный JSON в одну строку, лог с огромным стектрейсом) цикл просто остановится, а ошибка будет только в `sc.Err()`.

```go
long := strings.Repeat("a", 70000)

// Плохо: прочитали одну строку из трёх, и если не проверить Err, никто не узнает.
sc := bufio.NewScanner(strings.NewReader("ok\n" + long + "\nlast"))
n := 0
for sc.Scan() {
	n++
}
fmt.Println(n, sc.Err()) // 1 bufio.Scanner: token too long

// Хорошо: явный лимит (до 1 МБ) и обязательная проверка Err.
sc = bufio.NewScanner(strings.NewReader("ok\n" + long + "\nlast"))
sc.Buffer(make([]byte, 0, 64*1024), 1<<20)
// ...тот же цикл: 3 <nil>
```

Если длина строк не ограничена вовсе, используй `bufio.Reader.ReadString('\n')` или `ReadBytes`: они растят результат сколько нужно.
:::

### Writer и Flush

`bufio.Writer` копит данные и отправляет вниз, когда буфер заполнится. Остаток уходит только по `Flush`. Пока буфер не заполнен и не вызван `Flush`, нижний writer не получает ни байта (задача на это в конце урока):

```go
out := bufio.NewWriter(os.Stdout)
for _, line := range lines {
	fmt.Fprintln(out, line) // пишем в буфер, а не в терминал
}
if err := out.Flush(); err != nil { // без этой строки хвост вывода потеряется
	return err
}
```

Правило: после последней записи **всегда** `Flush` и проверка его ошибки. `defer w.Flush()` удобно, но ошибку так потеряешь; для файлов лучше явный `Flush`, затем `Close`, и обе ошибки проверить.

## fmt: глаголы, которые нужны каждый день

```go
type point struct{ X, Y int }
p := point{1, 2}
fmt.Printf("%v|%+v|%#v|%T\n", p, p, p, p)
// {1 2}|{X:1 Y:2}|main.point{X:1, Y:2}|main.point
fmt.Printf("%q|%x|%8.3f|%-5s|%05d\n", "го", "go", 3.14159, "ab", 42)
// "го"|676f|   3.142|ab   |00042
```

| Глагол | Что печатает |
|---|---|
| `%v` | значение в формате по умолчанию; для ошибок и `Stringer` их текст |
| `%+v` | структуры с именами полей: лучший выбор для логов и отладки |
| `%#v` | значение в синтаксисе Go: видно типы и кавычки |
| `%T` | тип значения |
| `%q` | строка в кавычках с экранированием: видно пробелы и невидимые символы |
| `%d`, `%x`, `%08b` | целые: десятичное, шестнадцатеричное, двоичное с нулями |
| `%.2f`, `%e` | вещественные |
| `%w` | только в `fmt.Errorf`: обернуть ошибку (урок «Ошибки») |

Семейство функций: `Print*` в stdout, `Sprint*` в строку, `Fprint*` в любой `io.Writer`, `Errorf` в ошибку. `fmt.Sscanf` и `fmt.Sscan` умеют разбирать строки, но для чисел обычно удобнее `strconv`.

`go vet` проверяет соответствие глаголов и аргументов (`%d` для строки, лишние аргументы), поэтому опечатки в формате ловятся до запуска.

## os: файлы, аргументы, окружение

```go
data, err := os.ReadFile("config.json")  // весь файл в память
err = os.WriteFile("out.txt", data, 0o644)

f, err := os.Open("big.log")             // только чтение, *os.File это io.Reader
if err != nil {
	return err
}
defer f.Close()

out, err := os.Create("result.txt")      // создать или обрезать до нуля
```

- `os.Args`: аргументы командной строки, `os.Args[0]` имя программы. Для флагов есть пакет `flag`.
- `os.Getenv("PORT")` возвращает `""`, если переменной нет. Чтобы отличить «пусто» от «не задано», используй `v, ok := os.LookupEnv("PORT")`.
- `os.Exit(code)` завершает процесс **немедленно, без выполнения `defer`**. Буферы `bufio.Writer` не сбросятся, файлы не закроются через `defer`.

```go
func main() {
	defer fmt.Println("defer")
	fmt.Println("main")
	os.Exit(3) // напечатает только main
}
```

Ошибки `os` содержат путь и операцию (`*fs.PathError`) и разворачиваются до `fs.ErrNotExist`, `fs.ErrPermission`: проверяй через `errors.Is(err, fs.ErrNotExist)`.

::: trap Закрытие файла, в который писали
```go
// Плохо: ошибка Close теряется, а для записи она важна:
// данные могут не дойти до диска именно в момент закрытия.
f, _ := os.Create("out.txt")
defer f.Close()
f.Write(data)

// Хорошо: ошибку Close проверяем и отдаём наружу.
func save(path string, data []byte) (err error) {
	f, err := os.Create(path)
	if err != nil {
		return err
	}
	defer func() {
		if cerr := f.Close(); cerr != nil && err == nil {
			err = cerr
		}
	}()
	_, err = f.Write(data)
	return err
}
```

Для файлов, которые только читаешь, `defer f.Close()` без проверки нормален.
:::

## time и его ловушки

`time` используется везде: дедлайны, таймауты, TTL, логи, расписания. И в нём больше всего неочевидного.

### Time и Duration

- `time.Time` это момент времени с наносекундной точностью **и часовым поясом** (`Location`).
- `time.Duration` это `int64` наносекунд. Константы `time.Second`, `time.Minute` и т.д. сами являются `Duration`.

```go
fmt.Println(time.Duration(100))          // 100ns
fmt.Println(90 * time.Minute)            // 1h30m0s
d, _ := time.ParseDuration("1h30m")       // 1h30m0s, d.Minutes() == 90
n := 5
fmt.Println(time.Duration(n) * time.Second) // 5s
```

`time.Sleep(100)` спит 100 **наносекунд**, а не миллисекунд. А `time.Second * n` с `n int` не скомпилируется: `invalid operation: time.Second * n (mismatched types time.Duration and int)`. Нетипизированная константа (`5 * time.Second`) работает, переменную нужно конвертировать.

Нулевое значение `time.Time` это 1 января года 1 UTC, а не «пусто» и не Unix-эпоха. Проверяй через `t.IsZero()`.

### Форматирование: 2006-01-02 15:04:05

Вместо `YYYY-MM-DD` Go использует **эталонную дату**: понедельник, 2 января 2006, 15:04:05, часовой пояс MST (-0700). Запоминалка: 1 2 3 4 5 6 7, месяц 01, день 02, час 03 (15), минута 04, секунда 05, год 06, пояс -07.

```go
t := time.Date(2026, time.March, 9, 14, 5, 7, 0, time.UTC)
t.Format("2006-01-02 15:04:05") // 2026-03-09 14:05:07
t.Format(time.RFC3339)          // 2026-03-09T14:05:07Z
t.Format("02.01.2006 3:04PM")   // 09.03.2026 2:05PM
t.Format(time.DateOnly)         // 2026-03-09 (константа с Go 1.20)
```

```go
t := time.Date(2026, time.March, 9, 14, 5, 7, 0, time.UTC)
fmt.Println(t.Format("YYYY-MM-DD"))
fmt.Println(t.Format("2006-02-01"))
```

<Predict :options="['2026-03-09 и 2026-03-09', 'YYYY-MM-DD и 2026-09-03', 'ошибка: неизвестный формат', 'YYYY-MM-DD и 2026-03-09']" :correct="1">

`YYYY`, `MM`, `DD` не являются элементами раскладки, и `Format` печатает их как есть, без ошибки. Во второй строке день и месяц перепутаны: `02` это день, `01` месяц, поэтому 9 марта превращается в «2026-09-03». Такая опечатка в API тихо переставит даты для всех дней до 12 числа.

</Predict>

### Parse и часовые пояса

```go
t, _ := time.Parse("2006-01-02 15:04", "2026-03-09 10:00")
fmt.Println(t) // 2026-03-09 10:00:00 +0000 UTC

msk, _ := time.LoadLocation("Europe/Moscow")
t2, _ := time.ParseInLocation("2006-01-02 15:04", "2026-03-09 10:00", msk)
fmt.Println(t2, t2.UTC()) // 2026-03-09 10:00:00 +0300 MSK 2026-03-09 07:00:00 +0000 UTC
fmt.Println(t.Sub(t2))    // 3h0m0s
```

- `time.Parse` без пояса во входной строке считает время **UTC**. Если пользователь из Москвы ввёл «10:00», нужен `ParseInLocation`.
- Храни и передавай время в UTC или в RFC3339 со смещением, в локальный пояс переводи только при показе.
- `LoadLocation` читает базу часовых поясов из системы. В минимальных Docker-образах (`scratch`, иногда `distroless`) её нет, и будет ошибка. Лечится `import _ "time/tzdata"`: база вшивается в бинарник (плюс примерно 450 КБ).

### == против Equal и монотонные часы

`time.Now()` возвращает время с двумя показаниями: «настенные» часы (wall clock), которые могут прыгнуть при синхронизации NTP, и **монотонные**, которые только растут. Монотонная часть используется в `Sub`, `Since`, `Until`, поэтому измерение длительности не ломается при переводе системных часов.

Но из-за этого `==` сравнивает не то, что ты думаешь: он сравнивает структуры целиком, включая монотонное показание и указатель на `Location`.

```go
t := time.Now()
t2 := t.Round(0) // убирает монотонное показание
fmt.Println(t == t2, t.Equal(t2)) // false true
u := t.UTC()
fmt.Println(t == u, t.Equal(u))   // false true
```

::: trap Сравнение времени через ==
```go
// Плохо: один и тот же момент в разных поясах или с монотонной частью не равен.
if order.CreatedAt == cached.CreatedAt { ... }
m := map[time.Time]int{} // ключи-моменты в разных поясах станут разными ключами

// Хорошо.
if order.CreatedAt.Equal(cached.CreatedAt) { ... }
m2 := map[int64]int{} // ключ t.UnixNano() или t.UTC().Round(0)
```

`Before`, `After`, `Equal`, `Compare` (Go 1.20) сравнивают моменты корректно.
:::

### Календарная арифметика

`Add` прибавляет точную длительность, `AddDate` календарные годы, месяцы и дни. Это разные вещи:

```go
ny, _ := time.LoadLocation("America/New_York")
// 8 марта 2026 в США переходят на летнее время, в сутках 23 часа.
start := time.Date(2026, time.March, 7, 12, 0, 0, 0, ny)
fmt.Println(start.Add(24 * time.Hour)) // 2026-03-08 13:00:00 -0400 EDT
fmt.Println(start.AddDate(0, 0, 1))    // 2026-03-08 12:00:00 -0400 EDT
```

«Завтра в то же время» это `AddDate(0, 0, 1)`, а «через 24 часа» это `Add(24 * time.Hour)`. В России сейчас перевода часов нет, но клиенты твоего сервиса могут быть где угодно.

`AddDate` **нормализует** несуществующие даты переносом вперёд:

```go
jan31 := time.Date(2026, time.January, 31, 0, 0, 0, 0, time.UTC)
fmt.Println(jan31.AddDate(0, 1, 0).Format(time.DateOnly))
```

<Predict :options="['2026-02-28', '2026-03-03', '2026-02-31', 'паника: неверная дата']" :correct="1">

31 февраля не существует. `AddDate` сначала получает «2026-02-31», затем нормализует лишние 3 дня в март. Для подписки «списывать раз в месяц» это баг: клиент, оформивший её 31 января, получит следующее списание 3 марта. Как сделать «не позже последнего дня месяца», ты напишешь в домашке.

</Predict>

### Таймеры и Ticker

```go
select {
case res := <-ch:
	use(res)
case <-time.After(2 * time.Second):
	return errors.New("timeout")
}

ticker := time.NewTicker(time.Minute)
defer ticker.Stop()
for range ticker.C {
	collectMetrics()
}
```

Что поменялось в Go 1.23: таймеры и тикеры, на которые больше нет ссылок, собираются сборщиком мусора, даже если не вызван `Stop`. Поэтому классическая утечка «`time.After` в цикле `select` держит память до срабатывания» ушла. Каналы таймеров стали небуферизованными, и после `Reset` или `Stop` из канала гарантированно не придёт устаревшее значение. В Go 1.23-1.26 новое поведение включалось только для модулей с `go 1.23` и выше в `go.mod`, а настройка `asynctimerchan` возвращала старое. В Go 1.27 эту настройку удалили: начиная с тулчейна 1.27 каналы таймеров синхронные для любого модуля, независимо от версии в `go.mod`. В статьях до 2024 года ты ещё встретишь советы про обязательный `Stop` и сложный ритуал со сливом канала перед `Reset`: в современном коде он не нужен, но `defer ticker.Stop()` остаётся хорошим тоном.

::: trap time.Since в defer
```go
// Плохо: аргументы defer вычисляются сразу, будет ~0s.
start := time.Now()
defer log.Println("заняло", time.Since(start))

// Хорошо: вычисление внутри отложенной функции.
defer func() { log.Println("заняло", time.Since(start)) }()
```

С Go 1.22 `go vet` ловит это: `call to time.Since is not deferred`.
:::

## strconv: строки в числа и обратно

```go
n, err := strconv.Atoi("42")             // int
i, err := strconv.ParseInt("ff", 16, 64) // 255
f, err := strconv.ParseFloat("3.14", 64)
b, err := strconv.ParseBool("true")      // "yes" не примет: invalid syntax

s := strconv.Itoa(42)                    // "42"
s = strconv.FormatFloat(3.14159, 'f', 1, 64) // "3.1"
s = strconv.Quote("hi\n")                // "\"hi\\n\""
```

Ошибки разбора имеют тип `*strconv.NumError` с полями `Func`, `Num`, `Err`, где `Err` это `strconv.ErrSyntax` или `strconv.ErrRange`:

```go
_, err := strconv.Atoi("12a")
fmt.Println(err) // strconv.Atoi: parsing "12a": invalid syntax
_, err = strconv.Atoi("99999999999999999999")
fmt.Println(err) // strconv.Atoi: parsing "99999999999999999999": value out of range
errors.Is(err, strconv.ErrRange) // true
```

Частая ошибка новичка: `string(65)` вместо `strconv.Itoa(65)`. `string(rune(65))` даёт `"A"` (символ с кодом 65), а не `"65"`. `go vet` предупреждает о конверсии `string(int)`.

## encoding/json: основы

```go
type Event struct {
	Name  string   `json:"name"`
	Tags  []string `json:"tags,omitempty"` // не выводить, если пусто
	Count int      `json:"count,string"`   // число как строка "3"
	Skip  string   `json:"-"`              // никогда не выводить
}

b, _ := json.Marshal(Event{Name: "deploy", Count: 3, Skip: "x"})
fmt.Println(string(b)) // {"name":"deploy","count":"3"}
```

Что надо знать:

- В JSON попадают только **экспортированные** поля (урок про пакеты). Имя по умолчанию это имя поля, тег задаёт своё.
- `omitempty` пропускает нулевые значения для чисел, строк, слайсов, мап, указателей, но **не** для структур. С Go 1.24 есть `omitzero`: пропускает нулевое значение любого типа, включая `time.Time{}`, и учитывает метод `IsZero()`.
- `Unmarshal` по умолчанию **игнорирует неизвестные поля** и сопоставляет имена без учёта регистра. Для строгого разбора API: `json.Decoder` с `DisallowUnknownFields()`.
- Числа при разборе в `any` становятся `float64`. Большой ID `12345678901234567890` превратится в `1.2345678901234567e+19` и потеряет точность. Лечится `Decoder.UseNumber()` или конкретным типом поля.
- `json.NewDecoder(r)` читает из `io.Reader` потоком: `r.Body` HTTP-запроса или файл с объектом на строку (NDJSON) через цикл `for dec.More() { dec.Decode(&v) }`.

```go
var v any
json.Unmarshal([]byte(`{"n": 42, "list": [1, "a", true, null]}`), &v)
m := v.(map[string]any)
fmt.Printf("%T %T\n", m["n"], m["list"]) // float64 []interface {}
```

::: hood encoding/json в Go 1.27
В Go 1.27 в стандартную библиотеку вошли `encoding/json/v2` и `encoding/json/jsontext`: новая реализация со строгими значениями по умолчанию (отвергает невалидный UTF-8 и повторяющиеся ключи в объекте) и потоковым API на уровне токенов. Старый пакет `encoding/json` теперь работает **поверх новой реализации**: поведение `Marshal`/`Unmarshal` сохранено, но тексты ошибок могут отличаться, а разбор заметно быстрее. Мигрировать на v2 не обязательно, v1 поддерживается. Отключить новую реализацию можно сборкой с `GOEXPERIMENT=nojsonv2`, но эту возможность обещают убрать. Вывод для тебя: не сравнивай тексты ошибок JSON в тестах, проверяй сам факт ошибки или её тип.
:::

## Что выведет программа?

```go
var buf bytes.Buffer
w := bufio.NewWriter(&buf)
fmt.Fprint(w, "hello")
fmt.Println(buf.Len())
w.Flush()
fmt.Println(buf.Len())
```

<Predict :options="['5 и 5', '0 и 5', '0 и 0', '5 и 10']" :correct="1">

До `Flush` пять байт лежат во внутреннем буфере `bufio.Writer`, а в `buf` ничего нет. После `Flush` они уходят в `buf`. Забытый `Flush` в конце программы, которая пишет в файл, даёт пустой или обрезанный файл без единой ошибки.

</Predict>

```go
d := 1500 * time.Millisecond
fmt.Println(d, int(d.Seconds()), d/time.Second)
```

<Predict :options="['1.5s 1 1ns', '1.5s 1.5 1s', '1.5s 1 1s', '1500ms 1 1']" :correct="0">

`Duration` печатается в человекочитаемом виде `1.5s`. `d.Seconds()` возвращает `float64` 1.5, а `int` отбрасывает дробную часть. А `d/time.Second` это деление двух `Duration`, результат тоже `Duration`, равный 1, то есть одной наносекунде: `1ns`. Чтобы получить целое число секунд, пиши `int(d / time.Second)` или `int64(d.Seconds())`, а не печатай `Duration` как число.

</Predict>

```go
r := io.LimitReader(strings.NewReader("привет"), 3)
b, err := io.ReadAll(r)
fmt.Printf("%q %v\n", b, err)
```

<Predict :options="['привет и nil', 'при и nil', 'п с обрезком второй буквы и nil', 'п и ошибка io.ErrUnexpectedEOF']" :correct="2">

Выведется `"п\xd1" <nil>`. `LimitReader` считает **байты**, а кириллица в UTF-8 занимает по 2 байта: «п» это `d0 bf`, от «р» остался только первый байт `d1`. Для `ReadAll` конец лимита это обычный `io.EOF`, поэтому ошибки нет. Если режешь текст по байтам, будь готов к разрезанной руне: `utf8.Valid` подскажет, всё ли цело.

</Predict>

```go
var e struct {
	Name  string `json:"name"`
	Count int    `json:"count,string"`
}
err := json.Unmarshal([]byte(`{"name": "a", "extra": 1, "count": "7"}`), &e)
fmt.Println(e.Name, e.Count, err)
```

<Predict :options="['a 7 &lt;nil&gt;', 'ошибка: unknown field extra', 'a 0 и ошибка типа', 'ошибка: count строка, а не число']" :correct="0">

`Unmarshal` по умолчанию молча пропускает неизвестные поля (`extra`). Опция тега `,string` говорит, что число в JSON записано строкой, поэтому `"7"` разбирается в `7`. Неизвестное поле стало бы ошибкой только у `Decoder` с `DisallowUnknownFields()`.

</Predict>

::: interview
<details><summary>Опиши контракт io.Reader.</summary>

`Read(p)` записывает в `p` до `len(p)` байт и возвращает их число и ошибку. Может вернуть меньше, чем просили, даже если данные ещё будут. Может вернуть `n > 0` вместе с ошибкой, включая `io.EOF`, поэтому сначала обрабатывают `n` байт, потом ошибку. `io.EOF` означает нормальный конец. `0, nil` разрешено, но не означает конец. Реализация не должна сохранять `p`. При `len(p) == 0` возвращает `0`.

</details>
<details><summary>Зачем нужен bufio и какие у него ловушки?</summary>

Уменьшает число системных вызовов: читает и пишет большими блоками через внутренний буфер. Ловушки: `bufio.Writer` отдаёт данные вниз только при заполнении буфера или `Flush`, и забытый `Flush` теряет хвост; `bufio.Scanner` по умолчанию ограничивает токен 64 КБ и при превышении останавливается с ошибкой, видимой только в `Err()`. Для длинных строк `Scanner.Buffer` с большим лимитом или `Reader.ReadString`.

</details>
<details><summary>Чем отличаются %v, %+v и %#v?</summary>

`%v` печатает значение в формате по умолчанию, для структур только значения полей. `%+v` добавляет имена полей, удобно в логах. `%#v` печатает в синтаксисе Go с именем типа и кавычками у строк. `%T` печатает тип. Для ошибок и типов с `String()` `%v` вызывает эти методы.

</details>
<details><summary>Как в Go задать формат даты и почему он такой странный?</summary>

Через эталонную дату `Mon Jan 2 15:04:05 MST 2006`: в раскладке пишешь, как эта дата выглядела бы в нужном формате, например `2006-01-02`. Элементы соответствуют числам 1-7: месяц 1, день 2, час 3 (15), минута 4, секунда 5, год 6, пояс -7. Неизвестные символы печатаются как есть, поэтому `YYYY-MM-DD` не даёт ошибки, а молча выводится буквально. Готовые константы: `time.RFC3339`, `time.DateOnly`, `time.DateTime`.

</details>
<details><summary>Почему время нельзя сравнивать через ==?</summary>

`==` сравнивает структуру `time.Time` целиком: стенные часы, монотонное показание и указатель на часовой пояс. Один и тот же момент в UTC и в Москве, или с монотонной частью и без неё, по `==` не равны. Для сравнения моментов есть `Equal`, `Before`, `After`, `Compare`. По той же причине `time.Time` плохой ключ мапы.

</details>
<details><summary>Чем Add(24*time.Hour) отличается от AddDate(0, 0, 1)?</summary>

`Add` прибавляет точную длительность, `AddDate` календарные единицы с учётом часового пояса. В день перехода на летнее время в сутках 23 или 25 часов, и результаты различаются на час. Кроме того, `AddDate` нормализует несуществующие даты: 31 января плюс месяц даёт 3 марта (в невисокосный год).

</details>
<details><summary>Что изменилось в таймерах в Go 1.23?</summary>

Таймеры и тикеры без ссылок на них собираются сборщиком мусора даже без `Stop`, поэтому `time.After` в цикле больше не держит память. Каналы таймеров стали небуферизованными (`cap` равна 0), и после `Reset`/`Stop` не придёт устаревшее значение. В 1.23-1.26 это действовало для модулей с `go 1.23+`; в Go 1.27 настройку `asynctimerchan` удалили, и с тулчейном 1.27 синхронные каналы таймеров работают для любого модуля.

</details>
<details><summary>Какие подводные камни у encoding/json?</summary>

Только экспортированные поля; неизвестные поля молча игнорируются (для строгости `Decoder.DisallowUnknownFields`); имена сопоставляются без учёта регистра; числа в `any` становятся `float64` и теряют точность на больших ID (`UseNumber`); `omitempty` не пропускает нулевые структуры, для этого `omitzero` (Go 1.24). В Go 1.27 v1 работает поверх новой реализации v2, тексты ошибок могут отличаться.

</details>
:::

## Мини-проект модуля

Утилита в духе `wc` и `grep`, построенная на `io.Reader`. Ядро логики (подсчёт и поиск) лежит в пакете с тестами, а CLI-обвязку ты пишешь сам по ТЗ ниже. Это первый проект курса, где сходятся интерфейсы (`io.Reader` вместо файлов), ошибки (частичный результат плюс ошибка чтения) и стандартная библиотека (`bufio`, `unicode/utf8`, `os`, `flag`).

### Часть 1: ядро с тестами

Пакет `homework/m02/project-wc/`, два файла:

- `count.go`: `Count(r io.Reader) (Stats, error)` считает строки (как `wc -l`, по числу `\n`), слова (отрезки без пробельных рун по `unicode.IsSpace`), руны и байты. Память O(1): не читай вход целиком. Тесты подают данные по одному байту, половинками, вместе с `io.EOF`, строку в 1 МБ без переводов строки, битый UTF-8 и reader, который падает посередине (нужно вернуть посчитанное и ошибку).
- `grep.go`: `Grep(r io.Reader, pattern string, opt Options) ([]Match, error)` возвращает строки с подстрокой и их номера. Опции: `IgnoreCase` (в том числе для кириллицы) и `Invert`. Тесты проверяют последнюю строку без `\n`, CRLF, пустой шаблон, строку в 400 КБ и ошибку чтения. Там же потоковая `GrepFunc(r, pattern, opt, fn func(Match) error) error`: она не копит совпадения, а сразу отдаёт каждое в `fn`, и останавливается, если `fn` вернула ошибку. `Grep` удобно написать поверх неё. Память `Grep` растёт с числом совпадений, у `GrepFunc` нет.

```bash
cd homework && go test -v ./m02/project-wc/
```

Подсказка: подумай, почему `bufio.Scanner` без настройки здесь не подойдёт, и что умеет `bufio.Reader` из коробки (`ReadRune`, `ReadString`).

### Часть 2: CLI по ТЗ

Две команды в том же модуле домашки: `homework/m02/project-wc/cmd/gowc/main.go` и `homework/m02/project-wc/cmd/gogrep/main.go`. Обе используют ядро из части 1 и никакой логики подсчёта и поиска сами не содержат.

**gowc** `[-l] [-w] [-m] [-c] [файл...]`

- Флаги через пакет `flag`: `-l` строки, `-w` слова, `-m` руны, `-c` байты. Без флагов печатает строки, слова и байты (как `wc`).
- Без файлов читает stdin. С файлами печатает строку на файл с именем в конце, а при двух и более файлах ещё строку `total`.
- Числа выровнены по правому краю в колонках (`fmt.Printf("%8d")`).
- Если файл не открылся, печатает ошибку в stderr (`gowc: нет.txt: no such file or directory`), продолжает с остальными и в конце выходит с кодом 1.

**gogrep** `[-i] [-v] [-n] [-c] шаблон [файл...]`

- `-i` без учёта регистра, `-v` инверсия, `-n` префикс `номер:` у строк, `-c` вместо строк печатать только количество.
- Без файлов читает stdin. При нескольких файлах каждая строка начинается с `имя_файла:`.
- Коды выхода как у настоящего grep: 0 если что-то нашлось, 1 если ничего, 2 при ошибке (нет шаблона, файл не открылся).
- Вывод через `bufio.Writer` поверх `os.Stdout` с `Flush` перед выходом. Помни: `os.Exit` не выполняет `defer`.
