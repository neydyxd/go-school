# Интерфейсы под капотом

На собеседовании по Go почти гарантированно будет вопрос: «функция вернула `nil`, а `err != nil` сработало, почему?». Ответ «так устроены интерфейсы» засчитают только наполовину. Нужно уметь нарисовать, из чего состоит интерфейсное значение, и показать, где в нём прячется не-`nil`.

Это не только собесная экзотика. Ловушка с `nil` в интерфейсе ломает реальные сервисы: обработчик возвращает «ошибку», которой нет, клиент получает 500, а в логах `<nil>`. Знание устройства интерфейсов объясняет и другие вещи: почему сравнение двух `any` может паниковать, почему значение в интерфейсе часто уезжает в кучу и почему вызов через интерфейс чуть дороже прямого.

В этом уроке спускаемся в рантайм: смотрим на `iface` и `eface` прямо в исходниках Go 1.27, разбираем `itab`, конверсии, сравнение и ту самую ловушку.

## Два слова в памяти

Интерфейсное значение в Go занимает **два машинных слова**: 16 байт на 64-битной платформе.

```go
var e any
var s fmt.Stringer
fmt.Println(unsafe.Sizeof(e), unsafe.Sizeof(s)) // 16 16
```

В рантайме есть две структуры. Открой `$(go env GOROOT)/src/runtime/runtime2.go`:

```go
type iface struct {
	tab  *itab
	data unsafe.Pointer
}

type eface struct {
	_type *_type
	data  unsafe.Pointer
}
```

- **`eface`** (empty interface) это представление `any`. Первое слово указывает на **дескриптор типа** `_type`, второе на данные.
- **`iface`** это представление интерфейса с методами (`error`, `io.Reader`, `fmt.Stringer`). Первое слово указывает на **`itab`**: таблицу, в которой есть и тип, и методы.

Почему две структуры: у пустого интерфейса нет методов, таблица ему не нужна, достаточно знать тип. У непустого интерфейса при каждом вызове метода нужно быстро найти адрес функции, и для этого заведена `itab`.

::: hood Что лежит в itab
`itab` объявлена в `src/internal/abi/iface.go` (в рантайме это псевдоним `type itab = abi.ITab`):

```go
type ITab struct {
	Inter *InterfaceType
	Type  *Type
	Hash  uint32     // copy of Type.Hash. Used for type switches.
	Fun   [1]uintptr // variable sized. fun[0]==0 means Type does not implement Inter.
}
```

```text
 iface (error)                  itab для пары (error, *MyErr)
┌──────────────┐              ┌───────────────────────────────┐
│ tab  ────────┼─────────────►│ Inter ──► описание error       │
├──────────────┤              │ Type  ──► описание *MyErr      │
│ data ────┐   │              │ Hash      хеш типа             │
└──────────┼───┘              │ Fun[0] ──► (*MyErr).Error      │
           │                  └───────────────────────────────┘
           ▼
     объект MyErr в куче
```

- `Inter`: какой интерфейс.
- `Type`: какой конкретный тип лежит внутри (тот самый **динамический тип**).
- `Hash`: копия хеша типа, ускоряет type switch.
- `Fun`: массив адресов методов **в порядке методов интерфейса**. Объявлен как `[1]uintptr`, но память под `itab` выделяется с запасом, и массив на деле длиной в число методов. `Fun[0] == 0` это специальная отметка «тип не реализует интерфейс», рантайм кеширует и отрицательные ответы.

Вызов `err.Error()` компилируется примерно в «возьми `tab`, возьми `tab.Fun[0]`, вызови его, передав `data` первым аргументом». Это один косвенный переход.

Где берутся `itab`. Для пар (интерфейс, тип), известных на этапе компиляции (`var e error = &MyErr{}`), компилятор генерирует `itab` статически. Для пар, которые появляются только в рантайме (утверждение `x.(io.Writer)` над `any`), работает функция `getitab` в `src/runtime/iface.go`: она ищет `itab` в глобальной хеш-таблице `itabTable` без блокировок, а если не нашла, берёт lock, строит таблицу (`itabInit` проходит методы интерфейса и типа за один проход, оба списка отсортированы) и добавляет в кеш. Память под `itab` выделяется через `persistentalloc` и никогда не освобождается: пар (интерфейс, тип) в программе конечное число.
:::

## nil-интерфейс

Нулевое значение любого интерфейса: оба слова нулевые.

```text
var err error            // iface{tab: nil, data: nil}   err == nil -> true
```

Сравнение `err == nil` проверяет именно это: **оба слова** пустые. И вот откуда ловушка. Положим в интерфейс nil-указатель:

```go
var p *MyErr          // p == nil
var err error = p     // iface{tab: itab(error, *MyErr), data: nil}
fmt.Println(err == nil) // false
```

```text
 err (error)
┌───────────────┐
│ tab  ─────────┼──► itab(error, *MyErr)    тип известен!
├───────────────┤
│ data = nil    │    указатель пустой
└───────────────┘
 err == nil ?  нет: tab не nil
```

Интерфейс не nil: он знает, что внутри `*MyErr`. То, что сам указатель `nil`, интерфейс не делает `nil`. Аналогия: коробка с наклейкой «тут кот», в которой нет кота. Коробка не пустая, на ней наклейка.

Полная версия классической ловушки:

```go
type MyErr struct{}

func (*MyErr) Error() string { return "boom" }

func run() error {
	var p *MyErr
	// ...где-то тут p мог стать не nil, но не стал...
	return p
}

func main() {
	err := run()
	fmt.Println(err == nil)
}
```

<Predict :options="['true', 'false', 'паника: nil pointer dereference', 'ошибка компиляции']" :correct="1">

`return p` конвертирует `*MyErr` в `error`. Получается интерфейс с типом `*MyErr` и пустым указателем. `err == nil` проверяет оба слова, первое не пустое, поэтому `false`. Вызывающий код решит, что произошла ошибка, хотя её не было.

</Predict>

::: trap Возвращай nil явно, а не через типизированную переменную
Ловушка появляется всегда, когда функция с результатом-интерфейсом возвращает переменную конкретного указательного типа.

```go
// Плохо: при успехе возвращается не-nil error с nil-указателем внутри.
func validate(u User) error {
	var verr *ValidationError
	if u.Name == "" {
		verr = &ValidationError{Field: "name"}
	}
	return verr
}

// Хорошо: на пути успеха явный nil интерфейсного типа.
func validate(u User) error {
	if u.Name == "" {
		return &ValidationError{Field: "name"}
	}
	return nil
}
```

То же правило для вспомогательных функций: если `check()` возвращает `*ValidationError`, то в функции с результатом `error` пиши `if e := check(); e != nil { return e }; return nil`, а не `return check()`. Правило шире ошибок: любая функция, возвращающая интерфейс (`io.Reader`, `Shape`), страдает так же.
:::

А что будет, если такую «не-nil» ошибку напечатать?

```go
type NotFound struct{ ID int }

func (e *NotFound) Error() string { return fmt.Sprintf("id %d не найден", e.ID) }

func find(id int) *NotFound { return nil }

func main() {
	var err error = find(1)
	if err != nil {
		fmt.Println("ошибка:", err)
	}
}
```

<Predict :options="['ничего не выведет', 'ошибка: &lt;nil&gt;', 'ошибка: id 0 не найден', 'паника: nil pointer dereference']" :correct="1">

`err != nil` истинно (интерфейс знает тип `*NotFound`), поэтому `Println` вызывается. Метод `Error` разыменовывает `e.ID` на nil-указателе и паникует, но `fmt` перехватывает панику из `Error`/`String`, и если получатель nil-указатель, печатает `<nil>`. В логах получается загадочное `ошибка: <nil>`: верный признак этой ловушки.

</Predict>

Заметь: вызывать методы на nil-указателе внутри интерфейса можно, это не паника сама по себе. Метод получает `nil` в качестве получателя, и если он не обращается к полям, всё работает:

```go
var p *MyErr
var e error = p
fmt.Println(e.Error()) // boom: метод не трогает поля

var e2 error
e2.Error() // panic: invalid memory address or nil pointer dereference
```

У `e2` нет `itab`, адрес метода взять неоткуда, отсюда паника.

### Как проверить «nil внутри»

Иногда это всё-таки нужно (например, в общем коде, который получает `any`). Через `reflect`:

```go
func isNil(v any) bool {
	if v == nil {
		return true
	}
	rv := reflect.ValueOf(v)
	switch rv.Kind() {
	case reflect.Pointer, reflect.Map, reflect.Slice, reflect.Chan, reflect.Func, reflect.Interface:
		return rv.IsNil()
	}
	return false
}
```

`IsNil` паникует для типов, которые не могут быть `nil` (числа, структуры), отсюда `switch` по `Kind`. Но в нормальном коде правильный ответ не «проверять через reflect», а «не создавать такие значения»: возвращать явный `nil`.

## Как значение попадает в интерфейс

Второе слово, `data`, всегда указатель. Что если положить в интерфейс `int` или структуру?

- **Указателеподобные типы** (указатели, каналы, мапы, функции и структуры/массивы из одного такого поля) кладутся **прямо в слово `data`**. Рантайм называет это direct interface, флаг `TFlagDirectIface`. Аллокации нет.
- **Всё остальное** копируется в отдельный участок памяти, и в `data` пишется указатель на копию. Эту копию компилятор чаще всего размещает в куче.

Рантайм-функции конверсии живут в `src/runtime/iface.go`: `convT`, `convT64`, `convTstring`, `convTslice`. В них есть оптимизации, которые можно увидеть своими глазами:

```go
// convT64 (сокращённо)
if val < uint64(len(staticuint64s)) {
	x = unsafe.Pointer(&staticuint64s[val]) // 0..255: готовая ячейка, без аллокации
} else {
	x = mallocgc(8, uint64Type, false)
	*(*uint64)(x) = val
}
```

`staticuint64s` это массив `[256]uint64` с числами от 0 до 255. Маленькие числа в интерфейсе указывают в него. Пустая строка и nil-слайс указывают на общий `zeroVal`. Проверим аллокации:

```go
var (
	sink       any
	small, big = 5, 1000 // глобальные: компилятор не знает их значений заранее
)

func main() {
	p := &big
	fmt.Println(testing.AllocsPerRun(100, func() { sink = small })) // 0
	fmt.Println(testing.AllocsPerRun(100, func() { sink = big }))   // 1
	fmt.Println(testing.AllocsPerRun(100, func() { sink = p }))     // 0
	fmt.Println(testing.AllocsPerRun(100, func() { sink = 1000 }))  // 0
}
```

Число 1000 из переменной потребовало аллокации, 5 нет, указатель тоже нет (он direct). Константа `1000` не аллоцирует: компилятор заранее кладёт её в read-only память. То же он делает с локальной переменной, которая не меняется и адрес которой не берут, поэтому в таких замерах значения берут из глобальных переменных (или из `os.Args`), иначе все результаты выйдут нулевыми. Отсюда практический вывод: `fmt.Println(x)` с не-указательным `x` часто вызывает аллокацию, потому что аргументы `...any`. Увидеть это можно анализом побега:

```bash
go build -gcflags=-m .
# ./main.go:6:14: n escapes to heap
```

Для горячих путей (логирование в цикле на миллион итераций) это важно, поэтому быстрые логгеры вроде `log/slog` и `zap` имеют типизированные методы (`slog.Int`, `zap.Int`), которые не упаковывают число в `any`.

## Сравнение интерфейсов

Два интерфейсных значения равны, если у них **одинаковый динамический тип** и **равные значения** этого типа. В рантайме это функции `efaceeq` и `ifaceeq` из `src/runtime/alg.go`:

```go
func efaceeq(t *_type, x, y unsafe.Pointer) bool {
	if t == nil {
		return true
	}
	eq := t.Equal
	if eq == nil {
		panic(errorString("comparing uncomparable type " + toRType(t).string()))
	}
	if t.IsDirectIface() {
		return x == y
	}
	return eq(x, y)
}
```

Оператор `==` для двух `any` компилятор превращает в проверку `x._type == y._type && efaceeq(...)` (для интерфейсов с методами сравниваются `tab` и вызывается `ifaceeq`). Та же логика лежит в рантайм-функциях `nilinterequal` и `interequal`: ими пользуются мапы с ключом-интерфейсом и сравнение структур и массивов с полями-интерфейсами. Следствия:

1. **Разные типы никогда не равны**, даже если «значение одно»:

```go
var a any = 1
var b any = int64(1)
fmt.Println(a == b, a == 1) // false true
```

2. **Несравнимый тип паникует в рантайме**. Компилятор пропустит `a == b` для двух `any`, ведь интерфейсы сравнимы. Но если внутри слайсы, мапы или функции, у их дескриптора нет функции `Equal`:

```go
var c, d any = []int{1}, []int{1}
fmt.Println(c == d) // panic: runtime error: comparing uncomparable type []int
```

То же случится, если такое значение стало ключом `map[any]V`: `panic: runtime error: hash of unhashable type []int`. И с дженериками: ограничение `comparable` с Go 1.20 пропускает `any`, а паника переносится в рантайм (подробнее в уроке про дженерики).

3. **Указатели сравниваются по адресу.** Поэтому `errors.New("x") == errors.New("x")` даёт `false`: это два разных указателя на две структуры с одинаковым текстом. Именно поэтому sentinel-ошибки сравнивают с переменной, а не создают заново.

```go
var e1 error = errors.New("x")
var e2 error = errors.New("x")
fmt.Println(e1 == e2, e1.Error() == e2.Error()) // false true
```

::: trap Сравнение any со слайсом внутри
Код компилируется и годами работает, пока в `any` не прилетит слайс.

```go
// Плохо: паника, если в кеш положат []byte или map.
func changed(old, new any) bool {
	return old != new
}

// Хорошо: явно решаем, что делать с несравнимыми значениями.
func changed(old, new any) (diff bool, ok bool) {
	defer func() {
		if recover() != nil {
			diff, ok = true, false // не смогли сравнить: считаем изменившимся
		}
	}()
	return old != new, true
}
```

Ещё лучше не хранить `any` там, где тип известен: дженерик с ограничением `comparable` над конкретным типом даст ошибку компиляции, а не панику. `reflect.DeepEqual` сравнит и слайсы, но он медленный и для продакшен-логики подходит редко.
:::

## Утверждения и type switch внутри

- **Утверждение к конкретному типу** `x.(*MyErr)`: компилятор знает адрес дескриптора `*MyErr` (или статической `itab` для пары с интерфейсом `x`) и сравнивает с первым словом интерфейса. Одно сравнение указателей.
- **Утверждение к интерфейсу** `x.(io.Writer)`: нужно выяснить, реализует ли динамический тип `io.Writer`, и получить `itab`. Это `getitab` с глобальным кешем, а в современных версиях у таких мест вызова есть ещё и собственный маленький кеш (`typeAssert` и `TypeAssertCache` в `src/runtime/iface.go`).
- **Type switch** работает похоже: для веток с конкретными типами используется сравнение (и `Hash` из `itab`/`_type` для быстрого отсева), для интерфейсных веток рантайм-функция `interfaceSwitch` с кешем.

Вывод для практики: утверждения и type switch дешёвые, ими не нужно бояться пользоваться. Но они не бесплатны по сравнению с прямым вызовом метода, где тип известен компилятору.

## Цена вызова через интерфейс

Вызов метода через интерфейс это косвенный вызов по адресу из `itab.Fun`. Сам переход стоит наносекунды, главная цена в другом: компилятор не знает, какая функция будет вызвана, поэтому **не может её встроить** (inline) и хуже анализирует побег аргументов. Для 99% бэкенд-кода это не важно: запрос в БД в миллион раз дороже.

Компилятор умеет **девиртуализацию**: если он видит, что в интерфейсе точно лежит конкретный тип (например, переменную только что присвоили), он заменяет косвенный вызов прямым. С Go 1.21 при сборке с профилем (PGO, `default.pgo` в пакете `main`) компилятор девиртуализирует и горячие вызовы, где по профилю чаще всего встречается один тип, добавляя проверку типа и прямой вызов.

::: hood Посмотреть на eface своими глазами
`unsafe` позволяет наложить на интерфейс свою структуру того же вида и убедиться, что «nil-указатель в интерфейсе» это заполненный тип и пустые данные:

```go
type eface struct {
	typ, data unsafe.Pointer
}

func main() {
	var p *int
	var x any = p
	var e any

	ef := (*eface)(unsafe.Pointer(&x))
	fmt.Println(ef.typ != nil, ef.data == nil) // true true

	ef2 := (*eface)(unsafe.Pointer(&e))
	fmt.Println(ef2.typ == nil, ef2.data == nil) // true true
}
```

Только для экспериментов: раскладка внутренних структур не входит в гарантии совместимости и может измениться в любой версии.
:::

## Что выведет программа?

```go
var p *int
var x any = p
fmt.Println(x == nil, x == (*int)(nil))
```

<Predict :options="['true true', 'false true', 'false false', 'true false']" :correct="1">

`x == nil` сравнивает с nil-интерфейсом (в нём нет ни типа, ни значения): у `x` есть тип `*int`, значит не равно. `x == (*int)(nil)` сначала превращает правую часть в `any` с типом `*int` и nil-данными: типы совпали, указатели оба nil, равно.

</Predict>

```go
type Cat struct{ name string }

func (c Cat) Sound() string { return c.name + ": мяу" }

type Animal interface{ Sound() string }

func main() {
	var a, b Animal = Cat{"Барсик"}, Cat{"Барсик"}
	fmt.Println(a == b)
	var x, y any = map[string]int{}, map[string]int{}
	fmt.Println(x == y)
}
```

<Predict :options="['true, затем false', 'false, затем false', 'true, затем panic', 'ошибка компиляции']" :correct="2">

`Cat` сравнимая структура: одинаковые типы, поля равны, `true`. Во второй строке оба `any` содержат мапы. Компилятор разрешает сравнивать интерфейсы, но в рантайме у типа `map[string]int` нет функции сравнения: `panic: runtime error: comparing uncomparable type map[string]int`.

</Predict>

```go
func get() *bytes.Buffer { return nil }

func main() {
	var w io.Writer = get()
	var x any = w
	fmt.Println(w == nil, x == nil)
}
```

<Predict :options="['true true', 'false false', 'false true', 'true false']" :correct="1">

`w` получает `itab` для пары (`io.Writer`, `*bytes.Buffer`) и nil-данные, значит `w != nil`. При присваивании `x = w` интерфейс конвертируется в `any`: из `itab` берётся тип `*bytes.Buffer`, данные копируются. Тип не теряется, поэтому и `x != nil`. Ловушка переживает любое число перекладываний из интерфейса в интерфейс.

</Predict>

::: interview
<details><summary>Как интерфейс устроен в памяти?</summary>

Два машинных слова. Для пустого интерфейса (`any`) это `eface{_type, data}`: указатель на дескриптор типа и указатель на данные. Для интерфейса с методами `iface{tab, data}`, где `tab` указывает на `itab`: структуру с описанием интерфейса, конкретного типа, хешем типа и таблицей адресов методов. Данные либо лежат прямо в слове `data` (указатели и указателеподобные типы), либо `data` указывает на копию значения.

</details>
<details><summary>Почему функция вернула nil, а err != nil?</summary>

Функция вернула nil-указатель конкретного типа (например, `*MyErr`) через результат типа `error`. При конверсии в интерфейс заполняется `tab` (тип известен), а `data` остаётся nil. Интерфейс равен `nil`, только когда оба слова пустые, поэтому `err != nil`. Лечится явным `return nil` на пути успеха и тем, что функции не возвращают конкретные типы ошибок, если их результат потом идёт в `error`.

</details>
<details><summary>Что такое itab и когда он создаётся?</summary>

Таблица для пары (интерфейс, конкретный тип): указатели на оба дескриптора, хеш типа и массив адресов методов в порядке методов интерфейса. Для пар, известных при компиляции, компилятор генерирует itab статически. Для пар, возникающих в рантайме (утверждение к интерфейсу, type switch), `runtime.getitab` ищет их в глобальной таблице `itabTable`, при промахе строит и кеширует навсегда, включая отрицательный результат.

</details>
<details><summary>Когда сравнение интерфейсов паникует?</summary>

Когда динамические типы совпадают и этот тип несравним: слайс, мапа, функция или структура/массив с таким полем. Компилятор не может это проверить, потому что интерфейсы формально сравнимы. Если типы разные, сравнение вернёт `false` без паники. Аналогично паникует использование такого значения как ключа `map[any]V`.

</details>
<details><summary>Аллоцирует ли присваивание значения в интерфейс?</summary>

Зависит от типа. Указатели, каналы, мапы, функции кладутся прямо в слово данных, аллокации нет. Остальные значения копируются, и копия обычно уезжает в кучу. Есть оптимизации: числа 0-255 указывают в статический массив `staticuint64s`, пустые строки и nil-слайсы в общий `zeroVal`, а константы компилятор кладёт в read-only память. Поэтому `fmt.Println(x)` в горячем цикле может давать аллокации.

</details>
<details><summary>Почему errors.New("a") == errors.New("a") ложно?</summary>

`errors.New` возвращает указатель на новую структуру `errorString`. Интерфейсы сравниваются по типу и значению, а значение указателя это адрес. Адреса разные, значит не равны. Поэтому sentinel-ошибки объявляют один раз как переменную пакета и сравнивают через `errors.Is` с этой переменной.

</details>
<details><summary>Можно ли вызвать метод у интерфейса, внутри которого nil-указатель?</summary>

Да. Адрес метода берётся из `itab`, а nil-указатель передаётся как получатель. Если метод не разыменовывает получатель, всё сработает. Паника будет при обращении к полям или если сам интерфейс nil (`tab == nil`, адрес метода взять неоткуда).

</details>
<details><summary>Чем вызов через интерфейс дороже прямого?</summary>

Это косвенный вызов через таблицу методов. Сам переход дешёвый, основная потеря в том, что компилятор не может встроить функцию и хуже анализирует побег аргументов. Компилятор умеет девиртуализировать вызов, если тип известен статически, а с PGO (Go 1.21+) и для горячих мест по профилю. Для типичного бэкенда, где время тратится на сеть и БД, разница несущественна.

</details>
:::
