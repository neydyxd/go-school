# Ошибки

В JavaScript ошибка летит исключением куда-то вверх по стеку, и ты надеешься, что кто-то её поймает. В Go ошибка это обычное значение, которое функция возвращает последним результатом. Ты видишь её в сигнатуре, обязан с ней что-то сделать, и путь ошибки по программе читается глазами, без прыжков через `catch`.

Отсюда знаменитое `if err != nil { return err }`, над которым шутят все, кто пришёл из других языков. Шутки шутками, но на собесе по Go про ошибки спросят обязательно: чем `%w` отличается от `%v`, как работают `errors.Is` и `errors.As`, когда делать sentinel-ошибку, а когда свой тип, когда допустима паника. А в реальном сервисе от этого зависит, получит ли клиент 404 или 500, и сможешь ли ты по логу понять, где всё сломалось.

Урок опирается на предыдущий: ошибка в Go это интерфейс, и вся ловушка с `nil` в интерфейсе относится к ошибкам в первую очередь.

## error это интерфейс

```go
type error interface {
	Error() string
}
```

Любой тип с методом `Error() string` является ошибкой. Простейшие способы создать ошибку:

```go
err := errors.New("файл пуст")
err := fmt.Errorf("строка %d: неожиданный символ %q", line, ch)
```

Соглашения о стиле, которые проверяют на ревью:

- Текст с **маленькой буквы и без точки** в конце: ошибки склеиваются в цепочку `загрузка конфига: открытие файла: permission denied`, и заглавные буквы посреди строки выглядят странно.
- Ошибка **последний результат** функции: `func Load(path string) (*Config, error)`.
- При ошибке остальные результаты обычно нулевые и вызывающий их **не использует**. Исключения документируются (например, `io.Reader` может вернуть и данные, и ошибку одновременно).

### Обработай ошибку один раз

На каждом уровне у тебя три варианта: вернуть ошибку выше (обычно добавив контекст), обработать её (повторить запрос, вернуть значение по умолчанию) или залогировать и остановиться. Но **не два сразу**:

```go
// Плохо: одна ошибка попадёт в лог трижды на трёх уровнях.
if err != nil {
	log.Printf("не удалось сохранить заказ: %v", err)
	return err
}

// Хорошо: добавляем контекст и отдаём наверх, логирует один верхний уровень.
if err != nil {
	return fmt.Errorf("сохранение заказа %d: %w", order.ID, err)
}
```

## Обёртки: %w против %v

С Go 1.13 ошибку можно **обернуть**: новая ошибка содержит текст старой плюс контекст и при этом хранит саму старую ошибку внутри. Делает это глагол `%w` в `fmt.Errorf`:

```go
base := errors.New("base")
e1 := fmt.Errorf("a: %v", base) // просто текст
e2 := fmt.Errorf("b: %w", base) // обёртка
fmt.Println(e1, "|", e2)       // a: base | b: base
fmt.Println(errors.Unwrap(e2) == base, errors.Unwrap(e1) == nil) // true true
```

Текст одинаковый, а разница принципиальная. `%v` превращает ошибку в строку, и связь с исходной ошибкой теряется навсегда. `%w` сохраняет цепочку: `fmt.Errorf` возвращает значение с методом `Unwrap() error`, и по цепочке можно пройти вниз.

```text
 e2: "b: base"
   │ Unwrap()
   ▼
 base: "base"
   │ Unwrap()
   ▼
  nil
```

Когда что использовать:

- `%w`, если вызывающему может понадобиться узнать исходную ошибку: «не найдено» или «таймаут». Почти всегда.
- `%v`, если ты сознательно **прячешь** детали реализации. Обёрнутая ошибка становится частью твоего API: если сервис оборачивает `sql.ErrNoRows`, вызывающие начнут на неё полагаться, и ты уже не сможешь сменить БД, не сломав их. Иногда лучше перевести ошибку в свою (`ErrNotFound`) и обернуть уже её.

С Go 1.20 в одном `fmt.Errorf` можно использовать несколько `%w`: получится ошибка с методом `Unwrap() []error`, которая оборачивает все сразу.

::: trap Сравнение ошибок через == и по тексту
```go
// Плохо: сломается, как только кто-то обернёт ошибку.
if err == sql.ErrNoRows { ... }

// Ещё хуже: сломается при любой правке текста или локализации.
if strings.Contains(err.Error(), "no rows") { ... }

// Хорошо: проходит по всей цепочке обёрток.
if errors.Is(err, sql.ErrNoRows) { ... }
```

`==` сработает только для голой, необёрнутой ошибки. Как только между тобой и источником появится хоть один `fmt.Errorf("...: %w", err)`, сравнение начнёт молча возвращать `false`. Текст ошибки предназначен людям, а не коду.
:::

## errors.Is: «это та самая ошибка?»

`errors.Is(err, target)` идёт по цепочке (на самом деле по дереву) обёрток и проверяет каждый узел: равен ли он `target` через `==` или говорит ли его метод `Is(error) bool`, что равен.

```go
err := fmt.Errorf("handler: %w", fmt.Errorf("repo: %w", sql.ErrNoRows))
errors.Is(err, sql.ErrNoRows) // true: нашли на глубине 2
```

### Sentinel-ошибки

**Sentinel** (сигнальная) ошибка это заранее объявленная переменная пакета, с которой сравнивают:

```go
var ErrNotFound = errors.New("not found")

func (s *Store) Get(key string) (string, error) {
	v, ok := s.data[key]
	if !ok {
		return "", fmt.Errorf("get %q: %w", key, ErrNotFound)
	}
	return v, nil
}
```

Примеры из стандартной библиотеки: `io.EOF`, `sql.ErrNoRows`, `fs.ErrNotExist`, `context.Canceled`, `context.DeadlineExceeded`, `http.ErrServerClosed`. Имя по конвенции начинается с `Err`. Плюсы: просто и дёшево. Минус: никаких подробностей, кроме самого факта, и переменная становится частью публичного API пакета.

Сравнение работает потому, что `errors.New` возвращает указатель, а указатели сравниваются по адресу (см. предыдущий урок). Две разные `errors.New("not found")` никогда не равны, даже с одинаковым текстом.

::: trap io.EOF это не ошибка, а сигнал
`io.EOF` означает «данные кончились», и функции обязаны возвращать его **голым**, без обёрток: множество кода в экосистеме сравнивает `err == io.EOF`. Если твой `io.Reader` вернёт `fmt.Errorf("read: %w", io.EOF)`, `io.ReadAll` и `bufio.Scanner` решат, что случилась настоящая ошибка.

```go
// Плохо: обёрнутый EOF ломает чужой код.
return 0, fmt.Errorf("my reader: %w", io.EOF)

// Хорошо.
return 0, io.EOF
```
:::

## errors.As: «есть ли там ошибка такого типа?»

Иногда нужна не сама ошибка, а **подробности**: какой файл не открылся, какое поле не прошло валидацию. Для этого делают свой тип ошибки и достают его через `errors.As`:

```go
type QueryError struct {
	Query string
	Err   error
}

func (e *QueryError) Error() string { return "query " + e.Query + ": " + e.Err.Error() }
func (e *QueryError) Unwrap() error { return e.Err }

func main() {
	err := fmt.Errorf("загрузка профиля %d: %w", 42, getUser(42))
	fmt.Println(err)
	// загрузка профиля 42: query SELECT ... WHERE id=$1: sql: no rows in result set

	fmt.Println(errors.Is(err, sql.ErrNoRows)) // true: Unwrap ведёт к sql.ErrNoRows

	var qe *QueryError
	if errors.As(err, &qe) {
		fmt.Println(qe.Query) // SELECT ... WHERE id=$1
	}
}
```

`errors.As(err, &target)` ищет в дереве первую ошибку, которую можно присвоить в `target`, и если нашла, кладёт её туда и возвращает `true`. Второй аргумент всегда **указатель на переменную** нужного типа. Раз `Error` объявлен на `*QueryError`, переменная имеет тип `*QueryError`, а передаём `&qe` (то есть `**QueryError`).

Свой метод `Unwrap() error` делает тип частью цепочки: через него `errors.Is` и `errors.As` пройдут дальше вниз. Так устроены `*fs.PathError`, `*url.Error`, `*net.OpError`:

```go
_, err := os.Open("/нет/такого/файла")
fmt.Println(err) // open /нет/такого/файла: no such file or directory
fmt.Println(errors.Is(err, fs.ErrNotExist), err == fs.ErrNotExist) // true false

var pe *fs.PathError
fmt.Println(errors.As(err, &pe), pe.Op, pe.Path) // true open /нет/такого/файла
```

### errors.AsType (Go 1.26)

С Go 1.26 есть дженерик-версия, которая короче и не требует заводить переменную заранее:

```go
if qe, ok := errors.AsType[*QueryError](err); ok {
	fmt.Println(qe.Query)
}
```

Release notes называют её типобезопасной и более быстрой. Тип параметра ограничен `error`, поэтому ошибку «передал не тот тип» поймает компилятор, а не паника.

::: trap Не тот тип в errors.As
```go
type NotFoundError struct{ ID int }

func (e *NotFoundError) Error() string { return "not found" }

// Плохо: NotFoundError (без звёздочки) не реализует error,
// метод объявлен на указателе. Это паника в рантайме.
var nf NotFoundError
errors.As(err, &nf) // panic: errors: *target must be interface or implement error

// Хорошо: тип переменной совпадает с тем, что реально лежит в цепочке.
var nf *NotFoundError
errors.As(err, &nf)
```

`go vet` ловит эту ошибку (проверка `errorsas`), поэтому запускай его всегда. А ещё лучше `errors.AsType[*NotFoundError](err)`: там ошибка типа не скомпилируется.
:::

### Свои методы Is и As

Тип может сам решать, чему он «равен». Пример: ошибка таймаута с деталями, которая при этом должна ловиться через `errors.Is(err, ErrTimeout)`:

```go
var ErrTimeout = errors.New("timeout")

type TimeoutError struct{ Op string }

func (e TimeoutError) Error() string        { return e.Op + ": timeout" }
func (e TimeoutError) Is(target error) bool { return target == ErrTimeout }

err := fmt.Errorf("запрос: %w", TimeoutError{Op: "db"})
fmt.Println(errors.Is(err, ErrTimeout)) // true
```

Метод `Is` должен только сравнивать и не разворачивать цепочку сам: обход делает `errors.Is`. Аналогично существует метод `As(any) bool`, он нужен редко.

## Несколько ошибок: errors.Join

Валидация формы, закрытие нескольких ресурсов, параллельные запросы: иногда ошибок несколько, и нужно вернуть все. С Go 1.20 для этого есть `errors.Join`:

```go
err := errors.Join(
	&FieldError{"name", "обязательно"},
	nil, // nil-ы отбрасываются
	&FieldError{"age", "должно быть не меньше 18"},
)
fmt.Println(err)
// name: обязательно
// age: должно быть не меньше 18
```

- Текст: тексты всех ошибок через перевод строки.
- `errors.Join()` и `errors.Join(nil, nil)` возвращают `nil`, поэтому можно копить ошибки в слайс и в конце вернуть `errors.Join(errs...)`: если слайс пустой, получится настоящий `nil`.
- Результат реализует `Unwrap() []error`, и `errors.Is`/`errors.As` обходят **все** ветки. Ошибки образуют дерево, обход идёт в глубину по порядку.
- `errors.Unwrap` (функция) для такой ошибки вернёт `nil`: она умеет только одиночный `Unwrap() error`.

```go
err := errors.Join(errors.New("a"), nil, errors.New("b"))
fmt.Println(err)
fmt.Println(errors.Join(nil, nil) == nil)
```

<Predict :options="['a, nil, b в одной строке', 'a и b на двух строках, затем true', 'a и b на двух строках, затем false', 'паника из-за nil']" :correct="1">

`Join` выбрасывает nil-аргументы и склеивает тексты оставшихся через `\n`. Если не осталось ни одной ошибки, возвращается `nil`, поэтому вторая строка `true`.

</Predict>

## Какой вид ошибки выбрать

| Вид | Как выглядит | Когда |
|---|---|---|
| Непрозрачная | `errors.New(...)` или `fmt.Errorf("...: %v", err)` | вызывающему достаточно знать «что-то сломалось» и прочитать текст; детали реализации спрятаны |
| Обёртка с контекстом | `fmt.Errorf("...: %w", err)` | по умолчанию внутри своего кода: добавить контекст и оставить исходную ошибку доступной для `errors.Is/As` |
| Sentinel | `var ErrNotFound = errors.New(...)` | вызывающему нужно различать конкретный случай, деталей не нужно |
| Свой тип | `type FieldError struct{...}` | нужны подробности: поле, код, ID, ретраить ли |
| Поведение | `interface{ Timeout() bool }` | нужно спросить про свойство, не завязываясь на тип (`net.Error`) |

В типичном HTTP-сервисе это складывается в схему: слой хранения возвращает свои sentinel-ошибки (`ErrNotFound`, `ErrConflict`), бизнес-слой добавляет контекст через `%w` и типизированные ошибки валидации, а HTTP-обработчик в одном месте переводит их в статусы через `errors.Is`/`errors.As`. Это ровно то, что ты напишешь в домашке.

## panic и recover

`panic` это не «исключение для ошибок», а аварийная остановка: программа в состоянии, которого не должно было быть. Паника разматывает стек текущей горутины, выполняя все `defer`, и если её никто не остановил, программа падает с трассировкой.

Когда паника уместна:

- **Ошибка программиста**: выход за границы слайса, разыменование nil, нарушенный инвариант. Рантайм паникует сам.
- **Невозможность стартовать**: нет обязательной настройки при инициализации. Функции с префиксом `Must` (`regexp.MustCompile`, `template.Must`) паникуют, потому что вызываются с константами при старте, и ошибка там это баг в коде.

Во всех остальных случаях (нет файла, сеть упала, пользователь прислал мусор) возвращай `error`. Библиотека не должна паниковать на плохом вводе.

`recover` останавливает панику, но работает **только внутри отложенной функции** и только в той же горутине:

```go
func safe(f func()) (err error) {
	defer func() {
		if r := recover(); r != nil {
			err = fmt.Errorf("panic: %v", r)
		}
	}()
	f()
	return nil
}
```

Именованный результат `err` нужен, чтобы отложенная функция могла его изменить уже после того, как основная функция «вернулась». Так устроен middleware восстановления в HTTP-фреймворках: одна паника в обработчике не роняет весь сервер. Стандартный `net/http` делает это сам для каждого запроса.

::: hood panic(nil) с Go 1.21
Раньше `panic(nil)` было неотличимо от «паники не было»: `recover()` возвращал `nil`. С Go 1.21 такой вызов превращается в панику со значением `*runtime.PanicNilError`, и `recover()` возвращает не-nil. Вернуть старое поведение можно через `GODEBUG=panicnil=1`. Проверка `if r := recover(); r != nil` теперь надёжна.

```go
fmt.Println(safe(func() { panic(nil) }))
// panic: runtime error: panic called with nil argument
```
:::

::: trap Паника в горутине роняет весь процесс
`recover` в `main` или в middleware не поймает панику из горутины, которую ты запустил внутри обработчика. Каждая горутина, которая может запаниковать, должна иметь свой `defer` с `recover`, иначе упадёт весь сервис.

```go
// Плохо: паника внутри go func() уронит процесс, middleware не поможет.
go process(job)

// Хорошо: свой recover в горутине.
go func() {
	defer func() {
		if r := recover(); r != nil {
			log.Printf("job %d: panic: %v", job.ID, r)
		}
	}()
	process(job)
}()
```

Подробнее про горутины будет в модуле про конкурентность.
:::

## Что выведет программа?

```go
base := errors.New("base")
e1 := fmt.Errorf("a: %v", base)
e2 := fmt.Errorf("b: %w", base)
fmt.Println(errors.Is(e1, base), errors.Is(e2, base))
```

<Predict :options="['true true', 'false true', 'false false', 'true false']" :correct="1">

`%v` вставил текст `base` в строку и больше ничего не хранит, цепочки нет. `%w` сохранил ссылку, и `errors.Is` её нашёл. Тексты у `e1` и `e2` при этом почти одинаковые: по выводу в лог разницу не увидишь.

</Predict>

```go
var ErrA = errors.New("a")

func main() {
	err := fmt.Errorf("ctx: %w", errors.Join(ErrA, io.EOF))
	fmt.Println(errors.Is(err, io.EOF), errors.Unwrap(err) == nil)
}
```

<Predict :options="['true true', 'true false', 'false true', 'false false']" :correct="1">

`errors.Is` обходит всё дерево: обёртку от `fmt.Errorf`, затем результат `Join` и обе его ветки, и находит `io.EOF`. А `errors.Unwrap` снимает ровно один слой: у обёртки есть `Unwrap() error`, и он возвращает ошибку-`Join`, то есть не `nil`. Если бы мы вызвали `errors.Unwrap` у самой ошибки-`Join`, получили бы `nil`.

</Predict>

```go
func g() error {
	var err error
	defer func() {
		if r := recover(); r != nil {
			err = fmt.Errorf("panic: %v", r)
		}
	}()
	panic("boom")
	return err
}

func main() {
	fmt.Println(g())
}
```

<Predict :options="['panic: boom', '&lt;nil&gt;', 'программа упадёт с паникой', 'ошибка компиляции: код после panic']" :correct="1">

`recover` остановил панику, и `g` вернулась нормально. Но результат у неё **безымянный**: `return err` не выполнился, а присваивание локальной `err` в отложенной функции на возвращаемое значение не влияет. Вернулось нулевое значение `error`, то есть `nil`. Чтобы отложенная функция могла подменить результат, он должен быть именованным: `func g() (err error)`. Код после `panic` компилируется, `go vet` только предупредит о недостижимом коде.

</Predict>

<details><summary>Чем %w отличается от %v в fmt.Errorf?</summary>

Оба вставляют текст ошибки в сообщение. `%w` дополнительно сохраняет саму ошибку: результат реализует `Unwrap() error` (или `Unwrap() []error` при нескольких `%w`), и `errors.Is`/`errors.As` находят её в цепочке. `%v` превращает ошибку в строку, связь теряется. `%w` используют, когда вызывающему важно распознать исходную ошибку; `%v`, когда сознательно скрывают детали реализации, чтобы они не стали частью API.

</details>
<details><summary>Как работают errors.Is и errors.As?</summary>

Обе функции обходят дерево ошибок в глубину, начиная с самой `err`, разворачивая через `Unwrap() error` и `Unwrap() []error`. `Is` на каждом узле проверяет `node == target` или `node.Is(target)`. `As` проверяет, присваивается ли узел в тип, на который указывает `target` (или его метод `As` согласен), и если да, записывает его туда. `As` паникует, если `target` не указатель на тип, реализующий `error`, или на интерфейс. С Go 1.26 есть `errors.AsType[E](err)`, где тип проверяет компилятор.

</details>
<details><summary>Что такое sentinel-ошибка? Плюсы и минусы.</summary>

Заранее объявленная переменная пакета вроде `io.EOF` или `sql.ErrNoRows`, с которой сравнивают через `errors.Is`. Плюсы: просто, дёшево, ясно. Минусы: не несёт деталей; становится частью публичного API, и её уже нельзя убрать; создаёт зависимость вызывающего от пакета. Если нужны подробности, делают свой тип ошибки.

</details>
<details><summary>Когда делать свой тип ошибки?</summary>

Когда вызывающему нужны данные: какое поле не прошло валидацию, HTTP-код внешнего API, можно ли повторить запрос. Тип реализует `Error()`, при необходимости `Unwrap()`, чтобы цепочка шла дальше. Методы обычно на указателе, а возвращают `*MyError`. Достают через `errors.As` или `errors.AsType`.

</details>
<details><summary>Что делает errors.Join и чем отличается от нескольких %w?</summary>

`errors.Join(errs...)` объединяет ошибки в одну с методом `Unwrap() []error`, отбрасывая `nil`; если все `nil`, возвращает `nil`. Текст: тексты через перевод строки. `fmt.Errorf("%w и %w", a, b)` тоже даёт `Unwrap() []error`, но с собственным форматом текста. Удобно для валидации, когда нужно вернуть все ошибки сразу, и для закрытия нескольких ресурсов.

</details>
<details><summary>Когда паника оправдана, а когда нужен error?</summary>

Паника для ситуаций, которых не должно быть: ошибки программиста и нарушенные инварианты, а также невозможность запуститься (функции `Must*` с константами при инициализации). Всё, что может случиться в нормальной работе (нет файла, сеть, плохой ввод), это `error`. Библиотеки не должны паниковать на пользовательских данных. Паника не пересекает границу горутины: необработанная паника в любой горутине роняет весь процесс.

</details>
<details><summary>Где и как работает recover?</summary>

Только внутри функции, вызванной через `defer`, и только для паники в той же горутине. Возвращает значение, переданное в `panic`, и останавливает размотку стека: функция с этим `defer` возвращается нормально. Чтобы вернуть ошибку наружу, используют именованный результат. С Go 1.21 `panic(nil)` превращается в `*runtime.PanicNilError`, поэтому проверка `recover() != nil` надёжна.

</details>
<details><summary>Почему нельзя одновременно логировать и возвращать ошибку?</summary>

Каждый уровень, получив ошибку, тоже залогирует и вернёт её, и одна проблема даст несколько записей в логе с разным контекстом. Правило: обработай ошибку один раз. Нижние уровни добавляют контекст через `%w` и возвращают, а логирует и решает, что сказать пользователю, один верхний уровень (HTTP-обработчик, main).

</details>
<details><summary>Почему функция вернула nil-ошибку, а проверка err != nil сработала?</summary>

Функция вернула nil-указатель конкретного типа (`*MyErr`) через результат `error`. Интерфейс получил тип, но не значение, и перестал быть `nil`. Возвращай явный `nil` на пути успеха. Подробно в уроке «Интерфейсы под капотом».

</details>
:::
