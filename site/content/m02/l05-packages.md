# Пакеты и модули

Пока программа помещается в один `main.go`, о пакетах можно не думать. Но любой сервис на работе это десятки пакетов: `handler`, `service`, `storage`, `config`, плюс сотня внешних зависимостей. От того, как ты режешь код на пакеты, зависит, можно ли его тестировать, читать и менять без страха. А от понимания модулей зависит, сможешь ли ты обновить библиотеку, подключить свой форк или работать над двумя связанными репозиториями одновременно.

В уроке «[Установка и инструменты](../m00/l02-tools)» мы уже создавали модуль, ставили зависимости и разбирали `go.sum` и Minimal Version Selection на уровне «как пользоваться». Здесь идём глубже: видимость и `internal`, порядок инициализации и `init`, семантические версии и `/v2`, `replace`, рабочие области `go.work`.

Аналогия для фронтендера: пакет примерно как ES-модуль (файл с `export`), только в Go единица это **каталог**, а не файл. Модуль это как npm-пакет с `package.json`, но без `node_modules` в проекте и без lock-файла: всё решают `go.mod`, `go.sum` и детерминированный выбор версий.

## Пакет это каталог

Все `.go`-файлы в одном каталоге образуют один пакет и объявляют одно и то же имя `package`. Файлы внутри пакета видят всё друг у друга, никаких импортов между ними не нужно. Исключение: файлы `_test.go` могут объявить пакет `<имя>_test` (внешние тесты), про это в модуле о тестировании.

```text
shop/                  модуль example.com/shop
├── go.mod
├── cmd/
│   └── shop-api/
│       └── main.go    package main: точка входа
├── order/
│   ├── order.go       package order
│   └── price.go       package order (тот же пакет)
└── internal/
    └── db/
        └── db.go      package db
```

**Путь импорта** пакета = путь модуля + путь каталога: `example.com/shop/order`. **Имя пакета** это то, что после `package`, и по нему ты обращаешься к содержимому: `order.New()`. По конвенции имя совпадает с последним элементом пути.

Как называть пакеты:

- коротко, строчными буквами, одним словом: `order`, `http`, `strconv`. Не `orderService`, не `order_utils`;
- имя пакета часть имени всего, что в нём лежит: `order.New`, а не `order.NewOrder`; `http.Client`, а не `http.HTTPClient`;
- никаких `util`, `common`, `helpers`, `models`: такие пакеты притягивают всё подряд и становятся свалкой с импортами отовсюду.

### Видимость: заглавная буква

В Go нет `public`/`private`/`export`. Видимость определяется **первой буквой имени**:

```go
package order

type Order struct {   // экспортирован: виден из других пакетов
	ID    int         // экспортировано
	total int         // не экспортировано: только внутри пакета order
}

func New(id int) *Order { ... }   // экспортирована
func validate(o *Order) error { ... } // только внутри пакета
```

Правило одинаковое для типов, функций, переменных, констант, полей структур и методов. Граница видимости это **пакет**, а не файл и не тип: функция из `price.go` спокойно читает `o.total`, объявленное в `order.go`.

Неэкспортированные поля невидимы и для пакетов, работающих через рефлексию, например `encoding/json`:

```go
type user struct {
	name string
	Age  int
}

b, _ := json.Marshal(user{"Аня", 30})
fmt.Println(string(b))
```

<Predict :options="['объект с полями name и Age', 'объект только с полем Age', 'пустой объект', 'ошибка компиляции: user не экспортирован']" :correct="1">

Выведется `{"Age":30}`. Поле `name` с маленькой буквы недоступно пакету `encoding/json`, и он его молча пропускает. А вот сам тип `user` неэкспортированный, но это не мешает: мы передаём значение, а `json` смотрит на поля через reflect. Частая причина «пустого JSON» у новичков.

</Predict>

### internal: видно только своим

Иногда пакет нужен нескольким твоим пакетам, но наружу его отдавать нельзя: это деталь реализации, и ты не хочешь, чтобы чужой код на неё завязался. Для этого есть каталог `internal`. Правило компилятора: пакет в `a/b/internal/c` можно импортировать только из кода внутри `a/b/`.

```text
example.com/shop/internal/db       импортируют shop/order, shop/cmd/...
example.com/other/...              не может: ошибка сборки
```

```text
package x/other
	other/main.go:6:2: use of internal package x/shop/internal/price not allowed
```

Это не соглашение, а проверка `go build`. В сервисах почти весь код кладут в `internal/`: сервис не библиотека, его пакеты никто не должен импортировать.

### Импорты

```go
import (
	"fmt"                       // стандартная библиотека
	"net/http"

	"github.com/jackc/pgx/v5"   // внешний модуль
	"example.com/shop/order"     // свой пакет

	_ "github.com/lib/pq"        // только ради побочного эффекта (init)
	str "strings"                // псевдоним
)
```

- **Пустой импорт** `_` подключает пакет только ради его `init`: так регистрируются драйверы `database/sql` и декодеры картинок `image/png`.
- **Псевдоним** нужен при конфликте имён (`crand "crypto/rand"` рядом с `math/rand/v2`).
- **Циклические импорты запрещены**: `import cycle not allowed`. Если пакеты `order` и `customer` нужны друг другу, это сигнал к перепроектированию: вынести общее в третий пакет или развернуть зависимость через интерфейс на стороне потребителя (урок про интерфейсы).

## Инициализация и init

Перед `main` Go инициализирует все пакеты программы. Правила:

1. Каждый пакет инициализируется **один раз**, даже если его импортируют десять других.
2. Пакет инициализируется только после **всех пакетов, которые он импортирует**. Порядок между независимыми пакетами с Go 1.21 тоже определён: пакеты сортируются по пути импорта, и каждый раз инициализируется первый, у которого все зависимости готовы.
3. Внутри пакета сначала инициализируются **переменные уровня пакета** в порядке зависимостей между ними (не обязательно в порядке объявления), затем вызываются функции `init` в порядке их появления в файлах (файлы `go` передаёт компилятору отсортированными по имени).
4. Только потом `main.main`.

```go
var a = b + 1
var b = f()

func f() int {
	fmt.Println("f")
	return 1
}

func init() { fmt.Println("init1", a) }
func init() { fmt.Println("init2") }

func main() { fmt.Println("main") }
```

<Predict :options="['init1 0, init2, f, main', 'f, init1 2, init2, main', 'init1 2, init2, f, main', 'ошибка компиляции: два init']" :correct="1">

Переменная `a` зависит от `b`, поэтому сначала вычисляется `b = f()` (печатает `f`), затем `a = 2`. Потом функции `init` по порядку, и только затем `main`. Несколько `init` в одном пакете и даже в одном файле разрешены.

</Predict>

У `init` особый статус: нет аргументов и результатов, её нельзя вызвать вручную (`init()` в коде даст `undefined: init`) и нельзя взять на неё ссылку.

::: trap Логика в init
`init` выполняется при импорте пакета, до `main`, без возможности вернуть ошибку и без контроля вызывающего. Тяжёлый или падающий `init` ломает любые тесты пакета и любую программу, которая его импортирует.

```go
// Плохо: подключение к БД при импорте, паника без БД, тесты не запустить.
var db *sql.DB

func init() {
	var err error
	db, err = sql.Open("pgx", os.Getenv("DB_URL"))
	if err != nil {
		panic(err)
	}
}

// Хорошо: явная функция, ошибка наружу, зависимость передаётся параметром.
func Open(ctx context.Context, url string) (*sql.DB, error) {
	db, err := sql.Open("pgx", url)
	if err != nil {
		return nil, fmt.Errorf("open db: %w", err)
	}
	return db, db.PingContext(ctx)
}
```

Нормальные применения `init`: регистрация в реестре (драйверы, кодеки), предвычисление таблиц из констант. Глобальное изменяемое состояние, сеть, файлы, переменные окружения: не в `init`.
:::

## Модули: go.mod подробнее

```go
module example.com/shop

go 1.27.3

require (
	github.com/jackc/pgx/v5 v5.7.1
	golang.org/x/sync v0.10.0
)

require (
	github.com/jackc/puddle/v2 v2.2.2 // indirect
)

replace example.com/billing => ../billing

retract v1.3.0 // опубликован с багом в расчёте НДС
```

| Директива | Что делает |
|---|---|
| `module` | путь модуля, префикс импортов всех его пакетов |
| `go` | минимальная версия языка; включает новую семантику (например, переменную цикла на итерацию с 1.22) |
| `toolchain` | рекомендуемый тулчейн для сборки |
| `require` | минимальные версии зависимостей; `// indirect` значит «нужен не мне напрямую, а моим зависимостям» |
| `replace` | подменить модуль другой версией или локальным каталогом |
| `exclude` | запретить конкретную версию |
| `retract` | автор отзывает свои опубликованные версии (`go get` не выберет их сам) |
| `tool` | инструменты разработки (с Go 1.24) |
| `ignore` | каталоги, которые `go` игнорирует при поиске пакетов по `./...` (с Go 1.25) |

С Go 1.27 `go mod tidy` для модулей с `go 1.27` и выше держит не больше двух блоков `require`: прямые зависимости и косвенные, сам сливая лишние (если косвенных нет, блок один).

### Семантические версии

Версии модулей в Go обязаны быть в формате **semver**: `vMAJOR.MINOR.PATCH`, например `v1.4.2`, с необязательным пререлизом `v2.0.0-rc.1`.

- **PATCH**: исправления без изменения API.
- **MINOR**: новая функциональность, обратно совместимая.
- **MAJOR**: несовместимые изменения.
- **v0.x.y**: API нестабилен, может ломаться в любой версии.
- **Пререлиз** младше релиза: `v1.0.0-rc.1 < v1.0.0`.

Сравнивают части **как числа**: `v1.10.0` новее `v1.9.0`, хотя строкой меньше. Это ты реализуешь в домашке.

Если нужный коммит не помечен тегом, Go использует **псевдоверсию**: `v0.0.0-20260301120000-abcdef123456`, если тегов у модуля нет вовсе, или `v1.2.4-0.20260301120000-abcdef123456` для коммита после тега `v1.2.3`. Это базовая версия, время коммита и начало хеша. Её видно, когда делаешь `go get example.com/lib@main` или `@<хеш>`.

### Правило совместимости импорта и /v2

Главное отличие Go от npm: если у модуля сменилась **мажорная версия** (v2 и выше), меняется его **путь**:

```go
import "github.com/jackc/pgx/v5"   // модуль github.com/jackc/pgx/v5
```

```go
// go.mod модуля версии 2
module example.com/lib/v2
```

Правило звучит так: *если у старого и нового пакета один путь импорта, новый обязан быть обратно совместим со старым*. Значит, несовместимые версии должны жить по разным путям. Следствия:

- `example.com/lib` (v1) и `example.com/lib/v2` это **разные модули**, их можно использовать в одной программе одновременно: удобно для постепенной миграции.
- `go get -u` никогда не переведёт тебя с v1 на v2 сам: это смена импортов в коде, решение за тобой.
- Если видишь в `go.mod` версию с суффиксом `+incompatible` (`v4.1.0+incompatible`), это модуль, у которого есть тег v2+, но нет суффикса в пути (обычно старые проекты без `go.mod`).

::: hood Выбор версий и go.sum ещё раз
Напомню из урока про инструменты: версию каждого модуля выбирает **Minimal Version Selection**. Построение списка сборки в простейшей форме из статьи Расса Кокса: обойти граф требований от главного модуля, собрать все достижимые пары `модуль@версия`, затем для каждого модуля оставить **максимальную** из встреченных версий. Не самую свежую из существующих, а максимальную из **требуемых**.

```text
 shop ──► pgx v5.5.0 ──► puddle v2.2.1
   │
   └────► billing v1.2.0 ──► pgx v5.7.1
                    
 итог: pgx v5.7.1 (максимум из v5.5.0 и v5.7.1), puddle v2.2.1
```

Поэтому список сборки воспроизводим без lock-файла: он вычисляется из `go.mod`, а не из состояния реестра на момент установки. Новая версия появится в сборке, только если кто-то в графе её потребует или ты сам сделаешь `go get`. Реальный `go` с 1.17 ещё и **обрезает граф** (module graph pruning): у зависимостей с `go 1.17+` в `go.mod` записаны все нужные им модули, и глубже не нужно ходить. Ты реализуешь базовый алгоритм в домашке.

Команды для исследования графа:

```bash
go list -m all             # итоговый список сборки
go mod graph               # все рёбра «кто кого требует»
go mod why -m golang.org/x/text  # зачем нужен модуль
go list -m -u all          # какие обновления доступны
```

**go.sum подробнее.** На каждую версию модуля в нём бывает до двух строк:

```text
github.com/dustin/go-humanize v1.0.1 h1:GzkhY7T5VNhEkwH0PVJgjz+fX1rhBrR7pRT3mDkpeCY=
github.com/dustin/go-humanize v1.0.1/go.mod h1:Mu1zIs6XwVuF/gI1OepvI0qD18qycQx+mFykh5fBlto=
```

Первая строка это хеш всего содержимого модуля (`h1:` значит SHA-256 по списку файлов архива), вторая хеш только его `go.mod`. Строки `/go.mod` появляются и для версий, которые в итоговую сборку не попали: чтобы выполнить MVS, `go` читает `go.mod` встреченных версий и проверяет и их. Поэтому `go.sum` не lock-файл: это журнал проверенных хешей, в нём бывают «лишние» версии, а выбор версий делает `go.mod`. При первом скачивании хеш сверяется с публичной базой `sum.golang.org` (переменная `GOSUMDB`); для приватных модулей сверку отключают через `GOPRIVATE` или точечно `GONOSUMDB`. Команда `go mod verify` проверяет, что файлы в локальном кеше модулей не изменились с момента скачивания.
:::

## replace: локальная копия зависимости

Нашёл баг в библиотеке и хочешь проверить исправление, не публикуя его? `replace` подменяет модуль:

```bash
go mod edit -replace example.com/lib=../lib
```

```go
replace example.com/lib => ../lib
```

Подменить можно и на форк: `replace github.com/some/lib => github.com/me/lib v1.2.4-fix`.

Важное правило: **`replace` и `exclude` работают только в главном модуле**. Если библиотека, которую ты используешь, содержит `replace` в своём `go.mod`, на твою сборку это не влияет. Поэтому `replace` на локальный путь нельзя оставлять в библиотеке, которую будут импортировать другие: у них сборка пойдёт с оригиналом.

::: trap Забытый replace на локальный каталог
```go
// Плохо: закоммичено в репозиторий сервиса. На CI и у коллег каталога ../lib нет.
replace example.com/lib => ../lib
```

Сборка у всех, кроме тебя, упадёт с ошибкой про отсутствующий каталог. Для локальной разработки нескольких модулей сразу есть рабочие области: они живут в отдельном файле `go.work`, который обычно не коммитят.

```bash
# Хорошо: подмена только у тебя локально.
go work init ./shop ./lib
```
:::

## Рабочие области: go.work

С Go 1.18 можно объединить несколько модулей в **рабочую область**. Типичный случай: сервис и библиотека в соседних каталогах, правишь обе одновременно.

```bash
mkdir ws && cd ws
# в ws лежат каталоги app (модуль example.com/app) и lib (модуль example.com/lib)
go work init ./app ./lib
```

Получается файл `go.work`:

```go
go 1.27.3

use (
	./app
	./lib
)
```

Теперь `go build` и `go run` внутри любого из модулей видят оба как главные: импорт `example.com/lib` в `app` берётся из `./lib`, даже если в `go.mod` приложения его нет и он нигде не опубликован. Команды: `go work use ./other` добавить модуль, `go work sync` перенести версии зависимостей из рабочей области обратно в `go.mod` модулей. Отключить рабочую область для одной команды: `GOWORK=off go build`.

Коммитить `go.work` в общем случае не стоит, это прямо сказано в справочнике по модулям: чужой `go.work` может перекрыть рабочую область разработчика, а CI начнёт тестировать не те версии, что увидят пользователи модуля. Исключение: монорепозиторий, где модули разрабатываются только вместе.

## Приватные модули и прокси

По умолчанию `go` скачивает модули через `proxy.golang.org` и сверяет их с `sum.golang.org`. Для модулей компании (`gitlab.company.ru/...`) это не сработает: прокси их не видит. Переменная `GOPRIVATE` перечисляет шаблоны путей, для которых прокси и база сумм не используются, а код берётся напрямую из VCS:

```bash
go env -w GOPRIVATE='gitlab.company.ru/*'
```

На собесе это спрашивают как «как подключить приватную зависимость». Дальше обычно нужно настроить доступ git к приватному репозиторию (SSH-ключ или токен в `.netrc`).

## Что выведет программа?

```go
// файл counter/counter.go
package counter

type counter struct{ N int }

func New() *counter { return &counter{} }
```

```go
// файл main.go
package main

import (
	"fmt"

	"example.com/app/counter"
)

func main() {
	c := counter.New()
	c.N = 5
	fmt.Println(c.N)
}
```

<Predict :options="['5', 'ошибка компиляции: counter не экспортирован', 'ошибка компиляции: нельзя вызвать New', '0']" :correct="0">

Неэкспортированное **имя** `counter` нельзя написать в другом пакете (`var c counter.counter` не скомпилируется), но значение этого типа получить можно, а его экспортированные поля и методы доступны. Через `:=` имя типа писать не нужно. Так делать не принято: линтеры ругаются на экспортированную функцию, возвращающую неэкспортированный тип, потому что вызывающий не может объявить переменную такого типа или написать функцию, которая его принимает.

</Predict>

```text
example.com/shop/
├── go.mod                 module example.com/shop
```

<details><summary>Чем пакет отличается от модуля?</summary>

Пакет это каталог с `.go`-файлами с одним именем `package`, единица компиляции, видимости и импорта. Модуль это дерево пакетов с общим `go.mod`, единица версионирования и распространения. Путь импорта пакета = путь модуля + путь каталога внутри модуля.

</details>
<details><summary>Как в Go устроена видимость?</summary>

По первой букве имени: заглавная значит экспортировано из пакета, строчная видно только внутри пакета. Касается типов, функций, переменных, констант, полей и методов. Граница это пакет, а не файл или тип. Кроме того, каталог `internal` ограничивает импорт пакета кодом внутри родителя `internal`.

</details>
<details><summary>В каком порядке выполняется инициализация программы?</summary>

Сначала инициализируются импортированные пакеты (каждый один раз, зависимости раньше зависящих; с Go 1.21 порядок независимых пакетов определён сортировкой по пути импорта). Внутри пакета переменные уровня пакета инициализируются в порядке зависимостей между ними, затем вызываются функции `init` в порядке появления в файлах. После всех пакетов вызывается `main.main`.

</details>
<details><summary>Почему init считают опасной и когда она уместна?</summary>

Она выполняется неявно при импорте, не может вернуть ошибку, усложняет тесты (выполняется в каждом тестовом бинарнике) и прячет зависимости в глобальном состоянии. Уместна для регистрации (драйверы `database/sql`, кодеки `image`) и вычисления таблиц из констант. Подключения, чтение конфигов и окружения лучше делать явно из `main`.

</details>
<details><summary>Что такое правило совместимости импорта и зачем /v2 в пути?</summary>

Если у двух версий пакета один путь импорта, новая обязана быть обратно совместима. Поэтому несовместимая мажорная версия v2+ получает новый путь модуля с суффиксом `/v2`. Это разные модули: их можно использовать одновременно, и `go get -u` не переведёт на новую мажорную версию сам. Версии v0 и v1 суффикса не имеют.

</details>
<details><summary>Как подключить локальную версию зависимости?</summary>

Два способа. `replace example.com/lib => ../lib` в `go.mod` главного модуля: работает только в главном модуле, в зависимостях игнорируется, и его легко забыть закоммитить. Или рабочая область: `go work init ./app ./lib`, файл `go.work`, который обычно не коммитят. Для временной подмены удобнее рабочая область.

</details>
<details><summary>Что такое псевдоверсия?</summary>

Версия для коммита без тега: `v0.0.0-20260301120000-abcdef123456` (базовая версия, время коммита в UTC, 12 символов хеша). Появляется при `go get module@branch` или `@hash`. Формально это пререлиз, поэтому, например, `v1.2.4-0.20260301120000-abcdef123456` (коммит после тега `v1.2.3`) старше `v1.2.3` и младше будущего `v1.2.4`.

</details>
<details><summary>Как Go выбирает версию зависимости, если её требуют разные модули?</summary>

Minimal Version Selection: обходит граф требований от главного модуля и для каждого модуля берёт максимальную из требуемых версий, а не последнюю опубликованную. Результат детерминирован и не зависит от времени сборки, поэтому lock-файл не нужен: `go.mod` им и служит, а `go.sum` хранит хеши для проверки целостности.

</details>
<details><summary>Как работать с приватными модулями?</summary>

Указать шаблоны путей в `GOPRIVATE` (например, `gitlab.company.ru/*`): для них `go` не ходит в публичный прокси и базу контрольных сумм, а клонирует напрямую. Плюс настроить git-доступ (SSH или токен). В компаниях часто стоит свой прокси (Athens, Nexus, Artifactory), тогда его прописывают в `GOPROXY`.

</details>
:::
