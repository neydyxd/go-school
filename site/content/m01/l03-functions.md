# Функции, замыкания, defer, panic

Функции в Go выглядят просто, но на них держится весь стиль языка. Ошибки возвращаются вторым результатом, а не бросаются исключениями. Ресурсы закрываются через `defer`, а не через `try/finally`. Middleware в HTTP-сервере это функция, которая принимает обработчик и возвращает новый обработчик. Если ты писал на JavaScript, замыкания и функции как значения покажутся знакомыми, но `defer`, именованные результаты и `panic/recover` придётся разобрать с нуля.

На собесе по этому уроку любят задачи «что выведет программа» с `defer`: в каком порядке выполнится, какое значение аргумента попадёт, изменит ли `defer` возвращаемое значение. Это проверяет, понимаешь ли ты механику, а не просто помнишь синтаксис. Разберём всё по шагам.

## Объявление и несколько результатов

```go
func add(a, b int) int { // одинаковые типы подряд можно сгруппировать
	return a + b
}

func divmod(a, b int) (int, int) { // несколько результатов
	return a / b, a % b
}

q, r := divmod(7, 2) // 3 1
_, r = divmod(9, 4)  // ненужный результат отбрасываем через _
```

Несколько результатов это основа обработки ошибок в Go:

```go
n, err := strconv.Atoi(s)
if err != nil {
	return 0, fmt.Errorf("разбор %q: %w", s, err)
}
```

Чего в Go нет, и это частый вопрос от тех, кто пришёл из других языков:

- **Перегрузки**: две функции с одним именем и разными параметрами не объявить. Пишут разные имена: `ParseInt`, `ParseFloat`.
- **Параметров по умолчанию и именованных аргументов**: вместо них передают структуру с опциями или используют паттерн functional options (разберём позже).
- **Исключений**: ошибки это обычные значения. Есть `panic`, но это не замена исключениям, о нём ниже.

## Именованные результаты

Результатам можно дать имена. Тогда они объявлены как обычные переменные с нулевыми значениями, а `return` без аргументов («голый return») вернёт их текущие значения:

```go
func split(sum int) (x, y int) {
	x = sum * 4 / 9
	y = sum - x
	return // вернёт x и y
}
```

Когда это полезно:

- **Документация**: `func Size() (width, height int)` понятнее, чем `(int, int)`.
- **Изменение результата в `defer`**: единственный способ поменять возвращаемое значение после `return`. Ниже увидишь, как это используется с `recover`.

Голый `return` в длинной функции ухудшает читаемость: непонятно, что возвращается. Используй его только в коротких функциях. И помни, что именованный результат может затенить переменная из `:=` во вложенном блоке.

## Variadic-функции

Последний параметр может принимать любое количество аргументов. Внутри функции это обычный слайс:

```go
func sum(nums ...int) int {
	total := 0
	for _, n := range nums {
		total += n
	}
	return total
}

sum()        // 0: nums == nil
sum(1, 2, 3) // 6
s := []int{4, 5}
sum(s...)    // 9: распаковка слайса
```

Так устроены `fmt.Println(a ...any)` и `append(s []T, elems ...T)`.

Тонкость, которую спрашивают: при вызове `f(s...)` **новый слайс не создаётся**, функция получает тот же слайс, что у вызывающего, и изменения элементов видны снаружи. Проверь себя на задачке `mutate(s...)` в разделе «Что выведет программа?». Практический вывод: если функция сохраняет переданный слайс у себя (например, в замыкании), ей стоит сделать копию.

## Функции как значения

Функции в Go это значения первого класса: их можно класть в переменные, передавать в другие функции и возвращать.

```go
var op func(int, int) int // тип функции; нулевое значение nil
op = add
fmt.Println(op(2, 3)) // 5

func apply(nums []int, f func(int) int) []int {
	res := make([]int, 0, len(nums))
	for _, n := range nums {
		res = append(res, f(n))
	}
	return res
}

apply([]int{1, 2, 3}, func(x int) int { return x * x }) // [1 4 9]
```

Для функциональных типов часто объявляют имя. Ты его встретишь в первом же HTTP-сервере:

```go
type HandlerFunc func(w http.ResponseWriter, r *http.Request)
```

Две особенности:

- Вызов `nil`-функции паникует: `invalid memory address or nil pointer dereference`.
- Функции **сравниваются только с `nil`**. `f == g` не скомпилируется: `func can only be compared to nil`. Поэтому функцию нельзя сделать ключом мапы.

## Замыкания

Анонимная функция видит переменные окружающей функции и может их менять. Такая функция вместе с захваченными переменными называется **замыканием** (closure):

```go
func counter() func() int {
	c := 0
	return func() int {
		c++
		return c
	}
}

next := counter()
next()
next()
fmt.Println(next()) // 3
other := counter()
fmt.Println(other()) // 1: у каждого вызова counter своя c
```

Главное правило: замыкание захватывает **переменную, а не её значение** в момент создания. Если переменная потом изменится, замыкание увидит новое значение:

```go
x := 1
show := func() { fmt.Println(x) }
x = 2
show() // 2
```

Где это встречается в бэкенде: middleware (функция-обёртка над обработчиком), генераторы ID, кеширование результатов, отложенные действия в `defer`. В модуле про конкурентность ты увидишь, как замыкание, захватившее переменную из нескольких горутин, становится гонкой данных.

::: hood Как устроено замыкание
Значение функционального типа это указатель на небольшую структуру (`funcval`): первым полем адрес машинного кода функции, дальше захваченные переменные.

```
next ──► ┌──────────────────────┐
         │ fn: код counter.func1│
         │ c:  указатель ───────┼──► [ c = 2 ]   (в куче)
         └──────────────────────┘
```

Если захваченная переменная меняется после захвата (как `c` в `counter`), компилятор хранит в замыкании **указатель** на неё и переносит саму переменную в кучу, ведь она должна жить после возврата из `counter`. Если переменная после захвата не меняется и маленькая, компилятор может молча скопировать значение: снаружи разницы не видно.

Убедиться можно флагом `-gcflags=-m`: для `counter` компилятор сообщает `moved to heap: c` и `func literal escapes to heap`. Подробно про стек, кучу и escape analysis будет в уроке про указатели и в модуле про рантайм.
:::

## defer

`defer` откладывает вызов функции до момента, когда **окружающая функция завершается**: через `return`, по достижении конца тела или из-за паники.

```go
func readConfig(path string) ([]byte, error) {
	f, err := os.Open(path)
	if err != nil {
		return nil, err
	}
	defer f.Close() // закроется при любом выходе из функции

	return io.ReadAll(f)
}
```

Идиома: **открыл ресурс, проверил ошибку, сразу же написал `defer` для освобождения**. Так ресурс не утечёт, сколько бы `return` ни было ниже. Так же отпускают мьютексы (`mu.Lock(); defer mu.Unlock()`) и закрывают тела HTTP-ответов.

Три правила `defer`, которые надо знать наизусть.

### 1. Аргументы вычисляются сразу

Функция откладывается, а её аргументы вычисляются **в момент выполнения `defer`**:

```go
x := 1
defer fmt.Println("x =", x)
x = 2
```

<Predict :options="['x = 1', 'x = 2', 'ничего', 'ошибка компиляции']" :correct="0">

На строке с `defer` вычисляются все аргументы, `x` в этот момент равен 1. Вызов откладывается уже с готовым значением. Если нужно увидеть итоговое значение, оберни в замыкание: `defer func() { fmt.Println("x =", x) }()`: тогда `x` прочитается при выполнении и будет 2.

</Predict>

Это касается и получателя метода, и цепочек вызовов: в `defer Trace("f")()` функция `Trace` вызывается **сразу**, а откладывается только вызов того, что она вернула. На этом построен приём трассировки входа и выхода из функции (будет в домашке).

### 2. Порядок обратный (LIFO)

Отложенные вызовы складываются в стек и выполняются в обратном порядке: последний отложенный выполнится первым. Это логично: ресурс, открытый последним, часто зависит от открытых ранее и должен закрыться первым.

```go
defer fmt.Print("1")
defer fmt.Print("2")
defer fmt.Print("3")
// 321
```

### 3. defer может менять именованные результаты

Отложенная функция выполняется **после** того, как `return` записал значение в результат, но **до** того, как управление вернулось вызывающему. Если результат именованный, `defer` может его поменять:

```go
func double() (n int) {
	defer func() { n *= 2 }()
	return 3
}

func noNamed() int {
	n := 3
	defer func() { n *= 2 }()
	return n
}

fmt.Println(double(), noNamed())
```

<Predict :options="['6 6', '3 3', '6 3', '3 6']" :correct="2">

В `double` инструкция `return 3` сначала записывает 3 в именованный результат `n`, потом выполняется `defer` и удваивает его: 6. В `noNamed` результат безымянный: `return n` копирует значение 3 в слот результата, а `defer` меняет локальную `n`, которая уже ни на что не влияет: 3.

</Predict>

`return x` с именованным результатом можно мысленно разложить на три шага: `результат = x`, выполнить все `defer`, вернуть `результат`.

::: trap defer в цикле
```go
// плохо: все файлы закроются только при выходе из функции
for _, path := range paths {
	f, err := os.Open(path)
	if err != nil {
		return err
	}
	defer f.Close() // тысяча файлов будет открыта одновременно
	process(f)
}

// хорошо: тело итерации в отдельной функции, defer срабатывает на каждой итерации
for _, path := range paths {
	if err := processFile(path); err != nil {
		return err
	}
}

func processFile(path string) error {
	f, err := os.Open(path)
	if err != nil {
		return err
	}
	defer f.Close()
	return process(f)
}
```

`defer` привязан к функции, а не к блоку или итерации. В длинном цикле это исчерпание файловых дескрипторов (`too many open files`) или соединений с базой. Второй минус: `defer` в цикле не может быть «встроенным» (см. под капотом) и работает медленнее.
:::

::: hood Как устроен defer и сколько он стоит
Раньше `defer` стоил десятки наносекунд: рантайм заводил запись о каждом отложенном вызове и связывал их в список у горутины. С Go 1.14 большинство `defer` **встроенные** (open-coded): компилятор вставляет вызовы прямо в эпилог функции перед каждым `return` и заводит битовую маску, какие из `defer` уже «взведены». Стоимость падает почти до обычного вызова.

Условия, при которых компилятор так делает (проверено по исходникам компилятора Go 1.27, `cmd/compile/internal/walk` и `ssagen`):

- в функции не больше 8 `defer` (маска занимает один байт);
- ни один `defer` не стоит в цикле;
- произведение числа `return` на число `defer` не больше 15.

Иначе используется старый механизм с записями. При панике рантайм в обоих случаях находит отложенные вызовы и выполняет их, раскручивая стек. Вывод для практики: обычный `defer f.Close()` бесплатен, не бойся его и не заменяй ручными вызовами «ради скорости».
:::

## panic и recover

`panic` останавливает обычное выполнение текущей функции и начинает **раскручивать стек**: выполняет отложенные вызовы текущей функции, потом вызвавшей её, и так далее вверх. Если паника дошла до верха стека горутины, программа падает с сообщением и трассировкой стека, код выхода 2.

Паники бывают двух видов:

- **Ошибки рантайма**: выход за границы слайса, разыменование nil-указателя, запись в nil-мапу, деление на ноль. Их значение реализует интерфейс `runtime.Error`.
- **Явный вызов** `panic(v)` с любым значением.

`recover()` останавливает панику и возвращает переданное в неё значение. Работает он только при двух условиях: вызван **внутри отложенной функции** и **непосредственно в ней**, а не во вложенном вызове. В остальных случаях `recover` возвращает `nil` и ничего не делает.

```go
func safe() (err error) {
	defer func() {
		if r := recover(); r != nil {
			err = fmt.Errorf("поймали: %v", r)
		}
	}()
	var m map[string]int
	m["a"] = 1 // паника: запись в nil-мапу
	return nil
}

fmt.Println(safe()) // поймали: assignment to entry in nil map
```

Обрати внимание на именованный результат `err`: это единственный способ вернуть ошибку из функции, которая паниковала. После `recover` функция `safe` завершается нормально и возвращает то, что лежит в `err`. Выполнение **не продолжается** со строки после паники.

### Когда использовать panic

Коротко: почти никогда в обычном коде. Ошибки, которые можно ожидать (нет файла, плохой ввод, упала сеть), возвращаются как `error`. `panic` оставляют для:

- **Нарушения инвариантов программы**, то есть багов: «сюда мы попасть не могли». Например, `default` в `switch` по закрытому набору значений.
- **Ошибок инициализации**, без которых программа бессмысленна: `regexp.MustCompile` паникует на неверном выражении, потому что выражение зашито в код.
- **Внутреннего механизма пакета** с обязательным `recover` на границе: так `encoding/json` выходит из глубокой рекурсии, а наружу отдаёт обычную ошибку.

`recover` на практике стоит в одном месте: на границе обработки запроса. HTTP-сервер из `net/http` сам ловит панику в обработчике, чтобы один кривой запрос не уронил весь сервис; в Gin это middleware `Recovery`.

::: trap recover спасает только свою горутину
```go
// плохо: recover в main не поймает панику из другой горутины
func main() {
	defer func() { recover() }()
	go func() {
		panic("бум") // упадёт вся программа
	}()
	time.Sleep(time.Second)
}

// хорошо: каждая горутина, которая может паниковать, ловит сама
go func() {
	defer func() {
		if r := recover(); r != nil {
			log.Printf("воркер упал: %v", r)
		}
	}()
	work()
}()
```

Паника раскручивает стек **только той горутины, где произошла**. Если в этой горутине её никто не поймал, падает весь процесс, вместе со всеми остальными горутинами и обслуживаемыми запросами. Поэтому в фоновых воркерах `recover` ставят внутри самой горутины.
:::

::: trap recover не во вложенной функции
```go
func helper() { recover() } // бесполезно

// плохо: recover вызван не непосредственно отложенной функцией
defer func() { helper() }()

// хорошо
defer func() {
	if r := recover(); r != nil { /* ... */ }
}()

// тоже работает: отложена сама функция, recover вызван прямо в ней
defer helper()
```

Рантайм проверяет, что `recover` вызван именно отложенной функцией, которую он сейчас выполняет при раскрутке. Вызов из функции, вызванной отложенной, вернёт `nil`, и паника пойдёт дальше.
:::

### os.Exit и panic(nil)

Две детали для собеса:

- `os.Exit(code)` завершает процесс **немедленно, без выполнения `defer`**. То же делает `log.Fatal` (он вызывает `os.Exit(1)`). Поэтому `log.Fatal` в середине программы может оставить незакрытые файлы и несброшенные буферы.
- С Go 1.21 `panic(nil)` превращается в панику со значением типа `*runtime.PanicNilError`. Раньше `recover()` возвращал `nil`, и нельзя было отличить «паники не было» от «паника с nil». Старое поведение возвращается через `GODEBUG=panicnil=1` или автоматически, если главный модуль объявляет в `go.mod` версию `go 1.20` и ниже. Это тот же принцип, что с переменной цикла в прошлом уроке: семантику выбирает версия в `go.mod`.

## Что выведет программа?

```go
func mutate(nums ...int) { nums[0] = 100 }

s := []int{1, 2, 3}
mutate(s...)
fmt.Println(s)
```

<Predict :options="['[1 2 3]', '[100 2 3]', 'ошибка компиляции', 'паника']" :correct="1">

`s...` передаёт сам слайс без копирования: `nums` и `s` смотрят на один и тот же массив, поэтому запись `nums[0] = 100` видна снаружи: `[100 2 3]`. А при вызове `mutate(1, 2, 3)` компилятор создал бы новый слайс, и вызывающий ничего бы не заметил. Если функция сохраняет переданный слайс у себя (например, в замыкании), ей стоит сделать копию.

</Predict>

```go
func helper() { recover() }

func notDirect() (res string) {
	defer func() {
		if r := recover(); r != nil {
			res = "внешний поймал"
		}
	}()
	defer func() { helper() }()
	panic("бум")
}

func main() { fmt.Println(notDirect()) }
```

<Predict :options="['внешний поймал', 'пустая строка', 'паника: бум, программа падает', 'ошибка компиляции']" :correct="0">

Отложенные вызовы идут в обратном порядке. Первым выполняется `func() { helper() }`: `recover` внутри `helper` вызван не непосредственно отложенной функцией, поэтому возвращает `nil`, паника продолжается. Вторым выполняется первая отложенная функция, где `recover` стоит прямо в ней: паника поймана, `res` получает значение. Функция возвращает «внешний поймал».

</Predict>

```go
func main() {
	defer fmt.Println("отложенный")
	os.Exit(3)
}
```

<Predict :options="['отложенный, код выхода 3', 'ничего не печатает, код выхода 3', 'отложенный, код выхода 0', 'паника']" :correct="1">

`os.Exit` завершает процесс сразу, отложенные вызовы не выполняются. Программа ничего не напечатает и выйдет с кодом 3. Если запускать через `go run`, он допишет `exit status 3` от себя.

</Predict>

```go
func f() (n int) {
	defer func() { n++ }()
	n = 10
	return n * 2
}

func main() { fmt.Println(f()) }
```

<Predict :options="['10', '11', '20', '21']" :correct="3">

`return n * 2` вычисляет 20 и записывает в именованный результат `n`. Затем выполняется `defer` и увеличивает `n` до 21. Именно это значение получает вызывающий.

<details><summary>В каком порядке выполняются defer и когда вычисляются их аргументы?</summary>

В обратном порядке объявления (LIFO), при любом выходе из функции: `return`, конец тела, паника. Аргументы отложенного вызова и сам функциональный объект вычисляются в момент выполнения строки с `defer`, а не при вызове. Поэтому `x := 1; defer fmt.Println(x); x = 2` напечатает 1, а `defer func() { fmt.Println(x) }()` напечатает 2: замыкание читает переменную при выполнении.

</details>
<details><summary>Может ли defer изменить возвращаемое значение функции?</summary>

Да, если результат именованный. `return v` сначала записывает `v` в именованный результат, потом выполняются отложенные функции, и только потом управление возвращается вызывающему. Отложенное замыкание видит именованный результат как переменную и может его изменить. С безымянным результатом изменить нельзя: `return n` уже скопировал значение. Этим пользуются, чтобы вернуть ошибку после `recover` или дописать контекст к ошибке.

</details>
<details><summary>Как работают panic и recover? Где recover сработает, а где нет?</summary>

`panic` останавливает выполнение и раскручивает стек текущей горутины, выполняя отложенные вызовы. `recover` возвращает значение паники и останавливает её, только если вызван непосредственно в отложенной функции во время паники. Вызов вне `defer`, во вложенной функции или без паники возвращает `nil`. После успешного `recover` функция, в которой стоял этот `defer`, завершается нормально с текущими значениями результатов. Паника в другой горутине так не ловится и роняет весь процесс.

</details>
<details><summary>Когда в Go уместен panic, а когда нужно возвращать error?</summary>

`error` для всех ожидаемых ситуаций: неверный ввод, недоступный файл, сбой сети, ненайденная запись. `panic` для багов и нарушенных инвариантов, для фатальных ошибок инициализации (`regexp.MustCompile`, `template.Must`) и как внутренний механизм пакета, который сам же ловит его на своей границе. Публичный API библиотеки не должен паниковать на плохом вводе от пользователя.

</details>
<details><summary>Что такое замыкание и что оно захватывает?</summary>

Функция вместе с переменными из окружающей области, которые она использует. Захватывается переменная, а не её значение: замыкание видит последующие изменения и может менять переменную само. Если замыкание переживает функцию, где создано, захваченные переменные переезжают в кучу. Классическая ловушка: замыкания в цикле до Go 1.22 разделяли одну переменную цикла. Ещё одна: замыкание, захватившее переменную, которую меняют несколько горутин, это гонка данных.

</details>
<details><summary>Как передать слайс в variadic-функцию и что при этом происходит?</summary>

Через распаковку `f(s...)`. Новый слайс не создаётся: параметр функции ссылается на тот же массив, что и `s`, поэтому изменения элементов видны вызывающему. При вызове со списком значений `f(1, 2, 3)` компилятор создаёт новый слайс. Внутри функции без аргументов параметр равен `nil`.

</details>
<details><summary>Выполнятся ли defer при os.Exit, log.Fatal, панике?</summary>

При панике выполнятся, это главный механизм очистки и основа `recover`. При `os.Exit` нет: процесс завершается немедленно. `log.Fatal` вызывает `os.Exit(1)`, поэтому тоже без `defer`. Отсюда совет: `log.Fatal` и `os.Exit` только в `main`, а остальной код возвращает ошибки.

</details>
<details><summary>Можно ли сравнить две функции? Использовать функцию как ключ мапы?</summary>

Нельзя: функции сравниваются только с `nil`, `f == g` это ошибка компиляции. Поэтому функция не может быть ключом мапы. Если нужно идентифицировать обработчики, их кладут в мапу по имени-строке.

</details>
<details><summary>Сколько стоит defer?</summary>

С Go 1.14 большинство `defer` встроенные (open-coded): компилятор вставляет вызовы в эпилог функции, стоимость близка к обычному вызову. Условия: не больше 8 `defer` в функции, ни одного в цикле, произведение числа `return` на число `defer` не больше 15. Иначе используется более медленный механизм с записями в рантайме. Практический вывод: `defer` для освобождения ресурсов писать всегда, но не в горячих циклах.

</details>
:::
