# Мапы

Мапа (`map[K]V`) это встроенная хеш-таблица: по ключу за O(1) в среднем находит значение. В бэкенде она повсюду: кеш пользователей по ID, счётчики запросов по эндпоинтам, индекс «email -> пользователь», дедупликация событий, заголовки HTTP (`http.Header` это `map[string][]string`). Во фронтенде её аналоги `Map` и обычный объект `{}`.

Мапы обожают на собеседованиях по двум причинам. Первая: у них много поведения, которое нужно просто знать (nil-мапа, случайный порядок, нельзя взять адрес значения, падение при конкурентной записи). Вторая: вопрос «как мапа устроена внутри» отлично проверяет глубину. И здесь важна актуальность: в Go 1.24 реализацию полностью заменили на **Swiss Tables**, а большинство статей и ответов на собесах до сих пор описывают старую схему с бакетами. Хороший ответ знает обе и говорит, какая где.

В уроке: базовые операции, требования к ключам, почему мапа ведёт себя как ссылка, случайный порядок обхода, множества на `map[T]struct{}`, конкурентный доступ, пакет `maps` и подробный разбор устройства до и после Go 1.24.

## Базовые операции

```go
ages := map[string]int{ // литерал
	"Аня":  30,
	"Петя": 25,
}
scores := make(map[string]int)    // пустая мапа
users := make(map[int64]User, 1000) // подсказка: место примерно под 1000 элементов

ages["Вася"] = 41        // вставка или перезапись
fmt.Println(ages["Аня"]) // 30
delete(ages, "Петя")     // удаление; удалять несуществующий ключ можно
fmt.Println(len(ages))   // 2
```

Чтение отсутствующего ключа **не ошибка**: возвращается нулевое значение типа значения. Чтобы отличить «ключа нет» от «значение нулевое», используй форму с двумя результатами, её называют comma ok:

```go
v, ok := scores["Гоша"]
if !ok {
	fmt.Println("нет такого ключа")
}
```

Нулевое значение при чтении делает счётчики и группировки короткими:

```go
counts := map[string]int{}
for _, w := range words {
	counts[w]++ // для нового слова counts[w] это 0, получится 1
}

byCity := map[string][]User{}
for _, u := range users {
	byCity[u.City] = append(byCity[u.City], u) // append к nil-слайсу работает
}
```

```go
m := map[string]int{}
m["a"]++
v, ok := m["b"]
fmt.Println(m["a"], v, ok)
```

`m["a"]++` читает нулевое значение 0 для нового ключа, прибавляет 1 и записывает. Чтение отсутствующего `"b"` возвращает 0 и `ok == false`. Сам ключ `"b"` при чтении **не** создаётся.

Перебор и очистка:

```go
for k, v := range ages { // порядок случайный, об этом ниже
	fmt.Println(k, v)
}
clear(ages) // Go 1.21: удалить всё, мапа остаётся рабочей
```

`fmt.Println(m)` печатает мапу с ключами, отсортированными по возрастанию (так `fmt` делает с Go 1.12). Это свойство печати, а не мапы: удобно в отладке, но не доказывает, что мапа «упорядочена».

## nil-мапа

Нулевое значение типа мапы это `nil`. Читать из nil-мапы можно, писать нельзя:

```go
var m map[string]int
fmt.Println(m["x"], len(m), m == nil) // 0 0 true
for range m {}                        // ноль итераций
delete(m, "x")                        // ничего не делает

m["a"] = 1 // panic: assignment to entry in nil map
```

::: trap Мапа в структуре не создаётся сама
```go
type Cache struct {
	items map[string]string
}

// Плохо: items == nil, первая запись паникует
var c Cache
c.items["k"] = "v" // panic: assignment to entry in nil map

// Хорошо: конструктор
func NewCache() *Cache {
	return &Cache{items: make(map[string]string)}
}

// Или ленивая инициализация в методе
func (c *Cache) Set(k, v string) {
	if c.items == nil {
		c.items = make(map[string]string)
	}
	c.items[k] = v
}
```

Слайсы так себя не ведут: `append` к nil-слайсу работает. Мапу перед записью надо создать через `make` или литерал.
:::

## Какие типы годятся в ключи

Ключ должен быть **сравнимым** (comparable): для него определён `==`. Подходят числа, строки, `bool`, указатели, каналы, массивы и структуры из сравнимых полей, интерфейсы. Не подходят слайсы, мапы и функции:

```go
_ = map[[]int]int{} // ошибка компиляции: invalid map key type []int

type Point struct{ X, Y int }
visited := map[Point]bool{{1, 2}: true} // структура как составной ключ
fmt.Println(visited[Point{1, 2}])        // true
```

Структура как ключ это идиоматичный способ сделать составной ключ: `map[Point]...`, `map[struct{ UserID, ChatID int64 }]...`. Склеивать строку `fmt.Sprintf("%d:%d", a, b)` для этого не нужно.

::: trap Ключ-интерфейс паникует во время выполнения
Тип `any` формально сравним, поэтому `map[any]int` компилируется. Но если положить в ключ слайс, проверка случится только в рантайме:

```go
m := map[any]int{}
m[[]int{1}] = 1 // panic: runtime error: hash of unhashable type []int
```

Ещё одна экзотика: `NaN != NaN`, поэтому ключ `math.NaN()` можно вставить много раз и ни разу не найти. Удалить такие ключи через `delete` невозможно, только `clear(m)`. Проверено на Go 1.27.3: две записи по ключу NaN дают `len(m) == 2`, а чтение возвращает 0.
:::

## Мапа ведёт себя как ссылка

Переменная типа мапы это, по сути, **указатель** на структуру в рантайме: `unsafe.Sizeof(m)` равен 8 на 64-битной машине при любом размере мапы. Поэтому:

- передача мапы в функцию копирует указатель, функция меняет **ту же** мапу;
- присваивание `m2 := m` не создаёт копию, обе переменные указывают на одну таблицу.

```go
func addDefaults(cfg map[string]string) {
	cfg["timeout"] = "30s" // видно снаружи
}

a := map[string]int{"x": 1}
b := a
b["x"] = 100
fmt.Println(a["x"]) // 100

c := maps.Clone(a) // настоящая копия (поверхностная)
c["x"] = 1
fmt.Println(a["x"]) // 100
```

`maps.Clone` копирует пары ключ-значение, но не то, на что значения указывают: если значения это слайсы или указатели, клон будет делить с оригиналом их данные.

## Значения мапы неадресуемы

Взять адрес элемента мапы нельзя, и поменять поле структуры прямо внутри мапы тоже:

```go
type Stats struct{ Hits int }
m := map[string]Stats{"home": {}}

m["home"].Hits++   // ошибка компиляции: cannot assign to struct field m["home"].Hits in map
p := &m["home"]    // ошибка компиляции: cannot take address of m["home"]
```

Причина в устройстве: при росте таблицы элементы **переезжают** в новую память. Указатель на элемент стал бы висячим. Поэтому язык просто не даёт его получить.

Два рабочих способа:

```go
// 1. Достать копию, изменить, положить обратно
s := m["home"]
s.Hits++
m["home"] = s

// 2. Хранить указатели: тогда меняется объект, на который указывает значение
mp := map[string]*Stats{"home": {}}
mp["home"].Hits++
```

## Порядок обхода случаен

Спецификация говорит, что порядок обхода мапы **не определён**. Реализация идёт дальше и **специально** его перемешивает при каждом `range`, чтобы никто не начал на него опираться.

```go
m := map[int]int{}
for i := range 100 {
	m[i] = i
}
for k := range m {
	fmt.Println(k) // первый ключ разный от запуска к запуску
	break
}
```

Проверено на Go 1.27.3: 1000 обходов мапы из 100 ключей с `break` после первого ключа дали 99-100 разных «первых» ключей.

Если нужен стабильный порядок (вывод в API, отчёт, тест), отсортируй ключи явно:

```go
keys := slices.Sorted(maps.Keys(m)) // Go 1.23: maps.Keys возвращает итератор
for _, k := range keys {
	fmt.Println(k, m[k])
}
```

::: trap Тест, который иногда падает
```go
// Плохо: порядок элементов в result зависит от порядка обхода мапы
func Names(byID map[int]string) []string {
	var out []string
	for _, name := range byID {
		out = append(out, name)
	}
	return out
}
// тест сравнивает с []string{"Аня", "Петя"} и падает примерно в половине запусков

// Хорошо: явная сортировка, результат детерминирован
func Names(byID map[int]string) []string {
	out := slices.Collect(maps.Values(byID))
	slices.Sort(out)
	return out
}
```

Тот же баг бывает в JSON-ответах, собранных обходом мапы в слайс, и в логах. Если в выходных данных есть порядок, его должна задавать сортировка, а не мапа.
:::

### Изменение мапы во время обхода

Удалять элементы во время `range` безопасно, удалённые ещё не пройденные элементы не появятся. Добавленные во время обхода элементы **могут** появиться в этом обходе, а могут и нет. Изменять во время обхода значения существующих ключей тоже можно.

```go
for k, v := range m {
	if v == 0 {
		delete(m, k) // нормально
	}
}
```

## Множество: map[T]struct{}

В Go нет встроенного типа «множество», его делают на мапе. Значение берут типа `struct{}`: пустая структура занимает **0 байт**, поэтому множество не тратит память на значения.

```go
seen := make(map[string]struct{})
seen["go"] = struct{}{}

if _, ok := seen["go"]; ok {
	fmt.Println("уже было")
}
fmt.Println(unsafe.Sizeof(struct{}{})) // 0
```

Вариант `map[string]bool` тоже встречается: его проще читать (`if seen[x]`), но он тратит байт на значение и допускает три состояния (нет ключа, `false`, `true`). В собеседовании от тебя ждут знания про `struct{}` и умения объяснить разницу.

## Мапы и горутины

Встроенная мапа **не потокобезопасна**. Если одна горутина пишет, а другая одновременно читает или пишет, рантайм замечает это и **роняет всю программу**:

```text
fatal error: concurrent map writes
```

Это не паника: `recover` её не перехватывает, процесс просто завершается. Проверено на Go 1.27.3: восемь горутин, пишущих в одну мапу, валят программу, `defer` с `recover` не помогает. Детектор не гарантирует срабатывание на каждой гонке, но срабатывает часто, поэтому такой баг обычно ловится на нагрузке, в проде.

Решения:

```go
type SafeCache struct {
	mu    sync.RWMutex
	items map[string]string
}

func (c *SafeCache) Get(k string) (string, bool) {
	c.mu.RLock() // много читателей одновременно
	defer c.mu.RUnlock()
	v, ok := c.items[k]
	return v, ok
}

func (c *SafeCache) Set(k, v string) {
	c.mu.Lock() // писатель один, читатели ждут
	defer c.mu.Unlock()
	c.items[k] = v
}
```

- `sync.Mutex` или `sync.RWMutex` рядом с мапой: универсальный вариант по умолчанию.
- `sync.Map`: специализированная мапа для двух сценариев из документации: ключ пишется один раз и много читается, или горутины работают с непересекающимися наборами ключей. В остальных случаях мапа с мьютексом обычно не хуже и типобезопасна.
- Шардирование: N мап, у каждой свой мьютекс, ключ выбирает шард по хешу. Для очень горячих кешей.

Подробно про мьютексы и `sync.Map` поговорим в модуле про конкурентность. Детектор гонок `go test -race` находит такие ошибки ещё в тестах.

## Пакет maps и встроенные функции

| Что | Зачем |
|---|---|
| `clear(m)` | удалить все элементы (Go 1.21) |
| `maps.Clone(m)` | поверхностная копия |
| `maps.Copy(dst, src)` | скопировать все пары из `src` в `dst` с перезаписью |
| `maps.Equal(a, b)`, `maps.EqualFunc` | сравнение содержимого (`a == b` для мап не компилируется) |
| `maps.DeleteFunc(m, f)` | удалить пары по условию |
| `maps.Keys(m)`, `maps.Values(m)`, `maps.All(m)` | итераторы по ключам, значениям, парам (Go 1.23) |
| `maps.Collect(it)`, `maps.Insert(m, it)` | собрать мапу из итератора, добавить из итератора (Go 1.23) |

```go
m := map[string]int{"b": 2, "a": 1}
fmt.Println(slices.Sorted(maps.Keys(m))) // [a b]

maps.DeleteFunc(m, func(k string, v int) bool { return v > 1 })
fmt.Println(m) // map[a:1]
```

Пакет `maps` появился в Go 1.21. Функции `Keys` и `Values` в нём с Go 1.23 возвращают итераторы, а не слайсы: в старых статьях встретишь `maps.Keys` из `golang.org/x/exp/maps`, который возвращал слайс.

## Память: мапа не сжимается

Удаление элементов освобождает слоты, но **не уменьшает** саму таблицу. Мапа, которая однажды выросла до миллиона элементов, а потом опустела, продолжает занимать память под миллион. В коде рантайма Go 1.27.3 нет логики уменьшения таблицы. Если в долгоживущем процессе мапа «надувается» пиками, периодически пересоздавай её: `m = make(map[K]V)` и перенеси живые элементы.

## Как устроена мапа

Сначала общая идея, потом две реализации.

Хеш-таблица хранит пары в массиве **слотов**. Хеш-функция превращает ключ в число, по числу выбирается место в массиве. Два ключа могут попасть в одно место, это **коллизия**. Способов разрешения два: цепочки (в каждом месте список) и открытая адресация (ищем соседнее свободное место по детерминированному правилу).

::: hood До Go 1.24: бакеты и эвакуация
Эту схему спрашивают по старой памяти, поэтому её надо узнавать. Структура `hmap` хранила число элементов, `B` (логарифм числа бакетов: бакетов `2^B`), указатель на массив бакетов и на старый массив во время роста.

```text
hmap
 ├─ count = 11
 ├─ B = 1            -> 2 бакета
 ├─ buckets ──────┐
 └─ oldbuckets    │
                  ▼
   бакет 0: [ tophash x8 | ключи x8 | значения x8 | overflow ] ──> бакет переполнения
   бакет 1: [ tophash x8 | ключи x8 | значения x8 | overflow ]
```

- Младшие `B` бит хеша выбирали бакет, в бакете 8 слотов.
- `tophash`: старшие 8 бит хеша каждого ключа, чтобы быстро отсеивать неподходящие слоты, не сравнивая ключи.
- Если бакет заполнен, к нему цеплялся бакет переполнения (overflow), по сути цепочка.
- Рост, когда в среднем больше 6.5 элементов на бакет: число бакетов удваивалось, но элементы переносились (эвакуировались) **постепенно**, по паре бакетов при каждой записи или удалении. Так не было длинной паузы на перенос всей таблицы.
- Второй повод для роста: слишком много бакетов переполнения (после множества вставок и удалений). Тогда запускался рост «того же размера» (same-size grow): число бакетов не менялось, элементы переупаковывались плотнее, цепочки переполнения исчезали.
:::

::: hood С Go 1.24: Swiss Tables
Новая реализация живёт в `internal/runtime/maps` и основана на дизайне Swiss Table из библиотеки Abseil от Google. Всё ниже сверено с комментариями в исходниках Go 1.27.3 (`map.go`, `table.go`, `group.go`).

**Группа** это 8 слотов (ключ + значение) плюс **контрольное слово** из 8 байт, по байту на слот. Контрольный байт говорит, пуст слот, удалён или занят, а если занят, хранит 7 младших бит хеша ключа.

```text
группа:
  control word:  [ 0x80 | 0x3a | 0x80 | 0x11 | 0xfe | 0x80 | 0x5c | 0x80 ]
                    пуст   H2=58  пуст  H2=17  удалён  пуст  H2=92  пуст
  слоты:         [ k/v  | k/v  | k/v  | k/v  | k/v  | k/v  | k/v  | k/v  ]
```

Хеш ключа (64 бита) делится на две части:

- **H1**, старшие 57 бит: выбирают группу, с которой начинается поиск;
- **H2**, младшие 7 бит: лежат в контрольном байте.

**Поиск ключа:**

1. По H1 выбрать стартовую группу.
2. Одной битовой операцией сравнить H2 искомого ключа сразу со всеми 8 контрольными байтами группы (это и есть главный трюк: 8 проверок за одну инструкцию). Получить маску кандидатов.
3. Для каждого кандидата сравнить ключ целиком (7 бит совпадают случайно с вероятностью 1/128, поэтому полная проверка обязательна).
4. Если не нашли, а в группе есть пустой слот, ключа нет. Если пустых нет, перейти к следующей группе по **квадратичному пробированию** и повторить.

Это **открытая адресация**: никаких цепочек и бакетов переполнения, все пары лежат в одном массиве групп. Поэтому важно, чтобы таблица никогда не заполнялась целиком: максимальная загрузка 7/8 (константа `maxAvgGroupLoad = 7` на 8 слотов группы).

**Удаление** не всегда помечает слот пустым: если группа была полностью заполнена, поиск другого ключа мог пройти через неё дальше, и «дырка» оборвала бы его раньше времени. Такой слот помечается **надгробием** (tombstone, `ctrlDeleted`). Надгробия вычищаются при перестройке таблицы, а когда таблица заполнилась, рантайм сначала пробует убрать ненужные надгробия на месте (`pruneTombstones`, срабатывает, если надгробий не меньше 10% ёмкости), и только если не вышло, растит таблицу.

**Рост без долгих пауз.** При росте таблицу нужно перестроить целиком: последовательность пробирования зависит от числа групп. Чтобы не копировать миллион элементов разом, мапа состоит из нескольких **таблиц** по максимум 1024 слота (`maxTableCapacity`). Старшие биты хеша выбирают таблицу через **каталог** (directory), это схема extendible hashing. Маленькая таблица растёт удвоением, а достигнув предела, **делится на две**. Так каждая операция роста затрагивает не больше одной таблицы.

```text
Map
 └─ directory (globalDepth = 2: смотрим на 2 старших бита хеша)
      00 ─┐
      01 ─┴──> table (localDepth 1)  [группа][группа]...[группа]
      10 ────> table (localDepth 2)  [группа]...
      11 ────> table (localDepth 2)  [группа]...
```

**Маленькие мапы** (до 8 элементов) вообще обходятся без таблиц и каталога: вся мапа это одна группа.

**Случайный порядок обхода** реализован случайными смещениями: итератор начинает со случайной позиции в каталоге и со случайного слота в группе (`entryOffset`, `dirOffset` в `table.go`). Забавное следствие, проверено на Go 1.27.3: у мапы из 5 ключей обход всегда выдаёт **циклический сдвиг** одной и той же последовательности (`abcde`, `cdeab`, `eabcd`...), причём один из вариантов выпадает около половины раз. Случайно, но не равномерно. Ещё раз: опираться на порядок нельзя.

**Что это дало.** По данным блога Go, операции с мапами в микробенчмарках ускорились до 60%, а на полном наборе бенчмарков рантайм стал в среднем на 1.5% экономнее по CPU. Datadog сообщил о сотнях гигабайт сэкономленной памяти в своих сервисах.

В Go 1.24 старую реализацию можно было вернуть через `GOEXPERIMENT=noswissmap`. В Go 1.27.3 такого переключателя уже нет: сборка с ним падает с `go: unknown GOEXPERIMENT swissmap`.
:::

### Что из этого следует для обычного кода

- `make(map[K]V, n)` с подсказкой размера избавляет от последовательных ростов, если размер известен.
- Хеш строки считается по всем её байтам, поэтому очень длинные строковые ключи дороже коротких.
- Хеш-функция рандомизирована: у каждой мапы своя случайная «соль» (поле `seed`: задаётся при создании мапы и заново выбирается при `clear`). Нельзя заранее подобрать ключи, которые все попадут в одну группу, это защита от DoS через коллизии.
- Значение нельзя адресовать именно потому, что элементы переезжают при росте и делении таблиц.

<details><summary>Как устроена мапа в Go?</summary>

С Go 1.24 это Swiss Table: элементы лежат в группах по 8 слотов с 8-байтным контрольным словом. Хеш делится на H1 (57 бит, выбор группы) и H2 (7 бит, хранится в контрольном байте). Поиск сравнивает H2 сразу со всеми 8 контрольными байтами одной битовой операцией, затем проверяет ключи кандидатов; коллизии разрешаются открытой адресацией с квадратичным пробированием. Максимальная загрузка 7/8. Мапа разбита на таблицы до 1024 слотов, которые выбираются через каталог по старшим битам хеша (extendible hashing), поэтому рост затрагивает одну таблицу. Мапа до 8 элементов это одна группа. До 1.24 была схема с бакетами по 8 элементов, `tophash`, бакетами переполнения, ростом при средней загрузке 6.5 и постепенной эвакуацией. Хорошо назвать обе и сказать, где какая.

</details>
<details><summary>Почему порядок обхода мапы случаен?</summary>

Спецификация его не определяет, а реализация специально рандомизирует начальную позицию обхода (случайные смещения по каталогу и по слотам группы). Цель: чтобы программы не начали опираться на порядок, который может поменяться с ростом мапы или версией Go. Для стабильного порядка сортируют ключи: `slices.Sorted(maps.Keys(m))`.

</details>
<details><summary>Что будет при чтении и записи в nil-мапу?</summary>

Чтение, `len`, `delete` и `range` работают: нулевое значение, 0, ничего, ноль итераций. Запись паникует: `assignment to entry in nil map`. Мапу нужно создать через `make` или литерал, частая ошибка с полем-мапой в структуре без конструктора.

</details>
<details><summary>Можно ли использовать мапу из нескольких горутин?</summary>

Только на чтение. Одновременная запись с чтением или записью это гонка, и рантайм часто обнаруживает её и завершает процесс с `fatal error: concurrent map writes`, который не ловится `recover`. Защищают мьютексом (`sync.Mutex` или `sync.RWMutex` для преобладающего чтения), используют `sync.Map` для его специальных сценариев (ключ пишется один раз, или непересекающиеся наборы ключей у горутин) или шардируют мапу.

</details>
<details><summary>Почему нельзя взять адрес элемента мапы?</summary>

При росте элементы перемещаются в новую память, указатель стал бы висячим. Поэтому `&m[k]` и `m[k].Field = v` не компилируются. Решения: копировать значение, менять и записывать обратно, или хранить указатели в значениях.

</details>
<details><summary>Какие типы могут быть ключами?</summary>

Сравнимые: числа, строки, `bool`, указатели, каналы, интерфейсы, массивы и структуры из сравнимых элементов. Слайсы, мапы и функции нельзя. С ключом-интерфейсом есть ловушка: если положить в него несравнимое значение (слайс), будет паника в рантайме. С `float` есть ловушка NaN: такой ключ нельзя найти и удалить через `delete`, только `clear`.

</details>
<details><summary>Как сделать множество? Почему struct{}?</summary>

`map[T]struct{}`: ключи это элементы множества. Пустая структура занимает 0 байт, поэтому значения не тратят память, а тип явно говорит, что значение не несёт смысла. `map[T]bool` работает, но тратит байт на элемент и допускает лишнее состояние `false`.

</details>
<details><summary>Освобождает ли delete память?</summary>

Слот освобождается для новых элементов, но таблица не уменьшается: мапа, выросшая до миллиона элементов, после удаления всех продолжит занимать память под них. Для долгоживущих мап с пиками размера их пересоздают.

</details>
<details><summary>Мапа передаётся по ссылке?</summary>

В Go всё передаётся по значению. Значение типа мапы это указатель на структуру рантайма, поэтому при передаче копируется указатель, и функция работает с той же таблицей. Отсюда поведение «как у ссылки»: изменения видны снаружи, `m2 := m` не копирует данные. Копию делают через `maps.Clone`.

</details>
:::
