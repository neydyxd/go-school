# Указатели

В JavaScript ты не думал об указателях: объекты и массивы передаются «по ссылке», примитивы по значению, и язык решает за тебя. В Go правило одно и без исключений: **всё передаётся по значению**, то есть копируется. Хочешь, чтобы функция изменила твою переменную, передай ей адрес этой переменной. Это и есть указатель.

Звучит как C, но без его опасностей. В Go нет арифметики указателей, нет висячих указателей (сборщик мусора не освободит память, пока на неё кто-то указывает), а вернуть адрес локальной переменной из функции совершенно нормально. Зато есть `nil`, и разыменование nil-указателя это самая частая паника в Go-сервисах.

В бэкенде указатели повсюду: обработчики получают `*http.Request`, репозитории возвращают `*User`, необязательные поля JSON описываются как `*int`, а методы, меняющие объект, объявляются на указателе. В этом уроке разберём механику, а в уроке про структуры и методы применим её к получателям методов.

## Адрес и разыменование

У каждой переменной есть место в памяти. **Указатель** это значение, которое хранит адрес этого места.

```go
x := 42
p := &x         // & берёт адрес: p имеет тип *int, "указатель на int"
fmt.Println(*p) // * разыменовывает: читает значение по адресу, 42
*p = 100        // пишет по адресу
fmt.Println(x)  // 100: мы изменили саму x
```

```
  x                     p
┌──────┐  адрес 0xc000012080   ┌──────────────┐
│ 100  │ ◄──────────────────── │ 0xc000012080 │
└──────┘                       └──────────────┘
```

Обозначения:

- `*T` в типе: «указатель на значение типа T». `*int`, `*User`, `*[]string`.
- `&x` в выражении: адрес переменной `x`.
- `*p` в выражении: значение, на которое указывает `p`. Можно и читать, и писать.

Нулевое значение любого указателя `nil`: он никуда не указывает.

Указатели сравнимы: `p == q` истинно, если они указывают на одну и ту же переменную (или оба `nil`). Равенство значений тут ни при чём:

```go
a, b := 1, 1
pa, pb := &a, &b
fmt.Println(pa == pb, *pa == *pb) // false true
```

Адрес можно взять у переменной, у поля структуры, у элемента массива или слайса. Нельзя взять адрес у константы, литерала числа или элемента мапы:

```go
&5      // ошибка: cannot take address of 5
&m["a"] // ошибка: cannot take address of m["a"]
```

С элементом мапы это не каприз: мапа при росте перекладывает элементы в новую память, и указатель стал бы недействительным. Подробнее в уроке про мапы.

## Всё передаётся по значению

Это главное утверждение урока и частый вопрос на собесе. При вызове функции каждый аргумент **копируется** в параметр.

```go
func swapVal(a, b int)  { a, b = b, a }
func swapPtr(a, b *int) { *a, *b = *b, *a }

x, y := 1, 2
swapVal(x, y)
fmt.Println(x, y) // 1 2: функция поменяла свои копии
swapPtr(&x, &y)
fmt.Println(x, y) // 2 1: функция писала по адресам наших переменных
```

С указателем копируется **сам указатель**, то есть адрес. Копия адреса ведёт туда же, поэтому `*a = ...` меняет переменную вызывающего. Но присвоить новое значение самому параметру-указателю бесполезно, это изменит только копию:

```go
func reassign(p *int) {
	x := 100
	p = &x // меняем локальную копию указателя
}

func setNil(p *int) { p = nil }

v := 1
pv := &v
reassign(pv)
setNil(pv)
fmt.Println(*pv, pv == nil)
```

<Predict :options="['1 false', '100 false', '100 true', 'паника']" :correct="0">

Обе функции присваивают новое значение своей копии указателя, а не пишут через него. Указатель `pv` у вызывающего не изменился: он по-прежнему ведёт на `v`, где лежит 1, и он не `nil`. Чтобы функция могла поменять сам указатель вызывающего, ей нужен указатель на указатель `**int` (или пусть возвращает новый указатель).

</Predict>

### А как же слайсы и мапы?

Ты увидишь, что функция, получившая слайс, может поменять его элементы, а получившая мапу может добавить ключ. Это не исключение из правила: слайс и мапа это небольшие значения, **внутри которых** уже есть указатель на данные. При передаче копируется это небольшое значение, а указатель внутри него ведёт на те же данные.

| Тип | Что копируется при передаче | Видны ли изменения данных вызывающему |
|---|---|---|
| `int`, `string`, `bool` | само значение | нет |
| массив `[N]T` | **весь массив** | нет |
| структура | **все поля** | нет |
| указатель `*T` | адрес | да, через `*p` |
| слайс `[]T` | заголовок: указатель, длина, ёмкость | изменения элементов да, `append` не всегда |
| мапа, канал | указатель на внутреннюю структуру | да |

Массив это значение целиком, в отличие от JS:

```go
arr := [3]int{}
arr2 := arr // полная копия
arr2[0] = 1
fmt.Println(arr[0]) // 0
```

Поэтому на вопрос «в Go есть передача по ссылке?» правильный ответ: **нет, только по значению**. Есть типы, значения которых содержат указатели. Подробно про заголовок слайса и `append` в следующем уроке.

## new и составные литералы

`new(T)` выделяет память под значение типа `T`, заполняет её нулевым значением и возвращает указатель:

```go
p := new(int)
fmt.Println(*p, p == nil) // 0 false
```

На практике для структур чаще пишут `&T{...}`: так можно сразу задать поля.

```go
u := &User{Name: "Вася"} // то же, что new(User) плюс заполнение полей
```

### new с выражением (Go 1.26)

С Go 1.26 `new` принимает не только тип, но и **выражение**: создаётся новая переменная, инициализированная его значением.

```go
age := new(30)                   // *int, указывает на 30
name := new("go")                // *string
fmt.Printf("%T %v\n", age, *age) // *int 30
```

Раньше для указателя на число или строку приходилось заводить временную переменную или писать хелпер `func ptr[T any](v T) *T { return &v }`, который был почти в каждом проекте. Особенно это мешало с необязательными полями:

```go
type UserPatch struct {
	Name *string `json:"name,omitempty"`
	Age  *int    `json:"age,omitempty"`
}

// до 1.26
age := 31
patch := UserPatch{Age: &age}

// с 1.26
patch := UserPatch{Age: new(31)}
```

Не путай: `&5` по-прежнему не компилируется, а `new(5)` работает. В старом коде и у собеседующего на Go 1.25 и ниже ты этой формы не увидишь.

Про `make` отдельно: `make` создаёт только слайсы, мапы и каналы и возвращает **не указатель**, а готовое к работе значение. `new(map[string]int)` даст указатель на nil-мапу, писать в которую нельзя. Сравнение `new` и `make` будет в уроках про слайсы и мапы.

## Указатели на структуры

Чтобы функция изменила структуру, передают указатель на неё. Для доступа к полям Go **автоматически разыменовывает**: `p.Name` значит `(*p).Name`. Оператора `->`, как в C, нет.

```go
type User struct {
	Name string
	Age  *int // nil означает "возраст неизвестен"
}

func rename(u User)   { u.Name = "Петя" } // меняет копию
func renameP(u *User) { u.Name = "Петя" } // меняет оригинал

u := User{Name: "Вася"}
rename(u)
fmt.Println(u.Name) // Вася
renameP(&u)
fmt.Println(u.Name) // Петя
```

Два указателя на одну структуру видят одни и те же изменения:

```go
a := &User{Name: "x"}
b := a
b.Name = "y"
fmt.Println(a.Name) // y
```

## nil и nil-указатель

Разыменование `nil` это паника во время выполнения:

```go
var u *User
fmt.Println(u == nil) // true
fmt.Println(u.Name)
// panic: runtime error: invalid memory address or nil pointer dereference
// [signal SIGSEGV: segmentation violation code=... addr=0x0 pc=...]
```

Откуда берутся nil-указатели в реальном коде:

- функция вернула `nil, err`, а ошибку не проверили;
- поле-указатель в структуре не заполнили (`Config.DB *sql.DB` остался `nil`);
- поиск вернул `nil` как «не найдено».

Указатель удобен как «значение или его отсутствие». В JSON это различие между `"age": 0` и отсутствием поля: `*int` равен `nil`, если поля не было, и указывает на 0, если пришёл ноль. В базе данных так же отличают `NULL` от нуля. Плата за удобство: каждое чтение требует проверки на `nil`.

::: hood Почему разыменование nil это паника, а не порча памяти
`nil` для указателя это адрес 0. Операционная система никогда не отображает самую первую страницу памяти процесса, поэтому чтение или запись по адресу 0 (или по небольшому смещению от него, как `u.Name`) вызывает аппаратное исключение, сигнал `SIGSEGV`. Рантайм Go перехватывает этот сигнал и превращает его в обычную панику `runtime.Error`, которую можно поймать `recover`. Отсюда строчка `addr=0x0` в сообщении.

Если структура огромная и поле лежит далеко от начала, обращение по `nil` могло бы попасть за пределы защищённой страницы. Для таких случаев компилятор сам вставляет явную проверку на `nil` перед обращением. В итоге гарантия одна: разыменование `nil` всегда паника, а не тихое чтение чужой памяти.
:::

## Указатель на локальную переменную безопасен

В C вернуть адрес локальной переменной это ошибка: переменная живёт на стеке и исчезает после возврата. В Go это обычная практика:

```go
func newCounter() *int {
	c := 0
	return &c // законно и безопасно
}

p := newCounter()
*p++
fmt.Println(*p) // 1
```

Компилятор сам решает, где разместить переменную. Это решение называется **escape analysis** (анализ побега).

::: hood Стек, куча и escape analysis
У каждой горутины есть свой **стек**: память под локальные переменные функций. Выделение на стеке почти бесплатное (сдвиг указателя стека), а освобождение происходит автоматически при возврате из функции. **Куча** это общая память, которую обслуживает сборщик мусора: выделение дороже, и каждый объект в куче добавляет работы GC.

Компилятор анализирует, может ли ссылка на переменную пережить функцию. Если может (адрес возвращается, сохраняется в глобальную переменную, захватывается долгоживущим замыканием), переменная «убегает» в кучу. Если нет, она остаётся на стеке, даже если ты брал её адрес.

Посмотреть решения компилятора:

```bash
go build -gcflags=-m .
```

```go
func newInt() *int {
	x := 42
	return &x // ./main.go: moved to heap: x
}

func local() int {
	y := 1
	p := &y // y остаётся на стеке: адрес не покидает функцию
	return *p
}
```

```
   стек newInt (исчезает после return)       куча (живёт, пока есть ссылки)
  ┌────────────────────────┐                ┌──────────┐
  │ (x тут не хранится)    │                │  x = 42  │ ◄── указатель,
  └────────────────────────┘                └──────────┘     который вернули
```

Указатель занимает 8 байт на 64-битной платформе. Сборщик мусора знает, в каких словах памяти лежат указатели, и по ним находит живые объекты: пока на `x` есть хоть один указатель, память не освободят. Поэтому висячих указателей в Go не бывает (если не использовать пакет `unsafe`). Про стек, кучу и GC подробно в модуле про рантайм.
:::

## Указатель на указатель

Иногда функции нужно поменять **сам указатель** вызывающего. Тогда ей передают адрес этого указателя, тип `**T`:

```go
type Node struct {
	Val  int
	Next *Node
}

func PushFront(head **Node, v int) {
	*head = &Node{Val: v, Next: *head} // меняем переменную вызывающего
}

var list *Node // пустой список
PushFront(&list, 1)
PushFront(&list, 2) // list: 2 -> 1
```

В прикладном коде `**T` встречается редко, чаще функция возвращает новый указатель: `list = pushFront(list, 2)`. Но на собесе и в задачах на связные списки этот приём пригодится.

## Чего в Go нет

- **Арифметики указателей**: `p++` для указателя не скомпилируется. Пройти по памяти можно только через пакет `unsafe`, и в обычном коде это запрещённый приём.
- **Ссылок как в C++** (`int&`): только указатели.
- **Ручного освобождения памяти**: `free` и `delete` нет, этим занимается GC.

## Когда брать указатель

Бери указатель, если:

1. **Функция должна изменить значение** вызывающего.
2. **Нужно отличать «нет значения» от нулевого**: необязательные поля, «не найдено».
3. **Значение большое** и копировать его на каждом вызове дорого. Граница размытая: копирование небольших структур (несколько полей) обычно не медленнее указателя, а указатель может заставить значение уйти в кучу. Решай по профилировщику, а не на глаз.
4. **Значение нельзя копировать** по смыслу: структура с `sync.Mutex` внутри, соединение с базой. `go vet` ругается на копирование мьютекса.

Не бери указатель:

- на маленькие неизменяемые значения: `int`, `time.Time`, небольшие структуры;
- на слайсы, мапы, каналы и функции: внутри них уже есть указатель (исключение: функция должна заменить сам слайс, тогда обычно возвращают новый);
- на интерфейсы: `*io.Reader` почти всегда ошибка, интерфейс сам умеет хранить указатель (модуль про интерфейсы).

::: trap Указатель на копию из range
```go
type User struct {
	Name   string
	Active bool
}

users := []User{{Name: "a"}, {Name: "b"}}

// плохо: &u это адрес копии элемента, а не самого элемента
var ptrs []*User
for _, u := range users {
	ptrs = append(ptrs, &u)
}
ptrs[0].Active = true
fmt.Println(users[0].Active) // false

// хорошо: адрес элемента слайса
for i := range users {
	ptrs = append(ptrs, &users[i])
}
```

С Go 1.22 у каждой итерации своя `u`, поэтому указатели хотя бы разные. Но это всё равно указатели на **копии**: изменения через них в слайс не попадут. До 1.22 было ещё хуже: все указатели смотрели на одну переменную с последним элементом.
:::

::: trap Указатель на элемент слайса после append
```go
s := []int{1, 2, 3}
p := &s[0]
s = append(s, 4) // места нет: append выделил новый массив и скопировал данные
*p = 100
fmt.Println(s[0], *p) // 1 100: p смотрит в старый массив
```

Указатель на элемент слайса привязан к конкретному массиву под слайсом. Если `append` перевыделил память, слайс уехал в новый массив, а указатель остался в старом. Это не порча памяти (старый массив жив, пока на него есть указатель), а тихая логическая ошибка. Правило: не держи указатели на элементы слайса, который может расти. Механику `append` разберём в следующем уроке.
:::

## Что выведет программа?

```go
p := new(int)
q := new(int)
*p = 5
*q = 5
fmt.Println(p == q, *p == *q)
```

<Predict :options="['true true', 'false true', 'false false', 'true false']" :correct="1">

Каждый вызов `new` создаёт новую переменную, поэтому указатели разные: `p == q` ложно. Значения по адресам одинаковые: `*p == *q` истинно. Сравнение указателей это сравнение адресов, а не содержимого.

</Predict>

```go
type Point struct{ X, Y int }

func move(p Point)     { p.X++ }
func movePtr(p *Point) { p.X++ }

func main() {
	pt := Point{1, 1}
	move(pt)
	movePtr(&pt)
	pp := &pt
	movePtr(pp)
	fmt.Println(pt.X)
}
```

<Predict :options="['1', '2', '3', '4']" :correct="2">

`move` получает копию структуры, оригинал не меняется. Два вызова `movePtr` получают адрес `pt` (второй раз через переменную `pp`, в которой тот же адрес), каждый увеличивает `X` на 1. Итог `1 + 2 = 3`.

</Predict>

```go
var u *User
if u != nil && u.Name != "" {
	fmt.Println("есть имя")
}
fmt.Println("готово")
```

<Predict :options="['готово', 'есть имя, готово', 'паника: nil pointer dereference', 'ошибка компиляции']" :correct="0">

`&&` вычисляется слева направо и останавливается на первом `false` (short-circuit). `u != nil` ложно, поэтому `u.Name` не вычисляется и паники нет. Если поменять условия местами, `u.Name` выполнится первым и программа упадёт. Это стандартный способ безопасно проверять поля указателя.

</Predict>

<details><summary>В Go передача по значению или по ссылке?</summary>

Всегда по значению: аргумент копируется в параметр. Передавая указатель, копируешь адрес; через копию адреса можно изменить исходную переменную, но присваивание самому параметру вызывающего не затронет. Слайсы, мапы и каналы тоже копируются, но их значения содержат указатели на общие данные, поэтому изменения данных видны. Передачи по ссылке в смысле C++ в Go нет.

</details>
<details><summary>Можно ли вернуть указатель на локальную переменную?</summary>

Да, это безопасно и идиоматично. Компилятор с помощью escape analysis видит, что адрес покидает функцию, и размещает переменную в куче (`moved to heap` в выводе `-gcflags=-m`). Сборщик мусора не освободит её, пока на неё есть указатели, поэтому висячих указателей не бывает.

</details>
<details><summary>Чем new отличается от make?</summary>

`new(T)` работает для любого типа: выделяет память под нулевое значение `T` и возвращает `*T`. С Go 1.26 `new(expr)` создаёт переменную со значением выражения: `new(42)` это `*int`. `make` только для слайсов, мап и каналов: создаёт и инициализирует внутреннюю структуру и возвращает само значение (`[]T`, `map[K]V`, `chan T`), а не указатель. `new(map[string]int)` вернёт указатель на nil-мапу, запись в которую паникует.

</details>
<details><summary>Когда использовать указатель, а когда значение?</summary>

Указатель: когда нужно изменить значение, отличить «нет значения» от нуля, избежать копирования действительно большой структуры или когда значение нельзя копировать (содержит мьютекс). Значение: для маленьких и неизменяемых данных, для слайсов, мап и каналов (у них указатель уже внутри), для интерфейсов. Лишние указатели заставляют переменные уходить в кучу и добавляют работы GC, так что «всегда указатель ради скорости» неверно.

</details>
<details><summary>Что происходит при разыменовании nil-указателя?</summary>

Паника `runtime error: invalid memory address or nil pointer dereference`. Обращение по адресу около нуля вызывает у процессора исключение, ОС присылает сигнал SIGSEGV, рантайм превращает его в панику (для далёких полей компилятор вставляет явную проверку). Её можно поймать `recover`, но правильнее не допускать: проверять ошибки и `nil` перед использованием.

</details>
<details><summary>Есть ли в Go арифметика указателей?</summary>

Нет. `p + 1` для указателя не компилируется. Это сделано ради безопасности памяти и работы сборщика мусора. Низкоуровневые операции возможны через пакет `unsafe` (`unsafe.Pointer`, `unsafe.Add`), но такой код не защищён гарантиями языка и встречается в основном в рантайме и высокопроизводительных библиотеках.

</details>
<details><summary>Почему нельзя взять адрес элемента мапы?</summary>

`&m[k]` запрещён компилятором, потому что мапа при росте переносит элементы в новую память, и указатель стал бы недействительным. Если нужно менять значения по месту, храни в мапе указатели (`map[string]*User`) или читай значение, меняй и записывай обратно. Элемент слайса адресуем (`&s[i]`), но указатель привязан к текущему массиву, и после `append` с перевыделением он смотрит в старые данные.

</details>
<details><summary>Зачем нужен указатель на указатель?</summary>

Чтобы функция изменила сам указатель вызывающего, а не данные по нему. Пример: вставка в начало связного списка `PushFront(head **Node, v int)` меняет переменную-голову у вызывающего. В прикладном коде вместо этого обычно возвращают новый указатель.

</details>
