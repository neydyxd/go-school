# Переменные, типы, константы

На фронтенде у тебя был один тип для чисел: `number`, он же float64. В Go чисел больше десятка: `int`, `int8`, `uint32`, `float64` и другие, и каждый ведёт себя по-своему на границах. Это не бюрократия. Бэкенд хранит деньги, считает просмотры, режет байты из сети и отдаёт ID в JSON. Если не понимать, где кончается `int32` и что происходит после, получишь отрицательный баланс у клиента или ID, который «внезапно» стал другим.

Вторая важная идея урока: в Go **нет неинициализированной памяти**. Любая переменная с момента объявления имеет осмысленное **нулевое значение**. На этом держится половина идиом языка, от `var mu sync.Mutex` до `var buf bytes.Buffer`.

Третья: Go **никогда не преобразует типы неявно**. `int + float64` не скомпилируется. Поначалу раздражает, потом понимаешь, что так ловится целый класс ошибок, которые в JavaScript всплывают в проде.

## Переменные

Четыре способа объявить переменную:

```go
var a int      // тип есть, значения нет: будет нулевое (0)
var b int = 10 // тип и значение
var c = 10     // тип выведен из значения: int
d := 10        // короткая форма, только внутри функций
```

Группы и множественное присваивание:

```go
var (
	host = "localhost"
	port = 8080
)

x, y := 1, 2
x, y = y, x // обмен без временной переменной: правая часть вычисляется целиком
```

Когда что использовать:

- `:=` для большинства локальных переменных, когда есть начальное значение.
- `var x T`, когда нужно именно нулевое значение (`var count int`, `var sb strings.Builder`), и для переменных уровня пакета: там `:=` запрещён.
- `var x T = v`, когда тип выражения не тот, что тебе нужен: `var ratio float64 = 1`.

### Правило `:=` и повторное объявление

`:=` объявляет **хотя бы одну новую** переменную слева. Остальные, уже объявленные **в этой же области видимости**, просто получают новое значение:

```go
x := 10
x, y := 20, 30    // ок: y новая, x переприсвоена
fmt.Println(x, y) // 20 30
```

```go
x := 10
x := 20 // ошибка компиляции: no new variables on left side of :=
```

Если же старая переменная объявлена во **внешней** области, `:=` создаст новую, которая её **затенит** (shadowing). Это главный источник багов с `:=`, разберём в граблях.

### Неиспользуемые переменные

Объявил локальную переменную и не прочитал: ошибка компиляции `declared and not used`. Чтобы проигнорировать значение, есть пустой идентификатор `_`:

```go
_, err := strconv.Atoi("42") // число не нужно, нужна только ошибка
```

## Базовые типы

| Группа | Типы | Заметки |
|---|---|---|
| Логический | `bool` | только `true`/`false`, с числами не смешивается |
| Целые со знаком | `int8`, `int16`, `int32`, `int64`, `int` | `int` 64 бита на 64-битных платформах, 32 на 32-битных |
| Целые без знака | `uint8`, `uint16`, `uint32`, `uint64`, `uint`, `uintptr` | `uintptr` для низкоуровневой работы с адресами, в обычном коде не нужен |
| Синонимы | `byte` = `uint8`, `rune` = `int32` | это не отдельные типы, а алиасы |
| С плавающей точкой | `float32`, `float64` | IEEE 754; по умолчанию бери `float64` |
| Комплексные | `complex64`, `complex128` | в бэкенде почти не встречаются |
| Строка | `string` | неизменяемая последовательность байт, обычно UTF-8 |

Практические правила:

- **`int` по умолчанию** для счётчиков, индексов, длин. `len()` возвращает `int`, и вся стандартная библиотека на нём.
- **Типы с размером** (`int64`, `uint32`) там, где размер важен: бинарные протоколы, поля БД (`BIGINT` это `int64`), хеши.
- **`uint` не для «неотрицательных» величин.** Соблазнительно объявить возраст как `uint`, но `a - b` при `a < b` даст огромное число вместо отрицательного. Беззнаковые нужны для битовых операций и протоколов.
- **`byte`** для сырых данных (`[]byte` из сети и файлов), **`rune`** для символа Unicode. Подробно в уроке про строки.

Размер легко проверить:

```go
fmt.Println(unsafe.Sizeof(int(0)), unsafe.Sizeof(true), unsafe.Sizeof(""))
// 8 1 16
```

Строка занимает 16 байт: это не сами символы, а заголовок из указателя на байты и длины. Про это подробно в уроке про строки.

## Нулевые значения

Каждый тип имеет нулевое значение, и переменная без явной инициализации получает именно его:

| Тип | Нулевое значение |
|---|---|
| числа | `0` (`0.0` для float) |
| `bool` | `false` |
| `string` | `""` (пустая строка, не nil) |
| указатели, слайсы, мапы, каналы, функции, интерфейсы | `nil` |
| массивы и структуры | каждый элемент и поле в своём нулевом значении |

```go
var s string
var p *int
var e error
fmt.Printf("%q %v %v %v %v\n", s, p, e, 0.0, false)
// "" <nil> <nil> 0 false
```

Отсюда идиома **«сделай нулевое значение полезным»**: тип проектируют так, чтобы его можно было использовать без конструктора. `var wg sync.WaitGroup`, `var mu sync.Mutex`, `var b strings.Builder` сразу готовы к работе. Когда будешь писать свои типы, держи это в голове.

::: hood Почему нулевые значения бесплатны
Компилятор и рантайм гарантируют, что память под новую переменную обнулена: для переменных на стеке компилятор сам вставляет обнуление, а аллокатор кучи отдаёт обнулённые блоки (свежие страницы от ОС и так нулевые, повторно используемую память он зачищает). Поэтому «нулевое значение» не требует отдельной инициализации поля за полем: ноль в каждом байте и есть `0`, `false`, `""` (нулевой указатель и нулевая длина) и `nil`. Именно поэтому в Go нет понятия «мусор в неинициализированной переменной», как в C.
:::

## Константы

Константа вычисляется **на этапе компиляции**. Значением может быть только то, что компилятор способен посчитать сам: литералы, арифметика над ними, `len` от массива, другие константы. Вызвать функцию нельзя:

```go
const Pi = 3.14159
const Timeout = 5 * time.Second // ок: time.Second тоже константа
const N = len("hello")          // ок: длина строковой константы известна
// const Now = time.Now()       // ошибка: значение известно только при запуске
```

### Типизированные и нетипизированные

Это самая недооценённая тема урока и частый вопрос на собесе.

```go
const a = 10      // нетипизированная (untyped) целая константа
const b int8 = 10 // типизированная: тип int8
```

**Нетипизированная** константа ещё не выбрала тип. Она подстраивается под контекст, где её используют:

```go
const c = 10

var f float64 = c // ок: 10 представимо как float64
var i int = c     // ок
var u uint8 = c   // ок
```

Если контекст не задаёт тип (`x := c`, `fmt.Println(c)`), берётся **тип по умолчанию**: `int` для целых, `float64` для дробных, `rune` для символьных (`'a'`), `string` для строк, `bool` для логических.

С переменной так не выйдет:

```go
x := 3
var f float64 = x // ошибка: cannot use x (variable of type int) as float64 value
```

**Типизированная** константа ведёт себя как значение своего типа и проверяется на переполнение:

```go
const typed int8 = 100
fmt.Println(typed * 2) // ошибка компиляции: constant 200 of type int8 overflows int8
```

### Произвольная точность

Нетипизированные константы считаются с огромной точностью: спецификация требует от компилятора минимум 256 бит для целых. Поэтому промежуточные вычисления не переполняются:

```go
const big = 1 << 100
fmt.Println(big >> 98) // 4
// fmt.Println(big)    // ошибка: 1267650600228229401496703205376 не влезает в int
```

Тот же механизм объясняет знаменитый пример с дробями:

```go
fmt.Println(0.1+0.2 == 0.3)
```

<Predict :options="['true', 'false', 'ошибка компиляции']" :correct="0">

`true`. Все три числа здесь нетипизированные константы, компилятор складывает их точно, как рациональные числа, и только потом превращает результат в `float64`. С переменными (`x, y := 0.1, 0.2; x+y == 0.3`) будет `false`, а `x+y` напечатается как `0.30000000000000004`: сложение идёт уже в двоичной арифметике float64, где ни 0.1, ни 0.2 не представимы точно.

</Predict>

Обратная сторона: целочисленность константы тоже сохраняется. `5 / 2` это деление двух целых нетипизированных констант, результат `2`, даже если дальше он попадёт во float:

```go
var f float64 = 5 / 2
fmt.Println(f)           // 2
fmt.Println(5.0 / 2)     // 2.5
fmt.Println(5 / 2 * 2.0) // 4
```

### iota

`iota` это счётчик внутри блока `const`: в первой строке блока он равен 0, в каждой следующей на 1 больше. Вторая хитрость блока: строка без выражения **повторяет выражение предыдущей**, но с новым `iota`.

```go
type Weekday int

const (
	Sunday  Weekday = iota // 0
	Monday                 // 1: повторяется "Weekday = iota"
	Tuesday                // 2
)
```

Типичные приёмы:

```go
// Пропуск значения: 0 часто резервируют под "не задано".
const (
	_       = iota
	Created // 1
	Paid    // 2
)

// Битовые флаги: каждый в своём бите.
type Perm uint8

const (
	Read  Perm = 1 << iota // 1 (001)
	Write                  // 2 (010)
	Exec                   // 4 (100)
)

// Единицы размера.
const (
	_  = iota
	KB = 1 << (10 * iota) // 1 << 10 = 1024
	MB                    // 1 << 20
	GB                    // 1 << 30
)
```

Флаги проверяют побитовым И: `p&Write != 0` значит «право записи есть». Комбинируют через `|`: `Read | Write`.

Важно: `iota` это **номер строки внутри блока**, а не «сколько раз его использовали». Он сбрасывается в 0 в каждом новом блоке `const`.

```go
const (
	A = iota
	B
	_
	D
	E = "x"
	F
	G = iota
)

func main() { fmt.Println(D, F, G) }
```

<Predict :options="['3 x 6', '2 x 3', '3 x 4', 'ошибка компиляции']" :correct="0">

`D` стоит в строке с номером 3 (`_` тоже занимает строку). `E` задана явно, `F` повторяет предыдущее выражение, то есть `"x"`. `G = iota` в строке номер 6, поэтому 6. iota продолжал расти, даже когда не использовался.

</Predict>

::: trap iota в публичном API
Если вставить новую константу в середину блока, все следующие сдвинутся. Для значений, которые уходят в базу данных, JSON или другой сервис, это ломает совместимость: вчерашний `Paid = 2` сегодня стал `3`.

```go
// плохо: значения хранятся в БД
const (
	StatusNew = iota
	StatusPaid
	StatusShipped
)

// хорошо: явные значения, вставка новой не сдвинет старые
const (
	StatusNew     = 1
	StatusPaid    = 2
	StatusShipped = 3
)
```

`iota` хорош для внутренних перечислений и флагов. Для «внешних» кодов пиши числа явно.
:::

## Преобразования типов

В Go нет неявных преобразований между разными типами, даже между `int` и `int64`. Преобразование пишется как вызов: `T(x)`.

```go
a := 7
b := 2
fmt.Println(float64(a/b), float64(a)/float64(b)) // 3 3.5
```

Первое выражение делит целые (получается 3), и только потом превращает результат во float. Порядок скобок решает.

Что происходит при преобразованиях:

| Из | В | Поведение |
|---|---|---|
| целое | целое меньшего размера | отбрасываются старшие биты: `int64`-переменная `1 << 40` в `int32` даёт `0`, `uint8`-переменная `200` в `int8` даёт `-56` |
| float | целое | дробная часть **отбрасывается к нулю**: `3.99` даёт `3`, `-3.99` даёт `-3` |
| float вне диапазона | целое | результат зависит от платформы (спецификация: implementation-dependent), не полагайся |
| целое | `string` | **не число в строку**, а символ с этим кодом: `string(rune(65))` это `"A"` |

Числа в строки и обратно переводит пакет `strconv`:

```go
s := strconv.Itoa(42)        // "42"
n, err := strconv.Atoi("42") // 42, nil
f, err := strconv.ParseFloat("3.14", 64)
```

С константами компилятор строже, чем с переменными: `int(3.99)` для константы не скомпилируется (`cannot convert 3.99 (untyped float constant) to type int`), а `uint8(300)` даст `overflows`. Компилятор видит потерю данных и не даёт её допустить. С переменными он этого не видит, и потеря происходит молча.

### Свои типы и алиасы

```go
type Celsius float64 // новый тип: определение (type definition)
type Fahrenheit float64

c := Celsius(100)
f := Fahrenheit(c*9/5 + 32) // нужна явная конверсия, иначе ошибка компиляции
fmt.Println(f)              // 212
```

`Celsius` и `Fahrenheit` устроены одинаково, но это **разные типы**: сложить их без конверсии нельзя. Так компилятор ловит смешение единиц, рублей с копейками, `UserID` с `OrderID`. К своему типу можно добавлять методы (урок про структуры и методы).

Алиас пишется со знаком `=` и **не создаёт** новый тип, а даёт второе имя существующему:

```go
type MyInt int   // новый тип
type Alias = int // то же самое, что int

var a Alias = 5
var n int = a         // ок: это один и тот же тип
fmt.Printf("%T\n", a) // int
```

`byte` и `rune` как раз алиасы. В своём коде алиасы нужны редко, в основном при постепенном переносе типа между пакетами.

::: trap string(int) вместо числа
```go
// плохо
id := 65
s := "user-" + string(id) // "user-A", а не "user-65"

// хорошо
s := "user-" + strconv.Itoa(id) // "user-65"
s = fmt.Sprintf("user-%d", id)  // тоже "user-65", медленнее, зато гибко
```

`go vet` ловит эту ошибку: `conversion from int to string yields a string of one rune, not a string of digits`. Ещё одна причина гонять `go vet` всегда. Если символ по коду и правда нужен, пиши явно: `string(rune(id))`.
:::

## Переполнение

Числа в Go имеют фиксированный размер, и выход за границу **не паника и не ошибка**, а «заворачивание» (wraparound). Для беззнаковых это арифметика по модулю 2^N, для знаковых поведение тоже строго определено спецификацией, в отличие от C, где это undefined behavior.

Например, `uint8` хранит 0-255, и переменная со значением 255 после `x++` станет не 256, а чем именно, проверь на первой задачке раздела «Что выведет программа?». Со знаковыми то же самое, только вместо нуля получается отрицательный край:

```go
var i8 int8 = 127
i8++
fmt.Println(i8) // -128

i := math.MaxInt64
i++
fmt.Println(i) // -9223372036854775808
```

::: hood Дополнительный код: почему 127 + 1 = -128
Знаковые целые хранятся в **дополнительном коде** (two's complement). Для `int8`:

```
 0111 1111  =  127   (максимум)
+0000 0001
 ---------
 1000 0000  = -128   (минимум: старший бит "весит" -128)

 1111 1111  =   -1   (-128 + 127)
```

Старший бит имеет вес `-128`, остальные обычные `+64, +32, ... +1`. Процессор складывает знаковые и беззнаковые числа одной и той же инструкцией, разница только в том, как трактовать результат. Поэтому `uint8`-переменная со значением 200, преобразованная в `int8`, даёт `-56`: те же биты `1100 1000`, прочитанные как `-128 + 72`.

Отсюда же единственный случай, когда деление «переполняется». Речь о значениях во время выполнения, то есть о переменных:

```go
x := int64(math.MinInt64)
m := int64(-1)
fmt.Println(x/m, -x == x) // -9223372036854775808 true
```

Математически `x / -1` это `2^63`, но в `int64` он не помещается, и спецификация прямо говорит, что результат равен самому `x`. То же с `-x`. С константами так не выйдет: `-math.MinInt64` это нетипизированная константа, она точно равна `2^63`, и `var y int64 = -math.MinInt64` не скомпилируется (`overflows`). Константы считаются точно, заворачиваются только переменные.
:::

Что **паникует**, а что нет:

| Операция | Результат |
|---|---|
| целочисленное переполнение `+ - * <<` | молча заворачивается |
| целочисленное деление на ноль (переменная) | паника `runtime error: integer divide by zero` |
| деление на ноль константы (`10 / 0`) | ошибка компиляции `division by zero` |
| float деление на ноль | `+Inf`, `-Inf` или `NaN`, без паники |
| переполнение константы | ошибка компиляции `overflows` |

```go
var z float64
fmt.Println(1/z, -1/z, z/z)           // +Inf -Inf NaN
fmt.Println(math.NaN() == math.NaN()) // false: NaN не равен ничему, даже себе
```

### Как ловить переполнение

Встроенной проверки нет, ловят вручную. Для сложения: переполнение возможно, только если знаки слагаемых совпадают, и тогда у результата знак другой:

```go
func addOK(a, b int64) bool {
	s := a + b
	return !((a > 0 && b > 0 && s < 0) || (a < 0 && b < 0 && s >= 0))
}
```

Для беззнаковых есть пакет `math/bits`: `bits.Add64` и `bits.Mul64` возвращают перенос и старшую половину результата.

```go
sum, carry := bits.Add64(math.MaxUint64, 1, 0)
fmt.Println(sum, carry) // 0 1: перенос сигналит о переполнении
```

::: trap Деньги во float
```go
// плохо
price := 0.1
total := price * 3 // 0.30000000000000004

// хорошо: храни минимальные единицы в целых
var cents int64 = 1999                        // 19.99 ₽
fmt.Printf("%d.%02d\n", cents/100, cents%100) // 19.99
```

float64 не может точно представить большинство десятичных дробей, ошибки накапливаются при сложении тысяч платежей. Деньги хранят в копейках в `int64` или в десятичном типе (в Postgres `numeric`, в Go библиотеки вроде `shopspring/decimal`). Вопрос «почему нельзя хранить деньги во float» любят задавать на собесах.
:::

::: trap Затенение через := в блоке
```go
// плохо
var err error
if cond {
	v, err := find() // НОВАЯ err, видна только внутри if
	_ = v
	_ = err
}
fmt.Println(err) // <nil>: внешнюю err никто не трогал

// хорошо
var err error
var v int
if cond {
	v, err = find() // обычное присваивание во внешние переменные
}
```

`:=` внутри блока всегда создаёт новые переменные этого блока, если хотя бы одна слева новая в нём. Компилятор не жалуется, потому что внутренняя `err` использована. Стандартный `go vet` такое не ловит; ловит анализатор `shadow` из `golang.org/x/tools`, который можно включить в `golangci-lint`. Но надёжнее привычка: видишь `:=` во вложенном блоке рядом с одноимённой внешней переменной, остановись.
:::

## Что выведет программа?

```go
var x uint8 = 255
x++
fmt.Println(x)
```

<Predict :options="['256', '0', '255', 'паника: overflow']" :correct="1">

`uint8` хранит 0-255. 255 + 1 в восьми битах это `1 0000 0000`, девятый бит не помещается и отбрасывается, остаётся 0. Никакой паники, Go молча продолжает. Аналогично `var u uint = 0; u--` даёт 18446744073709551615.

</Predict>

```go
fmt.Println(7/2, -7/2, -7%3, 7%-3, 7.0/2)
```

<Predict :options="['3 -3 -1 1 3.5', '3 -4 2 1 3.5', '3.5 -3.5 -1 1 3.5', '3 -4 -1 -1 3.5']" :correct="0">

Целочисленное деление в Go **отбрасывает дробную часть к нулю**, а не округляет вниз: `-7/2` это `-3`, а не `-4` (как в Python). Знак остатка совпадает со знаком делимого: `-7%3 == -1`, `7%-3 == 1`. Всегда выполняется `(a/b)*b + a%b == a`. `7.0/2` это деление нетипизированной дробной константы, отсюда 3.5.

</Predict>

```go
var b uint8 = 200
fmt.Println(int8(b), int16(b))
```

<Predict :options="['-56 200', '200 200', '-56 -56', 'ошибка компиляции']" :correct="0">

Для `int8` биты `1100 1000` трактуются в дополнительном коде: `-128 + 72 = -56`. В `int16` всё помещается, старшие биты заполняются нулями, получается `200`. Ошибки компиляции нет: `b` переменная, компилятор не знает её значение. Будь там константа `int8(200)`, получили бы `overflows`.

</Predict>

```go
x := 1
{
	x := 2
	x++
}
x++
fmt.Println(x)
```

<Predict :options="['2', '3', '4', 'ошибка компиляции: x redeclared']" :correct="0">

Внутри `{ }` своя область видимости: `x := 2` объявляет новую переменную, которая затеняет внешнюю. `x++` внутри меняет внутреннюю. Снаружи внешняя `x` была 1, после `x++` стала 2. Ошибки нет: повторное объявление запрещено только в одной и той же области.

</Predict>

<details><summary>Какие нулевые значения у типов в Go и зачем они нужны?</summary>

Числа `0`, `bool` `false`, строка `""`, указатели, слайсы, мапы, каналы, функции и интерфейсы `nil`, массивы и структуры поэлементно нулевые. Переменная никогда не содержит мусор, это исключает класс ошибок. Хорошие типы проектируют так, чтобы нулевое значение было готово к работе: `sync.Mutex`, `bytes.Buffer`, `strings.Builder` не требуют конструктора. Тонкость: у nil-слайса можно брать `len` и делать `append`, а запись в nil-мапу паникует.

</details>
<details><summary>Чем типизированная константа отличается от нетипизированной?</summary>

Нетипизированная (`const a = 10`) не привязана к типу, хранится с высокой точностью (минимум 256 бит для целых) и подстраивается под контекст: одну и ту же `a` можно присвоить в `int8`, `float64`, `uint`. Если контекст не задаёт тип, берётся тип по умолчанию (`int`, `float64`, `rune`, `string`, `bool`). Типизированная (`const b int8 = 10`) ведёт себя как значение своего типа: её нельзя без конверсии присвоить в `int`, и выражения с ней проверяются на переполнение на этапе компиляции.

</details>
<details><summary>Что такое iota и какие у него подводные камни?</summary>

Счётчик внутри блока `const`, равный номеру строки (с нуля); строка без выражения повторяет предыдущее выражение с новым `iota`. Применяется для перечислений, битовых флагов (`1 << iota`), единиц (`1 << (10 * iota)`). Камни: вставка константы в середину сдвигает все следующие значения, что опасно, если значения сохраняются в БД или уходят по сети; `iota` растёт и в строках с `_` и с явными значениями; в новом блоке `const` начинается заново.

</details>
<details><summary>Какой размер у int? Когда брать int, а когда int64?</summary>

`int` равен размеру машинного слова: 64 бита на amd64/arm64, 32 бита на 32-битных платформах. Его используют для индексов, длин, счётчиков: на нём построены `len`, `cap`, индексация. Типы с явным размером берут, когда размер важен для формата данных: колонки БД (`BIGINT` в `int64`), бинарные протоколы, хеши, JSON-ID, которые должны совпадать между сервисами.

</details>
<details><summary>Что произойдёт при переполнении int в Go? А при делении на ноль?</summary>

Переполнение целых не паникует: значение заворачивается по правилам дополнительного кода (`var i8 int8 = 127; i8++` даёт `-128`), и это определённое спецификацией поведение. Деление целой переменной на ноль паникует (`integer divide by zero`), деление константы на ноль не компилируется. Float при делении на ноль даёт `±Inf` или `NaN`. Отдельный случай: для переменной `x == math.MinInt64` выражения `x / -1` и `-x` снова дают `x`, без паники. С константами всё иначе: константная арифметика точная, и `int8(127)+1` как константа это ошибка компиляции `overflows`. Ловить переполнение нужно руками или через `math/bits`.

</details>
<details><summary>Почему в Go нет неявных преобразований типов?</summary>

Неявные преобразования прячут потерю данных и изменение семантики: смешали `int32` и `int64`, и где-то обрезались старшие биты; сложили `int` с `float`, и непонятно, какая арифметика выполнилась. Go требует явного `T(x)`, чтобы такие места были видны в коде. Исключение по сути одно: нетипизированные константы, которые принимают тип по контексту, потому что компилятор проверяет их представимость.

</details>
<details><summary>Чем `type A int` отличается от `type A = int`?</summary>

Первое это определение нового типа: у `A` то же устройство, что у `int`, но это другой тип, без конверсии их не смешать, и к `A` можно добавлять методы. Второе это алиас: второе имя того же типа, полностью взаимозаменяемое. Метод, объявленный через алиас, добавляется к исходному типу, поэтому для `type A = int` его не объявить вовсе (`cannot define new methods on non-local type`): `int` не из твоего пакета. Встроенные `byte` и `rune` это алиасы `uint8` и `int32`.

</details>
<details><summary>Чем `var x int` отличается от `x := 0`?</summary>

Результат одинаковый: переменная `int` со значением 0. Различия в применимости: `:=` работает только внутри функций, требует значения и объявляет хотя бы одну новую переменную, остальные слева переприсваивает (если они в той же области). `var` работает и на уровне пакета, позволяет указать тип без значения. Опасность `:=` в затенении: во вложенном блоке он создаёт новую переменную с тем же именем.

</details>
