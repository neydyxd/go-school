# Массивы и слайсы

Слайс (`[]T`) это главная коллекция в Go. Через него ходят строки из базы, байты из сети, элементы JSON-массива, результаты фильтрации. В JavaScript ту же роль играет `Array`, но устроены они по-разному: массив в JS это объект, который сам растёт и всегда передаётся по ссылке. Слайс в Go это маленькая структура из трёх полей, которая **смотрит** в массив. Почти все сюрпризы со слайсами следуют из этой одной фразы.

На собеседовании по Go слайсы спрашивают почти всегда, причём не «что такое слайс», а задачей «что выведет программа» с `append` внутри функции. Ответить можно, только если держишь в голове картинку памяти: где заголовок, где массив, когда массив общий, а когда уже новый.

В этом уроке строим эту картинку с нуля: массивы, заголовок слайса, `len` и `cap`, рост при `append`, алиасинг, `copy`, полное выражение среза с тремя индексами, утечки памяти через подслайс и пакет `slices`.

## Массивы: фиксированный размер и семантика значения

Массив в Go это последовательность элементов **фиксированной длины**, и длина входит в тип: `[3]int` и `[4]int` это разные типы, присвоить одно другому нельзя.

```go
var a [3]int            // [0 0 0]: нулевое значение, память уже выделена
b := [3]int{1, 2, 3}
c := [...]string{"x", "y"} // длину посчитает компилятор: [2]string
fmt.Println(len(b), c)     // 3 [x y]
```

Главное свойство: массив это **значение**. Присваивание и передача в функцию копируют все элементы целиком, как копируется `int`.

```go
a := [3]int{1, 2, 3}
b := a
b[0] = 100
fmt.Println(a[0]) // 1
```

`b := a` скопировал все три элемента в новую переменную. `a` и `b` живут в разных местах памяти, поэтому `a[0]` остался `1`. Для сравнения: в JS `const b = a` для массива копирует ссылку, и изменение было бы видно через обе переменные.

Ещё массивы можно сравнивать через `==` (если сравним тип элемента) и использовать как ключи мапы. На практике массивы встречаются редко: в криптографии (`[32]byte` для хеша SHA-256), в фиксированных буферах и как «подложка» для слайсов. Почти везде ты работаешь со слайсами.

## Слайс: окно в массив

Слайс описывается **заголовком** из трёх полей. В рантайме он объявлен так (`runtime/slice.go`):

```go
type slice struct {
	array unsafe.Pointer // указатель на первый элемент окна
	len   int            // сколько элементов видно
	cap   int            // сколько элементов есть от начала окна до конца массива
}
```

На 64-битной машине заголовок занимает 24 байта (`unsafe.Sizeof` слайса любого типа даёт 24). Сами элементы лежат отдельно, в **базовом массиве** (backing array).

Аналогия: массив это длинная полка с книгами, а слайс это рамка, которую ты накладываешь на полку. В рамке видно `len` книг, а `cap` говорит, сколько места есть до конца полки, если рамку растянуть вправо.

```go
arr := [6]int{10, 20, 30, 40, 50, 60}
s := arr[1:4]
fmt.Println(s, len(s), cap(s)) // [20 30 40] 3 5
```

```text
arr:   [ 10 | 20 | 30 | 40 | 50 | 60 ]
index:   0    1    2    3    4    5
              ^              ^
              |              s видит до сюда (len = 3)
              s.array

s = { array: &arr[1], len: 3, cap: 5 }   // cap = 6 - 1: от arr[1] до конца
```

Выражение `a[low:high]` создаёт новый заголовок: указатель на `a[low]`, `len = high - low`, `cap = cap(a) - low`. **Элементы не копируются.** Поэтому запись через слайс видна в массиве:

```go
s[0] = 99
fmt.Println(arr) // [10 99 30 40 50 60]
```

### Создание слайсов

```go
var s1 []int              // nil-слайс: array = nil, len = 0, cap = 0
s2 := []int{}             // пустой, но не nil
s3 := []int{1, 2, 3}      // литерал: компилятор создаёт массив и слайс на него
s4 := make([]int, 3)      // [0 0 0], len 3, cap 3
s5 := make([]int, 0, 100) // [], len 0, cap 100: место под 100 элементов заранее
```

`make([]T, len, cap)` выделяет базовый массив на `cap` элементов, заполняет нулями и возвращает слайс на первые `len`.

::: trap make с длиной вместо ёмкости
Частая ошибка: хотели заранее выделить место, а получили нули в начале.

```go
// Плохо: len = 3, append пишет ПОСЛЕ трёх нулей
ids := make([]int, 3)
ids = append(ids, 1)
fmt.Println(ids) // [0 0 0 1]

// Хорошо: len = 0, cap = 3
ids := make([]int, 0, 3)
ids = append(ids, 1)
fmt.Println(ids) // [1]
```

Правило: если дальше будет `append`, задавай ёмкость третьим аргументом. Если будешь писать по индексу `ids[i] = ...`, задавай длину.
:::

### nil-слайс и пустой слайс

Для `len`, `cap`, `range` и `append` разницы между `nil` и `[]int{}` нет: оба ведут себя как пустой слайс, `append` к nil-слайсу работает. Отличие видно в двух местах:

```go
var n []int
e := []int{}
fmt.Println(n == nil, e == nil) // true false

a, _ := json.Marshal(n)
b, _ := json.Marshal(e)
fmt.Println(string(a), string(b)) // null []
```

Для API это важно: фронтенд, который ждёт массив, на `null` может упасть. Поэтому в ответах API пустой список часто явно делают `[]T{}`. Сравнивать слайс можно только с `nil`: `s1 == s2` для двух слайсов это ошибка компиляции. Для сравнения содержимого есть `slices.Equal`.

## append: как растёт слайс

`append(s, x...)` добавляет элементы в конец и **возвращает новый заголовок**. Результат обязательно присваивают обратно: `s = append(s, x)`. Внутри два сценария:

1. **Места хватает** (`len + n <= cap`): элементы пишутся в тот же базовый массив, возвращается заголовок с большим `len`. Аллокаций нет.
2. **Места не хватает**: рантайм выделяет новый массив побольше, копирует туда старые элементы, дописывает новые и возвращает заголовок на **новый** массив. Старый массив остаётся как был.

```go
s := make([]int, 0, 2)
s = append(s, 1)    // сценарий 1: len 1, cap 2
s = append(s, 2)    // сценарий 1: len 2, cap 2
s = append(s, 3)    // сценарий 2: новый массив, cap 4
```

```text
до третьего append:
  s ---> [ 1 | 2 ]               len 2, cap 2

после:
         [ 1 | 2 ]               старый массив (соберёт GC, если на него никто не смотрит)
  s ---> [ 1 | 2 | 3 | _ ]       новый массив, len 3, cap 4
```

Отсюда главное правило: **после `append` нельзя полагаться на то, что слайс смотрит в тот же массив, что и до него.** Иногда смотрит, иногда нет, и это зависит от `cap`.

::: hood Формула роста в рантайме
Новая ёмкость считается в функции `nextslicecap` (`runtime/slice.go`, Go 1.27):

```go
func nextslicecap(newLen, oldCap int) int {
	newcap := oldCap
	doublecap := newcap + newcap
	if newLen > doublecap { // добавляют сразу много: берём ровно сколько нужно
		return newLen
	}
	const threshold = 256
	if oldCap < threshold { // маленький слайс: удваиваем
		return doublecap
	}
	for { // большой: плавный переход от 2x к 1.25x
		newcap += (newcap + 3*threshold) >> 2
		if uint(newcap) >= uint(newLen) {
			break
		}
	}
	// ...
	return newcap
}
```

Это ещё не конец: `growslice` округляет размер в байтах **вверх до класса размера аллокатора** (size class). Аллокатор Go раздаёт память блоками фиксированных размеров (8, 16, 24, 32, 48, 64, 80... байт), и брать меньше блока бессмысленно. Пример для `[]int` (8 байт на элемент): из 512 формула даёт 512 + (512 + 768) / 4 = 832 элемента, это 6656 байт, ближайший класс 6784 байта, то есть **848** элементов.

Если отключить стековые оптимизации компилятора (о них ниже), рост `[]int` при добавлении по одному выглядит так:

```text
1 2 4 8 16 32 64 128 256 512 848 1280 1792 2560
```

До 256 удвоение, дальше шаги заметно меньше двух. Вывод для собеса: «удваивается до 256 элементов, потом растёт примерно в 1.25 раза с плавным переходом, и всё округляется до класса размера». Формула с порогом 256 появилась в Go 1.18, до этого порог был 1024 элемента.
:::

::: hood Почему у тебя числа могут не совпасть
Начиная с Go 1.25 компилятор умеет класть базовый массив слайса **на стек**, а в Go 1.26 таких случаев стало больше (см. release notes). Если слайс не «убегает» из функции, первый `append` может получить готовый 32-байтный буфер на стеке, и для `[]int` первая ёмкость окажется 4, а не 1. Проверено на Go 1.27.3: цикл `append` по одному в локальный слайс печатает `4 8 16 32...`. Отключить эти оптимизации можно флагом `-gcflags=all=-d=variablemakehash=n`. С ним компилятор печатает в stderr тысячи служебных строк `[DISABLED] [bisect-match ...]`, это нормально; чтобы не искать вывод программы среди них, добавь `2>/dev/null`.

Мораль: точное значение `cap` это деталь реализации. Код, который на неё опирается, сломается при обновлении Go.
:::

### Предвыделение

Если итоговый размер известен заранее, выдели его сразу. Это убирает лишние аллокации и копирования:

```go
// Плохо: log2(n) переаллокаций и копирований
var ids []int64
for _, u := range users {
	ids = append(ids, u.ID)
}

// Хорошо: одна аллокация
ids := make([]int64, 0, len(users))
for _, u := range users {
	ids = append(ids, u.ID)
}
```

Линтер `prealloc` и ревьюеры ловят именно этот паттерн.

## Алиасинг: два слайса, один массив

Алиасинг (aliasing) это ситуация, когда два слайса смотрят в один базовый массив. Запись через один видна через другой. Иногда это то, что нужно (функция сортирует переданный слайс на месте), иногда это баг.

```go
a := []int{1, 2, 3, 4}
b := a[:2]
b = append(b, 99)
fmt.Println(a)
```

<Predict :options="['[1 2 3 4]', '[1 2 99 4]', '[1 2 99]', 'паника']" :correct="1">

`b` это окно `[1 2]` с `cap` 4: справа в массиве ещё два элемента. `append` видит, что места хватает, и пишет `99` прямо в базовый массив на позицию 2, затирая `3`. `a` смотрит в тот же массив, поэтому печатает `[1 2 99 4]`.

```text
a ---> [ 1 | 2 | 3 | 4 ]       len 4, cap 4
b ---> [ 1 | 2 ]               len 2, cap 4 (тот же массив)

после b = append(b, 99):
a ---> [ 1 | 2 | 99 | 4 ]
b ---> [ 1 | 2 | 99 ]          len 3, cap 4
```

</Predict>

### Слайс в функции

Go всегда передаёт аргументы **по значению**. Для слайса копируется заголовок (24 байта), а не массив. Значит, функция:

- **может** менять существующие элементы: копия заголовка указывает на тот же массив;
- **не может** поменять `len` или указатель у вызывающего: у него свой заголовок.

```go
func addOne(s []int) {
	s = append(s, 1) // меняет только локальный заголовок
}

func zeroFirst(s []int) {
	s[0] = 0 // меняет общий массив
}

nums := []int{5, 6}
addOne(nums)
zeroFirst(nums)
fmt.Println(nums) // [0 6]
```

Поэтому функции, которые растят слайс, возвращают его (как сам `append`), а не меняют аргумент.

::: trap append в функции с запасом ёмкости
Самый коварный вариант: если у переданного слайса есть запас `cap`, функция с `append` запишет данные в общий массив, но вызывающий их «не увидит», потому что его `len` не изменился. А следующий `append` вызывающего молча их перетрёт.

```go
func collect(dst []string) {
	dst = append(dst, "секрет") // пишет в общий массив, если есть cap
}

buf := make([]string, 0, 10)
collect(buf)
fmt.Println(len(buf)) // 0, но в buf[:1] уже лежит "секрет"

// Хорошо: возвращай результат и присваивай его
func collect(dst []string) []string {
	return append(dst, "значение")
}
buf = collect(buf)
```
:::

### Две ветки от одного слайса

```go
base := make([]int, 3, 10)
p := append(base, 1)
q := append(base, 2)
fmt.Println(p[3], q[3])
```

<Predict :options="['1 2', '2 2', '1 1', 'паника: индекс за пределами']" :correct="1">

У `base` длина 3 и ёмкость 10. Первый `append` пишет `1` в ячейку 3 общего массива. Второй `append` снова начинает от `base` (у него по-прежнему `len` 3) и пишет `2` в **ту же** ячейку 3. `p` и `q` смотрят в один массив, поэтому оба печатают `2`.

Так ломаются функции, которые строят «варианты» от общего префикса, например генерация комбинаций в рекурсии. Лечится копированием или полным выражением среза (ниже).

</Predict>

## copy: явная копия

`copy(dst, src)` копирует `min(len(dst), len(src))` элементов и возвращает их число. Ёмкость не важна, важна длина `dst`:

```go
dst := make([]int, 2)
n := copy(dst, []int{7, 8, 9})
fmt.Println(n, dst) // 2 [7 8]

var empty []int
fmt.Println(copy(empty, []int{1})) // 0: в nil-слайс нечего копировать
```

`copy` корректно работает с перекрывающимися областями одного массива (как `memmove`), поэтому сдвиг элементов внутри слайса делают через него: `copy(s[i:], s[i+1:])` сдвигает хвост влево на одну позицию.

Три способа получить независимую копию:

```go
c1 := make([]int, len(s))
copy(c1, s)

c2 := append([]int(nil), s...) // идиома до появления пакета slices
c3 := slices.Clone(s)           // Go 1.21+, читается лучше всего
```

## Полное выражение среза: a[low:high:max]

Третий индекс ограничивает **ёмкость** результата: `cap = max - low`. Это защита от алиасинга через `append`: у слайса нет запаса, значит первый же `append` уйдёт в новый массив и не тронет соседей.

```go
a := []int{1, 2, 3, 4}
y := a[1:3:3]          // len 2, cap 2
y = append(y, 99)      // места нет: новый массив
fmt.Println(a, y, cap(y)) // [1 2 3 4] [2 3 99] 4
```

```text
a ---> [ 1 | 2 | 3 | 4 ]
y ---> [ 2 | 3 ]                    cap 2: правее рамку не растянуть

после append:
a ---> [ 1 | 2 | 3 | 4 ]            не тронут
y ---> [ 2 | 3 | 99 | _ ]           новый массив
```

Где пригождается: когда отдаёшь наружу часть своего буфера и не хочешь, чтобы чужой `append` его портил (задача про `Chunk` в домашке), и в задаче «две ветки от одного слайса» выше: `append(base[:len(base):len(base)], 1)`.

## Утечка памяти через подслайс

Пока жив хоть один слайс, который смотрит в массив, **весь** массив не может быть собран сборщиком мусора, даже если слайс видит три байта из ста мегабайт.

```go
var cache [][]byte

func remember(packet []byte) {
	cache = append(cache, packet[:10]) // держит весь packet
}
```

Проверено на Go 1.27.3: десять буферов по 10 МБ, от каждого в глобальном слайсе сохранено `big[:10]`. После `runtime.GC()` куча занимает около 100 МБ. Если вместо подслайса сохранять копию, куча после GC почти пустая.

```go
// Хорошо: копия держит только 10 байт
cache = append(cache, slices.Clone(packet[:10]))
```

::: trap Удаление элемента и висящие указатели
Похожая утечка случается со слайсами указателей. После «удаления» элемент остаётся в хвосте массива за пределами `len`, и GC считает его живым.

```go
// Плохо: последний элемент массива всё ещё ссылается на *User
users = append(users[:i], users[i+1:]...)

// Хорошо: slices.Delete с Go 1.22 зануляет освободившийся хвост
users = slices.Delete(users, i, i+1)
```

Ещё одна классическая ловушка с той же строкой: `append(s[:i], s[i+1:]...)` **меняет исходный массив**. Если у кого-то ещё был слайс на него, он увидит сдвинутые элементы.
:::

## range по слайсу

```go
for i, v := range s { ... } // i индекс, v КОПИЯ элемента
for i := range s { ... }    // только индекс
for _, v := range s { ... } // только значение
```

Два факта, которые проверяют на собесе:

1. `v` это копия. Запись в `v` не меняет слайс. Чтобы изменить элемент, пиши `s[i] = ...`. Особенно важно для слайса структур (подробнее в уроке про структуры).
2. Выражение справа от `range` вычисляется **один раз** до начала цикла. Длина зафиксирована. Задача на это есть в разделе «Что выведет программа?» ниже.

С Go 1.22 переменные цикла `i` и `v` создаются заново на каждой итерации, поэтому замыкания и горутины внутри цикла видят «свои» значения. Подробно это разобрано в уроке про управляющие конструкции.

## Пакет slices

С Go 1.21 в стандартной библиотеке есть дженерик-пакет `slices`. Раньше это писали руками в каждом проекте, сейчас за ручной цикл поиска на ревью попросят заменить на `slices.Contains`.

| Функция | Что делает |
|---|---|
| `slices.Contains(s, v)`, `slices.Index(s, v)` | поиск, `Index` возвращает -1, если нет |
| `slices.IndexFunc(s, f)`, `slices.ContainsFunc` | поиск по условию |
| `slices.Sort(s)`, `slices.SortFunc(s, cmp)` | сортировка на месте |
| `slices.SortStableFunc` | стабильная сортировка |
| `slices.BinarySearch(s, v)` | поиск в отсортированном |
| `slices.Equal(a, b)` | поэлементное сравнение |
| `slices.Clone(s)` | копия |
| `slices.Insert(s, i, v...)`, `slices.Delete(s, i, j)` | вставка и удаление, возвращают новый слайс |
| `slices.Compact(s)` | убрать соседние дубли |
| `slices.Reverse(s)` | развернуть на месте |
| `slices.Max(s)`, `slices.Min(s)` | максимум и минимум, паника на пустом |
| `slices.Concat(a, b, c)` | склейка (Go 1.22) |
| `slices.Repeat(s, n)` | повтор (Go 1.23) |
| `slices.Collect(it)`, `slices.Sorted(it)`, `slices.All(s)`, `slices.Chunk(s, n)` | работа с итераторами (Go 1.23) |

```go
s := []int{3, 1, 2, 2}
slices.Sort(s)
fmt.Println(s)                    // [1 2 2 3]
fmt.Println(slices.Contains(s, 2)) // true
s = slices.Compact(s)
fmt.Println(s)                    // [1 2 3]

t := []int{1, 2, 3, 4, 5}
u := slices.Delete(t, 1, 3)
fmt.Println(u, t) // [1 4 5] [1 4 5 0 0]
```

Последняя строка показывает важную деталь: `Delete`, `Compact` и похожие функции работают **на месте** и с Go 1.22 зануляют освободившиеся элементы. Старый слайс `t` после вызова использовать не надо, только результат.

Встроенная функция `clear(s)` (Go 1.21) зануляет все элементы слайса, длина не меняется: `clear([]int{1, 2, 3})` даёт `[0 0 0]`.

::: hood Как append вызывает рантайм
Компилятор разворачивает `s = append(s, x)` в код вида:

```go
if len(s)+1 > cap(s) {
	s = growslice(s.array, len(s)+1, cap(s), 1, typeOf(x))
}
s.array[len(s)] = x
s.len++
```

Быстрый путь (место есть) это одна проверка и запись, без вызова функций. Медленный путь `growslice` считает новую ёмкость, вызывает `mallocgc`, копирует старые элементы через `memmove` и возвращает новый заголовок. Поэтому `append` в цикле дёшев в среднем: дорогие переаллокации случаются всё реже по мере роста (амортизированно O(1)).
:::

## Двумерные слайсы

`[][]int` это слайс заголовков, каждый из которых смотрит в свой массив. Строки могут быть разной длины.

```go
grid := make([][]int, 3)
for i := range grid {
	grid[i] = make([]int, 4) // 3 отдельные аллокации под строки
}
```

Если матрица большая и прямоугольная, лучше выделить одно непрерывное хранилище и нарезать строки из него: меньше аллокаций и лучше для кеша процессора. Это задача со звёздочкой в домашке.

## Что выведет программа?

```go
s := []int{1, 2, 3}
for _, v := range s {
	s = append(s, v)
}
fmt.Println(len(s))
```

<Predict :options="['бесконечный цикл', '6', '3', 'паника']" :correct="1">

`range` запомнил исходный заголовок (длина 3) до первой итерации. Цикл делает ровно 3 итерации, каждая добавляет элемент, итого 6. В JS аналогичный `for...of` с `push` внутри действительно ушёл бы в бесконечный цикл, потому что итератор массива проверяет текущую длину.

</Predict>

```go
func modify(s []int) {
	s[0] = 100
	s = append(s, 4)
	s[1] = 200
}

func main() {
	s := []int{1, 2, 3}
	modify(s)
	fmt.Println(s)
}
```

<Predict :options="['[1 2 3]', '[100 2 3]', '[100 200 3]', '[100 200 3 4]']" :correct="1">

`s` создан литералом: `len` 3, `cap` 3. В `modify` копия заголовка сначала пишет `100` в общий массив, это видно снаружи. Затем `append`: места нет, поэтому локальный `s` теперь смотрит в **новый** массив. `s[1] = 200` пишет туда, внешний массив не меняется. Итог `[100 2 3]`.

Если бы исходный слайс был создан как `make([]int, 3, 10)`, `append` писал бы в общий массив, и ответ был бы `[100 200 3]`: длина снаружи осталась 3, но вторую ячейку функция перезаписала бы.

</Predict>

```go
a := []int{1, 2, 3, 4, 5}
b := a[1:3]
fmt.Println(len(b), cap(b))
b = b[:cap(b)]
fmt.Println(b)
```

<Predict :options="['2 4, затем [2 3 4 5]', '2 2, затем паника', '2 4, затем [2 3]', '3 4, затем [2 3 4 5]']" :correct="0">

`b = a[1:3]` имеет `len` 2 и `cap` 5 - 1 = 4. Слайс можно **растянуть вправо** до ёмкости: `b[:cap(b)]` видит элементы от `a[1]` до конца массива, `[2 3 4 5]`. Растянуть влево (к `a[0]`) нельзя никак. Так подслайс «видит» данные, которые ты, казалось бы, отрезал: ещё один довод отдавать наружу копию или слайс с тремя индексами.

</Predict>

```go
var s []int
for i := range 3 {
	s = append(s, i)
}
t := s[:2]
t = append(t, 100)
fmt.Println(s[2], len(s))
```

<Predict :options="['2 3', '100 3', '100 4', 'зависит от ёмкости, которую выделил рантайм']" :correct="3">

`t = s[:2]` и `append(t, 100)` пишет в общий массив, **если** у `t` есть запас ёмкости. Ёмкость `s` после трёх `append` это деталь реализации: классический рост даёт 4 (места хватает, ответ `100 3`), а если рантайм вдруг выделит ровно 3, ответ будет `2 3`. На Go 1.27.3 печатается `100 3`, но правильный ответ на собесе именно «зависит от ёмкости», с объяснением механизма. Код, где результат зависит от `cap`, это баг.

</Predict>

::: interview
<details><summary>Чем слайс отличается от массива?</summary>

Массив `[N]T` имеет фиксированную длину, которая входит в тип, и это значение: присваивание и передача в функцию копируют все элементы. Слайс `[]T` это заголовок из трёх полей (указатель на базовый массив, `len`, `cap`), который смотрит в массив. Копирование слайса копирует только заголовок, элементы остаются общими. Массивы сравнимы через `==`, слайсы сравниваются только с `nil`.

</details>
<details><summary>Что такое len и cap? Как они меняются при срезе a[i:j]?</summary>

`len` это число видимых элементов, `cap` это число элементов от начала окна до конца базового массива. Для `a[i:j]`: `len = j - i`, `cap = cap(a) - i`. Для `a[i:j:k]`: `cap = k - i`. Индексация разрешена до `len`, а срез можно растянуть вправо до `cap`.

</details>
<details><summary>Как работает append и как растёт ёмкость?</summary>

Если `len + n <= cap`, элементы пишутся в тот же массив, аллокаций нет. Иначе `growslice` выделяет новый массив, копирует элементы и возвращает заголовок на него. Новая ёмкость: если нужно больше удвоенной, берётся нужная; до 256 элементов удвоение; дальше рост с плавным переходом к 1.25x по формуле `newcap += (newcap + 768) / 4`. Затем размер округляется вверх до класса размера аллокатора, поэтому реальные числа бывают «некруглыми» (512 переходит в 848 для `[]int`). Опираться на конкретные значения нельзя.

</details>
<details><summary>Почему результат append надо присваивать обратно?</summary>

`append` возвращает новый заголовок: у него другой `len`, а при переаллокации и другой указатель. Старая переменная продолжает смотреть на прежнюю длину и, возможно, на старый массив. Компилятор даже ругается на `append(s, x)` без использования результата.

</details>
<details><summary>Функция получила слайс и сделала append. Увидит ли вызывающий новый элемент?</summary>

Нет: заголовок передан по значению, `len` у вызывающего не изменился. Но если у слайса был запас `cap`, элемент физически записан в общий массив и может перетереть данные вызывающего при его следующем `append`. Если запаса не было, функция работает уже с новым массивом, и даже изменения существующих элементов после `append` снаружи не видны. Правильный стиль: функция возвращает слайс.

</details>
<details><summary>Чем nil-слайс отличается от пустого?</summary>

У nil-слайса указатель `nil`, у пустого (`[]int{}`) указатель на «нулевой» массив. Для `len`, `cap`, `range`, `append` разницы нет. Разница в `s == nil` и в сериализации: `encoding/json` превращает nil-слайс в `null`, а пустой в `[]`. В API это важно, поэтому пустые списки в ответах часто делают явно `[]T{}`.

</details>
<details><summary>Что такое полное выражение среза и зачем оно?</summary>

`a[low:high:max]` дополнительно ограничивает ёмкость результата: `cap = max - low`. Если отдать наружу такой слайс с `cap == len`, любой `append` к нему создаст новый массив и не перезапишет соседние элементы исходного. Это способ безопасно отдать «окно» в свой буфер без копирования.

</details>
<details><summary>Как подслайс может привести к утечке памяти?</summary>

Подслайс держит указатель на базовый массив, и GC не может освободить массив целиком, пока жив хотя бы один такой слайс. Сохранив `big[:10]` от буфера в 10 МБ, ты держишь все 10 МБ. Решение: копировать нужную часть (`slices.Clone`, `copy`). Для слайсов указателей ещё надо занулять «удалённые» элементы в хвосте (`slices.Delete` делает это с Go 1.22), иначе они не будут собраны.

</details>
<details><summary>Как удалить элемент из слайса?</summary>

С сохранением порядка: `s = slices.Delete(s, i, i+1)` или вручную `s = append(s[:i], s[i+1:]...)`, оба варианта O(n) и меняют исходный массив. Без сохранения порядка за O(1): `s[i] = s[len(s)-1]; s = s[:len(s)-1]`. Для слайса указателей стоит занулить освободившийся последний элемент.

</details>
:::
