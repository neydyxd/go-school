# Управляющие конструкции и range

В Go мало управляющих конструкций: `if`, `for`, `switch`, `select` и `goto`. Нет `while`, нет `do-while`, нет тернарного оператора `a ? b : c`, нет `forEach`. Это сознательный минимализм: меньше способов написать одно и то же, проще читать чужой код. Зато у каждой конструкции есть особенности, которых нет в JavaScript: инструкция инициализации в `if`, `switch` без `break`, метки для выхода из вложенных циклов.

Главная тема урока для собеса: **`range` и переменная цикла**. До Go 1.22 переменная цикла была одна на весь цикл, и замыкания с горутинами ловили её последнее значение. Этот баг десять лет был вопросом номер один на собеседованиях. С 1.22 поведение изменили, и теперь спрашивают уже «что изменилось и почему». Ещё `range` научился ходить по числам (1.22) и по функциям-итераторам (1.23).

В бэкенд-коде всё это встречается постоянно: обработка ошибок через `if err := ...; err != nil`, разбор статусов через `switch`, обход строк из базы, итераторы по результатам запроса.

## if

```go
if x > 0 {
	fmt.Println("положительное")
} else if x < 0 {
	fmt.Println("отрицательное")
} else {
	fmt.Println("ноль")
}
```

Скобки вокруг условия не пишут, фигурные скобки обязательны всегда, даже для одной строки. Условие строго `bool`: `if n` для числа не скомпилируется, никаких «truthy»-значений, как в JS.

### Инструкция инициализации

Перед условием можно выполнить короткую инструкцию. Объявленные в ней переменные видны только внутри `if` и всех его `else`:

```go
if n, err := strconv.Atoi(s); err != nil {
	return fmt.Errorf("не число: %w", err)
} else if n < 0 {
	return errors.New("отрицательное")
} else {
	fmt.Println("ок:", n) // n видна и здесь
}
// здесь n и err уже не видны
```

Идиома Go: **обработай ошибку и выйди пораньше** (early return), а основной сценарий пусть идёт без отступа:

```go
// не по-гошному
if err == nil {
	// ... 30 строк основной логики
} else {
	return err
}

// по-гошному
if err != nil {
	return err
}
// ... основная логика без вложенности
```

## for: единственный цикл

Один `for` в трёх формах:

```go
// 1. Классическая: init; условие; post
for i := 0; i < 3; i++ {
	fmt.Print(i)
}

// 2. Только условие: это и есть while
for n > 1 {
	n /= 2
}

// 3. Без всего: бесконечный цикл, выход через break или return
for {
	line, err := r.ReadString('\n')
	if err != nil {
		break
	}
	process(line)
}
```

`break` выходит из ближайшего цикла (или `switch`/`select`), `continue` переходит к следующей итерации. В классической форме при `continue` выполняется `post` (`i++`).

Бесконечный `for {}` в бэкенде обычное дело: так пишут воркеры, читающие задачи из очереди, и серверные циклы accept.

## switch

```go
switch status {
case 200, 201, 204:
	fmt.Println("успех")
case 404:
	fmt.Println("не найдено")
default:
	fmt.Println("что-то другое")
}
```

Отличия от C и JavaScript:

- **`break` не нужен**: выполняется только совпавший `case`, проваливания в следующий нет.
- В одном `case` можно перечислить несколько значений через запятую.
- Значения в `case` не обязаны быть константами: можно `case f(x):`.
- `case` проверяются **сверху вниз**, выполняется первый подходящий.
- Как и у `if`, есть инструкция инициализации: `switch x := f(); x { ... }`.

### switch без выражения

Самая полезная форма: `switch` без значения равен `switch true`, и каждый `case` это условие. Цепочка `if-else if` становится плоской:

```go
switch {
case score >= 90:
	grade = "отлично"
case score >= 75:
	grade = "хорошо"
default:
	grade = "так себе"
}
```

### fallthrough

Если нужно провалиться в следующий `case`, это пишут явно словом `fallthrough`. Оно передаёт управление в тело следующего `case` **без проверки его условия**. Используется редко; в ревью кода `fallthrough` обычно повод присмотреться.

Как именно `fallthrough` выбирает, куда перейти, проверь на задачке в разделе «Что выведет программа?».

Про `switch` по типам (`switch v := x.(type)`) поговорим в модуле про интерфейсы.

## Метки, break и continue с меткой

`break` внутри `switch` или `select` выходит **из них**, а не из окружающего цикла. Чтобы выйти из цикла, нужна метка:

```go
for i := 0; i < 3; i++ {
	switch i {
	case 1:
		break // выходит только из switch
	}
	fmt.Print(i)
}
```

<Predict :options="['012', '0', '02', '01']" :correct="0">

`break` в `case 1` завершает `switch`, а не `for`. После `switch` выполнение продолжается с `fmt.Print(i)`, поэтому печатаются все три числа. Чтобы выйти из цикла, нужна метка: `loop: for ... { switch { case ...: break loop } }`.

</Predict>

Метка ставится перед циклом и используется в `break` или `continue`:

```go
outer:
	for i := range 3 {
		for j := range 3 {
			if j == 2 {
				continue outer // к следующему i
			}
			if i == 2 {
				break outer // выход из обоих циклов
			}
			fmt.Print(i, j, " ")
		}
	}
// 0 0 0 1 1 0 1 1
```

Метки нужны в двух местах: выход из вложенных циклов (поиск в матрице) и выход из цикла с `switch`/`select` внутри (типичный воркер: `for { select { case <-ctx.Done(): break loop } }`). Неиспользуемая метка, как и переменная, это ошибка компиляции.

Есть и `goto` с меткой. Он существует, в стандартной библиотеке встречается в сгенерированном и низкоуровневом коде, но в прикладном коде им не пользуются. Компилятор не даёт прыгать через объявления переменных и внутрь блоков.

## range

`range` перебирает коллекции. Что выдаёт на каждой итерации:

| Что перебираем | Первое значение | Второе значение |
|---|---|---|
| массив, указатель на массив, слайс | индекс `int` | копия элемента |
| строка | индекс **байта**, где начинается символ | `rune` (символ) |
| мапа | ключ | значение (порядок не определён) |
| канал | элемент (до закрытия канала) | нет |
| целое `n` (с 1.22) | `0 ... n-1` | нет |
| функция-итератор (с 1.23) | то, что передано в `yield` | второе значение, если итератор `Seq2` |

```go
for i, v := range []string{"a", "b"} { ... } // индекс и значение
for i := range s { ... }                      // только индекс
for _, v := range s { ... }                   // только значение
for range s { ... }                           // ни того, ни другого
```

### Строки: по символам, а не байтам

```go
for i, r := range "héllo" {
	fmt.Print(i, ":", string(r), " ")
}
// 0:h 1:é 3:l 4:l 5:o
```

`é` занимает в UTF-8 два байта, поэтому индекс прыгает с 1 на 3. `range` по строке декодирует UTF-8 и выдаёт руны, а `s[i]` выдаёт байты. Подробно в уроке про строки.

### Мапы: порядок случайный

Порядок обхода мапы не определён спецификацией, и рантайм специально его рандомизирует, чтобы никто на него не полагался. Нужен порядок: собери ключи, отсортируй, обходи по ним. Подробно в уроке про мапы.

### range по числу (Go 1.22)

```go
for i := range 3 {
	fmt.Print(i) // 012
}
for range 5 {
	retry() // просто пять раз
}
```

Если `n <= 0`, цикл не выполнится ни разу. Тип `i` совпадает с типом `n`: `for i := range uint8(3)` даст `i` типа `uint8`, а для нетипизированной константы будет `int`.

### range вычисляет выражение один раз

Выражение справа от `range` вычисляется **один раз до начала цикла**. Для слайса это значит, что длина зафиксирована: append внутри цикла не делает его бесконечным.

```go
s := []int{1, 2, 3}
for i := range s {
	s = append(s, i)
}
fmt.Println(len(s)) // 6, а не бесконечный цикл
```

Для **массива** (не слайса) `range` с переменной значения работает с **копией массива**: массив в Go это значение, а не ссылка. Изменения внутри цикла не видны:

```go
a := [3]int{1, 2, 3}
for _, v := range a {
	a[2] = 100
	fmt.Print(v, " ")
}
```

<Predict :options="['1 2 3', '1 2 100', '100 100 100', 'ошибка компиляции']" :correct="0">

Перед циклом `a` вычисляется и копируется целиком, `v` берётся из копии. Запись `a[2] = 100` меняет оригинал, но цикл его не видит: `1 2 3`. Если перебирать `&a` или слайс `a[:]`, увидишь `1 2 100`: слайс ссылается на те же данные, копируется только его заголовок. Разница массивов и слайсов будет в уроке про слайсы.

</Predict>

### Переменная цикла: одна на итерацию с Go 1.22

Это главный вопрос урока. Сравни:

```go
var fs []func()
for i := 0; i < 3; i++ {
	fs = append(fs, func() { fmt.Print(i) })
}
for _, f := range fs {
	f()
}
```

- В модуле с `go 1.22` и новее в `go.mod` печатается **`012`**.
- В модуле с `go 1.21` и старше печатается **`333`**.

Раньше переменная `i` создавалась **один раз** на весь цикл и перезаписывалась на каждой итерации. Все три замыкания захватывали одну и ту же переменную и после цикла видели её последнее значение 3. То же с горутинами и с `&v` из `range`: все указатели вели на одну переменную.

С Go 1.22 **каждая итерация получает свою переменную**. В классическом цикле новая переменная на очередной итерации инициализируется значением предыдущей перед выполнением `i++`, поэтому семантика счётчика не меняется.

Важная деталь: поведение определяет **версия `go` в `go.mod` модуля**, где лежит код, а не версия установленного тулчейна. Старый модуль с `go 1.21`, собранный новым Go 1.27, сохраняет старую семантику (это проверено: та же программа печатает `333`). Так Go не ломает старый код при обновлении.

::: hood Сколько стоит переменная на итерацию
Кажется, что «новая переменная на каждой итерации» должна быть дорогой. На деле нет. Разница видна только тогда, когда адрес переменной или замыкание с ней переживают итерацию: тогда escape analysis отправляет переменную в кучу, по одной на итерацию. Если адрес берут, но он не покидает тело (`p := &i; sum += *p`), или замыкание вызывается тут же, переменная остаётся на стеке или в регистре, как и раньше.

```
до 1.22:  [ i ] <- все замыкания смотрят сюда, в конце i == 3

с 1.22:   итерация 0: [ i=0 ] <- замыкание 0
          итерация 1: [ i=1 ] <- замыкание 1   (копия i перед i++)
          итерация 2: [ i=2 ] <- замыкание 2
```

Перед релизом команда Go включила новую семантику во всех сборках внутри Google: за четыре месяца ни одной проблемы в продакшн-коде, зато нашлось много тестов, которые из-за старой семантики проверяли совсем не то, что думали авторы. Подробности в посте «Fixing For Loops in Go 1.22» из источников.
:::

::: trap Старый приём v := v
В коде до 1.22 ты встретишь «странную» строку:

```go
for _, v := range items {
	v := v // копия на итерацию, нужна была до Go 1.22
	go func() { process(v) }()
}
```

В модулях на `go 1.22+` она не нужна, можно удалять: `go fix` (обновлённый в Go 1.26) убирает её сам, проверено на 1.27. Но на собесе спросят, зачем она была, и тут важно ответить про общую переменную цикла. Обратная ловушка: если поддерживаешь модуль с `go 1.21` в `go.mod`, новый тулчейн тебя не спасёт, старое поведение остаётся.
:::

::: trap Значение из range это копия
```go
type User struct {
	Name   string
	Active bool
}

// плохо: меняем копию, слайс не изменится
for _, u := range users {
	u.Active = true
}

// хорошо: обращаемся к элементу по индексу
for i := range users {
	users[i].Active = true
}
```

`v` в `for _, v := range s` это копия элемента. Для структур это частая ошибка, а для больших структур ещё и лишнее копирование. Указатели на элементы (`&users[i]`) разберём в уроке про указатели.
:::

### range по функциям (Go 1.23)

С Go 1.23 `range` умеет ходить по **функциям-итераторам**. Итератор это функция, которая принимает `yield` и вызывает его для каждого элемента:

```go
import "iter"

// iter.Seq[V] это func(yield func(V) bool)
func Count(n int) iter.Seq[int] {
	return func(yield func(int) bool) {
		for i := range n {
			if !yield(i) { // false значит: тело цикла сделало break
				return
			}
		}
	}
}

for v := range Count(10) {
	if v == 3 {
		break
	}
	fmt.Print(v) // 012
}
```

Есть три формы: `func(yield func() bool)`, `func(yield func(V) bool)` (`iter.Seq[V]`) и `func(yield func(K, V) bool)` (`iter.Seq2[K, V]`). В стандартной библиотеке ими уже пользуются: `slices.All`, `slices.Values`, `maps.Keys`, `strings.Lines` (1.24) возвращают итераторы.

Зачем это бэкендеру: обойти большую выборку, дерево или поток событий тем же `for range`, не собирая всё в слайс и не изобретая свой интерфейс `Next()`.

::: hood Как range по функции превращается в обычный код
Компилятор переписывает тело цикла в функцию и передаёт её в итератор как `yield`:

```
for v := range seq {        seq(func(v int) bool {
	if v == 3 {                 if v == 3 {
		break          ==>          return false   // break
	}                           }
	fmt.Print(v)                fmt.Print(v)
}                               return true        // следующая итерация
                            })
```

`continue` превращается в `return true`, `break` в `return false`. `return` из внешней функции и `goto` наружу тоже работают: компилятор запоминает, что надо сделать после выхода из итератора.

Если итератор проигнорирует `false` и вызовет `yield` снова, рантайм упадёт с паникой `range function continued iteration after function for loop body returned false`. Поэтому в итераторе всегда пиши `if !yield(v) { return }`.
:::

## Что выведет программа?

```go
switch x := 1; x {
case 1:
	fmt.Print("a")
	fallthrough
case 2:
	fmt.Print("b")
case 3:
	fmt.Print("c")
}
```

<Predict :options="['a', 'ab', 'abc', 'ошибка компиляции']" :correct="1">

`case 1` совпал, печатается `a`. `fallthrough` безусловно переходит в тело `case 2`, хотя `x` не равен 2: печатается `b`. В `case 2` своего `fallthrough` нет, поэтому до `c` дело не доходит. Итог: `ab`.

</Predict>

```go
for i := range 3 {
	defer fmt.Print(i)
}
```

<Predict :options="['012', '210', '333', '222']" :correct="1">

`defer` откладывает вызов до выхода из функции, а аргумент `i` вычисляется сразу при `defer`. Отложенные вызовы выполняются в обратном порядке (стек): `210`. Подробно про `defer` в следующем уроке.

</Predict>

```go
s := []int{1, 2, 3}
for i := range s {
	s = append(s, i)
}
fmt.Println(len(s))
```

<Predict :options="['3', '6', 'бесконечный цикл', 'паника: index out of range']" :correct="1">

`range` вычисляет `s` один раз до начала цикла и делает ровно 3 итерации, сколько было элементов вначале. Каждая добавляет элемент, итого 6. В JavaScript `for...of` по растущему массиву ведёт себя иначе, это частая ловушка при переходе.

</Predict>

```go
var ps []*int
for _, v := range []int{1, 2, 3} {
	ps = append(ps, &v)
}
for _, p := range ps {
	fmt.Print(*p)
}
```

<Predict :options="['123', '333', '111', 'зависит от go в go.mod']" :correct="3">

В модуле с `go 1.22` и новее у каждой итерации своя `v`, указатели разные: `123`. В модуле с `go 1.21` и старше `v` одна на весь цикл, все указатели смотрят на неё, и после цикла там 3: `333`. Обе версии проверены запуском. На собесе правильный ответ: «с 1.22 будет 123, раньше было 333, и решает версия в go.mod».

</Predict>

::: interview
<details><summary>Какие циклы есть в Go?</summary>

Только `for`, в трёх формах: классическая `for init; cond; post`, с одним условием (аналог `while`) и бесконечная `for {}`. Плюс `for ... range` для перебора слайсов, массивов, строк, мап, каналов, целых чисел (1.22) и функций-итераторов (1.23). `do-while` нет, его делают через `for { ...; if !cond { break } }`.

</details>
<details><summary>Что изменилось в переменной цикла в Go 1.22 и почему?</summary>

До 1.22 переменная, объявленная в `for` (и в классическом цикле, и в `range`), была одна на весь цикл. Замыкания, горутины и указатели `&v` разделяли её и видели последнее значение. Это был самый частый баг Go, приходилось писать `v := v`. С 1.22 каждая итерация получает свою переменную; в классическом цикле она копируется из предыдущей перед `post`. Включается по версии `go` в `go.mod` модуля, а не по версии тулчейна: старые модули сохраняют старое поведение. Компилятор выделяет отдельную переменную только если её адрес или замыкание переживают итерацию, так что обычные циклы не дорожают.

</details>
<details><summary>Чем switch в Go отличается от switch в C или JavaScript?</summary>

Нет проваливания по умолчанию, `break` писать не нужно; провалиться можно явно через `fallthrough`, и он переходит в следующий `case` без проверки условия. В одном `case` может быть список значений. Значения не обязаны быть константами. Есть `switch` без выражения, заменяющий цепочку `if-else`, инструкция инициализации и отдельный type switch для интерфейсов.

</details>
<details><summary>Что делает break внутри switch, который стоит в цикле?</summary>

Выходит из `switch`, а не из цикла. То же для `select`. Чтобы выйти из цикла, ставят метку перед `for` и пишут `break label`. Это частая ошибка в воркерах вида `for { select { case <-done: break } }`: цикл после этого продолжает крутиться.

</details>
<details><summary>Что выдаёт range по строке?</summary>

Индекс первого байта символа и сам символ типа `rune`, декодированный из UTF-8. Индексы идут не подряд, если в строке многобайтовые символы (кириллица занимает 2 байта). Невалидный UTF-8 даёт руну `U+FFFD` и сдвиг на один байт. Обычная индексация `s[i]` и `len(s)` работают с байтами.

</details>
<details><summary>Как работает range по функции и что будет, если итератор не проверит результат yield?</summary>

Итератор это функция вида `func(yield func(V) bool)`. Компилятор превращает тело цикла в функцию `yield`: `continue` становится `return true`, `break` и выход из цикла `return false`. Итератор обязан прекратить вызывать `yield` после `false`. Если он продолжит, рантайм паникует: `range function continued iteration after function for loop body returned false`. Типы `iter.Seq` и `iter.Seq2` описаны в пакете `iter`, стабильно с Go 1.23.

</details>
<details><summary>Можно ли менять слайс во время range? Что будет?</summary>

Можно, но надо понимать механику. Выражение `range` вычисляется один раз, число итераций по слайсу фиксируется по исходной длине, поэтому `append` не делает цикл бесконечным, а новые элементы не перебираются. Изменения существующих элементов по индексу видны, если слайс ссылается на тот же массив. Для массива (не слайса) с переменной значения перебирается копия, изменения не видны. Удалять элементы во время перебора по индексу опасно: индексы сдвигаются.

</details>
<details><summary>Зачем в старом коде пишут v := v внутри цикла?</summary>

До Go 1.22 переменная цикла была общей для всех итераций. `v := v` создавало копию на итерацию, чтобы горутина или замыкание захватили своё значение. В модулях с `go 1.22+` это не нужно, строку удаляет `go fix`. Но её стоит узнавать в легаси-коде и объяснять на собесе.

</details>
:::
