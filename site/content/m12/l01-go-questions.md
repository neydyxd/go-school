# Банк вопросов по Go

Ты прошёл весь маршрут, и в каждом уроке был блок «На собесе спросят». Вместе это больше шестисот вопросов с разобранными ответами: от нулевых значений до планировщика, от `JOIN` до gRPC. Проблема в том, что прочитанный когда-то ответ на собесе не всплывает. Всплывает то, что ты много раз доставал из памяти сам, вслух и без подсказки.

Поэтому этот урок не про новую теорию, а про тренажёр. Ниже карточки: все вопросы курса в одной колоде, с фильтром по модулям и отметками «знаю / повторить». Дальше разберём, как готовиться так, чтобы знания держались неделями, по каким темам реально гоняют на собесе Go-джуна, и добавим к банку сорок вопросов, которых в уроках не было: про инструменты, свежие версии языка и детали, на которых любят ловить.

Работа бэкендера на собесе проверяется не тем, сколько ты знаешь, а тем, как ты объясняешь: коротко, с механизмом и примером. Карточки тренируют именно это.

## Карточки

<Flashcards />

Как пользоваться:

- **Фильтр по модулям.** Без выбора в колоде все вопросы. Нажми на модули, которые сейчас повторяешь: колода пересоберётся и перемешается.
- **Сначала ответь сам.** Вслух, своими словами, хотя бы 20-30 секунд. Только потом открывай ответ (пробел или кнопка).
- **Честная отметка.** «Знаю» ставь, если ответил по сути и с механизмом, а не «примерно помню, о чём это». Иначе «повторить» (стрелка влево).
- **Режим «только повторить».** Колода из карточек, которые ты пометил «повторить». С него начинай каждую следующую сессию.
- **Ссылка «к уроку».** Если ответ не понятен, а не просто забыт, иди в урок и перечитай раздел. Карточка не заменяет объяснение.

Отметки хранятся в браузере (`localStorage`, ключ `go-school:cards`), отдельно от прогресса уроков. Новые вопросы в уроках попадают в колоду сами при следующей сборке сайта.

## Как готовиться

### Вспоминать, а не перечитывать

Перечитывание создаёт иллюзию знания: текст кажется знакомым, и мозг путает узнавание с умением воспроизвести. На собесе узнавать нечего, есть только вопрос и тишина. Поэтому единица тренировки это **попытка вспомнить** (retrieval practice): закрыл ответ, сформулировал, сверился. Ошибка при попытке полезнее, чем гладкое перечитывание, потому что после неё правильный ответ запоминается прочнее.

### Интервальное повторение

Забывание идёт по кривой: сразу после изучения быстро, потом медленнее. Каждое успешное вспоминание «выпрямляет» кривую, и следующий повтор можно отложить дольше. Отсюда схема, которую реализуют Anki и коробки Лейтнера: то, что знаешь, показывать реже, то, что путаешь, чаще.

С нашими карточками это выглядит так:

| День | Что делать |
|---|---|
| Каждый день, 20-30 минут | Режим «только повторить» до пустой колоды, потом 20-30 новых карточек одного-двух модулей |
| Раз в неделю | Весь модуль целиком, включая «знаю»: проверка, что знание не выветрилось |
| За 3-5 дней до собеса | Темы из карты ниже по приоритету «спросят почти точно» |
| Накануне | Только «повторить» и свои ответы на поведенческие вопросы из [урока про резюме](./l04-resume-interview) |

Не пытайся пройти 600 карточек за выходные. 30 карточек в день в течение месяца дают больше, чем марафон: интервалы между повторами и есть механизм запоминания.

### Проговаривать вслух

Мысленный ответ всегда кажется связным. Вслух вылезают дыры: «ну, там слайс, он, это, ссылается на массив». Отвечай вслух, а лучше запиши себя на телефон и послушай. Хороший ответ на технический вопрос собирается по одной схеме:

1. **Определение в одну фразу.** «Слайс это дескриптор из трёх полей: указатель на массив, длина и ёмкость».
2. **Механизм.** Как это работает внутри и почему так сделано.
3. **Пример.** Пара строк кода или ситуация из практики.
4. **Грабли.** Где на этом ошибаются. Это показывает, что ты писал код, а не читал статью.
5. **Когда применять.** Или когда не применять.

Укладывайся в минуту-полторы. Интервьюер сам попросит подробностей, если ему интересно; длинный монолог без пауз съедает время собеса и выглядит как заученный текст.

## Грабли, на которых ловят

Дополнительные вопросы ниже в основном про детали языка и инструментов. Два примера, которые встречаются в задачах «найди баг».

::: trap Затенение err
`:=` внутри блока создаёт **новую** переменную, даже если снаружи уже есть одноимённая. Внешняя `err` остаётся `nil`, и ошибка теряется молча. `go vet` по умолчанию это не ловит: анализатор `shadow` нужно подключать отдельно (например, через golangci-lint).

```go
// плохо: ошибка find потерялась
var err error
if cond {
	_, err := find() // новая err, видна только внутри if
	_ = err
}
fmt.Println(err) // <nil>

// хорошо: присваивание, а не объявление
var err error
if cond {
	_, err = find()
}
```
:::

::: trap Рекурсивный String
`fmt` при печати значения с методом `String()` вызывает этот метод. Если внутри `String()` снова печатать само значение через `%v`, получится бесконечная рекурсия и падение с `fatal error: stack overflow`. `go vet` такое видит и пишет, что `fmt.Sprintf` с аргументом `s` вызывает рекурсивный вызов метода `String` (в сообщении `causes recursive (пакет.S).String method call`).

```go
// плохо
func (s S) String() string { return fmt.Sprintf("%v", s) }

// хорошо: печатать поля, а не само значение
func (s S) String() string { return fmt.Sprintf("S(%d)", s.n) }

// или через тип без методов, если нужен формат по умолчанию
func (s S) String() string {
	type plain S
	return fmt.Sprintf("%v", plain(s))
}
```
:::

## Что выведет программа?

```go
type T struct{ n int }

func (t *T) String() string { return fmt.Sprintf("T(%d)", t.n) }

func main() {
	v := T{1}
	fmt.Println(v, &v)
}
```

<Predict :options="['T(1) T(1)', '{1} T(1)', '{1} &{1}', 'ошибка компиляции']" :correct="1">

Метод `String` объявлен на `*T`, поэтому `T` (значение) не реализует `fmt.Stringer`: в его method set этого метода нет. `fmt` печатает значение по умолчанию: `{1}`. Указатель `&v` интерфейс реализует, и для него вызывается `String`.

</Predict>

```go
type C struct{ n int }

func (c C) Get() int { return c.n }

func main() {
	c := C{1}
	get := c.Get
	c.n = 2
	fmt.Println(get(), c.Get())
}
```

<Predict :options="['2 2', '1 2', '1 1', 'ошибка компиляции']" :correct="1">

`c.Get` без скобок это **method value**: функция, к которой уже привязан получатель. Для value receiver получатель копируется в момент вычисления выражения `c.Get`, то есть когда `n` ещё 1. Дальнейшее изменение `c` на копию не влияет. Будь получатель указателем, скопировался бы указатель, и `get()` вернул бы 2.

</Predict>

```go
s := []int{1, 2, 3}
clear(s)
fmt.Println(s, len(s))
```

<Predict :options="['[] 0', '[0 0 0] 3', '[] 3', 'nil 0']" :correct="1">

Встроенная `clear` (Go 1.21) для слайса обнуляет элементы, но не меняет длину. Для мапы она удаляет все ключи: `len` станет 0.

</Predict>

```go
items := []C{{1}, {2}}
for _, it := range items {
	it.n *= 10
}
fmt.Println(items)
```

<Predict :options="['[{10} {20}]', '[{1} {2}]', '[{10} {2}]', 'ошибка компиляции']" :correct="1">

`it` это копия элемента. Меняется копия, слайс остаётся прежним. Чтобы изменить элементы, обращайся по индексу: `for i := range items { items[i].n *= 10 }`.

</Predict>

## Дополнительные вопросы

Этих вопросов нет в уроках курса: они закрывают инструменты, свежие версии Go и детали, которые всплывают на собесах middle-уровня. Они тоже попадают в карточки.

::: interview
<details><summary>Почему в Go нет исключений? Что в этом хорошего и плохого?</summary>

Ошибка в Go это обычное значение, которое функция возвращает последним результатом. Авторы языка сознательно отказались от исключений: с ними поток управления становится невидимым, любая строка может «выпрыгнуть» из функции, и по коду не видно, какие ошибки где возможны. В Go путь ошибки виден в тексте: `if err != nil` стоит ровно там, где ошибка обрабатывается.

Плюсы: явность, ошибку легко обернуть контекстом (`fmt.Errorf("load user %d: %w", id, err)`), нет скрытой стоимости раскрутки стека. Минусы: многословность и риск забыть проверку (тут помогают линтеры, например `errcheck`). Для действительно невосстановимых ситуаций остаются `panic` и `recover`, но это не замена исключениям для обычных ошибок.

</details>
<details><summary>Что такое затенение (shadowing) переменных и чем оно опасно?</summary>

Объявление во внутренней области видимости с тем же именем, что и во внешней, создаёт новую переменную, которая «заслоняет» внешнюю. Чаще всего это `err`: внутри `if` или `for` пишут `x, err := f()`, и внешняя `err` остаётся `nil`. Ошибка теряется без единого предупреждения компилятора.

Стандартный `go vet` это не проверяет: анализатор `shadow` живёт отдельно (`golang.org/x/tools/go/analysis/passes/shadow`) и включается в golangci-lint. Лекарство: внутри блоков присваивать (`=`), а не объявлять (`:=`), если переменная уже есть снаружи, и не плодить длинные функции, где за затенением трудно уследить.

</details>
<details><summary>Почему defer внутри цикла считают ошибкой?</summary>

`defer` выполняется при выходе из **функции**, а не из итерации цикла. Если в цикле по тысяче файлов писать `f, _ := os.Open(p); defer f.Close()`, все тысяча файлов останутся открытыми до конца функции: можно упереться в лимит дескрипторов. Кроме того, отложенные вызовы копятся в памяти.

Решение: вынести тело итерации в отдельную функцию (или замыкание), тогда `defer` сработает в конце каждой итерации:

```go
for _, p := range paths {
	if err := processFile(p); err != nil { // внутри processFile есть defer f.Close()
		return err
	}
}
```

</details>
<details><summary>Как правильно закрыть файл, в который ты писал?</summary>

Для файла, открытого на запись, ошибка `Close` значима: данные могли осесть в буферах ОС, и именно `Close` сообщает, что запись на диск не удалась (особенно на сетевых файловых системах). `defer f.Close()` молча выбрасывает эту ошибку.

Идиома: отложить закрытие с проверкой и не потерять первую ошибку.

```go
func write(path string, data []byte) (err error) {
	f, err := os.Create(path)
	if err != nil {
		return err
	}
	defer func() {
		if cerr := f.Close(); cerr != nil && err == nil {
			err = cerr
		}
	}()
	_, err = f.Write(data)
	return err
}
```

Для файлов только на чтение обычного `defer f.Close()` достаточно. Если важна гарантия записи на диск, перед `Close` вызывают `f.Sync()`.

</details>
<details><summary>Что такое method value и method expression?</summary>

**Method value** `x.M` это функция с уже привязанным получателем: `get := c.Get`, потом `get()`. Получатель вычисляется и (для value receiver) копируется в момент создания method value, поэтому позднейшие изменения `c` не видны. Удобно передавать как колбэк: `http.HandleFunc("/", srv.handleIndex)`.

**Method expression** `T.M` это обычная функция, у которой получатель стал первым параметром: `f := C.Get; f(C{7})` вернёт 7. Для методов на указателе пишут `(*T).M`. Используют редко, например чтобы выбрать метод из таблицы.

</details>
<details><summary>Почему fmt.Println(v) не вызывает String, если он объявлен на указателе?</summary>

`fmt` проверяет, реализует ли переданное значение интерфейс `fmt.Stringer`. Method set значения `T` содержит только методы с value receiver, а `String` объявлен на `*T`. Значит, `T` не `Stringer`, и `fmt` печатает поля по умолчанию: `{1}`. Указатель `&v` интерфейс реализует, и для него вызовется `String`.

Отсюда правило: `String()` обычно объявляют на значении, чтобы он работал и для `T`, и для `*T` (method set указателя включает методы значения). Исключение: тип, который нельзя копировать (с мьютексом внутри).

</details>
<details><summary>Почему String(), который печатает сам себя через %v, роняет программу?</summary>

Внутри `func (s S) String() string { return fmt.Sprintf("%v", s) }` `fmt` видит, что `s` реализует `Stringer`, и вызывает `s.String()`, который снова вызывает `Sprintf`, и так бесконечно. Стек горутины растёт до предела (по умолчанию 1 ГБ на 64-битных системах), и программа падает с `fatal error: stack overflow`. Это не паника, `recover` её не поймает.

`go vet` предупреждает о рекурсивном вызове `String` (`... causes recursive (пакет.S).String method call`). Решение: печатать поля явно или конвертировать в локальный тип без методов: `type plain S; fmt.Sprintf("%v", plain(s))`.

</details>
<details><summary>Что вернёт string(65) и почему vet на это ругается?</summary>

Вернёт `"A"`, а не `"65"`: преобразование целого в строку трактует число как код символа Unicode. Это частая ошибка у тех, кто пришёл из JavaScript. `go vet` (а значит и `go test`, который запускает часть проверок vet) выдаёт: `conversion from untyped int to string yields a string of one rune, not a string of digits`.

Правильно: `strconv.Itoa(65)` или `fmt.Sprint(65)` для числа в виде текста и `string(rune(65))`, если действительно нужен символ.

</details>
<details><summary>Что делают встроенные min, max и clear?</summary>

Все три появились в Go 1.21. `min` и `max` принимают один или больше аргументов упорядоченного типа (числа, строки) и возвращают наименьший или наибольший: `min(3, 1, 2)` даёт 1. Для чисел с плавающей точкой учитываются особые значения: если среди аргументов есть NaN, результат NaN.

`clear` работает с мапами и слайсами по-разному. Для мапы удаляет все элементы (`len` станет 0). Для слайса **обнуляет элементы**, не меняя длину: `[1 2 3]` станет `[0 0 0]`. Полезно, чтобы отпустить указатели в переиспользуемом буфере и дать GC собрать объекты.

</details>
<details><summary>Почему изменение v в for _, v := range items не меняет слайс?</summary>

`range` по слайсу на каждой итерации **копирует** элемент в переменную цикла. Изменение `v.n` меняет копию. Для слайса структур это ещё и цена: каждая итерация копирует всю структуру.

Чтобы менять элементы, обращайся по индексу: `for i := range items { items[i].n *= 10 }`, либо храни в слайсе указатели (`[]*Item`), если элементы и так живут как отдельные объекты. С Go 1.22 переменная цикла новая на каждой итерации, но это не меняет того, что она копия.

</details>
<details><summary>Как сравнить два слайса или две мапы?</summary>

Через `==` нельзя: слайсы, мапы и функции сравниваются только с `nil`, иначе ошибка компиляции. Варианты:

- `slices.Equal(a, b)` для слайсов с comparable-элементами: одинаковая длина и попарно равные элементы. `slices.EqualFunc` для своего правила.
- `maps.Equal(m1, m2)` и `maps.EqualFunc` для мап.
- `reflect.DeepEqual` для произвольных вложенных структур, но он медленный и с сюрпризами: nil-слайс не равен пустому, а NaN не равен сам себе даже для него.

В тестах для сложных структур удобен `github.com/google/go-cmp` (`cmp.Diff` ещё и показывает разницу).

</details>
<details><summary>Что такое reflect и когда он оправдан?</summary>

Пакет `reflect` позволяет в рантайме узнать тип значения (`reflect.TypeOf`), пройтись по полям структуры, прочитать теги, вызвать метод по имени. На нём построены `encoding/json`, валидаторы, ORM.

В прикладном коде рефлексия почти всегда лишняя: она медленнее прямого кода в разы, теряет проверки компилятора (ошибки типов становятся паниками в рантайме) и плохо читается. С появлением дженериков многие старые случаи (универсальные контейнеры, `Map` и `Filter`) решаются без неё. Оправдана, когда пишешь библиотеку общего назначения, которая работает с заранее неизвестными типами пользователя: сериализация, маппинг строк базы в структуры.

</details>
<details><summary>Что такое unsafe.Pointer и чем он отличается от uintptr?</summary>

`unsafe.Pointer` это указатель на что угодно: через него можно привести `*T` к `*U` в обход системы типов. Сборщик мусора его видит, то есть объект, на который он указывает, не будет собран.

`uintptr` это просто целое число размером с адрес. GC его **не** считает ссылкой: если сохранить адрес в `uintptr`, объект могут собрать, а при перемещении стека горутины адрес устареет. Поэтому арифметику указателей делают одним выражением: `unsafe.Pointer(uintptr(p) + off)`, не сохраняя промежуточный `uintptr` в переменную.

Где встречается: zero-copy преобразования `unsafe.Slice` (с 1.17), `unsafe.String` и `unsafe.StringData` (с 1.20), низкоуровневые библиотеки. Код с `unsafe` не защищён гарантией совместимости Go 1 и может сломаться на новой версии.

</details>
<details><summary>Что такое функциональные опции (functional options)?</summary>

Паттерн для конструкторов с множеством необязательных параметров. Опция это функция, которая меняет конфигурацию:

```go
type Option func(*Server)

func WithTimeout(d time.Duration) Option { return func(s *Server) { s.timeout = d } }

func NewServer(addr string, opts ...Option) *Server {
	s := &Server{addr: addr, timeout: 30 * time.Second} // значения по умолчанию
	for _, o := range opts {
		o(s)
	}
	return s
}

srv := NewServer(":8080", WithTimeout(5*time.Second))
```

Плюсы: читаемые вызовы, разумные значения по умолчанию, новые опции не ломают API. Минусы: больше кода, чем у структуры `Config`. Для внутреннего кода часто проще передать `Config` с нулевыми значениями по умолчанию; опции хороши в публичных библиотеках (так устроены `grpc.Dial` и многие клиенты).

</details>
<details><summary>Как сделать «перечисление» (enum) в Go?</summary>

Отдельного enum в языке нет. Идиома: свой целый тип и константы через `iota`:

```go
type Status int

const (
	StatusUnknown Status = iota // нулевое значение: «не задано»
	StatusActive
	StatusBlocked
)
```

Нулевое значение стоит сделать осмысленным (`Unknown`), чтобы забытая инициализация не превратилась в «активен». Для печати добавляют метод `String()`, руками или генератором `stringer` (`//go:generate stringer -type=Status`). Для JSON реализуют `MarshalText` и `UnmarshalText`, чтобы в API уходило `"active"`, а не `1`, и чтобы неизвестная строка давала ошибку. Компилятор не мешает записать `Status(42)`, поэтому на входе из внешнего мира значение надо проверять.

</details>
<details><summary>Что делает go generate и когда он запускается?</summary>

`go generate` ищет в файлах пакета комментарии `//go:generate команда аргументы` и выполняет эти команды. Типичные генераторы: `stringer` для `String()` у перечислений, `mockgen` для моков, `sqlc` для кода доступа к базе, `protoc` для protobuf.

Важно: `go build` и `go test` **не** запускают генерацию. Это ручной шаг разработчика, а сгенерированный код коммитят в репозиторий, чтобы сборка не зависела от установленных генераторов. Сгенерированные файлы помечают строкой `// Code generated ... DO NOT EDIT.`, по ней линтеры и ревьюеры понимают, что файл не правят руками.

</details>
<details><summary>Что такое build tags и суффиксы файлов вроде _linux.go?</summary>

Это условная компиляция. Строка `//go:build linux && amd64` в начале файла (до `package`) включает файл в сборку только при выполнении условия. Теги бывают системными (`linux`, `darwin`, `amd64`), версионными (`go1.22`), `cgo` и пользовательскими: `go test -tags=integration` включит файлы с `//go:build integration`.

Суффиксы имени работают так же без комментария: `file_linux.go` собирается только под Linux, `file_arm64.go` только под arm64, `_test.go` только в тестах. Старый синтаксис `// +build` встречается в коде до Go 1.17; сейчас пиши `//go:build`.

</details>
<details><summary>Что такое //go:embed?</summary>

Директива встраивает файлы в бинарник во время компиляции. Над переменной пакетного уровня пишут `//go:embed путь`, и тип переменной определяет форму: `string` или `[]byte` для одного файла, `embed.FS` для дерева файлов.

```go
import "embed"

//go:embed templates/*.html static
var assets embed.FS
```

Так сервис поставляется одним бинарником вместе с шаблонами, миграциями и статикой, что особенно удобно для образов `scratch` и `distroless`. Ограничения: пути относительно каталога пакета, без `..`, при встраивании каталога файлы, начинающиеся с `.` или `_`, по умолчанию пропускаются (префикс `all:` их включает; явно названный файл встраивается всегда). Для `string` и `[]byte` всё равно нужен импорт пакета `embed` (обычно `import _ "embed"`).

</details>
<details><summary>Что такое vendoring и когда нужен go mod vendor?</summary>

`go mod vendor` копирует исходники всех зависимостей в каталог `vendor/` проекта. Если `vendor/` есть и его версия Go в `go.mod` не ниже 1.14, команды `go` по умолчанию собирают из него, не обращаясь к сети и кешу модулей.

Зачем: сборка в закрытом контуре без доступа к прокси, аудит и ревью кода зависимостей в том же репозитории, защита от исчезновения зависимости. Минусы: репозиторий распухает, диффы обновлений огромные. Большинство проектов обходится без вендоринга: модульный прокси и `go.sum` уже дают воспроизводимость и защиту от подмены.

</details>
<details><summary>Что такое cgo и почему его стараются избегать?</summary>

cgo позволяет вызывать C-код из Go (`import "C"`). Цена:

- Вызов через границу Go и C намного дороже обычного вызова функции: рантайм переключает стек и сообщает планировщику, что поток ушёл в C (в Go 1.26 базовые накладные расходы снизили примерно на 30%, но они всё равно заметны).
- Ломается простая кросс-компиляция: нужен C-компилятор под целевую платформу.
- Бинарник становится динамически слинкованным с libc, и `scratch`-образ не подойдёт.
- Ошибки памяти в C роняют весь процесс, race detector и профилировщик их не видят.

Поэтому для сервисов собирают с `CGO_ENABLED=0`, а библиотеки выбирают на чистом Go (например, `modernc.org/sqlite` вместо `mattn/go-sqlite3`). Как это выглядит в Dockerfile, разобрано в уроке [Docker для Go](/m10/l01-docker).

</details>
<details><summary>Что такое инлайнинг и как узнать, встроил ли компилятор функцию?</summary>

Инлайнинг это подстановка тела маленькой функции в место вызова. Убирается накладной расход вызова, и, что важнее, открываются другие оптимизации: escape analysis видит, что значение не убегает, и оставляет его на стеке.

Компилятор Go встраивает функции, «стоимость» которых не превышает бюджета (80 узлов промежуточного представления); с PGO горячие функции получают бюджет больше. Посмотреть решения: `go build -gcflags=-m ./...` печатает `can inline f` и `inlining call to f`. Запретить встраивание для отладки или бенчмарка можно директивой `//go:noinline`. На собесе достаточно знать, что маленькие геттеры бесплатны, а вызов через интерфейс обычно не встраивается (без PGO-девиртуализации).

</details>
<details><summary>Что такое PGO в Go?</summary>

Profile-guided optimization: компилятор использует CPU-профиль реальной нагрузки, чтобы агрессивнее оптимизировать горячие места: встраивать горячие функции сверх обычного бюджета, девиртуализировать частые вызовы через интерфейс.

Работает с Go 1.21: кладёшь профиль `default.pgo` в каталог пакета `main`, и `go build` использует его автоматически (`-pgo=auto` по умолчанию). Профиль снимают с продакшена через `net/http/pprof`. По оценке команды Go (с версии 1.22, когда PGO научился девиртуализировать больше вызовов), выигрыш обычно 2-14%; в 1.21 называли 2-7%. Профиль коммитят в репозиторий; старый профиль после изменений кода не ломает сборку, просто даёт меньше пользы.

</details>
<details><summary>Что такое GODEBUG и директива //go:debug?</summary>

`GODEBUG` это переменная окружения с настройками рантайма и стандартной библиотеки через запятую: `GODEBUG=gctrace=1` печатает строку на каждый цикл GC, `schedtrace=1000` показывает состояние планировщика раз в секунду.

Второе назначение: обратная совместимость. Когда Go меняет поведение (например, правила TLS или разбор URL), старое поведение часто можно вернуть настройкой GODEBUG. Значения по умолчанию зависят от строки `go` в `go.mod` главного модуля: обновил тулчейн, но не `go`-версию, и получаешь старое поведение. Переопределить можно директивой `//go:debug имя=значение` в пакете `main` или блоком `godebug` в `go.mod`.

</details>
<details><summary>Что такое false sharing?</summary>

Процессор кеширует память строками (обычно 64 байта). Если две горячие переменные, которые меняют разные ядра, лежат в одной строке кеша, каждое изменение инвалидирует строку у другого ядра. Логически данные независимы, а физически ядра постоянно перекидывают строку друг другу, и производительность падает в разы.

Пример: массив счётчиков `[8]atomic.Int64`, где каждый воркер обновляет свой элемент. Лечится выравниванием: между полями добавляют отступ до размера строки кеша (`_ [56]byte`), как сделано внутри рантайма Go. Делать это стоит только после того, как профилирование показало проблему.

</details>
<details><summary>Когда нужен sync.Cond, а когда хватит канала?</summary>

`sync.Cond` это «ждать, пока условие над данными под мьютексом станет истинным». Горутина берёт мьютекс, проверяет условие в цикле и вызывает `Wait` (он атомарно отпускает мьютекс и засыпает). Тот, кто меняет данные, вызывает `Signal` (разбудить одного) или `Broadcast` (всех).

Канал проще и безопаснее в большинстве случаев: одноразовый сигнал это `close(ch)`, передача работы это буферизованный канал. Cond оправдан, когда условие сложное и многократное, а состояние уже защищено мьютексом: ограниченная очередь с ожиданием «есть место» и «есть элемент», многократный broadcast. Минус Cond: он не работает с `select`, то есть его нельзя совместить с таймаутом или отменой через context.

</details>
<details><summary>Что такое singleflight и от какой проблемы он спасает?</summary>

`golang.org/x/sync/singleflight` схлопывает одновременные одинаковые запросы в один. Если десять горячих горутин одновременно запрашивают ключ, которого нет в кеше, без защиты все десять пойдут в базу (cache stampede). С `singleflight.Group.Do(key, fn)` первая горутина выполнит `fn`, остальные подождут и получат тот же результат; третий результат `shared` скажет, что значение разделено.

Это одно из лекарств от cache stampede, другие (распределённая блокировка на пересчёт, разброс TTL, раннее фоновое обновление) в уроке [Redis и кеширование](/m07/l09-redis). Важные детали: схлопываются только вызовы, которые пересекаются по времени (это не кеш); ошибка тоже разделяется на всех ждущих; если `fn` зависнет, зависнут все (поэтому есть `DoChan`, с которым можно ждать в `select` с таймаутом).

</details>
<details><summary>Что делает runtime.Goexit?</summary>

Завершает текущую горутину, **выполнив все её defer**, но без паники. `recover` в отложенных функциях вернёт `nil`, потому что паники нет. Именно так работают `t.Fatal` и `t.FailNow` в тестах: они вызывают `runtime.Goexit`, поэтому их нельзя вызывать из горутин, запущенных тестом, иначе завершится не тест, а эта горутина.

Если вызвать `Goexit` в главной горутине, программа не завершится сразу: она продолжит работу, пока работают другие горутины, а когда их не останется, упадёт с `fatal error: no goroutines (main called runtime.Goexit) - deadlock!`.

</details>
<details><summary>Что возвращают len(ch) и cap(ch) и можно ли на них полагаться?</summary>

`cap(ch)` это размер буфера (0 для небуферизованного), `len(ch)` это число элементов, которые сейчас лежат в буфере. Для `nil`-канала оба 0.

Для логики синхронизации `len` бесполезен: между проверкой `if len(ch) < cap(ch)` и отправкой другая горутина может заполнить буфер, это классическая гонка «проверил, потом сделал» (check-then-act). Неблокирующая отправка делается через `select` с `default`. `len(ch)` годится для метрик и отладки: например, экспортировать заполненность очереди в Prometheus.

</details>
<details><summary>Сколько горутин создаёт сервер net/http?</summary>

`http.Server.Serve` в цикле принимает соединения и на каждое запускает горутину `go c.serve(ctx)`. Для HTTP/1.1 запросы внутри одного соединения обрабатываются последовательно в этой горутине. Для HTTP/2 соединение одно, но на каждый поток (stream) запускается своя горутина обработчика, поэтому запросы одного клиента идут параллельно.

Следствия: обработчик обязан быть потокобезопасным (общие данные под мьютексом), паника в обработчике ловится сервером и рвёт только это соединение, а утечка горутины внутри обработчика (забытый канал) копится с каждым запросом. Лимита на число соединений по умолчанию нет: его задают на балансировщике или через `netutil.LimitListener`.

</details>
<details><summary>Почему maps.Keys не возвращает слайс? Как получить ключи по порядку?</summary>

С Go 1.23 `maps.Keys` и `maps.Values` возвращают итератор `iter.Seq[K]`, а не слайс. Итератор ленивый: если нужно найти первый подходящий ключ, весь слайс не строится. Порядок обхода, как и у `range` по мапе, не определён.

Нужен слайс: `slices.Collect(maps.Keys(m))`. Нужен отсортированный: `slices.Sorted(maps.Keys(m))`, это стандартный способ получить детерминированный вывод, например для логов или golden-файлов в тестах.

</details>
<details><summary>Что делает iter.Pull и когда он нужен?</summary>

Итератор `iter.Seq` работает в режиме «push»: он сам вызывает `yield` для каждого элемента, а `range` подставляет тело цикла. Это удобно, пока обходишь одну последовательность. Если нужно идти по двум последовательностям одновременно (слить два отсортированных потока, сравнить попарно), push-модель мешает.

`iter.Pull(seq)` превращает его в «pull»: возвращает `next()`, который отдаёт следующий элемент и `ok`, и `stop()`, который нужно вызвать, если не дочитал до конца (иначе останется висящая сопрограмма). Внутри рантайм использует облегчённое переключение между горутинами, поэтому `Pull` дороже обычного `range`: брать его только когда без него никак.

</details>
<details><summary>Что такое дженерик-алиасы типов?</summary>

С Go 1.24 алиас может иметь параметры типа: `type Set[T comparable] = map[T]struct{}`. Алиас это другое имя того же типа, а не новый тип: `Set[string]` и `map[string]struct{}` взаимозаменяемы, и методы к алиасу добавить нельзя.

Где пригодится: при переносе типа между пакетами (старое имя становится алиасом нового, и пользователи не ломаются) и для коротких имён громоздких типов. Если нужны свои методы, нужен определённый тип: `type Set[T comparable] map[T]struct{}` без знака `=`.

</details>
<details><summary>Что такое unique.Make?</summary>

Пакет `unique` (Go 1.23) интернирует значения: `unique.Make(v)` возвращает `Handle[T]`, и для равных значений хендлы равны. Сравнение хендлов это сравнение указателей, то есть O(1) даже для длинных строк, а в памяти хранится одна копия значения.

Применение: много повторяющихся строк (имена тегов метрик, коды стран, IP-адреса в `net/netip` построены на нём), частые сравнения. Интернированные значения не живут вечно: когда хендлов на значение не осталось, рантайм его освобождает. Получить значение обратно: `h.Value()`.

</details>
<details><summary>Что такое weak.Pointer и runtime.AddCleanup?</summary>

Оба появились в Go 1.24. `weak.Make(p)` создаёт **слабый** указатель: он не удерживает объект от сборки мусора. `wp.Value()` вернёт исходный указатель, пока объект жив, и `nil` после его сборки. Применение: кеши и канонизация, которые не должны держать память.

`runtime.AddCleanup(ptr, fn, arg)` регистрирует функцию, которую рантайм вызовет после того, как объект станет недостижим. Это замена `runtime.SetFinalizer` с меньшим числом ловушек: к объекту можно привязать несколько cleanup, они не «воскрешают» объект и не мешают собирать циклы. Главное правило: `fn` и `arg` не должны ссылаться на сам `ptr`, иначе объект никогда не станет недостижимым. Ни финализаторы, ни cleanup не гарантируют запуск, поэтому ресурсы закрывают явно через `Close`.

</details>
<details><summary>Что такое testing/synctest?</summary>

Пакет для тестирования конкурентного кода с фейковым временем, стабилен с Go 1.25. `synctest.Test(t, func(t *testing.T) {...})` запускает функцию в «пузыре»: у горутин внутри своё виртуальное время, которое стоит на месте, пока хоть одна горутина работает, и мгновенно прыгает вперёд, когда все заблокированы. `time.Sleep(time.Hour)` занимает микросекунды реального времени, а результаты детерминированы.

`synctest.Wait()` ждёт, пока все горутины пузыря заблокируются: удобно проверить состояние «после того, как всё устаканилось» без `time.Sleep`. Если по завершении теста в пузыре остались навсегда заблокированные горутины, тест падает: так ловятся утечки. В Go 1.27 добавили `synctest.Sleep`, это `time.Sleep` плюс `Wait`.

</details>
<details><summary>Зачем t.Context() в тестах?</summary>

С Go 1.24 у `testing.T` (и `B`, `F`) есть метод `Context()`: он возвращает контекст, который отменяется прямо перед запуском функций, зарегистрированных через `t.Cleanup`. Раньше в каждом тесте писали `ctx, cancel := context.WithCancel(context.Background()); defer cancel()`.

Польза не только в краткости: фоновые горутины, запущенные тестом с этим контекстом, получат отмену до того, как cleanup начнёт закрывать базу или сервер. Порядок «сначала остановить работу, потом убрать ресурсы» получается сам.

</details>
<details><summary>Аллоцирует ли m[string(b)], если b это []byte?</summary>

Нет. Обычно `string(b)` копирует байты в новую строку, потому что строка неизменяема, а слайс можно поменять. Но компилятор распознаёт частые случаи, где копия не нужна, потому что строка не переживает выражение: поиск в мапе `m[string(b)]` и сравнение `string(b) == "x"`. В этих случаях байты используются напрямую. Проверить: `testing.AllocsPerRun(100, func() { _ = m[string(b)] })` вернёт 0.

Запись `m[string(b)] = v` аллоцирует: ключ остаётся в мапе, ему нужна своя копия. На собесе это хороший пример того, что «под капотом» компилятор умнее наивной модели.

</details>
<details><summary>Как сделать структуру «неизменяемой» для внешнего кода?</summary>

Ключевого слова для этого нет. Приёмы:

- Поля с маленькой буквы, доступ только через методы-геттеры, конструктор, который проверяет инварианты.
- Методы на значении (value receiver), которые возвращают новую копию вместо изменения: `func (m Money) Add(o Money) Money`.
- **Защитные копии** ссылочных полей: геттер слайса или мапы возвращает `slices.Clone(s.items)`, конструктор копирует входной слайс. Иначе вызывающий сохранит ссылку на тот же массив и изменит «неизменяемый» объект.

Строки в Go неизменяемы сами по себе, поэтому поле `string` защищать не нужно; слайсы, мапы и указатели нужно.

</details>
<details><summary>Чем errors.AsType лучше errors.As?</summary>

`errors.AsType[E error](err) (E, bool)` появился в Go 1.26. Он делает то же, что `errors.As`, но тип передаётся параметром типа, а результат возвращается значением:

```go
// раньше
var pe *fs.PathError
if errors.As(err, &pe) { use(pe) }

// с Go 1.26
if pe, ok := errors.AsType[*fs.PathError](err); ok { use(pe) }
```

Плюсы: не нужно заранее объявлять переменную, переменная живёт только внутри `if`, ошибки вроде «передал не указатель» ловит компилятор, а не паника в рантайме, и работает быстрее (без рефлексии).

</details>
<details><summary>Что нового в Go 1.26 и 1.27, о чём стоит знать на собесе?</summary>

**Go 1.26:** встроенная `new` принимает выражение: `new(42)` или `Age: new(yearsSince(born))` создаёт переменную с этим значением (удобно для опциональных полей-указателей в JSON). Сборщик мусора Green Tea включён по умолчанию: обещанное снижение накладных расходов GC на 10-40% на программах с большим числом мелких объектов. `errors.AsType`, дешевле вызовы cgo, экспериментальный профиль утечек горутин.

**Go 1.27:** дженерик-методы (у метода могут быть свои параметры типов, но не у методов интерфейсов), профиль `goroutineleak` стал стабильным (в том числе эндпоинт `/debug/pprof/goroutineleak`), новые пакеты `encoding/json/v2` и `uuid` в стандартной библиотеке, ускорение мелких аллокаций.

Полезно знать и про более ранние вехи: переменная цикла на итерацию и `range` по числу (1.22), итераторы (1.23), swiss-таблицы в map (1.24), `WaitGroup.Go` и GOMAXPROCS с учётом cgroup (1.25). Если спросят «что нового», назови пару пунктов и объясни, зачем они нужны, это ценнее перечисления.

</details>
